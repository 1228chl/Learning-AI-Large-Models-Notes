# AI 大模型岗位简历与面试稿准备指南

> **资料索引**：请先阅读 `00_使用说明_先看这个.md`  
> **本文件类型**：阅读材料（简历五维 ↔ 面试五维如何互相证明）  
> **下一步**：简历和面试对得上后，进入 `04` 跟学；时间紧可跳过本文，优先 `01`→`04`

> 适用对象：黑马程序员 AI 大模型班学员  
> 适用岗位：AI 应用开发工程师、RAG/Agent 开发工程师、NLP 应用工程师、大模型应用工程师  
> 核心目标：不是让大家背一篇“标准答案”，而是帮助每个人建立一套完整、可信、经得住追问的面试表达体系。

---

## 一、为什么要按照这五个维度准备

黑马程序员统一要求大家从以下五个部分准备：

1. 自我介绍
2. 个人工作履历
3. 项目讲解
4. 技术讲解
5. 项目优化

这五个部分并不是随意拼出来的，它们基本对应了面试官判断候选人的完整过程。

| 准备维度 | 面试官真正想判断的问题 |
|---|---|
| 自我介绍 | 你是谁？你适不适合这个岗位？ |
| 个人工作履历 | 你的经历是否连续、合理、可信？ |
| 项目讲解 | 你到底做过什么？是否真正具备解决业务问题的能力？ |
| 技术讲解 | 你是会调用接口，还是理解技术原理和使用边界？ |
| 项目优化 | 你是否具备发现问题、分析问题和持续改进系统的能力？ |

可以把这五部分理解为一条递进的“面试判断链”：

> **岗位匹配 → 经历可信 → 项目能做 → 技术能讲 → 系统能优化**

只准备其中一部分通常是不够的。

例如：

- 只会自我介绍，但项目讲不清楚，面试官会认为“表达不错，但技术能力不确定”。
- 项目能背出来，但工作履历前后矛盾，面试官会怀疑经历真实性。
- 会讲技术名词，但讲不出业务场景，面试官会认为“只学过知识点，没有工程经验”。
- 能讲项目功能，但不知道项目有哪些问题、如何优化，面试官会认为“只完成过课程作业，没有生产意识”。

因此，这套框架的价值不只是帮助大家“写简历”，而是帮助大家把简历中的每一句话，扩展成一套可以应对追问的证据链。

## 二、先明确：简历和面试逐字稿不是同一份东西

### 1. 简历的作用

简历不是技术说明书，也不是项目文档。

简历的作用是：

- 让招聘人员快速判断你是否匹配岗位；
- 给面试官提供可以继续追问的线索；
- 用有限篇幅展示最有价值的经历和能力；
- 帮助你获得面试机会。

因此，简历应该做到：

- 内容精炼；
- 重点突出；
- 与岗位匹配；
- 尽量量化；
- 每一条都能展开解释。

### 2. 面试逐字稿的作用

面试逐字稿不是让大家在面试时机械背诵，而是帮助大家提前完成以下工作：

- 梳理经历；
- 统一项目口径；
- 准备表达顺序；
- 发现简历漏洞；
- 预判面试官追问；
- 降低紧张时的大脑负担。

简历上可能只写一行：

> 基于 LangGraph 构建多 Agent 协作流程，实现任务拆解、状态管理和人工审核。

但面试时至少要能继续讲清楚：

- 为什么要使用多 Agent；
- 为什么使用 LangGraph；
- 一共有几个 Agent；
- Agent 之间如何传递状态；
- 哪些节点使用条件路由；
- 如何避免死循环；
- 如何记录执行过程；
- 出现过什么问题；
- 最后如何优化。

所以要记住：

> **简历负责“引出问题”，逐字稿负责“接住问题”。**

## 三、合理包装的正确理解

找工作需要包装，但包装不等于编造。

### 可以做的包装

- 把零散经历整理成完整项目；
- 把技术操作转化成业务价值；
- 把课程项目按照企业项目的表达方式重新组织；
- 突出自己真正负责的模块；
- 使用专业、准确、统一的技术术语；
- 补齐项目背景、用户、流程、指标和问题；
- 根据不同 JD 调整技能和项目重点；
- 将“完成了什么”提升为“为什么这样做、解决了什么问题”。

例如：

原始表达：

> 用 Milvus 做了知识库。

优化表达：

> 负责知识库检索模块设计，使用 BGE-M3 生成稠密向量和稀疏向量，并基于 Milvus 实现 Hybrid Search，通过 WeightedRanker 融合双路召回结果，再使用 BGE Reranker 完成精排。

### 不能做的包装

- 编造不存在的公司；
- 编造无法解释的岗位和职责；
- 编造自己完全没有参与过的核心模块；
- 编造无法自洽的高并发、大规模用户量和性能指标；
- 写上自己完全不会的技术；
- 项目时间、工作履历和技术版本明显冲突；
- 所有人使用完全相同的项目描述和问题案例。

包装的底线是：

> **表达可以优化，经历可以重组，项目可以深化，但面试时必须能够讲清楚、经得住追问。**

# 四、第一部分：自我介绍

## 1. 为什么要准备自我介绍

自我介绍并不是让你从姓名、年龄、学校开始念简历。

面试官主要通过自我介绍判断三件事：

1. 你是否知道自己应聘什么岗位；
2. 你的经历和岗位是否匹配；
3. 接下来应该重点问你什么。

一段好的自我介绍，本质上是在主动引导面试方向。

如果自我介绍没有重点，面试官只能随机提问；如果自我介绍结构清楚，面试官通常会沿着你最擅长的项目继续问。

## 2. 应该准备哪些内容

建议按照以下结构准备：

### 第一段：个人定位

说明：

- 自己目前的职业方向；
- 有多少年相关开发或项目经验；
- 当前主要应聘什么岗位。

例如：

> 我目前主要从事 AI 大模型应用开发，方向集中在 RAG、Agent 工作流和企业知识库问答系统。

### 第二段：核心能力

选择与目标岗位最相关的 3～4 项能力，例如：

- Python 后端开发；
- FastAPI；
- LangChain / LangGraph；
- RAG；
- Milvus / Qdrant；
- Prompt Engineering；
- 模型调用与结构化输出；
- Docker 部署；
- Redis / MySQL / PostgreSQL。

不要把所有学过的技术都念一遍。

### 第三段：代表项目

用 2～3 句话介绍最重要的项目：

- 项目解决什么业务问题；
- 自己负责什么；
- 使用了哪些关键技术；
- 有什么可展示的结果。

### 第四段：岗位匹配

最后说明：

- 为什么投递这个岗位；
- 自己能为岗位提供什么价值；
- 希望继续发展的方向。

## 3. 准备到什么程度

建议准备三个版本：

- **30 秒版本**：招聘人员电话沟通、时间很短时使用；
- **60～90 秒版本**：正常技术面试开场；
- **2 分钟版本**：面试官明确让你详细介绍自己时使用。

合格标准：

- 不看稿可以完整讲完；
- 不超过 2 分钟；
- 能自然引出自己的核心项目；
- 不出现明显背诵腔；
- 不重复朗读简历；
- 每一句都与目标岗位有关。

## 4. 常见问题

### 问题一：从出生经历开始讲

错误方式：

> 我叫某某，来自某地，毕业于某学校，我性格开朗……

这些内容通常不能帮助面试官判断岗位能力。

### 问题二：罗列技术名词

错误方式：

> 我会 Python、Java、MySQL、Redis、Docker、Kubernetes、LangChain、LangGraph、Dify、Coze……

技术越多，面试官可追问的范围越大。不会的技术不要主动送给面试官。

### 问题三：没有项目主线

介绍结束后，面试官不知道你真正擅长什么，只能随机提问。

### 问题四：说得过满

例如：

- 精通大模型；
- 精通 LangGraph；
- 独立完成企业级系统；
- 熟练掌握所有主流模型。

对于初入行学员，更稳妥的表达是：

- 熟悉；
- 掌握常见使用方式；
- 在项目中负责；
- 能够独立完成某个具体模块。

# 五、第二部分：个人工作履历

## 1. 为什么要准备工作履历

工作履历是面试可信度的重要来源。

面试官会关注：

- 每一段经历的时间是否连续；
- 岗位变化是否合理；
- 技术转型是否有过程；
- 项目与公司业务是否匹配；
- 你的职责是否符合当时的岗位级别；
- 离职原因是否合理；
- 简历内容能否互相印证。

很多学员项目讲得不错，但一到履历部分就出现：

- 时间记不清；
- 项目顺序混乱；
- 公司业务说不清；
- 职位和工作内容不匹配；
- 转行原因前后矛盾；
- 离职原因过于负面；
- 空窗期无法解释。

这些问题会直接影响面试官对整份简历的信任。

## 2. 每段履历要准备什么

每一段经历至少要能讲清楚以下内容：

1. 公司或团队主要做什么业务；
2. 你所在的部门负责什么；
3. 你的岗位是什么；
4. 你主要负责哪些工作；
5. 参与过哪些项目；
6. 使用了哪些核心技术；
7. 做出了什么结果；
8. 为什么离开；
9. 这段经历与下一段经历有什么关系。

建议使用统一结构：

> **公司业务 → 团队业务 → 个人职责 → 代表项目 → 工作成果 → 离职原因**

## 3. 准备到什么程度

每段工作经历建议准备：

- **30 秒概括版**；
- **1～2 分钟详细版**；
- 3 个可能被追问的职责；
- 1 个代表项目；
- 1 个离职原因；
- 与下一段经历的衔接说明。

时间线必须做到：

- 年月准确；
- 项目时间与工作时间一致；
- 技术版本与项目时间基本一致；
- 各段经历之间没有明显冲突。

## 4. 没有正式工作经验怎么办

没有正式工作经验，不代表没有内容可以准备。

可以从以下经历中提炼：

- 实习；
- 课程实训；
- 毕业设计；
- 独立项目；
- 外包或兼职；
- 学校比赛；
- 真实业务模拟；
- 个人开源项目；
- 原行业中的业务经验。

但必须明确经历性质，不要把课程项目直接说成已经在某家公司上线运行。

可以重点强调：

- 自己负责的模块；
- 如何进行需求分析；
- 如何设计技术方案；
- 如何测试；
- 如何发现并解决问题；
- 如何进行项目迭代。

## 5. 空窗期如何准备

空窗期不应只准备一句“在学习”。

需要准备清楚：

- 为什么产生空窗；
- 空窗期做了哪些具体事情；
- 学习了哪些技术；
- 完成了哪些项目；
- 当前为什么已经具备重新求职的条件。

例如：

> 这段时间我主要完成了 AI 大模型应用方向的系统学习，并独立完成了企业知识库问答和多 Agent 项目。除了学习框架使用，我重点补充了检索、重排序、状态管理、接口开发和部署等工程能力。目前已经能够独立完成一个大模型应用项目从需求分析到接口交付的主要流程。

不要长篇解释个人困难，也不要表现出长期失去行动力。

# 六、第三部分：项目讲解

项目讲解通常是整场技术面试中最重要的部分。

对于 AI 应用开发岗位，项目往往比单独背知识点更重要，因为项目可以同时体现：

- 业务理解；
- 技术选型；
- 架构设计；
- 编码能力；
- 问题解决；
- 团队协作；
- 工程意识；
- 优化能力。

一个项目必须从以下五个方面准备：

1. 为什么做这个项目；
2. 项目整体架构；
3. 一个具体业务如何实现；
4. 至少三个项目问题及解决过程；
5. 项目还有哪些优化方向。

---

## 6.1 为什么做这个项目

### 面试官想听什么

面试官并不只想听“这是一个 RAG 项目”。

他想知道：

- 真实业务痛点是什么；
- 原来的解决方式有什么问题；
- 为什么需要 AI；
- 为什么选择 RAG、Agent 或模型分类；
- 项目的用户是谁；
- 项目最终解决了什么问题。

### 推荐表达结构

> **业务场景 → 原有问题 → 用户需求 → 方案目标 → 项目价值**

例如，企业知识库项目不要只说：

> 我做了一个 RAG 问答系统。

应该讲成：

> 企业内部存在大量产品文档、操作手册和历史解决方案，员工查询信息时主要依赖人工搜索或向经验员工咨询，效率较低，而且不同人员给出的答案不一致。因此项目希望建设一个面向内部员工的知识库问答系统，让用户可以直接使用自然语言提问，并基于企业资料生成带有来源依据的答案。

### 准备到什么程度

至少能回答：

- 谁提出了需求；
- 谁使用；
- 原流程是什么；
- 原流程有什么问题；
- 为什么不能直接使用普通大模型；
- 为什么采用当前方案；
- 项目成功的判断标准是什么。

---

## 6.2 项目架构

### 面试官想听什么

项目架构主要用于判断你是否具有整体视角。

面试官会关注：

- 系统有哪些模块；
- 数据如何流动；
- 每个模块负责什么；
- 模块之间如何通信；
- 为什么这样拆分；
- 你主要负责哪里。

### 推荐讲解顺序

不要对着架构图从左到右机械念组件，而应按照一次真实请求来讲。

例如 RAG 项目：

1. 用户通过前端或 API 提交问题；
2. 后端完成身份校验、参数校验和会话识别；
3. Query Classifier 判断是否需要进入知识库检索；
4. 对问题进行改写或多路扩展；
5. 执行 Dense 和 Sparse 混合召回；
6. 通过 WeightedRanker 融合候选；
7. 使用 Reranker 精排；
8. 拼接上下文并调用大模型；
9. 通过 SSE 流式返回；
10. 保存会话记录、引用来源和执行日志。

### 准备到什么程度

必须能做到：

- 不看图也能讲清楚主流程；
- 看图时能解释每一个核心模块；
- 能说明模块之间的数据格式；
- 能说明自己负责的部分；
- 能解释至少 3 个关键技术选型；
- 能回答“为什么不用另一个方案”。

建议准备：

- 1 张总体架构图；
- 1 张核心业务流程图；
- 1 张数据流转图；
- 1 份模块职责表。

---

## 6.3 一个具体业务实现

### 为什么必须准备具体业务

很多学员讲项目时只会说：

> 使用 LangGraph 编排工作流，使用 Milvus 检索，使用 FastAPI 提供接口。

这只是技术清单，不是业务实现。

面试官需要确认你是否真正写过代码，因此通常会追问：

- 某个接口怎么实现；
- 输入和输出是什么；
- 数据经过哪些步骤；
- 使用了哪些类和方法；
- 状态如何变化；
- 异常如何处理；
- 结果如何保存；
- 如何测试。

### 推荐选择的业务

每个项目至少选择一个最能体现能力的核心业务，例如：

- 文档上传后如何完成解析、切块、向量化和入库；
- 用户问题如何完成 Query 分类和路由；
- Hybrid Search 如何完成双路召回和融合；
- Agent 如何进行任务拆解和状态流转；
- 人工审核节点如何暂停和恢复；
- 多轮会话记忆如何保存和加载；
- 模型结构化输出如何校验和重试；
- SSE 流式输出如何实现。

### 推荐讲解结构

> **输入 → 核心处理步骤 → 关键代码/组件 → 输出 → 异常处理 → 测试方式**

### 准备到什么程度

合格标准：

- 能讲清楚接口或节点的输入输出；
- 能讲清楚核心数据结构；
- 能讲出关键代码的大致逻辑；
- 能解释为什么这样实现；
- 能回答异常情况；
- 能画出流程；
- 能在白板或纸上写出伪代码；
- 能说明如何验证功能正确。

不要求逐行背代码，但必须真正理解代码。

---

## 6.4 至少三个项目问题及解决过程

### 为什么必须准备问题

真正做过项目的人，一定遇到过问题。

如果一个项目“从头到尾没有任何问题”，面试官通常会怀疑：

- 项目只是照着教程完成；
- 候选人没有参与核心部分；
- 候选人只记住了最终结果；
- 缺少真实调试经验。

面试官通过问题案例，重点判断：

- 你能否发现问题；
- 是否会定位原因；
- 是否有分析过程；
- 是否比较过不同方案；
- 是否验证了解决效果；
- 是否进行了复盘。

### 问题案例的正确结构

建议使用以下结构：

> **现象 → 影响 → 排查过程 → 根因 → 解决方案 → 验证结果 → 后续预防**

不要只说：

> 检索不准确，后来加了 Reranker，效果变好了。

应该说明：

- 哪些问题回答不准确；
- 错误来自召回还是生成；
- 如何通过日志和测试集判断；
- 原因是关键词匹配不足、切块不合理，还是 Top-K 设置不合理；
- 尝试过哪些方案；
- 为什么最终选择当前方案；
- 使用什么指标或案例验证；
- 后续如何防止同类问题再次出现。

### 三类问题建议

每个项目至少准备三类不同问题，避免三个问题都只是“改了参数”。

#### 第一类：业务或数据问题

例如：

- 用户问题表达模糊；
- 文档格式复杂；
- 数据质量差；
- 类别不平衡；
- 私有知识与通用知识难以区分；
- 文档更新后旧向量未清理。

#### 第二类：技术或效果问题

例如：

- Dense 检索漏掉 API 名称；
- Sparse 检索无法理解同义表达；
- Reranker 延迟过高；
- 模型输出格式不稳定；
- Agent 出现循环调用；
- 长上下文导致答案偏移；
- 分类阈值设置不合理。

#### 第三类：工程或稳定性问题

例如：

- 并发请求导致共享状态污染；
- SSE 中途断开；
- 模型接口超时；
- Redis 缓存不一致；
- 数据库连接未释放；
- 上传大文件导致内存占用过高；
- 服务重启后任务状态丢失。

### 准备到什么程度

每个问题至少准备 1～2 分钟。

三个问题不能完全相同，应体现不同层面的能力：

1. 一个效果问题；
2. 一个工程问题；
3. 一个业务或数据问题。

每个问题都要有真实的排查过程，不能只背最终答案。

# 七、第四部分：技术讲解

## 1. 为什么项目之外还要单独准备技术讲解

项目可以证明你使用过技术，但不能完全证明你理解技术。

例如，简历写了：

- RAG；
- LangGraph；
- Milvus；
- Redis；
- FastAPI；
- BGE-M3；
- Reranker。

面试官会继续判断：

- 你只是调用过，还是理解原理；
- 知道什么时候使用，还是只会照抄；
- 知道优缺点，还是只会讲优势；
- 能否比较不同方案；
- 能否结合业务做选型。

所以每一个写进简历的核心技术，都应该准备成一个“小专题”。

## 2. 每项技术要准备的六个维度

建议按照以下结构准备：

1. **它是什么**
2. **它解决什么问题**
3. **核心原理是什么**
4. **在项目中怎么使用**
5. **有什么优点和限制**
6. **还有哪些替代方案，为什么这样选**

例如讲 Reranker：

- 它是什么：对召回候选进行二次精排的模型；
- 解决什么问题：向量召回速度快，但排序精度有限；
- 原理：将 Query 和文档候选共同输入交叉编码模型，计算更精细的相关性分数；
- 项目中怎么用：先召回 Top-20，再精排选择 Top-3；
- 优点：提高最终上下文相关性；
- 限制：计算开销和延迟更高；
- 替代方案：只使用向量相似度、LLM 打分等；
- 选型原因：在候选数量可控时，效果与延迟较平衡。

## 3. 技术讲解准备到什么程度

每个核心技术至少准备三个层次。

### 第一层：一句话解释

能让非专业人员听懂。

### 第二层：项目使用

能说明在自己的项目中放在哪里、解决了什么问题。

### 第三层：原理与取舍

能回答：

- 为什么使用；
- 为什么不使用其他方案；
- 有什么局限；
- 参数如何设置；
- 出现问题如何排查；
- 业务变化后如何调整。

核心技术建议准备 5～8 个，不要试图把所有技术都准备成重点。

## 4. AI 大模型岗位建议重点准备的技术

根据学员常见项目，可重点准备：

- 大模型基本调用流程；
- Prompt 设计与结构化输出；
- Function Calling / Tool Calling；
- RAG 完整链路；
- 文本切块；
- Embedding；
- Dense / Sparse / Hybrid Search；
- Milvus 或 Qdrant；
- Reranker；
- Query 分类与路由；
- LangGraph 状态、节点和条件边；
- Agent 规划、执行与反思；
- 短期记忆与长期记忆；
- FastAPI；
- SSE；
- Redis；
- 数据库；
- Docker 部署；
- 日志、监控、超时、重试和降级。

# 八、第五部分：项目优化

## 1. 为什么必须准备项目优化

项目优化是区分“会做 Demo”和“具备工程意识”的关键部分。

很多学员只会讲：

> 这个功能已经实现了。

但企业更关心：

- 效果是否稳定；
- 延迟是否可接受；
- 成本是否可控；
- 并发是否支持；
- 数据是否安全；
- 出错后是否能恢复；
- 后续是否方便扩展。

项目优化反映的是候选人的成长上限。

## 2. 优化可以从哪些维度展开

### 1. 效果优化

例如：

- 优化 Prompt；
- 增加 Few-shot；
- 调整切块策略；
- 使用 Hybrid Search；
- 增加 Reranker；
- 调整 Top-K；
- 建立评测集；
- 加入查询改写；
- 增加引用来源；
- 针对 Bad Case 做专项优化。

### 2. 性能优化

例如：

- 并行调用；
- 异步处理；
- 缓存；
- 批量向量化；
- 减少重复检索；
- 模型量化；
- 调整并发数；
- 流式返回；
- 减少不必要的 LLM 调用。

### 3. 稳定性优化

例如：

- 超时；
- 重试；
- 熔断；
- 降级；
- 幂等；
- 状态持久化；
- 异常日志；
- 服务健康检查；
- 数据库连接池；
- 任务恢复。

### 4. 成本优化

例如：

- 简单问题使用小模型；
- 不需要检索的问题直接调用 LLM；
- 缓存高频结果；
- 控制上下文长度；
- 减少 Token；
- 合并请求；
- 对不同任务进行模型分级。

### 5. 安全优化

例如：

- 权限控制；
- 多租户隔离；
- 敏感信息脱敏；
- Prompt Injection 防护；
- 文件类型校验；
- 输出内容审核；
- 操作日志；
- 数据访问范围限制。

### 6. 可维护性优化

例如：

- 模块解耦；
- 配置中心；
- 统一异常处理；
- 统一日志；
- Prompt 版本管理；
- 数据版本管理；
- 自动化测试；
- 测试环境与生产环境隔离；
- 灰度发布。

## 3. 准备到什么程度

优化不能只讲想法，要区分三个层次：

### 已经完成的优化

需要讲清：

- 原问题；
- 优化方案；
- 实施过程；
- 优化结果；
- 如何验证。

### 正在进行的优化

需要讲清：

- 当前瓶颈；
- 已经验证到哪一步；
- 下一步计划；
- 存在哪些风险。

### 未来可以做的优化

可以体现思考，但不能伪装成已经完成。

推荐表达：

> 当前项目已经完成了混合检索和重排序优化。下一步如果进入真实生产环境，我会继续补充离线评测集、链路监控、Prompt 版本管理和模型调用降级机制。

这种表达既体现思考，又不会夸大实际完成程度。

# 九、准备程度的统一标准

同学们不能只以“我写完稿了”作为完成标准。

建议采用以下四级标准。

## 第一级：写得出来

- 能整理出完整稿件；
- 项目流程基本连贯；
- 技术名词基本正确。

这只是起点，还不能直接参加面试。

## 第二级：说得出来

- 不看稿可以讲；
- 表达时间基本可控；
- 没有大段停顿；
- 逻辑顺序稳定。

达到这一层，可以参加模拟面试。

## 第三级：经得住追问

- 每一句简历内容都能展开；
- 能回答“为什么”；
- 能回答“怎么做”；
- 能回答“出问题怎么办”；
- 能解释技术选型和替代方案；
- 经历、项目和技术可以互相印证。

达到这一层，才算基本具备正式面试能力。

## 第四级：可以灵活调整

- 能根据不同 JD 调整重点；
- 能根据面试官的关注方向切换项目；
- 能长讲，也能短讲；
- 能用业务语言，也能用技术语言；
- 遇到不会的问题，能基于已知内容合理分析。

这是比较成熟的面试状态。

# 十一、不同经历学员的准备重点

## 1. 有相关开发经验的同学

重点：

- 真实业务场景；
- 自己承担的职责；
- 复杂问题处理；
- 性能和稳定性；
- 项目上线与协作；
- 技术选型依据。

避免只讲培训项目，而忽略真实工作经历。

## 2. 有工作经验但准备转 AI 的同学

重点：

- 原行业经验如何迁移到 AI；
- 为什么转型；
- 已经补充了哪些能力；
- AI 项目与原业务如何结合；
- 过去的工程经验如何帮助当前岗位。

不要把过去经历全部删掉。业务理解、后端能力、数据处理和项目协作都可能成为优势。

## 3. 没有正式开发经验的同学

重点：

- 项目真实参与过程；
- 核心模块；
- 技术理解；
- 问题排查；
- 代码能力；
- 学习能力；
- 项目复盘。

不要通过夸大用户量、并发量和公司背景制造“高级感”。对于新人，面试官更看重基础是否扎实、项目是否真的做过、能否快速成长。

# 十二、常见注意事项

## 1. 所有内容必须互相一致

以下信息必须统一：

- 简历；
- 招聘平台个人资料；
- 自我介绍；
- 工作履历；
- 项目时间；
- 技术版本；
- 项目职责；
- 离职原因。

## 2. 不要所有项目都讲成一个套路

如果每个项目都是：

- 使用 FastAPI；
- 使用 LangChain；
- 使用 Milvus；
- 使用大模型；
- 提高效率。

面试官会感觉项目缺乏差异。

每个项目应突出不同能力：

- 项目一突出 RAG 检索；
- 项目二突出 Agent 工作流；
- 项目三突出 NLP 分类或模型训练；
- 项目四突出工程部署和性能优化。

## 3. 不要只背结果，不讲过程

面试官最关注的通常不是“最终用了什么”，而是：

- 你怎么发现问题；
- 为什么判断是这个原因；
- 尝试过什么；
- 为什么最终这样改；
- 如何验证。

## 4. 数据指标必须能解释

不要随意写：

- 准确率提升 30%；
- 响应速度提升 50%；
- 支持百万用户；
- 并发提升 10 倍。

如果写了指标，必须知道：

- 指标如何计算；
- 优化前是多少；
- 优化后是多少；
- 测试数据是什么；
- 测试环境是什么；
- 是否可复现。

没有完整测量时，可以使用更稳妥的表达：

- 在测试集上明显降低某类错误；
- 减少无效召回；
- 缩短平均响应时间；
- 提高输出格式稳定性；
- 降低重复模型调用。

## 5. 不会的问题不要硬编

可以这样回答：

> 这个点我在项目中没有实际使用过，所以不能给出非常确定的结论。基于我目前的理解，我会从以下几个方向分析……

这比编造答案更可靠。

## 6. 逐字稿要经过口语化处理

书面表达：

> 本项目旨在通过检索增强生成技术提升企业内部非结构化知识的利用效率。

口语表达：

> 这个项目主要解决企业内部资料很多，但员工查找效率低的问题。我们把文档处理后存入知识库，员工可以直接提问，系统检索相关资料后再让大模型回答。

面试时要像正常交流，而不是朗诵项目说明书。

# 十三、建议的课堂训练方式

## 第一轮：完成材料

要求每位同学完成：

- 60～90 秒自我介绍；
- 完整工作时间线；
- 1 个主项目逐字稿；
- 3 个项目问题；
- 5 个技术专题；
- 3 个优化方向。

## 第二轮：同桌互问

一人讲，一人只负责追问：

- 为什么；
- 怎么做；
- 为什么不用别的；
- 出问题怎么办；
- 如何验证。

只要连续追问三次后答不上来，就说明准备还不够深入。

## 第三轮：脱稿表达

要求：

- 不能照稿念；
- 项目控制在 8～12 分钟；
- 自我介绍控制在 90 秒；
- 每个问题案例控制在 1～2 分钟。

## 第四轮：压力面试

模拟以下场景：

- 面试官打断；
- 临时切换项目；
- 质疑项目真实性；
- 追问代码细节；
- 要求比较两种方案；
- 询问没有准备过的问题。

## 第五轮：根据 JD 调整

针对不同岗位重新调整：

- 自我介绍重点；
- 技能顺序；
- 项目顺序；
- 技术专题；
- 面试问题。

# 十五、最后给同学们的一段话

这五个部分不是为了把大家训练成“背稿机器”。

- 知道自己是谁；
- 知道自己做过什么；

- 知道技术是怎么工作的；
- 知道项目哪里还有问题；
- 知道下一步应该如何改进。

一份好的简历，不是看起来技术很多，而是每一句都能够成为可信的证据。

一场好的面试，也不是所有问题都回答得完美，而是让面试官看到：

> **你有真实的项目理解，有基本的技术深度，有解决问题的过程，也有继续成长的能力。**

因此，大家准备面试稿时，不要只问：

> “这句话怎么说得更高级？”

更应该问：

> “面试官听完这句话后会追问什么？我能不能继续讲清楚？”

当简历、逐字稿、项目代码、技术原理和问题案例能够互相印证时，整套面试准备才真正完成。
