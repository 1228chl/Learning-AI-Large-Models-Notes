> **资料索引**：请先阅读同文件夹下的 `00_使用说明_先看这个.md`  
> **本文件类型**：阅读材料（建立面试五段框架，建议第一个通读）

> 适用方向：AI 大模型应用开发、RAG、Agent、NLP、模型微调、智能问答、知识库、自动化工作流等岗位

# 一、为什么要按照这五个部分准备

面试通常不是随机提问，而是在不断确认五件事情：

1. **你是谁，适合什么岗位**
2. **你过去做过什么，经历是否可信**
3. **你是否真正做过项目**
4. **你是否理解项目中使用的技术**
5. **你是否具备发现问题和继续优化的能力**

因此，可以把整个面试看成一条完整的判断链：

```text
自我介绍
→ 个人履历
→ 项目讲解
→ 技术追问
→ 项目优化
```

这五个部分不是彼此独立的。

比如：

- 自我介绍中提到了 RAG，后面项目就要能讲清 RAG。
- 项目中写了 LangGraph，技术讲解就要能说明为什么使用 LangGraph。
- 项目中写了“提升了准确率”，就要能说明如何评测、优化前后如何对比。
- 项目中写了“负责整体架构”，就要能回答完整链路、模块划分和技术选型。

所以，准备面试稿的本质不是写五篇文章，而是建立一套**前后一致、能够互相证明的内容体系**。

# 二、同学们最终需要准备哪些内容

每名同学至少需要准备：

## 1. 一份 60～90 秒的自我介绍

让面试官快速知道：

- 你是谁
- 你做什么方向
- 你有什么核心能力
- 你最值得追问的项目是什么

## 2. 一份 2～3 分钟的个人履历

让面试官能够听懂：

- 你的经历顺序
- 每一阶段做了什么
- 为什么转行或换方向
- 现在为什么选择 AI 大模型岗位

## 3. 一个 8～12 分钟的主项目

主项目必须能够完整讲清：

- 为什么做
- 整体架构
- 个人职责
- 一个具体业务实现
- 至少三个真实问题
- 如何优化

## 4. 一个 3～5 分钟的备用项目

备用项目不需要像主项目一样详细，但必须能够说明：

- 项目定位
- 核心技术
- 个人负责内容
- 与主项目的区别

## 5. 三到五个重点技术

每个技术要能讲清：

- 是什么
- 为什么用
- 在项目什么位置
- 如何实现
- 有什么限制

## 6. 三个以上项目问题

问题要覆盖不同类型：

- 效果问题
- 数据问题
- 性能问题
- 稳定性问题
- 成本问题
- 多轮对话问题
- 工具调用问题
- 部署问题

## 7. 三个以上优化方向

不能只说“换大模型”，而要能从多个维度思考：

- 效果
- 性能
- 稳定性
- 成本
- 安全
- 可观测性
- 用户体验

# 三、第一部分：自我介绍怎么准备

## 1. 自我介绍的目的

自我介绍不是个人传记，也不是把简历全部念一遍。

它的作用是让面试官在 1 分钟左右快速完成定位：

```text
这个人是什么背景
→ 做过什么
→ 适合什么岗位
→ 接下来应该重点问什么
```

## 2. 推荐结构

建议按照下面五个部分准备：

```text
基本身份
→ 过去经历
→ 当前技术方向
→ 代表项目
→ 求职目标
```

## 3. 通用模板

```text
面试官您好，我叫【姓名】，毕业于【学校和专业】。

我之前主要从事或学习【原来的方向】，在这段经历中积累了
【与目标岗位相关的能力】。

目前我的求职方向是【AI 大模型应用开发 / RAG / Agent / NLP】，
已经系统学习并实践了【核心技术方向】。

我重点完成了【项目类型或项目名称】，主要解决【业务问题】，
我在项目中负责【个人职责】，重点处理了【一个有价值的难点】。

我希望应聘【岗位名称】，进一步参与【对应业务方向】的开发和优化。
```

## 4. 不同类型同学的重点

### 有开发经验的同学

重点突出：

```text
原有工程能力
+ 大模型能力
= 可以快速进入企业项目
```

例如：

- 原来做 Java，可以突出接口、数据库、微服务和部署经验。
- 原来做 Python，可以突出数据处理、后端和模型调用经验。
- 原来做算法，可以突出数据、模型、评估和调优经验。

### 转行同学

重点突出：

```text
过去能力可以迁移
→ 为什么转型
→ 做了哪些准备
→ 已经完成哪些项目
```

不要把过去经历全部隐藏，也不要强行说过去一直在做 AI。

### 应届或工作经验较少的同学

重点突出：

- 学习方向清楚
- 项目完成度高
- 能讲清具体实现
- 有主动学习和解决问题的能力

## 5. 自我介绍要准备到什么程度

至少能够应对以下追问：

- 你为什么转 AI？
- 为什么选择大模型应用开发？
- 你最擅长的方向是什么？
- 你认为自己最有竞争力的能力是什么？
- 你做过的项目中哪个最能代表你？
- 你为什么适合我们这个岗位？

## 6. 常见问题

### 问题一：介绍太长

自我介绍超过 3 分钟，容易变成简历朗读。

### 问题二：只有技术名词

例如：

```text
我会 Python、LangChain、LangGraph、Redis、MySQL、Milvus、vLLM……
```

这不能说明能力，只是在念工具名称。

### 问题三：没有个人定位

面试结束后，面试官仍然不知道你更适合：

- RAG
- Agent
- NLP
- 模型部署
- 后端开发

### 问题四：使用无法证明的词

尽量少使用：

- 精通
- 专家级
- 全面掌握
- 深入掌握所有原理
- 独立负责全部项目

更稳妥的表达是：

- 熟悉
- 有实际使用经验
- 重点负责
- 能够完成
- 在项目中使用过

# 四、第二部分：个人工作履历怎么准备

## 1. 履历讲解的目的

面试官通过履历主要判断：

- 时间线是否合理
- 经历是否真实
- 每段经历做了什么
- 能力是如何形成的
- 离职和空窗期是否可以解释
- 当前求职方向是否稳定

## 2. 每段经历的通用结构

每一段工作、实习或学习经历，都可以按照四句话准备：

```text
这是什么阶段
→ 我承担什么职责
→ 我做了什么事情
→ 我获得了什么能力
```

## 3. 通用模板

```text
在【时间】到【时间】期间，我在【公司 / 学校 / 培训阶段】
主要从事【业务或学习方向】。

我的主要职责是【职责一】、【职责二】和【职责三】。

期间我参与或完成了【项目 / 任务】，主要负责【具体工作】，
最终实现了【真实结果】。

这段经历让我积累了【可以迁移到目标岗位的能力】。
```

## 4. 不同经历如何连接

履历不能只是把几家公司依次念出来，要形成成长逻辑。

例如：

```text
第一阶段：掌握基础开发能力
第二阶段：接触数据或算法任务
第三阶段：开始大模型项目实践
第四阶段：明确 AI 应用开发方向
```

面试官听完后，应该能够理解：

> 你为什么会走到现在这个方向。

## 5. 转行经历怎么讲

正确逻辑：

```text
原岗位做了什么
→ 哪些能力可以迁移
→ 为什么选择 AI
→ 具体做了哪些准备
→ 当前已经具备什么能力
```

错误逻辑：

```text
我以前的工作没什么用，所以我重新开始学习 AI。
```

这种表达会否定自己的过去，也会让面试官担心你以后再次轻易换方向。

## 6. 空窗期怎么讲

空窗期不需要回避，但必须说明自己做了什么。

通用模板：

```text
这段时间我没有正式就职，主要用于调整职业方向。

期间我系统补充了【技术】，完成了【项目】，
同时针对【目标岗位】进行了简历、面试和技术准备。

目前我的方向已经比较明确，希望进入【岗位】继续积累真实业务经验。
```

## 7. 履历要准备到什么程度

每一段经历都要能回答：

- 公司或团队做什么业务？
- 你所在部门做什么？
- 你的岗位职责是什么？
- 每天主要做什么？
- 你参与了什么项目？
- 你和其他成员如何分工？
- 你做出的结果是什么？
- 为什么离职？
- 这段经历对现在有什么帮助？

## 8. 注意事项

### 不要虚构

不能虚构：

- 公司
- 工作时间
- 项目
- 团队人数
- 职责
- 指标
- 客户
- 上线情况

### 不要把课程项目说成商业项目

可以说：

- 课程项目
- 个人项目
- 模拟企业项目
- 功能验证项目

项目本身有价值，不需要靠虚构商业背景来证明。

### 不要把所有事情都说成自己负责

企业项目通常有明确分工。

比“我负责全部项目”更可信的说法是：

```text
我主要负责检索链路和问答流程，
前端和部分基础设施由其他成员负责。
```

# 五、第三部分：项目讲解怎么准备

项目讲解通常是技术面试最核心的部分。

项目准备得好，面试官会认为你有实际能力。

项目准备得不好，即使背了很多八股文，也很难证明你能做事。

# 六、项目第一问：为什么要做这个项目

## 1. 面试官想听什么

面试官不是只想知道项目名称，而是想判断：

- 你是否理解业务
- 这个项目是不是为了使用技术而强行设计
- 项目解决了什么真实问题
- 大模型在其中有没有必要

## 2. 推荐结构

```text
业务场景
→ 原有方式
→ 原有问题
→ 目标用户
→ 项目方案
→ 项目价值
```

## 3. 通用模板

```text
这个项目主要面向【用户或部门】。

在项目建设前，用户通常通过【原有方式】完成【任务】，
但存在【效率、成本、准确性、体验等问题】。

因此，我们设计了【项目类型】，通过【核心方案】
解决【具体问题】。

这个项目的价值主要体现在【减少人工、提升效率、
统一信息、提高准确率、改善用户体验】。
```

## 4. 不同项目如何思考项目背景

### RAG 项目

重点思考：

- 为什么不能只用通用大模型？
- 企业知识在哪里？
- 原来的查找方式有什么问题？
- 为什么需要引用来源？
- 为什么需要权限隔离？

### Agent 项目

重点思考：

- 为什么一个模型调用不能完成？
- 是否需要多步骤执行？
- 是否需要调用工具？
- 是否存在条件判断、循环和状态？
- 是否需要多个专业能力协同？

### NLP 分类项目

重点思考：

- 原来是否人工分类？
- 数据量和处理速度是多少？
- 错误分类会带来什么影响？
- 为什么需要训练专用模型？
- 为什么不能直接使用大模型全量处理？

### 模型微调项目

重点思考：

- 基础模型哪里不满足业务？
- Prompt 是否已经尝试过？
- RAG 是否适合这个问题？
- 微调要改变模型什么能力？
- 是否有足够高质量数据？

### 多模态项目

重点思考：

- 为什么文字不够？
- 图像、音频或视频提供了什么信息？
- 多模态结果如何进入业务流程？
- 如何进行效果评测？

## 5. 项目背景要准备到什么程度

至少能够回答：

- 项目的真实用户是谁？
- 项目解决什么问题？
- 原来的方案是什么？
- 为什么要使用大模型？
- 不用大模型能不能做？
- 项目成功的标准是什么？
- 项目目前处于 Demo、测试还是生产阶段？

# 七、项目第二问：项目架构怎么讲

## 1. 项目架构不是技术栈列表

错误表达：

```text
项目使用了 Python、FastAPI、LangChain、LangGraph、
Redis、MySQL、Milvus、Docker……
```

正确表达：

```text
一个用户请求进入系统后，依次经过哪些模块，
每个模块负责什么，数据如何发生变化。
```

## 2. 项目架构的通用拆解方法

几乎所有 AI 大模型应用，都可以从下面几个层次进行拆解：

```text
用户与接入层
→ 业务编排层
→ AI 能力层
→ 数据与存储层
→ 服务与部署层
→ 监控与评测层
```

## 3. 每层应该讲什么

### 第一层：用户与接入层

可能包含：

- Web 或 App
- API 接口
- FastAPI
- 参数校验
- 身份认证
- 会话 ID
- SSE 或 WebSocket

回答：

- 请求从哪里进入？
- 返回方式是什么？
- 如何处理异常参数？

### 第二层：业务编排层

可能包含：

- 普通 Python 逻辑
- LangChain
- LangGraph
- 工作流
- Agent
- 路由
- 状态管理

回答：

- 系统如何决定下一步做什么？
- 哪些步骤是固定的？
- 哪些步骤由模型决策？
- 状态如何传递？

### 第三层：AI 能力层

可能包含：

- 大模型
- Embedding 模型
- Reranker
- 分类模型
- OCR
- ASR
- 多模态模型
- 微调模型

回答：

- 每个模型具体负责什么？
- 为什么选这个模型？
- 输入输出是什么？

### 第四层：数据与存储层

可能包含：

- MySQL
- Redis
- Elasticsearch
- Milvus
- Qdrant
- 对象存储
- 日志系统

回答：

- 每种数据存在哪里？
- 为什么这样存？
- 数据生命周期是什么？
- 如何更新？

### 第五层：服务与部署层

可能包含：

- Docker
- Nginx
- vLLM
- GPU
- CPU 服务
- 异步队列
- Celery

回答：

- 模型如何部署？
- 接口如何暴露？
- 如何处理并发？
- 如何超时和重试？

### 第六层：监控与评测层

可能包含：

- 日志
- Trace
- 指标面板
- 离线评测
- badcase 平台
- 人工审核

回答：

- 如何知道系统是否正常？
- 如何知道效果是否变差？
- 如何定位某一次失败？

## 4. 项目架构讲解模板

```text
整个项目可以分为【几层】。

第一层是【接入层】，主要负责【职责】。

第二层是【核心业务层】，主要负责【职责】。

第三层是【AI 能力层】，包含【模型或检索能力】，
分别用于【具体作用】。

第四层是【数据层】，其中【存储一】负责【数据】，
【存储二】负责【数据】。

一次完整请求的流程是：
【从用户输入开始，按照顺序讲到结果返回】。

我在项目中主要负责【个人模块】，
重点完成了【具体工作】。
```

## 5. 架构要准备到什么程度

必须能够回答：

- 请求完整链路是什么？
- 每一步输入和输出是什么？
- 模块之间如何通信？
- 为什么这样分层？
- 哪些步骤可以并行？
- 哪些步骤必须串行？
- 某个模块失败怎么办？
- 数据存在哪里？
- 模型在哪里部署？
- 你的个人职责在哪里？

# 八、项目第三问：如何讲一个具体业务实现

## 1. 为什么必须准备一个具体业务

很多同学能讲项目架构，但一问：

> 用户真正发起一次请求时，系统具体怎么跑？

就讲不下去了。

这说明只记住了架构图，没有理解业务流程。

## 2. 选择业务案例的标准

优先选择：

- 能体现核心技术
- 能覆盖多个模块
- 个人参与较多
- 容易出现异常情况
- 面试官容易理解

不要选择：

- 只有一个接口调用
- 自己没有参与
- 只能讲产品效果
- 无法讲输入输出

## 3. 通用“七步法”

```text
用户输入
→ 接口接收
→ 业务判断
→ 模型或工具处理
→ 中间结果
→ 结果校验
→ 返回用户
```

## 4. 通用模板

```text
以【业务场景】为例。

第一步，用户输入【内容】。

第二步，系统通过【接口】接收请求，
并完成【鉴权、参数校验、会话处理】。

第三步，系统根据【规则、分类模型或大模型】
判断用户意图，并决定进入【流程】。

第四步，系统调用【检索、模型、Agent 或工具】，
中间会生成【结构化数据、候选结果或状态】。

第五步，系统对结果执行【排序、校验、过滤、聚合】。

第六步，如果结果满足条件，就通过【SSE / 普通 HTTP / WebSocket】
返回用户。

第七步，如果出现【参数缺失、检索为空、模型失败、工具超时】，
系统会执行【追问、重试、降级或人工处理】。
```

# 九、项目第四问：三个问题怎么准备

## 1. 为什么要求至少三个问题

项目能跑起来，只能说明完成了功能。

真正体现能力的是：

```text
出现问题
→ 发现问题
→ 分析问题
→ 解决问题
→ 验证结果
```

如果项目从头到尾“完全没有问题”，通常说明：

- 项目做得太浅
- 没有认真测试
- 没有记录 badcase
- 只是照着教程运行

## 2. 问题不能全部是同一类型

建议至少准备：

### 问题一：效果类

例如：

- 检索不到正确内容
- 分类准确率低
- 模型容易幻觉
- 工具选择错误
- 结构化输出错误

### 问题二：性能或成本类

例如：

- 响应时间太长
- 模型调用次数过多
- Token 消耗太高
- 检索速度慢
- 并发能力不足

### 问题三：工程稳定性类

例如：

- 外部接口超时
- Agent 陷入循环
- JSON 解析失败
- 缓存不一致
- 长任务阻塞
- 服务重启后状态丢失

还可以准备：

- 数据类问题
- 多轮记忆问题
- 权限安全问题
- 部署显存问题
- 用户体验问题

## 3. 每个问题统一使用“六步法”

```text
问题现象
→ 如何发现
→ 如何定位
→ 根本原因
→ 解决方案
→ 验证方式
```

## 4. 通用模板

```text
当时遇到的问题是【现象】。

这个问题是通过【日志、测试集、用户反馈、人工抽检、监控指标】
发现的。

我们先排查了【可能原因】，最终定位到【根本原因】。

针对这个问题，我们尝试了【方案一】和【方案二】，
最终选择【最终方案】，原因是【取舍】。

优化后，我们通过【指标或测试方式】进行验证。

这个方案也存在【成本、副作用或限制】，
后续还可以通过【下一步】继续优化。
```

## 5. 不同方向常见问题池

### RAG 项目

- Chunk 太大或太小
- 相似问题检索不到
- 关键词内容被 Dense 检索遗漏
- 召回内容多但不准确
- Reranker 延迟高
- 上下文太长
- 引用内容和回答不一致
- 无答案时仍然生成
- 多租户数据串库
- 文档更新后旧向量未删除

### Agent 项目

- 意图判断错误
- 任务拆解不完整
- 工具参数缺失
- 结构化输出不稳定
- Agent 重复调用工具
- Agent 进入死循环
- 多工具串行导致延迟高
- 短时异步和长时任务混淆
- 状态无法恢复
- 外部工具不稳定

### NLP 项目

- 类别不均衡
- 新类别不断出现
- 阈值难设置
- 相似类别容易混淆
- 文本太短或信息不足
- 训练数据标注不一致
- 模型上线后分布变化
- 推理延迟过高

### 微调项目

- 数据质量不稳定
- 训练集和测试集泄漏
- 模型过拟合
- 学习率不合适
- 格式遵循没有提升
- 微调后通用能力下降
- 训练效果无法稳定复现
- 显存不足

### 部署项目

- 显存不足
- 并发请求排队
- 首 Token 延迟高
- 模型加载时间长
- 多模型抢占 GPU
- 服务异常无法自动恢复
- 日志不完整
- GPU 利用率低

## 6. 问题要准备到什么程度

不能只说：

```text
我们调了参数，问题就解决了。
```

要能讲清：

- 调了什么参数？
- 为什么调？
- 原来是多少？
- 新值是多少？
- 依据是什么？
- 如何比较？
- 是否有副作用？

# 十、第四部分：技术讲解怎么准备

## 1. 技术讲解不是背百科定义

面试官不会因为你能背出 LangGraph、LoRA 或 Milvus 的定义，
就认为你会做项目。

技术讲解要和项目绑定。

## 2. 通用“五层讲法”

```text
是什么
→ 在项目哪里
→ 为什么选择
→ 如何工作
→ 有什么限制
```

## 3. 通用模板

```text
【技术名称】主要用于【一句话作用】。

在我的项目中，它位于【具体模块】，
主要负责【具体任务】。

当时选择它，是因为【业务需求和技术原因】。

它的核心工作流程是【原理或执行步骤】。

它的限制是【性能、成本、复杂度、适用范围】，
如果换一种场景，也可以考虑【替代方案】。
```

## 4. 技术准备要分三个层次

### 第一层：会使用

能够回答：

- 基本 API
- 核心参数
- 输入输出
- 在项目中如何调用

### 第二层：理解原理

能够回答：

- 核心工作机制
- 数据如何流动
- 为什么有效
- 关键组件是什么

### 第三层：理解选型和取舍

能够回答：

- 为什么选择它
- 不选择其他方案的原因
- 什么情况下不适用
- 有什么替代方案

同学们不需要每个技术都讲到源码级别，
但简历中重点写出的技术，至少要达到第二层，
核心技术最好达到第三层。

# 十一、第五部分：项目优化怎么准备

## 1. 为什么面试官喜欢问优化

面试官通过优化问题判断：

- 你是否只会完成 Demo
- 你是否能发现不足
- 你是否理解真实生产环境
- 你是否有工程取舍能力
- 你是否具备继续迭代的思路

## 2. 优化的通用公式

```text
当前问题
→ 优化目标
→ 具体方案
→ 验证指标
→ 成本与副作用
```

## 3. 七个常见优化方向

### 方向一：效果优化

可以思考：

- 数据是否足够
- Prompt 是否清晰
- 检索是否准确
- 模型是否合适
- 是否需要精排
- 是否需要后处理
- 是否需要微调
- 是否需要人工审核

常用指标：

- Accuracy
- Precision
- Recall
- F1
- Recall@K
- MRR
- NDCG
- 任务完成率
- 人工满意度

### 方向二：性能优化

可以思考：

- 是否可以并行
- 是否可以缓存
- 是否可以减少模型调用
- 是否可以批处理
- 是否可以异步
- 数据库是否有索引
- 模型是否需要量化

常用指标：

- 平均延迟
- P95 延迟
- QPS
- 首 Token 延迟
- GPU 利用率
- 吞吐量

### 方向三：成本优化

可以思考：

- 是否所有任务都需要大模型
- 能否使用规则
- 能否使用小模型
- 能否压缩 Prompt
- 能否减少历史消息
- 能否缓存结果
- 能否按任务路由模型

常用指标：

- 单次请求 Token
- 单次请求成本
- GPU 小时
- 缓存命中率
- 大模型调用次数

### 方向四：稳定性优化

可以思考：

- 超时
- 重试
- 熔断
- 降级
- 幂等
- 状态恢复
- 异常数据校验
- 外部服务故障

常用指标：

- 成功率
- 超时率
- 重试率
- 降级率
- 错误率
- 服务恢复时间

### 方向五：可观测性优化

可以思考：

- 是否有 trace_id
- 是否记录模型输入输出
- 是否记录工具调用
- 是否能看到每个节点耗时
- 是否能自动收集 badcase
- 是否有监控面板

常用指标：

- 节点耗时
- 错误类型分布
- 工具成功率
- 模型调用成功率
- badcase 数量

### 方向六：安全与合规优化

可以思考：

- Prompt Injection
- 越权访问
- 数据泄漏
- 敏感信息
- 外部工具权限
- 数据来源合规
- 高风险操作确认

### 方向七：用户体验优化

可以思考：

- 流式输出
- 进度展示
- 失败提示
- 主动追问
- 结果引用
- 用户反馈
- 结果可修改
- 多轮对话连贯性

## 4. 项目优化通用模板

```text
如果继续优化这个项目，我会优先从【方向】进行。

目前的问题是【现状】。

我计划通过【方案】进行改进。

优化后会使用【指标】进行验证。

这个方案的代价是【成本或复杂度】，
因此需要根据【业务量、预算、准确性要求】决定是否采用。
```

## 5. 项目优化要准备到什么程度

面试官可能继续问：

- 为什么先优化这个方向？
- 如何判断这个问题最严重？
- 你准备使用什么指标？
- 优化后可能出现什么副作用？
- 如果效果和成本冲突怎么办？
- 如果只能做一个优化，你选哪个？
- 哪些优化已经做过，哪些只是计划？

必须明确区分：

```text
已经完成的优化
和
未来计划优化
```

不能把计划说成已经实现。

# 十八、老师培训时建议重点强调的内容

## 1. 不要统一背同一份稿

统一的是方法，不是答案。

每个人应该根据自己的：

- 经历
- 项目
- 职责
- 能力
- 目标岗位

生成不同的面试稿。

## 2. 不要只追求“说得像”

面试的真正目标不是听起来高级，而是：

```text
真实
→ 清楚
→ 有逻辑
→ 能追问
→ 有证据
```

## 3. 不要堆技术

技术越多，面试官可追问的范围越大。

简历中每增加一个技术，都相当于给面试官增加一个问题入口。

## 4. 不要只讲成功

真实项目一定会有：

- 错误
- 延迟
- badcase
- 数据问题
- 设计取舍

能够讲清问题，比只讲“项目成功上线”更有说服力。

## 5. 不要编指标

没有测过，就不要写。

可以这样表达：

```text
目前完成了功能验证，尚未进行正式生产压测。
```

这比编造一个 QPS 更安全，也更专业。

## 6. 不要把未来计划说成已经完成

必须使用明确表达：

- 已经实现
- 已经测试
- 目前正在优化
- 如果继续迭代，我会考虑

# 十九、课堂训练流程建议

## 第一阶段：讲清五段式逻辑

让同学理解：

```text
自我介绍负责定位
履历负责证明经历
项目负责证明实践
技术负责证明理解
优化负责证明潜力
```

## 第二阶段：让同学拆自己的项目

每人填写：

- 项目背景
- 项目架构
- 一条业务链路
- 三个问题
- 三个技术
- 三个优化

## 第三阶段：两人互相追问

一名同学讲，另一名同学只能问：

- 为什么？
- 怎么做？
- 如何发现？
- 如何验证？
- 有没有其他方案？
- 你具体负责什么？

## 第四阶段：老师随机打断

不要让同学每次从头背。

可以随机问：

- 直接讲问题二
- 直接讲数据怎么存
- 直接讲为什么选这个模型
- 直接讲项目还能怎么优化

目的是训练“打乱顺序后仍然能讲清”。

## 第五阶段：录音复盘

让同学检查：

- 是否语速太快
- 是否重复
- 是否空话太多
- 是否名词太多
- 是否没有主语
- 是否说不清个人职责

---

# 二十、建议的课后作业

每名同学提交：

1. 90 秒自我介绍
2. 个人履历时间线
3. 主项目 10 分钟讲稿
4. 备用项目 3 分钟讲稿
5. 三个真实项目问题
6. 三个核心技术讲解
7. 三个项目优化方向
8. 项目事实核对表
9. 20 个可能追问
10. 一段模拟面试录音或视频

# 二十一、评分标准

| 维度 | 分值 | 评价标准 |
|---|---:|---|
| 自我介绍 | 10 | 定位清楚，内容精炼 |
| 个人履历 | 10 | 时间线合理，经历可信 |
| 项目背景 | 10 | 有真实业务问题 |
| 项目架构 | 15 | 能讲完整链路 |
| 个人职责 | 10 | 边界明确，可深入追问 |
| 业务实现 | 15 | 输入、处理、输出清楚 |
| 项目问题 | 15 | 有定位、方案和验证 |
| 技术讲解 | 10 | 能讲原理、选型和限制 |
| 项目优化 | 5 | 有指标，有取舍 |

## 严重扣分项

- 前后说法矛盾
- 只会背固定顺序
- 项目流程讲不清
- 无法说明个人职责
- 技术只会念定义
- 指标没有来源
- 将课程项目说成商业项目
- 将计划说成已经完成

# 二十二、使用 AI 辅助整理面试稿

AI 可以帮助：

- 梳理结构
- 发现遗漏
- 模拟追问
- 优化表达
- 检查前后矛盾
- 将长稿压缩为关键词

AI 不应该帮助：

- 虚构工作经历
- 虚构项目
- 虚构数据
- 虚构指标
- 添加没有使用过的技术
- 编造自己无法解释的代码

## 通用提示词

```text
你是一名 AI 大模型应用开发岗位的技术面试教练。

我会提供自己的真实简历和项目资料。
请严格遵守以下要求：

1. 不得虚构工作经历、项目、团队规模、数据量、上线情况和指标。
2. 不得添加我没有使用过的技术。
3. 无法确认的信息必须标记为“需要本人补充”。
4. 所有内容必须能够经受面试官连续追问。
5. 不要围绕某个固定项目套模板，要根据我的实际项目进行整理。
6. 技术讲解必须和项目中的具体使用位置结合。
7. 区分“已经完成”和“未来计划”。

请按照下面结构帮助我整理：

一、自我介绍
二、个人工作履历
三、项目讲解
  1. 为什么做
  2. 项目架构
  3. 个人职责
  4. 一个具体业务实现
  5. 至少三个真实问题
四、技术讲解
五、项目优化

整理完成后，请继续输出：

1. 20 个面试官可能追问的问题
2. 项目中证据不足的内容
3. 前后矛盾的内容
4. 需要本人补充的数据
5. 一份只包含关键词的复习提纲

以下是我的真实资料：
【粘贴简历和项目资料】
```

# 二十三、最后的核心要求

面试稿准备可以分为三个阶段：

```text
第一阶段：写完整逐字稿
第二阶段：压缩为结构和关键词
第三阶段：脱离稿件随机回答
```

最终目标不是让同学们说出完全一样的话，而是：

```text
无论面试官从背景、架构、代码、数据、问题还是优化开始问，
都能够回到同一套真实、完整、前后一致的项目逻辑中。
```

统一格式只是帮助大家不遗漏内容。

真正决定面试结果的，是：

```text
项目真实
+ 逻辑清楚
+ 职责明确
+ 技术理解
+ 能够追问
+ 有优化思路
```
