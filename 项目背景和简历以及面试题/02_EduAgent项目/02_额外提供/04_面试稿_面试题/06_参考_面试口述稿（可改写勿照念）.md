# A. 开场 90 秒（自我介绍 + 项目）

### 参考说法

> 面试官你好，我是【姓名】，主要做大模型应用，偏【RAG / Agent / 工程】方向。  
> 最近一个项目叫**【慧企助手】**，服务**【内部员工】**查**【制度与产品手册】**。原先咨询群里重复问题很多，人工答得慢、还容易口径不一致。  
> 我负责**【检索链路和评测】**，同事负责**【前端和权限】**。我们用 RAG：文档入库检索后再生成，并带来源。  
> 目前黄金集上 Top5 命中大概**【78% → 89%】**，人工抽检合格率大概**【80% → 92%】**。  
> 今天可以重点聊：检索怎么调优、幻觉怎么定位，以及后面怎么加工具做成办事助手。

### 结构提示（背这个，别背全文）

`我是谁 → 项目服务谁/痛点 → 我负责什么 → 技术方案一词带过 → 1～2 个数字 → 想深聊什么`

### 容易踩坑

- 开场讲技术细节超过 90 秒  
- 没有「我负责」边界，全是「我们」  
- 没有任何数字或结果

# B. RAG 全链路（约 2～3 分钟）

### 参考说法

> 我们项目本质是检索增强生成。分离线和在线两段。  
> **离线**：把制度、手册清洗干净，按**【条款/标题】**分块，过 Embedding 写成向量，进向量库，并带上**【来源、部门、密级】**这些元数据。  
> **在线**：用户提问后，先把问题向量化去做检索，我们还会加**【关键字检索】**做混合，必要时再 **Rerank** 精排，取出 Top**【5】** 片段塞进 Prompt，让模型「只根据资料回答」，最后把答案和来源一起返回。  
> 这样有两个好处：知识更新主要改文档重建索引就行；答案可追溯，方便追责和纠错。

### 若面试官说「画一下」

边画边说同一套词：

`文档 → 清洗 → 分块 → 向量化 → 入库`  
`问题 → 检索 →（重排）→ 拼 Prompt → 生成 → 带来源`

### 一句话收口

> 所以 RAG 不是“有个向量库”就结束，关键是分块质量、检索准不准、以及生成有没有忠实用检索结果。

# C. 分块怎么做（约 90 秒）

### 参考说法

> 分块我们踩过坑。一开始用固定大约**【800】**字切，结果制度里「原则上」和「要审批」经常被切开，模型只看到一半就敢答。  
> 后来改成按**【章节/条款】**切，并且块开头带上标题，这样检索到一段时语境还在。块和块之间留一点 overlap，避免句子被拦腰斩。  
> 验证很简单：挑一批容易答漏条件的题，看改前改后人工是否还漏「需审批」这类约束。我们改完后，这类失误明显下降。

### 追问：「具体多大？」

> 我不会迷信某一个魔法数字。制度类我们更认「语义完整的一条款」；技术手册可能会再看段落长度。核心标准是：块里信息完整、又不过度嘈杂。

# D. 召回不准怎么办（约 2 分钟）

### 参考说法

> 召回不准我会先分层看，不上来就换模型。  
> 第一，问法和原文差很多，比如用户说「机票超标」，原文写「民航超标准购票」——这时会做查询改写，或多路查询。  
> 第二，专名、型号、条款号，纯语义检索可能漂，所以我们上了**【稠密 + BM25 稀疏】**混合。  
> 第三，候选里其实有对的，但排不进前几名，就加 **Rerank**，先宽召回再精排。  
> 第四，如果发现命中段落本身就切坏了，或索引过期，那就回退去改分块和更新节奏。  
> 在我们项目里，混合检索对「专名/口语不一致」这类题帮助最大；Rerank 是在候选已经差不多时，把真正相关的顶上去，但会换一点延迟。

### 对比口述（稠密 vs 稀疏）

> 稠密擅长时间义表达；稀疏擅长关键字和专名。企业文档两者都常出现，所以很多时候不是二选一，是组合。

# E. 幻觉定位：检索还是生成（约 90 秒～2 分钟）

### 参考说法

> 我把幻觉当工程问题定位，不只当玄学。  
> 拿到错误答案，先打开当时检索到的片段：  
> ——如果片段里根本没有支撑事实，甚至跑题，那是 **检索侧**：分块、索引、查询、过滤条件的问题。  
> ——如果片段是对的，模型却不用，或者自行编数字，那是 **生成侧**：Prompt 约束不够、上下文太乱、温度偏高，或者模型没按引用回答。  
> 例子：有次模型说住宿限额 800，一查命中的其实是实习生补贴，不是差旅住宿——这就是检索错。  
> 另一类是限额段落已经命中 500，它仍说 800——那就加强「资料不足就说不知道」「必须引用条款」，并把温度调低。

### 收口

> 先看证据在不在检索结果里，再怪模型，定位会快很多。

# F. 效果怎么评测（约 90 秒）

### 参考说法

> 我们评测分三层。  
> **检索层**：做了大约**【120】**条黄金问答，看正确答案段落是否进 TopK，看命中率变化。  
> **生成层**：每周抽日志做人工打分，看是否忠实、是否完整、该拒答时拒了没有。  
> **业务层**：看重复咨询量、转人工之类是不是下降。  
> 我一般不跟面试官只说「用户感觉还行」，而会把离线集和线上抽检都提到。这样显得有闭环。

*（可选）*  
> 如果人力不够，会用 LLM 初筛再人工复核，但最终口径仍以业务抽检为准。

# G. Agent 是什么 + 我们怎么用（约 2 分钟）

### 参考说法

> 如果说 RAG 是“答得有据”，Agent 更像“为了目标多步做事”。它会观察结果、再决定下一步，并且能调工具。  
> 我们后期不满足于只问答，希望「给出差预算并生成申请草稿」。流程大概是：先调检索工具查制度，再调日历工具看冲突，再生成草稿，最后做一次合规检查。  
> 所以它不是单次补全，而是工具调用 + 状态流转。失败了可以回到检索或提示用户补信息，而不是硬编。

### 追问：「你们 Agent 什么模式？」

> 更接近 Tool-using / ReAct：一步行动看结果，再决定下一步。后来步骤变多，我们就用图的方式把节点显式化，方便调试和加人工卡点。  
> *（若用 LangGraph）* 简单链够用时不必上图；一旦有分支、重试、审核，图更清晰。

# H. Function Call、MCP、Skill 怎么区分（约 90 秒）

### 参考说法（对比清晰即可）

> 我是这么区分的：  
> **Function Call** 解决「这一步调用哪个函数、参数是什么」，模型输出结构化调用，系统执行后再把结果喂回去。  
> **MCP** 更像工具接入的协议层，让同一套工具能被不同客户端/Agent 标准地挂上去，不用每个应用都手搓一套对接。  
> **Skill** 更像给 AI 的标准作业能力包：规范、流程、约束、甚至操作说明，让它按团队方式做事，而不只是一句 Prompt。  
> 一句话：FC 管“怎么调”，MCP 管“怎么标准接入”，Skill 管“按什么规范长期做”。

### 落项目一句

> 在我们场景里，查制度、写草稿更像 FC 工具；如果要跟 IDE/多种 Agent 复用同一工具，会考虑 MCP；代码规范和评测流程则适合沉淀成 Skill，减少 AI 乱用目录、乱改配置。

# I. 为什么不（只）微调？（约 2 分钟）

### 参考说法

> 制度知识月更、还要求引用来源，这种 **事实型、常变更、要可追溯** 的问题，我们优先 RAG。微调更适合改变说话语气、固定输出格式、或路由分类这类「能力/习惯」。  
> 也不是绝对互斥。有的团队会用轻量 LoRA 管格式，用 RAG 管事实。  
> 我们如果上 LoRA，一般是因为想稳定输出字段，比如归类、安抚语、下一步动作；但仍不会把整本制度“背进参数”，否则更新成本和幻觉风险都不好控制。

### 追问：「LoRA 是什么？」

> 直观说：不全量改大模型，而是加很小的旁路参数来学增量，省算力显存；QLoRA 则是把底座量化后再做 LoRA，进一步省显存。我讲解时会强调它是参数高效微调，不是新的模型种类。

# J. 项目深挖 STAR（约 2 分钟）

### 参考说法

> **背景：** 内部制度咨询重复又易口径不一，人工压力大。  
> **任务：** 我负责检索与评测，不负责前端权限。  
> **行动：** 第一，把固定长度分块改成条款分块；第二，上混合检索；第三，建黄金集做回归。  
> **结果：** 命中率和合格率都有提升，重复咨询下降约**【35%】**。  
> **复盘：** 若重做，我会更早上 Rerank，并把权限做成更细的文档级控制。

### 替换口诀

`痛点有多痛 → 我边界在哪 → 三个决策为何如此 → 数字 → 重做改进`

# K. 排障题「同代码不同机器报错」（约 60～90 秒）

### 参考说法

> 我一般按环境差分来排：Python/依赖版本、CUDA 与驱动、模型文件是否一致、环境变量、配置路径、权限、磁盘与内存。  
> 先让两边打印版本和关键配置哈希，对齐依赖；再用同一条最小复现输入对比中间结果。  
> 大模型场景还要额外看：权重是否下完整、量化方式是否一致、GPU 显存是否触发了不同降级策略。  
> 原则是：先复现、再对齐环境、再比中间态，不盲目改业务代码。

# L. 软素质短答（各 45～60 秒）

### 职业规划

> 近一年我想把大模型应用的「检索质量 + 评测闭环 + 工具编排」做扎实，能独立扛一个业务助手从 0 到 1 再到可维护。中期希望能带小模块，把效果指标和工程规范性一起抓起来。选择贵司也是看重**【业务场景/数据闭环/工程比重】**。

### 你有什么缺点 / 压力

> 早期我会有点追求技术方案完整，评审偏慢。后来用“先最小闭环再迭代”约束自己，例如先黄金集和抽检跑起来，再上重排。压力大时我会先把问题拆成可验证小目标，每天对齐一次进展，避免空转。

# M. 综合 7～8 分钟「连贯版」（串讲参考）

> 我做的是企业内部知识助手。痛点是制度咨询重复且易答错，所以用 RAG：条款级分块、向量入库、混合检索，必要时重排，再生成并附来源。我负责检索和评测。  
> 分块上固定长度切碎过审批条件，改成条款切后指标上来。幻觉用二分法：先看片段有没有事实，再看模型是否忠实。  
> 后来要做申请草稿，就在 RAG 外加工具调用，用显式流程串检索、日历、生成和质检。制度事实仍走 RAG，因为要更新、要追溯；格式习惯才考虑轻量微调。  
> 结果上命中和合格率都有提升。若重做，会上更完整的 Rerank 和更细权限。  
> 我也可以展开讲评测怎么做，或讲一个具体误答怎么定位。

# O. 练习法（比背诵重要）

1. **遮盖练习：** 只看章节标题，自己说；说完对照参考稿补洞。  
2. **替换练习：** 把所有【】换成你的词，再念流畅版。  
3. **打断练习：** 让同学在中途插问「为什么不微调？」，训练跳转。  
4. **计时练习：** B/D/G/I 各不超过设定时长。  
5. **降级练习：** 不会的点说「我这块没深做，但我的排查思路是…」，接 E 或 K 的结构，别瞎编。
