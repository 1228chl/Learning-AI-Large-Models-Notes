# AI 大模型班学生简历自检、问题发现与 7 天投递规划提示词手册
## AI 应用开发岗位实用修订版

> **资料索引**：请先阅读 `00_使用说明_先看这个.md`  
> **本文件类型**：提示词手册（简历写完后使用）  
> **用法**：把简历内容粘贴给 AI，按提示词做体检、模拟面试、制定 7 天投递计划；通过后去 `../面试稿/` 准备面试

> 适用人群：准备在北京投递成长型公司、中型技术企业、AI 解决方案公司、ToB 项目公司、创业团队、乙方交付团队及其他市场化企业的 AI 应用开发、RAG、Agent、NLP 应用和 Python 后端岗位的同学。  
> 核心目标：先自行发现简历问题，在 **7 天内形成可投递版本并开始投递**。  
> 本手册不按照大厂招聘标准要求学生准备大量材料，也不要求面试时展示 Git 提交、工作证明、完整项目文档或正式测试报告。

> 这里不按“大公司”或“小公司”简单划分企业。学生可能面对创业团队、成长型公司、中型技术企业、成熟 ToB 服务商，也可能进入规模较大的传统企业数字化部门。共同特点是：招聘更关注岗位匹配、项目表达、实际开发能力和到岗后的落地能力，而不是照搬头部互联网大厂多轮算法筛选标准。

# 一、先理解我们真正面对的面试

对于招聘市场中多数初级或中初级 AI 应用开发岗位，常见流程通常是：

```text
招聘平台沟通或 HR 初筛
→ 技术面试
→ 负责人、项目经理或用人部门复试
→ HR 沟通薪资、入职时间
→ 发放 Offer 或进入后续流程
```

不同公司可能只有一轮技术面，也可能有两轮。部分公司会增加笔试、简单编程题或现场写代码，但并不是每家公司都会按照大厂方式考算法。

## 1. 简历初筛通常看什么

招聘人员和技术负责人主要会快速判断：

- 学历、专业和毕业时间；
- 工作年限与求职方向；
- 是否有明显空档期；
- 项目是否与 RAG、Agent、NLP 或后端开发有关；
- 技能是否与岗位要求接近；
- 工作地点、薪资和入职时间是否匹配；
- 简历有没有明显夸大、冲突和技术堆砌。

简历的任务不是把所有技术都写上去，而是让对方快速判断：

> 这个候选人的经历与岗位是否匹配，项目能不能讲，入职后能不能完成实际开发任务。

## 2. 技术面试通常怎么问

最常见的是：

1. 自我介绍；
2. 个人工作或学习经历；
3. 选择一个项目详细讲解；
4. 为什么选择这套技术；
5. 项目中遇到过什么问题；
6. RAG、Agent、Prompt、模型调用等基础知识；
7. Python、FastAPI、数据库、Linux 等工程基础；
8. 根据业务场景追问如何设计；
9. 询问离职原因、求职方向和入职时间。

面试官通常不会要求你现场提交：

- Git 提交记录；
- 公司项目源代码；
- 正式工作证明；
- 完整测试报告；
- 全套架构文档；
- 客户项目截图；
- 公司内部数据；
- 项目验收材料。

这些内容不是多数技术面试的标准环节。

## 3. 真正需要准备的不是“材料证明”，而是“回答自洽”

你需要做到：

- 简历上的内容确实做过或学习实践过；
- 能说明项目是什么性质；
- 能说清自己负责的模块；
- 能讲出一个具体功能是怎么实现的；
- 能解释为什么选择这项技术；
- 能讲出遇到的问题和解决方式；
- 能说明项目最终做成了什么；
- 遇到没有做过的内容时，不硬编答案。

## 4. 哪些内容属于可选加分项

以下内容不是必须，但个人项目具备时可以加分：

- 一个能运行的简单 Demo；
- 清楚的 README；
- 整理过的 GitHub 或 Gitee 项目；
- 简单架构图；
- 接口截图或演示视频；
- 少量真实测试结果；
- 技术博客或项目复盘。

注意：

> 可选加分项不能代替面试表达，也不应该为了准备这些材料而推迟投递。

公司内部项目通常不适合公开代码、数据和截图，也不需要为了“证明”经历而违反保密要求。

# 二、AI 可以帮助什么，不能帮助什么

## AI 可以帮助

- 检查简历结构；
- 发现时间线冲突；
- 找出技术堆砌；
- 判断项目表达是否清楚；
- 重写真实经历；
- 匹配目标岗位 JD；
- 生成面试追问；
- 帮助整理项目讲解；
- 制定 7 天修改计划；
- 模拟符合目标岗位实际难度的技术面试。

## AI 不能帮助

- 虚构公司和工作经历；
- 把课程项目改成真实商业项目；
- 虚构客户和上线情况；
- 编造数据规模与性能指标；
- 把团队工作全部写成个人工作；
- 把确定性工作流包装成多 Agent；
- 把函数调用包装成 MCP；
- 把没做过的 LoRA、GraphRAG、A2A 写入简历；
- 生成一套自己无法解释的高级技术方案。

# 三、使用前准备

不需要准备一大堆证明材料，只需要尽量准备以下信息：

1. 当前最新版简历；
2. 想投递的岗位名称；
3. 3～10 条目标岗位 JD；
4. 每个项目的真实性质；
5. 自己真正负责的模块；
6. 项目中使用过的主要技术；
7. 一个能够详细讲解的具体功能；
8. 两到三个遇到过的问题；
9. 项目最终完成的功能或真实结果；
10. 当前最担心被追问的内容。

如果某些信息记不清，可以标记为“需要核实”，不要让 AI 自行补全。

# 四、建议使用顺序

```text
第一步：整份简历综合体检
第二步：时间线和真实性检查
第三步：确定目标岗位和简历主线
第四步：逐个检查项目
第五步：压缩技能栏
第六步：重写项目内容
第七步：根据 JD 调整版本
第八步：模拟技术面试
第九步：制定 7 天计划
第十步：投递前终检
```

不建议一开始就让 AI 直接“优化简历”。先找问题，再修改。

# 五、提示词一：整份简历综合体检

## 使用场景

第一次检查简历，先判断目前最大的问题，不急着润色。

```text
你现在是一名熟悉北京 AI 应用开发、RAG、Agent、NLP 应用和 Python 后端岗位招聘的简历审查人员。

我不以头部互联网大厂的算法岗为主要目标，请按照北京招聘市场中成长型公司、中型技术企业、AI 解决方案公司、ToB 项目公司和创业团队的实际要求分析。

请不要立刻润色，先对整份简历进行综合体检。

一、综合判断
1. 当前简历是否已经具备投递基础；
2. 是局部修改、较大调整，还是需要重新梳理；
3. 最适合投递的 1～2 个岗位方向；
4. 简历中最有价值的 3 个优势；
5. 最严重的 5 个问题；
6. 最容易在实际技术面试中被问住的内容。

二、逐模块检查
1. 基本信息；
2. 教育经历；
3. 工作经历；
4. 项目经历；
5. 专业技能；
6. 数据与指标；
7. 时间线；
8. 版式和篇幅。

三、重点找出
1. 基础、简单、没有区分度的内容；
2. 重复表达和车轱辘话；
3. 没有业务背景的技术堆砌；
4. 没有原因和结果的模型对比；
5. “参与”“熟悉”“具备较强能力”等模糊表达；
6. 技能栏中项目没有体现的技术；
7. 与目标岗位无关或准备成本过高的技术；
8. 面试中难以解释的高级技术名词。

四、输出格式
1. 一句话结论；
2. 推荐岗位；
3. 真实优势；
4. 主要问题；
5. 高风险内容；
6. 建议保留的内容；
7. 建议删除或降低表述的内容；
8. 修改优先级；
9. 7 天内是否可以完成；
10. 下一步需要我确认的事实。

不要要求我准备 Git 提交、工作证明、正式报告或公司内部材料。
无法确认的内容标记为“需要核实”，不要替我补全。

以下是我的简历：
【粘贴简历或上传文件】
```

# 六、提示词二：时间线与真实性检查

## 使用场景

检查教育、实习、全职、项目时间以及经历性质是否自洽。

```text
请对我的简历进行“时间线与真实性专项检查”。

目的不是让我在面试时提交证明材料，而是保证简历内容真实、自洽，能够正常回答追问。

一、时间线检查
请整理：
1. 教育经历时间；
2. 实习时间；
3. 全职工作时间；
4. 兼职时间；
5. 项目时间；
6. 是否存在重叠、倒置、未来日期或无法解释的空档。

二、经历性质检查
请判断是否明确区分：
1. 全职工作；
2. 实习；
3. 兼职；
4. 公司内部项目；
5. 客户交付项目；
6. 技术预研或 PoC；
7. 实训或课程项目；
8. 个人项目；
9. 企业场景模拟项目。

三、个人职责检查
请检查“主导、独立完成、负责、参与、协同完成”等词是否准确。

重点判断：
1. 项目规模是否与我的工作年限匹配；
2. 个人职责是否写得过大；
3. 团队成果是否被写成个人成果；
4. “参与”是否没有说明具体负责内容；
5. 项目背景与个人工作是否混在一起。

四、面试口径准备
请为每段重要经历整理我必须能回答的问题：
1. 这是什么项目；
2. 项目是什么性质；
3. 谁使用；
4. 我负责什么；
5. 我具体完成了哪个模块；
6. 使用了哪些主要技术；
7. 为什么这样选；
8. 遇到什么问题；
9. 最终做成了什么；
10. 如果重新做会怎么改。

五、输出格式
请生成表格：
- 原简历内容；
- 存在的问题；
- 面试可能如何追问；
- 推荐保留、修改还是删除；
- 需要我核实的事实；
- 推荐回答口径。

最后分别列出：
1. 可以直接保留；
2. 需要改写；
3. 需要降低表述；
4. 必须删除；
5. 需要向老师或项目成员确认。

不要要求我为每段经历准备 Git、截图、工作证明或正式测试报告。

以下是我的简历：
【粘贴简历或上传文件】
```

# 七、提示词三：岗位定位与简历主线

## 使用场景

简历方向太多，不清楚应该投什么岗位。

```text
请根据我的真实经历，帮助我确定最合理的求职方向。

我主要考虑北京的成长型公司、中型技术企业、AI 解决方案公司、创业团队、ToB 项目公司和乙方交付团队，不以头部互联网大厂算法岗为主要目标。

请比较：
- AI 应用开发工程师；
- RAG 应用开发工程师；
- Agent 应用开发工程师；
- Python 后端开发工程师；
- NLP 应用工程师；
- AI 测试或模型评测工程师；
- 大模型算法工程师；
- 模型训练与推理工程师。

判断标准：
1. 与我的真实经历是否匹配；
2. 7 天内能否准备到可以面试；
3. 项目是否能讲清；
4. 技能是否符合目标岗位的实际要求；
5. 是否有机会获得第一份相关工作。

请输出：
1. 最推荐的主投岗位；
2. 可以兼投的岗位；
3. 暂时不建议投的岗位；
4. 推荐原因；
5. 简历应该围绕哪条主线；
6. 哪些项目放前面；
7. 哪些技术删除或弱化；
8. 技能栏应该保留哪 3～4 类；
9. 一句话个人定位；
10. 搜索 JD 时建议使用的岗位关键词。

以下是我的简历和真实情况：
【粘贴内容】
```

# 八、提示词四：单个项目检查

## 使用场景

判断项目是否写得太大、太空、太复杂或不符合本人水平。

```text
请按照北京多数 AI 应用开发岗位的技术面试方式，检查下面这个项目。

不要按照论文答辩、大厂架构岗或项目验收标准要求我。

一、项目是否清楚
1. 谁使用；
2. 解决什么问题；
3. 项目属于公司、客户、实训、个人还是模拟项目；
4. 项目范围是否过大；
5. 一句话能否讲清。

二、个人工作是否清楚
1. 我具体负责哪个模块；
2. 我写了哪些核心逻辑；
3. 哪些是调用框架或第三方服务；
4. 哪些是团队工作；
5. 是否存在职责夸大；
6. 是否大量使用“参与”。

三、技术是否合理
1. 为什么使用这些技术；
2. 技术之间是否形成真实链路；
3. 是否存在技术名词堆砌；
4. 是否存在概念混淆；
5. 是否写了短期无法准备的技术；
6. 面试官最可能追问哪些实现细节。

四、结果是否真实
1. 最终做成了哪些功能；
2. 是否解决了原来的问题；
3. 是否有真实使用反馈；
4. 是否做过简单测试；
5. 如果没有正式指标，应该如何真实表达；
6. 是否存在编造或夸大的数字。

五、输出
1. 项目当前得分，满分 10 分；
2. 最严重的 5 个问题；
3. 建议保留的内容；
4. 建议删除的内容；
5. 需要补充说明的事实；
6. 推荐的一句话项目介绍；
7. 推荐的 3～5 条项目描述；
8. 实际技术面试最可能问的 15 个问题；
9. 是否适合作为主项目。

重写必须遵循：
业务场景 → 具体问题 → 个人动作 → 技术方案 → 真实结果。

以下是项目内容：
【粘贴项目经历】
```

# 九、提示词五：项目描述重写

## 使用场景

已经确认了真实事实，需要生成简历可用版本。

```text
请根据我提供的真实项目事实，重写成适合 AI 应用开发岗位的项目经历。

必须遵守：
1. 不增加我没有做过的技术；
2. 不编造公司、客户、数据、上线和指标；
3. 不把课程项目包装成真实商业项目；
4. 不把团队成果全部写成个人成果；
5. 不写大量基础、低价值功能；
6. 不堆框架名称；
7. 每条尽量包含：
   业务问题 + 个人动作 + 技术方案 + 真实结果；
8. 每个项目保留一句话介绍和 3～5 条核心内容；
9. 最重要的内容放在前两条；
10. 没有数字时，可以写真实的定性结果；
11. 语言要自然，不要写成项目报告；
12. 不额外生成 Git、README、验收报告和项目证明要求。

请先区分：
1. 确认真实的事实；
2. 需要核实的内容；
3. 不建议写入简历的内容。

然后输出：
1. 项目名称；
2. 一句话项目介绍；
3. 3～5 条核心描述；
4. 适合放入技能栏的关键词；
5. 10 个面试追问。

以下是我的真实项目事实：
【粘贴内容】
```

# 十、提示词六：技能栏压缩

## 使用场景

技能栏太多、太散，或者与项目不对应。

```text
请帮我检查并重写专业技能部分。

目标岗位是北京市场中的 AI 应用开发、RAG、Agent、NLP 应用或 Python 后端岗位，不是头部互联网大厂的算法专家岗位。

要求：
1. 技能控制在 2～4 行或 3～4 类；
2. 只保留与岗位有关的技能；
3. 只保留我项目中真正使用过或能解释的技能；
4. 删除旧技术、重复技术和无关技术；
5. 不写“精通”“具备较强能力”等空话；
6. 不把框架名称简单罗列；
7. 技能应该说明我能完成什么开发工作；
8. 不要求每项技能都提供代码仓库或书面证明。

请先生成“技能可追问性检查表”：
- 技能；
- 在哪个项目中使用；
- 我具体怎么使用；
- 面试可能问什么；
- 我能否讲清；
- 建议保留、弱化还是删除。

然后按以下类别重写：
- 大模型应用；
- RAG 与检索；
- Agent 与工作流；
- NLP 与模型应用；
- Python 后端；
- 数据库、部署与调试。
```

# 二十一、常见错误提示词

## 错误一

```text
帮我加入更多前沿技术，让简历看起来更高级。
```

容易造成技术堆砌。

## 错误二

```text

```

容易生成虚假数字。

## 错误三

```text
把课程项目写成公司上线项目。
```

项目性质不真实。

## 错误四

```text
把 LangGraph 多节点包装成多 Agent、MCP 和 A2A。
```

概念错误，容易被面试官追问。

## 错误五

```text
为每个项目生成一套证明材料和完整验收文档。
```

会浪费大量时间，也不符合多数技术面试的实际流程。

# 二十四、最终原则

以后检查简历，重点问四个问题：

```text
这件事是否真实？
这项技术我是否真的理解并使用过？
技术面试追问时我能否讲清？
它是否值得占用简历和准备时间？
```

简历不是证明材料目录，也不是技术名词展示墙。

企业更希望听到：

```text
项目为什么要做
→ 你负责什么
→ 具体怎么实现
→ 为什么这样选择
→ 遇到什么问题
→ 最终做成了什么
```

我们的目标不是准备一套大厂级作品集，而是尽快形成一份：

- 真实；
- 聚焦；
- 能投递；
- 能讲清；
- 符合目标岗位实际要求；
- 能够经受项目追问；
- 有机会获得面试和第一份 AI 相关工作的简历。
