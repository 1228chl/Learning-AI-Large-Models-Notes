# 2026 热门文档生成与“去 AI 味”提示词框架及 Skill 指南

> **资料索引**：请先阅读 `00_使用说明_先看这个.md`  
> **本文件类型**：附录（可选，非简历核心流程）  
> **用法**：写项目 README、自我介绍、技术方案时查阅，让文字更自然

> 适用场景：课程讲义、技术文档、项目方案、分析报告、总结复盘、公众号文章、简历说明等。

## 一、先记住核心结论

现在效果最稳定的做法，不是寻找一句“万能提示词”，而是组合使用：

**结构化框架 → 分阶段生成 → 提供参考样例 → Humanizer 润色 → 人工复核事实。**

“去 AI 味”也不是故意加入错别字或绕过检测，而是让文字具有更真实的表达习惯、具体信息和个人判断。

---

## 二、当前最值得使用的文档生成框架

### 1. CO-STAR：最适合日常文档生成

CO-STAR 由六部分组成：

- **Context**：背景是什么
- **Objective**：需要完成什么任务
- **Style**：采用什么写作方式
- **Tone**：语气如何
- **Audience**：写给谁看
- **Response**：输出格式、长度和结构

**适合：**讲义、报告、方案、总结、通知、文章。

**简化模板：**

```text
背景：我正在为【对象】准备一份【文档类型】。
任务：请围绕【主题】完成文档。
风格：清晰、实用、重点突出，避免空泛理论。
语气：专业但易懂，像有经验的老师或从业者在讲解。
读者：【读者基础、身份、使用场景】。
输出：使用 Markdown，包含标题、核心结论、主要内容、使用步骤和注意事项；总长度约【字数】。
```

---

### 2. XML / Markdown 分区：最适合复杂长文档

将提示词拆成不同区域，避免背景、资料、任务和输出要求混在一起。

```text
<context>
文档背景、读者情况、业务场景
</context>

<materials>
可使用的原始资料、数据、代码或案例
</materials>

<task>
需要完成的具体任务
</task>

<constraints>
不能虚构；重点突出；避免重复；术语首次出现时解释
</constraints>

<output_format>
Markdown；三级以内标题；包含示例和总结
</output_format>
```

**适合：**技术方案、完整讲义、调研报告、根据多份资料整合文档。

---

### 3. Few-shot 示例法：最适合控制文风

直接提供 1～3 段你认可的文字，让模型学习：

- 句子长短
- 用词习惯
- 段落节奏
- 举例方式
- 是否喜欢先讲结论

**提示方式：**

```text
下面是我认可的写作样例。请学习它的表达节奏、段落组织和用词习惯，但不要照抄内容。

【样例文本】

现在请用相同风格撰写【新主题】。
```

这是目前降低模板感、形成个人风格最有效的方法之一。

---

### 4. Prompt Chaining：最适合生成长文

不要让模型一次性完成全部内容，而是分阶段处理：

```text
明确目标与读者
→ 整理素材
→ 生成目录
→ 分章节撰写
→ 检查重复和逻辑
→ 统一文风
→ 模拟读者审阅
→ 输出最终版
```

**适合：**超过 2000 字的讲义、报告、项目文档、课程资料。

---

### 5. POML：适合程序化、批量化生成

POML 是微软推出的 Prompt Orchestration Markup Language，可以像写 HTML 一样组织提示词，支持角色、任务、示例、文档、表格、变量、循环和条件。

**适合：**

- 同一模板批量生成不同文档
- 团队维护大型提示词
- 在程序中动态插入资料
- 需要版本管理和复用的企业场景

普通用户不必优先学习；当提示词已经成为项目的一部分时再使用。

## 三、当前较有代表性的文档与润色 Skill

### 1. Anthropic Doc Co-authoring

核心流程只有三步：

1. **Context Gathering**：先收集背景和素材
2. **Refinement & Structure**：逐步完善结构与内容
3. **Reader Testing**：让一个不了解上下文的模型模拟读者检查

**适合：**技术文档、提案、PRD、设计文档、决策文档。

### 2. Anthropic 文档类 Skills

官方 Skills 仓库中提供了 DOCX、PDF、PPTX、XLSX 等文档处理 Skill，可用于创建、读取、编辑和检查正式文件。

**适合：**不仅需要文字，还需要生成真正的 Word、PDF、PPT 或表格文件。

### 3. Skill Creator

将反复使用的提示词、步骤、质量标准和输出格式，固化为一个 `SKILL.md`。

**适合：**教师、团队或企业建立自己的：

- 课程讲义生成 Skill
- 简历分析 Skill
- 项目文档 Skill
- 周报总结 Skill
- 技术文章润色 Skill

### 4. Humanizer Skill

目前社区中较有代表性的是 `blader/humanizer`。它不是简单替换同义词，而是检查并修改常见 AI 写作特征，例如：

- 过度宣传和夸张表达
- 大量“首先、其次、最后”
- 每段结构过于整齐
- 高频套话和空洞总结
- 句子长度过于一致
- 模糊来源和无依据判断
- 破折号、三段式和被动句使用过多

最好同时提供作者自己的写作样例，让它在去除模板感后，向真实个人文风靠近。

## 四、推荐的“去 AI 味”提示词

```text
请将下面的内容作为一名专业编辑进行重写，而不是简单替换同义词。

目标：保留原意、事实、术语和关键结论，让文字更像真实作者写成。

请重点处理：
1. 删除空泛开场、万能总结和没有信息量的过渡句；
2. 避免每段结构、句式和长度过于整齐；
3. 将抽象表达改为具体动作、场景、案例或判断；
4. 减少“值得注意的是、综上所述、赋能、助力、深度解析”等模板词；
5. 不要为了自然故意加入错别字、口水话或虚假经历；
6. 保留作者应有的立场和取舍，不要把所有观点写得四平八稳；
7. 面向【目标读者】，采用【专业/教学/口语化】风格；
8. 输出重写后的完整版本，不解释修改过程。

如果下面提供了我的历史写作样例，请优先学习其句子长短、用词和段落节奏。

【参考文风】
……

【待修改内容】
……
```

## 五、最推荐的完整使用流程

### 普通文档

```text
CO-STAR 明确需求
→ 让 AI 先生成目录
→ 确认目录后分段生成
→ 合并并检查逻辑
→ 使用 Humanizer 提示词润色
→ 人工核对事实、案例和个人经历
```

### 经常重复的文档任务

```text
确定固定流程
→ 整理成功案例与失败案例
→ 写成 SKILL.md
→ 设置触发条件和输出格式
→ 用不同输入测试
→ 持续修改 Skill
```

## 六、如何选择

| 使用场景 | 推荐方法 |
|---|---|
| 快速生成一份讲义或报告 | CO-STAR |
| 输入资料很多、要求复杂 | XML / Markdown 分区 |
| 模仿自己的表达方式 | Few-shot 写作样例 |
| 生成较长、较重要的文档 | Prompt Chaining |
| 批量生成或嵌入程序 | POML |
| 反复执行同一种文档任务 | 自定义 Skill |
| 已经有初稿，需要降低模板感 | Humanizer + 个人样例 |

---

## 七、注意事项

- 不要只写“请写得更像人”，必须说明读者、场景和真实文风。
- 不要一次同时要求生成、扩写、查错、润色和排版，复杂任务应分阶段执行。
- 不要把“去 AI 味”等同于绕过检测工具，检测结果本身并不可靠。
- 简历、论文、项目经历和业务数据必须人工核实，不能让 AI 自行补全。
- 最自然的文字通常来自：**真实素材 + 明确观点 + 具体案例 + 个人写作样例。**
