# 一、先给大家一个最重要的信心

现在开始写简历，并不意味着你已经把所有知识学完、所有项目做完、所有面试题都准备好了。

恰恰相反：

> **写简历，是帮助你发现自己已经会什么、还缺什么、下一步应该准备什么。**

第一版简历不是最终交卷，而是一张“求职准备地图”。

很多同学迟迟不敢写，是因为觉得：

- 项目还不够完善；
- 技能还不够多；
- 自己不是科班；
- 没有真实企业项目；
- 不知道该写哪个方向；
- 担心写完以后被面试官追问。

这些担心都很正常。

但解决它们的方法不是继续等待，而是：

```text
先写出第一版
→ 找到缺口
→ 用项目补能力
→ 用 AI 帮助修改
→ 用模拟面试继续完善
```

只要第一步迈出来，后面的方向就会越来越清楚。

# 二、2026 年准备 AI 应用开发岗，我们应该看到什么

AI 应用开发仍然是一个值得投入的方向。

企业正在把大模型应用到越来越多的场景中，例如：

- 企业知识库；
- 智能客服；
- 数据分析；
- 办公助手；
- 合同和文档处理；
- 运维诊断；
- 教育辅助；
- 政务服务；
- 招聘和人力资源；
- 研发提效。

这意味着，同学们可以选择的项目方向很多。

与此同时，企业会更加喜欢这样的候选人：

- 能够使用 Python 完成功能；
- 能够开发接口和连接数据库；
- 理解 RAG 或 Agent 的基本流程；
- 能够把模型能力放进真实业务中；
- 遇到问题愿意排查和学习；
- 能够清楚说明自己的项目。

这并不要求大家一开始就做到非常复杂。

对于刚进入这个方向的同学，企业首先希望看到的是：

> **你有完整做成一件事的能力，而且具备继续成长的潜力。**

所以大家的目标不是把自己包装成已经工作多年的专家，而是用简历证明：

- 我学过；
- 我做过；
- 我理解；
- 我能够继续解决问题。

# 三、写简历时，最容易让大家停下来的几个问题

## 1. “这个项目是不是已经很多人写过？”

很多同学担心：

- 企业知识库太常见；
- RAG 项目太多；
- 智能客服很多人做；
- 高考志愿和简历分析也有人做。

其实，一个项目是否值得写，不是看“有没有别人做过”，而是看你做到了什么程度。

十个人都做企业知识库，可能有十种不同水平：

- 有人只实现文档上传和问答；
- 有人增加了文档分块；
- 有人做了混合检索；
- 有人做了版本过滤；
- 有人增加引用和拒答；
- 有人建立了测试集；
- 有人分析了错误案例；
- 有人加入缓存、异常处理和部署。

所以大家不用追求“全网唯一”的项目。

更重要的是：

> **这个项目是否真正经过了你的理解、修改、测试和完善。**

项目可以相似，但你的思考、实现过程和解决问题的经历不会完全一样。

---

## 2. “ToB 项目没有真实客户，会不会不能写？”

可以写。

同学们可以完成：

- 个人项目；
- 实训项目；
- 企业场景模拟项目；
- PoC 验证项目；
- 基于公开资料设计的项目。

简历中如实写清项目性质即可。

例如：

> 面向企业数据平台技术支持场景，设计并实现智能知识问答与故障诊断 PoC。

这是一种合理、诚实的表达。

我们不需要虚构：

- 真实客户名称；
- 已经生产上线；
- 服务了多少企业；
- 带来了多少真实收益。

面试官关注的重点通常是：

- 这个业务是否合理；
- 系统是怎么设计的；
- 哪些功能是你做的；
- 为什么选择这些技术；
- 你遇到过什么问题。

只要项目真实做过、能够演示、能够讲清楚，就有价值。

---

## 3. “项目必须来自自己以前的公司吗？”

不需要。

自己的工作经历可以给项目提供灵感，但不必完全照搬。

例如：

```text
以前做过客服
→ 可以延伸为知识库、工单分类和回复辅助

以前做过教育
→ 可以延伸为课程知识库、作业分析和学习规划

以前做过财务
→ 可以延伸为制度问答、报销审核和异常检查

以前做过开发
→ 可以延伸为代码知识库、故障诊断和发布审查

以前做过数据
→ 可以延伸为数据口径问答、Text2SQL 和数据质量分析
```

这种扩展并不是造假，而是把已有经验和 AI 技术结合起来。

需要注意的是：

- 不泄露原公司数据；
- 不虚构真实上线结果；
- 不把计划中的功能写成已经完成；
- 自己要补充相关业务知识。

---

## 4. “我不是计算机专业，是不是不适合？”

非计算机专业并不代表不能做 AI 应用开发。

大家需要补的主要是：

- Python；
- 数据库；
- HTTP 和接口；
- Git；
- Linux；
- 基础的数据结构；
- 调试和排错能力。

这些能力都可以通过学习和项目逐步补起来。

同时，非计算机专业可能拥有自己的优势：

- 教育专业更容易理解教学场景；
- 财务专业更容易理解报销和制度；
- 新闻传播专业更容易理解内容和舆情；
- 物流专业更容易理解供应链和运输；
- 人力资源专业更容易理解招聘和员工服务。

正确方式不是反复强调“我不是科班”，而是：

> **用项目证明我已经具备进入岗位所需要的基础能力。**

---

## 5. “我没有行业经验，怎么选项目？”

没有行业经验很正常。

我们不需要一开始就是行业专家，可以边调研、边做项目、边理解业务。

一个合理的过程是：

```text
选择一个场景
→ 使用 AI 和公开资料调研
→ 整理用户和流程
→ 准备几个案例
→ 设计最小项目
→ 在开发中继续补充理解
```

大家真正需要避免的，不是“不了解行业”，而是：

> 完全没有调研，就直接把技术套进一个行业名称中。

只要愿意查资料、问问题、整理流程，行业理解是可以逐步建立的。

# 四、哪些问题应该想，哪些问题不用想太久

## 不用反复纠结的问题

下面这些问题简单确认后，就可以继续行动：

- 别人是不是也做过；
- 项目名称是不是足够高级；
- 项目是不是百分之百来自真实公司；
- 自己是不是计算机专业；
- 第一版简历是不是已经非常完美；
- 所有技术是不是都已经完全掌握；
- 面试官会不会问到一个自己暂时不会的问题。

这些问题不会通过继续空想自动消失。

它们会在：

- 写简历；
- 做项目；
- 模拟面试；
- 真实投递

的过程中逐步解决。

---

## 也要提醒另一类同学：不要脑袋一热就一头扎进去

有些同学不是不敢开始，而是开始得太快。

看到一个项目名字不错，就马上写代码；  
看到别人用了多 Agent，就立刻给自己的项目安排很多 Agent；  
看到政务、高考、医疗、金融这些方向听起来“有业务”，就马上往里面套 RAG 和工作流。

这种行动力很宝贵，不应该被打击。

但真正高效的行动，不是马上写很多代码，而是先用半天确认方向是否成立。

建议这类同学在正式开发前，先完成一张“一页项目说明”。

至少回答下面十个问题：

1. 这个项目服务谁？
2. 用户在什么情况下会使用？
3. 当前真正的问题是什么？
4. 现在没有 AI 时，别人怎么解决？
5. AI 适合负责哪一步？
6. 为什么需要 RAG？
7. 为什么需要 Agent，而不是普通流程？
8. 数据从哪里来？
9. 最小闭环是什么？
10. 项目最后如何测试和证明有效？

如果这十个问题暂时答不完整，不代表这个项目不能做。

它只是说明：

> **先补半天调研，再开始写代码，会比直接开干更快。**

---

### 用三个案例检验自己是不是真的理解业务

项目开始前，先写出三个完整案例。

如果一个项目连三个真实使用案例都很难描述清楚，往往说明目前只是看中了项目名称，还没有真正理解业务。

#### 例如：高考志愿项目

一个案例至少要包含：

- 考生所在省份和年份；
- 选科情况；
- 分数和位次；
- 目标地区或专业；
- 家庭约束；
- 需要查询哪些数据；
- 推荐依据是什么；
- 有哪些风险提示。

如果只知道“输入分数，推荐学校”，还需要继续了解：

- 平行志愿；
- 专业组；
- 位次；
- 招生章程；
- 选科要求；
- 调剂、滑档和退档风险；
- 不同省份、不同年份的规则差异。

#### 例如：政务项目

一个案例至少要包含：

- 谁提交事项；
- 提交什么材料；
- 哪个部门受理；
- 依据什么政策；
- 哪一步需要审批；
- 哪些数据比较敏感；
- 是否允许调用外部模型；
- 如何保留操作记录。

如果只知道“做一个政务问答助手”，还需要继续了解：

- 国产化和信创；
- 私有化部署；
- 数据不出域；
- 权限；
- 政策版本；
- 审计；
- 人工复核。

#### 例如：医疗、金融等高风险场景

还需要额外思考：

- AI 是辅助还是直接决策；
- 错误结论可能造成什么影响；
- 哪些内容必须人工确认；
- 数据如何脱敏；
- 回答是否需要引用依据；
- 知识是否有时间和版本要求。

这些内容不是为了吓退大家，而是帮助大家把项目做得更真实、更容易讲清楚。

---

### 先区分：普通程序、RAG 和 Agent

不要为了让项目看起来高级，就把所有功能都写成 Agent。

可以先这样判断：

#### 普通规则或程序更适合

- 判断条件非常明确；
- 流程固定；
- 不需要理解大量自然语言；
- SQL 或条件判断就能完成。

#### RAG 更适合

- 资料很多；
- 内容经常更新；
- 需要引用依据；
- 涉及企业内部知识；
- 需要按版本或权限过滤。

#### Agent 更适合

- 需要调用多个工具；
- 需要多步判断；
- 中间结果会改变后续路径；
- 需要保存状态；
- 需要人工审批；
- 失败后需要重试或重新规划。

如果普通流程可以完成，就先用普通流程。

如果基础 RAG 还没有跑通，就先不要急着增加很多 Agent。

> **少做几个真正有作用的节点，比堆很多名字更有价值。**

---

### 给行动力强的同学一个“半天刹车法”

在正式开发前，先用半天完成：

- 一页项目说明；
- 三个业务案例；
- 数据来源清单；
- 最小流程图；
- 10 条测试问题；
- “为什么使用 RAG / Agent”的说明。

完成以后再开工。

这不是拖慢速度，而是在帮助你：

- 少走弯路；
- 减少返工；
- 更容易写简历；
- 更容易准备面试；
- 更容易让 AI 给出准确帮助。

真正值得保留的不是“马上写代码”的冲动，而是：

> **快速行动，也快速验证。**

## 真正应该认真思考的问题

### 1. 我想找什么岗位？

建议先选择一个主要方向：

- 大模型应用开发；
- RAG 开发；
- Agent 开发；
- AI 后端开发。

不用一开始区分得特别细，但要有一个主线。

### 2. 我的项目服务谁？

例如：

- 企业员工；
- 客服人员；
- 技术支持；
- 老师；
- 学生；
- 数据分析师；
- 运维人员。

### 3. 它解决什么问题？

不要只写“使用大模型实现智能问答”。

应该更具体：

- 文档太多，不容易查；
- 不同版本容易混淆；
- 重复问题很多；
- 故障需要查询多种资料；
- 人工整理信息耗时；
- 数据查询门槛高。

### 4. 数据从哪里来？

可以来自：

- 官方文档；
- 开源资料；
- 公开数据集；
- 自己整理的 FAQ；
- 自己设计的模拟案例；
- 脱敏后的个人资料。

### 5. 最小可以先做什么？

例如一个 RAG 项目的第一步可以只是：

```text
加载文档
→ 文本分块
→ 向量入库
→ 用户提问
→ 检索文档
→ 返回答案和引用
```

先把这一条链路跑通，再增加其他功能。

### 6. 我真正完成了什么？

简历首先写已经完成的内容。

计划中的内容可以保留在项目计划里，但暂时不要写成成果。

### 7. 如何证明它有效？

不必一开始就做复杂评测。

可以先从以下方式开始：

- 准备 10～20 个测试问题；
- 记录哪些回答正确；
- 记录哪些文档召回错误；
- 对比修改前后的效果；
- 收集典型错误案例。

这是最初级、也是最真实的评测。

# 五、项目选题不用一次决定一生

选项目并不是选择未来十年的职业。

它只是帮助你：

- 把学到的技术串起来；
- 形成一段可以写进简历的经历；
- 准备面试讨论材料；
- 发现自己更喜欢哪个方向。

所以同学们不用给自己太大压力。

## 推荐的选题方法

从三个候选项目中选择一个：

| 判断维度 | 要问的问题 |
|---|---|
| 岗位相关 | 和我想投的岗位是否有关？ |
| 自己愿意做 | 我对这个场景是否有兴趣？ |
| 数据可获得 | 能否找到文档和测试数据？ |
| 两周能起步 | 能否完成最小闭环？ |
| 能够讲清 | 我是否愿意补业务知识？ |
| 可以扩展 | 后续能否增加评测和工程能力？ |

满足其中大部分，就可以开始。

不用等到所有条件都是满分。

# 六、不同类型同学，应该如何找到自己的优势

## 1. 刚毕业、没有工作经验的同学

你们不需要假装自己已经有多年企业经验。

更适合突出：

- 学习能力；
- 编程基础；
- 项目完整性；
- 对新技术的理解；
- 自己解决过的问题；
- 做过的测试和优化。

建议准备：

- 一个核心 AI 项目；
- 一个辅助项目；
- 清晰的技能栏；
- 可以运行的项目仓库；
- 一分钟项目介绍。

你们的优势是：

> 可塑性强、学习速度快、愿意投入新方向。

---

## 2. 毕业 1～2 年，但没有 AI 工作经验的同学

你们可以把过去经历中的可迁移能力找出来。

例如：

- 做过数据：SQL、数据处理、指标理解；
- 做过测试：测试用例、接口测试、错误分析；
- 做过运营：用户需求、业务流程、内容处理；
- 做过实施：需求沟通、部署、问题排查；
- 做过客服：知识库、工单和标准流程。

正确表达方式是：

```text
原有经验
+
AI 技术学习
+
一个能够证明转型能力的项目
```

不需要把过去全部否定掉。

---

## 3. 非计算机专业同学

你们可以把专业背景作为项目差异化来源。

但简历中不要一直解释自己的劣势。

与其写：

> 虽然我不是计算机专业，但我非常热爱编程。

不如用项目证明：

- 完成了 FastAPI 接口；
- 使用数据库保存数据；
- 实现了 RAG 检索；
- 设计了测试集；
- 完成了 Docker 部署。

行动本身比解释更有力量。

---

## 4. 以前做过开发、年龄稍长一些的同学

你们不用把自己完全当作零基础新人。

已有的开发经验非常有价值：

- 后端架构；
- 数据库；
- 中间件；
- 接口；
- 并发；
- 部署；
- 排障；
- 团队协作。

可以把自己的定位写成：

> **拥有开发经验，正在完成 AI 应用能力升级的工程师。**

项目中应该重点体现：

- 原有工程能力；
- AI 技术如何接入系统；
- 如何处理异常和性能；
- 如何完成部署和维护。

# 七、第一版简历应该怎么写

第一版简历不追求完美，只需要把信息放对位置。

推荐结构：

```text
基本信息
求职方向
专业技能
项目经历
工作/实习经历
教育经历
```

## 1. 求职方向

可以写：

> 求职方向：大模型应用开发工程师 / AI 后端工程师

先有一个主方向，不需要把所有岗位都写上。

## 2. 专业技能

技能不要只堆技术名词。

推荐结构：

### Python 与后端

- Python 基础、面向对象和异步编程；
- FastAPI、Pydantic、REST API、SSE；
- MySQL/PostgreSQL、Redis；
- Git、Linux、Docker。

### RAG

- 文档加载和清洗；
- 文本分块；
- Embedding；
- 向量数据库；
- 混合检索；
- Reranker；
- 引用和拒答；
- 基础评测。

### Agent

- LangGraph State；
- 节点和条件路由；
- 工具调用；
- 结构化输出；
- 人工审批；
- 重试和降级。

只保留自己真正学习和使用过的部分。

## 3. 项目经历

每个项目写清：

- 项目解决什么问题；
- 使用什么技术；
- 自己完成了什么；
- 遇到什么问题；
- 有什么测试或改进。

建议写 5～7 条核心内容。

# 八、项目描述应该如何写

推荐使用这个结构：

```text
动作
+
技术方法
+
解决的问题
+
真实结果或验证
```

## 普通写法

> 使用 Milvus 和 BGE-M3 实现 RAG 系统。

## 更好的写法

> 使用 BGE-M3 生成稠密与稀疏向量，结合 Milvus 混合检索和版本元数据过滤，减少错误码、配置项及相似版本文档的误召回。

两句话都提到了技术，但第二句更能说明你真正做了什么。

---

# 九、第一版项目还不完整，能不能先写？

可以先写已经完成的部分。

例如：

> 当前已完成文档加载、文本分块、向量入库和基础问答链路，正在继续完善混合检索、引用展示和评测模块。

项目本来就是逐步完成的。

不需要等所有模块全部完成后才开始整理简历。

推荐使用三个版本管理自己的简历：

## V0：起步版

作用：

- 梳理已有经历；
- 找到技能缺口；
- 确定项目方向。

## V1：项目版

加入：

- 完整项目；
- 个人工作；
- 测试结果；
- 技术亮点。

## V2：投递版

根据具体 JD 调整：

- 技能顺序；
- 项目重点；
- 关键词；
- 自我介绍。

简历应该不断迭代，不是一稿定终身。

# 十、如何用 AI 帮助自己写简历

它不是用来替你虚构经历的，而是帮助你把真实经历表达得更清楚。

## 第二步：让 AI 帮你分析目标岗位

## 第三步：让 AI 帮你选择项目

```text

【写出自己学习过的内容】
```

## 第四步：让 AI 把项目事实改写成简历语言

```text

5. 输出项目简介、技术栈和 5～7 条个人工作。

项目事实：
【粘贴真实内容】
```

## 第五步：让 AI 检查简历有没有写过头


# 十一、AI 使用中最重要的原则

## 1. AI 可以帮助，但你必须理解

每段核心代码都要能回答：

- 输入是什么；
- 输出是什么；
- 为什么这样写；
- 哪里可能出错；
- 如何测试；
- 如何修改。

## 2. AI 给出的内容要核对

核对：

- 框架版本；
- API 是否存在；
- 技术是否真的用过；
- 指标是否真实；
- 项目流程是否合理。

## 3. 不需要隐藏自己使用 AI

现在开发中使用 AI 很正常。

更好的表达是：

> 我使用 AI 辅助调研、代码拆解和错误排查，但会通过官方文档、实际运行、测试用例和代码审查验证结果。

这比假装完全没有使用 AI 更真实。

# 十五、最后想对大家说

现在的你，不需要已经成为一个成熟的 AI 工程师，才有资格开始写简历。

写简历的过程，本来就是帮助你成为更成熟的候选人。

大家不需要：

- 一开始就有完美项目；
- 一开始就懂完整行业；
- 一开始就回答所有问题；
- 一开始就比所有人优秀。

你只需要做到：

```text
今天比昨天更清楚一点
这周比上周多完成一个功能
下一版简历比上一版更真实、更具体
下一次回答比上一次更有结构
```

不要因为别人已经开始，就觉得自己来不及。  
不要因为不是科班，就提前否定自己。  
不要因为项目有人做过，就觉得没有价值。  
不要因为第一版不完美，就迟迟不写。

请先迈出第一步。

> **简历不是对过去的审判，而是对下一步行动的规划。**

项目也不需要全网唯一，但要逐渐真正属于你：

- 业务经过你的调研；
- 代码经过你的理解；
- 问题经过你的排查；
- 效果经过你的测试；
- 面试时能够用自己的话讲清楚。

从第一版开始，慢慢修改，持续行动。

你会发现，原来那些让自己害怕的问题，会在一次次实践中变得越来越具体，也越来越容易解决。
