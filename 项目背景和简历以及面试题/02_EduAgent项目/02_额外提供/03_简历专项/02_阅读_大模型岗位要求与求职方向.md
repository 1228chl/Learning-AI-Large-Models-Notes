## 面向黑马程序员学员｜2026 年 7 月版

同学们现在准备 AI 大模型方向简历，不能再按照传统 Python 后端、普通算法、普通项目经验的方式来写。2026 年 7 月，北京的大模型岗位已经明显进入“应用落地阶段”，企业更关心的不是你会不会背概念，而是你能不能把大模型真正接入业务系统，解决知识库问答、智能客服、流程自动化、Agent 工具调用、企业知识库、内容生成、评测优化、稳定性治理等问题。

从公开招聘信息看，北京不少大模型应用岗位都在要求 RAG、Agent、Prompt Engineering、向量数据库、LangChain / LlamaIndex / LangGraph、MCP、流式响应、模型微调、推理部署、评估体系等能力。比如部分岗位明确要求负责 AI Agent 系统开发、RAG 企业知识库建设、多 Agent 协作、工具调用、Prompt 优化和 Agent 评估体系；也有岗位要求参与 Prompt、RAG、微调、MCP 链路搭建与性能调优。

所以，简历的核心不是写“我学过大模型”，而是要证明：

> 我能把大模型做成一个可运行、可调用、可检索、可评估、可上线的业务系统。

## 一、求职方向不要乱写

很多同学容易在求职意向里写：

- AI 大模型工程师
- 大模型算法工程师
- NLP 算法工程师
- Agent 工程师
- RAG 工程师
- Python 后端工程师
- AIGC 应用开发工程师

这些方向不能随便堆。因为不同岗位看的能力不一样。

如果你主要是黑马课程体系出来，重点做过 RAG、Agent、FastAPI、数据库、向量检索、LLM API、业务项目，那么更推荐写：

**大模型应用工程师 / RAG Agent 开发工程师 / AI 应用开发工程师**

不建议轻易写：

**大模型算法工程师**

因为算法工程师通常会更关注模型训练、预训练、SFT、RLHF / DPO、模型压缩、推理优化、论文、实验指标、GPU 训练经验等。部分北京算法岗位已经明确要求文本和多模态大模型研发、SFT、RL、Agent / Multi-Agent、RAG、训练优化等能力。

如果你没有真正做过模型训练、微调、实验对比和指标优化，就不要把自己包装成“算法工程师”。更稳的定位是：

> 我是大模型应用开发方向，能完成 RAG、Agent、后端接口、数据库、工具调用和业务落地。

## 二、EduAgent 是课程项目，不建议直接写进简历

大家必须注意：**EduAgent 是课程里统一讲的项目，不建议所有人直接把 EduAgent 原封不动写进简历。**

原因很简单：

第一，班级里很多人如果都写同一个项目、同一套模块、同一套技术栈，HR 和面试官很容易看出来这是培训项目。

第二，面试官不会只看项目名字。他会追问你：

- 这个项目是不是你独立做的？
- 哪些模块是你自己写的？
- 你有没有改过需求？
- 你有没有自己加功能？
- 你有没有部署？
- 你有没有压测？
- 你有没有真实数据？
- 你有没有解决过线上问题？

如果你只是跟着课程敲了一遍，项目写得越大，面试风险越高。

之前有同学简历里把 EduAgent 写成“教育场景 AI 多智能体辅助平台”，里面包含智能问答、试卷批改、简历审查、模拟面试、RAG、LangGraph、Milvus、MCP 等大量内容；这种项目如果不是自己真正消化并做过二次开发，面试时非常容易被问穿。

正确做法不是完全不能借鉴课程项目，而是要做到：

> 课程项目只作为学习基础，简历项目必须写成自己的二次开发版本。

可以改成：

- 企业内部知识库问答系统
- 招聘简历智能评估系统
- 客服工单智能助手
- 法律 / 医疗 / 教培 / 财务知识库问答系统
- 面试题生成与答题评估系统
- 舆情分析智能 Agent
- 电商客服智能 Agent
- 代码知识库问答助手
- 合同审查智能助手
- 安全日志分析 Agent

项目名字、业务场景、数据来源、功能模块、个人职责、优化点都要和课程项目拉开差异。

## 三、2026 年大模型岗位最看重什么

现在北京的大模型应用岗位大致分成四类。

1. RAG 知识库应用岗

这类岗位最常见，主要做企业知识库、智能客服、内部文档问答、政策问答、客服助手、科研文献问答等。

企业会关心你是否懂：

- 文档解析
- 文本清洗
- 语义分块
- Embedding
- 向量数据库
- BM25
- 混合检索
- Reranker
- Prompt 拼接
- 答案引用
- 幻觉控制
- 检索效果评估

有些岗位明确写到主导 RAG 系统开发，覆盖数据预处理、检索、生成、模型融合，并要求至少熟练一种向量数据库。

所以简历里不要只写：

> 熟悉 RAG。

要写成：

> 独立完成文档解析、分块、Embedding、Milvus 入库、BM25 + 向量混合检索、Rerank 精排、Prompt 组装和答案生成，并基于测试问题集评估召回率和答案准确性。

1. Agent 应用开发岗

这类岗位正在变多，常见在客服、办公自动化、数据分析、营销运营、运维、内容生产、代码生成等场景。

岗位会关注：

- Agent 工作流
- 工具调用
- Function Calling
- MCP
- 多轮记忆
- 状态管理
- 多 Agent 协作
- 人在环中
- 失败重试
- 权限控制
- 任务执行结果校验

部分招聘信息已经明确提到负责 AI Agent 系统开发、智能体工作流、多 Agent 协作、工具调用、Agent 策略优化和评估体系。

所以简历里不要只写：

> 使用 LangGraph 搭建智能体。

要写成：

> 基于 LangGraph 将业务流程拆分为意图识别、任务规划、工具调用、结果校验、异常兜底等节点，通过 State 传递上下文，并使用条件边完成不同任务路径路由。

1. AI 应用后端工程岗

很多公司不是单独招“纯大模型工程师”，而是招能把 AI 能力接进系统里的后端工程师。

这类岗位会关注：

- Python / Java 基础
- FastAPI / Flask / Spring AI
- HTTP 接口
- SSE / WebSocket 流式响应
- MySQL / PostgreSQL
- Redis
- Docker
- 日志
- 鉴权
- 异常处理
- 接口性能
- 系统稳定性

有些岗位虽然叫 AI 应用开发，但职责里会写“集成到客户现有业务系统”“日常运维”“监控系统状态”“处理故障”“保障稳定运行”。

所以，同学们不要只展示大模型概念，也要展示工程能力。因为企业最终要的是能上线的系统，不是课堂 Demo。

1. 大模型算法 / 训练 / 微调岗

这类岗位门槛最高，适合研究能力强、数学基础好、有模型训练经验、实验指标扎实的同学。

通常会关注：

- PyTorch
- Transformer
- LLaMA / Qwen / DeepSeek
- SFT
- LoRA
- DPO / RLHF
- 模型压缩
- 推理加速
- 数据构造
- 评测体系
- 多卡训练
- 算法论文

如果你没有这些经历，不建议把简历主方向写成算法岗。可以把微调写成加分项，但不要作为核心卖点。

## 四、简历项目是重点，项目必须按“业务问题 → 技术方案 → 个人贡献 → 结果指标”来写

项目不能写成技术栈堆砌。

错误写法：

> 本项目使用 LangChain、LangGraph、Milvus、FastAPI、PostgreSQL、Redis、Docker、Pydantic、MCP，实现智能问答、简历审查、试卷批改、模拟面试等功能。

这种写法的问题是：看起来很大，但不知道你到底做了什么。

正确写法：

> 针对企业内部制度文档分散、员工查询效率低、人工答疑成本高的问题，设计并实现一套 RAG 知识库问答系统。本人负责文档解析、语义分块、Embedding 入库、混合检索、Rerank 精排和答案生成模块，使用 FastAPI 提供问答接口，并通过 SSE 实现流式输出。系统支持 PDF / Word / Markdown 文档入库，基于测试问题集评估 Top-K 召回率和答案命中率。

这就清楚很多。

每个项目建议控制在这几个部分：

1. 项目背景

写清楚业务痛点，不要空泛。

例如：

> 企业知识文档分散在 PDF、Word、飞书文档中，新员工查询制度和业务流程依赖人工答疑，效率低且答案不统一。

1. 技术方案

写清楚系统怎么解决问题。

例如：

> 构建文档解析、文本分块、向量化、Milvus 入库、混合检索、Rerank 精排、LLM 答案生成的 RAG 全链路。

1. 个人职责

必须写你本人做了什么。

例如：

> 负责文档处理和检索模块开发，实现 PDF 文本提取、chunk 切分、Embedding 生成、Milvus schema 设计和 Top-K 召回接口。

1. 优化点

写你如何改进效果。

例如：

> 针对短问题召回不准的问题，引入查询改写和 BM25 + 向量混合检索；针对召回内容相关性不足的问题，引入 Reranker 精排。

1. 结果指标

一定要有结果。

例如：

> 在 200 条测试问题集上，Top-5 召回率达到 xx%，答案人工可用率达到 xx%，平均响应时间控制在 x 秒内。

如果没有真实指标，就不要乱编。可以自己补做测试，哪怕数据量小，也比没有强。

## 五、简历里不要出现这些危险写法

1. 不要写“精通大模型”

学生阶段最多写“熟悉”或“掌握基础应用开发”。“精通”容易被面试官重点拷打。

1. 不要写自己没做过的技术

比如 MCP、LangGraph、多 Agent、Reranker、LoRA、vLLM、K8s，只要写了就默认会被问。

写之前先问自己：

- 我能不能画出流程？
- 我能不能说出代码怎么写？
- 我能不能解释为什么用它？
- 我能不能说出踩过什么坑？
- 我能不能说出不用它会怎样？

如果不能，就不要放在核心技能区。

1. 不要把课程项目原封不动写上去

课程项目可以作为基础，但简历项目必须有个人改造。

至少要做到以下任意三点：

- 换了真实业务场景；
- 换了数据集；
- 增加了新功能；
- 做了部署；
- 做了评测；
- 做了性能优化；
- 做了权限和日志；
- 做了异常兜底；
- 写了接口文档；
- 做了前端演示；
- 做了项目复盘。

否则就是“课堂练习”，不是“简历项目”。

1. 不要写过大的系统

不要动不动写“企业级多智能体平台”“千万级知识库”“全链路智能中台”。学生项目可以有完整链路，但不要吹成大型商业系统。

更稳的写法是：

> 面向某个具体场景的 RAG 问答系统 面向某类业务流程的 Agent 助手 面向某类文档的智能分析工具

范围越具体，越容易讲清楚。

## 六、推荐大家准备的项目方向

### 方向一：企业知识库 RAG 问答系统

这是最适合大多数学员的项目。

建议功能：

- 文档上传
- PDF / Word 解析
- 文本清洗
- chunk 分块
- Embedding
- Milvus / FAISS 入库
- BM25 + 向量混合检索
- Rerank
- Prompt 组装
- 答案生成
- 引用来源
- SSE 流式输出
- 问答记录保存
- 用户登录

这个项目对应北京很多 RAG、知识库、智能客服岗位。公开岗位中也经常要求企业知识库、RAG、向量数据库、检索策略、LangChain 等经验。

### 方向二：客服 / 工单 Agent

适合想冲 Agent 应用开发的同学。

建议功能：

- 用户问题意图识别
- 工单分类
- 查询知识库
- 调用订单 / 用户 / 售后工具
- 自动生成回复
- 低置信度转人工
- 多轮上下文记忆
- 操作日志记录
- 敏感操作确认

这个方向非常贴近企业真实场景。北京有不少岗位已经把 Agent、上下文管理、RAG、工具调用、流式响应写进职责里。

### 方向三：招聘简历智能评估系统

适合希望项目和就业场景结合的同学。

建议功能：

- 简历 PDF 解析
- 基本信息提取
- 技能匹配度分析
- 项目经历评分
- 岗位 JD 匹配
- 缺点诊断
- 优化建议生成
- 修改计划生成
- Pydantic 结构化输出
- 结果入库

注意：不要写成课程里的 EduAgent 简历模块，要写成你自己独立开发的“简历智能评估系统”，并且最好结合真实 JD 做匹配分析。

### 方向四：行业文档审查 Agent

适合想做垂直行业应用的同学。

比如：

- 合同审查 Agent
- 招标文件问答 Agent
- 医疗指南问答 Agent
- 财务制度问答 Agent
- 网络安全日志分析 Agent
- 舆情分析 Agent

这类项目比普通 ChatBot 更有业务感。

## 八、每个同学最终要准备的材料

大家至少要准备以下内容：

1. 一份聚焦大模型应用方向的简历；
2. 一个能跑通的个人项目；
3. 一份项目架构图；
4. 一份项目流程图；
5. 一份接口说明；
6. 一份数据库表设计；
7. 一份项目演示截图；
8. 一份面试项目讲解稿；
9. 一组 RAG / Agent 高频问题答案；
10. 一份项目优化记录。

如果只是简历上写项目，但电脑里没有代码、没有截图、没有接口、没有演示，那面试风险非常大。

## 九、简历最终检查清单

投递前逐项检查：

- 求职方向是否聚焦？
- 是否主打“大模型应用 / RAG / Agent”？
- 是否避免直接写课程项目 EduAgent？
- 项目是否有自己的业务场景？
- 项目是否写清楚个人职责？
- 是否有技术方案，而不是只堆技术栈？
- 是否有结果指标？
- 是否能讲清楚 RAG 全流程？
- 是否能讲清楚 Agent 工作流？
- 是否能解释数据库、接口、部署？
- 是否删掉了“精通”“企业级”“千万级”等高风险词？
- 是否每个技术点都能经得起追问？

## 十、最后给大家一句话

2026 年的大模型岗位，不缺“听过 RAG、Agent、LangChain 的人”，缺的是能把这些技术做成具体业务系统的人。

所以简历不要写成：

> 我学过很多大模型技术。

而要写成：

> 我用这些技术解决了一个具体问题，并且能讲清楚系统怎么设计、代码怎么实现、效果怎么验证、问题怎么优化。

项目是简历的核心。项目不是越大越好，而是越真实、越具体、越能讲清楚越好。
