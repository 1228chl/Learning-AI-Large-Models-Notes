# 从课程项目到个人求职项目
## AI 大模型应用开发项目改造指南｜重点精简版

> **资料索引**：请先阅读 `00_使用说明_先看这个.md`  
> **本文件类型**：专项指南（适合学过 RAG / EduAgent 的同学）  
> **用法**：按五步改造法把课程项目变成自己的求职项目，改造完用 `06` 写进简历

> 适用对象：正在学习 RAG、工作流、Agent、LangGraph、FastAPI、Milvus 等内容，准备投递 AI 大模型应用开发相关岗位的同学。  
> 目标：把班级统一学习的“学科答疑 RAG”和“EduAgent”，尽快改造成符合自己专业、经历和目标岗位的 2～3 个个人项目。

---

# 一、先看最重要的结论

你不需要重新发明三个项目。

最推荐的项目组合是：

```text
项目一：结合个人背景的行业 RAG 项目
+
项目二：结合个人背景的业务工作流 / Agent 项目
+
项目三：NLP、AI 评测、Text2SQL 或 Python 工程项目（可选）
```

两个课程项目应该这样改：

## 学科答疑 RAG

不要继续写成“AI 学科在线答疑系统”。

应该改造成：

> 你熟悉领域中的知识库、业务问答或技术支持系统。

例如：

- 制造背景：设备技术支持知识库；
- 电商背景：商品运营与客服知识库；
- 财务背景：财务制度与报销咨询知识库；
- 测试背景：技术文档与故障排查知识库；
- 教育背景：某一具体课程或考试知识库；
- 没有行业背景：开源软件文档与技术支持知识库。

## EduAgent

不要把四个教育 Agent 原样写进简历。

应该从中选择一种最适合自己的业务能力：

- 结构化审核；
- 多维度分析；
- 有状态对话；
- 工具调用与任务流程。

然后改造成一个聚焦的行业工作流或 Agent。

例如：

- 制造背景：设备故障诊断与维修引导；
- 电商背景：客服工单分析与回复辅助；
- 财务背景：报销材料完整性检查；
- 测试背景：AI 应用评测与 Bad Case 管理；
- 人力背景：招聘材料分析与面试问题生成；
- 教育背景：错题分析与学习任务规划。

## 项目完成到什么程度就可以写简历

不用等待项目全部完善。

至少完成：

1. 业务场景清楚；
2. 主流程可以运行；
3. 有一个自己真正实现的核心功能；
4. 能讲清为什么选择这些技术；
5. 有三到五个测试问题或 Bad Case；
6. 能用三分钟讲清整个项目。

达到这些要求后，就可以先写入简历、开始投递，再继续完善。

# 二、企业真正想从项目中看到什么

当前 AI 应用开发岗位更重视：

- Python 开发能力；
- RAG、Agent、Tool Calling 等核心机制；
- FastAPI 或类似接口开发；
- 数据库和向量数据库；
- 工作流和状态管理；
- 模型与业务系统集成；
- Docker、Linux、日志和异常处理；
- 项目评测与 Bad Case；
- 能否结合业务完成落地。

Dify 可能在部分岗位中作为可选框架出现，但通常只是 LangChain、LangGraph、LlamaIndex 等工具中的一种，不是岗位能力的核心。

因此：

> 可以使用 Dify 快速验证流程，但项目不能只剩下“用 Dify 拖了一个工作流”。

主项目更应该体现：

- 业务理解；
- Python 代码；
- RAG 或 Agent 原理；
- 接口和数据处理；
- 问题分析和优化。

# 三、项目改造只需要完成五步

## 第一步：选择自己熟悉的领域

优先顺序：

```text
以前的工作
→ 原专业
→ 实习经历
→ 长期兴趣
→ 数据容易获得的通用场景
```

熟悉领域的价值是：

- 知道谁会使用；
- 知道真实流程；
- 知道常见问题；
- 知道专业术语；
- 更容易准备 Bad Case；
- 面试时更容易讲清。

不要因为某个方向热门，就强行做自己完全不了解的医疗诊断、金融交易或工业视觉。

## 第二步：把学科答疑改造成行业 RAG

原项目骨架可以保留：

```text
FAQ 高置信匹配
→ 命中后直接返回标准答案
→ 未命中进入知识库检索
→ 检索相关文档
→ 大模型基于文档回答
```

但必须替换：

- 用户；
- FAQ；
- 知识文档；
- 业务术语；
- Metadata；
- 测试问题；
- Bad Case。

### 不是只改名字

错误改法：

```text
学科在线答疑系统
→
企业在线答疑系统
```

正确改法：

```text
FAQ 从“课程问题”
改为“设备错误码、售后政策、报销要求或技术报错”

知识文档从“课程讲义”
改为“设备手册、商品规则、财务制度或 API 文档”

用户从“学生”
改为“维修人员、客服、员工、测试或实施人员”
```

## 第三步：从 EduAgent 中只选一种核心能力

EduAgent 包含四种可迁移能力。

### 1. 知识问答

适合改成：

- 企业知识库；
- 技术支持；
- 制度咨询；
- 商品客服。

如果项目一已经是完整 RAG，项目二不要继续以知识问答为核心。

### 2. 结构化审核与人工复核

原来是试卷批改，可以改成：

- 报销材料检查；
- 合同条款提示；
- 质量文档审核；
- 客服回复质检；
- 入职材料检查；
- 测试用例评审。

通用流程：

```text
材料输入
→ 信息抽取
→ 规则检查
→ 大模型分析
→ 结构化结果
→ 人工确认
```

### 3. 多维度分析

原来是简历审查，可以改成：

- 客服对话质量分析；
- 商品内容质量检查；
- 用户反馈归因；
- 工单问题分析；
- 项目文档完整性检查；
- 营销文案审核。

这类项目更准确的名称通常是：

> 多维度分析工作流

不一定要包装成多 Agent。

### 4. 有状态的多阶段对话

原来是模拟面试，可以改成：

- 故障诊断；
- 需求澄清；
- 售后问题排查；
- 材料补充引导；
- 旅行需求收集；
- 学习计划跟踪。

通用流程：

```text
收集信息
→ 判断当前阶段
→ 动态追问
→ 调用知识或工具
→ 检查结果
→ 输出建议或转人工
```

## 第四步：删除不需要的高级技术

不要为了让项目显得高级，强行加入：

- 多 Agent；
- MCP；
- A2A；
- GraphRAG；
- LoRA；
- 模型微调；
- 复杂知识图谱。

每增加一项技术，必须回答：

1. 原来遇到了什么问题；
2. 为什么现有方案不能解决；
3. 新技术具体解决了什么；
4. 如何验证它有效。

回答不了，就先不加。

## 第五步：完成最小可讲版本后立刻使用

不要先做：

- 复杂前端；
- 大量权限系统；
- 全套运营后台；
- 十几个 Agent；
- 完整商业平台；
- 大规模正式评测。

先完成：

```text
一个明确输入
→ 一条核心流程
→ 一个真实输出
```

然后补充：

- 一个有价值的技术优化；
- 三到五个 Bad Case；
- 一段项目介绍；
- 三到五条简历描述；
- 三分钟项目讲解。

完成后就可以先投递，项目继续边投递边优化。

# 四、不同背景应该怎样组合项目

## 1. 制造、机械、自动化

- 项目一：设备技术支持知识库与故障问答系统；
- 项目二：设备故障诊断与维修引导工作流；
- 可选项目三：维修工单分类或质量文档审核。

## 2. 电商、运营、市场

- 项目一：商品运营与平台规则知识库；
- 项目二：客服工单分析与回复辅助工作流；
- 可选项目三：评论主题与情感分类。

## 3. 财务、会计

- 项目一：企业财务制度与报销咨询知识库；
- 项目二：报销材料完整性检查与风险提示工作流；
- 可选项目三：财务数据问答或 Text2SQL。

## 4. 软件开发、测试

- 项目一：技术文档与故障排查知识库；
- 项目二：AI 应用评测与 Bad Case 管理平台；
- 可选项目三：Prompt 与接口回归测试系统。

## 5. 教育、培训

- 项目一：具体课程或考试知识库；
- 项目二：错题分析与学习任务规划工作流；
- 可选项目三：问题分类或学习意图识别。

## 6. 人力资源、行政

- 项目一：企业制度与员工办事知识库；
- 项目二：招聘材料结构化分析与面试问题生成；
- 可选项目三：会议纪要与任务跟踪工作流。

## 7. 新闻、传媒、舆情

- 项目一：新闻资料检索与专题研究助手；
- 项目二：舆情专题报告生成工作流；
- 可选项目三：主题、情感或风险分类。

## 8. 没有明显行业背景

- 项目一：开源软件文档与技术支持知识库；
- 项目二：技术问题诊断与解决方案生成工作流；
- 可选项目三：AI 应用自动评测平台。

# 五、两个项目应该体现不同能力

## 项目一重点证明 RAG 深度

重点选择：

- FAQ 分流；
- 文档解析；
- Chunk；
- Embedding；
- BM25 或向量检索；
- Hybrid Search；
- Reranker；
- Metadata；
- 引用；
- 拒答；
- 评测。

不需要全部加入，选最符合业务的部分。

## 项目二重点证明业务流程能力

重点选择：

- State；
- Node；
- 条件路由；
- Tool Calling；
- 结构化输出；
- 人工介入；
- 失败重试；
- 结果校验；
- 状态恢复。

两个项目不要都把完整 RAG 链路重复一遍。

# 六、项目一：RAG 改造时必须注意的三个问题

## 1. FAQ 数据存 MySQL，不代表在 MySQL 中做语义检索

更准确的流程是：

```text
FAQ 存入 MySQL
→ 应用层对用户问题和标准问题进行语义匹配
→ 高置信命中直接返回
→ 否则进入 RAG
```

需要说清楚相似度是如何计算的。

## 2. 0.85 不是所有项目的固定阈值

阈值应该根据验证问题进行调整。

可以在项目中写：

> 根据验证问题中的相似度分布设置 FAQ 高置信阈值，降低误命中后直接返回错误答案的风险。

## 3. FAQ 分流和混合检索不是一回事

FAQ 分流决定是否直接返回标准答案。

混合检索是在进入 RAG 后，使用 BM25、Dense、Sparse 等方式召回知识文档。

不要混写。

---

# 七、EduAgent 改造时必须注意的三个问题

## 1. 不要保留四个完全不同的 Agent

选择一个最适合自己的业务流程做深，比同时写四个 Agent 更有价值。

## 2. 多节点不等于多 Agent

```text
抽取节点
→ 检索节点
→ 生成节点
→ 校验节点
```

通常是 LangGraph 工作流，不是多 Agent。

## 3. MCP 不是普通函数调用

只有真正实现 MCP Server、MCP Client、Tool Schema、工具发现和协议连接，才适合写 MCP。

否则写：

> Tool Calling / 工具调用。

不需要写很长的项目报告，但必须能回答：

1. 谁在使用；
2. 原来有什么问题；
3. 项目是什么性质；
4. 数据来自哪里；
5. 核心流程是什么；

8. 一个具体功能怎么实现；

10. 有哪些 Bad Case；
11. 如何判断项目效果；
12. 后续还能怎么优化。

# 十一、补充：Dify 应该怎样使用

Dify 不需要作为项目重点。

它更适合：

- 快速验证 Prompt；
- 快速验证知识库；
- 搭建固定流程 PoC；
- 给业务人员展示原型；
- 对比代码实现前后的差异。

简历中可以写：

> 使用 Dify 快速验证业务流程和 Prompt 方案，核心检索、工作流和服务能力使用 Python、LangGraph、FastAPI 等完成。

前提是确实这样做过。

只使用 Dify 搭建一个简单知识库，不足以作为主项目。

# 十二、最后记住四句话

```text
先选业务，再选技术。
课程项目必须改数据、流程和问题，不能只改名称。
一个 RAG 主项目，加一个业务工作流项目，已经足够形成主线。
完成最小可讲版本后立即使用，不要等项目完美。
```

真正适合求职的项目，不一定技术最多，但应该做到：

- 与本人背景有关；
- 与目标岗位有关；
- 业务问题具体；
- 数据可以获得；
- 主流程可以运行；
- 技术选择合理；
- 有一个核心功能能深入讲；
- 有 Bad Case；
- 能够写入简历；
- 能够承受面试追问。
