## 一、项目主线

### 问题：介绍一下你的 RAG 项目流程。

项目目标是解决 `[业务场景]` 中知识分散、更新频繁且人工查询成本高的问题。离线侧将 PDF、Word、网页等文档解析、清洗、按结构切块，生成 embedding 并写入向量库；在线侧先识别问题类型和知识库范围，再进行向量/关键词召回、重排，把带来源的上下文交给大模型生成答案。最后返回引用，并记录问题、召回、答案和反馈用于评测。我的职责是 `[真实模块]`，遇到的主要问题是 `[真实问题]`，通过 `[真实改动]` 把 `[真实指标]` 从 `[改前]` 优化到 `[改后]`。

### 问题：为什么不用普通搜索、FAQ 或微调？

FAQ 适合问题和答案稳定、数量有限的场景；全文检索适合精确编号和关键词；RAG 适合用户问法多样、知识需要频繁更新且需要引用依据的场景。微调解决的是模型行为或领域表达，不适合频繁注入事实知识：更新成本高、难以逐条溯源。因此我的选择是 FAQ 处理高频固定问法，RAG 处理长尾知识问答；若有结构化实时数据，则另走数据库查询。

## 二、项目真实性与职责

### 问题：你具体负责什么？项目难点是什么？

我会按“输入—动作—结果”回答：我负责 `[文档解析/检索链路/接口/评测]`，具体完成了 `[两个真实模块]`。最难的问题是 `[例如复杂表格导致召回缺少表头]`，我先通过日志和失败问答定位是解析问题而非模型问题，再改为 `[表题+表头+行组]` 的切块并增加回归集；结果是 `[真实结果]`。没有量化结果时，不能编造百分比，应说明抽检样本、失败现象和验证方法。

## 三、软技能与交付

### 问题：客户觉得效果不好、工期又到了怎么办？

先把“效果不好”拆成可验证问题：数据缺失、召回不准、答案表达、响应慢还是需求范围变化；再用日志和样例复现。对已承诺范围交付可用闭环，对高风险问题给出明确限制、临时降级和迭代计划，并把验收样例、负责人和时间点写入记录。不要承诺“模型一定完全准确”，而要对齐可量化标准，如关键问题通过率、引用覆盖率、人工转接率和响应时间。

## 四、场景设计

### 问题：给你 PDF/Markdown，如何从零设计 RAG？

先问四个约束：文档规模与更新频率、是否有图片表格、权限模型、准确率和时延目标。随后设计：解析与对象存储、结构化 chunk 与 metadata、向量/关键词混合召回、rerank、引用式生成、离线评测和线上监控。MVP 先支持主格式和核心问答；生产版再补权限、增量索引、失败回退、监控和灰度。对于“4 个知识库”，优先用知识库 metadata 和权限过滤缩小候选范围，再在目标库内检索，不依赖模型自由猜分类。

## 五、数据预处理与切块

### 问题：文档如何处理、PDF 如何切块？

先区分原生文本 PDF、扫描件、图片、表格和结构化表。原生文本按标题、段落、列表恢复结构；扫描件走 OCR 并记录置信度；表格保留表头、行列、单位和页码；图文混排按坐标恢复阅读顺序。切块先按语义和结构边界，超长块再二次切分，overlap 只做边界兜底。每块保存 `doc_id、version、page、section_path、content_type、source_uri、permission`，保证回溯、权限过滤和增量更新。

### 问题：表格、图片、跨页表怎么处理？

表格不能只抽文字。将表题、表头、行名、列名、单位和脚注转为 HTML/Markdown/JSON；大表按“表题+必要表头+行组”切，跨页先验证表头与 schema 一致再合并。图片要绑定相邻标题与正文，保留页码和原图引用；扫描件低置信内容隔离抽检。解析失败时记录文件、页码、解析器版本和错误类型，回退页级文本、OCR 或原图，不把错误内容直接入向量库。

## 六、Embedding 与向量库

### 问题：为什么选这个 embedding 模型？能直接替换版本吗？

选型看语言、领域、向量维度、检索效果、推理成本和部署条件，而不是只看榜单。模型升级即使维度相同，也不应直接混用旧新向量，因为向量空间分布可能变化；正确方式是离线重建索引、双索引灰度对比、验证召回后切流。元数据除文本外应保存来源、页码、知识库、版本、权限和时间，检索时先做 metadata filter 再做相似度召回。

### 问题：为什么用 Milvus/FAISS/ES/pgvector？

数据量小、单机原型可用 FAISS 或 pgvector；需要文本检索和筛选可用 ES；需要大规模向量检索与集群能力可选 Milvus。选型必须结合项目规模和运维能力，不能说某个库“绝对最好”。

## 七、数据库配合

### 问题：Redis、Milvus、MySQL 怎么分工？

若项目同时使用三者：Milvus 存向量和检索 metadata；MySQL 存用户、权限、文档元数据、配置和问答日志；Redis 存热点 FAQ、会话短期状态、检索缓存和限流。原文件放对象存储。请求进入后先认证并确定知识库范围，再读缓存或检索 Milvus，最后用 MySQL/对象存储回溯详情。实际项目未使用其中某一项时应如实说明替代方案。

## 八、检索、召回与混合检索

### 问题：语义、全文和混合检索分别何时用？

语义检索适合用户问法与文档表述不一致；全文/BM25 适合产品名、编号、法规条款等精确词；混合检索用于同时要求语义理解和精确约束的场景。融合前要做分数归一化或采用 rank fusion，不能直接比较不同检索器的原始分数。topK 通过离线评测选择：太小会漏召回，太大增加 rerank 和上下文成本。

### 问题：检索不准如何定位？

按链路排查：正确文档是否入库 → chunk 是否完整 → query 是否表达真实意图 → 召回是否包含正确块 → rerank 是否把正确块压低 → prompt 是否使用了正确上下文 → 生成是否脱离资料。每层都保留 trace，避免看到错答案就直接怪模型。

## 九、Rerank

### 问题：为什么有向量召回还要 rerank？

embedding 通常是双塔编码，适合从大规模候选中快速粗召回，但 query 与 passage 交互有限。reranker 联合看 query 和候选文本，精度更高但成本更大。因此常见链路是召回 topK → rerank → 取 topN 给 LLM。若 rerank 慢，可减少候选、批处理、缓存、量化或按问题类型跳过；前提是用评测集证明对效果的影响。

## 十、意图与 FAQ/RAG 路由

### 问题：FAQ + RAG 怎么路由？分类错了怎么办？

先识别问题是否是固定高频问法、知识库问答、闲聊、越权或知识库外问题。FAQ 通过精确/高置信匹配快速返回；复杂或低置信问题走 RAG；知识库外应澄清、转人工或明确拒答。分类模型可以是规则、embedding、轻量分类器或 LLM，但必须设置置信度与兜底。分类准确率用有标签测试集计算 precision、recall、F1，并重点看哪些类别容易互相混淆。

## 十一、多轮上下文与记忆

### 问题：上下文太长、用户换话题怎么办？

不把所有历史原样拼进 prompt。保留最近关键轮次、结构化查询条件和任务摘要；长历史做摘要或按需检索。用户明显换话题时重置检索上下文，只保留必要身份和权限信息。长期记忆只存对用户有价值且获得授权的信息，并设置过期与删除机制。

## 十二、MCP 与 Function Calling

### 问题：MCP 和 Function Calling 有什么区别？

Function Calling 是模型根据函数 schema 选择工具并生成参数的能力；MCP 是把外部工具、资源和提示能力标准化暴露给客户端/模型的协议。两者可结合：MCP Server 暴露工具，应用层再以函数 schema 或其他方式让模型调用。无论哪种方式，都要做参数校验、权限控制、超时和审计。

## 十三、幻觉、安全与权限

### 问题：RAG 如何减少幻觉？

先保证检索质量，再要求模型仅基于上下文回答并给出来源；无可靠依据时明确“不确定”或转人工。通过引用匹配、答案与上下文一致性、人工抽检定位问题。提示词注入则通过输入识别、系统指令隔离、工具最小权限、敏感操作二次确认和输出过滤共同防护。权限过滤应尽量在检索前/检索中完成，不能先召回越权文本再让模型“不要说”。

## 十四、性能与并发

### 问题：RAG 回答慢怎么优化？

先拆分耗时：鉴权、query 改写、召回、rerank、prompt 拼接、首 token、完整生成和网络。对热点 FAQ/检索结果做缓存；并行独立召回；控制候选数和上下文长度；批处理或量化 rerank；采用流式输出改善感知时延。高并发还要配置连接池、队列、限流、超时、熔断和降级，而不是只增加线程。

## 十五、部署与接口

### 问题：FastAPI/Docker 上线后出问题怎么排查？

从请求 trace_id 开始，检查接口参数、应用日志、容器状态、环境变量、模型服务、数据库连接和网络。若本地正常线上异常，优先比较镜像版本、依赖、配置、挂载文件、权限和资源限制。接口需要区分同步问答、文件上传和流式响应；幂等请求、超时和重试策略要明确，敏感日志需要脱敏。

## 十六、评估指标

### 问题：RAG 准确率/召回率怎么评估？

先构建覆盖高频、长尾、表格、否定条件和知识库外问题的评测集，并标注相关文档。检索层看 Recall@K、MRR、nDCG 或人工命中率；生成层看答案正确性、引用正确性、faithfulness、answer relevancy；系统层看 P50/P95、TTFT、失败率和用户反馈。所有提升要说明 baseline、样本量、时间范围和评测方法。

## 十七、模型基础

### 问题：Transformer、自注意力、temperature/top_p/top_k 怎么回答？

Transformer 用自注意力建模 token 间关系，编码器更适合理解和表征，解码器更适合自回归生成。注意力核心是用 Q 和 K 计算相关性，经 softmax 得到权重，再对 V 加权汇聚。temperature 控制采样随机性；top_k 限制候选数量；top_p 从累计概率候选中采样。知识问答通常降低随机性，并不能仅靠低温度解决幻觉。

## 十八、复习顺序

先准备：项目流程、数据与切块、检索与 rerank、数据库分工、幻觉治理、个人职责和一个真实难点。再准备：多轮上下文、权限、部署、评测和性能。进阶内容包括索引参数、融合策略、RAGAS、复杂表格/长文档和生产治理。

# 逐题补全答案（技术题）

## 1. RAG 项目主线

### 问题：RAG 的目标是什么？怎么证明达到目标？

目标不是笼统“让模型更聪明”，而是让模型在 `[私有/频繁变化]` 知识上回答可追溯、可更新的问题。证明时拆成三层：检索层看正确文档 Recall@K；答案层看人工正确率/引用正确率；业务层看人工咨询量、解决率或满意度。比较对象、样本数和统计周期必须说清楚。

### 问题：数据来源、更新频率和脏数据怎么答？

说明谁提供数据、授权范围、格式占比和更新方式。增量更新用文档 hash 或版本号判断变化：新增文档直接解析入库；变更文档先删除/失效旧 version 的 chunk 再写新版本；删除文档同步删除索引和对象存储引用。脏数据包括重复文档、乱码、空页、失效版本和错误 OCR，进入隔离队列而非直接入库。

## 2. 预处理与切块补充

### 问题：父子块、语义块、按标题块分别何时用？

按标题块适合制度、手册等层级清晰文档；语义块适合无稳定标题的长文本，通过段落/句子边界保持主题一致；父子块适合既要精确召回又要补全上下文的场景，子块检索、父块交给 LLM。不要把三种方案说成互斥关系，可以按文档类型组合。

### 问题：切块大小、overlap 设多少？

先以 token 而不是“汉字数”理解大小，并根据文档类型、embedding 模型和最终上下文预算确定。可从一个保守配置开始，在标注问答集上调 Recall@K、答案正确率、上下文 token 和延迟；发现条件句或列表被切断时优先调整结构边界，最后才加 overlap。不给固定万能数字，真实项目就报真实配置与测试结论。

### 问题：多模态文件如何保证图文顺序？

用页内坐标、栏位和 block 类型重建阅读顺序；图片绑定最近标题和说明文字，保留 page/bbox/image_id。对多栏文档不能依赖 PDF 原始文本流；应抽样比对渲染页，检查标题、正文、图片和表格是否错位。

## 3. embedding 与索引补充

### 问题：向量索引 IVF_FLAT、HNSW、IVF_PQ、FLAT 怎么选？

FLAT 精确但规模大时慢，适合小数据或做基准；IVF 先聚类再搜部分桶，靠 nprobe 平衡速度和召回；HNSW 图索引通常召回高、查询快但内存和构建成本更高；IVF_PQ 用压缩换内存和精度。选择依据是数据量、内存、写入频率、目标 Recall 和 QPS，先用 FLAT/高精度配置建立 baseline，再压测调参。

### 问题：BERT 为什么不直接替代 BGE？

BERT 是通用语言表征模型，原始训练目标不等于检索相似度；BGE 等 embedding 模型通常在 query-passage 对比学习上优化，且对 query 指令、向量归一化等有特定要求。不是 BERT 完全不能用，而是默认检索效果和工程约定通常不如专门检索模型，必须以项目评测验证。

## 4. 数据库与权限补充

### 问题：Milvus 只存向量吗，原文在哪里？

可以存短文本和 metadata，但原始文件、长正文、图片一般放对象存储或关系库；Milvus 保留检索需要的向量、chunk 文本/摘要、doc_id、页码和权限字段。这样索引轻、原文可版本化，检索后再按 source_uri 回溯。

### 问题：多租户如何防止越权召回？

文档/chunk 写入时绑定 tenant_id、kb_id、role/ACL；请求先完成认证，再把可访问范围作为 metadata filter 与向量检索同时执行。不能先全库召回再让 LLM 忽略越权结果；日志中也不能记录明文敏感上下文。

## 5. 检索与融合补充

### 问题：BM25 与 embedding 各自缺点是什么？

BM25 依赖词项匹配，口语表达和同义改写时容易漏；embedding 擅长语义但对编号、版本、专有缩写可能不够精确。混合检索通过并行召回取长补短，再用 RRF 或归一化加权融合；权重根据离线集调，不凭感觉固定。

### 问题：Query 改写怎么避免语义漂移？

只补全指代、规范化术语、拆分复合问题，不改变用户约束；改写 prompt 明确要求保留时间、数量、否定条件和实体。保留原 query 与改写 query 并行/回退检索，记录改写结果；低置信或高风险问题先澄清而不是擅自扩写。

### 问题：topK、topN 怎么确定？

topK 是粗召回候选数，取决于索引召回质量和 rerank 成本；topN 是给 LLM 的最终上下文数，取决于上下文预算和信息密度。用 Recall@K 找到“正确文档开始饱和”的候选区间，再用答案质量和时延决定 topN；不同意图可用不同配置。

## 6. rerank 补充

### 问题：Cross-Encoder 为什么更准但更慢？

双塔分别编码 query 和 passage，可提前离线建库，查询时只算一次 query 向量；Cross-Encoder 把 query-passage 一起输入模型，能看到细粒度交互，因此相关性更准，但每个候选都要跑一次模型。它应只用于小候选集的精排，不取代大规模向量召回。

### 问题：rerank 分数能直接当概率吗？

通常不能。不同模型的分数标度和温度不同，更多用于同一次候选集合内排序。若要跨模型/跨请求使用阈值，需要在验证集上校准；不能把某个分数天然解释成“80% 正确”。

## 7. 路由、多轮与记忆补充

### 问题：短问题“查一下这个”怎么办？

先结合最近对话、当前知识库和已知对象补全；仍无法确定时提出最小澄清问题，例如“请问要查询哪份文档或哪个产品？”不能默认检索全库并生成看似合理的答案。

### 问题：历史信息冲突时以谁为准？

当前用户明确输入优先于历史摘要；业务数据库/权威文档优先于模型记忆；冲突若影响结论，就展示来源差异或要求确认。上下文中标注时间和来源，避免旧版本规则覆盖新版本。

## 8. 安全、性能、部署补充

### 问题：如何判断幻觉在召回还是生成？

先检查正确证据是否被召回；再检查是否被 rerank 和 context builder 丢弃；若证据已在 prompt 但答案仍违背，才是生成/提示约束问题。每次请求保存 query、候选、最终 context、模型输出和引用，才能定位。

### 问题：提示词注入怎么防？

将外部文档视为不可信数据而非系统指令；系统提示与检索内容分区；工具权限由服务端校验，不由模型文本决定；敏感操作二次确认；对输入和输出做安全检测和审计。仅靠“忽略注入”提示词不够。

### 问题：Docker 与线上排查顺序？

先用 trace_id 对齐请求、应用和依赖日志，再检查容器状态/资源、环境变量、镜像与依赖版本、挂载文件、网络/DNS、模型服务和数据库连接。把配置外置且版本化，避免本地环境变量掩盖线上差异。
