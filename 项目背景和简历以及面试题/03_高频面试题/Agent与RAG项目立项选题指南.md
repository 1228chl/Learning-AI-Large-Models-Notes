# Agent 与 RAG 项目立项选题指南

> 适用对象：AI 就业班学生，需要为简历打磨一个能通过面试的 Agent/RAG 项目。
> 使用方式：先读第 0 章（好项目的标准），再浏览第 1-9 章的场景，选中方向后填写附录 B 的立项工作纸。

## 0. 什么样的项目才是"好项目"

### 0.1 两个一票否决标准

在选方向之前，先用两个测试淘汰不成立的项目：

**测试一（RAG 项目）："为什么不直接发 PDF？"**

如果你的 RAG 系统做的事情 = 把文档内容检索出来，那用户为什么不直接 Ctrl+F 查 PDF？

| 能过关 | 不能过关 |
|--------|---------|
| 用户需要在 **15 秒内** 从 **500 份文档** 中找到答案，人翻不过来 | 用户只是想查"年假几天"，公司手册就 20 页，Ctrl+F 更快 |
| 用户的问题和文档表述 **不在同一个语言/术语体系** 里（"机器异响" ≠ 手册里的"设备异常振动"） | 文档少、标准、固定，不需要语义检索 |
| 检索结果需要 **跨文档推理**（A 文档说原因，B 文档说方案，需要拼在一起） | 每个问题只对应一个文档的一个段落 |

**测试二（Agent 项目）："一个 LLM + 一个 Prompt 能搞定吗？"**

如果你的多 Agent 系统做的事情，用一个精心设计的 prompt + 一次 LLM 调用就能完成，那 Multi-Agent 就是过度设计。

| 能过关 | 不能过关 |
|--------|---------|
| 任务涉及 **多个系统**（ERP + WMS + MES），一个 LLM 调不了所有 API | 任务只是"分析一段文本"，单次 LLM 调用就够了 |
| 不同步骤需要 **不同权限**（查询可以自动，执行需要人工确认） | 所有步骤都是只读查询，没有权限差异 |
| 需要 **状态追踪和异常恢复**（第 3 步失败了不能从头再来） | 任务只有 2-3 步，失败重跑就行 |

### 0.2 项目成立的因果链

一个好的项目，技术选型必须能追溯到用户画像和数据量：

```
用户画像（谁在用、多少人、什么频率、什么终端、响应时间要求）
    ↓
数据量（多少文档/SKU/运单、什么格式、更新频率）
    ↓
技术决策（为什么用 Milvus 而不是 ES？为什么 chunk_size 是 512？为什么需要 RRF 融合？）
```

面试官追问"为什么选这个技术"，学生不能回答"因为比较快"。必须回答："我的数据量是 X，QPS 是 Y，延迟要求是 Z，所以选了 A 而不是 B。"

### 0.3 你能讲清楚这 3 个关键决策点吗？

任何一个项目，学生必须能脱稿讲清楚 **至少 3 个技术决策点**：

- "别人都选 A，我选 B，因为我的用户场景下 B 更合适。具体原因是……"
- "这个参数默认是 1024，我调到了 512，因为我观察到的数据特征是……"
- "这里用了 RRF 融合而不是加权求和，因为两种召回的打分不在同一个量纲上……"

如果项目里找不到 3 个这样的决策点，说明项目深度不够。

### 0.4 常见不合格项目对照表（反面教材）

以下案例**看起来像一个项目，但实际不成立**。对照你自己的项目想法，如果命中了左边任何一行，需要重新想。

| 不合格案例 | 为什么不合格 | 怎么改 |
|-----------|-------------|--------|
| "做一个企业内部知识库 RAG，员工可以搜公司制度" | 公司制度就 50 份文档，Ctrl+F 搜 PDF 够用了。没有跨文档推理需求。 | 加上约束：客服在电话中需 30 秒内找到答案，涉及 500+ 份 SOP，且问题常跨文档（A 文档说原因，B 文档说方案） |
| "做一个电商客服机器人，回答用户咨询" | "这件衣服什么面料"→查商品详情页就能回答。这不是 RAG 问题，是查数据库问题。 | 改成：用户问"这件和那件有什么区别"，需要分别检索两件商品并做对比——这是 RAG 检索 + Agent 对比的逻辑 |
| "做一个 Multi-Agent 系统，包含对话 Agent、分析 Agent、生成 Agent" | 这三个 Agent 做的事情可以是一个 LLM 三次调用的结果。Agent 拆分的理由是"每个 Agent 负责一个任务"，但没说为什么一个 Agent 不行 | 必须说明：为什么这三个任务需要不同权限、不同工具、不同系统访问能力 |
| "做一个 Agent 自动处理订单：接单→查库存→发货" | 这是传统工作流/ETL 的经典场景，一个规则引擎就能做。Agent 的附加价值在哪？ | 必须加异常分支：库存不足→查替代品→调拨→通知客户，这才需要 Agent 的判断和路由 |
| "用 RAG 做一个法律咨询系统，用户问法律问题就回答" | 法律建议涉及责任归属，AI 回答错了谁负责？而且法律咨询的本质是"你的具体情况适用哪条法律"，不是"这条法律是什么意思" | 改成：合规检索（上架前查某句话能不能写），不涉及给用户提供法律建议，只提供法规依据供人判断 |
| "做一个 Agent 管理项目进度：分配任务→催进度→汇总报告" | 这是一个项目经理的日常工作，Jira+Trello 已经做完了。Agent 的价值增量不明显 | 必须找到"人力做不到而 Agent 能做到"的点：比如跨 5 个项目的资源冲突检测+自动建议调度方案 |
| "做一个政府规范性文件合法性审查系统，给法制办用" | 一个地级市法制办只有 3-5 个人，全国才多少个市？没有商业市场。这是政府内部流程，不是学生能碰到的用户。 | 用户画像不成立的项目不能做。要选有真实商业市场的方向——用户是一个行业里真实存在的岗位，企业会为这个系统付费。 |
| "做一个三甲医院数据访问审批系统，三权分立" | 只有大三甲有数据管理委员会。区县级医院信息化外包给 HIS 厂商。用户规模太小，且本质是审批工作流——OA 系统就能做。 | 不要为了"合规叙事"硬凹一个不存在的市场。审批工作流 ≠ 多智能体。拆 7 个 Agent 做审批是过度设计。 |
| "我的 Agent 调芝麻信用、运营商、电商记录、设备指纹、黑名单——5 个数据源所以 5 个 Agent" | 调 API 不是 Agent。一个 HTTP 请求+JSON 解析是函数，不是 Agent。Agent 的标志是"做判断"——收到数据后判断结果意味着什么。 | 5 个 API 调用 = 1 个 Agent 的 5 个工具。Agent 数量由业务职责决定，不由 API 数量决定。 |

> **怎么用这个表**：选完方向、写完业务场景陈述之后，回来逐条对照。如果你的项目描述和左边某一行长得像，不要提交给老师——先按右边的方向改。

### 0.5 数据量怎么估算（不要背数字，要会推算）

面试官一定会追问："你这个数据量数字怎么来的？"

以下数字全部来自本文档各场景——但**你不能说"选题指南里写的"**。你需要能说出推算逻辑。

**推算公式（通用）**：

```
数据总量 = 日均产生量 × 运营天数 × 年数

示例：
  日均运单量 50 万 × 异常率 1% = 日均异常 5000 条
  日均异常 5000 × 365 天 × 2 年 = 历史异常记录约 360 万条

chunk 数估算：
  文档类：页数 × 每页约 2-3 个 chunk（按章节切）
  短文本类（维修记录/SOP）：每条 ≈ 1-2 个 chunk
  数据库字段类：按表的字段数 × 表数量

增量估算：
  日均新增 = 日均业务量 × 异常率/缺陷率/故障率
  文档更新 = 每月新增 + 每月修订
```

**面试时如果被追问数字来源**：

| 数字类型 | 可以说的来源 |
|---------|------------|
| 业务规模（日均运单 50 万） | "参考了行业内中型公司的公开数据" |
| 异常率（1%） | "参考了快递行业的平均异常率" |
| 员工数量、团队规模 | "根据业务量反推的人力需求" |
| 设备数量、文档数量 | "根据企业规模做的合理假设" |
| SKU 数量、供应商数量 | "参考了同品类电商的典型规模" |

> **关键**：你不需要数字 100% 准确，但需要**推算过程自洽**。如果日均运单 1 万但 chunk 数 1000 万，面试官会觉得你数字是编的。如果日均运单 50 万且 chunk 7500 条，面试官追问"为什么 chunk 这么少"，你能说"因为每个 chunk 是一条完整的 SOP 或网点信息，不是按字符数拆的"——这就自洽了。

### 0.5b 效果数字怎么来（不要背数字，要会推演）

文档中各场景的"X 分钟→Y 秒"类效果数字（如"8 分钟→30 秒""3 小时→5 分钟"）是**基于场景假设的推演**，不是实测数据。在面试中，你需要能拆解这些数字：

**三层回答结构**：

```
第1层 假设条件：我的场景假设是"客服日均处理 80 条工单，每单需操作 3 个系统，
                人工平均 8 分钟一单"——这个假设基于中型快递公司的公开运营数据。

第2层 推演逻辑：Agent 并行调 4 个子 Agent（诊断/方案/地址/赔付），
                总延迟=最慢那个 ~3 秒，加上人工确认 30 秒。
                所以是 8 分钟 → 30 秒。推演逻辑是"并行化+自动化中间环节"。

第3层 Demo 实测：我的 Demo 用假数据跑了 20 条测试用例，
                端到端 P95 延迟是 XX 秒，人工确认环节另计。
```

> **面试时的正确话术**：不说"我的系统能把 8 分钟变成 30 秒"（这是断言），而是说"按照行业公开数据，中型快递公司客服处理一单异常平均 8 分钟；我的系统并行化后，机器处理部分约 3 秒，加上人工确认约 30 秒——Demo 实测的机器处理 P95 是 X 秒"（这是有条件的推演+可复现的验证）。

**如何获得 Demo 实测数据**：
- RAG 场景：用 `time.perf_counter()` 记录检索+生成的端到端延迟
- Agent 场景：记录每个子 Agent 的执行时间和主 Agent 聚合时间
- 在自检清单第 11 条中记录测试集规模和评测结果

```
问题 1：你有没有特定行业的工作经验或实习经历？
  ├─ 有土木/建筑/工程造价背景 → 翻到第 6 章（工程造价）
  ├─ 有视频/影视/传媒/直播背景 → 翻到第 9 章（娱乐传媒）
  ├─ 有制造业/工厂经验 → 翻到第 4 章（工厂生产）
  ├─ 有电商/零售/客服经验 → 翻到第 2 章（电商）
  ├─ 有金融/风控/信贷经验 → 看场景 F（风控审核）
  └─ 没有特定行业经验 → 继续下一题

问题 2：你想做什么技术方向？
  ├─ 我只想做 RAG，不想碰 Agent → 看场景 H（设备经验共享）、场景 Q（定额检索）、场景 U（合法性审查）、场景 X（临床指南检索）或场景 Z（药品核验）
  ├─ 我想做真多智能体（并行+动态路由）→ 看场景 A（物流异常）、场景 B（电商选品）、场景 C（智能客服）、场景 F（风控审核）、场景 M（医疗数据质量稽核）
  ├─ 我想用真数据做 Demo，不想模拟数据 → 看场景 U/Q/X/Z（政府法律/定额/临床指南/药品核验，数据全公开）
  └─ 我不确定 → 默认场景 A（物流异常处理），人人都收过快递

问题 3：你有没有时间/条件跑 Demo？
  ├─ 我能写代码，有时间做完整 Demo → 任意场景都可选
  ├─ 我能写一些代码，但时间紧 → 优先选纯 RAG 场景（H/Q/U/X/Z），架构简单
  └─ 我代码能力弱，主要靠讲 → 优先选业务逻辑最清晰的场景（A/B/C），面试叙事强
```

**如果你回答了上面 3 个问题还是不确定，默认选场景 A（物流异常处理）**。理由：人人都收过快递、可替代性测试最容易被面试官接受、Agent+RAG 混合、技术决策链完整。

## 1. 物流方向

### 场景 A：快递末端异常处理（Agent + RAG）⭐⭐ —— 推荐

#### 用户画像

| 维度 | 数据 |
|------|------|
| 用户 | 一线客服 200 人，日均处理 80 条工单 |
| 使用场景 | 客服接到投诉 → 输入运单号 → 系统自动识别异常类型 → 给出处理方案 |
| 性能要求 | 异常识别 < 5 秒，方案生成 < 10 秒，简单 Case 自动执行率 > 60% |
| 核心痛点 | 客服需要同时操作轨迹系统、地址库、赔付系统，新手培训周期长 |

#### 数据量

| 数据类型 | 规模 | 说明 |
|---------|------|------|
| 日均运单 | 50 万单 | 中型快递公司一个区域 |
| 日均异常 | 5000 单 | 异常率约 1% |
| 历史异常记录 | 360 万条 | 5000 条/天 × 365 天 × 2 年 |
| 异常处理 SOP | 150 条规则文档 | 50 种异常类型 × 各 2-3 种场景 |
| 赔付标准 | 36 条规则 | 3 品类 × 4 保价等级 × 3 责任方 |
| 网点信息 | 5000+ 网点 | 每个有地址、联系人、可处理异常类型 |
| 总 chunk 数 | ~7500 条 | SOP 2000 + 网点 5000 + 规则 500 |

#### Agent 架构（拆分为 8 个子 Agent + 主Agent）

```
用户输入运单号 → 主Agent（意图识别+任务规划+最终聚合）
                      ↓
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
  异常诊断Agent   方案检索Agent   地址服务Agent    赔付评估Agent
  判断异常类型+   RAG检索SOP+    查询地址库+      判断责任方+
  严重程度       历史判例        地图API补全+     计算赔付金额
  工具:查轨迹    工具:向量检索   网点匹配         工具:赔付规则库
        ↓             ↓             ↓             ↓
        └─────────────┴─────────────┴─────────────┘
                      ↓ 4路结果聚合到主Agent
                 决策Agent（综合评估→自动/人工路由）
                      ↓
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
  执行Agent        审查Agent      通知Agent
  改址/转网点/     独立校验方案    短信/电话话术生成
  发起赔付         合理性          (执行结果经审查
  权限:不同操作    权限:只读       通过后才发送)
  不同确认级别
```

> **拆分依据（对标串讲第1节）**：按**业务职责+工具权限+风险等级**拆分。异常诊断需要判断能力（"地址不详"和"收件人拒收"的处理链路完全不同），方案检索需要 RAG 能力，地址服务需要调外部 API，赔付评估涉及金额和责任方判断需要独立权限。执行和审查分离是因为赔付涉及钱——生成方案的 Agent 不能自己审查自己。

#### 技术决策点

| 为什么 | 答案 |
|--------|------|
| 为什么 8 个子 Agent 而不是更少？ | 按业务职责拆分——异常诊断、方案检索、地址服务、赔付评估是四个独立的业务能力（各有专属工具和权限），需要并行执行。决策 Agent 独立是因为"综合判断"与"执行"要分开。执行、审查、通知三个 Agent 分离是因为赔付涉及钱——执行操作（发起赔付）和审查校验（独立核对金额/品类/责任方）的权限不能混在同一 Agent 里，通知 Agent 只在审查通过后才发送短信。 |
| 为什么 4 个诊断 Agent 并行？ | 异常诊断、方案检索、地址服务、赔付评估互相独立——查 SOP 不需要等地址补全结果，算赔付不需要等方案检索结果。并行执行，总延迟 = 最慢的那个（~3 秒），串行要 12 秒。 |
| 为什么审查 Agent 在执行 Agent 之前？ | "赔付 500 元"涉及钱。审查 Agent 独立校验：品类匹配？保价金额够？责任方判对？三个校验全过，执行 Agent 才能发起赔付。生成方案的 Agent 不能自己审查自己。 |
| 为什么不是传统规则引擎？ | 50 种异常 × 36 条赔付规则 × 5000 个网点，规则组合是指数级的。"地址好像写错了"和"收件地址不对吧"是同一种意思，规则引擎匹配不到这种自然语言变体。 |

#### 可替代性测试

**面试官问：现在快递公司不是已经有异常处理流程了吗？**

> 现有方案是"自动发现 + 纯人工处理"——系统识别出"地址不详"，打标签，转给客服。客服需要：打电话确认地址 → 在系统里改地址 → 判断网点能不能送 → 超区就转网点 → 生成新运单。平均 **8 分钟一单**。
>
> 我的方案是"自动发现 + 自动匹配方案 + 人工确认"——系统识别异常后，自动调地址库补全，自动匹配最近可配送网点，生成完整改址方案。客服只需要确认或修改，**30 秒结单**。
>
> 8 分钟 vs 30 秒，差的不是"发现异常"这一步，而是"从发现到方案"中间的全部人工环节。这就是为什么需要 RAG 检索 SOP + Agent 串联子任务——把"知道怎么做"到"做完"之间的链路自动化。

#### 项目价值

**面试一句话**：把快递异常处理从"人工 8 分钟"变成"系统 30 秒+人工确认"，关键不是自动化，是把"知道该怎么做"到"做完"之间的 7 分半钟省掉。

**为什么这个项目能通过面试**：
- **可量化叙事**："8 分钟→30 秒"是一个面试官 3 秒能记住的数字对比。所有面试官都收过快递，不需要行业背景就能追问
- **权限分级有真金白银**：赔付涉及钱、地址修改涉及隐私——审查 Agent 独立校验、人工确认 Gate 不是设计出来的，是钱逼出来的
- **Agent+RAG 混合**：既展示了 RAG（SOP 检索），又展示了 Agent（多子 Agent 调度），面试可聊的技术点最多
- **可替代性一击必杀**："为什么不让人工直接处理？"→"8 分钟 vs 30 秒"

### 场景 B：电商智能选品（Agent）⭐⭐⭐

#### 用户画像

| 维度 | 数据 |
|------|------|
| 用户 | 电商运营/选品经理，负责一个品类（如母婴/家居）的商品上新 |
| 使用场景 | 每周评估 10-20 款候选商品，回答"下一季卖什么、从哪进货、能不能赚钱" |
| 核心痛点 | 选错一个品 = 库存积压几十万。一个品的调研需要 3 小时，一周 10 个品就是 30 小时 |

#### 数据量

| 数据类型 | 规模 | 说明 |
|---------|------|------|
| 竞品销售数据 | 本店+竞品店铺近 6 个月 | 销量、价格、评价分布 |
| 市场趋势数据 | 搜索热词、品类增长趋势 | 来自生意参谋/抖音罗盘等 |
| 供应商数据 | 1688/义乌等多渠道 | 报价、起订量、交期、资质 |
| 利润模型参数 | 物流费、佣金、广告费、退货率 | 历史均值 + 实时波动 |
| 历史选品记录 | 过去选品+销售结果 | 成功和失败的原因标签 |

#### Agent 架构

```
运营输入品类方向 → 主Agent
                     ↓
   ┌────────┬────────┼────────┬────────┐
   ↓        ↓        ↓        ↓        ↓
趋势分析  竞品分析  供应商比价 利润测算  风险评估
Agent     Agent     Agent     Agent    Agent
(搜索趋势 (爬竞品   (多渠道   (毛利-   (季节性+
+品类增长) 销量/价格) 比价)    费用模型) 规则风险)
   └────────┴────────┼────────┴────────┘
                      ↓
                 汇总Agent（生成选品建议报告）
                      ↓
                 人工决策 Gate
```

> **拆分依据（对标串讲第1、5节）**：5 个子 Agent 对应 5 个独立业务能力，每个访问不同数据源——趋势分析（外部平台数据）、竞品分析（爬虫）、供应商比价（1688等渠道）、利润测算（内部财务模型）、风险评估（平台规则库）。数据源类型不同→工具不同→权限边界不同→应该拆。5 个并行执行，总延迟 = 最慢的那个。

#### 技术决策点

| 为什么 | 答案 |
|--------|------|
| 为什么 5 个子 Agent 并行？ | 趋势、竞品、供应商、利润、风险互相独立——查竞品价格不需要等供应商比价结果，算利润不需要等风险评估。并行执行，一个品的调研从"串行 3 小时"变成"并行 5 分钟"。 |
| 为什么拆 Agent 而不是一个 Agent 串行调 5 个工具？ | 供应商比价 Agent 只需要访问外部渠道数据（爬虫），利润测算 Agent 只需要内部财务参数。如果是一个 Agent 绑全部工具，它就能同时看供应商报价和内部成本——权限边界没了。权限最小化要求不同数据源配不同 Agent。 |
| 为什么不是 BI 报表？ | BI 报表告诉你"过去什么卖得好"，Agent 能回答"如果选这个品，在当前的广告费、物流费、退货率下，毛利还够不够吃"。这是预测和推演，不是统计数据展示。 |

#### 可替代性测试

> 一个母婴运营选"夏季婴儿防晒"新品：查生意参谋看趋势（30 分钟）→ 搜竞品店铺看价格（1 小时）→ 1688 找供应商比价（1 小时）→ 算利润（30 分钟）→ 查广告法和化妆品备案规则（30 分钟）。一个品 3 小时，一周 10 个品 30 小时。
>
> Agent 不是替代人的判断，是把"信息收集+初步分析"从 3 小时压到 5 分钟，让人专注于"这个品到底能不能卖"的最后判断。

#### 项目价值

**面试一句话**：选品决定库存是变成现金还是变成死货。Agent 把"收集信息判断能不能卖"从 3 小时压到 5 分钟。

**为什么这个项目能通过面试**：
- **技术决策有区分度**：为什么不是 BI 报表？BI 告诉你"过去什么卖得好"，Agent 告诉你"如果选这个品，现在的费用结构下利润还够不够吃"——预测 vs 统计
- **多数据源是天然的技术点**：5 个数据源（竞品/趋势/供应商/利润模型/规则）→多 Agent 各管各的→权限隔离。不是为了多 Agent 而多 Agent
- **可量化叙事**："一个品调研 3 小时→5 分钟"

### 场景 C：电商智能客服（Agent + RAG）⭐⭐⭐

#### 用户画像

| 维度 | 数据 |
|------|------|
| 用户 | 店铺客服团队 20 人，日均 2000 次咨询 |
| 使用场景 | 售前"这款和那款有什么区别"、售中"快递到哪了"、售后"破了要退货" |
| 核心痛点 | 客服同时操作 3 个系统（商品、订单、物流），新人培训 2 周才能独立上岗 |

#### 数据量

| 数据类型 | 规模 | 说明 |
|---------|------|------|
| 商品知识库 | 500+ SKU | 参数、卖点、使用说明、对比信息 |
| 售后政策 | 退换货规则 | 按品类区分（服饰/食品/电子产品规则不同） |
| 平台规则 | 淘宝/京东/抖音各不同 | 不同平台的售后时效和责任划分 |
| 订单数据 | 实时查询 | 当前状态、物流轨迹、历史订单 |
| 总 chunk 数 | ~1.2 万条 | 商品库 1 万 + 政策 2000 |

#### Agent 架构

```
用户输入问题 → 意图识别Agent（售前/售中/售后 + 商品/订单/物流）
                     ↓
    ┌─────────┬────────┼────────┐
    ↓         ↓        ↓        ↓
售前Agent   订单Agent  售后Agent  升级Agent
(RAG查商品  (调订单    (RAG查售后  (情绪激烈/
库+对比)    系统)      政策)      金额大→人工)
    └─────────┴────────┼────────┘
                       ↓
                  回复生成Agent
```

> **拆分依据（对标串讲第1、2节）**：按**业务职责+工具权限+风险等级**拆分。主Agent 做意图识别和路由（对标串讲第2节——规则优先+LLM fallback）——"查物流"明确路由到订单Agent，"这件和那件区别"路由到售前Agent。售前、订单、售后三个Agent 访问不同系统（商品库/订单系统/售后政策库），权限互不交叉。升级Agent 独立是因为"我要投诉到12315"的情绪识别是独立的安全能力，不应和业务Agent 混在一起。

#### 技术决策点

| 为什么 | 答案 |
|--------|------|
| 为什么主Agent 用意图路由而不是一个Agent 全做？ | 意图路由决定了"该调哪个子Agent"——查物流走订单Agent（调订单系统），问区别走售前Agent（查商品库），要退货走售后Agent（查售后政策）。如果是一个Agent 绑全部工具，售前查询时可能误操作订单状态——权限边界就没了。路由不是模型拍脑袋，是规则优先（"查物流""退货"明确关键词→直接路由）+ LLM fallback（模糊问题）。 |
| 为什么需要升级 Agent？ | 用户说"我要投诉到 12315"——这不是技术问题，是需要立即转人工的信号。升级Agent 独立于业务Agent，不依赖意图识别结果——不管主Agent 把这句话路由到哪，升级Agent 都能检测到并触发转人工。 |
| 为什么 Agent + RAG 而不是 FAQ 机器人？ | 用户问"这件和那件有什么区别"——FAQ 里没有直接答案，因为"区别"不在某一个 chunk 里，而是需要分别查两件商品再对比。RAG 检索 + Agent 对比，才能回答。 |

#### 可替代性测试

> 新人客服培训 2 周才能独立上岗。因为 500 个 SKU 各有不同的材质、尺码建议、售后规则。智能客服 Agent 让新人只需要判断"Agent 给的答案靠谱吗"——从零搜 3 个系统自己组织语言变成审核一个已有答案。培训周期从 2 周降到 2 天。

#### 项目价值

**面试一句话**：新人客服培训从 2 周降到 2 天。Agent 不是替代客服，是让新人第一天就能独立接客。

**为什么这个项目能通过面试**：
- **意图识别+多系统路由**：售前查商品、售中查订单、售后查政策——三个系统三种权限。Agent 拆分的理由不是因为"复杂"，是因为"不同系统的权限不能混"
- **升级 Agent 是加分项**："我要投诉到 12315"→立即转人工。这个设计让项目从"技术 Demo"变成"生产系统"
- **可量化叙事**："培训 2 周→2 天"

## 3. 以租代购方向

> **注意：简历上写"手机租赁平台风控系统"，不写"以租代购"或"灰产"。以租代购本身是合法商业模式（支付宝官方入口就有）。**

### 场景 F：风控审核流水线（Agent）⭐⭐⭐ 

#### 用户画像

| 维度 | 数据 |
|------|------|
| 用户 | 风控审核员，5 人团队，日均审核 300 单 |
| 使用场景 | 用户提交资料后，系统自动完成初审，人工只复审高风险单 |
| 性能要求 | 自动审核 < 30 秒，高风险单转人工 < 5 分钟 |
| 核心痛点 | 欺诈手段不断变化（伪造信用分截图、冒用身份、团伙作案），规则写死跟不上欺诈演变 |

#### 数据量

| 数据类型 | 规模 | 说明 |
|---------|------|------|
| 信用数据源 | 芝麻信用、运营商在网时长、电商消费记录、社保/公积金 | 5 个外部数据源 |
| 历史订单 | 日均 300 单 × 365 天 × 2 年 ≈ 22 万条 | 含审批结果和履约情况 |
| 欺诈黑名单 | 已知欺诈用户/设备/IP/地址约 2 万条 | 持续更新 |
| 设备型号库 | 500+ 款在租设备 | 参数、折价曲线、历史回收率 |
| 反欺诈规则 | 约 100 条硬规则 + 200 条弱特征 | 硬规则=命中即拒，弱特征=组合判断 |

#### Agent 架构（拆分为 3 个子 Agent + 主Agent）

```
用户提交资料 → 主Agent（OCR提取关键字段+槽位校验+任务规划）
                     ↓
        ┌────────────┼────────────┐
        ↓                         ↓
  身份核验Agent              反欺诈Agent
  判断"这个人是不是真的"      判断"有没有欺诈嫌疑"
  工具:                      工具:
  · query_zhima()            · query_blacklist()
  · query_operator()         · query_device_fingerprint()
  · query_ecommerce()        · query_address_cluster()
  · compare_identity()       · match_fraud_pattern()
  并行调3个接口→交叉比对      并行调3个接口→模式匹配
  姓名/身份证/地址一致性       设备/IP/地址聚集度
        ↓                         ↓
        └────────────┬────────────┘
                     ↓
              决策Agent
              综合评分+风险定级
              ├─ 低风险 → 自动通过
              ├─ 中风险 → 人工复审
              └─ 高风险 → 冻结+人工复核（不自动拒绝）
                     ↓
              人工复审 Gate（中风险的 30%）
```

> **拆分依据（对标串讲第1、5节）**：按**业务职责+数据源类型+风险等级**拆分。身份核验和反欺诈是两个独立的业务问题——"是不是本人"（身份核验）和"有没有欺诈"（反欺诈）需要不同的数据源、不同的判断逻辑。芝麻信用、运营商、电商记录是用于核验身份的；黑名单、设备指纹、地址聚集度是用于检测欺诈的。每个子 Agent 封装一个业务能力+一组相关工具。不是 5 个 API 调用就建 5 个 Agent。

#### 技术决策点

| 为什么 | 答案 |
|--------|------|
| 为什么是 3 个子 Agent 而不是 5 个（每个数据源一个）？ | 调芝麻信用、调运营商、查电商记录——这些不是 Agent，是工具（一个 HTTP 请求+JSON 解析）。Agent 的标志是"做判断"：身份核验 Agent 收到 3 路数据后，判断"张三"和"张X三"是不是同一个人——这是需要语义理解和业务规则的判断。一个 Agent 封装一个业务判断+所需工具，不是一个 API 一个 Agent。 |
| 为什么身份核验和反欺诈要并行？ | 两个 Agent 的业务问题独立——"是不是本人"和"有没有欺诈"互不依赖。并行执行，总延迟 = 两个中较慢的那个（~3 秒），串行要 6-8 秒。在"30 秒内完成审核"的性能要求下，并行决定了自动化率能不能达标。 |
| 为什么决策 Agent 独立？ | 身份核验和反欺诈各自给出自己的结论（"身份一致""有欺诈嫌疑"），但最终的风险定级和路由决策需要综合两者+业务规则。决策 Agent 做的是"综合判断"——身份核验通过但反欺诈报警，该冻结人工复核还是降级通过？决策 Agent 负责这个"最后一步判断"和路由，但拒绝决定权始终在人手里。 |

#### 可替代性测试

> 300 单/天，每单查 5 个数据源+做交叉验证。人审一单 8-10 分钟，300 单就是 50 小时/天，需要 7 个人。自动审核解决 70% 的简单单子，人只处理存疑的 30%，5 个人就够了。
>
> 更关键的是——人的判断会疲劳。第 200 单和第 1 单的判断标准不一样。Agent 不会有这种波动。

#### 项目价值

**面试一句话**：风控审核不是"打分"，是"5 个数据源交叉验证+分级路由"。Agent 的价值不在快，在不漏和不疲劳。

**为什么这个项目能通过面试**：
- **多源数据交叉验证天然驱动多 Agent**：征信、运营商、电商记录、设备指纹、黑名单——5 个源 5 种权限。不是为了多 Agent 而多 Agent
- **分级路由有真金白银**：通过/拒绝/人工复审三级——但"自动拒绝"涉及用户权益，本设计将其改为"高风险→冻结+人工复核"，Agent 只做风险定级和路由建议，拒绝决定权始终在人手里。根据《个人信息保护法》，对个人权益有重大影响的自动化决策，用户有权要求说明并拒绝仅由自动化决策作出决定。
- **规则引擎 vs Agent 的对比清晰**：规则只能查"同一地址 3 个不同身份证"，Agent 能捕捉"同一地址 3 个不同身份证但都通过了基础信用分"——弱特征组合

#### 数据量

| 数据类型 | 规模 |
|---------|------|
| 历史维修记录 | 5 个工厂 × 3 年 × 日均 30 条 = 约 16 万条维修工单 |

| 增量 | 每天新增 300 条维修记录 |

#### 技术决策点

| 为什么 | 答案 |
|--------|------|
| 为什么 RAG？ | 维修手册只能覆盖标准故障的标准方案。"主轴异响"和"主轴转动时有咔咔声"和"Spindle abnormal noise"——三句话关键词毫无重叠，但语义上是同一个故障。RAG 做语义匹配，关键词搜索无法覆盖这类跨表述匹配场景。 |
| 为什么多路召回？ | 路1（文本语义）：故障现象 → embedding检索。路2（设备型号）：型号+故障代码 → 精确匹配。路3（跨语言）：中文故障 → 匹配英文设备手册。三路独立打分不能直接相加（量纲不同），RRF 用排名融合规避归一化问题。 |
| 为什么需要验证 embedding 选型？ | 工业维修场景中英混用严重："伺服电机报 AL-05""PLC 输出模块 LED 不亮""变频器显示 Err-13"。通用 embedding 在中英混合+缩写+行业术语场景下的检索性能可能下降，需用该领域的测试集对比候选模型（如 BGE-M3）的 Recall@k，以实测结果决定选型。 |

#### 可替代性测试

> 16 万条记录。关键词搜索"主轴异响"只能匹配到同样写了"主轴异响"的记录。但最有价值的案例写的是"加工中心主轴运转不平稳，伴随周期性响声"——关键词完全不重叠，语义高度相关。关键词搜索查到 0 条，RAG 能查到。

#### 项目价值

**面试一句话**：老师傅退休带走了 20 年经验。RAG 让 300 个工程师共享 16 万条维修记录，新手也能搜到老师傅才见过的罕见故障。

**为什么这个项目能通过面试**：
- **语义鸿沟故事清晰**："主轴异响" vs "加工中心主轴运转不平稳，伴随周期性响声"——关键词搜索 0 条，RAG 能查到
- **多路召回有业务驱动**：文本语义+设备型号精确匹配+跨语言—三个独立维度天然驱动 RRF 融合
- **纯 RAG 但不薄**：因为有跨表述、跨语言、跨型号三个维度，技术决策点够 3 个

## 5. 医疗数据治理方向

> **定位说明：医疗数据治理不涉及临床诊断（不碰诊疗决策、不需医疗器械认证），聚焦的是数据工程问题——数据质量、合规审批、标准映射、术语编码。合规不是加分项，是准入门槛，这让权限隔离和人工 Gate 有了天然的业务合理性，不是"为了面试编的"。**

### 场景总览

| 子方向 | 核心任务 | 涉及系统 | 特色技术 | 方向 | 难度 |
|--------|---------|---------|-----------|:--:|:--:|
| 数据质量稽核 | 数据入湖→多维度并行检查→分级路由→派单→修复→复检 | HIS/EMR/LIS、数据湖、工单系统 | 多维度并行检查+分级路由+阻断决策 | Agent+RAG | ⭐⭐⭐ |

---

### 场景 M：医疗数据质量稽核流水线（Agent + RAG）⭐⭐⭐

#### 用户画像

| 维度 | 数据 |
|------|------|
| 用户 | 医院数据管理中心 / 数据治理工程师，3-5 人团队 |
| 使用场景 | 数据从 HIS/EMR/LIS 抽取到数据仓库后，自动执行质量稽核，发现问题→分级→派单→追踪修复 |
| 数据规模 | 三甲医院日均产生约 50 万条诊疗数据（医嘱、检验、处方、病历） |
| 核心痛点 | 数据质量靠人工抽查。一个字段的值域错误（如性别=3），可能一个月后才被发现，期间所有用到这个字段的报表和分析都是错的 |

#### 数据量

| 数据类型 | 规模 |
|---------|------|
| 质量规则库 | 完整性/一致性/准确性/及时性/唯一性 5 大类，约 300 条规则 |
| 数据标准文档 | ICD-11（约 5.5 万个编码）、HL7 FHIR R4（约 150 个资源类型）、WS 445-2014（约 1000 个字段定义）、院内字典表 |
| 历史质量问题 | 2 年 × 日均 50 条 = 约 3.6 万条（含问题描述、根因、修复方案、修复效果） |
| 元数据 | 所有源表的字段定义、值域、主外键、数据血缘 |
| 总 chunk 数 | 标准文档约 3 万条 + 质量问题约 3 万条 + 元数据约 1 万条 = 约 7 万条 |

#### Agent 架构（拆分为 6 个子 Agent + 主Agent）

```
数据入湖 → 主Agent（字段解析+元数据提取+任务规划）
                     ↓
        ┌────────────┼────────────┬────────────┐
        ↓            ↓            ↓            ↓
  完整性检查      一致性检查    准确性检查    及时性检查
  Agent           Agent         Agent         Agent
  判断"数据       判断"跨系统    判断"数据       判断"数据
   齐不齐"         数据是否一致"  是否符合标准"   是否在时效内"
  工具:          工具:          工具:          工具:
  · 必填项规则   · HIS查询接口  · ICD-11字典   · 时间戳比对
  · 业务流程规则 · EMR查询接口  · HL7 FHIR规范  · 时效规则库
  · 字段依赖关系 · 比对逻辑     · 值域规则     · 依赖检查
        ↓            ↓            ↓            ↓
        └────────────┴────────────┴────────────┘
                     ↓ 4维度结果返回主Agent
              主Agent 聚合 → 分级路由
              ├─ L1（严重）→ 阻断+紧急通知（人工确认Gate）
              ├─ L2（重要）→ 入湖+打标签+24h修复
              └─ L3（一般）→ 入湖+本周修复
                     ↓
        ┌────────────┼────────────┐
        ↓                         ↓
  根因推荐Agent              追踪复检Agent
  (RAG检索历史类似问题       (监控修复进度→超时升级
   →推荐根因+修复方案)         →修复后重新执行质量规则)
```

> **拆分依据（对标串讲第1、5节）**：按**数据源类型+业务职责**拆分。完整性只需检查本地字段是否为空（毫秒级），一致性需要跨 HIS/EMR 两个系统比对数据（秒级），准确性需要 RAG 检索 ICD-11 和 HL7 标准文档（秒级），及时性检查时间戳逻辑（毫秒级）。四个维度的数据源和执行耗时完全不同。用一个 Agent 串行调四个——总延迟是四者之和。拆成四个 Agent 并行——总延迟是最慢的那个。

#### 技术决策点

| 为什么 | 答案 |
|--------|------|
| 为什么是 4 个检查 Agent 而不是 1 个？ | 完整性和及时性是毫秒级的本地规则检查，一致性需要跨 HIS/EMR 做数据比对（需要调两个外部系统），准确性需要 RAG 检索标准文档（向量检索+LLM）。如果合并成一个 Agent 串行执行——4 步加起来 5-8 秒。并行——总延迟 = 最慢的一致性检查，约 2-3 秒。更重要的是，四个能力互相独立，一致性失败不应阻塞完整性检查的结果。 |
| 为什么 RAG 做规则匹配？ | 一个字段"诊断编码"在去年用 ICD-10，今年升级到 ICD-11。质量规则从"编码必须在 ICD-10 字典表中"变成"编码必须在 ICD-11 字典表中"。RAG 检索最新标准文档，但规则匹配结果仍需人工审核确认——标准文档更新后，RAG 能检索到新版本，但"是否适用"的判断由数据治理工程师做。 |
| 为什么 L1 阻断需要人工 Gate？ | L1 阻断入湖→临床决策支持系统数据断供。Agent 只能建议阻断，数据管理员手动确认后才执行。建议和执行必须分离——这是合规要求。 |

#### 可替代性测试

> 传统数据质量工具（Informatica/Dataphin）的痛点是"规则谁来维护"。300 条质量规则 × 每年几十次标准变更 = 团队一半时间在维护规则。RAG 检索最新标准文档辅助规则更新——数据治理工程师从"从头维护规则"变成"基于检索结果验证和确认"，减少了人工逐一查找标准变更的工作量。

#### 项目价值

**面试一句话**：数据质量稽核不是跑脚本出报告，是"发现→分级→阻断/放行→派单→追踪→复检"一条链。L1阻断入湖涉及下游断供，必须人工确认Gate。

**为什么这个项目能通过面试**：
- **L1/L2/L3 分级路由有真金白银**：L1 阻断入湖→临床决策支持数据断供，Agent 只能建议阻断、人确认。这不只是权限隔离，是"有人为这个决定负责"
- **RAG 做规则匹配有说服力**：诊断编码去年用 ICD-10，今年升级 ICD-11——RAG 检索最新标准文档辅助规则更新，传统数据质量工具的规则更新依赖人工逐一查找标准变更
- **纯数据工程，不碰临床决策**：定位清晰——管数据质量，不管诊疗对错
## 6. 工程造价与土木工程方向

> 同一个施工工艺在不同定额里叫不同名字——"C30混凝土柱"在土建定额里叫"现浇混凝土柱"，在市政定额里叫"混凝土矩形柱"。RAG 填平做法描述和定额子目名称之间的语义鸿沟。

### 场景 Q：工程造价定额与信息价检索（RAG）⭐⭐⭐

#### 用户画像

| 维度 | 数据 |
|------|------|
| 用户 | 造价员/造价工程师，负责编制工程预算和投标报价 |
| 使用场景 | 拿到工程量清单，逐项查定额、套单价、查最新材料信息价 |
| 频率 | 一个项目几千个清单子目，每个都要查 |
| 响应要求 | 投标报价期通常 15-30 天，查询效率直接影响能否按时交标 |
| 核心痛点 | 同一施工工艺在不同定额里叫不同名字——"C30混凝土柱"在土建定额里叫"现浇混凝土柱"，在市政定额里叫"混凝土矩形柱"。造价员靠记忆翻书 |

#### 数据量

| 数据类型 | 规模 |
|---------|------|
| 定额库 | 一个省的建设工程定额约 15-20 本，每本 300-500 页，共约 5 万个定额子目 |
| 材料信息价 | 每月一期，每期约 5000-8000 种材料价格，不同地区不同价格 |

#### 技术决策点

| 为什么 | 答案 |
|--------|------|
| 为什么 RAG？ | 造价员不是"查数据库"（那是计价软件的功能），而是"这个东西该套哪个定额子目"——这是语义匹配问题。"地库地面防水"该套土建定额的"屋面及防水"还是市政定额的"隧道及地下工程"？取决于做法描述。RAG 检索最相似的定额子目+历史项目做法参考。 |
| 为什么多路召回？ | 路1（工艺描述语义）：做法描述→检索最匹配定额子目。路2（材料+规格精确匹配）：C30+直径25mm→精确匹配材料编码。路3（历史项目匹配）：同类项目+同一甲方→历史中标价参考。 |
| 为什么 RRF 融合？ | 历史中标价（路3）和定额子目（路1）不能直接加权——历史低价可能因为投标策略激进。RRF 用排名融合，保证工艺匹配优先，价格信号只做参考。 |

#### 可替代性测试

> 计价软件（广联达/斯维斯）能查定额数据库，但前提是你知道子目编号。图纸上写"地面做法详见苏J01-2019-地1"，你要从做法描述反推该套哪个定额。做法描述和定额子目名称之间有巨大的语义鸿沟——新手造价员最大的时间开销不是"算量"，而是"找该套哪个定额"。RAG 把这步从"翻 5 本定额书+凭经验猜"变成"输入做法描述→Top 5 候选子目→人选"。

#### 项目价值

**面试一句话**：同一个工艺在不同定额里叫不同名字——"C30混凝土柱" vs "现浇混凝土柱" vs "混凝土矩形柱"。RAG 填平了做法描述和定额子目名称之间的语义鸿沟。

**为什么这个项目能通过面试**：
- **语义鸿沟是真实痛点**：新手造价员最大时间开销不是算量，是"图纸上写的这个东西该套哪本定额的哪个子目"
- **多路召回有业务驱动**：工艺语义检索+材料规格精确匹配+历史项目价格参考——三个独立维度。历史低价不能和当前定额直接加权（可能因为投标策略激进），RRF 融合天然合理

## 7. 政府法律公文核对方向

> **定位说明：这个方向有两个独特优势是其他方向不具备的——第一，法律法规全部公开可查，学生 Demo 可以用真数据，不需要"模拟"；第二，中国的法律层级体系（宪法→法律→行政法规→地方法规→规章→规范性文件）天然创造了"上位法追溯"的技术需求，多路召回是业务驱动的，不是设计出来的。**

### 先理解法律层级体系

```
宪法
  ↓
法律（全国人大及其常委会）
  ↓
行政法规（国务院）
  ↓
地方性法规（省/市人大）+ 部门规章（国务院各部委）
  ↓
地方政府规章 + 规范性文件（各级政府部门）

核心规则：下位法不得与上位法冲突。
一份市政府的规范性文件，需要与几十部上位法一致。
```

### 场景 U：规范性文件合法性审查（RAG）⭐⭐⭐

#### 用户画像

| 维度 | 数据 |
|------|------|
| 用户 | 政府法制办/司法局合法性审查科，3-5 人 |
| 使用场景 | 收到一份新起草的市规范性文件草案（如《XX市建筑垃圾管理办法》），在 5-10 个工作日内出具合法性审查意见 |
| 频率 | 市级政府年均出台 50-100 份规范性文件，每份都需要合法性审查 |
| 核心痛点 | 一份文件需要向上追溯几十部上位法。最危险的不是查不到，是根本没意识到该查某部法——"运输建筑垃圾应当取得核准"，如果上位法没设这个许可，本市增设就违法了。审查员没注意到行政许可法第 16 条的限制 |

#### 数据量（全部公开可获取）

| 数据类型 | 规模 |
|---------|------|
| 宪法+法律 | 约 300 部现行有效法律 |
| 行政法规 | 约 600 部 |
| 省级地方性法规 | 一个省约 200-400 部 |
| 市级法规+政府规章 | 一个市约 100-200 部 |
| 部门规章 | 约 3000 部 |
| 规范性文件 | 一个市约 500-1000 份现行有效文件 |
| 总 chunk 数（以地级市为范围） | 约 15-25 万条 |
| 数据来源 | 国家法律法规数据库、司法部规章库、省级法规库——全部公开 |

#### 技术决策链

| 为什么 | 答案 |
|--------|------|
| 为什么 RAG？ | 审查员需要沿"上位法链"向上追溯：市文件→省条例→国务院条例→固废法→环保法→行政许可法→行政处罚法→宪法。一个条款涉及 3-5 个法律层级 × 每层级 5-10 条相关条款 = 几十个检索点。RAG 输入条款内容 → 跨层级检索所有可能相关的上位法条款 → 不是替代审查员的判断，而是确保"没有遗漏该查的法"。 |
| 为什么多路召回？ | 路1（条款语义匹配）：草案条款→检索上位法相似条款。路2（禁止性/义务性表述精确匹配）："不得""禁止""应当""必须"——这些词在法律文本中有精确含义。路3（权限条款匹配）：草案设定了许可→检索行政许可法第 12-16 条（设定许可的权限）。路4（同类城市横向比对）：同类城市的类似文件→发现差异点。 |
| 为什么路2要精确匹配禁止性表述？ | "不得"=禁止，"应当"=强制性义务，"可以"=授权性条款。一份文件如果把上位法的"应当"改为"可以"——降低了法定义务，可能违法。精确匹配这些表述是合法性审查的基础。 |
| 为什么数据公开是优势？ | Demo 可以用国家法律法规数据库的真数据，不需要模拟。面试被问"你的数据怎么来的"，回答"国家公开的法律法规数据"，比"我模拟的"可信得多。 |
| 输出格式如何约束？ | 每条检索结果须包含：法规名称+生效状态+地域+版本+条款原文+发布日期。系统输出"待审查风险点及上位法依据"，不输出"违法/合法"结论——合法性判断由审查员作出。 |

#### 可替代性测试

> 审查员用北大法宝/威科先行等专业法律数据库能查到每部法的全文。但核心问题是：审查员需要知道"管建筑垃圾的"涉及固废法+行政许可法+行政处罚法+城市市容管理条例+省条例。新手审查员可能只查了固废法和省条例，忽略了行政许可法第 16 条——"规章不得增设行政许可"——这就是越权设定许可的合法性漏洞。RAG 不是替代法律数据库，而是替代"资深审查员脑子里的上位法关系网"。

#### 项目价值

**面试一句话**：一份市规范性文件需要向上追溯 3-5 个法律层级。最危险的不是查不到，是没想到该查——RAG 替代的是"资深审查员脑子里的上位法关系网"。

**为什么这个项目能通过面试**：
- **上位法追溯天然多路召回**：条款语义+禁止性表述精确匹配+权限条款+同类城市横向比对——四个独立维度，不是设计的是法律层级体系决定的
- **数据完全公开**：国家法律法规数据库、司法部规章库全部免费可查。Demo 跑真数据，面试说"我的数据来自国家公开数据库"比"我模拟的"可信一个量级
- **禁止性表述精确匹配是独创技术点**："不得""禁止""应当""必须"在法律文本中有精确含义，需要结构化提取+独立索引
## 8. 医疗病历辅助方向

> **⚠️ 本章有重要法律风险提示，选这个方向前必须先读。**

> **核心红线**：根据《医疗器械监督管理条例》，提供诊断/治疗建议的软件属于第三类医疗器械。本章全部场景定位为"辅助工具"——系统只负责检索信息、整理信息、标记缺失信息，**不做任何临床决策**。面试时必须主动讲清楚"辅助"和"诊断"的边界——"我的系统帮医生找指南、整理病历时间线、提醒缺失字段，但诊断和治疗决策永远是医生做的"。

### 场景 X：临床指南检索（RAG）⭐⭐⭐

#### 用户画像

| 维度 | 数据 |
|------|------|
| 用户 | 临床医生（主治/住院医师），日均接诊 30-50 名患者 |
| 使用场景 | 遇到病情复杂的患者（如"高血压+糖尿病+肾功能不全"），需同时参考心内科、内分泌科、肾内科三个科室的指南 |
| 响应要求 | 诊间 < 30 秒给出指南相关章节 |
| 核心痛点 | 指南太厚（每本 200 页）、太多（1000+ 部）、太新（5 年更新一次，医生记忆可能是旧版本）。三科室指南可能有冲突 |

#### 数据量（大部分公开）

| 数据类型 | 规模 | 来源 |
|---------|------|------|
| 中华医学会临床指南 | 约 1000+ 部 | 中华医学期刊网，大部分公开 |
| 国际指南（ESC/ACC/AHA/KDIGO等） | 200+ 部 | 公开 |
| NMPA 药品说明书 | 约 16 万条 | 公开 |
| 总 chunk 数 | 约 28 万条 | |

#### 技术决策点

| 为什么 | 答案 |
|--------|------|
| 为什么 RAG？ | 医生查询"肾功能不全患者(eGFR<60)的高血压管理相关指南推荐"——答案跨了心内科指南（降压通用原则）+肾内科指南（肾功能不全特殊人群）。任何一本指南不会在一个章节里同时覆盖这两个维度。需要跨文档检索+拼接。**输出限定**：仅返回指南来源、版本、原文片段、推荐等级和跨指南冲突提示；不输出剂量建议、适应证变更或诊断结论。 |
| 为什么多路召回？ | 路1（指南正文语义检索）：病情→相关章节。路2（推荐等级精确匹配）："I类推荐""A级证据""应当"——I类=必须做，IIa=可以做，IIb=可考虑。检索必须区分推荐强度，否则5条结果全是弱推荐，医生照着做可能出事。 |
| 为什么需要验证 embedding 选型？ | 医学文献中英混用："患者 eGFR<60ml/min/1.73m²，血压控制在 <130/80mmHg"——中英文+数字+单位的组合。通用 embedding 在此类场景下性能可能下降，需用领域测试集对比 BGE-M3 与通用模型的 Recall@k，以实测结果决定选型。 |

#### 可替代性测试

> UpToDate/Dynamed 等临床决策支持系统以英文内容为主，中国指南（如中国 2 型糖尿病防治指南、医保目录限制的用药选择、中成药推荐）覆盖不足。且 UpToDate 是关键词搜索，不支持"肾功能不全+老年+心衰"多维交叉检索。更重要的是——医生诊间只有 30 秒，打开 UpToDate→搜索→浏览→找到至少 2-3 分钟。RAG 能做到 30 秒内返回。

> ⚠️ **简历提示**：适合有医学背景的转行学生（临床医学/药学/护理/公卫）。无医学背景慎选——面试官追问"你怎么知道这个结果是正确的"，无法回答。

#### 项目价值

**面试一句话**：医生诊间只有 30 秒。RAG 在 30 秒内从 1000+ 部指南+16 万条药品说明书中检索到答案，还能区分 I 类推荐（必须做）和 IIb 类推荐（可考虑）。

**为什么这个项目能通过面试**：
- **推荐等级区分是独创技术点**：指南里"应当使用 ACEI"（I 类推荐）和"可考虑联合使用 CCB"（IIb 类推荐）——检索不区分推荐等级，5 条结果全是弱推荐，医生照着做可能出事
- **跨科室多维度检索**："肾功能不全+老年+心衰"三个条件同时满足——关键词搜索返回各 100 条，RAG 语义检索找到同时满足三个条件的那一个段落
- **数据全公开**：中华医学会指南+NMPA 说明书全部公开可查

### 场景 Z：药品信息交叉核验（RAG）⭐⭐

#### 用户画像

| 维度 | 数据 |
|------|------|
| 用户 | 临床医生（开药时）+ 临床药师（审方时） |
| 使用场景 | 患者同时服用 5-8 种药物，医生需新增一种——系统检索各药品说明书中关于相互作用的原始描述，供医生和药师自行判断。**不输出"建议调整剂量"等临床决策。** |
| 频率 | 每个住院患者的医嘱至少经过 1 次药师审方 |
| 核心痛点 | 药品说明书太长（每份 50-100 页），相互作用信息分散在"药物相互作用""禁忌""注意事项""特殊人群用药"四个章节中。单份说明书不会穷举所有药物组合 |

#### 数据量（全部公开）

| 数据类型 | 规模 |
|---------|------|
| NMPA 药品说明书 | 约 16 万条，公开 |
| FDA 药品说明书（DailyMed） | 约 14 万条，公开 |
| 药物相互作用数据库（DrugBank） | 学术用途可用 |
| 国家基本药物处方集 | 公开 |
| 总 chunk 数 | 约 25 万条 |

#### 技术决策点

| 为什么 | 答案 |
|--------|------|
| 为什么 RAG？ | 患者服用：阿司匹林+氯吡格雷+阿托伐他汀+美托洛尔+二甲双胍。医生想加"布洛芬"。RAG 需要跨 6 份说明书检索：布洛芬+阿司匹林→减弱抗血小板作用。布洛芬+氯吡格雷→NSAIDs 增加出血风险。布洛芬+美托洛尔→NSAIDs 减弱降压效果。三条信息在三份说明书的不同章节。 |
| 为什么多路召回？ | 路1（药品名称精确匹配）："布洛芬"→检索布洛芬说明书全文。路2（药物分类语义匹配）：阿司匹林+氯吡格雷属于"抗血小板药"类→检索布洛芬说明书中关于"抗血小板药""NSAIDs"的章节。路3（相互作用关键词匹配）：检索阿司匹林说明书中关于"布洛芬""ibuprofen""NSAIDs"的段落。路2泛化、路3精确，互补。 |
| 为什么不是医院合理用药系统？ | 医院合理用药系统（美康/大通）基于规则库，只能查已知"药物-药物对"。未录入的相互作用不会提醒。RAG 直接检索说明书全文——最新版说明书新增的警告即使还没进规则库也能被检索到。而且传统系统不做 6 种药的协同效应分析（3 种药都有"增加出血风险"的副作用，叠加效应可能显著）。 |

#### 可替代性测试

> 临床药师审方：逐份翻说明书查相互作用。6 种药 = 至少翻 6 份说明书的相关章节。一个科室日均审方 50-80 条，时间压力下只能查"高风险组合"。RAG 把"翻说明书+交叉比对"从几分钟压到秒级，药师专注于判断"这个相互作用在临床上要不要干预"。

#### 项目价值

**面试一句话**：6 种药加 1 种新药，跨说明书检索相互作用。医院合理用药系统基于已知"药-药对"规则库，RAG 直接检索说明书全文，可补充发现规则库未录入的最新警告，还能提示多种药物副作用叠加的可能——与规则库形成互补。

**为什么这个项目能通过面试**：
- **与传统规则库的对比清晰**：医院合理用药系统（美康/大通）只查"已知对"，未录入的不会提醒。RAG 直接检索说明书全文——最新版新增警告即使还没进规则库也能被检索到
- **数据全公开**：NMPA+FDA 药品说明书全部公开，Demo 跑真数据
- **多路召回互补**：药品名称精确匹配+药物分类语义匹配+相互作用关键词匹配——三路互补

## 9. 娱乐传媒方向

### 场景 R1：综艺/影视后期素材检索（RAG）⭐⭐⭐

#### 用户画像

| 维度 | 数据 |
|------|------|
| 用户 | 后期剪辑师，一个综艺项目 5-10 人团队，全国后期制作公司数百家 |
| 使用场景 | 编导说"找一个两人对视、情绪紧张的镜头"，剪辑师从几百小时原始素材里凭记忆翻 |
| 数据规模 | 一个综艺季约 200 小时素材→按场景切分约 5000-8000 个片段 |
| 响应要求 | 3 秒内返回候选片段，不能中断剪辑工作流 |
| 核心痛点 | 编导的"情绪化描述"和素材标签系统之间有巨大语义鸿沟。标签只标注了"双人中景"，搜不到"紧张对视" |

#### 数据量

| 数据类型 | 规模 |
|---------|------|
| 原始素材 | 一个综艺季约 200 小时 |
| 片段数 | ASR转写+场景切割后约 5000-8000 个片段 |
| 总 chunk 数 | 约 2-5 万条（对话文本+场景描述+情绪标签） |
| 日增量 | 每天拍摄新增约 200 个片段 |

#### 技术决策点

| 为什么 | 答案 |
|--------|------|
| 为什么 RAG？ | 编导的查询是情绪化的——"紧张对视""尴尬的沉默"。标签只能搜客观描述，搜不到情绪。RAG 用语义检索匹配情绪描述和素材中实际存在的对话文本+场景上下文。 |
| 为什么不是标签搜索？ | 标签是人工打的，只能覆盖"双人中景""户外"这类客观描述。情绪标签标注成本高且主观——同一个镜头 A 觉得紧张、B 觉得温馨。RAG 绕过了标签——直接检索对话内容，从文本语义中匹配情绪。 |
| 为什么 chunk 按场景片段切？ | 剪辑师需要完整镜头。按固定时长切会切断表演段落。ASR 转写后按对话停顿+场景切换自动切分，每个 chunk = 一个完整叙事单元。 |

#### 可替代性测试

> 传统做法：编导凭记忆描述"他们俩站在天台上那场戏"，剪辑师在时间线上手动拖拽。200 小时素材，找一个特定情绪片段要 10-15 分钟。RAG 输入"天台+对视+紧张"→3 秒返回候选时间码。一天省下的找素材时间够多剪一场戏。

#### 项目价值

**面试一句话**：编导说"找一个两人对视、情绪紧张的镜头"——关键词搜索 0 条，RAG 从对话文本中匹配情绪语义，3 秒返回。

**为什么这个项目能通过面试**：
- **语义鸿沟故事人人能懂**：所有人看过综艺，知道情绪描述和标签系统的差距
- **纯 RAG 但有技术深度**：ASR 转写+场景切割+情绪语义匹配——多模态前处理+RAG，不是上传文档查文档
- **可量化叙事**："找一个镜头 10-15 分钟→3 秒"

### 场景 R2：直播内容合规审核（Agent + RAG）⭐⭐⭐

#### 用户画像

| 维度 | 数据 |
|------|------|
| 用户 | 平台内容审核员，抖音/快手/B站审核团队数百到数千人，日均处理 200+ 条预警 |
| 使用场景 | 直播间触发预警后，15 秒内判断是否违规。规则频繁更新——双11临时规则和日常规则不同 |
| 响应要求 | 15 秒内给出处置建议 |
| 核心痛点 | 一个直播间可能同时触发商品夸大宣传+未成年人出镜+BGM 侵权——三项规则在三份不同的文档里 |

#### 数据量

| 数据类型 | 规模 |
|---------|------|
| 平台规则文档 | 约 300 份（通用规则+品类专项+临时活动规则） |
| 历史判例库 | 约 5000 条已标注案例 |
| 日增量 | 规则更新 5-10 份/周，新判例 200 条/天 |
| 总 chunk 数 | 约 1-2 万条 |

#### Agent 架构（拆分为 5 个子 Agent + 主Agent）

```
直播间触发预警 → 主Agent（调度+聚合+处置路由）
                     ↓
    ┌────────┬────────┼────────┬────────┐
    ↓        ↓        ↓        ↓        ↓
内容合规   商品合规   未成年人   版权合规   决策Agent
Agent      Agent      Agent      Agent     (综合定级+
判断"说    判断"卖     判断"有     判断"BGM   处置路由
的话有     的东西有    没有未成    /画面有    +置信度阈值)
没有违     没有夸大    年人违规   没有版权    ├─ 高置信+低风险
规？"      宣传？"    出镜？"    问题？"    │   →警告
工具:      工具:      工具:      工具:      ├─ 置信不足
RAG+判例   RAG+判例   RAG+图像   RAG+音频   │   →人工复审+证据留存
                      识别API    指纹API    └─ 高置信+严重
                                            →断流+上报+申诉路径
```

> **拆分依据（对标串讲第1、5节）**：4 个审核 Agent 对应 4 类独立的平台规则体系——内容（直播言论规范）、商品（广告法+平台带货规则）、未成年人（未成年人保护条例）、版权（曲库+画面版权）。每类规则在不同的文档体系里，数据源不同→拆。4 个并行——一个直播间可能同时触发多项规则。

#### 技术决策点

| 为什么 | 答案 |
|--------|------|
| 为什么 4 个审核 Agent 并行？ | 一个直播间可能同时触发 3 项规则——串行审核 15 秒内不够。并行 = 4 个 Agent 同时查→3 秒内返回。更重要的是规则交叉——商品针对未成年人的宣传同时触发商品合规和未成年人保护两套规则，需要两个 Agent 的结果聚合判断。 |
| 为什么不是关键词过滤？ | 关键词只能抓"最好""第一"这类违禁词。"用了三个月皮肤就变好了"——没有违禁词，但暗示效果涉嫌夸大。Agent 需要语义理解。而且规则在变——双11允许的用语，双11后违规。RAG 检索最新规则。 |
| 为什么决策 Agent 独立？ | 4 个 Agent 各自给出"本维度是否违规"+置信度。决策 Agent 综合定级后分三路：高置信+低风险→警告（轻量自动处置）；置信不足→人工复审+证据留存（宁可多复审也不误判）；高置信+严重→断流+上报+申诉路径。三路的关键区别是置信度——机器判断不准的不自动处置。所有自动处置须留存截图/时间戳证据。 |

#### 可替代性测试

> 内容审核是真实行业——网易易盾、数美主要做文本/图片审核。直播审核的难点是"多维度并发"——4 个维度同时触发。传统方案是 4 个审核员各看不同维度。Agent 把 4 个维度并行化，审核员只确认 Agent 的判断。

#### 项目价值

**面试一句话**：直播审核不是查违禁词，是 4 个维度同时触发——15 秒内判断违规等级和处置方式。

**为什么这个项目能通过面试**：
- **4 个 Agent 不是设计的，是 4 套独立规则体系决定的**：内容/商品/未成年人/版权各有各的文档
- **并行审核有业务约束**：15 秒内 4 个维度→串行不可能
- **与风控（场景 F）结构相似但领域不同**：面试时可讲"风控和直播审核本质上都是多维度交叉验证，Agent 架构通用"

```
□ 2. 数据量可量化
     能报出具体数字：多少文档/SKU/运单、chunk 数、日增量
     每个数字有来源或推算逻辑

□ 3. 可替代性测试通过
     RAG 项目：能回答"为什么不直接 Ctrl+F 查 PDF？"
     Agent 项目：能回答"为什么一个 LLM + Prompt 不行？"

□ 4. Agent 边界清晰（仅 Agent 方向）
     每个子 Agent 职责单一，有明确的输入输出 schema
     不存在"万能 Agent"——如果有一个 Agent 做了超过 3 件事，拆

□ 5. 权限隔离明确（仅 Agent 方向）
     涉及钱/通知/删除/写库的操作有独立审查 Agent 或人工 Gate
     不能说"LLM 自己会判断"

□ 6. 异常兜底有方案
     子 Agent 失败后怎么降级？
     例：RAG 检索无结果 → 关键词搜索 fallback → 建议人工查询

□ 7. 状态可追溯（最小状态设计）
     至少设计并记录以下字段（Demo 用内存 dict 即可，不必上 Redis）：
     - task_id：一次请求的唯一标识
     - current_node：当前执行到哪个 Agent/步骤
     - slots：跨节点共享的中间结果（如运单号、用户信息）
     - agent_results：每个子 Agent 的返回结果（含时间戳）
     - errors：失败节点+错误信息
     - human_confirmed：人工确认状态（未确认/已确认/已驳回）
     进阶可选：checkpoint 恢复（中断后从断点续跑）、并行写冲突处理
     能说清楚"某次出错了怎么定位到是哪个 Agent/哪个节点的问题"

□ 8. 技术选型有因果链
     每个技术选择（Milvus/BGE-M3/RRF/chunk_size 等）能关联到用户画像或数据量
     不能只说"因为它好/因为它快/因为大家都在用"

□ 9. 至少 3 个技术决策点
     能脱稿讲"我选 A 不选 B，因为我的数据特征/用户场景下..."
     这些决策在面试中就是"项目亮点"

□ 10. 能跑 Demo
      不是纯 PPT 项目，至少能跑一个最小版本（2-3 个 Agent + 假数据）
      面试官问"能演示吗"时，有东西可以展示

□ 11. 质量评测有数据
      准备 30-50 条测试用例（覆盖正常路径+边界+异常输入），至少记录以下指标：
      - RAG 场景：Recall@k、引用准确率（生成内容是否来自检索到的 chunk）、拒答率（检索无结果时是否正确降级而非幻觉）
      - Agent 场景：路由准确率（主Agent 是否正确分发到子Agent）、工具调用成功率、人工接管率
      - 通用：端到端 P95 延迟、高风险错误数（如赔付金额算错、法规条款引用错误）
      失败案例必须逐条记录原因并复盘，不能只报"成功率 XX%"
```

## 附录 A：Demo 最小版本起步指引

> 自检清单第 10 条要求"能跑 Demo"。这部分告诉你怎么起步。

### A.1 RAG 项目的最小 Demo（适用场景 H/Q/U/X/Z/R1 等纯 RAG 场景）

**目标**：跑通"文档入库 → embedding → 检索 → LLM 生成回答"的完整链路。

**技术栈建议**：
```
Python 3.10+
├─ LangChain（文档加载、切分、检索链）
├─ ChromaDB（轻量向量库，不需要装 Docker，本地一个目录就是数据库）
├─ BGE-M3 / text2vec-large-chinese（embedding 模型，HuggingFace 可直接下载）
├─ 任意 LLM API（Qwen/DeepSeek/GLM，有免费额度即可）
└─ Gradio / Streamlit（最简单的 Web UI，十几行代码出界面）
```

**最小版本包含**：
```
□ 数据准备：10-20 份文档（法规/维修记录），自己写 Markdown 文件即可
□ 文档切分：按 ## 标题切 chunk，每 chunk 500-1000 字
□ Embedding：用 BGE-M3 做向量化，存入 ChromaDB
□ 检索：输入问题 → 向量检索返回 Top 5 chunk
□ 生成：Top 5 chunk + Prompt → LLM → 返回答案
□ 界面：Gradio 一个输入框 + 一个输出框
```

**假数据怎么造**：
- 电商合规检索：编 10 份"法规摘要"（广告法节选、食药监规定节选），自己写 5-10 个"执法案例"
- 设备经验共享：编 20 条维修记录（"设备型号XXX，故障现象YYY，维修方案ZZZ"）
- 质检缺陷库：编 15 条缺陷记录（"产品A，缺陷描述，判定结果，根因"）

**预计时间**：1-2 天（如果 Python 熟练，半天）

---

### A.2 Agent 项目的最小 Demo（适用场景 A/B/C/F/M/R2 等 Agent 场景）

**目标**：跑通"主 Agent 调度 → 2-3 个子 Agent → 结果聚合"的最小链路。

**技术栈建议**：
```
Python 3.10+
├─ LangGraph（StateGraph 做 Agent 编排，支持条件路由和状态管理）
├─ 子 Agent：每个 Agent 就是一个 Python 函数（先用函数模拟，后面再拆成独立 Agent）
├─ ChromaDB（如果需要 RAG 检索子 Agent）
├─ 任意 LLM API
└─ 假数据：JSON/YAML 文件模拟外部 API 返回
```

**最小版本包含（不要一上来做全部 Agent）**：
```
□ 选 2-3 个核心子 Agent（不要一上来做 8 个）
□ 主 Agent 做意图识别 → 路由到子 Agent
□ 子 Agent 返回结构化 JSON
□ 主 Agent 聚合结果
□ 至少 1 个异常分支（如"检索无结果→降级方案"）
□ 至少 1 个人工确认 Gate（打印"建议执行XX，请人工确认"，等待键盘输入 y/n）
```

**假数据怎么造**：
```
# 用一个 JSON 文件模拟外部 API 返回
# 例：物流异常处理
mock_data = {
    "waybill_123": {
        "status": "地址不详",
        "history": [...],
        "recipient_phone": "138****1234"
    }
}

# 例：风控审核
mock_credit = {
    "user_001": {
        "zhima_score": 680,
        "operator_months": 36,
        "blacklist_hit": False
    }
}
```

**预计时间**：2-3 天（如果 Python 熟练，1-2 天）
