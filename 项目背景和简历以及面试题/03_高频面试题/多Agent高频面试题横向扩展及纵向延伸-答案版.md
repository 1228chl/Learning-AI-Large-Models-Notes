# 多 Agent 高频面试题横向扩展及纵向延伸：答案版

> 按真实项目替换 Agent 数量、工具、状态字段和指标。

## 一、项目主线

### 问题：什么是 Multi-Agent？为什么不用单 Agent？

Multi-Agent 不是让多个模型自由聊天，而是把复杂任务拆成职责明确、输入输出稳定的协作单元。单 Agent 在工具多、权限不同、任务链长时容易 prompt 膨胀、工具选择不稳定、状态难排查；多 Agent 可以按业务能力拆分，例如检索、数据库查询、执行工具、审查。拆分标准不是“模型越多越好”，而是任务边界、权限边界、依赖关系和可观测性。简单任务仍然应该单 Agent 或固定 workflow 完成。

### 问题：Agent 和 Workflow 有什么区别？

Workflow 的路径通常固定，输入满足条件就走预定义节点；Agent 有在受约束范围内规划、选工具或决定下一步的能力。生产系统经常二者结合：确定性高的校验、权限、审批走 workflow；需要在工具间选择的环节才使用 Agent。这样可控性、成本和可测试性更好。

## 二、场景设计

> **基础/项目相关**

### 问题：面对抽象指令，Agent 如何执行？

先抽取目标、对象、约束和风险等级。信息不足时提出最少必要澄清问题；低风险任务可以根据明确假设执行并回显假设，高风险操作必须确认。之后生成受 schema 约束的计划，逐步调用白名单工具，记录每步结果；失败时只对可重试错误重试，其他情况返回可解释原因或转人工。

### 问题：设计售后 Agent 怎么做？

链路可设计为：用户识别与鉴权 → 订单/物流等结构化查询 → FAQ/RAG 查询 → 规则判断是否可自动处理 → 执行或创建工单 → 返回带依据的结果。订单退款、地址变更等有副作用操作必须经过权限、参数校验和用户二次确认；模型只负责理解和编排，真正执行由受控服务完成。

> **进阶（中高级/架构岗常见）**

### 问题：生产级多 Agent 系统需要补什么？

除功能外还需要：统一身份与权限、任务与状态持久化、幂等、超时重试熔断、可观测 trace、评测与回归集、限流、灰度、审计和灾备。上线前先压测工具依赖与模型服务，明确每类错误的降级路径。薪资不是分层标准，是否需要这些能力取决于岗位是否负责生产可靠性。

### 问题：几千个 API 怎么组织？

不能把几千个 API 全部直接暴露给模型。按业务域建立工具目录和能力摘要，由路由层先缩小候选域；每个域内再根据 schema、权限、风险和上下文选择工具。工具要有稳定的名称、参数 schema、幂等性、权限和审计信息；新增 API 通过注册、测试和评估进入目录，而不是只改 prompt。

## 三、主 Agent：意图与路由

### 问题：主 Agent 做什么？如何路由？

主 Agent 负责输入安全检查、意图识别、关键信息补全、任务计划、路由、结果聚合和异常处理。路由先用规则、权限和工具可用性过滤，再用分类模型或 LLM 在候选中选择；低置信度进入澄清或人工兜底。主 Agent 不应默认拥有所有业务工具，尤其不直接绕过权限执行高风险操作。

### 问题：意图识别错了怎么办？

识别结果应带置信度和候选意图。执行前可校验槽位与权限；执行后用工具返回和结果校验发现明显不一致时，允许有限次数重新路由。记录错误样本更新规则或评测集，而不是无限循环让模型自我反思。

## 四、槽位识别

### 问题：槽位如何抽取，缺失怎么办？

按意图定义 schema，例如查询订单需要订单号、用户身份和时间范围。规则适合日期、编号等稳定格式；模型处理自然语言实体；schema 校验必填、类型、枚举和范围。缺少关键槽位时澄清追问，非关键槽位可使用明确默认值并回显。历史槽位只能在同一任务和未冲突时复用。

## 五、任务 schema 与路由

### 问题：任务分发数据怎么设计？

至少包括 `task_id、session_id、trace_id、user_id、intent、slots、target_agents、dependencies、execution_mode、timeout、retry_policy、fallback_policy`。所有 Agent 的输入、输出和错误都要 schema 校验；模型生成 JSON 后使用解析器和业务校验，不合法就纠正或进入兜底，不能直接执行。

## 六、子 Agent 设计

### 问题：子 Agent 如何划分、如何通信？

按稳定业务能力拆分，不按模型名称拆分。例如 RAG Agent 只负责检索与引用，SQL Agent 只负责受控查询，Tool Agent 只负责执行授权动作，Review Agent 只负责规则与事实检查。每个 Agent 有明确 input/output、最小工具权限和结果命名空间。通信可采用共享状态、消息队列、HTTP 或 A2A 协议；无论方式如何，消息都需要 task_id、source、target、trace_id、版本和错误语义。

## 七、串行、并行与异步

### 问题：什么时候串行、并行、异步？

有数据依赖时串行，例如先鉴权再查询；互相独立时并行，例如同时检索知识库和查询订单；耗时且不要求实时返回时异步，例如批量报告。并行结果需要定义聚合规则、超时和部分成功策略；异步任务用 task_id 持久化状态，用户可轮询或订阅进度。

## 八、Plan-and-Execute

### 问题：计划由 LLM 生成可靠吗？

不完全可靠。计划必须限制在白名单 Agent/工具和 schema 内，校验依赖、权限、参数和预算。简单任务不必规划；复杂任务生成分步计划。执行中只有在新工具结果改变前提时才允许 replan，并限制最大步骤与总耗时，避免反复规划。

## 九、异常与兜底

### 问题：子 Agent 或工具失败怎么办？

先按错误类型分流：参数/权限错误通常不重试；网络超时可有限重试；依赖持续故障走备用工具或降级；高风险动作失败要停止并告知。错误结果应结构化返回，包括错误码、可重试性、已完成步骤和建议。对有副作用动作使用幂等键，避免重试导致重复扣款、重复发消息或重复建工单。

## 十、超时、重试、熔断与死循环

### 问题：如何防止死循环？

限制总步骤数、单 Agent 重试数和总时限；记录 `visited_agents` 及相同 action+input 的重复调用；工具连续失败时熔断；无有效进展时进入澄清、降级或人工节点。重试采用按错误类型的策略和指数退避，不是对任何错误反复调用。

## 十一、Checkpoint 与恢复

### 问题：Checkpoint 保存什么，怎么防止重复执行？

保存 task/session、当前节点、已完成与待执行节点、结构化 state、中间结果、重试次数、错误和更新时间。服务中断后从最近成功节点恢复。写数据库、通知、支付等副作用节点必须使用幂等键或事务外盒，不能只依赖“节点已经执行过”的内存标记。

## 十二至十五、上下文与状态

### 问题：上下文如何管理、防止污染？

区分用户原始输入、近期对话摘要、任务 state、工具结果和外部知识。进入模型前按当前任务和权限筛选，不把全量日志或原始大文档塞给模型。按 task_id 隔离状态；每个 Agent 只读必要字段、只写自己的 result namespace；并行写入用 reducer/版本控制或明确合并规则。长历史采用滑动窗口、摘要和按需检索，大文本只存引用。

## 十六、协同与 A2A

### 问题：Agent 怎么知道何时调用另一个 Agent？A2A 如何做？

优先由主 Agent 根据路由或计划依赖统一调度，不建议让子 Agent 无边界互调。若项目使用 A2A 或自定义协议，消息需要定义任务身份、目标能力、输入、上下文引用、权限、超时、trace 和回调/结果 schema；通信层还要鉴权、幂等、限流和审计。A2A 是协作通信方式，ReAct 是单 Agent 的推理—行动范式，二者不在同一层。

## 十七、工具层

### 问题：LangChain、LangGraph、MCP、Function Calling、Skill 的区别？

LangChain 提供模型、prompt、retriever、tool 等应用组件；LangGraph 用状态图管理复杂分支、循环和 checkpoint；Function Calling 是模型按 schema 选择和填写函数参数；MCP 是外部工具/资源的标准化接入协议；Skill 是固定任务的能力与操作规范封装。它们可以组合，但不能把 MCP 说成插件、把 Skill 说成单纯提示词。

## 十八、Agent + RAG

### 问题：RAG 在 Agent 中如何定位？

RAG 是一种受控能力：知识、制度、文档依据类问题调用 RAG Agent；结构化实时数据调用 SQL Agent；有副作用操作调用 Tool Agent。RAG Agent 返回召回片段、来源、置信度和摘要，不直接把未经审查的大段文本当最终答案。召回为空时先改写/澄清或明确无依据，不能让模型自由编造。

## 十九、聚合与审查

### 问题：多个 Agent 结果冲突怎么办？

先按数据源权威性、时效、权限和置信度排序；若关键事实冲突，展示差异、请求补充或转人工，而不是让 LLM 随机选一个。聚合后做 schema、事实引用、安全和格式校验；审查 Agent 也只是防线之一，不能替代权限与业务规则。

## 二十、流式输出

### 问题：用户刷新后如何继续输出？

不要把任务生命周期绑定单个浏览器连接。服务端以 task_id 保存执行状态和已生成内容；前端重连时携带 task_id，从已确认位置续传或返回最终结果。对内部多 Agent 通常聚合到可解释的阶段再对外流式，不把未经审查的内部推理直接暴露给用户。

## 二十一、评估

### 问题：如何评估 Agent 效果？

按层评估：意图/路由准确率、槽位正确率、工具调用成功率、子任务成功率、端到端任务完成率、平均/P95 时延、超时率、人工介入率和高风险错误率。评测集应覆盖正常、模糊、越权、工具失败和多步骤任务；每次改 prompt、工具或模型后做回归，而不是只看几个 demo。

## 二十二至二十五、连问与复习

一套项目回答顺序是：业务目标与为何多 Agent → Agent 边界和工具权限 → 主 Agent 路由与 state → 串并行/异步计划 → 异常、幂等、恢复与可观测 → 聚合与评估。基础岗位先掌握这条主线、一个真实工具调用和一个真实失败案例；再深入 checkpoint、熔断、上下文压缩、A2A 与生产架构。任何指标均说明统计口径、样本量和时间范围。

# 逐题补全答案（技术题）

## 1. 选型与项目边界

### 问题：项目里有几个 Agent，如何分工？

回答必须给出真实清单。例如主 Agent 只负责路由、计划和聚合；RAG Agent 返回带引用的知识结果；SQL Agent 执行只读参数化查询；Tool Agent 调用经过审批的业务动作；Review Agent 做格式、安全和依据检查。每个 Agent 要说明输入、输出、工具权限和失败结果，不能只说“一个负责检索、一个负责工具”。

### 问题：Agent 和 Coze/Dify 有什么区别？

Coze/Dify 是应用搭建或工作流平台，能快速集成模型、知识库和工具；Agent 是任务理解、决策和工具调用的能力形态。面试重点不是贬低平台，而是说明你在平台外或平台内做了什么：工具 schema、路由规则、权限、状态、评测或自定义服务。若项目就是低代码搭建，也要诚实说明其边界。

## 2. 路由与槽位补充

### 问题：规则路由和 LLM 路由冲突怎么办？

安全、权限、精确业务规则优先级高于 LLM；先用规则把不可执行和无权限候选排除，再让 LLM 在合法候选中分类。冲突时记录两者结果和置信度，低置信进入澄清/人工；不要让模型覆盖硬性风控规则。

### 问题：target_agent 不存在、返回 JSON 不合法怎么办？

Agent 注册中心维护白名单与版本；分发前校验 target 是否存在、是否健康、调用方是否有权限。模型输出先经 JSON parser、schema 和业务校验；失败可进行一次受约束修复或走固定 fallback，不能把不合法 JSON 直接当指令执行。

### 问题：槽位和意图谁先做？

通常先粗识别意图以确定所需 schema，再抽槽并校验；对多意图输入可联合抽取候选意图和槽位。关键不是固定顺序，而是不同意图必须有自己的必填字段，且缺失关键槽位时不能盲目执行。

## 3. Agent 通信与状态补充

### 问题：全局 state 和局部 state 怎么划分？

全局 state 只放任务级信息，如 task_id、用户身份、权限、意图、计划、节点状态和结果引用；局部 state 放某 Agent 的候选、临时变量、工具原始返回等。大文本、文件和完整日志放外部存储，state 只存 URI/摘要。并行 Agent 写不同 namespace，由 reducer 或聚合节点合并，避免覆盖。

### 问题：子 Agent 是否允许再调用子 Agent？

默认不允许或严格白名单。自由互调会让权限、依赖和循环难以控制。若确实需要，例如审查 Agent 调用事实校验工具，应在计划中显式定义调用边、最大深度、预算和回传 schema，并由统一 trace 记录。

## 4. 执行模型补充

### 问题：并行结果如何合并？某个慢节点怎么办？

先定义 all-success、partial-success 和 fail-fast 三种策略。独立的非关键查询可设置 deadline，到期返回已完成结果并声明缺失；关键节点失败则停止下游或走备用路径。聚合时按来源、时间、置信度和 schema 合并，而不是把多段自然语言直接拼接。

### 问题：异步任务怎么通知用户、刷新如何恢复？

创建任务后立即返回 task_id 和初始状态；状态与结果写入持久化存储，前端可轮询、SSE 或 WebSocket 订阅。用户刷新后用 task_id 重连并从已确认序号续传；任务完成后返回最终产物。要设置过期、取消和权限校验，防止他人凭 task_id 读取结果。

## 5. 计划、失败与可靠性补充

### 问题：什么时候允许 replan？

只有工具结果显示原计划前提不成立、候选资源不可用或用户补充关键约束时才允许；replan 继承已完成步骤和预算，不能重复执行有副作用动作。限制最大重规划次数；持续失败时转人工或返回部分结果。

### 问题：熔断、超时、重试怎么设置？

超时按工具、Agent 和整任务分层设置；网络抖动、限流等瞬时错误可指数退避重试，参数/权限/业务校验错误不重试；连续失败超过阈值熔断，半开状态探测恢复。熔断后主 Agent 走备用模型、降级 FAQ/规则或提示稍后重试。阈值需由历史时延和错误率配置，而非随意写死。

## 6. Checkpoint、上下文与污染补充

### 问题：Checkpoint 和日志区别是什么？

Checkpoint 是可恢复的结构化任务快照，包含当前节点、已完成步骤、中间结果引用和重试状态；日志是用于诊断的执行记录。恢复依赖 checkpoint，排障依赖日志和 trace；二者都要有版本、保留周期和敏感信息脱敏。

### 问题：如何防止上下文污染？

按 task_id/session 隔离；当前用户输入优先；工具结果通过 schema 和来源校验后才进入 prompt；失败工具输出不作为事实；切换话题时创建新任务状态；对检索文本施加权限和不可信内容标识。上下文摘要必须包含时间和来源，避免旧结论覆盖新事实。

## 7. 工具与 RAG 补充

### 问题：Function Calling 参数如何校验？

模型只产生候选参数，服务端通过 JSON Schema、类型、枚举、长度、权限、业务规则和幂等键校验。查询类工具优先只读、参数化；写操作要展示动作摘要并让用户确认。工具返回统一包含成功状态、数据、引用、错误码和可重试性。

### 问题：RAG Agent 的输出为何不能只是答案？

它至少应返回片段、来源、页码/文档、置信度和检索状态，供主 Agent 判断是否足以回答和向用户展示引用。召回为空、低置信或来源互相冲突时，主 Agent 应澄清或拒答，而不是把一个无依据的自然语言答案向后传递。

## 8. 聚合、流式与评估补充

### 问题：审查 Agent 是否一定可靠？

不是。它只能增加一层模型/规则检查，不能替代权限控制、参数校验和权威数据源。高风险规则必须由确定性服务校验；审查结果也要带理由/来源并纳入评测，避免“模型审模型”的循环自信。

### 问题：多 Agent 流式输出如何避免半截错误？

内部节点先产生结构化中间结果，只有达到可展示阶段才向用户流式输出。若后续关键节点失败，明确标注已完成范围和失败原因，不把未经审查的草稿当最终结论。已发送内容要可追踪版本，必要时追加更正而不是静默覆盖。

### 问题：Agent 指标如何算？

路由准确率以标注意图/目标 Agent 为真值；工具成功率区分调用成功、业务成功和用户成功；端到端任务完成率要定义完成条件；时延同时看平均、P95、TTFT 和超时率；高风险任务另看越权拦截率、错误执行率和人工介入率。每个指标明确样本范围和失败归因。
