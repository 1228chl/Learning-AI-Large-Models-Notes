# 哈希表

## 定义

哈希表（Hash Table / HashMap）是一种通过**键（Key）直接访问值（Value）** 的数据结构。它利用哈希函数将键映射到数组中的某个位置，实现近乎 $O(1)$ 的查找、插入和删除。

**核心思想**：设 $index$ 为数组下标，$capacity$ 为数组容量：$index = hash(key) \mod capacity$

## 直观理解

### 哈希表的键值映射机制

数组的随机访问是 $O(1)$——给定下标可直接定位。但下标必须是整数，而实际数据（如字符串"用户ID"）不是整数。哈希表的核心思想是：**设计一个函数，把任意键转换成整数下标**。

这个函数就是哈希函数 $h(key) = index$。理想情况下，每个键映射到不同的下标，此时哈希表就是数组——$O(1)$ 查找。但现实中没有完美的哈希函数，多个键可能映射到同一位置（冲突），此时需要额外的冲突解决策略。

### 负载因子对性能的影响

负载因子 $= \text{元素数} / \text{容量}$ 表示哈希表的"填充程度"：
- 负载因子低（< 0.5）：冲突少，查找快，但浪费空间
- 负载因子高（> 0.75）：冲突多，查找慢，但节省空间
- 超过阈值时触发扩容（rehash）：重新分配更大的数组，所有元素重新哈希，$O(n)$ 开销

Python dict 的负载因子阈值约 2/3，在时间和空间之间取得平衡。

## 核心操作复杂度

| 操作 | 平均 | 最坏 | 说明 |
|------|:----:|:----:|------|
| **查找** | $O(1)$ | $O(n)$ | 所有键冲突时退化为链表 |
| **插入** | $O(1)$ | $O(n)$ | 扩容或冲突严重时 |
| **删除** | $O(1)$ | $O(n)$ | 同查找 |

```python
# Python 字典（dict）和集合（set）底层就是哈希表
d = {}                                  # 创建空字典，底层分配初始哈希表数组

d["name"] = "AI"                        # 插入键值对：对键"name"计算哈希值确定存储位置
d["name"]                               # 查找：对键"name"再次哈希直接定位到存储位置，O(1)
del d["name"]                           # 删除：通过哈希找到位置后移除键值对

# set 也是哈希表
s = {1, 2, 3}                           # 集合只存键不存值，同样利用哈希实现O(1)查找
1 in s                                  # O(1)成员检查：对1哈希求值后直接判断是否存在
```

## 哈希冲突与解决

不同键映射到同一位置称为**哈希冲突**（Collision）。常用两种解决方式：

| 方法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **链地址法（Separate Chaining）** | 数组每个位置是个链表/树 | 实现简单，不限元素数 | 极端情况退化为链表 |
| **开放寻址法（Open Addressing）** | 冲突时找下一个空位（线性/平方探测） | 内存紧凑，缓存友好 | 删除复杂，负载因子敏感 |

Python 的 `dict` 采用**开放寻址法 + 随机探测**，Java 的 `HashMap` 采用**链地址法**（冲突超过阈值转为红黑树）。

## 负载因子

$$
\text{Load Factor} = \frac{\text{元素个数}}{\text{数组容量}}
$$

- 负载因子越高，冲突概率越大，性能下降
- 超过阈值时触发**扩容（Rehash）**——重新分配更大的数组，重新哈希所有元素
- Python dict 的负载因子阈值约为 $2/3$

## 哈希函数

好的哈希函数应：**确定性**（同一键总是同一哈希值） + **均匀分布**（减少冲突） + **高效计算**

```python
# Python 内置哈希
hash("hello")                            # 字符串哈希：快速计算且分布均匀，进程重启后种子变化
hash(42)                                 # 小整数哈希：直接返回自身，避免额外计算开销
```

## ML 中的哈希表

| 场景 | 使用方式 | 说明 |
|------|----------|------|
| **特征映射** | `{词: 索引}` 词表映射 | 将文本转换为整数 ID |
| **模型配置** | `dict` 存储超参数 | `{"lr": 0.001, "batch_size": 32}` |
| **嵌入查找** | `nn.Embedding` 本质是查表 | 输入 ID 映射为稠密向量 |
| **缓存结果** | `{输入: 输出}` 缓存推理结果 | 相同输入避免重复计算 |
| **去重** | `set` 检查数据是否已处理 | 海量数据去重 |
| **计数器** | `collections.Counter` | 统计词频、标签分布 |

## 面试追问

**Q1（基础）**：哈希表如何实现 $O(1)$ 的查找？哈希函数在其中起什么作用？
**回答要点**：

1. 哈希函数将键映射为数组下标，查找时再次哈希直接定位到存储位置，无需遍历
2. 检查该位置键是否与目标键一致，一致则返回值，不一致则按冲突解决策略继续查找
3. 哈希函数质量决定冲突概率：好的哈希函数需满足确定性、均匀分布、高效计算

**Q2（深挖）**：链地址法和开放寻址法解决哈希冲突各有什么优劣？Python 的 dict 和 Java 的 HashMap 为什么选择不同的方案？
**回答要点**：

1. 链地址法实现简单、允许元素超过容量，但极端退化为链表且需额外指针内存
2. 开放寻址法内存紧凑、缓存友好，但删除复杂、负载因子超过 2/3 性能骤降
3. Python dict 用开放寻址 + 随机探测追求紧凑和缓存效率；Java HashMap 用链地址 + 红黑树保证最坏情况性能

**Q3（实战）**：在 NLP 任务中构建词表时，为什么用哈希表（dict）做词到 ID 的映射？大量键冲突时如何影响性能？
**回答要点**：

1. 词表映射要求 O(1) 查询效率，每次 batch 需快速将 token 转为 ID，哈希表最合适
2. 冲突严重时查找退化为 O(n)，导致训练速度变慢
3. 可通过增大容量、选择均匀哈希函数（如 SipHash）、或使用 hashlib 定制哈希来缓解

**Q4（边界）**：哈希表在哪些场景下不适用？此时有哪些替代数据结构？
**回答要点**：

1. 有序遍历不适用（哈希表无序），需用平衡 BST 或跳表
2. 范围查询无法高效支持，需用 B+ 树或线段树
3. 键空间极小且可枚举时直接用数组比哈希表更高效；分布式场景需用一致性哈希环
