# 多态与鸭子类型

## 定义

多态（Polymorphism）指不同类的对象对同一消息（方法调用）做出不同响应——**同一个接口，不同实现**。Python 的多态基于**鸭子类型**（Duck Typing）：不检查对象的类型，只检查对象是否有需要的方法或属性。

> "如果它走路像鸭子、叫起来像鸭子，那它就是鸭子。"

## 鸭子类型

```python
# Dog 类实现了 speak 方法，模拟狗的叫声——类的名称和方法语义一致
class Dog:
    def speak(self):
        return "Woof!"

# Cat 类也实现了 speak 方法，但返回猫的叫声——与 Dog 使用相同接口但行为不同
class Cat:
    def speak(self):
        return "Meow!"

# Car 类同样拥有 speak 方法，但从语义上看 Car 跟"动物"毫无关系，
# 这恰恰体现了鸭子类型的核心：不要求继承关系，只要接口匹配即可使用
class Car:
    def speak(self):
        return "Vroom!"

# 鸭子类型函数：不检查传入对象的类型或类的继承关系，只要求对象拥有 speak 方法即可调用
# Python 在运行时动态查找该方法，不关心对象"是什么"，只关心"有什么行为"
def make_sound(animal):
    print(animal.speak())

# 验证鸭子类型：三个完全不同的类，因为都实现了相同的 speak 接口，可以无缝传入同一函数
make_sound(Dog())           # 输出 Woof!
make_sound(Cat())           # 输出 Meow!
make_sound(Car())           # 输出 Vroom! —— 即使是 Car 也能正常工作，体现了"有行为即是类型"的设计哲学
```

## 抽象基类（ABC）

需要定义显式接口时使用 `abc` 模块强制子类实现特定方法：

```python
from abc import ABC, abstractmethod

# 抽象基类 Model：通过 ABC 和 @abstractmethod 强制要求所有子类实现 train 和 predict 方法
# 这与鸭子类型相反——ABC 在实例化时（而非调用方法时）就检查子类是否实现了所有抽象方法
class Model(ABC):
    @abstractmethod
    def train(self, X, y):
        pass

    @abstractmethod
    def predict(self, X):
        pass

# LinearModel 继承 Model 抽象基类，必须实现父类声明的所有抽象方法才能通过实例化检查
# 这种设计确保了整个框架中所有模型都遵循统一的接口约定，方便 pipeline 等工具统一调度
class LinearModel(Model):
    def train(self, X, y):
        print("Linear model training...")

    def predict(self, X):
        print("Linear model predicting...")
```

## Protocol（Python 3.8+）

Python 3.8 引入 `typing.Protocol`，在静态类型检查时定义接口（不强制运行时检查）：

```python
from typing import Protocol

# 用 Protocol 定义 Speaker 接口：明确要求实现 speak() 方法并返回字符串
# Protocol 在运行时没有强制力，但静态类型检查工具（如 mypy、pyright）会据此验证代码
class Speaker(Protocol):
    def speak(self) -> str: ...

# Dog 类虽然没有显式继承 Speaker，但方法签名（方法名、参数、返回类型）完全匹配，
# 在静态类型检查中会被视为 Speaker 的隐式子类型——这被称为"结构子类型化"（structural subtyping）
class Dog:
    def speak(self) -> str:
        return "Woof!"

# 参数类型注解为 Speaker Protocol，类型检查工具会验证传入的实参是否正确实现了 speak 接口
def make_sound(animal: Speaker) -> None:
    print(animal.speak())

# Dog 实例传入——类型检查通过（结构匹配），运行时也可以正常工作
make_sound(Dog())
```

| 方式 | 强制运行时 | 静态检查 | 适用场景 |
|------|:---------:|:---------:|----------|
| **鸭子类型** | ❌ | ❌ | 快速原型、内部代码 |
| **ABC** | ✅（子类必实现） | ⚠️ 有限 | 框架设计、库 API |
| **Protocol** | ❌ | ✅ | 大型项目类型安全 |

### 选型决策流

```
需要运行时强制子类实现？ → 是 → ABC
     ↓ 否
需要静态类型检查 + IDE 提示？ → 是 → Protocol
     ↓ 否
需要最大灵活性？ → 鸭子类型
```

ABC 适合框架底座（如 PyTorch 的 `nn.Module`），Protocol 适合大型团队协作的统一接口约定，纯鸭子类型适合内部快速迭代。三者可以共存：用 Protocol 定义接口，用 ABC 提供默认实现，运行时用鸭子类型捕获异常。

## ML/DL 应用场景

| 应用场景 | 体现 | 说明 |
|----------|------|------|
| PyTorch 优化器统一接口 | `SGD`、`Adam`、`AdamW` 都继承 `Optimizer` | 鸭子类型风格，不关心哪种优化器，只调用 `step()` |
| 数据集加载 | `ImageFolder(Dataset)`、`TensorDataset(Dataset)` | 统一实现 `__len__` 和 `__getitem__` |
| sklearn Estimator 接口 | `fit()` / `predict()` / `transform()` | 所有模型遵循相同 API 约定（鸭子类型） |
| 回调函数 | `on_epoch_end`、`on_batch_end` 等钩子 | 不继承特定类，只要实现对应方法即可作为回调 |

## 面试追问

**Q1（基础）**：Python 的多态和 Java/C++ 的多态有什么本质不同？
**回答要点**：

1. Java/C++ 是编译时类型检查的多态——方法参数必须声明父类类型，通过虚函数表在运行时动态分派
2. Python 是运行时鸭子类型——不检查对象的继承关系，只检查对象是否有期望的方法
3. Python 的多态更灵活，但缺少编译时类型检查，静态检查能力更弱

**Q2（深挖）**：鸭子类型在什么场景下会失效或者带来隐患？如何缓解？
**回答要点**：

1. 当对象意外拥有同名方法但语义不同时，会静默执行错误逻辑且不报错
2. 缺乏显式类型约束导致 IDE 补全受限和代码可读性下降
3. 缓解方案：用 Protocol 定义显式接口、增加类型注解、完善单元测试覆盖

**Q3（实战）**：在 sklearn 统一 Estimator 接口设计中，鸭子类型体现在哪里？这给使用者带来什么好处？
**回答要点**：

1. 所有模型都有 `fit(X, y)` 和 `predict(X)` 方法，使用者无需关心模型内部实现
2. 用同一个训练和评估流程即可处理线性回归、随机森林、SVM 等不同模型
3. 这种设计使 pipeline 和 grid search 可以统一处理任何符合接口的模型，大幅提升框架的扩展性

**Q4（边界）**：ABC（抽象基类）和 Protocol 在实际项目中应该如何选择？什么场景下两者都不适用？
**回答要点**：

1. ABC 适合框架设计——需要强制子类实现特定方法、提供默认实现、运行时检查
2. Protocol 适合大型项目协作——需要静态类型检查但不希望有运行时代价
3. 两者都不适用的场景：性能敏感代码、需要动态添加/移除方法的场景，此时直接使用鸭子类型更合适
