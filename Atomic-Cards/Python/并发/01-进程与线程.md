# 进程与线程

> 本文为并发编程总览，详细内容见 [进程与多进程](03-进程与多进程.md) 和 [线程与GIL](04-线程与GIL.md)。

## 三种并发方式五维对比

| 对比维度 | 多进程 | 多线程 | 协程 |
|:--------:|:-------|:-------|:-----|
| **调度单位** | 进程（资源分配单位） | 线程（CPU 调度单位） | 函数（用户态协作式） |
| **内存开销** | 高（独立地址空间） | 中（共享进程内存） | 极低（单线程栈） |
| **通信方式** | IPC（Queue/Pipe/共享内存） | 共享变量 + 锁 | `await` 传递结果 |
| **CPU 密集** | **推荐**（多核并行） | 不推荐（GIL 串行化） | 不推荐（单线程） |
| **I/O 密集** | 可用（IPC 开销较大） | **推荐**（GIL 在 I/O 时释放） | **推荐**（性能最佳） |

## 选择逻辑：为什么不同场景要用不同并发方式？

**核心原则：并发方式的选择取决于瓶颈类型。**

- **CPU 密集型**（矩阵运算、数据预处理、模型推理）：瓶颈在 CPU 计算能力，必须利用多核并行。Python 的 GIL 使多线程无法并行执行 Python 字节码，因此只有多进程能加速。协程是单线程，CPU 密集型任务中无法提升吞吐。
- **I/O 密集型**（网络请求、文件读写、API 调用）：瓶颈在等待 I/O 完成，CPU 大部分时间空闲。协程在单线程中以极低开销切换等待任务，性能最优。多线程次之（GIL 在 I/O 等待时释放）。多进程可用但 IPC 通信成本较高。
- **GPU 推理**：模型参数在显存中，多进程无法共享显存（每个进程需独立加载模型，显存开销倍增）。多线程共享进程显存，模型参数零拷贝，是唯一合理选择。

**如何判断你的场景类型**：测量 CPU 利用率。若 CPU 利用率持续接近 100% 是 CPU 密集；若 CPU 利用率低且程序响应慢是 I/O 密集。

## Python 选择指南

| 场景 | 最佳方案 | 原因 |
|:----|:--------|:-----|
| CPU 密集型计算 | **多进程**（`multiprocessing`） | 绕过 GIL，利用多核 |
| I/O 密集型 | **协程** > **多线程** | 更轻量，无锁竞争 |
| 混合型（计算 + I/O） | 多进程 + 协程 | 各自优势互补 |
| 单 GPU 模型推理 | **多线程**（释放 GIL） | 共享模型参数，零拷贝 |

## 并发场景速查

- **CPU 密集**（矩阵运算、数据预处理）：多进程，利用多核并行
- **I/O 密集**（网络请求、文件读写、API 调用）：协程，单线程高效切换
- **GPU 推理**（加载模型 → 推理 → 返回）：多线程，模型参数共享零拷贝
- **混合负载**（数据分析 + 网络请求）：多进程 + 协程组合

## 面试追问

**Q1（基础）**：进程、线程和协程的核心区别是什么？
**回答要点**：

1. 进程是资源分配单位，拥有独立地址空间，内存开销高，通信需依赖 IPC
2. 线程是 CPU 调度单位，共享进程内存，通信方便但需加锁，可被操作系统抢占
3. 协程是用户态协作式调度，在单线程中通过 await 切换，内存开销极低

**Q2（深挖）**：Python 的 GIL 如何影响三种并发方式的选择？
**回答要点**：

1. CPU 密集型计算必须使用多进程绕过 GIL，才能实现多核并行
2. I/O 密集型任务中 GIL 在 I/O 等待时会主动释放，多线程可行，但协程性能更优
3. 多线程不适合 CPU 密集计算场景，因为 GIL 会串行化 Python 字节码的执行

**Q3（实战）**：需要同时执行 CPU 密集的数据分析和大量网络请求，如何设计并发方案？
**回答要点**：

1. 采用多进程 + 协程的混合方案，使各自优势互补
2. 多进程负责 CPU 密集型的数据分析任务，利用多核并行提升吞吐
3. 协程负责 I/O 密集的网络请求，在单线程中高效切换且无需锁竞争

**Q4（边界）**：在单 GPU 模型推理场景中，为什么多线程反而比多进程更合适？
**回答要点**：

1. 多线程共享进程内存空间，模型参数可以在线程间零拷贝共享
2. 模型推理时 Python 代码会释放 GIL，允许一定程度上的并行执行
3. 多进程的独立地址空间无法共享 GPU 显存，且进程间通信开销过大
