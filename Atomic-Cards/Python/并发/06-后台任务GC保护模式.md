# 后台任务 GC 保护模式

## 定义

`asyncio.create_task` 用于将协程"扔到后台去跑"，不阻塞当前流程。但返回的 `Task` 对象如果**没有用变量持有强引用**，Python 的垃圾回收器（GC）可能在任务还没跑完时就把它回收掉，导致**后台任务无声无息地消失**。

### 核心公式

```
安全后台任务 = create_task + 模块级集合(强引用) + done_callback(自动清理)
```

### 直观理解

> 好比你把一份文件放在"待处理"篮子（create_task），但如果你没把篮子放在显眼的位置（强引用），清洁工（GC）可能以为篮子里的纸是垃圾，直接扔掉了。你回来发现文件没了，但不知道发生了什么。

## 问题场景

有些操作很慢，但用户不需要傻等结果。比如试卷批改：接口可以先返回"已收到，正在后台批改"，批改任务在后台慢慢跑：

```python
# 试卷批改接口
@app.post("/exam/submit", status_code=202)
async def submit_exam(exam_id: str):
    # 把批改任务丢到后台
    task = asyncio.create_task(grade_exam(exam_id))
    return {"message": "已收到，正在后台批改", "exam_id": exam_id}
```

这段代码看起来没问题，但 `task` 是局部变量——函数返回后，`task` 的引用计数归零，GC 可能在批改还没完成时就把任务回收了。

## 标准防御模式

```python
import asyncio

# 模块级集合：持有所有后台任务的强引用，防止被 GC 提前回收
_background_tasks: set[asyncio.Task] = set()

async def grade_exam(exam_id):
    print(f"开始批改试卷 {exam_id}……")
    await asyncio.sleep(2)               # 模拟耗时的批改过程
    print(f"试卷 {exam_id} 批改完成")

async def submit():
    task = asyncio.create_task(grade_exam("EX-001"))  # 丢到后台
    _background_tasks.add(task)                         # 关键①：强引用，防 GC
    task.add_done_callback(_background_tasks.discard)   # 关键②：跑完自动移除
    print("接口立即返回：已收到，正在后台批改")

async def main():
    await submit()
    await asyncio.sleep(3)    # 模拟服务持续运行，给后台任务跑完的时间
    print("当前后台任务数：", len(_background_tasks))

asyncio.run(main())
```

输出：
```
接口立即返回：已收到，正在后台批改
开始批改试卷 EX-001……
试卷 EX-001 批改完成
当前后台任务数：0
```

**关键三件套**：

| 步骤 | 代码 | 作用 |
|:----|:-----|:-----|
| ① 模块级集合 | `_background_tasks: set[asyncio.Task] = set()` | 声明集合持有强引用 |
| ② 创建后加入 | `_background_tasks.add(task)` | 立即加入集合，防止 GC |
| ③ 完成时移除 | `task.add_done_callback(_background_tasks.discard)` | 跑完自动移除，防内存泄漏 |

## 标准模板

EduAgent 中的标准写法：

```python
# api/v1/exam.py 或 api/v1/resume.py 文件顶部
_background_tasks: set[asyncio.Task] = set()

def _on_task_done(task: asyncio.Task):
    """任务完成后的回调：清理后台任务引用"""
    _background_tasks.discard(task)     # 从集合移除
    # 其他清理逻辑：删除临时文件、标记数据库状态等
    if task.exception():
        logger.error("后台任务失败", error=str(task.exception()))
        # 标记数据库记录为 failed

# 创建后台任务
task = asyncio.create_task(graph.ainvoke(initial_state))
_background_tasks.add(task)
task.add_done_callback(_on_task_done)
```

## 常见问题

### 为什么不直接删掉这两个节点？

问：为什么不能直接 `await` 等任务完成？
答：如果直接 `await`，接口会卡住 30-60 秒等批改完成，用户体验极差。后台任务模式让接口立刻返回 202，任务在后台异步执行。

### 内存泄漏风险？

`_background_tasks` 集合如果不清理，会随着时间推移越来越大。但 `add_done_callback(_background_tasks.discard)` 确保任务完成时自动移除引用，不会泄漏。

## 面试追问

**Q1（基础）**：后台任务被 GC 回收的问题是什么？标准防御三件套是什么？
**回答要点**：
1. create_task 返回的 Task 没有强引用时，GC 可能在任务没跑完时回收
2. 模块级集合 `_background_tasks: set[asyncio.Task] = set()`
3. 创建后立即 `_background_tasks.add(task)` 加入集合
4. 通过 `task.add_done_callback(_background_tasks.discard)` 任务完成后自动移除

**Q2（深挖）**：为什么 create_task 的 Task 会被 GC 回收？Python 的 GC 机制是什么？
**回答要点**：
1. 局部变量在函数返回后引用计数归零，成为 GC 的回收目标
2. Python 的 GC 使用引用计数为主，标记清除为辅
3. Task 对象虽然内部有事件循环引用，但如果没有外部强引用，仍可能被回收

**Q3（实战）**：EduAgent 中哪些场景使用了后台任务 GC 保护模式？
**回答要点**：
1. 简历审查：上传 PDF 后，后台异步执行 8 个节点的审查流程
2. 试卷批改：提交试卷后，后台异步执行三轨并行批改
3. 两个场景的文件顶部都有 `_background_tasks: set[asyncio.Task] = set()`

**Q4（边界）**：后台任务能在模块级别直接 `await` 吗？如果不做 GC 保护，最坏情况是什么？
**回答要点**：
1. 模块级别不能直接 await（只能在 async def 内 await）
2. 最坏情况：任务被 GC 回收，审查/批改无声无息地失败，用户永远等不到结果
3. 数据库记录会永远卡在 `processing` 状态，需要超时兜底机制清理
