# 进程与线程

## 进程 vs 线程

| 对比维度 | 进程（Process） | 线程（Thread） |
|----------|----------------|----------------|
| **资源拥有** | 独立的地址空间、文件句柄等 | 共享所属进程的资源 |
| **调度单位** | 操作系统分配资源的基本单位 | CPU 调度的基本单位 |
| **通信方式** | IPC（管道、队列、共享内存） | 直接读写共享变量（需加锁） |
| **创建开销** | 大 | 小 |
| **隔离性** | 进程间相互隔离，一个崩溃不影响其他 | 一个线程崩溃可能影响整个进程 |
| **适用** | CPU 密集型任务 | I/O 密集型任务 |

## GIL（全局解释器锁）

CPython 的 GIL 使得**同一时刻只有一个线程能执行 Python 字节码**。这意味着多线程无法利用多核并行加速 CPU 密集型任务。

```python
# CPU 密集型：多进程更快
# I/O 密集型：多线程也有效（GIL 在 I/O 等待时释放）
```

| 场景 | 推荐方案 | 原因 |
|------|----------|------|
| CPU 密集（矩阵运算、数值计算） | **多进程** / 使用 NumPy/C扩展 | GIL 会串行化多线程 |
| I/O 密集（文件读写、网络请求） | **多线程** / **协程** | I/O 等待时 GIL 释放 |
| 混合场景 | 多进程 + 异步/协程 | 综合优势 |

## Python 并发编程三种方式

```python
# 1. 多线程
import threading
t = threading.Thread(target=func, args=(x,))
t.start(); t.join()

# 2. 多进程
import multiprocessing
p = multiprocessing.Process(target=func, args=(x,))
p.start(); p.join()

# 3. 协程（asyncio）
import asyncio
async def func():
    await asyncio.sleep(1)
asyncio.run(func())
```

| 方式 | 模块 | 特点 | 内存 |
|------|------|------|------|
| **多线程** | `threading` | 共享内存，需加锁 | 低 |
| **多进程** | `multiprocessing` | 隔离内存，IPC通信 | 高 |
| **协程** | `asyncio` | 单线程事件循环，无锁 | 极低 |

## 线程锁

```python
import threading
lock = threading.Lock()

def safe_update():
    with lock:              # 自动 acquire/release
        shared_var += 1
```

## ML 中的并发使用

| 场景 | 方案 | 说明 |
|------|------|------|
| **DataLoader 多进程加载** | `num_workers > 0` | 多进程预加载数据，避免 GPU 等待 |
| **分布式训练** | `torch.distributed` | 多进程 + NCCL，跨 GPU/节点 |
| **超参数搜索** | 多进程并行运行实验 | 每个进程独立训练一个配置 |
| **模型推理部署** | 多线程处理请求 | 每个请求一个线程，GIL不阻塞I/O |

> **面试追问**
> 
> Q1（基础）：进程和线程在资源隔离和通信方式上有什么区别？各自适合什么类型的任务？
> 回答要点：进程有独立地址空间和资源，通信需 IPC（队列、管道、共享内存），适合 CPU 密集型任务；线程共享进程内资源，直接读写变量（需加锁），适合 I/O 密集型任务；进程间隔离性强，一个崩溃不影响其他。
> 
> Q2（深挖）：Python 的 GIL 是什么？它对多线程和多进程的性能影响有什么本质区别？
> 回答要点：GIL 是 CPython 的全局解释器锁，同一时刻只有一个线程执行 Python 字节码；多线程无法利用多核加速 CPU 密集任务，但 I/O 密集任务中 GIL 在等待时释放，多线程仍然有效；多进程每个进程有独立 GIL，能利用多核，但内存开销更大。
> 
> Q3（实战）：PyTorch 的 `DataLoader` 中 `num_workers>0` 是如何实现数据预加载的？为什么通常推荐设置为 GPU 数量的 4 倍左右？
> 回答要点：`num_workers>0` 启动多个子进程并行加载和预处理数据，主进程（GPU 侧）训练同时后台预取下一批；设置为 GPU 数的 4 倍左右是为了保证数据流水线不阻塞 GPU 计算，但设置过大可能导致内存溢出和数据加载颠簸。
> 
> Q4（边界）：多线程中的 `threading.Lock` 有哪些常见陷阱？如何避免死锁？
> 回答要点：常见陷阱有忘记释放锁、重复加锁导致死锁、加锁顺序不一致导致循环等待；避免方法：使用 `with lock:` 自动管理获取/释放，避免在锁内调用可能阻塞的外部函数，必要时使用 `RLock`（可重入锁）代替 `Lock`。
>
