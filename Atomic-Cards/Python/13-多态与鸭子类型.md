# 多态与鸭子类型

## 定义

多态（Polymorphism）指不同类的对象对同一消息（方法调用）做出不同响应——**同一个接口，不同实现**。Python 的多态基于**鸭子类型**（Duck Typing）：不检查对象的类型，只检查对象是否有需要的方法或属性。

> "如果它走路像鸭子、叫起来像鸭子，那它就是鸭子。"

## 鸭子类型

```python
class Dog:
    def speak(self):
        return "Woof!"

class Cat:
    def speak(self):
        return "Meow!"

class Car:
    def speak(self):
        return "Vroom!"

def make_sound(animal):     # 不关心具体类型，只关心有无 speak 方法
    print(animal.speak())

make_sound(Dog())           # Woof!
make_sound(Cat())           # Meow!
make_sound(Car())           # Vroom!（即使是 Car，有 speak 方法就能用）
```

## 抽象基类（ABC）

需要定义显式接口时使用 `abc` 模块强制子类实现特定方法：

```python
from abc import ABC, abstractmethod

class Model(ABC):
    @abstractmethod
    def train(self, X, y):
        pass

    @abstractmethod
    def predict(self, X):
        pass

class LinearModel(Model):
    def train(self, X, y):
        print("Linear model training...")

    def predict(self, X):
        print("Linear model predicting...")
```

## Protocol（Python 3.8+）

Python 3.8 引入 `typing.Protocol`，在静态类型检查时定义接口（不强制运行时检查）：

```python
from typing import Protocol

class Speaker(Protocol):
    def speak(self) -> str: ...

class Dog:
    def speak(self) -> str:
        return "Woof!"

def make_sound(animal: Speaker) -> None:
    print(animal.speak())

make_sound(Dog())    # ✅ 通过类型检查
```

| 方式 | 强制运行时 | 静态检查 | 适用场景 |
|------|:---------:|:---------:|----------|
| **鸭子类型** | ❌ | ❌ | 快速原型、内部代码 |
| **ABC** | ✅（子类必实现） | ⚠️ 有限 | 框架设计、库 API |
| **Protocol** | ❌ | ✅ | 大型项目类型安全 |

## ML/DL 应用场景

| 应用场景 | 体现 | 说明 |
|----------|------|------|
| PyTorch 优化器统一接口 | `SGD`、`Adam`、`AdamW` 都继承 `Optimizer` | 鸭子类型风格，不关心哪种优化器，只调用 `step()` |
| 数据集加载 | `ImageFolder(Dataset)`、`TensorDataset(Dataset)` | 统一实现 `__len__` 和 `__getitem__` |
| sklearn Estimator 接口 | `fit()` / `predict()` / `transform()` | 所有模型遵循相同 API 约定（鸭子类型） |
| 回调函数 | `on_epoch_end`、`on_batch_end` 等钩子 | 不继承特定类，只要实现对应方法即可作为回调 |

## 面试追问

**Q1（基础）**：Python 的多态和 Java/C++ 的多态有什么本质不同？

**回答要点**：Java/C++ 是**编译时类型检查**的多态——方法参数必须声明父类类型，通过虚函数表在运行时动态分派；Python 是**运行时鸭子类型**——不检查对象的继承关系，只检查对象是否有期望的方法，更灵活但静态检查更弱。

**Q2（深挖）**：鸭子类型在什么场景下会失效或者带来隐患？如何缓解？

**回答要点**：当对象意外拥有同名方法但语义不同时，会静默执行错误逻辑且不报错（如一个有 `speak()` 方法的文件对象）；缺乏显式类型约束导致 IDE 补全受限和代码可读性下降；缓解方案：用 `Protocol` 定义显式接口、增加类型注解、完善单元测试覆盖。

**Q3（实战）**：在 sklearn 统一 Estimator 接口设计中，鸭子类型体现在哪里？这给使用者带来什么好处？

**回答要点**：所有模型都有 `fit(X, y)` 和 `predict(X)` 方法，使用者无需关心模型内部实现；用同一个训练和评估流程即可处理线性回归、随机森林、SVM 等不同模型；这种设计使 pipeline 和 grid search 可以统一处理任何符合接口的模型，大幅提升框架的扩展性。

**Q4（边界）**：ABC（抽象基类）和 Protocol 在实际项目中应该如何选择？什么场景下两者都不适用？

**回答要点**：ABC 适合框架设计——需要强制子类实现特定方法、提供默认实现、运行时检查；Protocol 适合大型项目协作——需要静态类型检查但不希望有运行时代价；两者都不适用的场景：性能敏感代码（ABC 的 isinstance 检查有开销）、需要动态添加/移除方法的场景（直接鸭子类型更合适）。
