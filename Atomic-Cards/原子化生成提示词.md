# 原子化知识卡片生成提示词

> 用途：将知识点生成为统一格式的原子卡片，存入仓库对应分类目录下
> 参考样例：`Atomic-Cards/线性代数/01-向量基础.md`

---

## 输出目录规则

所有卡片按知识点归属写入 `Atomic-Cards/<分类名>/` 下。使用**多级子目录**按知识点领域精确分类，无数量限制。

### 分类原则：基于内容，而非标题

分类时 **必须阅读卡片主体内容（定义、核心公式、应用场景）** 来决定归属，不得仅凭标题或文件名判断。常见陷阱：

- **标题含"光滑"** → 可能误判为模型压缩中的光滑技术 → 实际内容可能是"光滑损失函数"，应归入损失函数类
- **标题含"GPU"** → 可能误判为硬件 → 实际内容可能是"GPU并行与混合精度训练"，应归入深度学习训练优化
- **标题含"Claude"** → 可能误判为硬件 → 实际内容可能是"Claude使用指南（软件工具）"，应归入工程实践/工具
- **标题含"模型"** → 检查是否真的是模型压缩技术，还是模型训练/评估

**判断标准**：根据卡片**定义首句**和**核心公式**定位所属领域，而不是目录名或文件名。

**新卡片编号**：检查对应子目录下已有文件的最高编号，新卡片为 `{最高编号+1}-{概念名}.md`，两位数补零。

**多级目录规则**：

- 知识点相近的卡片（3 张以上）应归入同一子目录
- 若一个子目录内的卡片超过 10 张或知识点仍过于混杂，可创建**三级子目录**进一步细化
- 新知识点若不属于现有子目录，可新建子目录（甚至三级目录）
- 禁止将概念不同的卡片混放在同一扁平目录下——宁可创建只有 1 张卡片的子目录，确保知识分类精确

**重复卡片检查**：新增卡片前先搜索全局文件名是否已有同名概念（`grep -r "概念名" Atomic-Cards/`），若存在则更新现有卡片而非新建。

## 卡片格式要求

### Frontmatter（YAML 元数据）

```yaml
---
author: "XunZong"
created: "2026-07-06"
tags: ["所属分类", "二级标签", "核心概念"]
aliases: ["中文名", "English Term"]
---
```

- `tags`：至少 2 个，第一个为所属分类，第二个为具体标签
- `aliases`：包含中文名和常用英文术语

### 正文结构

每张卡片选择包含以下 **2-4 个部分**（定义必选）：

#### 1. 定义（必备）

严谨易懂的定义，包含数学形式。**必须有 LaTeX 公式**（行内 `$...$`，块级 `$$...$$$`）。

#### 公式变量含义标注（强制）

每个公式中的**每个字母/符号**都必须标注其含义。标注方式为以下两种之一（任选其一即可）：

**推荐格式：公式后逐行列出，每行一个变量**

```markdown
$$
\theta_{t+1} = \theta_t - \eta \nabla L(\theta_t)
$$

- $\theta_t$：第 $t$ 步的模型参数
- $\eta$：学习率（步长）
- $\nabla L(\theta_t)$：损失函数在 $\theta_t$ 处的梯度
```

**规则**：

- **禁止**让读者靠惯例或上下文推断变量含义（如 $W$ 表示权重、$b$ 表示偏置虽然是惯例，但仍需在首次出现时说明）
- 同一卡片中已标注过的变量可不再重复标注
- 表格内的公式：在表头行或表格前后说明通用符号含义，或每行"说明"列中解释
- 数学常量和公认符号（如 $\pi$、$e$、$\mathbb{R}$ 表示实数集）可省略标注

#### 2. 核心公式 / 分类表（若适用）

Markdown 表格列出公式/分类/对比，含名称、公式（LaTeX）、含义/几何意义、应用。

#### 2b. 公式推导（数学/ML 核心卡片强制，其他推荐）

公式类卡片必须提供**推导过程或直觉解释**，而非仅贴最终公式：

- **ML 算法**：给出损失函数→梯度→参数更新的完整推导链路
- **数学性质**：用"为什么"引出——为什么对称矩阵特征值是实数？为什么 softmax 要加 temperature？
- **反向传播**：关键公式的梯度推导链，如 LSTM 的梯度流为什么是加法而非乘法

#### 2c. 对比分析中的决策逻辑（推荐）

对比表格不只是罗列区别，每张对比表后应跟一段**"如何选择"**的结论，说明：

- 不同方案的适用前提和代价
- 典型场景下的推荐方案
- "不选某个方案会怎样"的反面论证

#### 3. 直观理解 / 几何意义（若适用）

一句话解释直觉含义，帮助理解。

#### 4. ML/DL 应用场景（重要，必选）

表格或列表说明概念在 AI 领域的具体出现位置及数学形式：

| 应用场景 | 数学形式 | 说明 |
|----------|----------|------|

**例外处理（纯基础数学卡片）**：若当前卡片属于纯数学工具（如线性代数中的行列式、特征值、范数；微积分中的导数定义等），且无法直接在表格中写出具体 ML 算法公式时，可降级为"**数学基础支撑**"模式——列明该数学概念为哪些上层 ML/DL 概念提供理论基础，并至少引用 1 张 `深度学习/` 或 `机器学习/` 目录下的卡片作为应用出口。

示例（`线性代数/07-行列式`）：

| 应用场景 | 数学形式 | 说明 |
|----------|----------|------|
| 判断矩阵可逆性 | $\det(A) \neq 0$ | 用于神经网络参数初始化时保证权重矩阵可逆 |
| 特征值求解前置条件 | $\det(A - \lambda I) = 0$ | 为 PCA 降维提供数学前提 |

### 引用链接（跨领域强制规则）

**链接格式总览**：所有卡片间的引用统一使用标准 Markdown 相对路径。**显示名中不包含编号前缀**，仅写概念名称。

- 同子目录：`[名称](./编号-名称.md)`，如 `[自注意力](./06-自注意力与Transformer.md)` ✅
- 同分类跨子目录：`[名称](../目标子目录/编号-名称.md)`，如 `[矩阵乘法](../矩阵/04-矩阵乘法.md)` ✅
- 跨分类：`[名称](../../目标分类/目标子目录/编号-名称.md)`，如 `[自注意力](../../NLP/架构/06-自注意力与Transformer.md)` ✅
- 跨分类无子目录：`[名称](../../目标分类/编号-名称.md)`，如 `[链式法则](../../微积分与优化/02-链式法则.md)` ✅
- 禁止 Obsidian 风格 `[[wiki链接]]`
- 禁止显示名带编号：`[06-自注意力](./06-自注意力.md)` ❌

卡片末尾引用行格式（每个引用单独成行，前有 `## 参考引用` 标题，每行详细说明引用原因）：

```markdown
## 参考引用

- 需要理解[具体原因]参见 [名称](./编号-名称.md)
- 需要掌握[具体原因]参见 [名称](../同分类子目录/编号-名称.md)
- 需要了解[具体原因]参见 [名称](../目标分类/目标子目录/编号-名称.md)
```

**核心原则**：引用必须跨域，覆盖**数学根基**（线性代数/微积分/概率统计）+ **同域依赖**（当前分类）+ **工程落地**（工程实践/深度学习/AI-Agent），按下方决策流程自检。

**去重规则**：每张卡片在 `## 参考引用` 中**只能出现一次**。同一张卡片不应因换了描述措辞而出两次——如需说明不同的引用角度，合并到同一行描述中。

**数量与配比**：

- 引用总数：**3 ~ 10 张**，必须含至少 1 张 `线性代数/` 或 `微积分与优化/` 的卡片（有数学公式时），以及至少 1 张跨一级目录的卡片
- **禁止为凑数而引用**：每个引用必须有实际意义

**决策流程**：

1. 看公式→引用数学根基  |  2. 看训练→引用深度学习/微积分  |  3. 看部署→引用工程实践

**错误示例**：

- 显示名带编号：`[06-自注意力](...)` ❌ → `[自注意力](...)` ✅
- 无上下文说明的裸引用：`> 参见 [A](./A.md)` ❌ → 每个引用前必须有上下文短语
- 引用路径少写子目录：`[矩阵乘法](../线性代数/04-矩阵乘法.md)` ❌（文件已在 `线性代数/矩阵/` 下）
  → `[矩阵乘法](../线性代数/矩阵/04-矩阵乘法.md)` ✅

### 卡片质量自检（强制）

生成新卡片或修改现有卡片后，必须逐条自查以下质量指标：

**1. 内容密度指标**

| 指标         | 要求                          | 违规处理                                     |
| :--------- | :-------------------------- | :--------------------------------------- |
| 卡片字符数      | **2000 ~ 7000 字符**          | <2000 需补充内容；>7000 检查是否应拆分                |
| 代码示例       | 至少 1 个完整可运行代码段              | 无代码的纯概念卡片需补充伪代码或公式推导                     |
| LaTeX 公式   | **有数学概念的卡片必须含 $ $ 或

$$
 
$$** | 纯工程/工具卡片（Docker/Git/Python logging 等）可豁免 |
| ML/DL 应用场景 | **必选**（表格格式，至少 2 行）         | 纯数学卡片用"数学基础支撑"模式列明支撑的上层概念                |

**2. 结构完整性指标**

| 检查项 | 必须/可选 | 说明 |
|:------|:---------:|:-----|
| Frontmatter（YAML） | 必须 | author/created/tags/aliases 齐全 |
| 定义 + 数学形式 | 必须 | 含 LaTeX 公式 + 每个变量含义标注 |
| 核心公式/分类表 | 适用时 | 对比类内容用表格呈现 |
| 直观理解 | 建议 | 一句话解释，帮助记忆 |
| ML/DL 应用场景 | **必须** | 表格形式，至少 2 行 |
| 面试追问 Q1-Q4 | **必须** | 覆盖基础到深挖到实战到边界 |
| 参考引用 3~10 张 | **必须** | 跨域覆盖数学根基加同域依赖加工程落地 |

**3. 拆分决策流程**

当卡片字符数超过 7000 时，按以下流程判断是否需要拆分：

1. 该卡是否包含两个或多个**独立知识点**？（如"BGE-M3 + BGE-Reranker"应拆为两张）
2. 该卡是否同时包含**基础概念**和**高级扩展**？（如"基础用法 + 高级技巧"应拆为两张）
3. 拆分后每张卡片是否仍满足 2000~7000 字符要求？
4. 拆分后是否有至少 3 张引用分别链接拆分出的子卡片？

若以上任意答案为"是"，则进行拆分；否则可保留单卡片但精简冗余内容。

**4. 重复与补全规则**

- 新增卡片前执行 `grep -r "NN-概念名" Atomic-Cards/` 搜索全局是否已有同名或相似概念
- 若存在相似卡片，用 `diff` 比较内容差异：差异小于 30% 则更新现有卡片而非新建
- 若不存在但有**关联卡片**应引用该卡而非重复阐述相同内容（如"注意力机制"卡片中不重复解释自注意力，应引用"自注意力与Transformer"卡片）

### 格式约束

- **不使用图标**（如 ✅、📝、🔗、💡 等）和 **emoji**
- 纯 Markdown：标题 `#` / `##`、表格、列表、LaTeX 公式
- Python 代码块用 ` ```python ` 包裹，**代码中的关键行必须加中文注释**解释该行/该段的功能和目的
- **代码块必须闭合**：任何 ` ``` ` 开头的代码块（python/bash/yaml/mermaid 等）必须有对应的 ` ``` ` 结束标记。缺失闭合会导致后续所有内容被吞入代码块，Markdown 表格、标题、引用等均无法正常渲染。生成后应手动检查或自动化验证每个代码块是否成对出现
- **LaTeX 公式不得放入代码块中**：` ```python ` / ` ``` ` 等代码块内禁止写入 LaTeX 公式（如 `score(m, n) = Q^T \cdot K`）。数学公式必须使用行内 `$...$` 或块级 `$$...$$` 渲染，放入代码块内无法被 LaTeX 解析器识别，将显示为纯文本 ❌
- 文件名：`<两位序号>-<概念名>.md`
- **内容充实要求**：每张卡片的知识点应足够详细——定义部分需至少包含数学形式或核心公式；分类/对比需用表格呈现并附带选择逻辑；代码示例的核心行需解释"为什么这么写"而非仅"在做什么"；面试问答 Q1-Q4 由浅入深覆盖基础、原理、实战、边界四个层次
- **深度要求**：数学/ML/DL 类卡片必须包含公式推导或直觉解释（"为什么这个公式长这样"），不能只有最终公式。对比分析需给出"所以怎么选"的决策结论。
- **代码比例上限**：代码块字符数不超过全文的 **25%**。代码必须是用来说明原理的**核心片段**（≤15 行），禁止贴完整可运行代码。多余的篇幅留给原理机制、对比权衡、边界条件
- **Markdown 高亮符号转义**：禁止在正文中裸写 `==text==` 格式（部分渲染器将 `==` 解析为高亮标记）。代码表达式含 `==` 时（如 `head==tail`、`(tail+1)%cap==head`），必须用反引号包裹为行内代码 ` ` `head == tail` ` `，防止被误解析为高亮
- **标题用语规范**：**禁止使用 `A = B` 或 `A: B` 的比喻式/等式结构作为章节标题**（如 `梯度下降 = 盲人下山`、`注意力 = 软性数据库查询`）。标题应使用陈述性、专业化的表述，如 `梯度下降的几何直觉`、`注意力机制的查询-键-值结构`。直观解释应写在段落正文中，而非作为标题格式的一部分。本节标题同样适用此规范。

### LaTeX 兼容性规则

在 Markdown 表格中使用 LaTeX 时，禁止 `|` 和 `&` 符号（会被解析为表格列分隔符）：

| 场景 | 错误 | 正确 |
|:----|:-----|:-----|
| 范数 | `$\|x\|$` | `$\Vert x \Vert$` |
| 条件概率 | `$P(A\|B)$` | `$P(A\vert B)$` |
| 绝对值 | `$\|x\|$` | `$\vert x \vert$` |
| 矩阵对齐 | `\begin{matrix} 1 & 2` | 移至表格外用独立 `$$...$$` |

部分 LaTeX 命令在 Obsidian/KaTeX 中不兼容，用替代表达：

| 错误（不兼容） | 正确（兼容） |
|:--------------|:-------------|
| `\argmin` | `\arg\min` 或 `\operatorname{argmin}` |
| `\argmax` | `\arg\max` 或 `\operatorname{argmax}` |
| `\softmax` | `\text{softmax}` 或 `\operatorname{softmax}` |
| `\R` / `\N` | `\mathbb{R}` / `\mathbb{N}` |
| `\Var` / `\Cov` / `\E` | `\operatorname{Var}` / `\operatorname{Cov}` / `\mathbb{E}` |
| `\relu` / `\sigmoid` | `\text{ReLU}` / `\text{sigmoid}` |
| `\lVert` / `\rVert` | `\Vert` |

**核心原则**：非标准运算符用 `\operatorname{}` 包裹，标准文本缩写用 `\text{}` 包裹。

### GitHub 渲染兼容性（强制）

生成的 LaTeX 公式必须能在 **GitHub 的 Markdown 渲染器（MathJax 3）** 中正确渲染。Obsidian 和 Typora 的渲染宽容度更高，不能仅以它们为准。

**块级公式 `$$...$$` 的空行隔离**：

| 正确 | 错误 |
|:-----|:-----|
| `前文段落。`<br><br>`$$`<br>`\mathbf{u} \cdot \mathbf{v} = 0`<br>`$$`<br><br>`后文段落。` | `前文段落。`<br>`$$`<br>`\mathbf{u} \cdot \mathbf{v} = 0`<br>`$$`<br>`后文段落。` |

- Opening `$$` **前必须有空行**，与上文段落隔离
- Closing `$$` **后建议空行**，使公式块与下文分离
- 禁止将 `$$` 直接放在段落末行末尾

**行内公式 `$...$` 的空格隔离**：

`$` 定界符与中文字符（含中文标点）之间**必须有空格**，否则 GitHub 可能无法识别公式边界：

| 正确 | 错误 |
|:-----|:-----|
| 向量 $W$ 的维度为 $d$ | 向量 $W$ 的维度为 $d$ |
| 其中 $\lambda$ 是正则化系数 | 其中 $\lambda$ 是正则化系数 |
| 即 $x \in \mathbb{R}^n$ ，满足 | 即 $x \in \mathbb{R}^n$，满足 |

**英文与 `$` 之间**：英文单词与 `$` 之间也需空格（`where $W$ is` ✅，`where$W$is` ❌），但英文标点（句号、逗号）与 `$` 之间不需要空格（`$W$ is invertible.` ✅）。

**`\|` 在 GitHub 行内公式中的限制**：`\|` 在部分 GitHub 渲染版本中会显示为两个竖线 `||` 而非双竖线符号。建议在行内公式中使用 `\Vert` 替代 `\|`（已在表格规则中覆盖）。

**验证方式**：生成每张卡片后，在 GitHub 仓库中预览确认公式渲染正常。重点关注：
- 表格中的行内公式是否渲染（最易失败）
- 含 `\text{}` 或 `\operatorname{}` 的行内公式
- 含 `\sum`、`\prod` 等大型运算符的块级公式，是否被错误截断

### Mermaid 图表格式限定

仅当需展示流程走向或状态转换时使用 mermaid。必须遵守：

| 要点 | 要求 |
|:----|:-----|
| **声明图类型** | 首行为 `flowchart LR/TD` 或 `sequenceDiagram` |
| **节点标识符** | 用 `A[文本]` 格式，字母标识符 + 方括号包裹显示文本 |
| **箭头** | 用 `-->` 连接，禁止 `→` Unicode 箭头 |
| **连线标注** | 用 `-->|说明|` 格式 |
| **禁止裸文本** | 所有文本都必须属于某个节点或连线 |

```mermaid
flowchart LR
    A[Agent] -->|动作| B[环境]
    B -->|反馈| A
```

### 面试问答（必选）

每张卡片**必须**在末尾附带 Q1→Q4 面试问答，由浅入深覆盖基础 → 深挖 → 实战 → 边界。

```markdown
## 面试追问

**Q1（基础）**：[核心概念的理解]
**回答要点**：

1. [第一得分点]
2. [第二得分点]

**Q2（深挖）**：[原理/优缺点/对比]
**回答要点**：[同上格式，省略 Q3/Q4]
```

**规则**：

- Q 行与 `**回答要点**` 之间 空行，要点后空一行再写编号列表，`**回答要点**` 之前也要有个空行
- **结构倒挂禁止**：主体内容（定义 + 原理 + 对比 + 应用场景）的字符数必须大于面试追问的字符数。面试追问的知识点应从主体中提炼而来，而非主体空白全靠 Q&A 填充。如果写完后发现 Q&A 比主体还长，说明主体内容不足，需要扩充原理/对比/机制部分。
- 回答要点**必须有实际内容**，不得使用泛泛占位语
