# 混合检索与重排序

## 混合检索（Hybrid Search）

单一检索方式各有局限：**稠密检索**擅长语义匹配但可能漏掉精确术语，**稀疏检索**（BM25）擅长精确匹配但缺乏语义泛化能力。混合检索将两者结合，取长补短。

```python
from pymilvus import WeightedRanker

# 混合检索：稠密向量(0.7) + 稀疏向量(0.3)
# 稠密检索擅长语义泛化（理解同义词、近义表达），稀疏检索擅长精确匹配（关键词、缩写）
# 两者加权融合可覆盖更广泛的查询需求，兼顾语义和关键词两方面
hybrid_results = collection.hybrid_search(

    reqs=[dense_req, sparse_req],             # 同时提交稠密和稀疏两种检索请求，各返回独立分数列表

    rerank=WeightedRanker(0.7, 0.3),          # 稠密占70%、稀疏占30%的加权融合，权重和为1.0

    limit=100                                 # 融合后取 Top-100 作为第一阶段候选结果
)
```

## 加权融合策略

| 策略 | 公式 | 特点 | 适用场景 |
|------|------|------|----------|
| **WeightedRanker**（加权融合） | $score = \alpha \cdot s_d + \beta \cdot s_s$ | 简单直接，权重可调 | 通用场景 |
| **RRF（互惠排名融合）** | $score = \sum \frac{1}{k + rank_i}$ | 对排序位置敏感，不需分数归一化 | 多个异构检索器 |
| **自适应融合** | 根据查询类型动态调整权重 | 灵活但复杂 | 高级生产系统 |

## 两阶段检索架构

```python
# 第一阶段：快速召回（牺牲精度换取速度，从大规模文档库中初步筛选）
第一阶段（检索）:
  用户查询 → 混合检索(稠密+稀疏) → 候选 Top-100
                     ↓
# 第二阶段：精细排序（牺牲速度换取精度，对少量候选做交互式注意力打分）
第二阶段（重排序）:
  候选 Top-100 → Reranker 模型(交叉编码) → 精细排序 → 最终 Top-10
                     ↓
#              LLM 基于重排序后的 Top-10 文档生成最终回答
               LLM 生成回答
```

**关键设计**：第一阶段用轻量级检索（快速召回），第二阶段用重量级 Reranker（精确排序）。这是平衡**性能**与**精度**的经典架构。

## BGE-Reranker 重排序

Reranker（重排序器）使用**交叉编码器**（Cross-Encoder）架构，将查询和文档对输入模型，输出更精确的相关性分数：

```python
from sentence_transformers import CrossEncoder

# 加载 BGE-Reranker 交叉编码器模型
# Cross-Encoder 架构让查询和文档在深层交互，比 Bi-Encoder 的独立编码精度更高
reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")

# 将查询与每个候选文档组成（查询，文档）对，供交叉编码器逐对计算相关性
pairs = [(query, doc1), (query, doc2), ...]

scores = reranker.predict(pairs)            # 返回每对（查询，文档）的相关性分数，值越大越相关

# 按相关性分数降序排列，最高分文档排在最前面，作为 LLM 最终的回答上下文
ranked = sorted(zip(docs, scores), key=lambda x: x[1], reverse=True)
```

| 对比 | 检索阶段（Bi-Encoder） | 重排序阶段（Cross-Encoder） |
|------|-----------------------|---------------------------|
| **架构** | 双塔编码器（互相独立） | 交叉编码器（交互注意力） |
| **速度** | 快（百万级可索引） | 慢（只能处理小规模候选） |
| **精度** | 中等 | 高 |
| **输入** | 查询和文档分别编码 | 查询+文档一起编码 |
| **典型延迟** | 毫秒级 | 百毫秒级（每对） |

> 两个阶段互补：Bi-Encoder 负责大规模粗筛，Cross-Encoder 负责小规模精排。

## 面试追问

**Q1（基础）**：为什么需要混合检索（Hybrid Search）？稠密检索和稀疏检索各自的局限性是什么？
**回答要点**：

1. 稠密检索擅长语义匹配（同义词、近义表达）但可能漏掉精确术语（如专业名词、缩写）。
2. 稀疏检索（BM25）擅长精确关键词匹配但缺乏语义泛化能力（无法理解"车"和"汽车"是同一个概念）。
3. 混合检索将两者结合：稠密向量覆盖语义相似，稀疏向量覆盖精确匹配，取长补短。

**Q2（深挖）**：WeightedRanker 加权融合、RRF 互惠排名融合和自适应融合三种策略各有什么特点？如何选择？
**回答要点**：

1. WeightedRanker：$score = \alpha \cdot s_d + \beta \cdot s_s$，简单直接权重可调，但需要分数归一化。
2. RRF：$score = \sum 1/(k + rank_i)$，对排序位置敏感，不需要分数归一化，适合异构检索器融合。
3. 自适应融合：根据查询类型动态调整权重，灵活但系统复杂度高。
4. 选型：通用场景用 WeightedRanker，检索器输出分数差异大用 RRF，有充足资源追求最优用自适应融合。

**Q3（实战）**：请描述两阶段检索架构（Bi-Encoder 粗筛 + Cross-Encoder 精排）的设计思路和为什么这样设计。
**回答要点**：

1. 第一阶段用 Bi-Encoder（双塔编码器）：查询和文档分别编码，通过向量相似度快速从百万级候选中召回 Top-100。
2. 第二阶段用 Cross-Encoder（交叉编码器）：查询+文档对一起输入模型做交互注意力计算，精确排序选出 Top-10。
3. 设计理由：Bi-Encoder 速度快但精度中等（可索引向量），Cross-Encoder 精度高但速度慢（不可索引），两者互补是经典的性能-精度平衡架构。

**Q4（边界）**：两阶段检索架构在什么场景下可能失效？如何改进？
**回答要点**：

1. Bi-Encoder 第一阶段的召回率不够高时，真实的 Top-K 文档在粗筛阶段就被过滤掉了，Cross-Encoder 无法挽回。
2. 改进方案：增大第一阶段召回数量（如从 100 增加到 500），同时优化 Bi-Encoder 的嵌入质量。
3. Cross-Encoder 的推理延迟在候选项较多时成为瓶颈，可用更小的 Reranker 模型或对候选项进行聚类抽样。
4. 新鲜度要求高的场景（新闻、实时数据）需要额外的时间衰减因子，避免旧文档分数过高。
