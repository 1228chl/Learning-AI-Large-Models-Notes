# HNSW 分层可导航小世界索引

## 定义

HNSW（Hierarchical Navigable Small World，分层可导航小世界）是当前向量数据库中最广泛使用的近似最近邻（ANN）搜索算法。它将百万级向量组织为**多层图结构**——顶层稀疏（快速定位目标区域）、底层稠密（精细搜索邻居）——使搜索复杂度从暴力遍历的 $O(N)$ 降至 $O(\log N)$，在保持 95% 以上召回率的同时实现 100-1000 倍加速。

HNSW 是对 NSW（Navigable Small World）图的改进：NSW 图利用"六度分隔"原理，每个节点连接若干近邻和一两条远程边，贪心搜索即可快速跳转到目标区域；但 NSW 的早期阶段（从随机入口出发）跳转缓慢，分层设计正是为了解决这一问题。

$$ \text{搜索性能：暴力 } O(N) \xrightarrow{\text{HNSW}} O(\log N)，\quad \text{召回率：} \geq 95\% $$

## 核心机制

### 分层结构

| 层 | 节点比例 | 连接密度 | 作用 | 搜索行为 |
|----|---------|---------|------|---------|
| 顶层（Layer 2+） | ~14% | 稀疏（$M$ 条边） | 洲际公路：快速跨区域跳跃 | 贪心搜索，只维护 1 个最近候选 |
| 中层（Layer 1） | ~37% | 中等（$M$ 条边） | 城市主干道：定位到小区 | 贪心搜索，只维护 1 个最近候选 |
| 底层（Layer 0） | **100%** | 稠密（$2M$ 条边） | 社区小巷：精细查找具体邻居 | 维护候选集 $C$ + 结果集 $W$（$\vert W \vert = ef$） |

节点能到达的层数由随机函数决定：`floor(-ln(uniform(0,1)) * mL)`，其中 $mL = 1/\ln(M)$。约 63% 的节点只存在于 Layer 0。

### 三参数调优

| 参数 | 默认值 | 作用 | 影响 |
|------|--------|------|------|
| $M$ | 16 | 每个节点最大出边数 | 越大→图越密→召回越高→内存越大 |
| $efConstruction$ | 256 | 建图时的候选池大小 | 越大→索引质量越高→建图越慢 |
| $ef$ | 64 | 搜索时的候选池大小 | 越大→搜索越准→速度越慢（必须 $\geq$ 返回数 $k$）|

经验法则：$ef$ 取 $2M \sim 4M$，$ef$ 越大搜索精度越高但延迟增加。

## 直观理解

> HNSW 像一套多比例尺地图：顶层是全国高速路网（几笔就跨越千里），中层是省市公路（定位到区县），底层是街巷详图（精确到门牌号）。查询一个向量时，先从顶层"粗定位"，逐层下降，到底层时只需在极小范围内精细搜索。

## Milvus 中使用 HNSW

```python
from pymilvus import Collection, FieldSchema, CollectionSchema, DataType

# 创建 Collection 时指定 HNSW 索引
index_params = {
    "metric_type": "COSINE",       # 文本语义用余弦，图像用 L2
    "index_type": "HNSW",          # 索引类型
    "params": {
        "M": 16,                   # 每个节点最大连接数
        "efConstruction": 256      # 建图时候选池大小
    }
}
collection.create_index(field_name="embedding", index_params=index_params)

# 搜索时指定 ef（查询精度/速度平衡）
search_params = {"metric_type": "COSINE", "params": {"ef": 64}}
results = collection.search(
    data=[query_vector], anns_field="embedding",
    param=search_params, limit=10  # ef=64 远大于 limit=10，保证精度
)
```

## AI/ML 工程应用场景

| 应用场景 | HNSW 参数选型 | 说明 |
|---------|-------------|------|
| RAG 知识库检索 | `metric_type="COSINE"`, $M=16$, $ef=64$ | 文本语义匹配，高召回优先 |
| 以图搜图 | `metric_type="L2"`, $M=32$, $ef=128$ | 图像空间距离，精度优先 |
| 推荐系统向量召回 | `metric_type="IP"`, $M=8$, $ef=32$ | 内积相似度，高吞吐优先 |
| 生物特征 1:N 识别 | `metric_type="L2"`, $M=64$, $ef=256$ | 千万级底库，极致精度 |

## 面试追问

**Q1（基础）**：HNSW 中的"分层"解决了什么问题？每层的作用是什么？

**回答要点**：

1. 分层解决 NSW 图"从随机入口跳转到目标区域太慢"的问题
2. 顶层（稀疏）：1% 节点，用于跨区域快速跳转，像高速公路
3. 中层：37% 节点，定位到目标小区
4. 底层（稠密）：100% 节点，精确查找 $k$ 个最近邻
5. 节点所在层数由指数衰减随机函数决定，~63% 节点仅存在于底层

**Q2（深挖）**：$M$、$efConstruction$、$ef$ 三个参数分别控制什么？增大 $ef$ 的代价是什么？

**回答要点**：

1. $M$：控制图密度（每节点最大连接数）——越大越密，内存越大
2. $efConstruction$：建图时的候选池——影响索引构建质量与时间，不影响查询速度
3. $ef$：搜索时维护的动态候选池——越大精度越高但延迟增加，必须 $\geq$ 返回数量 $k$
4. 增大 $ef$ 的代价：每次查询的候选池更大，贪心搜索计算的候选去重与排序开销增加
5. 经验值：$ef$ 取 $2M \sim 4M$，召回率与速度的平衡点

**Q3（实战）**：RAG 系统中 $M$ 设为 16、$ef$ 设为 64 的依据是什么？如果知识库从 10 万条扩展到 1000 万条怎么调？

**回答要点**：

1. $M=16$ 是 HNSW 论文推荐的平衡值——在召回率和内存之间取得最佳折中
2. $ef=64$ 远大于典型 RAG 返回数（top-5~10），确保重排序前不遗漏相关文档
3. 千万级扩展：$M$ 可升至 32（更密的图在大数据量下避免局部最优），$ef$ 升至 128-256
4. $efConstruction$ 从 256 升至 512——建图虽慢但只建一次

**Q4（边界）**：HNSW 与 IVF（倒排索引）的核心差异是什么？什么场景必须用 HNSW 而非 IVF？

**回答要点**：

1. IVF：先聚类找粗中心 → 搜最近的中心 → 中心内的向量暴力比对。内存低，但召回受聚类质量影响
2. HNSW：图结构贪心搜索 → 召回更高更稳定，但内存更大（需存储所有边）
3. 必须用 HNSW：高召回率要求（>95%）、查询延迟敏感（<10ms）、数据分布不均匀导致聚类不稳定
4. 可用 IVF：内存受限、百万级以上但可接受 90% 召回、离线批量检索
