# SQL 基础与数据库设计

## 数据库分类

| 类型 | 存储方式 | 特点 | 代表产品 |
|------|----------|------|----------|
| **关系型（SQL）** | 行列表格（二维表），通过 SQL 操作 | 数据一致性强，支持复杂查询和事务 | MySQL、PostgreSQL、Oracle |
| **非关系型（NoSQL）** | 键值/文档/列式/图 | 灵活、高扩展性、大数据量下性能好 | Redis（键值）、MongoDB（文档） |

## SQL 分类

| 分类 | 全称 | 作用 | 关键字 |
|------|------|------|--------|
| **DDL** | Data Definition Language | 定义数据库、表、列的结构 | `CREATE`、`DROP`、`ALTER` |
| **DML** | Data Manipulation Language | 操作表中的记录（增、删、改） | `INSERT`、`DELETE`、`UPDATE` |
| **DQL** | Data Query Language | 查询表中的记录（最核心） | `SELECT`、`FROM`、`WHERE` |
| **DCL** | Data Control Language | 管理权限和安全 | `GRANT`、`REVOKE` |

## 数据库设计范式

| 范式 | 规则 | 通俗理解 |
|------|------|----------|
| **1NF（第一范式）** | 每列不可再分 | 字段是原子值，不存列表 |
| **2NF（第二范式）** | 满足 1NF，且非主键列完全依赖主键 | 每列描述的是"这一个"实体 |
| **3NF（第三范式）** | 满足 2NF，且非主键列不传递依赖主键 | 每列只描述自身，不描述其他列 |

**反范式化**：在实际 ML 项目中，为了查询性能有时会刻意冗余数据（如将标签名直接存在行为表中，避免每次 JOIN）。

## ML 工程师的 SQL 场景

| 场景 | SQL 操作 | 说明 |
|------|----------|------|
| **数据探索** | `SELECT ... WHERE ... GROUP BY ... ORDER BY` | 快速了解数据集分布、统计信息 |
| **特征工程** | `JOIN` 多表、`CASE WHEN` 分箱、聚合统计 | 从原始表组合出特征宽表 |
| **数据清洗** | `DISTINCT` 去重、`COALESCE` 填充空值、`WHERE` 过滤异常 | 清洗脏数据 |
| **训练数据导出** | `SELECT ... INTO OUTFILE` 或 Python 读取 | 导出 CSV 供模型训练 |


## 面试追问

**Q1（基础）**：关系型数据库和非关系型数据库（NoSQL）的核心区别是什么？各适用于什么场景？
**回答要点**：① 关系型用行列表格+SQL，强调数据一致性和复杂查询；NoSQL用键值/文档/列式/图，强调灵活性和扩展性。② 关系型适合事务处理和精确查询；NoSQL适合缓存、大数据量、灵活Schema。

**Q2（深挖）**：第三范式和反范式化分别适用于什么场景？在ML项目中为什么有时需要反范式化？
**回答要点**：① 第三范式要求非主键列不传递依赖主键，减少数据冗余；反范式化故意引入冗余以提升查询性能。② ML特征工程中频繁使用JOIN组合多表为宽表，反范式化将标签名直接存在行为表，避免每次JOIN带来的性能开销。③ 核心权衡：存储冗余 vs 查询速度。

**Q3（实战）**：在ML数据探索和特征工程中，你最常用的SQL操作有哪些？请举例说明。
**回答要点**：① 数据探索用SELECT...WHERE...GROUP BY...ORDER BY查看数据分布和统计信息。② 特征工程用JOIN多表、CASE WHEN分箱、聚合函数（COUNT/AVG/SUM）构建特征宽表。③ 数据清洗用DISTINCT去重、COALESCE填充空值、WHERE过滤异常值。

**Q4（边界）**：在什么场景下关系型数据库不再适用？此时你会选择什么替代方案？
**回答要点**：① 海量高并发读写场景下关系型数据库成为瓶颈，如图片/视频元数据、用户行为日志。② 非结构化数据语义检索（如文本相似度搜索）无法用SQL精确匹配。③ 替代方案：Redis做缓存/计数器，向量数据库做语义检索，MongoDB做文档存储，HBase做列式存储。
