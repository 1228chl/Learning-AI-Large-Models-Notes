# 向量数据库概述

## 定义

向量数据库（Vector Database）是一种专门用于存储、索引和检索**高维向量**的数据库系统。它将数据（文本、图像、音频等）通过嵌入模型转换为向量，然后提供高效的**相似度搜索**能力——即找出与查询向量最相似的 Top-K 个向量。

## 关系型数据库 vs 向量数据库

| 对比维度 | 关系型数据库（MySQL） | 向量数据库（Milvus） |
|----------|---------------------|---------------------|
| **数据模型** | 行列表格（结构化） | 向量 + 标量字段 |
| **查询方式** | SQL 精确匹配、范围查询 | ANN（近似最近邻）搜索 |
| **索引** | B+ 树、哈希索引 | IVF、HNSW、磁盘索引 |
| **排序依据** | 数值大小、字典序 | 向量距离/相似度 |
| **适用场景** | 事务处理、精确查询 | 语义搜索、相似度匹配 |
| **典型延迟** | 毫秒级 | 毫秒级（百万级数据） |

## 主流向量数据库对比

| 产品 | 类型 | 特点 | 适用场景 |
|------|------|------|----------|
| **Milvus** | 分布式向量数据库 | 云原生、水平扩展、丰富索引类型 | 生产级 RAG、大规模检索 |
| **FAISS** | 向量检索库（非数据库） | Meta 开源，纯 Python/C++ 库 | 本地/离线检索、原型验证 |
| **Chroma** | 轻量级向量数据库 | 易上手、Python 原生、无需部署 | 小规模项目、学习原型 |
| **Pinecone** | 托管云服务 | 免运维、开箱即用、收费 | 快速上线的商业项目 |
| **Qdrant** | 向量数据库（Rust 实现） | 高性能、支持过滤、WAL 持久化 | 生产级替代方案 |

## 核心流程

```python
# ============================================================
# 向量数据库的完整工作流程 — 构成 RAG 系统的三条流水线
# ============================================================

# -------------------------------------------------------
# 阶段一：索引阶段（Indexing Pipeline）
# 将原始文档加工成向量存入数据库，为后续检索做准备。
# 为什么需要此阶段？
#   LLM 无法直接读取原始文档，必须先将文档中的语义
#   转化为高维向量表示，才能被向量数据库高效检索。
# -------------------------------------------------------
# 文档 → 分块（Chunk，控制块大小以避免超出 LLM 上下文窗口）
#     → 调用嵌入模型将语义转化为数值向量
#     → 存入向量数据库并建立索引（IVF / HNSW 等），
#       加速后续的近似最近邻搜索

# -------------------------------------------------------
# 阶段二：检索阶段（Retrieval Pipeline）
# 根据用户查询从向量库中召回最相关的文档片段。
# 为什么需要此阶段？
#   仅靠 LLM 自身的参数化知识无法覆盖最新或私域信息，
#   必须从外部知识库中动态检索上下文作为回答依据。
# -------------------------------------------------------
# 用户查询 → 使用与索引阶段相同的嵌入模型生成查询向量
#     → 向量数据库执行 ANN（近似最近邻）相似度搜索
#     → 按向量距离（余弦相似度 / 内积 / 欧氏距离）排序
#     → 返回 Top-K 个最相关的文档块及相似度分数

# -------------------------------------------------------
# 阶段三：生成阶段（Generation Pipeline）
# 将检索结果与用户问题合并，交给 LLM 生成最终答案。
# 为什么需要此阶段？
#   检索到的文档块只是原始素材，还需要 LLM 理解、
#   归纳并组织成通顺的自然语言回答，同时标注引用来源。
# -------------------------------------------------------
# 用户原始查询 + 检索到的 Top-K 文档块
#     → 按提示词模板拼接成完整的 Prompt
#     → 输入大语言模型，由模型基于上下文生成回答
#     → 最终输出带有知识来源引用的答案
```

## 与 Redis 的定位区别

| 维度         | Redis       | 向量数据库（Milvus）        |
| ---------- | ----------- | -------------------- |
| 核心能力       | 内存键值缓存      | 高效的向量相似度搜索           |
| 数据规模       | GB 级（受内存限制） | 百亿级（分布式）             |
| 索引方式       | 哈希表         | IVF / HNSW / DiskANN |
| 检索类型       | 精确键查找       | 近似最近邻（ANN）           |
| 在 RAG 中的角色 | BM25 结果缓存   | 语义向量存储与检索            |

## 面试追问

**Q1（基础）**：什么是向量数据库？它和传统关系型数据库（如 MySQL）的核心区别是什么？
**回答要点**：

1. 向量数据库专门用于存储和检索高维向量，通过 ANN 近似最近邻搜索找出语义最相似的 Top-K 个向量。
2. MySQL 用 SQL 精确匹配和范围查询，排序依据是数值大小；向量数据库按向量距离（余弦/欧氏/内积）排序。
3. 向量数据库的索引（IVF/HNSW）针对高维向量设计，不同于 MySQL 的 B+树索引。

**Q2（深挖）**：Milvus、FAISS 和 Chroma 三者的定位和适用场景有何不同？如何选型？
**回答要点**：

1. Milvus 是分布式向量数据库，支持水平扩展、丰富索引类型和云原生部署，适合生产级 RAG 和大规模检索。
2. FAISS 是 Meta 开源的向量检索纯 Python/C++库，非独立数据库，适合本地/离线检索和原型验证。
3. Chroma 是轻量级嵌入式向量数据库，易上手无需部署，适合小规模项目和学习原型。
4. 选型：生产环境用 Milvus，快速原型用 Chroma，定制化算法研究用 FAISS。

**Q3（实战）**：请描述 RAG 系统中向量数据库的完整工作流程（索引阶段→检索阶段→生成阶段）。
**回答要点**：

1. 索引阶段：原始文档→文本分块（Chunk）→嵌入模型生成向量→存入向量数据库。
2. 检索阶段：用户查询→同一嵌入模型生成查询向量→向量数据库相似度搜索→返回 Top-K 相关文档块。
3. 生成阶段：用户原始查询+检索到的相关文档块→拼接到 Prompt→输入 LLM 生成带引用的回答。
4. 关键设计：分块策略直接影响检索质量，向量维度与嵌入模型需匹配。

**Q4（边界）**：哪些类型的查询不适合用向量数据库处理？分别在什么场景下应回归传统数据库？
**回答要点**：

1. 精确匹配查询（如用户 ID=1001 查找用户名）用 Hash 索引毫秒级返回，向量数据库反而慢。
2. 范围查询、数值比较和事务操作（如年龄>18、转账）是关系型数据库的强项。
3. 结构化数据的分组聚合统计（SUM、AVG、GROUP BY）不支持。
4. 最佳实践：向量数据库做语义检索层，关系型数据库做精确数据存储，两者互补而非替代。
