# 多租户隔离三层设计

## 定义

多租户隔离是在同一套 AI Agent 系统中为多个独立租户（校区、企业、团队）提供**数据不可见、资源不冲突、记忆不串扰**的安全保障。EduAgent 采用三层隔离架构：数据库层（`tenant_id` 过滤所有 SQL 查询）、向量数据库层（Milvus 分区键 `partition_key` 物理隔离）、LangGraph 记忆层（`thread_id` 前缀绑定租户）。

核心设计原则：**每一层都必须独立过滤，绝不依赖上游传递的"信任"**——API 层从 JWT 解析出 tenant_id 后，后续每一层都自行验证并过滤。

$$ \text{请求} \to \underbrace{\text{JWT} \to \text{tenant\_id}}_{\text{入口鉴权}} \to \begin{cases} \text{SQL: WHERE tenant\_id = :tid} \\ \text{Milvus: partition\_key = tid} \\ \text{LangGraph: thread\_id = tid:xxx} \end{cases} $$

## 三层隔离架构

| 层 | 隔离机制 | 关键实现 | 若缺失则 |
|----|---------|---------|---------|
| 数据库层（PostgreSQL） | 每张业务表含 `tenant_id` 列，所有查询强制 `WHERE tenant_id = :tid` | `get_current_user` 从 JWT 提取 `tid` → 通过请求上下文注入 | 租户 A 能看到租户 B 的用户数据和试卷成绩 |
| 向量库层（Milvus） | Collection 创建时指定 `partition_key`，插入和搜索时按 tenant 分区 | `partition_name = tenant_id`，搜索只在指定分区内进行 | 租户 A 的知识库文档被检索给租户 B |
| 记忆层（LangGraph） | `thread_id` 格式为 `{tenant_id}:{业务_id}`，MemorySaver 的 checkpoint 按 thread_id 索引 | `config={"configurable": {"thread_id": f"{tid}:{sid}"}}` | 租户 A 的多轮对话历史在租户 B 的会话中继续 |

## 直观理解

> 一栋公寓楼——数据库层是每个房间的门锁（`WHERE tenant_id = :tid`，你只能进自己的房间），向量库层是每个楼层的分区门禁（Milvus partition，你只能在授权楼层活动），记忆层是房间内的私人日记（thread_id 前缀，你的日记只有你能读）。三道防线各自独立工作——即使门锁坏了，门禁和日记仍然保护着你的隐私。住户之间共享的是电梯和走廊（基础设施），不是房间里的东西。

## 数据库层隔离

```python
# 从 JWT 提取 tenant_id，注入到所有 SQL 查询
async def get_current_user(
    authorization: str = Header(...),
    db: AsyncSession = Depends(get_db)
):
    token = authorization.replace("Bearer ", "")
    payload = jwt.decode(token, SECRET_KEY, algorithms=["HS256"])
    tenant_id = payload["tenant_id"]           # JWT 中携带租户标识
    user_id   = payload["sub"]

    # 验证用户确实属于该租户（防止伪造）
    result = await db.execute(
        text("SELECT * FROM users WHERE id = :uid AND tenant_id = :tid"),
        {"uid": user_id, "tid": tenant_id}
    )
    if not result.fetchone():
        raise HTTPException(401, "用户不属于该租户")

    return {"user_id": user_id, "tenant_id": tenant_id}

# 后续所有业务查询都带 tenant_id 过滤
# 示例：查试卷记录
async def get_exam_records(tenant_id: str, user_id: str):
    result = await db.execute(
        text("SELECT * FROM exam_reviews WHERE tenant_id = :tid AND user_id = :uid"),
        {"tid": tenant_id, "uid": user_id}
    )
```

## LangGraph 记忆层隔离

```python
# thread_id 格式：{tenant_id}:{session_id} —— 前缀绑定租户
config = {
    "configurable": {
        "thread_id": f"{tenant_id}:qa_session_{session_id}"
    }
}

# 即使两个不同租户使用完全相同的 session_id，
# thread_id 前缀不同 → MemorySaver 中的 checkpoint 完全隔离
await graph.ainvoke(initial_state, config=config)
```

## AI/ML 工程应用场景

| 应用场景 | 关键隔离层 | 特殊考虑 |
|---------|----------|---------|
| 多校区 SaaS 教育平台 | 三层全部 | 每个校区的学员、试卷、知识库、面试记录完全隔离 |
| 企业级 RAG 知识库 | Milvus 分区 + DB tenant_id | 不同部门的知识库文档互不可见，但共享相同的检索基础设施 |
| 多客户 AI 客服 | DB tenant_id + thread_id | 每个客户的对话历史独立，FAQ 知识库可能在租户间共享 |
| B2B 简历筛选平台 | DB tenant_id | 不同企业的简历库、评分标准、审查记录完全隔离 |

## 面试追问

**Q1（基础）**：多租户隔离的三个层次分别是什么？各自用什么机制实现？

**回答要点**：

1. 数据库层：`tenant_id` 列 + `WHERE tenant_id = :tid` 强制过滤所有 SQL 查询
2. 向量库层：Milvus `partition_key` 物理分区隔离，搜索只在指定分区内
3. 记忆层：`thread_id` 前缀 `{tenant_id}:{业务_id}`，MemorySaver 按 thread_id 索引
4. 三层独立工作——某一层失效不会自动影响其他层，但任何一层缺失都是数据泄露风险

**Q2（深挖）**：为什么每一层都要独立隔离，而不是只在 API 入口做一次 tenant_id 校验？

**回答要点**：

1. 只校验入口是"单点信任"——API 层校验通过后，如果后续层有 bug（忘写 WHERE 条件），数据就泄露了
2. 纵深防御原则：每一层都假设上一层可能失效，自己再做一次过滤
3. 实际案例：developer 写了个内部调试接口没有走 API 入口校验——直接查库时依然有 `WHERE tenant_id` 保护
4. 绕过 API 层的场景：数据库直接查询、定时任务、数据迁移脚本——都需要 tenant 过滤

**Q3（实战）**：如果业务需要"租户 A 和租户 B 共享某个知识库"，三层隔离怎么调整？

**回答要点**：

1. 数据库层：创建 `shared_resources` 表记录共享关系，查询时 `WHERE tenant_id = :tid OR resource_id IN (shared)`
2. Milvus 层：共享知识库用独立 `partition`（如 `shared_medical_kb`），多租户搜索时搜索 `[own_partition, shared_partition]`
3. 记忆层：无需调整——记忆始终是租户私有的（共享的是知识库，不是对话历史）
4. 审计日志必须记录：哪个租户访问了哪个共享资源——满足合规要求

**Q4（边界）**：租户 A 上传了一个恶意文档（大文件、病毒、对抗性 Prompt 注入），会影响到租户 B 吗？

**回答要点**：

1. 不会直接影响——三层隔离确保租户 B 看不到租户 A 的数据
2. 但共享基础设施层的资源耗尽风险：恶意超大文件可能占满 MinIO 磁盘或拖慢 Milvus
3. 防护：文件大小限制（UploadFile size check）、处理超时（asyncio.wait_for）、每个租户的独立速率限制（rate limiting）
4. 对抗性 Prompt 注入：知识库文档中嵌入"忽略之前指令"文本——这是在生成阶段攻击 LLM，需在 Prompt 层防御（明确指令优先级、输入净化）
