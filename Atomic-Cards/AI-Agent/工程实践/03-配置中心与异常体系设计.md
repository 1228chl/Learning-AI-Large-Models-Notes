# 配置中心与异常体系设计

## 定义

EduAgent 的公共核心模块包含三件套：**配置中心（config.py）**、**结构化日志（logger.py）**、**统一异常体系（exceptions.py）**。它们构成所有 Agent 共享的"系统底座"，解决配置分散、日志混乱、异常处理不统一的问题。

### 配置中心：`@lru_cache` 单例模式

```python
from pydantic_settings import BaseSettings
from functools import lru_cache

class Settings(BaseSettings):
    db_host: str = "localhost"
    db_port: int = 5433
    db_user: str
    db_password: str                     # 无默认值 => 必填项
    deepseek_api_key: str                # 三个必填之一
    jwt_secret_key: str                  # 三个必填之一

    @property
    def database_url(self) -> str:
        return f"postgresql+asyncpg://{self.db_user}:{self.db_password}@{self.db_host}:{self.db_port}/eduagent"

    class Config:
        env_file = ".env.local"
        extra = "ignore"                 # .env.local 多出的字段自动忽略

@lru_cache()                             # 全局单例：只读一次文件
def get_settings() -> Settings:
    return Settings()
```

**关键设计**：

- `@lru_cache()`：保证全局单例，整个进程生命周期只创建一次 Settings 实例、只读一次 `.env.local` 文件
- `@property`：动态拼接 `database_url`，避免在 `.env.local` 中存一长串 URL
- 无默认值的字段自动成为必填项，启动时若缺失直接报错
- `extra = "ignore"`：`.env.local` 中多出的字段自动忽略，不报错

### 结构化日志

```python
logger.info("Agent 开始执行", agent_type="resume", review_id=review_id)
logger.info("六维度评分完成", scores=dimension_scores, total=weighted_score)
```

**设计要点**：

- 支持 `logger.info("事件", key=value)` 的键值对写法，自动附加到日志记录
- 必须压制第三方库日志噪音：`sqlalchemy` / `httpx` / `httpcore` 等提到 WARNING 级别
- 每个日志记录包含 `agent_type` 字段，便于按 Agent 筛选和排查问题

### 统一异常体系

```
EduAgentBaseError（基类，含 agent_type 和 details）
├── LLMAPIError             可重试  ← 大模型 API 调用失败
├── MilvusConnectionError   可重试  ← Milvus 连接失败
├── AgentExecutionError     视情况  ← Agent 业务逻辑执行失败
├── FileParseError          不可重试 ← 文件解析失败
├── InvalidInputError       不可重试 ← 用户输入不合法
└── AuthenticationError     不可重试 ← 认证失败
```

```python
class EduAgentBaseError(Exception):
    def __init__(self, message, agent_type="unknown", details=None):
        self.agent_type = agent_type
        self.details = details or {}
        super().__init__(message)

class LLMAPIError(EduAgentBaseError): pass      # 可重试
class MilvusConnectionError(EduAgentBaseError): pass  # 可重试
class InvalidInputError(EduAgentBaseError): pass  # 不可重试
```

**可重试 vs 不可重试规则**：

| 异常类 | 是否可重试 | 原因 |
|--------|-----------|------|
| `LLMAPIError` | 是 | 网络抖动/API 限流，重试通常能恢复 |
| `MilvusConnectionError` | 是 | 向量库连接闪断，重试可恢复 |
| `AgentExecutionError` | 视情况 | 业务逻辑错误，需具体分析 |
| `FileParseError` | 否 | 文件格式错误，重试 100 次也一样 |
| `InvalidInputError` | 否 | 用户输入不合法，重试无意义 |
| `AuthenticationError` | 否 | 认证凭证无效，重试不会变有效 |

### 直观理解

> 配置中心好比"总配电箱"——所有电源（配置）从这里统一引出，改一处全系统生效。结构化日志好比"黑匣子"——每个事件记录谁（agent_type）在哪（模块）干了什么（事件名）。异常体系好比"消防预案"——哪类火灾（异常）可以自己扑灭（重试），哪类必须等消防员（人工介入）。

## 应用场景

| 模块 | 异常捕获 | 处理方式 |
|------|---------|---------|
| 简历审查 Agent | `LLMAPIError` | 自动重试 2 次，仍失败降级为 50 分默认值 |
| 智能问答 Agent | `MilvusConnectionError` | 自动重试，失败降级为 LLM 直接回答 |
| 试卷批改 Agent | `FileParseError` | 不重试，直接返回"文件格式不支持" |
| 统一入口 | `AgentExecutionError` | 最外层 `try/except` 兜底，返回友好提示 |

## 面试追问

**Q1（基础）**：EduAgent 中 `@lru_cache()` 在配置中心的作用是什么？
**回答要点**：

1. 保证 `get_settings()` 全局只执行一次，后续调用直接返回缓存结果
2. 避免每次调用都重新读取 `.env.local` 文件
3. 配置在整个进程生命周期内不变，缓存是安全的

**Q2（深挖）**：为什么异常体系要区分可重试和不可重试？判断标准是什么？
**回答要点**：

1. 可重试异常通常是**临时性故障**（网络抖动、服务重启、连接超时），重试后大概率恢复
2. 不可重试异常是**确定性错误**（文件格式错误、用户输入不合法、认证凭证无效），重试 100 次结果一样
3. 判断标准：`@with_retry` 装饰器据此决定是否重试，避免对不可重试异常浪费资源
4. 设计原则：重试只解决"暂时出错"的问题，不解决"一直错"的问题

**Q3（实战）**：你在项目中如何设计统一异常体系？请给出一个具体的类层次结构。
**回答要点**：

1. 定义基类 `AppBaseError(Exception)`，包含 `module`（模块名）和 `details`（调试信息字典）
2. 按来源分三类：`ExternalServiceError`（外部服务，可重试）、`BusinessLogicError`（业务逻辑，视情况）、`ValidationError`（输入校验，不可重试）
3. 按业务继续细分：`ExternalServiceError` → `LLMTimeoutError` / `DatabaseConnectionError`
4. 装饰器 `@with_retry` 根据异常类型决定重试次数（可重试 3 次，不可重试 0 次）

**Q4（边界）**：`@lru_cache()` 单例配置在什么情况下会成为问题？如何解决？
**回答要点**：

1. 多租户场景：不同租户需要不同配置（如不同的数据库），单例配置无法满足
2. 热更新场景：配置中心修改后需要在不重启服务的情况下生效，lru_cache 做不到
3. 测试场景：单例导致测试间状态污染，一个测试改了配置影响后续测试
4. 解决方案：多租户用 `@lru_cache(maxsize=10)` 按 tenant_id 缓存；热更新用监听文件变化+清除缓存；测试用 `get_settings.cache_clear()` 清除缓存
