# 文档切分策略

## 定义

文档切分（Chunking / Text Splitting）是将长文档切割为适合 LLM 上下文窗口和检索粒度的**小文本块**。切分质量直接决定了 RAG 系统的检索效果。

```python
from langchain.text_splitter import (
    RecursiveCharacterTextSplitter,
    CharacterTextSplitter,
    TokenTextSplitter,
)
```

## 常见切分策略

| 策略 | 切分方式 | 特点 | 适用场景 |
|:----:|:---------|:----|:---------|
| **固定大小** | 按字符数硬切（带重叠） | 简单快速 | 通用基线 |
| **递归字符** | 按 `\n\n` → `\n` → 空格 逐级切 | **最常用**，语义完整性好 | 通用文档 |
| **语义切分** | 利用 Embedding 检测语义边界 | 边界准确但慢 | 高质量需求 |
| **Markdown/HTML** | 按标题/标签结构切 | 保留格式 | 网页、Markdown |
| **按 token** | 按 token 数而非字符数切 | 精确控制 LLM 上下文 | 优化成本 |
| **父子块** | 父块（大段）+ 子块（细粒度） | 检索子块，返回父块 | 需要上下文保留 |

## 递归字符切分（推荐）

```python
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,          # 每块最大字符数
    chunk_overlap=50,        # 块间重叠字符数
    separators=["\n\n", "\n", "。", ".", " ", ""],
)

chunks = text_splitter.split_documents(documents)
```

## 父子块策略（Parent-Child Chunking）

```
父块 1 (1000 tokens): 一整个段落
    ├── 子块 1.1 (200 tokens): 段落的前半段
    └── 子块 1.2 (200 tokens): 段落的后半段

检索时：将用户查询与子块匹配
返回时：用匹配到的子块找到对应的父块，将父块作为 LLM 上下文
```

**优势**：检索细粒度（匹配准确），上下文丰富（LLM 获得完整段落）。

## 切分参数选择

| 参数 | 说明 | 推荐值 |
|:----|:----|:------:|
| `chunk_size` | 每个文本块的大小 | 256-1024（字符）|
| `chunk_overlap` | 块间重叠大小 | 10-20% 的 chunk_size |
| `separators` | 切分优先级 | `\n\n` > `\n` > `。` > 空格 |

```python
# 不同文档类型的切分建议
strategies = {
    "代码": TokenTextSplitter(chunk_size=1000),       # 按 token 切
    "Markdown": MarkdownHeaderTextSplitter(),          # 按标题切
    "长文": RecursiveCharacterTextSplitter(1000, 200),  # 带重叠
    "FAQ": CharacterTextSplitter(separator="\n\n"),    # 逐条切分
}
```

## ML 中的文档切分

| 应用场景 | 推荐策略 | 原因 |
|:--------:|:--------|:----|
| **通用文档问答** | 递归字符切分（500-1000 字符） | 语义完整性和灵活性平衡 |
| **学术论文** | 按段落 + 语义切分 | 每个段落一个完整论点 |
| **代码库问答** | Token 切分 + 文件粒度 | 代码函数完整性 |
| **对话日志** | 按轮次切分 | 保持对话上下文 |
| **网页抓取** | HTML 标题结构切分 | 利用 DOM 树的天然结构 |

## 面试追问

**Q1（基础）**：为什么 RAG 系统中必须对文档进行切分？chunk_size 和 chunk_overlap 这两个参数各自的作用是什么？
回答要点：LLM 上下文窗口有限且检索粒度需要匹配问答粒度，整篇文档无法直接处理；chunk_size 控制每块最大字符数决定检索精度与上下文丰富度的平衡；chunk_overlap 控制块间重叠字符数，避免关键信息在切分边界丢失。

**Q2（深挖）**：递归字符切分器（RecursiveCharacterTextSplitter）的工作原理是什么？为什么它是最常用的方案？
回答要点：按分隔符优先级从高到低逐级尝试切分（`\n\n`→`\n`→`。`→空格→字符）；优先保留语义完整性较高的自然边界；相比固定大小切分语义更完整，相比语义切分速度快、实现简单，是效果和效率的最佳平衡点。

**Q3（实战）**：在同一个 RAG 系统中需要处理代码、Markdown 和学术论文三种文档，你会如何设计切分方案？
回答要点：不同类型分别处理——代码用 TokenTextSplitter 保证函数完整性，Markdown 用 MarkdownHeaderTextSplitter 按标题结构切，学术论文用递归字符切分（500-1000字符带重叠）；统一采用父子块策略——子块细粒度匹配检索，返回父块保障上下文完整性。

**Q4（边界）**：chunk_overlap 设得过大或过小分别会有什么后果？chunk_size 应该如何根据文档类型调整？
回答要点：chunk_overlap 过小（接近 0）容易在切分边界丢失关键信息导致召回下降；chunk_overlap 过大（>30%）导致大量冗余存储和检索噪声增加；chunk_size 应适配文档语义粒度——FAQ 用大块（1000+），对话日志用小块（200+）按轮次切，通用文档 500-1000 为宜。
