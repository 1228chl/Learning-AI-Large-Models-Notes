# Prompt 工程进阶

## 定义

Prompt Engineering（提示词工程）是**通过设计输入提示词来引导大语言模型输出期望结果**的技术。进阶方法超越了简单指令，利用模型的 **In-Context Learning** 能力和推理能力完成复杂任务。

## In-Context Learning（上下文学习）

零样本提示（Zero-shot）：直接用指令描述任务，不提供示例。

$$
\text{Answer} = \text{LLM}(\text{Instruction}, \text{Query})
$$

少样本提示（Few-shot）：在 prompt 中包含少量输入-输出示例，让模型从示例中推断模式：

$$
\text{Answer} = \text{LLM}(\text{Example}_1, \dots, \text{Example}_k, \text{Query})
$$

示例选择和排序直接影响效果：
- **语义相似性**：选择与测试样本最相似的示例（基于嵌入检索）
- **标签平衡**：各类别的示例数量均衡
- **顺序效应**：模型对靠后的示例更敏感（近因效应）

## 思维链（Chain-of-Thought, CoT）

引导模型在给出最终答案前展示中间推理步骤：

| CoT 类型 | 方法 | 适用场景 |
|:---------|:-----|:---------|
| **Zero-shot CoT** | 在 prompt 末尾加"让我们一步步思考" | 通用推理任务 |
| **Few-shot CoT** | 提供带推理步骤的示例 | 数学/逻辑推理 |
| **Auto-CoT** | 自动生成推理步骤示例 | 减少人工标注成本 |
| **Self-Consistency** | 多次采样 CoT 路径，多数投票 | 提高推理稳定性 |

```python
# Zero-shot CoT：最简单有效的推理增强方法
prompt = """问题: 一个商店买了 20 个苹果，卖出 8 个，又买了 15 个。
现在店里有多少个苹果？
让我们一步步思考。"""

# Few-shot CoT：提供带推理过程的示例
prompt_icl = """问题: 小明有 5 元钱，妈妈给他 10 元，他花了 3 元买笔，还剩多少？
推理: 小明原本有 5 元。妈妈给了他 10 元，所以他有 5+10=15 元。
他花了 3 元买笔，所以剩下 15-3=12 元。答案是 12。

问题: 一个商店买了 30 个西瓜，卖了 12 个，又进了 8 个。
现在有多少个西瓜？
推理:"""
```

## ReAct（推理 + 行动）

ReAct（Reasoning + Acting）让模型**交替进行推理和行动**，通过调用外部工具获取信息来辅助推理：

```
思考: 我需要知道2024年巴黎奥运会的中国金牌数量
行动: 搜索[2024巴黎奥运会 中国 金牌]
观察: 中国在2024年巴黎奥运会上获得15枚金牌
思考: 现在我需要知道中国银牌数量
行动: 搜索[2024巴黎奥运会 中国 银牌]
观察: 中国获得12枚银牌
思考: 金银牌总数为15+12=27枚
最终答案: 27枚
```

ReAct 的关键设计模式：

```
循环: Thought → Action → Observation → Thought → ... → Answer
```

## Tree of Thought（思维树 ToT）

ToT 将推理过程视为**树的搜索**，在每一步生成多个可能的推理分支，用搜索算法（BFS/DFS）探索，并用评估函数剪枝：

```
问题 → 推理思路1 → 子思路1A → 子思路1A1 → ✅
                ↘ 子思路1B → 子思路1B1 → ❌ 剪枝
      ↘ 推理思路2 → 子思路2A → 子思路2A1 → ✅ 最优路径
```

- Deep Exploration：先搜到最深再回溯（DFS）
- Breadth Exploration：每层保留 Top-K 个最优节点（BFS）

## 提示词设计原则

| 原则 | 说明 | 示例 |
|:-----|:------|:------|
| **明确角色** | 给模型一个明确的身份 | "你是一个资深 Python 工程师" |
| **分步指令** | 将任务拆解为清晰步骤 | "第一步：... 第二步：..." |
| **输出格式控制** | 明确指定输出格式 | "以 JSON 格式输出：`{'result': ...}`" |
| **限定范围** | 限制模型的想象空间 | "只基于以下上下文回答，不要编造" |
| **Negative Prompt** | 告诉模型不要做什么 | "不要解释，只输出答案" |
| **分隔符清晰** | 用明确标记分隔输入的不同部分 | "上下文：... 问题：..." |

## 进阶技巧对比

| 技巧 | 推理能力提升 | 计算成本增加 | 实现复杂度 |
|:-----|:-----------:|:-----------:|:---------:|
| Zero-shot CoT | 中 | 低（延长输出） | 极低 |
| Few-shot CoT | 高 | 中（增加输入） | 中 |
| Self-Consistency | 很高 | 高（N 次采样） | 低 |
| ReAct | 很高 | 中（多轮交互） | 中 |
| ToT | 极高 | 很高（树搜索） | 高 |

## ML/DL 应用场景

| 应用场景 | 使用的技巧 | 说明 |
|:---------|:-----------|:------|
| 数学推理 | Few-shot CoT + Self-Consistency | GSM8K 准确率从 18% 提升至 78%（GPT-3） |
| 代码生成 | ReAct（执行-调试循环） | 生成 → 运行 → 观察错误 → 修复 |
| 结构化数据提取 | Few-shot + 输出格式控制 | 从非结构化文本中提取实体关系 |
| 多步推理问答 | ReAct（搜索+推理交替） | 需要查询外部知识才能回答的复杂问题 |
| 创意写作 | ToT（多路径探索） | 先生成多个大纲 → 择优展开 → 评估后选择 |

## 面试追问

**Q1（基础）**：Zero-shot 和 Few-shot 提示有什么区别？为什么 Few-shot 有时会失效？
**回答要点**：

1. Zero-shot 直接用指令描述任务，Few-shot 在 prompt 中加入输入-输出示例让模型从示例中学习模式。
2. Few-shot 失效的原因：示例选择不当（与测试样本分布不匹配）、示例顺序不当（模型受近因效应影响）、示例质量差（包含错误标注）。
3. 示例的合理选择：检索与测试样本语义最相似的示例（基于嵌入距离），确保示例覆盖各类别，数量控制在 3~8 个（太长影响速度和效果）。

**Q2（深挖）**：Chain-of-Thought 为什么能提升推理能力？它在哪些任务上效果不明显？
**回答要点**：

1. CoT 显式引导模型生成中间推理步骤，将复杂推理分解为一系列较简单的子步骤，类似人类的"分步思考"。
2. 在需要符号推理（数学、逻辑、编码）的任务上效果显著；在直觉性任务（情感分析、分类）上效果不明显甚至有害（不必要的推理步骤引入噪声）。
3. Self-Consistency 进一步利用多次采样的投票机制提升稳定性，特别适合答案空间有限的推理任务。

**Q3（实战）**：ReAct 和常规 Chain-of-Thought 的核心区别是什么？在什么场景下必须用 ReAct？
**回答要点**：

1. 常规 CoT 纯粹依赖模型的内在知识进行推理，ReAct 在推理过程中可以调用外部工具（搜索、计算器、数据库）获取新信息。
2. 需要外部信息才能回答的场景必须用 ReAct：实时信息（当前股价、天气）、私有数据（公司内部知识库）、精确计算（大数运算、复杂公式）。
3. ReAct 的设计模式是 Think → Act → Observe 循环，每次 action 都会从环境获取新的 observation，作为下一步推理的基础。

**Q4（边界）**：Tree of Thought 相比 Chain-of-Thought 的优劣势是什么？ToT 的搜索策略如何影响效果？
**回答要点**：

1. 优势：ToT 探索多条推理路径而非单一线性路径，避免陷入局部最优；可以通过回溯绕过推理死胡同。
2. 劣势：计算成本高昂（每步生成多个候选 + 评估函数）；评估函数的设计是关键难点（谁来评估推理步骤的正确性？）。
3. 搜索策略的选择：BFS 适合每一步都有明确评估的任务（如数学题），DFS 适合需要深度探索的任务（如代码调试）。剪枝阈值影响探索的广度和深度平衡。
