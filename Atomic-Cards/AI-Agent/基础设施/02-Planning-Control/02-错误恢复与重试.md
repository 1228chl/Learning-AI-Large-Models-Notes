# 错误恢复与重试（Error Recovery）

## 定义

错误恢复系统是 Agent Harness 中处理 API 调用失败的鲁棒性机制，包含指数退避重试、max_tokens 自动升级、备用模型切换三种模式，确保 Agent 在不可靠的网络和服务环境中仍能正常工作。


## 问题描述

工具调用失败就崩溃——API 超时、网络抖动、Shell 命令出错、文件不存在……任何单点故障都导致整个任务失败。真实环境中，外部调用失败是常态而非异常。

不加区分的立即重试可能适得其反——对 API 限速错误立即重试只会加剧问题，而对 Shell 语法错误重试 10 次也是浪费。需要一套分类机制，针对不同错误类型采取不同的恢复策略。

### 核心公式

$$
\text{delay}(n) = \min(500 \times 2^{n}, 32000) \div 1000 + \text{random}(0, \text{base} \times 0.25)
$$

- $n$：重试次数（从 0 开始）
- $500$：初始退避延迟（毫秒），即 $500 \times 2^0 = 500$ms，常量 `BASE_DELAY_MS = 500`
- $2^{n}$：指数增长因子，每次重试延迟翻倍
- $32000$：最大延迟上限（毫秒），即 32 秒
- $\div 1000$：转换为秒
- $\text{random}(0, \text{base} \times 0.25)$：抖动比例，在 0~25% 之间随机，防止并发请求同时重试

### 三种恢复模式

| 模式 | 触发条件 | 恢复动作 | 重试次数上限 | 关键常量 |
|:-----|:---------|:---------|:------------|:---------|
| 输出截断 | `stop_reason == "max_tokens"` | 首次从 8K 升级到 64K（不追加截断内容），后续注入续写提示（最多 3 次） | `MAX_RECOVERY_RETRIES = 3` | `DEFAULT_MAX_TOKENS = 8000`, `ESCLATED_MAX_TOKENS = 64000` |
| 上下文超限 | `prompt_too_long` 错误 | 触发 reactive_compact 应急压缩（保留末尾 5 条消息）后重试 | 1 次 | `has_attempted_reactive_compact` 标记 |
| 临时故障 | 429（限流）/ 529（过载） | 指数退避 + 抖动，连续 3 次 529 切换到备用模型 | `MAX_RETRIES = 10` | `MAX_CONSECUTIVE_529 = 3`, `FALLBACK_MODEL` |

### 核心代码

```python
def with_retry(fn, state: RecoveryState):
    for attempt in range(MAX_RETRIES):  # 最多 10 次
        try:
            result = fn()
            state.consecutive_529 = 0  # 成功后重置
            return result
        except (RateLimitError, OverloadedError):
            # 429/529 -> 指数退避
            if "overloaded" in str(e).lower():
                state.consecutive_529 += 1
                if state.consecutive_529 >= 3 and FALLBACK_MODEL:
                    state.current_model = FALLBACK_MODEL  # 切换备用模型
            delay = retry_delay(attempt)
            time.sleep(delay)
            continue
    raise MaxRetriesExceeded()

def retry_delay(attempt, retry_after=None):
    if retry_after:
        return retry_after
    base = min(500 * (2 ** attempt), 32000) / 1000
    return base + random.uniform(0, base * 0.25)  # 抖动

class RecoveryState:
    def __init__(self):
        self.has_escalated = False           # 是否已升级到 64K
        self.recovery_count = 0              # 续写次数
        self.consecutive_529 = 0             # 连续 529 计数
        self.has_attempted_reactive_compact = False  # 是否已应急压缩
        self.current_model = PRIMARY_MODEL   # 当前模型
```

- `RateLimitError` / `OverloadedError`：API 返回的 429 和 529 错误
- `retry_after`：API 可能返回 `Retry-After` 头部指定重试时间
- `state.consecutive_529`：连续 529 计数，连续 3 次触发模型切换
- `FALLBACK_MODEL`：备用模型 ID，如主模型不可用时切换的轻量级模型

## 直观理解

错误恢复就像开车遇到堵车：先等一等看能不能通（指数退避，短等待），如果一直堵就换条路走（备用模型切换），如果输出的内容被截断就加张纸继续写（续写提示）。

## Agent 工程应用场景

| 应用场景 | 错误类型 | 恢复策略 |
|:---------|:---------|:---------|
| API 限流 | 429 RateLimitError | 指数退避 + 抖动，等待后重试 |
| 服务过载 | 529 OverloadedError | 连续 3 次切换备用模型 |
| 长输出截断 | max_tokens | 升级到 64K 窗口，或注入续写提示 |
| 上下文超限 | prompt_too_long | 触发 reactive_compact 压缩后重试 |
| 网络超时 | timeout | 增加超时时间后重试（如 60s→120s） |

## 面试追问

**Q1（基础）**：指数退避的三个关键参数是什么？为什么要加抖动？
**回答要点**：

1. 初始延迟（500ms）、增长因子（2 倍）、最大延迟上限（32s）
2. 抖动（jitter）是随机添加的额外延迟，防止大量并发请求在退避后同时重试
3. 抖动公式：`base + random(0, base * 0.25)`，即在基础延迟上增加 0~25% 的随机量
4. 没有抖动的话，所有同时失败的请求会在完全相同的时刻重试，造成"惊群效应"

**Q2（深挖）**：max_tokens 截断时，为什么先升级到 64K 而不是直接续写？
**回答要点**：

1. 升级到 64K 是一步到位，如果模型输出确实需要更多空间，64K 通常足够
2. 续写需要额外注入提示词并调用 API，增加成本和延迟
3. 64K 仍不够时再使用续写提示（最多 3 次），每次续写都从断点继续
4. 3 次续写后仍不够，说明模型可能陷入了循环输出，应终止并报错

**Q3（实战）**：如何实现备用模型切换，切换后如何保证回退？
**回答要点**：

1. 维护 `state.current_model` 和 `state.fallback_model` 两个状态
2. 连续 3 次 529 时将 `current_model` 设为 `FALLBACK_MODEL_ID`
3. 切换后用一个定时器，每 5 分钟尝试恢复主模型
4. 恢复成功后重置 `consecutive_529` 计数器，后续请求切回主模型

**Q4（边界）**：如果重试 10 次全部失败，系统应该怎么做？
**回答要点**：

1. 抛出 `MaxRetriesExceeded` 异常，向用户返回友好的错误提示
2. 将当前状态（消息列表、已执行工具）持久化，允许用户手动恢复
3. 记录完整错误日志供排查
4. 生产环境应触发告警通知运维人员
