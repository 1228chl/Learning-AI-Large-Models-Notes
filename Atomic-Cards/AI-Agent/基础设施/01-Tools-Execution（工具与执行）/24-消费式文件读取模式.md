# 消费式文件读取模式

## 定义

消费式文件读取（Read + Unlink）是一种基于文件系统的消息队列模式，通过 `read_text()` 读取文件内容后立即 `unlink()` 删除文件，实现"读取即消费"的语义。每条消息只被处理一次，天然支持进程间通信和持久化。

$$
\text{Consume} = \text{read\_text()} + \text{unlink()} = \text{消费}
$$


## 问题描述

读取大文件时，一次性将全部内容读入内存会导致内存占用飙升。更隐蔽的问题是：读取后没有及时释放文件句柄，长期运行的系统会逐渐耗尽文件描述符。

消费式文件读取模式（Consumptive Read）将文件读取设计为“消费”操作——读取内容后标记已处理，下次读取跳过已消费部分，用完即释放资源。

### 核心代码

```python
from pathlib import Path

MAILBOX_DIR = WORKDIR / ".mailboxes"

def read_inbox(agent: str) -> list[dict]:
    """读取并消费收件箱：读取后删除文件（消费式）。"""
    inbox = MAILBOX_DIR / f"{agent}.jsonl"  # 每个 Agent 一个文件

    # 1. 文件不存在 → 没有新消息
    if not inbox.exists():
        return []

    # 2. 读取所有消息（JSONL 格式：每行一个 JSON 对象）
    msgs = [json.loads(line) for line in inbox.read_text().splitlines() if line.strip()]

    # 3. 删除文件 → 消费完成
    inbox.unlink()

    return msgs

def send(from_agent: str, to_agent: str, content: str, msg_type: str = "message"):
    """发送消息：追加到收件人文件末尾。"""
    msg = {"from": from_agent, "to": to_agent, "content": content, "type": msg_type, "ts": time.time()}
    inbox = MAILBOX_DIR / f"{to_agent}.jsonl"
    with open(inbox, "a") as f:
        f.write(json.dumps(msg, ensure_ascii=False) + "\n")
```

## 三步流程

```
发送方:  open(inbox, "a") + write(msg) + close
                              ↓
                     收件人文件追加一行 JSON
                              ↓
接收方:  read_text() → 读取全部行 → unlink() → 删除文件
                              ↓
                     消息被消费，文件不复存在
```

## 直观理解

消费式文件读取像"一次性信封"——发信人把信放进信封（追加写入文件），收信人取出信后把信封扔掉（unlink 删除文件）。这样确保每封信只被读一次，不会出现"同一封信被读了两遍"的问题。

## Agent 工程应用场景

| 应用场景 | 文件路径 | 说明 |
|:---------|:---------|:-----|
| Agent 间通信 | `.mailboxes/{agent_name}.jsonl` | 队友发送消息给 Lead，Lead 消费后删除 |
| 后台任务通知 | 主线程收集后删除 | 后台线程完成通知，主线程消费后即消失 |
| 指令队列 | `.commands/{id}.json` | 主 Agent 向队友下发指令，队友消费后删除 |

## 面试追问

**Q1（基础）**：消费式文件读取的核心思想是什么？为什么用 `unlink()` 而不是 `write_text("")` 清空文件？
**回答要点**：

1. 核心思想：读取即消费，每条消息只处理一次
2. `unlink()` 删除文件比 `write_text("")` 清空更安全——如果进程在清空后崩溃，写入新消息前，其他进程看到空文件会误以为没有消息
3. `unlink()` 后文件不存在，新消息会创建一个新文件，不会混淆新旧消息
4. 删除文件比清空文件更符合"消费"的语义——消息不存在了

**Q2（深挖）**：这种模式在大规模消息场景下有什么性能瓶颈？什么情况下应该迁移到 Redis/消息队列？
**回答要点**：

1. 文件 I/O 性能：每秒处理数百条消息后开始下降，每读一次就需要一次磁盘操作
2. 无消息确认机制：读取后 unlink，如果处理过程中崩溃，消息丢失
3. 无订阅/发布模式：只能点对点通信，无法广播
4. 迁移条件：消息量 > 1000条/秒、需要广播、需要消息确认、需要持久化保证

**Q3（实战）**：如何实现一个"非破坏性检查"方法，检查是否有新消息但不消费？
**回答要点**：

1. 实现 `peek()` 方法：检查文件是否存在且大小 > 0
2. 不读取文件内容，仅检查 `inbox.exists() and inbox.stat().st_size > 0`
3. 这样主线程可以快速检查是否有新消息，决定是否需要唤醒 Agent 处理
4. 真正的消费仍由 `read_inbox()` 完成，`peek()` 只做判断

**Q4（边界）**：如果多个线程同时 `read_inbox` 同一个 Agent 的文件，会发生什么？如何解决？
**回答要点**：

1. 两个线程同时检查 `inbox.exists()` 都返回 True，然后都读取内容
2. 线程A 先 `unlink()` 成功，线程B 的 `unlink()` 抛出 FileNotFoundError
3. 导致：线程A 消费了消息，线程B 抛异常
4. 解决方案：使用文件锁（`fcntl.flock` 或 `portalocker`），加锁后再读取
