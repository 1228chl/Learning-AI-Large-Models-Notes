# 任务系统（Task System）

## 定义

任务系统是一种文件持久化的任务图管理机制，支持任务之间的依赖关系（`blockedBy`）声明，形成有向无环图（DAG）。任务可跨会话恢复，支持创建、认领、完成等全生命周期管理。

$$
\text{Task DAG} = \{\text{Task}_i \mid \text{Task}_i.\text{blockedBy} \subset \text{Tasks}\}, \quad \text{can\_start}(t) = \forall b \in t.\text{blockedBy}: \text{status}(b) = \text{completed}
$$

### 任务数据结构

```python
@dataclass
class Task:
    id: str                    # "task_{timestamp}_{random:04d}"，全局唯一
    subject: str               # 简短标题，一眼可识别
    description: str           # 详细描述，含具体需求
    status: str                # pending | in_progress | completed
    owner: str | None          # 认领该任务的 Agent 名
    blockedBy: list[str]       # 依赖的任务 ID 列表，形成 DAG
```


## 问题描述

模糊的目标“优化这个项目”难以跟踪和观察——Agent 做什么了？做到哪一步了？还有多少没做？用户和 Agent 都没有一个清晰的“任务地图”。

任务系统把模糊目标转化为结构化的任务图（Task Graph）：任务分解为子任务，子任务有明确的状态（待处理/进行中/已完成/阻塞），每个步骤都可观察、可追踪。

## 任务工具

| 工具 | 功能 | 关键参数 | 副作用 |
|:-----|:-----|:---------|:-------|
| `create_task` | 创建新任务 | `subject`、`description`、`blockedBy` | 写入 `.tasks/{id}.json` |
| `list_tasks` | 列出所有任务 | 无 | 读取 `.tasks/` 目录 |
| `get_task` | 查看任务详情 | `task_id` | 读取单个任务文件 |
| `claim_task` | 认领任务 | `task_id` | 检查依赖是否全部完成，写入 owner |
| `complete_task` | 完成任务 | `task_id` | 更改状态，自动解锁下游任务 |

## 状态机

```
pending ──claim（依赖全部完成）──→ in_progress ──complete──→ completed
                ↑                              ↓
         拒绝认领（依赖未完成）         自动解锁下游任务
```

## 直观理解

任务系统像一张"工程甘特图"——每个任务是一个节点，`blockedBy` 是箭头指向前置依赖。任务只有所有前置依赖完成后才能被认领执行。整个图持久化在文件系统中，就像把甘特图打印出来贴在墙上，即使人走了回来还能接着看。

## Agent 工程应用场景

| 应用场景 | 实现方式 | 说明 |
|:---------|:---------|:-----|
| 复杂任务分解 | 创建多个子任务 + blockedBy 依赖 | 大任务拆解为可并行/串行执行的小任务 |
| 跨会话持续工作 | 所有任务持久化为 `.json` 文件 | 重启会话后任务仍在，可恢复执行 |
| 多 Agent 协作 | 不同 Agent 认领不同任务 | 通过任务看板协调，无需人工分配 |
| 自动解锁 | complete_task 触发下游检查 | 依赖完成后自动解锁，任务可被认领 |

## 面试追问

**Q1（基础）**：任务系统的核心数据结构是什么？`blockedBy` 如何实现依赖管理？
**回答要点**：

1. 核心是 `Task` 数据类，包含 `id`、`subject`、`description`、`status`、`owner`、`blockedBy` 六个字段
2. `blockedBy` 是依赖任务 ID 列表，形成有向无环图（DAG）
3. 认领任务时检查 `can_start(t)`：依赖列表中所有任务状态均为 `completed`
4. 完成任务时自动扫描所有任务，检查是否有被解锁的下游任务，发送通知

**Q2（深挖）**：为什么用文件持久化而非数据库？文件系统在任务管理中的优缺点？
**回答要点**：

1. 优点：零依赖、调试友好（可直接 `cat` 查看）、跨会话免配置
2. 优点：天然支持并行读写（不同 Agent 操作不同文件）
3. 缺点：缺乏原子性操作（文件写入可能被中断导致损坏）
4. 缺点：无索引、无查询优化，大量任务时性能下降
5. 缺点：无事务支持，多个操作无法保证原子性

**Q3（实战）**：如何实现一个"依赖全部完成时自动通知相关 Agent"的机制？
**回答要点**：

1. 在 `complete_task` 函数中，标记任务为 `completed`
2. 扫描所有任务，找到 `blockedBy` 包含刚完成的任务 ID 的任务
3. 对这些任务的 `owner` 发送通知（通过消息总线或直接注入提醒）
4. 如果没有 `owner`（未被认领），在任务看板中标记为"可认领"
5. 利用 PostToolUse Hook 或 cron 调度器定期检查解锁状态

**Q4（边界）**：如果任务图中出现了循环依赖（环形 DAG），系统会怎样？
**回答要点**：

1. 循环依赖会导致所有任务永远无法被认领（每个任务都在等另一个完成）
2. 检测方式：创建任务时检查 `blockedBy` 链中是否包含自身（DFS 检测环）
3. 检测到环时拒绝创建，返回错误信息提示用户调整依赖关系
4. 如果已存在环，提供 `break_dependency(task_id)` 工具手动解除依赖
