# 回溯问题检索策略

## 定义

回溯问题检索（StepBack/Backtracking）是一种将复杂用户查询转化为更基础、更易于检索的问题的策略。当查询涉及需要前置知识或复合推理时，先回溯到更高层的抽象概念去检索，降低检索难度。

$$
\text{StepBack} = \text{LLM}_{\text{stepback}}(q) \rightarrow q_{\text{back}} \rightarrow \text{Retrieve}(q_{\text{back}})
$$

- $q$：用户原始复杂查询
- $q_{\text{back}}$：LLM 回溯后生成的简化问题，更基础、更易检索
- $\text{Retrieve}(q_{\text{back}})$：用简化问题执行混合检索+重排序

### 核心代码

```python
def _retrieve_with_backtracking(self, query):
    """使用回溯问题策略进行检索。"""
    # 1. LLM 生成回溯问题（简化/改写）
    backtrack_prompt = RAGPrompts.backtracking_prompt()
    simplified_query = self.llm(backtrack_prompt.format(query=query)).strip()

    # 2. 用简化问题进行混合检索+重排序
    return self.vector_store.hybrid_search_with_rerank(
        simplified_query, k=conf.RETRIEVAL_K
    )
```

### 回溯 Prompt 模板

```python
@staticmethod
def backtracking_prompt():
    return PromptTemplate(
        template="""  
        将以下复杂查询简化为一个更简单的问题：  
        查询: {query}  
        简化问题:  
        """,
        input_variables=["query"],
    )
```

## 回溯 vs 子查询 vs HyDE

| 对比维度 | 回溯问题 | 子查询 | HyDE |
|:---------|:---------|:-------|:-----|
| 输出形式 | 1 个简化问题 | 多个子问题 | 1 个假设答案 |
| 检索次数 | 1 次 | k 次 | 1 次 |
| 核心思路 | 降低问题复杂度 | 扩大检索覆盖面 | 填补语义鸿沟 |
| 典型查询 | "100亿条数据存 Milvus 可以吗？" | "对比A和B的优缺点" | "人工智能在教育领域的应用" |

## 直观理解

回溯问题检索像"从树枝退到树干"——用户问"这棵树的第三根树枝上有什么颜色的花？"（具体，复杂），先退到"这棵树是什么品种"（基础，易检索），找到树的信息后再回答具体问题。

## RAG 工程应用场景

| 应用场景 | 原始查询 | 回溯后的简化问题 |
|:---------|:---------|:----------------|
| 容量评估 | "100亿条数据存Milvus可以吗？" | "Milvus 最大支持多少数据量" |
| 技术可行性 | "用Transformer做实时语音识别可行吗？" | "Transformer 的推理延迟特性" |
| 对比前提 | "为什么Transformer不用RNN？" | "RNN 的序列处理原理是什么" |

## 面试追问

**Q1（基础）**：回溯问题检索的核心思路是什么？和子查询有什么区别？
**回答要点**：

1. 核心思路：将复杂问题简化为更基础的问题，降低检索难度
2. 回溯生成 1 个简化问题，子查询生成多个子问题
3. 回溯只需 1 次检索，子查询需要 k 次
4. 回溯适用于"需要前置知识"的问题，子查询适用于"多角度"的问题

**Q2（深挖）**：回溯策略的 Prompt 设计核心是什么？为什么不需要复杂指令？
**回答要点**：

1. 核心是"简化"——让 LLM 去掉具体约束，提取核心概念
2. 简单指令即可：`将以下复杂查询简化为一个更简单的问题`
3. 不需要复杂的 few-shot 示例，因为"简化问题"是 LLM 擅长的基础能力
4. 注意：简化过度可能丢失关键信息（如"100亿条"这个具体数字）

**Q3（实战）**：什么情况下回溯策略的检索结果可能不如直接检索？
**回答要点**：

1. 简化过度，丢失了原始查询中的关键约束条件
2. 原始查询本身已经很简单，回溯反而引入噪声
3. 需要精确匹配的查询（如"2024年3月的财报"），回溯后变成"公司财报"丢失时间信息
4. 建议：回溯结果和直接检索结果合并，取两者交集

**Q4（边界）**：回溯策略和 HyDE 策略可以组合使用吗？顺序如何？
**回答要点**：

1. 可以组合：先回溯简化问题，再对简化问题做 HyDE 生成假设答案
2. 顺序：先回溯（降低复杂度），再 HyDE（填补语义鸿沟）
3. 但组合使用会增加 2 次 LLM 调用和相应延迟
4. 生产建议：仅在直接检索效果不佳时，按"回溯→HyDE→子查询"的优先级尝试
