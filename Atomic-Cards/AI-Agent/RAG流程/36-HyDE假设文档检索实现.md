# HyDE 假设文档检索实现

## 定义

HyDE（Hypothetical Document Embedding）是一种检索增强策略，通过 LLM 将用户短查询生成一个**假设答案**（Hypothetical Answer），然后用假设答案代替原始查询进行向量检索。核心思想是"用生成填补检索鸿沟"——短查询的向量与相关文档的向量簇距离较远，而假设答案更接近文档的语言风格，检索命中率更高。

$$
\text{HyDE} = \text{LLM}(q) \rightarrow \hat{a} \rightarrow \text{Retrieve}(\hat{a})
$$

- $q$：用户原始查询（通常较短，语义稀疏）
- $\hat{a}$：LLM 根据 $q$ 生成的假设答案，包含更多与文档风格一致的语义细节
- $\text{Retrieve}(\hat{a})$：用假设答案的嵌入向量检索向量库

### 核心代码

```python
def _retrieve_with_hyde(self, query):
    """使用 HyDE 策略进行检索。"""
    # 1. 获取 HyDE 专用 Prompt 模板
    hyde_prompt = RAGPrompts.hyde_prompt()

    # 2. LLM 生成假设答案
    hypo_answer = self.llm(hyde_prompt.format(query=query)).strip()

    # 3. 用假设答案替代原始查询进行混合检索+重排序
    return self.vector_store.hybrid_search_with_rerank(
        hypo_answer, k=conf.RETRIEVAL_K
    )
```

### HyDE Prompt 模板

```python
@staticmethod
def hyde_prompt():
    return PromptTemplate(
        template="""  
        假设你是用户，想了解以下问题，请生成一个简短的假设答案：  
        问题: {query}  
        假设答案:  
        """,
        input_variables=["query"],
    )
```

## 四策略对比

| 策略 | 核心操作 | 额外 LLM 调用 | 适用场景 | 风险 |
|:-----|:---------|:-------------:|:---------|:-----|
| 直接检索 | 原始 query 直接检索 | 0 | 查询清晰、关键词明确 | 短查询语义不足 |
| **HyDE** | **LLM 生成假设答案 → 替代 query 检索** | **1 次** | **查询短小、抽象、和文档语言风格不同** | **假设答案可能偏离真实意图** |
| 子查询 | 拆分为多个子问题分别检索 | 1 次 | 多角度/多主题复合问题 | 子查询过多导致结果膨胀 |
| 回溯 | 简化/改写 query 后检索 | 1 次 | 复杂需前置知识的问题 | 简化过度丢失关键信息 |

## 直观理解

HyDE 像一个"翻译官"——用户说"那个东西怎么用"（短查询，模糊），翻译官先写一段使用说明（假设答案），然后用这段说明去图书馆找书（检索）。因为使用说明和书的语言风格一致，比用户的原话更容易命中。

## RAG 工程应用场景

| 应用场景 | 查询示例 | HyDE 生成效果 |
|:---------|:---------|:--------------|
| 抽象概念检索 | "人工智能在教育领域的应用" | 生成包含具体应用的假设答案，检索到相关案例文档 |
| 短查询弥补 | "学大模型测试有什么用" | 生成的假设答案包含"测试方法""评估指标"等关键词 |
| 语言风格不对齐 | 用户口语化查询 vs 文档书面化 | 假设答案趋向书面化，缩小与文档的语义差距 |

## 面试追问

**Q1（基础）**：HyDE 的核心思想是什么？它解决了什么问题？
**回答要点**：

1. 核心思想：让 LLM 先生成一个假设答案，用假设答案而非原始查询去检索
2. 解决的问题：用户短查询和知识库文档之间的**语义鸿沟（Semantic Gap）**
3. 短查询在 embedding 空间中是一个稀疏孤立点，假设答案更接近文档的语义区域
4. 本质上是"检索侧的数据增强"——通过 LLM 补充查询缺失的语义细节

**Q2（深挖）**：HyDE 可能引入什么风险？如何缓解？
**回答要点**：

1. 风险：LLM 生成的假设答案可能偏离真实用户意图，导致检索结果偏离
2. 幻觉放大：如果 LLM 在假设答案中编造了错误信息，检索会朝错误方向偏移
3. 缓解方案：对假设答案做长度限制（短答案更聚焦）、设置 temperature=0 减少随机性
4. 更安全的做法：HyDE 结果和直接检索结果合并，取两者交集

**Q3（实战）**：HyDE 和 RAG 系统中其他改写策略（子查询、回溯）有什么区别？
**回答要点**：

1. HyDE 是"生成答案"——LLM 输出的是假设的完整答案，风格接近文档
2. 子查询是"分解问题"——LLM 输出的是多个子问题，分别检索后合并
3. 回溯是"简化问题"——LLM 输出的是更基础的问题，降低检索难度
4. 选择依据：查询语义稀疏（HyDE）、多主题（子查询）、需要前置知识（回溯）

**Q4（边界）**：HyDE 在什么场景下效果可能比直接检索还差？
**回答要点**：

1. 查询本身已经很长且语义清晰时，HyDE 的假设答案可能引入噪声
2. 需要精确数字/事实的查询（如"2024年GDP是多少"），假设答案的数值可能出错
3. LLM 对领域知识不熟悉时，生成的假设答案质量差，误导检索
4. 建议：对简单事实类查询走直接检索，仅对抽象/模糊查询启用 HyDE
