# 父文档与子文档分块策略（Parent-Child Chunking）

## 定义

父文档与子文档分块策略（Parent-Child Chunking）是一种**两级分块**的文档处理方式，将同一文档同时切分为大块（父块）和小块（子块），检索时匹配小块但返回大块作为 LLM 上下文，兼顾检索精度和上下文完整性。

该策略解决了单级分块的核心矛盾：小分块检索精度高但上下文碎片化（LLM 看不到完整段落），大分块上下文完整但检索精度低（噪声多导致相关性下降）。

### 形式化定义

设文档 $D$ 被切分为两级分块集合：

$$
\text{Parents}(D) = \{p_1, p_2, \dots, p_m\}, \quad \text{Children}(D) = \{c_1, c_2, \dots, c_n\}
$$

其中每个子块 $c_j$ 唯一属于一个父块 $p_i$，满足分区映射关系：

$$
\forall c_j \in \text{Children}(D): \exists! p_i \in \text{Parents}(D) \text{ such that } c_j \subseteq p_i
$$

检索时，检索向量 $\mathbf{q}$ 与子块向量 $\mathbf{v}(c_j)$ 计算相似度：

$$
\text{Retrieve}(q) = p_i \text{ where } c\_j^* = \arg\max_{c_j} \text{sim}(\mathbf{q}, \mathbf{v}(c_j)), \quad c_j \subseteq p_i
$$

- $\mathbf{q}$：查询的嵌入向量
- $\mathbf{v}(c_j)$：子块 $c_j$ 的嵌入向量
- $\text{sim}(\cdot, \cdot)$：相似度函数（通常为余弦相似度）
- $p_i$：包含最佳匹配子块 $c_j^*$ 的父块

## 分块参数与配置

| 参数 | 父块推荐值 | 子块推荐值 | 说明 |
|:----|:----------:|:----------:|:----|
| **块大小** | 512-1024 tokens | 128-256 tokens | 父块提供完整上下文，子块保障检索精度 |
| **重叠（Overlap）** | 50-100 tokens | 20-50 tokens | 防止语义断裂在分割边界处 |
| **切分方式** | 按段落/标题 | 递归字符切分 | 父块保留语义单元，子块可用更细粒度切分器 |
| **Embedding** | 不生成向量（仅存原文） | 生成稠密+稀疏向量 | 只有子块需要向量化用于检索 |
| **存储字段** | 原文 + 元数据 | 原文 + 向量 + `parent_id` | 子块通过 `parent_id` 关联到父块 |

## 直观理解

> 父块是"完整章节"，子块是"章节中的关键段落"。搜索引擎找到最相关的段落（子块），然后拿出整个章节（父块）给 LLM 阅读。LLM 获得完整上下文，读者找到精确位置。

## 与单级分块的对比

| 对比维度 | 单级小分块 | 单级大分块 | 父子分块 |
|:--------:|:----------:|:----------:|:--------:|
| **检索精度** | 高（匹配粒度细） | 低（噪声多） | 高（子块匹配） |
| **上下文完整性** | 低（碎片化） | 高 | 高（父块返回） |
| **存储开销** | 低（一个向量/块） | 低 | 较高（额外存储父块原文） |
| **检索延迟** | 低 | 低 | 低（仅检索子块） |
| **实现复杂度** | 简单 | 简单 | 中等（需维护父-子关联） |

## ML/DL 应用场景

| 应用场景 | 子块角色 | 父块角色 | 说明 |
|:--------|:---------|:---------|:-----|
| **RAG 问答系统** | 精确匹配用户问题 | 提供完整段落上下文 | 用户提问后检索子块，返回父块给 LLM 生成答案 |
| **长文档摘要** | 识别关键句子 | 提供段落完整内容 | 多级匹配后综合多个父块生成摘要 |
| **法律条文检索** | 匹配具体条款关键词 | 提供完整法条上下文 | 律师查询时精确定位条款，返回整条法规供分析 |
| **代码库问答** | 匹配函数签名或注释 | 提供完整函数体 | 开发者提问 API 用法，检索到函数签名，返回完整函数实现 |

## 面试追问

**Q1（基础）**：父文档与子文档分块策略解决了单级分块的什么核心矛盾？
**回答要点**：

1. 小分块检索精度高但返回给 LLM 的上下文碎片化，缺少完整语义背景
2. 大分块上下文完整但包含大量噪声，降低检索准确率
3. 父子分块用子块做精确检索、父块提供完整上下文，二者兼顾

**Q2（深挖）**：父块和子块的块大小应该如何确定？有哪些权衡？
**回答要点**：

1. 子块大小以 128-256 tokens 为佳，足够表达一个完整语义单元又足够精确
2. 父块大小取决于 LLM 上下文窗口和文档结构，一般 512-1024 tokens 或按段落/标题切分
3. 子块过小（<50 tokens）语义不完整导致检索漂移；父块过大（>2000 tokens）失去上下文增益
4. 需根据实际文档类型（技术文档 vs 新闻 vs 代码）动态调整

**Q3（实战）**：在 Milvus 中如何实现父子块的关联存储和检索？
**回答要点**：

1. 子块表存储子块向量和文本，添加 `parent_id` 字段指向父块
2. 父块表只存储原文和元数据，不生成向量（减少存储和计算开销）
3. 检索时：子块表 `search()` 得到 top-k 子块 → `parent_id` 查父块表 → 拼接父块原文送 LLM
4. 也可以在单表中用 `parent_text` 字段存父块原文，子块 `text` 存子块原文，查询时返回 `parent_text`

**Q4（边界）**：什么场景下父子分块策略反而劣于单级分块？
**回答要点**：

1. 文档极短（<200 tokens）：父子分块无意义，直接单级分块即可
2. 文档语义连续无明确段落边界（如意识流文本、纯数据表格）：父子块边界难以定义
3. 实时性要求极高的场景：父子分块增加一次额外查询开销，虽小但对毫秒级系统有影响
4. 存储成本敏感的场景：需额外存储父块原文，虽廉价但对超大规模（数亿文档）系统不可忽视
