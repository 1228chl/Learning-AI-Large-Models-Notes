# 子查询检索策略

## 定义

子查询检索（SubQuery）是一种将复杂用户查询拆分为多个简单子查询、分别检索后合并去重的策略。适用于查询涉及多个实体或方面的问题，通过多路召回提升检索覆盖率。

$$
\text{SubQuery} = \text{LLM}_{\text{decompose}}(q) \rightarrow \{q_1, q_2, \dots, q_k\} \rightarrow \bigcup_{i=1}^k \text{Retrieve}(q_i) \rightarrow \text{Dedup}
$$

- $q$：用户原始复杂查询
- $\{q_1, q_2, \dots, q_k\}$：LLM 分解得到的子查询集合，通常 2-4 个
- $\text{Retrieve}(q_i)$：对每个子查询分别执行混合检索+重排序
- $\text{Dedup}$：基于文档内容去重，合并所有子查询的检索结果

### 核心代码

```python
def _retrieve_with_subqueries(self, query):
    """使用子查询策略进行检索。"""
    # 1. LLM 生成子查询列表
    subquery_prompt = RAGPrompts.subquery_prompt()
    subqueries_text = self.llm(subquery_prompt.format(query=query)).strip()
    subqueries = [q.strip() for q in subqueries_text.split("\n") if q.strip()]

    # 2. 对每个子查询分别检索
    all_docs = []
    for sub_q in subqueries:
        docs = self.vector_store.hybrid_search_with_rerank(sub_q, k=conf.RETRIEVAL_K)
        all_docs.extend(docs)

    # 3. 基于内容去重（相同内容只保留一份）
    unique_docs = {doc.page_content: doc for doc in all_docs}.values()
    return list(unique_docs)
```

### 子查询 Prompt 模板

```python
@staticmethod
def subquery_prompt():
    return PromptTemplate(
        template="""  
        将以下复杂查询分解为多个简单子查询，每行一个子查询：  
        查询: {query}  
        子查询:  
        """,
        input_variables=["query"],
    )
```

## 子查询 vs 其他策略

| 对比维度 | 子查询检索 | HyDE | 回溯问题检索 |
|:---------|:-----------|:-----|:------------|
| LLM 输出 | 多个子查询 | 一个假设答案 | 一个简化问题 |
| 检索次数 | k 次（等于子查询数） | 1 次 | 1 次 |
| 结果合并 | 多路合并 + 去重 | 单路 | 单路 |
| 开销 | 高（k 次检索） | 中（1 次检索 + 1 次 LLM） | 低（1 次检索 + 1 次 LLM） |
| 适用场景 | 多角度复合问题 | 语义稀疏问题 | 复杂需简化问题 |

## 直观理解

子查询检索像"多个探照灯同时照射"——一个大问题"A 和 B 有什么区别" = 探照灯照向 A + 探照灯照向 B + 探照灯照向"对比"。每个子查询照亮一个角度，最后把照亮的区域拼起来，去掉重复部分。

## 面试追问

**Q1（基础）**：子查询检索的核心流程是什么？为什么需要去重？
**回答要点**：

1. LLM 将复杂查询分解为多个子查询，每行一个
2. 对每个子查询分别执行混合检索+重排序
3. 合并所有子查询的检索结果
4. 基于文档内容去重——不同子查询可能检索到相同的文档

**Q2（深挖）**：子查询数量和检索开销如何平衡？子查询过多有什么问题？
**回答要点**：

1. 子查询越多，检索结果覆盖面越广，但检索次数线性增长（k 次检索）
2. 过多子查询导致结果膨胀，大量冗余信息需要 LLM 处理
3. 建议限制子查询数量在 2-4 个，LLM 应生成最核心的子查询而非穷举
4. 可在 Prompt 中明确要求"最多生成 3 个子查询"

**Q3（实战）**：子查询检索的结果去重应该基于什么粒度？为什么不用内存地址去重？
**回答要点**：

1. 应基于文档内容（`page_content`）去重，而非内存地址或对象引用
2. 不同子查询返回的 Document 对象即使内容相同，内存地址也不同
3. 实现方式：`unique_docs = {doc.page_content: doc for doc in all_docs}.values()`
4. 更精确的方案：使用文档 ID 或文本哈希值去重

**Q4（边界）**：如果子查询本身仍然很复杂，需要递归分解吗？
**回答要点**：

1. 当前实现只做一层分解，不递归
2. 递归分解可能导致子查询数量指数增长，成本和延迟失控
3. 改进方案：对首次检索结果不满意的子查询，单独再走一次策略选择
4. 生产建议：子查询结果做二次 Rerank，合并后的 TopK 传给 LLM，不追求面面俱到
