# LangGraph 滑动窗口与摘要压缩记忆管理

## 定义

LangGraph 记忆管理中，**滑动窗口 + 摘要压缩**是解决多轮对话"上下文无限膨胀"的核心策略。它将记忆分为两层：MemorySaver 存储完整 `messages` 历史（通过 `thread_id` 持久化，保障可追溯），推理上下文只取"最近 $W$ 轮原始消息 + 历史摘要"（固定大小，控制 token 成本）。摘要每 $W$ 轮触发一次压缩，将最近消息与已有摘要合并为新摘要。

核心设计原则：**存储与使用分离**。存全量是为了追溯和审计，用摘要+窗口是为了控制推理成本。

$$ \text{推理上下文} = \underbrace{\text{SystemMessage(最新摘要)}}_{\text{长期记忆}} + \underbrace{\text{最近 } W \text{ 轮消息}}_{\text{短期记忆}} + \underbrace{\text{当前问题}}_{\text{新输入}} $$

## 三大核心函数

| 函数 | 职责 | 输入 | 输出 |
|------|------|------|------|
| `trim_messages_to_window(state, W)` | 截取最近 $W$ 轮消息，保证推理上下文不超限 | 完整 messages 列表 | 截断后的 messages（只保留最近 $W$ 轮） |
| `should_trigger_summary(state, W)` | 判断是否需要压缩——消息数达到 $W$ 的倍数时触发 | 当前 messages 列表 | `True` / `False` |
| `compress_to_summary(state, W)` | LLM 将最近 $W$ 轮 + 旧摘要合并为新摘要 | 旧摘要 + 最近 $W$ 轮 | 新摘要字符串 |

## 直观理解

> 一本只有 10 页的笔记本——你不能把每次对话都完整抄下来（40 轮对话早就写满了）。所以每写满 10 页，就花一分钟把"最近 10 页说了什么"浓缩成一段摘要写回首页，然后把旧页撕掉只保留最近 10 页。下次翻笔记本时，先看首页的摘要（长期记忆），再看最近 10 页的详细记录（短期记忆），就能既知道"之前聊了什么"又不浪费纸张。每次撕掉的页（全量 messages）其实锁在保险柜里（MemorySaver），需要时可以调出来。

## 触发逻辑与时间线

摘要触发采用**倍增间隔**策略，避免连续压缩：

$$ \text{触发轮次：} W, 2W, 3W, \dots $$

每次压缩后计数器归零，下次触发从新基准算起。`should_trigger_summary` 只统计 HumanMessage + AIMessage（排除 SystemMessage）：

```python
def should_trigger_summary(state, window_size=10):
    """每 window_size 轮触发一次压缩"""
    msg_count = sum(1 for m in state["messages"]
                    if isinstance(m, (HumanMessage, AIMessage)))
    return msg_count > 0 and msg_count % window_size == 0
```

## 推理上下文构建

```python
def build_inference_context(state, summary, window_size=10):
    """构建传给 LLM 的完整上下文：摘要 + 窗口 + 当前问题"""
    system_msg = SystemMessage(content=f"对话历史摘要：\n{summary}" if summary else "")
    recent_msgs = state["messages"][-(window_size + 1):-1]   # 最近 W 轮，不含最后一条
    current_q  = state["messages"][-1]                        # 最后一条是当前问题

    return [system_msg] + recent_msgs + [current_q]           # 三段拼接
```

`messages[:-1]` 而不是 `messages[:]` 的原因：最后一条消息就是当前问题（已经作为 HumanMessage 传入），重复传入会浪费 token 且造成 LLM 困惑。

## AI/ML 工程应用场景

| 应用场景 | 窗口大小 $W$ | 摘要触发策略 | 说明 |
|---------|------------|------------|------|
| AI 面试对话（40+ 轮） | 10 | 每 10 轮压缩，保留最近 20 轮原始消息 | 面试对话长，摘要成本高但必要 |
| 客服对话（10-20 轮） | 5 | 每 5 轮压缩 | 短对话为主，窗口小、触发频繁 |
| 代码助手（持续会话） | 20 | 每 20 轮压缩 | 代码上下文需要更长的原始窗口来保持连贯性 |
| 教育辅导对话 | 8 | 倍增间隔 | 学生提问频率不定，需灵活调整 |

## 面试追问

**Q1（基础）**：为什么 LangGraph 记忆管理需要"存储与使用分离"？

**回答要点**：

1. 存储（MemorySaver）：全量 messages 历史——保障完整可追溯、支持审计和 debug
2. 使用（推理上下文）：只取最近 $W$ 轮 + 摘要——控制 token 成本在固定范围内
3. 如果存储和使用不分离：要么丢弃历史（无法追溯），要么每次全量传入（token 爆炸）
4. 摘要压缩是"存储"和"使用"之间的桥梁——将历史压缩为紧凑信息，同时保持全量可追溯

**Q2（深挖）**：摘要触发为什么不是"每轮都压缩"而是"每隔 $W$ 轮"？

**回答要点**：

1. 每轮压缩：计算成本高（每次调 LLM 做摘要），且连续多轮的摘要高度重叠——浪费 token
2. 隔 $W$ 轮压缩：$W$ 轮的新信息足够 LLM 生成有实质增量的摘要，投入产出比最优
3. 倍增间隔避免"刚压缩完又压缩"——如果 $W=10$，第 10 轮压缩后第 20 轮才再次触发
4. 推理上下文始终包含最近 $W$ 轮原始消息——即使不压缩，LLM 也能看到足够多的近期对话细节

**Q3（实战）**：`trim_messages_to_window` 为什么在压缩时也要调用（而不只是在推理时）？

**回答要点**：

1. 压缩输入也需要控制大小——如果不截断，每次压缩的输入消息会越来越多
2. 压缩函数只取最近 $W$ 轮 + 旧摘要——避免压缩输入无限增长
3. 窗口大小 $W$ 与触发间隔一致——确保每次压缩处理的原始消息量相等
4. 不截断的后果：第 40 轮压缩时输入可能是 40 轮原始消息 + 旧摘要 → token 爆炸

**Q4（边界）**：如果用户的单轮回复非常长（如贴了一大段代码），超过窗口的 token 预算怎么办？

**回答要点**：

1. 滑动窗口以"轮次"而非"token 数"为单位——单轮极端长度可能撑爆上下文
2. 混合策略：先按轮次截取，再检查 token 总数，超过阈值时对单条超长消息做截断
3. 对代码类超长消息：可提取摘要（"用户贴了一段约 200 行的 Python 代码"）代替原文
4. 最坏情况兜底：Token 计数硬限制 + `tiktoken` 截断——保证传给 LLM 的上下文永远在预算内
