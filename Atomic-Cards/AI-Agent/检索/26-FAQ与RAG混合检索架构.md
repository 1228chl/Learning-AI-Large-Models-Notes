# FAQ 与 RAG 混合检索架构

## 定义

FAQ 与 RAG 混合检索架构将**结构化 FAQ 问答**与**非结构化知识库检索**相结合，构建三级级联问答系统。Redis 拦截已缓存的高频问答结果；失配后 MySQL FAQ 通过 BM25 + Softmax 阈值判断是否命中标准答案；仍未命中时 BERT 分类器区分"通用"与"专业"——通用走 LLM 直接回答，专业走 Milvus RAG 深度检索生成。

## 系统架构

```python
用户查询
    │
    ├─→ Redis 缓存 → 命中? → YES → 返回答案
    │                           │
    │                        NO │
    │                           │
    │                     ┌─────┘
    │                     ↓
    │               jieba 分词
    │                     │
    │               BM25 计算相似度
    │                     │
    │               Softmax 归一化得分
    │                     │
    │              得分 > 0.85 ?
    │                ╱       ╲
    │              YES        NO
    │               │          │
    │         查 MySQL     BERT 意图分类
    │          (FAQ 库)     ↙        ↘
    │               │    通用        专业
    │         写入 Redis   │           │
    │               │  LLM 直接回答  Milvus RAG
    │               │               (向量检索+LLM)
    │               ↓                │
    │           返回答案        检索 top-k
    │                              │
    │                         LLM 生成答案
    │                              │
    └────────────────────────→  返回答案
```

## 核心组件

| 组件 | 技术 | 作用 |
|:----|:-----|:-----|
| **缓存** | Redis | 缓存高置信度 FAQ 问答结果，所有查询先查缓存 |
| **分词** | jieba | 对用户查询进行中文分词（BM25 匹配前预处理） |
| **FAQ 匹配** | BM25 + Softmax | 计算查询与 FAQ 库中问题的文本相似度 |
| **阈值路由** | 阈值 0.85 | Softmax 概率 > 0.85 时走 FAQ 通路 |
| **FAQ 存储** | MySQL | 持久化存储标准问答对（从 CSV 批量导入） |
| **意图分类** | BERT 二分类微调 | FAQ 未匹配后，区分"通用问题"与"专业问题" |
| **知识库** | Milvus | 存储文档切片的嵌入向量，支持语义检索（专业问题用） |
| **生成** | LLM（DashScope/Qwen） | 通用问题直接回答；专业问题基于检索结果生成答案 |

## Softmax 路由原理

BM25 为每个 FAQ 问题计算原始匹配得分后，使用 Softmax 将其归一化为概率分布：

$$
P(q_i) = \frac{e^{s_i}}{\sum_{j=1}^n e^{s_j}}
$$

- $s_i$ ：BM25 对第 $i$ 个文档的原始得分
- $P(q_i)$ ：归一化后的概率（所有文档概率之和为 1）
- **阈值 0.85**：高于此值认为匹配可靠，从 MySQL 返回答案并回写 Redis 缓存

**FAQ 未命中后的二级分流**：若 BM25 最高分低于 0.85，不直接走 RAG，而是先由 BERT 分类器判断——通用问题由 LLM 直接回答，专业问题才进入 Milvus RAG 语义检索。

## ML/DL 应用场景

| 应用场景 | 说明 |
|----------|------|
| 教育领域智能问答 | 高频标准问题（课程介绍、学费）走 FAQ，专业知识（课程内容）走 Milvus RAG，闲聊走 LLM |
| 客服系统 | 常见问题 FAQ 秒级回复 + Redis 缓存加速，特殊问题经分类后走 RAG 或 LLM |
| 企业内部知识库 | 制度流程类有标准答案走 FAQ，技术方案类走 Milvus RAG，生活类咨询走 LLM |

## 面试追问

**Q1（基础）**：为什么需要 FAQ + RAG 双系统架构？只用 RAG 不行吗？
**回答要点**：

1. 架构是四级级联：Redis 缓存 → MySQL FAQ（BM25） → BERT 意图分类 → LLM 直接回答或 Milvus RAG
2. Redis 缓存已验证的高频问答，毫秒级返回；MySQL FAQ 拦截标准高频问题，答案可控无幻觉
3. FAQ 未匹配后 BERT 分类器区分通用和专业：通用由 LLM 直接回答省去向量检索成本，专业才走 Milvus RAG 深度检索
4. 这种设计比纯 RAG 响应更快、成本更低、答案更可控

**Q2（深挖）**：为什么 BM25 的原始得分需要经过 Softmax 归一化才能设阈值？
**回答要点**：

1. BM25 原始得分范围不固定，受文档数和查询长度影响，不同查询间得分不可直接比较
2. Softmax 将得分映射到 0-1 概率值，使阈值 0.85 含义明确，表示 85% 的置信度
3. 归一化后不同查询可复用同一阈值标准，无需为每个查询单独调参

**Q3（实战）**：Redis 缓存策略应如何设计？缓存什么数据？
**回答要点**：

1. 仅缓存高置信度结果（Softmax > 0.85 且 MySQL 有答案），避免缓存低质量匹配
2. key 格式设计为 `answer:{query}`，设置 TTL 过期时间防止缓存膨胀，配合 LRU 淘汰策略
3. 查询流程为先查缓存再查 MySQL，缓存命中直接返回，未命中则查库并回写缓存

**Q4（边界）**：FAQ 数据量从 100 增长到 10 万条，系统哪些环节会成为瓶颈？
**回答要点**：

1. BM25 计算复杂度随文档数线性增长，10 万条全量计算达秒级，需引入倒排索引或 Elasticsearch 优化
2. MySQL 全表扫描不可接受，需给问题字段加全文索引；Redis 缓存需设置 LRU 淘汰冷数据
3. 从业务角度看，高频 FAQ 通常不会达到十万级，实际瓶颈更多集中在 BM25 计算效率
