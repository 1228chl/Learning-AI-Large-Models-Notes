# FAQ 与 RAG 混合检索架构

## 定义

FAQ 与 RAG 混合检索架构将**结构化 FAQ 问答**与**非结构化知识库检索**相结合，构建双通路问答系统。高频、有标准答案的问题通过 BM25 + Softmax 阈值判断从 MySQL FAQ 库直接返回；复杂、开放性问题则路由到 Milvus 向量库进行 RAG 检索生成，兼顾速度与覆盖面。

## 系统架构

```python
用户查询
    │
    ├─→ jieba 分词
    │
    ├─→ BM25 计算相似度
    │       │
    │       └─→ Softmax 归一化得分
    │               │
    │        得分 > 0.85 ?
    │          ╱       ╲
    │        YES        NO
    │         │          │
    │    查 Redis ─→ 缓存命中? ─→ 返回答案
    │         │                           │
    │    查 MySQL (FAQ 库)               │
    │         │                           │
    │    写入 Redis 缓存 ──────────────→ 直接返回
    │
    └─→ RAG 系统（Milvus 向量检索 + LLM 生成）
              │
              └─→ 检索 top-k 片段
                  → LLM 生成答案
                  → 返回答案
```

## 核心组件

| 组件 | 技术 | 作用 |
|:----|:-----|:-----|
| **分词** | jieba | 对用户查询进行中文分词 |
| **FAQ 匹配** | BM25 + Softmax | 计算查询与 FAQ 库中问题的文本相似度 |
| **阈值路由** | 阈值 0.85 | Softmax 概率 > 0.85 时走 FAQ 通路 |
| **FAQ 存储** | MySQL | 持久化存储标准问答对（从 CSV 批量导入） |
| **缓存** | Redis | 缓存高置信度问答结果，减少 MySQL 压力 |
| **知识库** | Milvus | 存储文档切片的嵌入向量，支持语义检索 |
| **生成** | LLM（DashScope/Qwen） | 基于检索结果生成最终答案 |

## Softmax 路由原理

BM25 为每个 FAQ 问题计算原始匹配得分后，使用 Softmax 将其归一化为概率分布：

$$
P(q_i) = \frac{e^{s_i}}{\sum_{j=1}^n e^{s_j}}
$$

- $s_i$ ：BM25 对第 $i$ 个文档的原始得分
- $P(q_i)$ ：归一化后的概率（所有文档概率之和为 1）
- **阈值 0.85**：高于此值认为匹配可靠，可直接返回答案

## ML/DL 应用场景

| 应用场景 | 说明 |
|----------|------|
| 教育领域智能问答 | 高频标准问题（课程介绍、学费）走 FAQ 快速响应，复杂问题走 RAG |
| 客服系统 | 常见问题 FAQ 秒级回复，特殊问题转 RAG 深度检索 |
| 企业内部知识库 | 制度流程类有标准答案走 FAQ，技术方案类走 RAG 生成 |

## 面试追问

**Q1（基础）**：为什么需要 FAQ + RAG 双系统架构？只用 RAG 不行吗？

**回答要点**：FAQ 通路对高频标准问题响应快（毫秒级）、答案可控（无幻觉）；RAG 通路由 LLM 生成，速度慢且可能产生幻觉。双系统架构让简单问题快速回复、复杂问题深入检索，降低 RAG 系统调用压力，节省 API 成本。

**Q2（深挖）**：为什么 BM25 的原始得分需要经过 Softmax 归一化才能设阈值？

**回答要点**：BM25 原始得分范围不固定（受文档数、查询长度影响），不同查询间不可比；Softmax 将得分映射到 0-1 概率值，阈值 0.85 含义明确——85% 置信度；归一化后不同查询的阈值可以复用同一标准，无需为每个查询单独调参。

**Q3（实战）**：Redis 缓存策略应如何设计？缓存什么数据？

**回答要点**：仅缓存高置信度结果（Softmax > 0.85 且 MySQL 有答案），避免缓存低质量匹配；key 格式为 `answer:{query}`；设置过期时间（TTL）防止缓存膨胀，可使用 LRU 淘汰策略；先查缓存再查 MySQL，命中直接返回。

**Q4（边界）**：FAQ 数据量从 100 增长到 10 万条，系统哪些环节会成为瓶颈？

**回答要点**：BM25 计算复杂度随文档数线性增长，10 万条全量计算达秒级，需引入倒排索引优化；MySQL 全表扫描不可接受，需给问题字段加全文索引；Redis 缓存需设置过期策略（LRU）淘汰冷数据；但从业务角度看，高频 FAQ 通常不会达到十万级。
