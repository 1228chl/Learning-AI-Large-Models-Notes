# 系统健康度评估指标

## 定义

系统健康度评估关注 AI Agent 系统的**稳定性、速度和成本**，与 Agent 质量评估（输出是否正确）是正交维度。四个核心指标构成监控面板：P95 延迟（用户体验）、回退率（系统韧性）、Token 消耗（成本控制）、TTFT（首 token 延迟，感知速度）。一句话概括：Agent 输出质量再高，如果 P95 延迟超过 30 秒或回退率超过 15%，用户已经流失了。

$$ \text{系统健康度} = \begin{cases} \text{P95 延迟} & \text{用户会等多久} \\ \text{回退率} & \text{系统多经常降级兜底} \\ \text{Token 消耗} & \text{每次请求花多少钱} \\ \text{TTFT} & \text{用户多久看到第一个字} \end{cases} $$

## 四维健康度指标

| 指标 | 统计口径 | 告警阈值 | 数据源 |
|------|---------|---------|--------|
| P95 延迟 | 95% 的请求在 X 秒内完成 | QA < 8s, Resume < 60s, Exam < 30s, Interview < 5s/轮 | Langfuse 或 HTTP 中间件计时 |
| 回退率 | 触发降级兜底的请求 / 总请求 | < 5% 正常，5-15% 告警，> 15% 危险 | 日志中 fallback 事件计数 |
| Token 消耗 | 单次请求的 input + output tokens | 按 Agent 类型建立基线，超 2× 基准告警 | LLM API 返回的 usage 字段 |
| TTFT | 从请求发出到收到第一个 token 的时间 | 流式请求 < 3s | HTTP 流式计时 |

## 直观理解

> 汽车仪表盘——P95 延迟是"踩油门到车子加速的最差响应时间"（大部分时候 3 秒，但偶尔 10 秒也不行），回退率是"发动机故障切到备用动力的频率"（偶尔切一次没事，天天切就要修），Token 消耗是"百公里油耗"（突然翻倍说明哪里漏了），TTFT 是"从拧钥匙到发动机启动的时间"（用户感知的第一步）。质量评估看"开得好不好"，健康度评估看"车会不会抛锚"。

## 延迟测量与 TTFT

```python
import time
import httpx

async def measure_latency_and_ttft(url: str, payload: dict):
    """测量端到端延迟和首 token 延迟（TTFT）"""
    start_time = time.time()
    first_token_time = None

    async with httpx.AsyncClient(timeout=120.0) as client:
        async with client.stream("POST", url, json=payload) as response:
            async for line in response.aiter_lines():
                if line.startswith("data:"):
                    if first_token_time is None:
                        first_token_time = time.time()  # 记录第一个 token 到达时刻
                    # 累计处理...

    total_time = time.time() - start_time
    ttft = (first_token_time - start_time) if first_token_time else total_time

    return {
        "total_latency": round(total_time, 2),       # 总延迟
        "ttft": round(ttft, 2),                       # 首 token 延迟
        "generation_time": round(total_time - ttft, 2) # 纯生成时间
    }

# P95 计算：将 N 次测试的延迟排序，取第 95 百分位
def p95(latencies: list[float]) -> float:
    return sorted(latencies)[int(len(latencies) * 0.95)]
```

## 回退率与三层兜底的关系

回退率 = 触发第二层（Agent 级降级）的次数 / 总请求数。第一层（自动重试成功）不计入回退率——因为对用户无感知。第三层（系统级兜底）是回退的子集——它意味着连降级都失败了。

```python
# 日志中统计回退事件
# 正常请求：log 中无 fallback 标记
# 触发降级：log 中出现 "degradation triggered for agent=qa"
# 系统兜底：log 中出现 "system_fallback triggered"

fallback_rate = count_degradation + count_system_fallback / total_requests

# 回退率渐进上升 → Prompt 漂移、知识库质量退化、模型版本变更
```

## 三级告警响应矩阵

| 指标 | 正常 | 告警（黄色） | 危险（红色） | 危险响应动作 |
|------|------|------------|------------|------------|
| P95 延迟 | 在阈值内 | 超阈值 1.5× | 超阈值 3× | 检查日志、降级非关键 Agent |
| 回退率 | < 5% | 5-15% | > 15% | 立即检查 LLM API 和 Milvus 状态 |
| Token 消耗 | 在基线 ±20% | 基线 1.5-2× | 基线 > 2× | 检查 Prompt 是否被意外修改 |
| TTFT | < 3s | 3-10s | > 10s | 检查模型预热状态和网络延迟 |

## AI/ML 工程应用场景

| 应用场景 | 关键监控指标 | 监控频率 |
|---------|------------|---------|
| 每次 Prompt 变更后 | P95 延迟 + Token 消耗 | 变更后立即运行 50-100 次测试 |
| 每周健康巡检 | 四个指标全量检查 | 每周一次，留存趋势图 |
| 月度知识库更新后 | Recall@K + P95 延迟 | 更新后立即评估 |
| 大促/峰值流量前 | 压力测试 + P95 延迟 + 回退率 | 提前一周 |

## 面试追问

**Q1（基础）**：系统健康度评估的四个核心指标是什么？各自关注什么？

**回答要点**：

1. P95 延迟：用户的等待体验——95% 请求的完成时间
2. 回退率（Fallback Rate）：系统韧性——多频繁被迫降级兜底
3. Token 消耗：成本控制——每次请求的花费
4. TTFT（Time to First Token）：感知速度——用户多久看到"系统在回复了"的第一个信号
5. 四者正交互补：延迟低但回退率高说明系统在"快速失败"；延迟高但回退率低说明系统在"慢但对"

**Q2（深挖）**：为什么用 P95 延迟而不是平均延迟？P95 和 P50 差距大说明什么？

**回答要点**：

1. 平均值抹平了极端情况——10 次请求中 9 次 1 秒、1 次 60 秒，平均值 6.9 秒（看似还行）
2. P95 = 60 秒——揭示了 5% 的用户正在经历不可接受的等待
3. P95 和 P50 差距大 → 系统有"尾部延迟"问题——少数请求因排队、GC、冷启动等原因严重滞后
4. P50 是"大多数用户的体验"，P95 是"最差可接受的用户体验"——先优化 P95

**Q3（实战）**：早上 9 点系统启动后 P95 延迟飙到 60 秒，10 分钟后恢复正常。根因是什么？怎么修？

**回答要点**：

1. 根因：本地模型（BGE-M3/BGE-Reranker/MiniLM）冷启动——首次推理需要加载模型到内存/显存
2. 验证：检查 TTFT 是否在首次请求时极端高（> 30 秒），后续请求正常
3. 修复：在 FastAPI lifespan 的 `yield` 前调用模型的 `warm_up()`——发送一条假输入触发模型加载
4. 预防：监控首次请求的 TTFT，若超过 10 秒触发预热告警

**Q4（边界）**：如果 Token 消耗翻倍但回退率和延迟都正常，需要排查什么？如何定位？

**回答要点**：

1. Token 消耗翻倍但其他指标正常 → 问题在 LLM 输入/输出侧，而非基础设施
2. 排查清单：Prompt 是否被意外改长（模板多了大段文字）→ 检索返回的文档数是否增多 → messages 历史是否未正确截断
3. 定位方法：用 Langfuse 对比变更前后的单次请求 input/output token 分布
4. 常见根因：摘要压缩失败（每次推理传入全量历史消息）或检索 top-K 被误调高
