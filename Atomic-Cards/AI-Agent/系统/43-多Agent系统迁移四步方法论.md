# 多 Agent 系统迁移四步方法论

## 定义

多 Agent 系统迁移方法论是将传统业务流程或单 LLM 调用转化为多 Agent 协作系统的**结构化拆解流程**，由四个步骤组成：识别（是否有拆解价值）→ 分解（按流程形状拆 Agent）→ 实现（选 LangGraph 范式）→ 组装（编排 + SSE + 懒加载）。这套方法论源于 EduAgent 四大 Agent 的实战经验，可迁移至智能客服、法律审查、代码审查、医疗导诊、投资研究等场景。

核心思想：**业务 = 一组角色，角色 = 一个 Agent + 一种范式，系统 = 编排（路由/串联/并行）把角色组织起来，架在通用地基上**。迁移的关键不是"用哪个模型"，而是"拆几个 Agent、各用什么范式、怎么编排"。

## 四步方法论

$$ \text{业务需求} \xrightarrow{\text{Step 1: 识别}} \text{角色清单} \xrightarrow{\text{Step 2: 分解}} \text{Agent 边界} \xrightarrow{\text{Step 3: 实现}} \text{LangGraph 图} \xrightarrow{\text{Step 4: 组装}} \text{多 Agent 系统} $$

| 步骤 | 核心问题 | 输出 | 关键判断标准 |
|------|---------|------|-------------|
| 1. 识别 | 这件事值得拆成多个 Agent 吗？ | 是否迁移的判定 | 是否有 3 特征：多步骤流程、多个独立关注点、需要私有知识 |
| 2. 分解 | 每件事的"流程形状"是哪一种？ | Agent 边界+角色定义 | 线性 / fan-out / fan-in / 状态机 / HitL |
| 3. 实现 | 为每个 Agent 选哪种 LangGraph 范式？ | 每个 Agent 的图拓扑 | 对照 EduAgent 四种范式选择 |
| 4. 组装 | 多个 Agent 之间是什么关系？怎么编排？ | 系统架构 | 互斥→路由 / 先后依赖→串联 / 可同时→并行 |

## 范式选择对照表

| 工作性质 | 对应的 LangGraph 范式 | EduAgent 出处 | 典型应用 |
|---------|---------------------|-------------|---------|
| 一个输入要从多个维度同时评估 | **并行评审**（fan-out/fan-in） | 简历审查（第 4 章） | 代码 PR 审查、合同多维审查 |
| 需要基于私有知识/文档回答 | **RAG**（检索增强生成） | 智能问答（第 5 章） | 企业知识库、法律条文检索 |
| 关键决策必须人来把关 | **Human-in-the-Loop**（interrupt） | 试卷批改（第 6 章） | 医疗处方确认、退款审批 |
| 有明确阶段的长时间交互 | **状态机+多轮对话** | 模拟面试（第 7 章） | 客服对话、在线教学辅导 |

## 五个迁移场景速查

| 场景 | Agent 拆解 | 范式组合 | 关键设计 |
|------|-----------|---------|---------|
| 智能客服中台 | FAQ-RAG + 订单状态机 + 退换货 HitL + 投诉 HitL | RAG + 状态机 + HitL | 前置规则拦截，路由分发为主 |
| 合同法律审查 | 条款抽取 + 多维审查 + 法条 RAG + 修订建议 + 律师 HitL | 并行评审 + RAG + HitL | 串联 Pipeline，审查内部并行 |
| 研发代码审查 | PR 四维审查 + 代码库 RAG + 测试生成 + 缺陷定位 | 并行评审 + RAG | 审查是 fan-out/fan-in |
| 医疗导诊 | 分诊路由 + 症状问询 + 医学指南 RAG + 医生 HitL | 状态机 + RAG + HitL | 安全规则前置，紧急词直接转急诊 |
| 投资研究 | 数据采集 MCP + 多维分析 + 研报 RAG + 估值建模 + 风控 HitL | 并行评审 + RAG + HitL | MCP 工具调用驱动数据采集 |

## 编排方式判定

```python
# 判断 Agent 之间的关系类型
def determine_orchestration(agents: list[Agent]):
    if all_independent(agents):
        return "路由分发"        # 互斥 → 意图分类后分发到不同 Agent
    if has_sequential_dependency(agents):
        return "串联 Pipeline"   # 先后依赖 → 前序输出注入后序 context
    if can_run_concurrently(agents):
        return "并行 fan-out"    # 可同时 → asyncio.gather 并行
```

## AI/ML 工程应用场景

| 应用场景 | 迁移难点 | 对应方法 |
|---------|---------|---------|
| 传统 SaaS → AI Agent 化 | 不知道从哪开始拆 | 第一步"找角色"：现有系统有哪些不同专业的人在协作？ |
| 单 LLM Prompt → 多 Agent | 害怕过度工程 | 判断标准：是否有 ≥ 2 个独立关注点？流程是否有 ≥ 2 步？ |
| 通用 Agent → 领域 Agent | 私有知识怎么注入 | 第三步：RAG 范式 + 知识库建库 + 混合检索 |
| MVP → 生产系统 | 稳定性不足 | 第四步：公共地基 + 三层兜底 + 统一入口 |

## 面试追问

**Q1（基础）**：多 Agent 系统迁移的四步方法论是什么？每步的核心问题是什么？

**回答要点**：

1. 识别：这件事值得拆成多个 Agent 吗？（3 特征：多步骤、多关注点、需私有知识）
2. 分解：每个角色的工作性质是哪种"流程形状"？（线性/fan-out/状态机/HitL）
3. 实现：每个 Agent 选择哪种 LangGraph 范式？（对照 EduAgent 四种范式）
4. 组装：Agent 之间什么关系？怎么编排？（路由/串联/并行）

**Q2（深挖）**：EduAgent 的四种 LangGraph 范式中，为什么简历审查用并行评审、试卷批改用 HitL、模拟面试用状态机？范式的选择标准是什么？

**回答要点**：

1. 简历审查：6 个维度无依赖关系，可以并行 → fan-out/fan-in 天然匹配
2. 试卷批改：成绩有法律效力，主观题 AI 可能误判 → 需要人工确认 → interrupt() 机制
3. 模拟面试：天然"分阶段"——热身不能问技术题，每个阶段行为不同 → 状态机管理阶段流转
4. 选择标准：看流程的"形状"——可并行用 fan-out，需人把关用 HitL，有阶段用状态机，需私有知识用 RAG

**Q3（实战）**：如果迁移一个业务系统时，某个流程既是"多轮对话"又是"关键决策需人把关"，该怎么选范式？

**回答要点**：

1. Agent 可以混合范式——同一个 Agent 图内可以同时使用状态机管理阶段和 interrupt 做人把关
2. 例如医疗问诊：状态机管理症状收集→检查→诊断→处方各阶段，处方阶段插入 interrupt 等医生确认
3. 实现上：状态机靠 check_stage 条件边，HitL 靠 interrupt 声明，两者在 LangGraph 中不冲突
4. 设计优先级：先定主范式（状态机），再在关键节点插入 HitL 断点

**Q4（边界）**：如果一个流程被拆成 10+ 个 Agent，编排复杂度爆炸，有什么收敛策略？

**回答要点**：

1. "一个角色一个 Agent"是指导原则而非铁律——合并功能内聚的 Agent
2. 收敛策略：看 Agent 间数据流——如果 A 的输出只是 B 的输入且无其他消费者，考虑合并 A 和 B 为一个 Agent 的两个节点
3. 分层编排：先按"领域"分组（如客服域、审批域），组内 Agent 由各域 Orchestrator 管理，顶层只有一个路由分发器
4. EduAgent 的四个 Agent 是一个合适的粒度——再多会陷入编排复杂度，再少会让单个 Agent 职责不清
