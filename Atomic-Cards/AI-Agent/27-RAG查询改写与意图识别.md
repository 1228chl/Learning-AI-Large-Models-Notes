# RAG 查询改写与意图识别

## 定义

查询改写（Query Rewriting）和意图识别（Intent Classification）是 RAG 系统**检索前优化**的关键步骤。意图识别判断用户查询的类型和路由目标；查询改写则在检索前对用户原始问题进行优化，解决信息不完整或噪声问题，从而提升向量检索的命中率。

## 意图识别（Query Classification）

意图分类器决定查询应路由到哪个子系统：

| 意图类别 | 路由目标 | 示例 |
|:--------|:---------|:-----|
| **FAQ 类** | MySQL FAQ（BM25 匹配） | "黑马课程有哪些" |
| **知识库类** | Milvus 向量检索（RAG） | "Transformer 自注意力机制原理" |
| **闲聊类** | 直接 LLM 回复 | "你好"、"谢谢" |

实现方式：可使用 BERT 微调分类模型、LLM Prompt 分类或规则匹配。

## 查询改写技术

查询改写解决两大问题：**信息不完整**和**查询噪声**。

### 应对信息不完整

| 改写策略 | 原理 | 适用场景 |
|:--------|:-----|:---------|
| **历史会话改写** | 结合对话历史补全当前 query 缺失的上下文 | 多轮对话："它的反向传播是怎样的？" → "Transformer 的反向传播是怎样的？" |
| **关键词扩写** | 为核心概念补充同义词或关联术语 | "CNN" → "CNN 卷积神经网络" |
| **伪答案改写** | 先生成初步答案，再以答案为 query 检索 | 提升首次检索不理想时的召回率 |

### 应对噪声问题

| 改写策略 | 原理 | 适用场景 |
|:--------|:-----|:---------|
| **一般去噪改写** | 移除 query 中的无关词、语气词 | "呃，那个 Python 的 GIL 锁具体是啥" → "Python GIL 锁" |
| **关键词改写** | 提取 query 核心关键词，删除冗余 | "我想了解一下关于深度学习中的反向传播算法" → "深度学习 反向传播" |
| **子查询改写** | 将复杂 query 拆分为多个子查询 | "LSTM 和 GRU 的区别以及各自的应用场景" → ["LSTM 原理", "GRU 原理", "LSTM GRU 区别"] |

## 实现示例

```python
def rewrite_query(query: str, history: list = None) -> str:
    """查询改写：补全对话上下文"""
    if not history:
        return query
    # 使用 LLM 补全不完整 query
    prompt = f"""对话历史：{history[-3:]}
当前问题：{query}
请将当前问题补全为完整的独立问题："""
    return llm.invoke(prompt)


def classify_intent(query: str) -> str:
    """意图识别：判断路由目标"""
    prompt = f"""判断查询意图，仅返回：FAQ / KNOWLEDGE / CHAT
查询：{query}"""
    intent = llm.invoke(prompt).strip()
    return intent
```

## ML/DL 应用场景

| 应用场景 | 说明 |
|----------|------|
| 多轮对话 RAG | 历史会话改写解决指代消解，使每轮检索都能基于完整语义 |
| 企业知识库搜索 | 关键词扩写补充同义词，提高长尾查询的检索命中率 |
| 复杂查询分解 | 子查询改写将一个多角度问题拆分为多个针对性检索 |
| 客服系统路由 | 意图识别将退换货/投诉/咨询分派到对应子系统 |

## 面试追问

**Q1（基础）**：为什么 RAG 系统需要查询改写？直接拿用户原始查询检索不行吗？

**回答要点**：用户原始查询常存在指代不明（"它的原理是什么"中"它"无上下文）、口语化噪声（"那个、就是"）、信息缺失（问"Transformer 和 BERT"但未具体说明要比较还是分别解释）等问题，直接检索会导致向量召回不准确，改写后显著提升检索命中率。

**Q2（深挖）**：历史会话改写和子查询改写分别解决什么问题？

**回答要点**：历史会话改写解决**指代消解和上下文补全**，在多轮对话中将"它是怎么训练的"补全为"BERT 是怎么训练的"；子查询改写解决**复合查询**，将"LSTM 和 GRU 的区别及应用"拆为多个子查询分别检索后合并结果，避免单一检索顾此失彼。

**Q3（实战）**：意图识别在 RAG 系统中如何降低延迟和成本？

**回答要点**：简单意图（闲聊问候）直接回复模板，不走检索和 LLM 生成；FAQ 类走 BM25 + MySQL 毫秒级返回，不调 LLM；仅知识库类才走完整的向量检索 + LLM 生成流程。按需路由大幅降低 API 调用量和响应延迟。

**Q4（边界）**：查询改写可能带来什么负面影响？如何设计兜底策略？

**回答要点**：改写可能改变原意（如关键词扩写引入歧义）、增加不必要的计算延迟、或对完整查询做无用改写。兜底策略：保留原始 query 作为检索备选；改写前后得分对比，改写后检索得分低于原 query 时回退；对明显完整的查询跳过改写步骤。
