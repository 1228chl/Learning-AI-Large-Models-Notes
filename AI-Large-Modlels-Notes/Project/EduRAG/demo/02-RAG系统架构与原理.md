## 一、为什么需要RAG？

### 1.1 LLM的两大根本缺陷

#### 缺陷1：知识截止

**底层原因**：LLM的知识来自训练数据，训练有时间截止点。

```
GPT-4训练数据截止: 2023年4月
→ 无法回答: "2024年奥运会在哪里举办？"
→ 无法回答: "最新的Python版本是什么？"
```

#### 缺陷2：幻觉（Hallucination）

**底层原因**：LLM本质是概率预测，会生成"看起来合理"但错误的内容。

```
问: "爱因斯坦什么时候出生的？"
LLM可能回答: "爱因斯坦出生于1889年"  # 错误！实际是1879年
原因: 模型预测"1889"这个token的概率较高，但它没有"验证"的能力
```

### 1.2 解决方案对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **微调** | 用私有数据继续训练，改变模型权重 | 模型内化知识，推理快 | 成本高、周期长、可能灾难性遗忘 |
| **RAG** | 不改变模型，检索相关文档作为上下文 | 成本低、可实时更新、可溯源 | 检索质量影响答案质量 |

**RAG的哲学**：与其让模型"记住"所有知识，不如让模型"查阅"知识库。

## 二、RAG的核心原理

### 2.1 三个阶段的本质

```
索引阶段: 知识 → 结构化存储（让知识可检索）
检索阶段: 问题 → 找到相关知识（找到答案的依据）
生成阶段: 问题 + 知识 → 生成答案（基于依据回答）
```

### 2.2 索引阶段：文档切片的数学原理

**为什么需要切片？**

LLM的上下文窗口有限（如128K token），而一个知识库可能有几百万token。

**切片的权衡**：

| 切片大小 | 优势 | 劣势 |
|----------|------|------|
| 太小（<100字符） | 检索精准 | 丢失上下文，信息不完整 |
| 太大（>2000字符） | 信息完整 | 检索不精准，噪声多 |
| 适中（300-500字符） | 平衡 | 最佳实践 |

**父子块策略的原理**：

```
检索时：用小块（精准匹配）
返回时：用大块（保留上下文）

子块: "Python是一种解释型语言"  → 用于检索
父块: "Python是一种解释型、面向对象的高级编程语言，由Guido van Rossum于1991年发布..."  → 用于生成
```

### 2.3 检索阶段：向量检索的数学原理

**核心思想**：将文本转换为向量，通过向量距离衡量语义相似性。

**余弦相似度的几何意义**：

```
向量A: [1, 0]  → 方向：正右方
向量B: [0, 1]  → 方向：正上方
余弦相似度 = 0  → 完全不相关

向量A: [1, 0]  → 方向：正右方
向量B: [0.9, 0.1]  → 方向：接近正右方
余弦相似度 ≈ 0.99  → 非常相似
```

**为什么用余弦相似度而不是欧氏距离？**

```
文档A: "Python是编程语言"  → 向量 [1, 2, 3]
文档B: "Python是一种编程语言"  → 向量 [2, 4, 6]  # 长度是A的2倍

欧氏距离: √((1-2)² + (2-4)² + (3-6)²) = √14 ≈ 3.74  # 距离大
余弦相似度: cos(A,B) = 1.0  # 完全相同方向，语义一致
```

**结论**：余弦相似度只关注**方向**（语义），不关注**长度**（词数）。

### 2.4 生成阶段：Prompt的组装原理

```python
# RAG的Prompt结构
prompt = f"""
你是一个智能助手，请基于以下上下文回答问题。

上下文: {检索到的文档内容}
问题: {用户的问题}

请基于上下文回答，如果上下文没有相关信息，请说明。
"""
```

**为什么这样设计？**
- 明确告诉模型"基于上下文回答"，约束模型不要编造
- 如果上下文没有相关信息，要求模型说"不知道"，减少幻觉

## 三、EduRAG项目架构

### 3.1 双系统设计的工程原理

```
用户查询
    ↓
┌─────────────────────────────┐
│    问题分类                  │
│    简单问题 → MySQL FAQ      │ 速度快，答案确定
│    复杂问题 → Milvus RAG    │ 灵活，语义理解
└─────────────────────────────┘
```

**为什么这样设计？**

| 问题类型 | 特征 | 最佳方案 |
|----------|------|----------|
| "Python是什么？" | 有标准答案 | BM25精确匹配 |
| "如何优化Python性能？" | 开放性问题 | RAG语义检索 |
| "你好" | 日常问候 | 直接回复 |

### 3.2 查询分类的底层原理

使用BERT进行二分类：**通用知识** vs **专业咨询**

```
BERT原理：
输入: "Python是什么？"
  ↓ Tokenize
[CLS] Python 是 什么 [SEP]
  ↓ BERT编码
[0.12, -0.45, 0.78, ...]  # [CLS]位置的向量
  ↓ 分类头
P(通用知识)=0.1, P(专业咨询)=0.9
  ↓ 取最大
专业咨询 → 走RAG流程
```

### 3.3 四种检索策略的原理

| 策略 | 原理 | 适用场景 |
|------|------|----------|
| **直接检索** | 原始query直接向量化检索 | 意图明确 |
| **HyDE** | 先生成假设答案，用答案检索 | query抽象 |
| **子查询** | 拆分为多个子query分别检索 | 多实体/多方面 |
| **回溯问题** | 简化query后检索 | query复杂 |

**HyDE的数学直觉**：

```
原始query: "人工智能在教育领域的应用"
  ↓ LLM生成假设答案
假设答案: "人工智能在教育领域有智能辅导、自动批改、个性化学习等应用"
  ↓ 向量化
假设答案的向量 与 真实文档的向量 更接近
  ↓ 检索
比直接用query检索效果更好
```

**原因**：假设答案的表述方式与知识库中的文档更相似，向量距离更近。

## 四、文档处理模块

### 4.1 文档加载的底层原理

不同格式的文档需要不同的解析器：

| 格式 | 解析原理 | 挑战 |
|------|----------|------|
| TXT | 直接读取 | 无 |
| PDF | 解析PDF结构，提取文本 | 可能有扫描图片 |
| DOCX | 解析XML结构 | 格式复杂 |
| 图片 | OCR识别文字 | 识别准确率 |

**OCR原理**：Optical Character Recognition，通过图像处理和模式识别技术，将图片中的文字转换为可编辑的文本。

**支持的文件加载器**：

| 文件格式 | 加载器 | 说明 |
|----------|--------|------|
| .txt | TextLoader | 纯文本，直接读取 |
| .pdf | OCRPDFLoader | PDF，支持OCR识别扫描件 |
| .docx | OCRDOCLoader | Word文档，解析XML结构 |
| .ppt/.pptx | OCRPPTLoader | PPT演示文稿 |
| .jpg/.png | OCRIMGLoader | 图片，OCR识别文字 |
| .md | TextLoader + MarkdownTextSplitter | Markdown，保留文档结构 |

### 4.1.1 Markdown特殊处理

```python
from langchain_text_splitters import MarkdownTextSplitter

# Markdown分割器：按标题、代码块等结构切分
markdown_splitter = MarkdownTextSplitter(
    chunk_size=500,
    chunk_overlap=50
)

md_text = """
# Python介绍

Python是一种解释型语言。

## 基本语法

```python
print("Hello World")
```

## 应用领域

- 数据分析
- 机器学习
- Web开发
"""

chunks = markdown_splitter.split_text(md_text)
# 按标题和代码块结构切分，保持语义完整
```

### 4.2 分层切分的工程价值

```
原始文档 (10000字符)
    ↓ 父块分割 (1200字符/块)
父块1, 父块2, ..., 父块10
    ↓ 子块分割 (300字符/块)
父块1-子块1, 父块1-子块2, ..., 父块10-子块4
```

**存储结构**：
```
每个子块存储：
├── id: 唯一标识
├── text: 子块内容 (300字符)
├── dense_vector: 稠密向量 (1024维)
├── sparse_vector: 稀疏向量
├── parent_id: 父块ID
├── parent_content: 父块内容 (1200字符)
└── source: 学科类别
```

**检索时**：
1. 用子块的向量检索（精准）
2. 返回父块的内容（完整上下文）

## 五、混合检索的底层原理

### 5.1 稠密向量 vs 稀疏向量

| 类型 | 表示方式 | 优势 | 劣势 |
|------|----------|------|------|
| **稠密向量** | 低维连续向量 [0.23, -0.15, ...] | 捕捉语义相似性 | 可能丢失关键词 |
| **稀疏向量** | 高维稀疏向量 {1024:0.5, 5123:0.3, ...} | 精确匹配关键词 | 无法理解同义词 |

**示例**：
```
查询: "Python学费"
文档A: "Python课程价格为5000元"  # 语义相关，但没出现"学费"
文档B: "Java学费是6000元"       # 出现了"学费"，但主题不对

稠密向量检索: A得分高 (语义相关)
稀疏向量检索: B得分高 (关键词匹配)
混合检索: 综合两者，选择最佳结果
```

### 5.2 加权融合的数学原理

```python
# WeightedRanker(0.7, 0.3)
# 稀疏向量权重0.7，稠密向量权重0.3

final_score = 0.7 * sparse_score + 0.3 * dense_score
```

**为什么稀疏向量权重更高？**
教育领域问答中，关键词匹配（如"学费"、"课程"）比纯语义理解更重要。

### 5.3 重排序的原理

```
混合检索结果 (top-10)
    ↓ BGE-Reranker
对每个(query, document)对打分
    ↓ 重新排序
top-5 最相关文档
```

**Reranker的原理**：使用更精确的交叉编码器（Cross-Encoder），同时处理query和document，比双塔模型更准确。

## 六、RAG评估的底层原理

### 6.1 四个评估指标的含义

| 指标 | 评估什么 | 数学定义 |
|------|----------|----------|
| **上下文相关性** | 检索到的文档与问题相关吗？ | P(文档相关\|问题) |
| **上下文召回率** | 标准答案在检索结果中吗？ | P(文档被检索\|文档相关) |
| **忠实度** | 答案是基于上下文生成的吗？ | P(答案可由上下文推出) |
| **答案相关性** | 答案回答了问题吗？ | P(答案相关\|问题) |

### 6.2 RAGAS评估流程

```
准备评估数据:
├── question: 用户问题
├── answer: 系统生成的答案
├── contexts: 检索到的文档
└── ground_truths: 标准答案

计算各指标:
1. 上下文相关性: 用LLM判断contexts与question的相关性
2. 上下文召回率: 用LLM判断contexts是否包含ground_truths的信息
3. 忠实度: 用LLM判断answer是否可以从contexts推出
4. 答案相关性: 生成多个假设问题，计算answer与它们的相似度
```

## 七、面试题深度解析

### Q1: 什么是RAG？它解决了LLM的什么问题？

**底层原理**：
- LLM是条件概率模型：$P(回答 | 问题)$
- RAG将其变为：$P(回答 | 问题, 检索到的文档)$
- 通过引入外部知识，约束模型的生成范围，减少幻觉

### Q2: 为什么要做文档切片？

**数学角度**：
- Embedding模型有最大输入长度限制（如512 token）
- LLM上下文窗口有限（如128K token）
- 向量检索的精度随文档长度增加而下降

### Q3: 向量数据库和传统数据库的区别？

**本质区别**：
- 传统数据库：精确匹配（`WHERE name = '张三'`）
- 向量数据库：近似匹配（找到与查询向量最相似的K个向量）

### Q4: 父子块策略的好处？

**检索精度 vs 信息完整性的权衡**：
- 子块小 → 检索精准，但信息不完整
- 父块大 → 信息完整，但检索不精准
- 父子块策略：检索用子块，返回用父块，两者兼得

```
用户查询: "Python学费是多少？"
    ↓
┌─────────────────────────────────────┐
│ 1. 查询分类 (BERT)                   │
│    P(专业咨询)=0.92 → 走RAG流程     │
└─────────────────────────────────────┘
    ↓
┌─────────────────────────────────────┐
│ 2. 策略选择 (LLM)                    │
│    "直接检索" (意图明确)             │
└─────────────────────────────────────┘
    ↓
┌─────────────────────────────────────┐
│ 3. BGE-M3嵌入                       │
│    生成稠密向量 + 稀疏向量           │
└─────────────────────────────────────┘
    ↓
┌─────────────────────────────────────┐
│ 4. 混合检索 (Milvus)                 │
│    WeightedRanker(0.7, 0.3)         │
│    返回top-10子块                    │
└─────────────────────────────────────┘
    ↓
┌─────────────────────────────────────┐
│ 5. 提取父块 (去重)                   │
│    返回top-5父块                     │
└─────────────────────────────────────┘
    ↓
┌─────────────────────────────────────┐
│ 6. 重排序 (BGE-Reranker)             │
│    精排后返回top-3                   │
└─────────────────────────────────────┘
    ↓
┌─────────────────────────────────────┐
│ 7. 组装Prompt                        │
│    上下文 + 对话历史 + 问题          │
└─────────────────────────────────────┘
    ↓
┌─────────────────────────────────────┐
│ 8. LLM生成答案 (流式)                │
│    "Python课程学费为5000元..."       │
└─────────────────────────────────────┘
```

| 知识点 | 底层原理 | 实践要点 |
|--------|----------|----------|
| **RAG核心** | $P(回答\|问题, 文档)$ 约束生成 | 三阶段：索引→检索→生成 |

| **查询分类** | BERT二分类 | 通用知识直接LLM，专业咨询走RAG |
| **检索策略** | HyDE/子查询/回溯 | LLM自动选择 |
| **RAG评估** | RAGAS四指标 | 持续优化检索和生成质量 |
