### ① 系统总览

#### 学习目标

- 三层架构是哪三层？每层包含什么？
- 四种 LangGraph 范式分别是什么？各自解决什么问题？
- 一条请求的完整生命周期？

#### 核心知识点

**一句话概括整个系统**：用户说一句话，系统自动听懂意图、路由到对的 Agent（或几个 Agent 串联）、执行并以流式返回结果，全程有记忆、能降级、可观测。

**三层架构**

```
┌───────────────────────────────────────────────────────┐
│  集成层（第8章）                                       │
│    unified_chat.py  统一入口：前置拦截 + LLM 路由 + SSE  │
│    orchestrator.py  编排器：单Agent直达/多Agent串联     │
│    main.py          应用装配：lifespan + 路由 + MCP     │
└──────────────────────┬────────────────────────────────┘
                       │ 调度
┌──────────────────────▼────────────────────────────────┐
│  Agent层（第4-7章）—— 四个Agent，四种LangGraph范式       │
│    简历审查（并行） QA（RAG） 试卷批改（HitL） 面试（状态机）│
└──────────────────────┬────────────────────────────────┘
                       │ 复用
┌──────────────────────▼────────────────────────────────┐
│  地基层（第3章+第5章公共件）—— 所有Agent共用              │
│    config/logger/exceptions/retry/llm_factory/认证     │
│    memory/MCP/本地模型（reranker/分类器/embedder）       │
└───────────────────────────────────────────────────────┘
```

**四种 LangGraph 范式**

| Agent | 范式 | 核心机制 | 解决的问题 |
|-------|------|---------|-----------|
| 简历审查 | **并行评审** | fan-out 多分支并行 → fan-in 聚合 | 一份输入要从多个维度同时评估 |
| 智能问答 | **RAG** | 检索 → 精排 → 增强生成 | 让 LLM 基于私有知识库回答 |
| 试卷批改 | **Human-in-the-Loop** | interrupt 暂停 → 人工介入 → resume 恢复 | 关键决策需要人来把关 |
| 模拟面试 | **状态机 + SSE** | 阶段流转 + 多轮对话 + 流式输出 | 有明确阶段的长流程交互 |

**一条请求的完整生命周期**（以"什么是 RAG"为例）

```
[unified_chat] 前置拦截未命中 → LLM 路由判为 qa → 推 routing_decision
[orchestrator] 懒加载 QA 图 → @with_retry 包裹调用
[load_memory]  读 MemorySaver 历史（thread_id 定位）+ 摘要
[classify]     意图分类器（MiniLM）判通用/专项
[retrieve]     BGE-M3 嵌入 → Milvus 检索
[rerank]       BGE-Reranker 精排
[generate]     get_llm("qa") 增强生成 → 流式 token
[unified_chat] 透传 progress + token + meta 事件 → SSE 流式返回
```

## 第二梯队：能力迁移

---

### ③ 迁移方法论（四步拆解）

#### 学习目标

- 拿到一个业务需求，如何用四步拆出多 Agent 架构？

#### 核心知识点

**第一步：找"角色"**——问自己，如果交给一个团队做，会有哪些不同专业的人？每个"专业角色"通常对应一个 Agent。

**第二步：定范式**——看工作性质，套 EduAgent 的四种范式：

| 工作性质 | 范式 | EduAgent 出处 |
|---------|------|-------------|
| 一个输入要从多个维度同时评估 | **并行评审** | 简历六维（第 4 章） |
| 需要基于私有知识/文档回答 | **RAG** | QA（第 5 章） |
| 关键决策必须人来把关 | **Human-in-the-Loop** | 试卷批改（第 6 章） |
| 有明确阶段的多轮交互 | **状态机 + 多轮** | 模拟面试（第 7 章） |

**第三步：定编排方式**——互斥 → 路由分发；有先后依赖 → 串联 Pipeline；同时进行 → 并行 fan-out。

**第四步：补地基**——不管什么场景，都需要：取模型（get_llm）、记忆（MemorySaver + thread_id）、容错（with_retry 三层兜底）、统一入口（路由 + SSE）。

> **一句话**：业务 = 一组角色，角色 = 一个 Agent + 一种范式，系统 = 路由/串联/并行把角色编排起来，再架在通用地基上。

**可迁移场景速览**

| 场景 | 核心 Agent 组合 | 主要范式映射 |
|------|-------------|-------------|
| 智能客服中台 | 意图路由 + FAQ RAG + 订单状态机 + 退换货 HitL | 路由 + RAG + 状态机 + HitL |
| 合同法律审查 | 条款拆解 + 多维审查并行 + 法条 RAG + 律师 HitL | 并行 + RAG + HitL |
| 代码审查平台 | PR 审查并行 + 代码库 RAG + 测试生成 HitL | 并行 + RAG + HitL |
| 医疗导诊 | 分诊路由 + 症状问询状态机 + 指南 RAG + 医生 HitL | 路由 + 状态机 + RAG + HitL |
| 智能投研 | 数据采集 + 多维分析并行 + 研报 RAG + 风控 HitL | 并行 + RAG + HitL |

## 第三梯队：面试准备

---

### ④ 面试题集要点（20+ 题）

#### 学习目标

- 面试中常见的 20 个问题，核心要点是什么？

#### 核心知识点

**架构与编排**

| Q | 核心要点 |
|---|---------|
| 多个 Agent 怎么协作？ | Orchestrator handle(request)，单 Agent 直达或 Pipeline 串联 |
| Agent 之间怎么传递上下文？ | 前序 structured_output 以 `{agent}_result` 为 key 注入 context |
| 为什么 Agent 图要懒加载？ | 避免启动时全量加载、浪费资源 |

**意图识别与路由**

| Q | 核心要点 |
|---|---------|
| 路由用 LLM 还是分类模型？ | 跨 Agent 路由用 LLM（频率低、语义差异大）；QA 内部用 MiniLM（频率高） |
| 路由判错怎么办？ | 降级回 qa，不阻断 SSE 流 |

**可靠性与容错**

| Q | 核心要点 |
|---|---------|
| 大模型调用失败怎么办？ | 三层兜底：自动重试 → Agent 降级 → 系统兜底 |
| 怎么保证 API 层总有合法响应？ | handle 最外层 try/except 兜底 |

**记忆与上下文**

| Q | 核心要点 |
|---|---------|
| 长对话怎么办？ | 滑动窗口 `trim_messages_to_window` + 增量摘要压缩 |
| 多个 Agent 的记忆怎么隔离？ | 独立 MemorySaver 实例 + `thread_id` 按会话隔离 |

**结构化输出**

| Q | 核心要点 |
|---|---------|
| 大模型 JSON 不稳定怎么办？ | `with_structured_output(schema, method="function_calling")` 强制约束 |
| 怎么控制 Agent 不输出有害内容？ | MCP 规范工具暴露 + guardrails 输出护栏 |

**RAG 与知识增强**

| Q | 核心要点 |
|---|---------|
| 检索不准怎么提升？ | 稠密+稀疏双向量召回 → Reranker 精排，可加 HyDE/多查询改写 |
| 怎么防止 RAG 幻觉？ | 答案带 sources 可溯源；检索不可用时降级不硬答 |

**成本与性能**

| Q | 核心要点 |
|---|---------|
| Token 成本怎么省？ | 规则前置拦截零 Token、本地 MiniLM 判通用、LLM 实例缓存 |
| 怎么降低延迟？ | SSE 流式 + 模型并行预热 + 图懒加载 |

**人机协作**

| Q | 核心要点 |
|---|---------|
| 关键决策怎么让人介入？ | LangGraph 的 interrupt/resume 实现 HitL |

### ⑤ Langfuse 监控

#### 学习目标

- Langfuse 的三个核心功能？
- 三种接入方式？

#### 核心知识点

**为什么需要 Langfuse**

| 困境 | Langfuse 能力 | 解决方式 |
|------|-------------|---------|
| 账单不透明 | Cost Tracking | 按模型/功能/用户分组统计 Token 和成本 |
| 问题难定位 | Trace | 每次请求的完整调用链（输入/输出/耗时/Token） |
| 迭代无基准 | Dataset + Evaluation | 评测集批量运行 + 指标对比 |

**三种接入方式**

| 方式 | 特点 | 适用场景 |
|------|------|---------|
| LangChain 回调 | 最快，改动最少 | 快速接入 |
| 手动 SDK | 最灵活，精确控制每步 span | 多步骤流程 |
| LangGraph 集成 | 节点级可见 | 调试 Agent 图 |

**问题定位实战**

| 问题 | 定位方法 |
|------|---------|
| RAG 答错 | 看 retrieval span 召回哪些文档 → rerank 排序 → generation context |
| 路由失败 | 过滤 tag=routing_decision 的 trace，看 LLM 路由的输入输出 |
| 高延迟请求 | 按 latency 降序拉取慢 trace，排查最慢的 Span |
