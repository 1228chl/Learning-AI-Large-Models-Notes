### ① 环境与基础设施

#### 学习目标

#### 核心知识点

**基础设施**：PostgreSQL（业务数据）+ Milvus（向量数据）。etcd 和 MinIO 是 Milvus 内部依赖，应用不直接连。

**端口隔离设计**

| 服务 | 对外端口 | 用途 | 应用是否直接连 |
|------|---------|------|---------------|
| PostgreSQL | **5433** | 业务数据 | 是 |
| Milvus | **19531** | 向量数据 | 是 |
| etcd | 不对外 | Milvus 元数据 | 否 |
| MinIO | 不对外 | Milvus 向量文件存储 | 否 |
| FastAPI | **8000** | 主应用 | — |

**Python 环境**：Python 3.11 严格锁定，conda 创建。

**requirements.txt 关键锁定版本**：

- `langchain==1.2.10`、`langchain-core==1.2.16`
- `langgraph==1.0.9`、`langgraph-prebuilt==1.0.8`
- `bcrypt==4.0.1`（新版与 passlib 不兼容）

**.env.local 三个必填项**：`DB_PASSWORD`、`DEEPSEEK_API_KEY`、`JWT_SECRET_KEY`。必须加入 `.gitignore`。

**安全红线**：密钥与代码分离，代码可以公开，密钥只在本地。

**项目目录结构（关键模块）**

```
EduAgent/
```

### ② 数据库设计（11 张表）

#### 学习目标

- 三大贯穿性设计是什么？
- 11 张表的核心用途和关键字段？
- 多租户 tenant_id 设计原理？
- 关键约束和索引策略？

#### 核心知识点

**三大贯穿性设计**

1. **UUID 主键**：`UUID DEFAULT gen_random_uuid()`，全局唯一不怕冲突，前端不暴露自增 ID
2. **多租户 tenant_id**：所有业务表含此字段，按租户逻辑隔离数据，默认值 `tenant_default`
3. **时间戳 + 触发器**：`created_at` + `updated_at`（TIMESTAMPTZ），触发器函数自动维护 `updated_at`

**11 张表核心用途**

| 表名 | 用途 |
|------|------|
| users | 用户信息（含 role/password_hash，bcrypt 加密） |
| knowledge_pending_queue | 知识库待补充问题队列 |
| exams | 试卷基本信息 |
| questions | 试题（含题型/正确答案/分值/知识点标签） |
| scoring_points | 主观题评分要点 |
| exam_submissions | 学生答卷提交（状态流转：submitted→ai_processing→pending_review→reviewed→published） |
| exam_reviews | 逐题批改详情（含 AI 分/教师分/最终分） |
| resume_reviews | 简历审查结果（含 JSONB 字段） |
| interview_questions | 面试题库 |
| interview_sessions | 面试会话（含 thread_id/report/status） |
| qa_sessions | 问答会话 |

**关键约束**：
- `exam_submissions` 有 `UNIQUE (exam_id, student_id)` — 一人一卷只能提交一次
- `exam_reviews` 冗余存储 `question_type` 和 `knowledge_tag` — 避免频繁 JOIN
- 所有表的外键使用 `ON DELETE CASCADE` 级联删除

### ③ 配置、日志与异常体系

#### 学习目标

- `config.py` 的核心设计是什么？`@lru_cache()` 的作用？
- 结构化日志的写法？为什么要压制第三方库日志？
- 异常体系有哪些子类？哪些可重试？

#### 核心知识点

**config.py — 配置中心**

- 继承 `BaseSettings`，自动从 `.env.local` 读取
- `@lru_cache()` 保证全局单例——只创建一次 Settings、只读一次文件
- `@property` 动态拼接 `database_url`，避免在 `.env.local` 存一长串
- `class Config`：`env_file=".env.local"`、`extra="ignore"`、`case_sensitive=False`

**logger.py — 结构化日志**

- 支持 `logger.info("事件", key=value)` 写法
- 压制第三方库噪音：sqlalchemy/httpx/httpcore 提到 WARNING

**exceptions.py — 统一异常体系**

基类 `EduAgentBaseError(Exception)` 带 `agent_type` 和 `details` 上下文。

| 异常类 | 是否可重试 |
|--------|-----------|
| LLMAPIError | 是 |
| MilvusConnectionError | 是 |
| AgentExecutionError | 视情况 |
| PipelineError | 视情况 |
| IntentRouteError | 视情况 |
| FileParseError | 否 |
| InvalidInputError | 否 |
| AuthenticationError | 否 |

### ④ LLM Factory

#### 学习目标

- 为什么需要 LLM Factory？直接在各 Agent 里调 `init_chat_model` 有什么问题？
- 两个核心入口 `get_llm` 和 `get_structured_llm` 的区别？
- 为什么设置 `trust_env=False` 和 `max_retries=0`？

#### 核心知识点

**为什么需要**：避免各 Agent 重复配置 model_provider/base_url/api_key/temperature；统一管控超时、重试、代理。

**两个核心入口**

```python
get_llm(agent_type, temperature=0, streaming=False)       # 普通模型
get_structured_llm(agent_type, output_schema)              # 绑定 Pydantic 结构
```

**关键设计**：
- `trust_env=False`：绕过 Windows 系统代理（否则 DeepSeek 请求失败）
- 缓存键 `cache_key = f"{model}_{temperature}_{streaming}"`，相同参数只创建一次
- `max_retries=0`：模型层不重试，统一由 retry.py 管理
- 所有 Agent 当前全部使用 `deepseek-chat`，扩展性好

> **项目规定**：所有 Agent 必须通过工厂获取模型，**禁止直接调用 `init_chat_model`**。

### ⑤ 三层兜底与重试机制

#### 学习目标

- 三层兜底分别是什么？每层的触发条件和处理方式？
- 可重试异常和不可重试异常的区别？
- 降级函数为什么统一返回字典？

#### 核心知识点

| 层级 | 触发条件 | 处理方式 |
|------|---------|---------|
| **第一层：自动重试** | 网络抖动/LLM 超时 | 最多重试 2 次（间隔 1s/3s），30s 超时保护 |
| **第二层：Agent 级降级** | 重试仍失败 | 退化为简单实现：QA→跳过检索直接答，批改→标记教师复核 |
| **第三层：系统级兜底** | 降级也失败 | 返回友好提示，保证用户始终能收到响应 |

**异常分类**
```python
RETRYABLE_ERRORS = (LLMAPIError, MilvusConnectionError, TimeoutError, ConnectionError)
NON_RETRYABLE_ERRORS = (InvalidInputError, AuthenticationError)
```

**装饰器**：`@with_retry(agent_type="qa")` 三层嵌套函数，5 个降级函数统一返回字典（对接 LangGraph 节点约定）。

### ⑥ 认证与依赖注入

#### 学习目标

- JWT 认证的完整流程？
- bcrypt 密码校验为什么要用 `run_in_executor`？
- `dependencies.py` 提供的两个 FastAPI 依赖？

#### 核心知识点

**JWT 认证流程**

```
① POST /login（用户名+密码）
  → ② 服务端查库、bcrypt 校验密码
    → ③ 签发 JWT Token（含 user_id/role/tenant_id）
      → ④ 后续请求带 Authorization: Bearer <token>
        → ⑤ get_current_user 解码验证 → 拿到用户身份
```

**bcrypt 密码安全**：
- 单向不可逆、自带盐值
- 密码校验是 CPU 密集型（~100ms），必须在异步接口里用 `run_in_executor` 丢到线程池
- 版本兼容坑：`bcrypt>=4.0` 删掉了 `__about__`，需手动注入

**dependencies.py 两个依赖**：

1. `get_db`：yield 型依赖，自动提交/回滚事务，用 `async with` 管理会话生命周期
2. `get_current_user`：`HTTPBearer` 自动解析 Authorization 头，`jwt.decode()` 验证，失败抛 401
