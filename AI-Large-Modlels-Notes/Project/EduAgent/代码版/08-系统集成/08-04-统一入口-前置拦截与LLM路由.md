## 一、为什么需要两层拦截？

如果没有路由拦截，所有用户输入都走 LLM 判断，浪费 Token：

| 用户输入 | 正确路由 | 拦截方式 |
|:---------|:---------|:---------|
| "你好" | 问候模板 | 规则前置拦截（零 Token） |
| "谢谢" | 感谢模板 | 规则前置拦截（零 Token） |
| "你是谁" | 身份模板 | 规则前置拦截（零 Token） |
| "Transformer 原理是什么" | QA Agent | LLM 路由 |
| "帮我看看简历" | Resume Agent | LLM 路由 |
| "我要找工作" | multi_agent | LLM 路由 |

**规则前置拦截**处理问候/感谢/道别/身份/功能五类高度确定场景，零 Token 消耗。**LLM 路由**处理需要理解语义的复杂场景。

## 三、规则前置拦截（第 75~197 行）

### 3.1 去尾标点 + 三组精确关键词

`_pre_filter` 先去掉末尾标点再做精确比对，因此需要一个辅助正则：

```python
# 第 75 行：去掉末尾的标点和空白，让"你好！"归一成"你好"
_STRIP_TAIL_RE = re.compile(r"[\s!！?？。~～,.，。]+$")
```

| 行号 | 代码 | 说明 |
|:-----|:-----|:------|
| 75 | `[\s!！?？。~～,.，。]+$` | 匹配串尾的一个或多个空白/中英文标点 |

三组精确关键词用 `frozenset` 存储（完整内容）：

```python
# 第 78~81 行：问候
_HELLO_KEYWORDS = frozenset([
    "你好", "您好", "hi", "hello", "hey", "哈喽", "嗨",
    "在吗", "在不在", "在线吗", "有人吗",
])

# 第 84~89 行：感谢
_THANKS_KEYWORDS = frozenset([
    "谢谢", "感谢", "多谢", "谢了", "非常感谢", "万分感谢",
    "辛苦了", "辛苦", "麻烦了", "不好意思",
    "太棒了", "太好了", "厉害", "厉害了", "牛", "牛啊", "牛逼",
    "好的好的", "明白了", "懂了", "知道了", "收到",
])

# 第 92~95 行：道别
_BYE_KEYWORDS = frozenset([
    "再见", "拜拜", "拜", "88", "886", "bye", "goodbye", "byebye",
    "下次见", "下次再聊", "先走了", "先撤了", "溜了", "闪了",
])
```

| 类别 | 行号 | 关键词覆盖 | 示例 |
|:-----|:-----|:-----------|:-----|
| 问候 | 78~81 | 通用问候 + 在线询问 | "你好"、"hi"、"在吗" |
| 感谢 | 84~89 | 致谢 + 夸奖 + 确认 | "谢谢"、"辛苦了"、"明白了" |
| 道别 | 92~95 | 标准道别 + 口语化 | "再见"、"bye"、"溜了" |

**为什么用 `frozenset`？** `frozenset` 的 `in` 操作是 O(1) 哈希查找，`list` 是 O(n) 线性扫描。三组加起来约 40 个词，用集合命中判断更快也更简洁。

### 3.2 两组正则关键词

身份询问和功能询问用 `re.compile` 正则匹配（因为表达方式太多变，无法穷举）：

```python
# 第 98~104 行：身份询问（你是谁 / 介绍你自己）
_IDENTITY_RE = re.compile(
    r"(你|您)(是谁|叫什么|的名字|是什么|是.*AI|是.*机器人|是.*助手)"
    r"|介绍.{0,4}(你自己|自己|一下)"
    r"|你是谁"
    r"|你叫(啥|什么名)",
    re.IGNORECASE,
)

# 第 107~114 行：功能询问（你能做什么 / 怎么用）
_CAPABILITY_RE = re.compile(
    r"(你|您)(能|可以|会).{0,6}(做|帮|干)"
    r"|(你|您).{0,4}(功能|用途|能力|特点)"
    r"|怎么(用|使用)(你|您|这个)?"
    r"|(使用说明|帮助菜单|help|usage)"
    r"|你能帮(我|忙)吗",
    re.IGNORECASE,
)
```

| 类别 | 行号 | 正则分支 | 匹配示例 |
|:-----|:-----|:---------|:---------|
| 身份询问 | 98~104 | `你是谁/叫什么/是什么`、`介绍你自己`、`你叫啥` | "你是谁"、"介绍一下自己" |
| 功能询问 | 107~114 | `你能做什么`、`你的功能`、`怎么用`、`help` | "你能帮我吗"、"使用说明" |

**为什么正则用原文 `t` 而非去尾的 `t_lower`？** 关键词比对用归一化后的 `t_lower`（去掉末尾标点），但正则里已经用 `re.IGNORECASE` 处理大小写，且要匹配"你是 什么"这类中间带空格的形态，所以直接用 `t`。

### 3.3 `_pre_filter` 函数（第 169~197 行）

```python
def _pre_filter(text: str) -> str | None:
    t = text.strip()
    t_lower = _STRIP_TAIL_RE.sub("", t.lower())   # 去末尾标点
    if t_lower in _HELLO_KEYWORDS: return _REPLY_HELLO
    if t_lower in _THANKS_KEYWORDS: return _REPLY_THANKS
    if t_lower in _BYE_KEYWORDS: return _REPLY_BYE
    if _IDENTITY_RE.search(t): return _REPLY_IDENTITY     # 正则用原文
    if _CAPABILITY_RE.search(t): return _REPLY_CAPABILITY  # 正则用原文
    return None
```

| 行号 | 逻辑 | 说明 |
|:----:|:-----|:------|
| 174 | `t = text.strip()` | 去首尾空白 |
| 175 | `t_lower = _STRIP_TAIL_RE.sub("", t.lower())` | 转小写 + 去末尾标点 |
| 178~186 | 精确匹配三类 | 问候/感谢/道别 |
| 189~194 | 正则匹配两类 | 身份/功能（用原文） |

**`_STRIP_TAIL_RE`**：`re.compile(r"[\s!！?？。~～,.，。]+$")`——"你好！" → "你好"，"拜拜~" → "拜拜"。

## 四、LLM 路由（第 200~287 行）

### 4.1 路由提示词（第 201~214 行）

```python
_ROUTE_PROMPT = """判断用户需求应路由到哪个功能。

可选功能：
- qa          : 技术知识问答（用户直接提问，不涉及文件上传）
- exam        : 试卷/作业批改（需上传 Word 答卷）
- resume      : 简历审查（需上传 PDF 简历）
- interview   : 模拟面试（用户提到"面试""练习面试"等）
- multi_agent : 综合求职准备（用户同时提到简历 + 面试）
- clarify     : 意图不明确，无法判断，需要追问

严格按以下 JSON 格式返回，不要有其他内容：
{{"label": "功能名", "reason": "一句话说明判断依据"}}

用户输入：{message}"""
```

**6 种路由目标**：

| label | 对应 Agent | 执行模式 |
|:------|:-----------|:---------|
| `qa` | QA | SINGLE |
| `exam` | EXAM | SINGLE |
| `resume` | RESUME | SINGLE |
| `interview` | INTERVIEW | SINGLE |
| `multi_agent` | QA（占位） | PIPELINE |
| `clarify` | QA（占位） | CLARIFY |

### 4.2 label 映射表（第 217~234 行）

```python
_LABEL_TO_AGENT = {"qa": AgentType.QA, "exam": AgentType.EXAM, ...}
_LABEL_TO_MODE = {"qa": ExecutionMode.SINGLE, "multi_agent": ExecutionMode.PIPELINE, ...}
_VALID_LABELS = frozenset(_LABEL_TO_AGENT.keys())
```

**`_VALID_LABELS` 校验**：LLM 可能返回不在列表中的非法 label，校验后降级为 `qa`。

### 4.3 `_llm_route` 函数（第 249~287 行）

`_llm_route` 调一次 LLM 判断用户意图，返回 `_RouteResult`。分三段看：调用 → 校验 → 返回。

#### 4.3.1 调用 LLM + 解析 JSON（第 261~268 行）

```python
async def _llm_route(message: str) -> _RouteResult:
    try:
        llm = get_llm("intent", temperature=0)       # 261 行：取"intent"专用模型，温度 0 求稳定
        resp = await llm.ainvoke([                    # 262 行：调 LLM
            HumanMessage(content=_ROUTE_PROMPT.format(message=message))  # 263 行：嵌入用户消息
        ])
        raw = resp.text.strip()                       # 265 行：取原始文本
        parsed = json.loads(raw)                      # 266 行：解析 LLM 返回的 JSON
        label = parsed.get("label", "qa").strip().lower()    # 267 行：取 label（缺省 qa）
        reason = parsed.get("reason", "LLM 路由判断")        # 268 行：取判断依据
```

| 行号 | 代码 | 说明 |
|:----:|:-----|:------|
| 261 | `get_llm("intent", temperature=0)` | 路由专用模型，配置见第 3 章 `LLMFactory`；`temperature=0` 保证每次同样输入输出稳定 |
| 262~263 | `llm.ainvoke([HumanMessage(...)])` | 把 `_ROUTE_PROMPT` 嵌入用户消息，发给 LLM |
| 265~266 | `json.loads(resp.text.strip())` | LLM 返回的 JSON 字符串 → Python dict |
| 267~268 | `parsed.get("label")` / `parsed.get("reason")` | 提取 label 和 reason，缺省值分别为 `"qa"` 和 `"LLM 路由判断"` |

#### 4.3.2 合法性校验 + 异常降级（第 270~278 行）

```python
        if label not in _VALID_LABELS:               # 270 行：LLM 返回了非法 label
            label = "qa"                               # 271 行：降级 qa
    except Exception as e:                            # 276 行：调用/解析异常
        label  = "qa"                                 # 278 行：降级 qa
        reason = "路由判断异常，默认转入智能问答"
```

| 行号 | 代码 | 说明 |
|:----:|:-----|:------|
| 270~271 | `if label not in _VALID_LABELS: label = "qa"` | LLM 可能返回幻觉 label（如 `"xxx_agent"`），`_VALID_LABELS` 校验 → 降级 qa |
| 276~278 | `except Exception: label = "qa"; reason = "..."` | 网络超时/JSON 解析失败等异常 → 降级 qa |

**两层降级**：LLM 说错话（非法 label）→ 第一层降级；LLM 根本没说话（异常）→ 第二层降级。最差情况永远走 QA。

#### 4.3.3 返回 `_RouteResult`（第 280~287 行）

```python

        label=label,                                  # 282 行：六类之一
        agent_type=_LABEL_TO_AGENT[label],            # 283 行：label → AgentType
        execution_mode=_LABEL_TO_MODE[label],         # 284 行：label → ExecutionMode
        confidence=0.85,                              # 285 行：固定值，仅供前端展示

```

| 行号 | 值 | 说明 |
|:----:|:---|:------|
| 282 | `label=label` | 来自 LLM 的原始 label，或降级后的 `"qa"` |
| 283 | `agent_type=_LABEL_TO_AGENT[label]` | 通过 `_LABEL_TO_AGENT` 映射表转换（见 4.2） |
| 284 | `execution_mode=_LABEL_TO_MODE[label]` | 通过 `_LABEL_TO_MODE` 映射表转换 |
| 285 | `confidence=0.85` | **固定值**——LLM 路由没有置信度概念，0.85 仅供前端 UI 展示 |
| 286 | `reason=reason` | 来自 LLM 的 `reason` 字段，或异常时的兜底文案 |

### 4.4 `_RouteResult` 路由结果（第 239~246 行）

`_llm_route` 返回一个 `_RouteResult` 对象，封装五个字段供后续分发和前端展示用：

```python
@dataclass
class _RouteResult:
    label:          str            # "qa"|"exam"|"resume"|"interview"|"multi_agent"|"clarify"
    agent_type:     AgentType      # 由 label 映射（如 "qa" → AgentType.QA）
    execution_mode: ExecutionMode  # 由 label 映射（如 "multi_agent" → PIPELINE）
    confidence:     float          # LLM 路由固定返回 0.85（无置信度概念，仅供前端展示）
    reason:         str            # 一句话判断依据（来自 LLM 的 reason 字段）
```

| 行号 | 字段 | 类型 | 说明 |
|:----:|:-----|:-----|:------|
| 242 | `label` | `str` | LLM 返回的原始标签，六选一 |
| 243 | `agent_type` | `AgentType` | 由 `_LABEL_TO_AGENT` 映射得到 |
| 244 | `execution_mode` | `ExecutionMode` | 由 `_LABEL_TO_MODE` 映射得到 |
| 245 | `confidence` | `float` | 固定 0.85，仅供前端 UI 展示 |
| 246 | `reason` | `str` | LLM 的 `reason` 字段，展示在路由卡片 |

**为什么用 `@dataclass` 而非 `BaseModel`？** `_RouteResult` 只在 unified_chat 内部使用，不涉及 API 序列化，`@dataclass` 比 `BaseModel` 更轻量，没有 Pydantic 的校验开销。

## 六、`★` 设计亮点总结

`★ Insight ─────────────────────────────────────`
**"规则前置 + LLM 路由"两层拦截，兼顾效率和灵活性**：
- 第一层：规则前置，五类场景用 `frozenset` 精确匹配 + 正则，零 Token
- 第二层：LLM 路由，复杂意图用 LLM 分类
- 问候/感谢/道别等场景高度确定，规则就能 100% 命中
- 这种"规则兜底浅层、LLM 处理模糊"的设计，在成本和准确率之间取得平衡
`─────────────────────────────────────────────────`

`★ Insight ─────────────────────────────────────`
**`get_llm("intent")` 路由专用模型**：
- 路由任务用 `"intent"` 配置的模型，独立于 QA 的 `"qa"` 和面试的 `"interview"`
- 不同任务可以用不同模型（如路由用更便宜的模型）
- 这是"按任务选择模型"而非"按 Agent 选择模型"的设计
`─────────────────────────────────────────────────`

`★ Insight ─────────────────────────────────────`
**`_VALID_LABELS` 校验 + 异常降级 = 两层安全兜底**：
- LLM 可能返回非法 label（如幻觉"xxx_agent"）→ `_VALID_LABELS` 校验降级 qa
- LLM 调用可能异常（网络超时）→ `try/except` 降级 qa
- 两层兜底确保路由永远不崩溃——最差情况是默认走 QA
