## 一、`api/router.py`：六个 router 聚合

每个功能模块（认证、问答、批改、简历、面试、统一入口）各自定义了一个 `APIRouter`。`router.py` 把它们**带前缀聚合**成一个总路由 `api_router`，再由 `main.py` 统一挂到 `/api/v1` 下。

```python
# router.py 第 1~15 行
from backend.api.v1 import auth, qa, exam, resume, interview, unified_chat

api_router = APIRouter()

api_router.include_router(auth.router,          prefix="/auth",      tags=["认证"])
api_router.include_router(unified_chat.router,  prefix="/chat",      tags=["AI助手"])
api_router.include_router(qa.router,            prefix="/qa",        tags=["智能问答"])
api_router.include_router(exam.router,          prefix="/exam",      tags=["试卷批改"])
api_router.include_router(resume.router,        prefix="/resume",    tags=["简历审查"])
api_router.include_router(interview.router,     prefix="/interview", tags=["模拟面试"])
```

| 路由 | 前缀 | 标签 | 对应章节 |
|:-----|:-----|:-----|:---------|
| `auth` | `/auth` | 认证 | 第 3 章 |
| `unified_chat` | `/chat` | AI 助手 | 第 8 章 |
| `qa` | `/qa` | 智能问答 | 第 5 章 |
| `exam` | `/exam` | 试卷批改 | 第 6 章 |
| `resume` | `/resume` | 简历审查 | 第 4 章 |
| `interview` | `/interview` | 模拟面试 | 第 7 章 |

**`tags` 的作用**：Swagger UI 中按标签分组显示接口，方便调试。

## 二、`main.py`：应用装配

### 2.1 Windows 平台适配（第 8~13 行）

```python
if sys.platform == "win32":
    _conda_base_lib_bin = os.path.normpath(
        os.path.join(os.path.dirname(sys.executable), "..", "..", "Library", "bin")
    )
    if os.path.isdir(_conda_base_lib_bin):
        os.add_dll_directory(_conda_base_lib_bin)
```

**为什么需要？** Python 的 `lzma` 模块在 Windows 上依赖 `liblzma.dll`，该 DLL 位于 conda 的 `Library/bin` 目录。这段代码把该目录显式加入 DLL 搜索路径。

### 2.2 MCP 子应用（第 28~32 行）

```python
from backend.mcp.knowledge_base_server import mcp as kb_mcp
from backend.mcp.web_search_server import mcp as ws_mcp

_kb_app = kb_mcp.streamable_http_app()
_ws_app = ws_mcp.streamable_http_app()
```

**在 lifespan 定义前创建**：MCP 子应用必须与 lifespan 共享同一实例。如果在 lifespan 内部创建，`mount` 时引用的是另一个实例，导致状态不一致。

### 2.3 生命周期 `lifespan`（第 35~76 行）

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    configure_logging()                                  # ① 结构化日志
    # ① DB Schema 自动迁移
    try:
        from backend.db.migrations import run_migrations
        await run_migrations()
    except Exception as e:
        logger.warning("app.migrations_failed | error=%s", e)

    # ② 并行预热三个本地模型
    try:
        from backend.core.reranker import BGEReranker
        from backend.core.query_classifier import QueryClassifier
        from backend.core.knowledge_base import BGEMEmbedder
        loop = asyncio.get_running_loop()
        await asyncio.gather(
            loop.run_in_executor(None, BGEReranker.get_instance),
            loop.run_in_executor(None, QueryClassifier.get_instance),
            loop.run_in_executor(None, BGEMEmbedder.get_instance),
        )
    except Exception as e:
        logger.warning("app.local_models_warmup_failed | error=%s", e)

    # ③ MCP lifespan + yield
    async with _kb_app.router.lifespan_context(_kb_app):
        async with _ws_app.router.lifespan_context(_ws_app):
            logger.info("app.started")
            yield
            logger.info("app.shutting_down")
            from backend.core.llm_factory import LLMFactory
            LLMFactory.clear_cache()
            logger.info("app.shutdown_complete")
```

| 步骤 | 行号 | 操作 | 说明 |
|:----:|:-----|:-----|:------|
| ① | 41~46 | 初始化日志 + DB 迁移 | 迁移失败只告警，不拦启动 |
| ② | 49~63 | 预热三个本地模型 | BGE-Reranker、MiniLM、BGE-M3 并行加载 |
| ③ | 66~75 | MCP lifespan + yield | 关闭时清 LLM 缓存 |

**三个本地模型并行预热**：`BGEReranker`（精排）、`QueryClassifier`（意图分类）、`BGEMEmbedder`（嵌入）首次加载都很慢。用 `asyncio.gather` + `run_in_executor` 并行加载，避免首个请求卡顿。

## 五、边界情况

| 场景 | 表现 | 处理 |
|:-----|:-----|:-----|
| DB 迁移失败 | 抛异常 | `try/except` 只告警，不拦启动 |
| 模型预热失败 | 模型加载异常 | 只告警，首请求时再加载 |
| MCP 子应用启动失败 | lifespan 异常 | `async with` 嵌套，异常向上传播 |
| 未知路由 | 404 | FastAPI 默认处理 |

## 六、`★` 设计亮点总结

`★ Insight ─────────────────────────────────────`
**lifespan 的"失败不阻断"哲学**：
- DB 迁移失败 → 只告警（可能表已存在）
- 模型预热失败 → 只告警（首请求时再加载）
- 这种"尽力而为 + 延迟加载"的设计，保证应用**永远能启动**
- 如果迁移失败就崩溃，那迁移 SQL 写错一次，整个系统就起不来了
`─────────────────────────────────────────────────`

`★ Insight ─────────────────────────────────────`
**main.py 是"装配器"而非"工厂"**：
- 所有业务组件（Agent 图、MCP、模型）都在各自的章节文件里定义
- main.py 只负责把它们组装起来，不包含任何业务逻辑
- 这符合"高内聚低耦合"——每个文件只做一件事
- 新增一个 Agent 时，main.py 只需在 router.py 加一行注册
`─────────────────────────────────────────────────`

`★ Insight ─────────────────────────────────────`
**`prefix="/api/v1"` 统一版本管理**：
- 所有接口在 `/api/v1` 前缀下
- 未来升级到 v2 时，只需改前缀为 `/api/v2`
- 新旧版本可以共存（同时挂 v1 和 v2 的总路由）
- 这是"版本化 API"的标准做法，避免破坏现有客户端
`─────────────────────────────────────────────────`
