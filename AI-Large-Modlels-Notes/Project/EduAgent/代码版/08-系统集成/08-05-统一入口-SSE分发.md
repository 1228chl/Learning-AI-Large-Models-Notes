## 二、`unified_chat_stream`：主端点（第 300~401 行）

理解这个函数的关键，是记住它**返回一个 SSE 流**，而不是直接返回响应。整个函数就是一个"事件生成器"——按顺序 `yield` 出不同类型的事件，前端逐个接收渲染。我们分段拆开看。

### 2.1 骨架：签名 + 事件生成器（第 300~304 行）

```python
@router.post("/stream")                               # 300 行：注册 POST /stream 路由
async def unified_chat_stream(                        # 301 行：SSE 端点
    req: UnifiedChatRequest,                          # 302 行：请求体（session_id + message）
    current_user: dict = Depends(get_current_user),   # 303 行：JWT 认证依赖
):
    async def event_generator():                      # 304 行：内层异步生成器
```

| 行号 | 代码 | 说明 |
|:----:|:-----|:------|
| 300 | `@router.post("/stream")` | 路由装饰器，挂到 `/chat/stream` |
| 301~303 | `async def unified_chat_stream(req, current_user=...)` | 端点签名，`current_user` 由 `get_current_user` 自动注入（第 3 章） |
| 304 | `async def event_generator():` | 内层生成器，后续所有 `yield` 都在这里 |

**为什么包一层生成器？** 因为 SSE 需要"边算边发"。`event_generator` 是异步生成器，每次 `yield` 就向客户端推一个事件，最后用 `EventSourceResponse` 包装它。

### 2.2 Step 0：规则前置拦截（第 306~312 行）

```python
        pre_reply = _pre_filter(req.message)          # 307 行：规则拦截，命中返回模板，否则 None
        if pre_reply is not None:                     # 308 行：命中
            yield _sse({"type": "token", "content": pre_reply})  # 310 行：模板内容当 token 事件推
            yield _sse({"type": "done"})              # 311 行：直接结束
            return                                    # 312 行：不再走 LLM，省 Token
```

| 行号 | 代码 | 说明 |
|:----:|:-----|:------|
| 307 | `pre_reply = _pre_filter(req.message)` | 调 08-04 的 `_pre_filter`，命中返回模板字符串，未命中返回 `None` |
| 308~312 | `if pre_reply is not None: ... return` | 命中 → 把模板当 `token` 推给前端，再推 `done`，`return` 结束整个生成器 |

**设计点**：规则拦截命中时**零 Token**——不调 LLM，模板直接回复，"你好"立即有响应。

### 2.3 Step 1 + Step 2：LLM 路由 + 决策卡片（第 314~320 行）

```python
        decision = await _llm_route(req.message)      # 314 行：LLM 路由，返回 _RouteResult
        yield _sse({                                  # 317 行：推送路由决策卡片
            "type":           "routing_decision",     # 318 行：事件类型
            "agent_type":     decision.agent_type.value,   # 319 行：Agent 英文标识
            "agent_display":  _AGENT_DISPLAY.get(decision.agent_type, ""),  # 中文名
            "confidence":     round(decision.confidence, 4),  # 0.85
            "reason":         decision.reason,        # 判断依据
            "execution_mode": decision.execution_mode.value,  # single / pipeline / clarify
        })
```

| 行号 | 代码 | 说明 |
|:----:|:-----|:------|
| 314 | `decision = await _llm_route(req.message)` | 规则未命中 → 调 08-04 的 `_llm_route`，得到 `_RouteResult` |
| 317~320 | `yield _sse({...routing_decision...})` | 推一个 `routing_decision` 事件，前端据此渲染"已转接到 XX"卡片 |

**为什么先推路由卡片再执行？** 让用户先看到"AI 判断你要做什么"，再看到后续结果，体验更透明。卡片里的 `agent_display` 来自 08-04 的 `_AGENT_DISPLAY` 中文映射。

### 2.4 Step 3：按路由结果四路分发（第 322~345 行）

```python
        label = decision.label                         # 322 行：用 label 决定分支

        if label == "qa":                              # 3a：qa → 流式
            async for event in _stream_qa_agent(req, current_user):  # 透传 QA 的 4 类事件
                yield event

        elif label in ("exam", "resume", "interview"): # 3b：引导跳转
            guidance = _GUIDANCE.get(decision.agent_type, {})
            yield _sse({"type": "guidance", "message": ..., "action_label": ..., "action_url": ...})

        elif label == "multi_agent":                   # 3c：求职全链路计划
            yield _sse({"type": "pipeline_plan", "title": "求职全链路", "steps": [...]})

        else:                                          # 3d：意图不明 → 追问
            yield _sse({"type": "guidance", "message": "您的问题我还不太确定..."})
```

| 分支 | 行号 | label | 动作 | 事件 |
|:----:|:-----|:------|:-----|:-----|
| 3a | 324~326 | `qa` | `_stream_qa_agent` 流式执行，透传事件 | `progress`/`token`/`meta` |
| 3b | 328~331 | `exam`/`resume`/`interview` | 取 `_GUIDANCE` 文案，返回引导卡片 | `guidance` |
| 3c | 333~338 | `multi_agent` | 推送 2 步求职计划列表 | `pipeline_plan` |
| 3d | 341~344 | 其他（`clarify`） | 返回追问提示 | `guidance` |

**为什么三条业务分支（3b）只引导不执行？** `exam`/`resume`/`interview` 需要文件上传或前置选岗位，纯文本对话入口做不了，所以统一入口只返回引导卡片，前端把用户导航到对应功能页。

### 2.5 收尾 + 响应包装（第 348~350 行）

```python
        yield _sse({"type": "done"})                   # 348 行：所有分支最终都推 done
    return EventSourceResponse(event_generator())      # 350 行：用 SSE 包装生成器返回
```

| 行号 | 代码 | 说明 |
|:----:|:-----|:------|
| 348 | `yield _sse({"type": "done"})` | 无论走哪条分支，最终都推 `done` 信号，前端据此关闭流 |
| 350 | `return EventSourceResponse(event_generator())` | 把生成器交给 `sse_starlette`，转成 `text/event-stream` 响应 |

### 2.6 四条分支路径

| 分支 | label | SSE 事件序列 |
|:-----|:------|:-------------|
| ① 规则拦截 | 命中关键词 | `token` + `done` |
| ② QA | `qa` | `routing_decision` → `progress` → `token` → `meta` → `done` |
| ③ 引导跳转 | `exam/resume/interview` | `routing_decision` → `guidance` → `done` |
| ④ Pipeline 计划 | `multi_agent` | `routing_decision` → `pipeline_plan` → `done` |
| ⑤ 追问 | `clarify` | `routing_decision` → `guidance` → `done` |

## 三、`_stream_qa_agent`：QA 流式执行（第 404~463 行）

这个函数把 QA Agent 的 LangGraph 执行转成 SSE 事件流。核心是一个 `astream_events` 循环——边跑图边监听事件，按事件类型和来源节点过滤后转发。我们分段拆开看。

### 3.1 初始化：取图 + 构造 State（第 411~425 行）

```python
async def _stream_qa_agent(req, current_user):
    orchestrator = get_orchestrator()                                 # 412 行：取编排器单例
    graph = orchestrator._get_agent_graph(AgentType.QA)               # 413 行：复用 QA 图（不重复 build）

    thread_id = build_thread_id(current_user["user_id"], req.session_id)  # 415 行：拼检查点 key
    initial_state = {                                                 # 416 行：构造 QA 图输入 State
        "messages":   [HumanMessage(content=req.message)],            # 417 行：用户提问
        "student_id": current_user["user_id"],                        # 418 行：学员 ID
        "tenant_id":  current_user["tenant_id"],                      # 419 行：租户 ID
        "session_id": req.session_id,                                 # 420 行：会话 ID
        "course_id":  None,                                           # 421 行：默认不限定课程
        "query_type": "PRECISE",                                      # 422 行：精确问答模式
    }
    config = {"configurable": {"thread_id": thread_id}}               # 424 行：命中 MemorySaver 检查点
```

| 行号 | 代码 | 说明 |
|:----:|:-----|:------|
| 412~413 | `orchestrator` / `_get_agent_graph(AgentType.QA)` | 复用编排器缓存的 QA 图，不重复 import/build |
| 415 | `build_thread_id(user_id, session_id)` | 拼接检查点 thread_id（第 5 章工具） |
| 416~422 | `initial_state` | 构造 QA 图输入 State，字段与 QAState 对齐 |
| 424 | `config = {"configurable": {"thread_id": thread_id}}` | 让这次执行命中同一个 MemorySaver 检查点，保持会话记忆 |

### 3.2 核心循环：`astream_events` 事件过滤（第 427~455 行）

```python
    answer_mode = None; confidence = 0.0; sources = []                # 428 行：准备收集的元数据

    try:
        async for event in graph.astream_events(initial_state, config=config, version="v2"):
            evt  = event["event"]                                     # 433 行：事件类型
            node = event.get("metadata", {}).get("langgraph_node", "")  # 434 行：来源节点

            # ① 节点开始且在进度表里 → 推 progress（"检索知识库..."等）
            if evt == "on_chain_start" and node in _PROGRESS_LABELS:  # 437 行
                yield _sse({"type": "progress", "stage": _PROGRESS_LABELS[node]})

            # ② 生成节点的 token 流 → 推 token（答案逐字）
            elif evt == "on_chat_model_stream" and node in _GENERATE_NODES:  # 441 行
                chunk = event["data"].get("chunk")
                if chunk and chunk.content:
                    yield _sse({"type": "token", "content": chunk.content})

            # ③ 生成节点结束 → 回填元数据（供最后 meta 用）
            elif evt == "on_chain_end" and node in _GENERATE_NODES:  # 447 行
                output = event["data"].get("output", {})
                if output.get("answer_mode"):
                    answer_mode = output["answer_mode"]               # 仅非空才更新，防覆盖
                if output.get("sources"):
                    sources = output["sources"]
                confidence = (output.get("structured_output") or {}).get("confidence", confidence)
```

| 行号 | 事件 | 触发条件 | 说明 |
|:----:|:-----|:---------|:-----|
| 428 | `answer_mode / confidence / sources` | 初始化 | 准备三个变量收集答案元数据 |
| 431 | `astream_events(...)` | 循环 | 流式跑 QA 图，`version="v2"` 输出结构化事件 |
| 433~434 | `evt` / `node` | 每事件 | 事件类型 + 来源节点，用于过滤 |
| 437~439 | `on_chain_start` + 节点在 `_PROGRESS_LABELS` | ① | 节点开始 → 推 `progress` 进度提示 |
| 441~445 | `on_chat_model_stream` + 节点在 `_GENERATE_NODES` | ② | 生成节点 token 流 → 推 `token` 逐字 |
| 447~455 | `on_chain_end` + 节点在 `_GENERATE_NODES` | ③ | 生成结束 → 回填元数据 |

**为什么 `if output.get("answer_mode")` 而非直接赋值？** 防止后续 `on_chain_end` 把已捕获的 `"rag"` 值覆盖成空——只在值非空时更新。

### 3.3 异常处理 + meta 收尾（第 457~464 行）

```python
    except Exception as e:                                            # 457 行：QA 执行异常
        logger.error("unified_chat.qa_stream_error", error=str(e), exc_info=True)
        yield _sse({"type": "error", "message": "问答服务异常，请稍后重试"})  # 459 行
        return                                                       # 460 行：提前结束

    if answer_mode:                                                   # 463 行：答完才推 meta
        yield _sse({"type": "meta", "answer_mode": answer_mode, "confidence": confidence, "sources": sources})
```

| 行号 | 代码 | 说明 |
|:----:|:-----|:------|
| 457 | `except Exception as e:` | 捕获 QA 图执行/流式异常 |
| 458~460 | `logger.error` + `yield error` + `return` | 记日志，推 `error` 事件，提前结束 |
| 463~464 | `if answer_mode:` → `yield meta` | 答完才推 `meta`（含答案模式/来源/置信度） |

### 3.4 四种 SSE 事件

| 事件类型 | 触发条件 | 内容 |
|:---------|:---------|:-----|
| `progress` | `on_chain_start` + 节点在 `_PROGRESS_LABELS` | 进度描述文本 |
| `token` | `on_chat_model_stream` + 节点在 `_GENERATE_NODES` | 逐字 token |
| `meta` | QA 生成完毕 | `answer_mode` / `sources` / `confidence` |
| `error` | 异常 | 错误信息 |

### 3.5 进度标签映射

```python
_PROGRESS_LABELS = {
    "classify_query":        "理解问题中...",
    "load_memory_and_embed": "检索知识库...",
    "retrieve":              "召回相关文档...",
    "rerank":                "精排中...",
    "hyde_generate":         "理解问题中...",
    "multi_query_rewrite":   "改写查询中...",
    "generate_general":      "思考中...",
}

```

**`_GENERATE_NODES`**：QA Agent 的三个生成节点，只有它们的 token 才被流式输出。其他节点只产生 `progress` 事件。

## 五、`pipeline_plan` 与 `_run_pipeline` 的分工

| 概念 | 职责 | 执行时机 |
|:-----|:-----|:---------|
| `pipeline_plan`（SSE 事件） | 推计划给前端，让用户确认 | 路由到 `multi_agent` 时 |
| `_run_pipeline`（Orchestrator） | 实际执行多 Agent 串联 | 用户确认后，通过其他端点触发 |

**`pipeline_plan` 推计划，`_run_pipeline` 执行计划**——两者分工明确，不耦合。

## 七、`★` 设计亮点总结

`★ Insight ─────────────────────────────────────`
**`astream_events` 的精准过滤 + 4 类事件覆盖完整 QA 流程**：
- `progress`：节点级别进度提示（"检索知识库..."）
- `token`：生成节点逐字输出
- `meta`：生成完毕后的元数据（answer_mode / sources / confidence）
- 前端根据事件类型渲染不同 UI：进度条→打字机效果→引用来源
- 这种"事件驱动"的流式架构，比 WebSocket 更简单，比轮询更实时
`─────────────────────────────────────────────────`

`★ Insight ─────────────────────────────────────`
**`pipeline_plan` 推计划，`_run_pipeline` 执行——关注点分离**：
- 统一入口不做执行，只做路由和分发
- 多 Agent 串联的实际执行在 Orchestrator 中
- SSE 端点只推计划，用户确认后走其他路径触发执行
- 这种"路由和执行分离"的设计，让统一入口职责清晰
`─────────────────────────────────────────────────`

`★ Insight ─────────────────────────────────────`
**8 种 SSE 事件类型 = 前端 UI 的 8 种渲染状态**：
- `routing_decision` → 路由卡片
- `progress` → 进度条
- `token` → 打字机效果
- `guidance` → 引导卡片
- `pipeline_plan` → 步骤列表
- `meta` → 引用来源
- `done` → 关闭流式
- `error` → 错误提示
- 每个事件对应一个前端 UI 行为，前后端通过事件类型契约协作
`─────────────────────────────────────────────────`
