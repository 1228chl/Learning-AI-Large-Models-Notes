## 一、为什么需要两个持久化节点？

面试结束时，需要把报告和记忆都写入 DB：

| 节点 | 写入内容 | 时机 |
|:-----|:---------|:-----|
| `save_report_node` | `InterviewReport` + `status=finished` | 面试结束时执行一次 |
| `save_memory_node` | 摘要压缩 + 会话记录 UPSERT | **每轮**都执行 |

`save_report` 只在结束时写一次，`save_memory` 每轮都写（含结束轮）。两者用同一个 `thread_id` 定位会话行。

## 二、`save_report_node`：报告持久化（第 672~701 行）

```python
# nodes.py 第 672~701 行
async def save_report_node(state: InterviewState) -> dict:
    thread_id = build_thread_id(state["student_id"], state["session_id"])
    report    = state.get("report", {})

    async with AsyncSessionLocal() as session:
        try:
            await session.execute(
                text("""
                    UPDATE interview_sessions
                    SET report        = :report,
                        overall_score = :overall_score,
                        status        = 'finished',
                        finished_at   = NOW(),
                        updated_at    = NOW()
                    WHERE thread_id = :thread_id
                """),
                {
                    "report":        json.dumps(report, ensure_ascii=False),
                    "overall_score": report.get("overall_score", 0),
                    "thread_id":     thread_id,
                },
            )
            await session.commit()
            logger.info("save_report.done", thread_id=thread_id)
        except Exception as e:
            await session.rollback()
            logger.error("save_report.db_failed", error=str(e))

    return {}
```

## 三、`save_memory_node`：记忆保存（第 708~753 行）

```python
# nodes.py 第 708~753 行
async def save_memory_node(state: InterviewState) -> dict:
    messages   = state.get("messages", [])
    student_id = state["student_id"]
    session_id = state["session_id"]
    tenant_id  = state["tenant_id"]
    thread_id  = build_thread_id(student_id, session_id)
    summary    = state.get("existing_summary")

    if state.get("should_summarize", False):
        try:
            summary = await compress_to_summary(messages, summary)
        except Exception as e:
            logger.warning("save_memory.compress_failed", error=str(e))

    async with AsyncSessionLocal() as session:
        try:
            await session.execute(
                text("""
                    INSERT INTO interview_sessions
                        (id, tenant_id, student_id, session_id, thread_id,
                         target_position, resume_review_id, summary, status)
                    VALUES
                        (:id, :tenant_id, :student_id, :session_id, :thread_id,
                         :target_position, :resume_review_id, :summary, 'in_progress')
                    ON CONFLICT (thread_id) DO UPDATE
                        SET summary    = EXCLUDED.summary,
                            updated_at = NOW()
                """),
                {...},
            )
            await session.commit()
        except Exception as e:
            await session.rollback()
            logger.warning("save_memory.db_failed", error=str(e))

    return {}
```

### 3.1 摘要压缩触发（第 717~721 行）

```python
if state.get("should_summarize", False):
    summary = await compress_to_summary(messages, summary)
```

`should_summarize` 由 `generate_response_node` 设置，通过 `should_trigger_summary(messages)` 判断（每 10 轮触发一次）。`compress_to_summary` 调用 LLM 压缩历史对话为结构化学员画像摘要。

### 3.2 UPSERT 逻辑

```sql
INSERT INTO interview_sessions (...) VALUES (...)
ON CONFLICT (thread_id) DO UPDATE
    SET summary    = EXCLUDED.summary,
        updated_at = NOW()
```

| 逻辑 | 说明 |
|:-----|:------|
| `INSERT ... ON CONFLICT` | PostgreSQL 的 UPSERT 语法 |
| `thread_id` 是唯一约束 | 同一会话只能有一条记录 |
| 首轮 | INSERT（`start_session` 已在 API 层 INSERT 初始记录） |
| 后续轮 | UPDATE 摘要和时间戳 |

## 六、`★` 设计亮点总结

`★ Insight ─────────────────────────────────────`
**`save_memory` 是两条路径的"汇合点"**：
- 正常对话路径和报告生成路径最终都汇聚到 `save_memory`
- 这样保证"无论走哪条路，记忆都能被保存"
- 避免了为每条路径单独加一条 `save_memory → END` 的重复边
- 这是"最终一致性"的保证——状态先更新，记忆后落库
`─────────────────────────────────────────────────`

`★ Insight ─────────────────────────────────────`
**UPSERT 而非 INSERT 的幂等设计**：
- PostgreSQL 的 `ON CONFLICT (thread_id) DO UPDATE` 在重复执行时不会报错
- 同一会话多次运行（如进程重启后恢复）不会产生重复记录
- 这是"幂等写入"的标准模式——无论执行多少次，结果一致
`─────────────────────────────────────────────────`

`★ Insight ─────────────────────────────────────`
**两级持久化：MemorySaver（内存）→ DB（磁盘）**：
- MemorySaver 存完整 State（快，但进程重启后丢失）
- DB 存摘要（慢，但持久）
- `load_context_node` 从 DB 读摘要恢复上下文，MemorySaver 恢复完整 State
- 这是"内存 + 磁盘"的两级存储策略，兼顾速度和持久性
`─────────────────────────────────────────────────`
