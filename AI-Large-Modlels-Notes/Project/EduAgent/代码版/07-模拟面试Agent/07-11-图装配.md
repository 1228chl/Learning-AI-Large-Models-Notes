## 一、为什么需要循环拓扑？

面试 Agent 的图拓扑与 QA Agent（条件分支）和 Exam Agent（线性链）都不同：

```
Interview Agent：
START → load_context → check_stage ─┬─ generate_report → save_report ─┐
                                    │                                   │
                                    └─ evaluate_answer → generate_response → save_memory → END
                                                                                  ↑
                                                            （下一轮从 check_stage 重新开始）
```

**核心区别**：面试 Agent 不是"一次执行完"的流程，而是**每轮对话执行一次子图**。`check_stage` 是状态机的转换器，决定当前轮走"正常对话"还是"结束收尾"。

## 二、条件路由函数（第 18~26 行）

```python
# graph.py 第 18~26 行
def _route_after_check_stage(state: InterviewState) -> str:
    if state.get("current_stage") == InterviewStage.FINISHED.value:
        return "generate_report"
    return "evaluate_answer"
```

| 行号 | 代码 | 说明 |
|:----:|:-----|:-----|
| 24 | `if state.get("current_stage") == FINISHED.value:` | 判断当前阶段是否为 FINISHED |
| 25 | `return "generate_report"` | 结束路径：生成报告 |
| 26 | `return "evaluate_answer"` | 正常对话路径：评估回答 |

**路由由 `check_stage_node` 的输出来驱动**：`check_stage_node` 把 `current_stage` 设为 `FINISHED` 时，路由到 `generate_report`；否则路由到 `evaluate_answer`。

## 三、图构建（第 29~74 行）

### 3.1 注册 7 个节点（第 41~47 行）

```python
builder.add_node("load_context",      load_context_node)
builder.add_node("check_stage",       check_stage_node)
builder.add_node("evaluate_answer",   evaluate_answer_node)
builder.add_node("generate_response", generate_response_node)

```

| 节点 | 类型 | 职责 |
|:-----|:-----|:-----|
| `load_context` | 初始化 | 首轮加载题库、简历、摘要 |
| `check_stage` | 状态机 | 判断阶段推进/强制结束 |
| `evaluate_answer` | 对话循环 | 评估学员回答质量 |
| `generate_response` | 对话循环 | 生成面试官回应 |
| `generate_report` | 收尾 | 生成五维度评估报告 |
| `save_report` | 收尾 | 报告写入 DB |
| `save_memory` | 公共 | 摘要压缩 + UPSERT 到 DB |

### 3.2 条件边（第 54~61 行）

```python
builder.add_conditional_edges(
    "check_stage",
    _route_after_check_stage,
    {
        "generate_report": "generate_report",
        "evaluate_answer": "evaluate_answer",
    },
)
```

| 参数 | 值 | 说明 |
|:-----|:---|:------|
| `"check_stage"` | 源节点 | 从 `check_stage` 出发 |
| `_route_after_check_stage` | 路由函数 | 读取 `current_stage` 判断方向 |
| 路径映射 | `{路径名 → 目标节点}` | 路由函数返回值必须在映射的键中 |

### 3.3 两条路径的固定边（第 63~70 行）

```python
# 正常对话路径
builder.add_edge("evaluate_answer",   "generate_response")
builder.add_edge("generate_response", "save_memory")
builder.add_edge("save_memory",       END)

# 报告生成路径
builder.add_edge("generate_report",   "save_report")
builder.add_edge("save_report",       "save_memory")
```

**两条路径共享 `save_memory` 节点**：无论走哪条路径，最终都要保存记忆到 DB。

### 3.4 编译图（第 73~74 行）

```python
checkpointer = get_memory_saver("interview")
return builder.compile(checkpointer=checkpointer)
```

**`get_memory_saver("interview")`**：获取 Interview Agent 专用的 MemorySaver 实例。与其他 Agent 的 MemorySaver 隔离，State schema 不同不会冲突。

## 四、每轮执行流程

### 4.1 首轮执行

```
① POST /sessions 创建会话
② API 层构造 initial_state → 调用 _graph.ainvoke(initial_state, config)
③ load_context_node：加载题库、简历，初始化所有字段
④ check_stage_node：WARMUP 阶段，stage_turns=0，不推进
⑤ 路由到 evaluate_answer_node：total_turns=0，跳过评估，返回 ADEQUATE
⑥ generate_response_node：调用 _respond_warmup，生成开场白
⑦ save_memory_node：UPSERT 初始摘要到 interview_sessions
⑧ 返回开场白给前端
```

### 4.2 结束轮次

```
① 学员发送最后一条消息，或达到轮数上限
② check_stage_node：设置 current_stage = FINISHED
③ 路由到 generate_report_node：生成五维度报告
④ save_report_node：报告写入 DB，status = finished
⑤ save_memory_node：保存最终摘要
⑥ 返回结束语 + 报告摘要给前端
```

## 五、与 QA Agent、Exam Agent 的对比

| 维度 | QA Agent | Exam Agent | 模拟面试 Agent |
|:-----|:---------|:-----------|:---------------|
| 节点数 | 10 | 9 | 7 |
| 条件边 | 3 条（5 路分支） | 0 条 | 1 条（2 路分支） |
| 执行方式 | 单次执行 | 单次执行（含 interrupt） | 多轮循环执行 |
| 是否中断 | 否 | 是（teacher_review） | 否 |
| 图复杂度 | 高（路由多） | 低（线性） | 中（循环 + 条件分支） |

**核心区别**：Interview Agent 是唯一一个每轮**从 START 开始重新执行**的 Agent。QA Agent 和 Exam Agent 都是一次 `ainvoke` 从头走到尾，而 Interview Agent 每轮调用 `ainvoke` 只走完一个子图，下一轮再从 START 开始。

## 六、`★` 设计亮点总结

`★ Insight ─────────────────────────────────────`
**循环拓扑是"每轮子图执行"而非"图内循环"**：
- LangGraph 不支持图内的循环边（`generate_response → check_stage` 会形成无限循环）
- 解决方案：每轮调用 `graph.ainvoke()` 只执行一次子图，`save_memory → END` 后本轮结束
- 下一轮调用时，MemorySaver 自动恢复上次的 State，`load_context` 从数据库读取摘要补充上下文
- 这种"外循环"模式每轮都是完整的图执行，不会因为循环次数过多导致上下文爆炸
`─────────────────────────────────────────────────`

`★ Insight ─────────────────────────────────────`
**`check_stage` 是状态机的"心脏"——它决定图的走向**：
- 它读取 `current_stage`、`stage_turn_count`、`total_turn_count` 等状态变量
- 它输出 `current_stage` 的变化（推进到下一阶段或强制结束）
- 条件路由函数 `_route_after_check_stage` 读取 `current_stage` 决定图的走向
- 所以整个图的行为完全由 `check_stage` 的输出来驱动——它同时是"传感器"（读取状态）和"执行器"（改变状态）
`─────────────────────────────────────────────────`

`★ Insight ─────────────────────────────────────`
**`save_memory` 是两条路径的"汇合点"**：
- 正常对话路径和报告生成路径最终都汇聚到 `save_memory`
- 避免了为每条路径单独加一条 `save_memory → END` 的重复边
- 同时也保证了"无论走哪条路，记忆都能被保存"——"最终一致性"保证
`─────────────────────────────────────────────────`
