## 二、`_respond_closing`：反问收尾（第 575~589 行）

```python
# nodes.py 第 575~589 行
async def _respond_closing(state: InterviewState) -> tuple[str, dict]:
    messages    = state.get("messages", [])
    stage_turns = state.get("stage_turn_count", 0)
    position    = state.get("target_position", "工程师")
    system      = _build_system_with_summary(state)

    if stage_turns <= 1:
        prompt = CLOSING_PROMPT["opening"]
    else:
        last_answer = _get_last_student_answer(messages)
        prompt = CLOSING_PROMPT["respond_question"].format(question=last_answer[:300], position=position)

    llm = get_llm("interview", temperature=0.6)
    response = await llm.ainvoke(_build_messages(system, messages, prompt, window=4))
    return _msg_text(response).strip(), {}
```

| 轮数 | 提示词 | 说明 |
|:----:|:-------|:-----|
| `stage_turns <= 1` | `CLOSING_PROMPT["opening"]` | 反问环节开场白 |
| `stage_turns > 1` | `CLOSING_PROMPT["respond_question"]` | 回应学员的具体提问 |

**两种状态**：第一轮是开场白，后续轮次回应学员的具体问题。`stage_turns` 在 `check_stage_node` 推进到 CLOSING 时重置为 0，每次 `evaluate_answer_node` 执行时 +1。

## 四、`★` 设计亮点总结

`★ Insight ─────────────────────────────────────`
**项目追问门槛比技术环节低是"面试策略"的体现**：
- 技术环节：只有 EXCELLENT 才追问（考察深度，不浪费轮次）
- 项目环节：EXCELLENT 或 ADEQUATE 都追问（深挖信息，了解项目细节）
- 理由：技术题有题库，换题成本低；项目题每个项目只有 3 次提问机会，追问越多信息越丰富
- 这是"面试策略"而非"代码逻辑"——业务规则驱动技术实现
`─────────────────────────────────────────────────`

`★ Insight ─────────────────────────────────────`
**`current_question` 在项目环节动态构造 dict**：
- 技术环节的 `current_question` 直接从题库取（固定结构）
- 项目环节的 `current_question` 是动态构造的（含 `project_name`、`tech_stack`）
- 因为项目的"题目"是动态的——每次追问生成不同的内容，但需要关联到同一个项目
- `projects_asked` 列表追踪已深挖的项目，防止重复
- 这种设计让"项目"和"题目"两个概念在 State 中清晰分离
`─────────────────────────────────────────────────`

`★ Insight ─────────────────────────────────────`
**`no_resume` 兜底 = "零简历也能面试"**：
- 学员没有简历时，项目环节不崩溃
- 根据学员已有的回答动态生成问题——"如果让你设计一个 XXX 系统，你会怎么考虑架构？"
- 这是"降级不降体验"的设计——即使没有简历联动，面试体验仍然完整
`─────────────────────────────────────────────────`
