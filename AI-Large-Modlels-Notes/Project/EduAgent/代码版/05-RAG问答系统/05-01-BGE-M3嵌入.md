## 一、类签名与动机

### 1.1 什么是向量嵌入？

计算机无法直接比较两段文字的"语义相似度"——它只能做数值运算。嵌入就是把文字转换成数值向量的过程：

```
"什么是 Spring IOC？"     →  [0.12, -0.34, 0.87, ..., 0.45]   （1024 个数字）
"IOC 容器负责管理对象"   →  [0.11, -0.31, 0.89, ..., 0.43]   （1024 个数字）
```

语义相近的文字，向量方向相近（余弦相似度高）；语义无关的文字，向量方向差异大。

### 1.2 稠密向量 vs 稀疏向量

| 类型 | 形态 | 优点 | 盲区 |
|------|------|------|------|
| 稠密 | `[0.12, -0.34, ...]` 1024 维 | 语义相似，用词不同也能匹配 | 精确关键词不敏感 |
| 稀疏 | `{token_id: weight}` 字典 | 精确匹配关键词 | 不理解语义 |

**两者互补**：稠密找不到的用稀疏找，稀疏找不到的用稠密找。

### 1.3 BGE-M3：一个模型输出两种向量

BGE-M3 是 BAAI 发布的多功能嵌入模型，一次推理同时输出两种向量：

| 输出 | 字段 | 维度 | 用途 |
|------|------|------|------|
| 稠密向量 | `dense_vecs` | 1024 维 | 语义相似度 |
| 稀疏向量 | `lexical_weights` | `{token_id: weight}` | 关键词匹配 |

### 2.4 encode() 批量编码（核心方法）

```python
# knowledge_base.py 第 92~129 行
def encode(self, texts: list[str], batch_size: int = 12) -> tuple[list[list[float]], list[dict]]:
    output = self._model.encode(
        texts, batch_size=batch_size,
        max_length=8192, return_dense=True, return_sparse=True, return_colbert_vecs=False,
    )
    dense_vecs = output["dense_vecs"].tolist()
    sparse_vecs = [
        {int(k): float(v) for k, v in d.items()}
        for d in output["lexical_weights"]
    ]
    return dense_vecs, sparse_vecs
```

## 七、设计亮点

```python
# ★ Insight ─── 稀疏向量类型转换：numpy.float16 → Python float
# 为什么必须做？
#   LangGraph 的 MemorySaver 用 msgpack 序列化 Agent State，
#   msgpack 不支持 numpy.float16，runtime 直接抛 TypeError。
# 为什么在 encode() 层做而不是在调用方做？
#   调用方（build_knowledge_base.py、retrieve）不需要知道序列化细节，
#   类型转换是嵌入层的职责，就应该封装在 encode() 内部。
sparse_vecs = [
    {int(k): float(v) for k, v in d.items()}
    for d in output["lexical_weights"]
]
```

```python
# ★ Insight ─── WeightedRanker(0.7, 0.3) vs RRFRanker 的选择
# RRFRanker（倒数排名融合）：score = Σ 1 / (k + rank_i)
#   只看排名不看原始分数，鲁棒但无法表达"语义比关键词更重要"的业务意图。
# WeightedRanker（加权平均分）：score = w_dense × score_dense + w_sparse × score_sparse
#   可以指定 Dense 和 Sparse 各自的权重比例。
# 本项目选 WeightedRanker(0.7, 0.3)：
#   课程问答以语义性问题为主（"为什么要用 IOC？"），语义检索应该主导；
#   但技术问答里偶尔出现精确的 API 名称、报错信息，稀疏检索不能完全忽视。
#   7:3 在实践中效果较好，可按实际场景调整。
```

```python
# ★ Insight ─── 类变量单例 + 延迟加载
# _client 是类变量，整个进程只创建一次 MilvusClient 连接。
# 不放在 __init__.py 的模块级初始化，而是延迟到第一次实例化时创建，
# 避免 import 时的副作用（非 Milvus 环境会报错）。
```

## 核心思想

```
BGEMEmbedder（单例）          →  dense + sparse 双向量
    │
DocumentChunk（数据类）       →  字段与 Milvus Schema 一一对应
    │
generate_chunk_id（工具函数）  →  MD5 散列，幂等 upsert
    │
KnowledgeBaseClient（客户端）  →  Upsert / Delete / Hybrid Search
```

**BGE-M3 一次推理输出两种向量，实现混合检索。KnowledgeBaseClient 封装了写入和检索的全部 Milvus 操作。**
