## 一、MCP 是什么？

MCP（Model Context Protocol）是 Anthropic 提出的**标准化工具调用协议**，让 AI Agent 通过统一接口调用外部工具。

```
┌──────────────┐     JSON-RPC     ┌──────────────────┐
│  QA Agent    │ ◄──────────────► │  MCP Server      │
│  nodes.py    │                  │  web_search.py   │
│              │  POST /mcp       │  ┌────────────┐  │
│ call_mcp_    │  {"jsonrpc":"2.0",│  │ @mcp.tool()│  │
│ tool()       │   "method":"tools/│  │ web_search│  │
│              │   call",          │  └────────────┘  │
│              │   "params":{...}} │                  │
└──────────────┘                  └──────────────────┘
```

#### ★ Insight ─── 为什么需要遍历 content 列表？

```python
# FastMCP 对 list[dict] 的序列化行为有两种版本：
# 版本A（常见）：每个 dict 单独放进一个 TextContent
#   content = [{"text": "{...}"}, {"text": "{...}"}]
# 版本B（部分版本）：整个列表序列化成一个 TextContent
#   content = [{"text": "[{...}, {...}]"}]
#
# 必须同时处理两种，不能只取 content[0]
for item in content:
    text = item.get("text", "")
    if not text:
        continue
    parsed = json.loads(text)  # 尝试 JSON 解析
    if isinstance(parsed, list):
        return parsed           # 版本B：整个列表，直接返回
    items.append(parsed)        # 版本A：单条结果，追加
```

FastMCP 版本不同导致序列化行为不一致——这段代码兼容两种行为，是生产环境踩坑后的最佳实践。

### 3.2 `list_mcp_tools()` — 列出工具（第 105~118 行）

```python
# backend/mcp/client.py 第 105~118 行
async def list_mcp_tools(server_url: str, timeout: float = 10.0) -> list[dict]:
    """
    列出 MCP Server 提供的所有工具（调试 / 验证用）。
    """
    payload = {"jsonrpc": "2.0", "id": 1, "method": "tools/list", "params": {}}
    headers = {"Content-Type": "application/json", "Accept": "application/json"}
    async with httpx.AsyncClient(timeout=timeout, trust_env=False) as client:
        resp = await client.post(f"{server_url}/mcp", json=payload, headers=headers)
        resp.raise_for_status()
    return resp.json().get("result", {}).get("tools", [])
```

#### 逐行精读

| 行号 | 代码 | 说明 |
|-----|------|------|
| 32 | `@mcp.tool()` | 装饰器，函数签名自动生成 JSON Schema，docstring 作为工具描述 |
| 33~37 | `async def search_knowledge_base(query, tenant_id, course_id=None, top_k=3)` | 4 个参数：查询文本、租户 ID（数据隔离）、课程 ID（可选过滤）、返回数量 |
| 39~58 | 文档字符串 | 描述 hybrid search 流程：BGE-M3 双向量编码 → Milvus hybrid_search → WeightedRanker 融合 → BGE-Reranker 重排 |
| 59~60 | `from backend.core.reranker import retrieve` | 延迟导入（lazy import），避免 Server 启动时加载所有依赖 |
| 69 | `loop = asyncio.get_running_loop()` | 获取当前事件循环 |
| 70~78 | `await loop.run_in_executor(None, lambda: retrieve(...))` | **为什么？** `retrieve()` 内部调用 BGE-M3 编码和 CrossEncoder 推理，都是同步 CPU 密集操作，直接调用会阻塞事件循环；`run_in_executor` 交给线程池运行 |
| 80~85 | `logger.info("kb_mcp.search_done", ...)` | 结构化日志，记录查询前 50 字符、命中数、置信度 |
| 87~96 | `return [{...} for doc in ranked_docs]` | 返回列表，每个元素包含 `content` / `source_name` / `score` / `confidence` / `is_high_confidence` |

#### ★ Insight ─── 为什么 retrieve() 必须用 run_in_executor？

```python
# knowledge_base_server.py 第 64~78 行
# search_knowledge_base 是 async 函数，运行在 asyncio 事件循环中。
# retrieve() 内部做了三件事：
#   1. BGE-M3 编码 query → 768 维向量      ← 同步 CPU 密集
#   2. Milvus hybrid_search（sparse + dense）← 同步 I/O（但 Milvus SDK 是同步的）
#   3. BGE-Reranker 交叉编码重排           ← 同步 CPU 密集
# 直接调用会阻塞事件循环，导致其他并发请求全部卡住。
# 正确做法：run_in_executor 交给线程池，
# 事件循环继续处理其他请求。
loop = asyncio.get_running_loop()
ranked_docs, confidence = await loop.run_in_executor(
    None,
    lambda: retrieve(query=query, tenant_id=tenant_id, course_id=course_id, rerank_top_k=top_k),
)
```

### 5.1 `_search_tavily()` — Tavily 搜索后端（第 26~59 行）

```python
# backend/mcp/web_search_server.py 第 26~59 行
async def _search_tavily(query: str, max_results: int, api_key: str) -> list[dict]:
    """Tavily 搜索（结构化结果，需 API key）"""
    async with httpx.AsyncClient(timeout=15.0) as client:
        resp = await client.post(
            "https://api.tavily.com/search",
            json={
                "api_key":             api_key,
                "query":               query,
                "max_results":         max_results,
                "include_answer":      False,   # 不需要 AI 总结（节约 token）
                "include_raw_content": False,   # 不需要原始内容（snippet 足够）
            },
        )
        resp.raise_for_status()
    return [
        {"title": r.get("title",""), "url": r.get("url",""),
         "snippet": r.get("content","")[:500], "content": r.get("content","")}
        for r in resp.json().get("results", [])
    ]
```

### 5.2 `_search_duckduckgo()` — DuckDuckGo 搜索后端（第 61~85 行）

```python
# backend/mcp/web_search_server.py 第 61~85 行
async def _search_duckduckgo(query: str, max_results: int) -> list[dict]:
    """DuckDuckGo 搜索（免费，无需 API key）"""
    from duckduckgo_search import DDGS

    def _sync_search() -> list[dict]:
        results = []
        with DDGS() as ddgs:
            for r in ddgs.text(query, max_results=max_results):
                results.append({
                    "title": r.get("title",""), "url": r.get("href",""),
                    "snippet": r.get("body","")[:500], "content": r.get("body",""),
                })
        return results

    return await asyncio.to_thread(_sync_search)
```

#### 逐行精读

| 行号 | 代码 | 说明 |
|-----|------|------|
| 61~63 | `async def _search_duckduckgo(query, max_results)` | 不使用 API key，免费 |
| 67 | `from duckduckgo_search import DDGS` | 延迟导入，避免 Server 启动时加载 |
| 69 | `def _sync_search()` | 同步函数，因为 duckduckgo-search 6.x+ 移除了 AsyncDDGS |
| 71~72 | `with DDGS() as ddgs:` | 上下文管理器，自动管理连接 |
| 72 | `ddgs.text(query, max_results=max_results)` | 同步搜索，返回迭代器 |
| 73~78 | `results.append({...})` | 提取 title / url（`href` 字段）/ snippet（`body` 字段） |
| 81 | `return await asyncio.to_thread(_sync_search)` | 同步函数包装进线程池，避免阻塞事件循环 |

#### ★ Insight ─── tavily 和 duckduckgo 返回字段的差异

```python
# Tavily 返回字段        DuckDuckGo 返回字段
# ├── title              ├── title
# ├── url                ├── href    ← 字段名不同！
# ├── content            ├── body    ← 字段名不同！
# └── score (可选)       └── ...
#
# 两个 _search 函数各自处理字段映射，对外统一输出：
# {"title": ..., "url": ..., "snippet": ..., "content": ...}
```

#### ★ Insight ─── 优雅降级设计

```python
# web_search_server.py 第 111~127 行
# 双后端 + 自动降级，不需要 Agent 感知后端选择逻辑：
#
# 有 Tavily Key → Tavily
#                    ├─ 成功 → 返回结果
#                    └─ 失败 → 日志记录 → 降级 DuckDuckGo
#                                  ├─ 成功 → 返回结果
#                                  └─ 失败 → 日志记录 → 返回空列表
#
# 整个降级过程对 Agent 完全透明：
# Agent 只调用 web_search(query)，不关心后端选择。
if settings.tavily_api_key:
    try:
        results = await _search_tavily(query, max_results, settings.tavily_api_key)
        return results
    except Exception as e:
        logger.warning("web_search_mcp.tavily_failed", error=str(e))

try:
    results = await _search_duckduckgo(query, max_results)
    return results
except Exception as e:
    logger.error("web_search_mcp.ddgs_failed", error=str(e))
    return []  # 全部失败时返回空列表，不抛异常
```

## 六、MCP 在 QA Agent 中的使用

```python
# backend/agents/qa/nodes.py 第 XX~XX 行
async def web_search_node(state: QAState) -> dict:
    from backend.mcp.client import call_mcp_tool

    results = await call_mcp_tool(
        server_url=settings.web_search_mcp_url,
        tool_name="web_search",
        arguments={"query": state["original_query"], "max_results": 5},
    )
    return {"web_search_results": results}
```

Agent 节点调用 MCP 工具的流程：

1. `call_mcp_tool(server_url, tool_name, arguments)` → POST JSON-RPC 到 MCP Server
2. MCP Server 的 `@mcp.tool()` 函数执行 → 返回结果
3. `call_mcp_tool` 解析 JSON-RPC 响应 → 返回 Python 对象

## 八、总结

```
MCP 协议 = JSON-RPC 标准化工具调用

三层架构：
                    客户端（client.py）
                       │
    ┌──────────────────┼──────────────────┐
    ▼                  ▼                  ▼
知识库 MCP Server  网页搜索 MCP Server  未来可扩展 MCP Server
(knowledge_base_   (web_search_
 server.py)         server.py)

客户端函数
  ├── call_mcp_tool()    → 调用工具（第 22~103 行）
  └── list_mcp_tools()   → 列出工具（第 105~118 行）

服务端工具
  ├── search_knowledge_base()  → 知识库混合检索（第 32~96 行）
  ├── web_search()             → 网页搜索入口（第 86~127 行）
  │     ├── _search_tavily()       → Tavily 搜索（第 26~59 行）
  │     └── _search_duckduckgo()   → DuckDuckGo 降级（第 61~85 行）
  └── 未来可扩展 ...
```

### ★ Insight ─── 核心设计思想

**MCP 让 Agent 和工具解耦，工具可以独立部署、独立维护。**

- **客户端单向依赖**：`client.py` 只依赖 JSON-RPC 协议，不依赖具体 Server 实现
- **服务端可替换**：`web_search_server.py` 内部替换搜索后端不需要修改客户端
- **可独立部署**：两个 MCP Server 可以跑在不同端口/机器上，Agent 只需配置 URL
- **可独立测试**：每个工具可以单独测试，不需要启动整个 Agent 系统
