# 📖 章节文档制作提示词（通用模板）

> 用途：为 EduAgent 项目任意章节（04 简历 / 05 RAG / 06 试卷 / 07 面试 / 08 集成...）的源文件制作**带精确行号标注**的学习文档。
> 使用方式：按本文档的"制作流程"逐步操作，AI 产出后按"核对清单"检查。
> 版本：v1.0（2026-08-07）

---

## 一、前置准备：读源码，拿行号

在写文档之前，先打开源文件，拿到精确的"行号地图"。

### 1.1 确定源文件

| 课件章节 | 目标源文件 |
|:---------|:-----------|
| 04 简历 Agent | `backend/agents/resume/nodes.py` / `state.py` / `prompts.py` / `graph.py` |
| 05 RAG 问答 | `backend/agents/qa/nodes.py` / `state.py` / `prompts.py` / `graph.py` |
| 06 试卷批改 | `backend/agents/exam/nodes.py` / `state.py` / `prompts.py` / `graph.py` |
| 07 模拟面试 | `backend/agents/interview/nodes.py` / `state.py` / `prompts.py` / `graph.py` |
| HTTP 接口 | `backend/api/v1/resume.py` / `qa.py` / `exam.py` / `interview.py` |
| 核心工具 | `backend/core/logger.py` / `retry.py` / `memory.py` / `exceptions.py` |

### 1.2 运行行号获取命令

```bash
# ① 文件总行数 —— 确认文件规模
wc -l backend/agents/exam/nodes.py

# ② 所有函数/类的行号 —— 拿到每个代码块的起点
grep -n "^def \|^async def \|^class \|^    def \|^    async def " \
    backend/agents/exam/nodes.py
# 输出示例：
# 55:def _sync_extract_text(pdf_path: str) -> dict:
# 93:async def extract_text_node(state: ResumeState) -> dict:
# ...

# ③ 关键变量/判断的行号 —— 定位核心逻辑
grep -n "is_two_column\|midpoint\|run_in_executor" \
    backend/agents/exam/nodes.py
# 输出示例：
# 71:    is_two_column = (
# 98:        result = await loop.run_in_executor(...)
```

### 1.3 阅读源码，理解 5 个要点

读源码时重点关注以下 5 点，边读边记笔记：

```
1. 输入输出：这个函数接收什么参数？返回什么？分别是什么类型？
2. 核心逻辑：函数内部做了什么？处理流程有几个步骤？
3. 边界处理：有哪些 if/else 分支？抛异常吗？怎么处理空值/异常？
4. 外部依赖：调用哪些其他函数？读/写 State 哪些字段？读/写 DB 吗？
5. 设计动机：为什么写这个函数？如果不写会怎样？跟其他方案比有什么优势？
```

## 二、制作流程：逐段产出

按以下步骤，**每完成一步就写一步**，不要跳步。

### 步骤 ①：写文档头部（固定格式）

```markdown
# 标题：反映核心内容
# 如：PDF 文本提取：`_sync_extract_text` 深度解析
# 如：State 与 Prompts 深度解析
# 如：三轨并行-简答题LLM评分深析

> 源文件：`backend/agents/exam/nodes.py`
> 核心函数：`_sync_extract_text`（**第 55~90 行**）
> 配套节点：`extract_text_node`（**第 93~106 行**）
> 对应课件：6.3 Word 文件解析
> 前置依赖：`python-docx`、`asyncio`、`ExamState`
```

### 步骤 ②：写"全文行号速查表"

用表格列出**每一行**的映射，格式：

```markdown
| 行号 | 内容 | 角色 |
|:----:|:-----|:-----|
| 55 | `def _sync_extract_text(pdf_path: str) -> dict:` | 函数定义 |
| 56 | `"""同步 PDF 文本提取..."""` | 文档字符串 |
| 57 | `import fitz` | 延迟导入 PyMuPDF |
| 58 | `doc = fitz.open(pdf_path)` | 打开 PDF |
| ... | ... | ... |
```

**覆盖范围**：被精读的函数（如第 55~90 行）**逐行**列出，其他函数（如前后的 import 区域、其他工具函数）**合并区域**列出。

### 步骤 ③：写"函数签名与定位"

```markdown
## 二、函数签名与定位（第 55~56 行）

```python
# nodes.py 第 55~56 行
def _sync_extract_text(pdf_path: str) -> dict:
    """同步 PDF 文本提取（线程池中运行），处理双栏布局。"""
\```

- **输入**：PDF 文件路径
- **输出**：`{"raw_text": str, "page_count": int}`
- **命名**：下划线前缀 `_sync` 表示"内部同步函数"——不直接暴露给外部调用，而是通过 `extract_text_node` 用线程池包装后调用
- **调用方**：`extract_text_node`（第 93 行）通过 `run_in_executor` 调用
```

### 步骤 ④：写"为什么需要这个"

用 1~2 段 + 一张对比图，说明：

- 这个函数解决什么问题？
- 如果不写这个函数，直接用原始库会有什么问题？
- **对比**：展示"有处理"和"没处理"的结果差异

### 步骤 ⑤：写"逐行精读"（核心，占 60% 篇幅）

把函数拆成若干**逻辑段落**，每段：

```markdown
### 4.X 段落标题（第 X~Y 行）

```python
# nodes.py 第 X~Y 行
代码片段（完整、可运行理解）
\```

| 行号 | 代码 | 说明 |
|:----:|:-----|:-----|
| 68 | `midpoint = page_width / 2` | 计算中线 |
| 69 | `left_blocks = [...]` | `b[0] < midpoint - 20` 判定为左栏块 |
| 70 | `right_blocks = [...]` | `b[0] >= midpoint - 20` 判定为右栏块 |
| 71~74 | `is_two_column = (...)` | 三个条件综合判定 |

**延伸说明**（可选）：
- 这个阈值的经验值来源
- 边界情况（如全空、异常时）的表现
- 设计权衡（为什么选这个方案而不是另一个）
```

**分段原则**：按代码的**自然逻辑段落**切分，而不是按行号平均分。段落之间用空行 或 `---` 分隔。

### 步骤 ⑥：写"调用方式与依赖"

说明这个函数/节点：

- **谁调用它**：上游节点、API 层、还是其他工具函数？
- **依赖哪些 State 字段**：读/写哪些字段？
- **依赖哪些外部资源**：DB 表、LLM 模型、文件系统、第三方库？
- **失败降级**：调用失败时怎么处理？（重试/降级/抛异常）

### 步骤 ⑦：写"★ 设计亮点"

用 `★ Insight ─────────────────────────────────────` 代码块强调 2~3 个关键设计思想：

```markdown
`★ Insight ─────────────────────────────────────`
**这里写核心见解**：
- 为什么这个设计比另一种方案好？
- 这个设计在什么场景下有效 / 无效？
- 如果去掉这个设计，系统会怎么样？
`─────────────────────────────────────────────────`
```

**与"逐行精读"的区别**：
- 精读取细节 + 举例子，亮点是**拔高一层**讲设计思想
- 精读是"这是什么"，亮点是"为什么这样设计"
- 每个亮点 3~5 句话，不要超过 10 句

### 步骤 ⑧：（可选）补充章节

根据需要选择补充：

> 七、与其他方案的对比（表格：方案 vs 优点 vs 缺点）
> 八、边界情况处理（表格：场景 vs 表现）
> 九、性能分析（如有性能敏感的函数）

## 三、提示词正文（可复制给 AI）

以下提示词封装了上述所有要求，可直接复制给 AI 使用：

```
请为 EduAgent 项目的【源文件路径】编写学习文档，覆盖【课件章节号 + 标题】。

## 硬性要求（必须全部满足）

1. **精确行号标注**：文档中每一段代码、每一个函数、每一个关键逻辑块，
   都必须标注其在源文件中的`精确行号`（如 `第 55~90 行`、`第 64~66 行`）。
   不允许只写"函数名"而不写行号，不允许写"大概在中间"这种模糊描述。

2. **行号速查表**：文档开头必须放一张"全文行号速查表"，
   列出行号 → 代码/内容 → 角色的逐行映射，方便读者对照源码。

3. **逐行精读**：对每个代码块，用 `行号 | 代码 | 说明` 三列表格逐行拆解，
   说明每行的作用、为什么这么写、边界情况。

4. **代码块带行号锚点**：每个代码块上方标注 `# 源文件名.py 第 X~Y 行`。

5. **结构完整**：必须包含以下章节（按顺序）：
   - 一、全文行号速查表
   - 二、函数签名与定位（含输入/输出/命名约定的解析）
   - 三、为什么需要这个？（背景与设计动机）
   - 四、逐行精读（核心，按行号分成若干小节）
   - 五、调用方式与依赖（谁调用它、依赖哪些 state/prompt/工具）
   - 六、★ 设计亮点（用 `★ Insight ───` 代码块强调 2~3 个关键设计思想）
   - 七、（可选）与其他方案对比 / 边界情况 / 性能分析

6. **结合源码注释**：优先引用源码中已有的注释，并解释其含义，
   不要凭空编造源码里没有的行为。

7. **语言**：中文，面向想理解代码细节的学员。

## 源文件内容（我会在后续消息中提供）

在收到源码后开始编写，行号以我提供的源码为准。
```

### 5.2 逐行精读表格示例

来源：`04-05-PDF文本提取-sync_extract_text深析.md`

```markdown
### 4.4 双栏判定（第 67~74 行）

```python
# nodes.py 第 67~74 行
page_width = page.rect.width
midpoint   = page_width / 2
left_blocks  = [b for b in text_blocks if b[0] < midpoint - 20]
right_blocks = [b for b in text_blocks if b[0] >= midpoint - 20]
is_two_column = (
    len(left_blocks) >= 2 and len(right_blocks) >= 2
    and len(right_blocks) / max(len(text_blocks), 1) > 0.3
)
\```

| 行号 | 代码 | 说明 |
|:----:|:-----|:-----|
| 67 | `page_width = page.rect.width` | 获取页面宽度 |
| 68 | `midpoint = page_width / 2` | 计算中线 |
| 69 | `left_blocks = [...]` | `b[0] < midpoint - 20` 判定为左栏 |
| 70 | `right_blocks = [...]` | `b[0] >= midpoint - 20` 判定为右栏 |
| 71~74 | `is_two_column = (...)` | 三个条件综合判定 |
```

### 5.3 ★ Insight 示例

```markdown
`★ Insight ─────────────────────────────────────`
**"软阈值判定"比"是否双栏"布尔值更鲁棒**：
- 硬编码 `if number_of_columns == 2:` 需要精确的列数检测，复杂度高
- 软阈值 `left≥2 && right≥2 && right_ratio > 0.3` 不依赖精确列数，而是用三个条件做"投票"
- 效果：面对复杂排版（如左栏有页眉页脚、右栏只有正文）仍能正确判断
- 可调：`20px` 容差和 `0.3` 比例是两个旋钮，遇到极端排版可以微调
`─────────────────────────────────────────────────`
```
