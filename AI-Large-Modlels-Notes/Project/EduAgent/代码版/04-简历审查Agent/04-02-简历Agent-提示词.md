## 〇、为什么需要提示词？

简历审查 Agent 的每个节点都要调用 LLM，而 LLM 的行为完全由**提示词**控制。提示词在这个 Agent 里扮演三个角色：

**① 角色设定**：`SYSTEM_PROMPT` 告诉 LLM"你是一位 IT 职业顾问"，限定回答风格（严格、客观、可操作），避免 LLM 给出模糊夸奖。

**② 任务指令**：每个节点有专属提示词，告诉 LLM 该做什么。如 `EXTRACT_STRUCTURED_PROMPT` 让 LLM 从简历原文提取结构化 JSON，`DIMENSION_REVIEW_PROMPTS` 让 LLM 从六个维度评分。

**③ 输出约束**：提示词约束 LLM 的输出格式，如"只输出 JSON"、"输出 5~15 条问题"、"按评分标准打分"。这保证下游节点能可靠解析 LLM 的输出。

**为什么用 6 组提示词而不是 1 个？** 因为 6 个节点职责不同（提取、评审、诊断、总结），用 1 个大提示词会让上下文混乱、输出格式冲突。每个提示词只做一件事，互不干扰，方便独立调试和修改。

## 一、系统提示

### 签名

```python
# prompts.py 第 4~6 行
SYSTEM_PROMPT = """你是一位经验丰富的 IT 行业职业顾问，专门为应届毕业生和初/中级工程师审查简历。
你的评审严格、客观、可操作，不给出模糊的夸奖，只给出具体的问题定位和修改建议。"""
```

### 动机

定义 LLM 的"人设"，作为 `SystemMessage` 放在每次对话最前。所有下游节点（提取、评审、诊断、总结）共享此上下文，确保 LLM 始终以"职业顾问"的身份作答。

### 逐行精读

| 行号 | 代码 | 说明 |
|------|------|------|
| 4 | `# 系统提示：定义 LLM 的「人设」...` | 注释：说明该常量的语义角色 |
| 5 | `SYSTEM_PROMPT = """...` | 变量名全大写，Python 约定表示模块级常量 |
| 5 | `你是一位经验丰富的 IT 行业职业顾问...` | 角色定义：限定"IT 行业"+"应届/初/中级"范围 |
| 6 | `你的评审严格、客观、可操作...` | 行为准则：三个关键词约束 LLM 输出风格 |

### 依赖关系

- **调用方**：`graph.py` 中所有节点的 `SystemMessage` 参数
- **被引用符号**：无（直接导入）
- **占位符**：无

### 设计亮点

```
★ Insight ─── 人设即约束
将角色限定在"IT 行业"+"应届/初/中级工程师"，排除了以下场景：
- 高级/架构师级别简历（另一套标准）
- 非技术岗位（产品、运营等）
- 通用"你好，有什么可以帮你的"模糊人设
单句交代"严格、客观、可操作"，比写 10 条规则更有效。
```

## 二、结构化提取提示

### 签名

```python
# prompts.py 第 12~22 行
EXTRACT_STRUCTURED_PROMPT = """请从以下简历文本中提取结构化信息。

【简历原文】
{resume_text}

提取要求：
- 完整保留项目描述的原始文字，不要改写或压缩
- 技术栈列表每项单独一个（如 Spring Boot、MySQL，不合并）
- 时间格式统一为 YYYY.MM - YYYY.MM（如写"至今"则保留"至今"）
- 无法提取的字段填空字符串，不要填"未知"或"无"
- 量化亮点：只提取含数字的句子（如"提升30%"、"10万DAU"）"""
```

### 动机

将非结构化的简历文本转为结构化 JSON，供后续评审节点使用。`{resume_text}` 是运行时填充的占位符。

### 逐行精读

| 行号 | 代码 | 说明 |
|------|------|------|
| 12 | `EXTRACT_STRUCTURED_PROMPT = """...` | 字符串常量，Python 三引号保留换行 |
| 14 | `【简历原文】` | 标记块：占位符区域的标题 |
| 15 | `{resume_text}` | 占位符，代码中 `.format(resume_text=...)` 填充 |
| 17 | `提取要求：` | 5 条规则的列表头 |
| 18 | `完整保留项目描述的原始文字` | 规则 1：禁止 LLM 改写/压缩，保证信息不失真 |
| 19 | `技术栈列表每项单独一个` | 规则 2：防止"Java/Spring Boot/MySQL"被合并为一条 |
| 20 | `时间格式统一为 YYYY.MM - YYYY.MM` | 规则 3：标准化时间，兼顾"至今"特例 |
| 21 | `无法提取的字段填空字符串` | 规则 4：填空字符串而非"未知"，避免下游误判 |
| 22 | `量化亮点：只提取含数字的句子` | 规则 5：预筛选量化数据，为评审节点提供输入 |

### 依赖关系

- **调用方**：`extract_structured` 节点
- **占位符**：`{resume_text}`
- **输出格式**：JSON（在 `graph.py` 中通过 `with_structured_output` 约束）

### 设计亮点

```
★ Insight ─── 规则 4 的"填空字符串"策略
如果 LLM 填"未知"或"无"：
  → 下游评审节点会把这些字段当作有效信息处理（LLM 可能误判为"有内容但模糊"）
如果填空字符串 ""：
  → 下游代码用 `if field:` 即可判断"该字段不存在"
  → 避免 LLM 产生"幻觉式"的默认值
```

## 三、六维度评审提示

### 签名

```python
# prompts.py 第 29~132 行
DIMENSION_REVIEW_PROMPTS = {
    "project_depth": """...""",   # 第 31~46 行
    "tech_match":    """...""",   # 第 48~63 行
    "expression":    """...""",   # 第 65~80 行
    "structure":     """...""",   # 第 82~97 行
    "quantification":"""...""",   # 第 99~114 行
    "authenticity":  """...""",   # 第 116~131 行
}
```

### 动机

六个维度共享同一模板结构，但每个维度的评分标准和评审重点不同。字典结构允许按维度键（`dimension_key`）在循环中动态取对应提示，避免重复代码。

### 维度速查子表

| 维度键 | 行号范围 | 名称 | 权重 | 评分标准最高档 |
|--------|----------|------|------|---------------|
| `project_depth` | 31~46 | 项目深度 | 30% | 量化指标 + 技术选型理由 + 个人贡献 |
| `tech_match` | 48~63 | 技术匹配度 | 25% | 技术栈高度匹配 + 掌握程度分级 |
| `expression` | 65~80 | 表达规范性 | 15% | 动词开头 + 逻辑清晰 + 无错别字 |
| `structure` | 82~97 | 简历结构 | 15% | 模块齐全 + 重要内容置顶 |
| `quantification` | 99~114 | 量化程度 | 10% | 绝大多数描述有具体数字 |
| `authenticity` | 116~131 | 描述一致性 | 5% | 技术深度与工作年限高度吻合 |

### 逐行精读（以 `project_depth` 为例，其余维度结构相同）

| 行号 | 代码 | 说明 |
|------|------|------|
| 31 | `"project_depth": """请评审...` | 字典键：小写蛇形命名，与维度配置表一致 |
| 33 | `【评审重点】{focus}` | 占位符 1：动态传入，如"项目是否有量化数据" |
| 36 | `{structured_summary}` | 占位符 2：结构化提取的输出摘要 |
| 39 | `{resume_text}` | 占位符 3：原文（截取前 3000 字，由代码控制） |
| 41 | `评分标准（0-100分）：` | 5 档评分，每档 20 分区间 |
| 42 | `90-100：每个项目都有量化指标...` | 最高档：三项明确要求 |
| 43 | `70-89：大部分项目有量化数据...` | 次高档：放松到"大部分" |
| 44 | `50-69：项目描述偏泛...` | 中档：缺少量化数据 |
| 45 | `30-49：项目描述流水账...` | 低档：看不出技术深度 |
| 46 | `0-29：项目描述极度简陋...` | 最低档：与岗位完全不相关 |

### 六个维度评分标准核心差异

| 维度 | 90-100 分关键特征 | 0-29 分关键特征 |
|------|-------------------|-----------------|
| `project_depth` | 量化指标 + 技术选型理由 + 个人贡献 | 项目描述极度简陋或与岗位完全不相关 |
| `tech_match` | 技术栈高度匹配 + 掌握程度分级 | 几乎无相关技术经验 |
| `expression` | 动词开头 + 逻辑清晰 + 无错别字 | 表达混乱，难以理解 |
| `structure` | 模块齐全 + 重要内容置顶 | 无清晰结构 |
| `quantification` | 绝大多数有具体数字（QPS/DAU/优化比例） | 完全无量化数据 |
| `authenticity` | 技术深度与工作年限高度吻合 | 描述极度空洞或前后矛盾 |

### 依赖关系

- **调用方**：`run_six_dimensions` 节点（循环 6 次，每次取 `DIMENSION_REVIEW_PROMPTS[dimension_key]`）
- **占位符**：`{focus}`、`{structured_summary}`、`{resume_text}`
- **输出格式**：JSON（`with_structured_output` 约束）

### 设计亮点

```
★ Insight ─── 模板复用 + 权重差异化
六个维度使用完全相同的占位符结构，但评分标准完全独立：
- 代码层面：graph.py 中只需一个循环 + 一个 LLM 调用函数
- 提示词层面：每个维度有自己的评分特征，评审更精准
- 权重层面：30% vs 5% 的差异体现在最终加权总分，而非提示词中
  提示词只负责打出"原始分"，权重计算在 Python 代码中完成
```

## 四、问题诊断提示

### 签名

```python
# prompts.py 第 139~162 行
DIAGNOSE_ISSUES_PROMPT = """请基于以下信息，生成简历的逐条问题诊断清单。

【结构化摘要】
{structured_summary}

【简历原文（前3000字）】
{resume_text}

【各维度已发现问题（参考，可扩充）】
{raw_issues}

输出要求：
1. 每条问题必须定位到简历的具体位置（如"项目经历-电商系统-第2句"）
2. 优先级判断标准：
   - high：严重影响 HR 通过率
   - medium：影响竞争力
   - low：锦上添花
3. 时间线推理规则（避免误判）：
   - 项目时间落在某段工作经历区间内，视为正常，不得标记为矛盾
   - 只有当项目时间与所有工作经历区间均无交集时，才提示补充说明
   - 多个项目与同一段工作经历时间重叠，同样正常
4. 建议必须具体可操作（给出修改示例或明确指导）
5. 去除重复问题，合并相似问题
6. 总数控制在 5-15 条"""
```

### 动机

将六维度评审中发现的原始问题（`raw_issues`）合并、去重、排序，生成最终推送给用户的问题诊断清单。核心在于"定位精确"和"优先级合理"。

### 逐行精读

| 行号 | 代码 | 说明 |
|------|------|------|
| 139 | `DIAGNOSE_ISSUES_PROMPT = """...` | 常量定义 |
| 141~142 | `【结构化摘要】` / `{structured_summary}` | 占位符：学员基本信息 |
| 144~145 | `【简历原文】` / `{resume_text}` | 占位符：全文（定位用） |
| 147~148 | `【各维度已发现问题】` / `{raw_issues}` | 占位符：六维度评审的输出 |
| 150 | `输出要求：` | 6 条规则的列表头 |
| 151 | 规则 1：定位到具体位置 | 防止 LLM 输出"项目描述不够详细"这种模糊问题 |
| 152~155 | 规则 2：三级优先级 | high/medium/low 的定义，指导 LLM 分类 |
| 156~159 | 规则 3：时间线推理规则 | 重要的防误判设计，见下方 Insight |
| 160 | 规则 4：建议具体可操作 | 禁止"建议补充更多细节"这类空话 |
| 161 | 规则 5：去重合并 | 六维度输入可能产生重复问题 |
| 162 | 规则 6：总数控制 | 5~15 条，避免太多或太少 |

### 依赖关系

- **调用方**：`diagnose_issues` 节点
- **上游依赖**：`DIMENSION_REVIEW_PROMPTS` 的输出（`raw_issues`）
- **占位符**：`{structured_summary}`、`{resume_text}`、`{raw_issues}`

### 设计亮点

```
★ Insight ─── 时间线推理规则的"防误判"设计
如果没有规则 3，LLM 容易犯两类错误：
  错误 A：看到"项目时间 2023.01-2023.06"和"工作经历 2023.01-2023.12"，
        认为时间重叠是"矛盾"（实际是正常工作项目）
  错误 B：简历上只有一段工作经历，但列了 5 个项目，
        LLM 可能认为"项目过多"（实际是正常的工作内容拆分）

规则 3 的三条子规则，显式告诉 LLM 什么情况是"正常"的，
减少 LLM 的"过度推理"倾向。
```

## 五、Think 提示（先想后答）

### 签名

```python
# prompts.py 第 196~210 行
DIAGNOSE_THINK_PROMPT = """在生成简历问题诊断清单之前，请先进行宏观分析。

【六维度评分汇总】
{dimension_scores_summary}

【已识别的原始问题列表】
{raw_issues}

请分析以下几点（中文，5-8句话）：
1. 这份简历最核心的短板是什么？（最多2个，直接影响竞争力）
2. 各维度问题之间是否存在共同模式或根本原因？
3. 声称的技能与实际项目经历描述之间是否存在明显落差？
4. 哪些问题最影响面试官的第一印象，应列为高优先级？

直接输出分析内容，不加任何前缀标签。"""
```

### 动机

在 `diagnose_issues` 节点中，先调用 LLM 进行一次宏观分析（Think），再将分析结果作为上下文调用 `DIAGNOSE_ISSUES_PROMPT`。这种"先想后答"（Chain-of-Thought）策略能提升问题诊断的深度和一致性。

### 逐行精读

| 行号 | 代码 | 说明 |
|------|------|------|
| 196 | `DIAGNOSE_THINK_PROMPT = """...` | 常量定义 |
| 198~199 | `【六维度评分汇总】` / `{dimension_scores_summary}` | 占位符：各维度的原始分 |
| 201~202 | `【已识别的原始问题列表】` / `{raw_issues}` | 占位符：六维度评审发现的原始问题列表 |
| 204 | `请分析以下几点（中文，5-8句话）：` | 字数限制：5~8 句，防止 LLM 过度生成 |
| 205 | 分析 1：核心短板 | 最多 2 个，直接定位 |
| 206 | 分析 2：共同模式/根本原因 | 跨维度模式识别，发现深层问题 |
| 207 | 分析 3：技能 vs 实际项目落差 | 检查"会"和"做过"的差距 |
| 208 | 分析 4：影响第一印象的问题 | 从面试官视角排序 |
| 210 | `直接输出分析内容，不加任何前缀标签` | 格式约束：纯文本，便于拼接 |

### 依赖关系

- **调用方**：`diagnose_issues` 节点（Think 阶段）
- **上游依赖**：`DIMENSION_REVIEW_PROMPTS` 的输出（评分 + 原始问题）
- **下游依赖**：`DIAGNOSE_ISSUES_PROMPT`（Think 的输出作为上下文传入）

### 设计亮点

```
★ Insight ─── 先想后答的"双阶段"架构
diagnose_issues 节点内部有两步 LLM 调用：
  第 1 步（Think）→ DIAGNOSE_THINK_PROMPT → 宏观分析文本
  第 2 步（Diagnose）→ DIAGNOSE_ISSUES_PROMPT + 宏观分析文本 → 问题清单

优势：
  - Think 阶段的输出被注入到 Diagnose 阶段的上下文中
  - LLM 在生成具体问题清单时，已经"看过全局"
  - 避免"只见树木不见森林"的问题：每个维度单独看都对，但合起来缺洞察
  代价：多一次 LLM 调用 ≈ 增加 ~500 token 的推理成本
```

## 六、整体评价提示

### 签名

```python
# prompts.py 第 170~189 行
GENERATE_SUMMARY_PROMPT = """请为学员生成简历审查的整体评价报告。

【学员信息摘要】
{structured_summary}

【各维度评分】
{scores_summary}

【综合得分】{weighted_score} / 100

【高优先级问题（最需解决的）】
{high_issues}

【目标岗位】{target_position}

生成要求：
1. 亮点：找出简历中真实存在的2-3个优势（有数据支撑更好），语气积极正面
```

| 172~173 | `【学员信息摘要】` / `{structured_summary}` | 占位符：学员基本信息 |
| 175~176 | `【各维度评分】` / `{scores_summary}` | 占位符：六维度逐项评分 |
| 178 | `【综合得分】{weighted_score} / 100` | 占位符：加权总分，由代码计算 |
| 180~181 | `【高优先级问题】` / `{high_issues}` | 占位符：`DIAGNOSE_ISSUES_PROMPT` 的输出 |
| 183 | `【目标岗位】{target_position}` | 占位符：用户输入的意向岗位 |
| 185 | `生成要求：` | 4 条生成规则 |
| 186 | 规则 1：亮点 2-3 个 | 语气积极，有数据支撑更好 |
| 187 | 规则 2：核心改进 2-3 个 | 指向 high 优先级问题，具体可操作 |
| 188 | 规则 3：综合评语 1-2 句 | 客观，不吹不踩 |
| 189 | 规则 4：匹配度评估 | 基于技术栈和经历，1 句话 |

### 依赖关系

- **调用方**：`generate_summary` 节点
- **上游依赖**：`DIMENSION_REVIEW_PROMPTS`、`DIAGNOSE_ISSUES_PROMPT`、`DIAGNOSE_THINK_PROMPT`
- **占位符**：`{structured_summary}`、`{scores_summary}`、`{weighted_score}`、`{high_issues}`、`{target_position}`

### 设计亮点

```
★ Insight ─── 生成要求中的"语气平衡"设计
规则 1（亮点）+ 规则 3（综合评语）+ 规则 4（匹配度）：
  三个"正面"输出，避免学员只看到问题清单后感到沮丧
规则 2（核心改进）：
  一个"负面"输出，但指向具体改进方向，而非单纯批评

这种"3 正 1 负"的结构，让 LLM 输出更符合"职业顾问"的人设：
  你既不是面试官（只找问题），也不是朋友（只夸你），
  而是帮你改进的顾问（既指出问题，也给出信心）。
```

## 十、边界情况与异常处理

| 场景 | 表现 | 处理 |
|------|------|------|
| LLM 提取结果为非 JSON | `EXTRACT_STRUCTURED_PROMPT` 输出格式错误 | `extract_structured_node` 的 `with_structured_output` 强制 Schema，非 JSON 会被重试/降级 |
| 六维度评审中某维度 LLM 超时 | `run_six_dimensions_node` 的 `asyncio.gather` 中该任务异常 | 降级为 `_empty_dimension_score`（score=0, issues=[]），不阻塞其他 5 个维度 |
| 问题诊断 LLM 返回空列表 | `DIAGNOSE_ISSUES_PROMPT` 输出空数组 | 跳过问题列表，`summary_node` 生成无问题报告 |
| 输入文本过长超 LLM context | 简历文本超过模型上下文窗口 | 提示词中 `{raw_text}` 会被截断，`extract_structured` 的 `structured_output` 重试机制可部分补偿 |
| 提示词占位符缺失 | `format()` 抛出 `KeyError` | 开发阶段发现，生产环境有模块自测覆盖 |
