### 2.1.1 为什么需要异步：先看一个痛点

EduAgent 后端做的事情，绝大多数是「发起一个请求，然后等着对方回应」：
- 调用 DeepSeek 大模型 API，等它把答案算出来（几秒甚至十几秒）
- 查询 PostgreSQL 数据库，等它返回结果
- 检索 Milvus 向量库，等它返回相似文档

这类操作的特点是：**CPU 几乎不干活，时间都花在「等」上面**。我们称之为 **I/O 密集型**任务。

如果用传统的**同步**写法，程序会「一件事等完再做下一件」。用 `time.sleep` 模拟「等待一次网络请求」：

```python
import time

def fetch(name, seconds):
    print(f"开始 {name}")
    time.sleep(seconds)          # 模拟一次耗时的网络请求
    print(f"完成 {name}")

start = time.time()
fetch("请求A", 2)
fetch("请求B", 2)
fetch("请求C", 2)
print(f"总耗时：{time.time() - start:.1f} 秒")
```

运行结果（耗时约 **6 秒**）：
```
开始 请求A
完成 请求A
开始 请求B
完成 请求B
开始 请求C
完成 请求C
总耗时：6.0 秒
```

三个请求各等 2 秒，串行累加成 6 秒。可问题是：**A 在等待的时候，CPU 是空闲的，完全可以同时去发起 B 和 C**。这正是异步要解决的问题——**在等待 I/O 的空档里去做别的事，让多个「等待」重叠起来**。

> **一个生活类比**：你去咖啡店点了三杯咖啡。同步做法是「点第一杯 -> 站在那等做完 -> 再点第二杯……」；异步做法是「三杯一起下单 -> 一起等 -> 谁好了拿谁」。后者显然快得多。注意：异步并没有让「做一杯咖啡」本身变快，它只是让你**在等待时不空耗**。

### 2.1.2 协程、async / await 与 asyncio.run

异步编程的三个最基础概念：

- **协程函数**：用 `async def` 定义的函数。调用它**不会立刻执行**，而是返回一个「协程对象」（可以理解为「一个待办任务」）。
- **`await`**：用来「等待一个协程跑完并拿到它的结果」。只能写在 `async def` 函数内部。
- **`asyncio.run(...)`**：异步世界的「总开关 / 入口」，负责启动事件循环并运行最外层的协程。

最小可运行例子：

```python
import asyncio

async def say_hello():
    print("Hello")
    await asyncio.sleep(1)        # 异步地等 1 秒（不阻塞事件循环）
    print("Async")
    return "完成"

async def main():
    result = await say_hello()    # 用 await 等它跑完并拿到返回值
    print("拿到结果：", result)

asyncio.run(main())               # 从同步世界进入异步世界的唯一入口
```

输出：
```
Hello
Async
拿到结果：完成
```

几个要点：

1. `async def` 定义的是协程，**不 `await`、也不 `asyncio.run`，它就不会真正运行**。
2. `await asyncio.sleep(1)` 和 `time.sleep(1)` 看着像，本质完全不同：前者「让出控制权，事件循环可以去干别的」，后者「死等，谁也别想动」。在异步代码里要等待，必须用前者这类**可等待（awaitable）**的写法。
3. 整个程序通常只有**一个** `asyncio.run` 作为入口。在 EduAgent 里，FastAPI 框架已经帮我们启动了事件循环，所以业务代码里几乎看不到 `asyncio.run`，我们的接口函数直接写成 `async def` 即可。

### 2.1.3 用 asyncio.gather 实现并发

`asyncio.gather` 能把多个协程**同时启动、一起等待**，这是异步最常用、最能体现价值的能力。把 2.1.1 的例子改成异步并发版：

```python
import asyncio
import time

async def fetch(name, seconds):
    print(f"开始 {name}")
    await asyncio.sleep(seconds)     # 注意：换成异步 sleep
    print(f"完成 {name}")
    return f"{name} 的结果"

async def main():
    start = time.time()
    results = await asyncio.gather(   # 三个任务同时开始，一起等
        fetch("请求A", 2),
        fetch("请求B", 2),
        fetch("请求C", 2),
    )
    print("所有结果：", results)
    print(f"总耗时：{time.time() - start:.1f} 秒")

asyncio.run(main())
```

输出（耗时只有约 **2 秒**，而不是 6 秒）：
```
开始 请求A
开始 请求B
开始 请求C
完成 请求A
完成 请求B
完成 请求C
所有结果：['请求A 的结果', '请求B 的结果', '请求C 的结果']
总耗时：2.0 秒
```

三个请求几乎同时开始，等待时间重叠，总耗时约等于「最慢的那一个」。`gather` 还会**按你传入的顺序**把每个协程的返回值收集成一个列表，方便你后续使用。

> **EduAgent 里的真实应用**：
> - 应用启动时，`main.py` 用 `asyncio.gather` **同时预热** BGE-Reranker、MiniLM、BGE-M3 三个本地模型，而不是一个加载完再加载下一个。
> - 简历审查 Agent 对一份简历做**六个维度的并行评分**，六次大模型调用用 `gather` 同时发出，总耗时约等于一次调用，而不是六次累加。
> - 试卷批改 Agent 把多道题**并行批改**。
> - 凡是「多件互不依赖的等待」，都应该用 `gather` 叠起来——这是异步性能优化最直接的手段。

### 2.1.4 在异步里跑同步阻塞代码：run_in_executor

异步的世界有一条铁律：**绝对不能在协程里直接调用「会长时间阻塞」的同步函数**。一旦这么做，整个事件循环会被卡死，所有并发任务全部停摆。

可现实是，我们经常不得不调用一些**只有同步版本**的重活，比如：
- 本地模型（BGE-M3 / BGE-Reranker / MiniLM）的推理是同步的、还挺吃 CPU
- 解析 PDF、解析 Word 文档是同步的
- 校验密码（bcrypt）是同步的、且故意设计得很慢

解决办法是 **`loop.run_in_executor`**：把这个同步函数**丢进一个线程池里执行**，主事件循环在它跑的时候继续处理别的任务，等它跑完再用 `await` 取回结果。

```python
import asyncio
import time

def heavy_sync_work(n):              # 一个阻塞的同步函数（模拟本地模型推理）
    print("同步重活开始……")
    time.sleep(2)                    # 故意阻塞 2 秒
    print("同步重活结束")
    return n * n

async def main():
    loop = asyncio.get_running_loop()        # 拿到当前事件循环
    # 第一个参数 None 表示用默认线程池；后面依次是「要执行的函数」和「它的参数」
    result = await loop.run_in_executor(None, heavy_sync_work, 10)
    print("结果：", result)

asyncio.run(main())
```

输出：
```
同步重活开始……
同步重活结束
结果：100
```

记住这个固定套路：
```python
loop = asyncio.get_running_loop()
结果 = await loop.run_in_executor(None, 同步函数, 参数1, 参数2, ...)
```

> **EduAgent 里的真实应用**：QA Agent 里所有本地模型推理（向量化、精排、意图分类）、试卷的 Word 解析、简历的 PDF 文本提取、登录时的密码校验，**全部**通过 `run_in_executor` 包装后调用。这是「把同步代码安全融入异步系统」的标准做法。

### 2.1.5 后台任务与「消失的任务」陷阱

有些活儿很慢，但用户不需要傻等结果。比如**试卷批改**：接口可以先告诉用户「已收到，正在后台批改」，立刻返回，批改任务在后台慢慢跑。这就要用到 **`asyncio.create_task`**——它把一个协程「扔到后台去跑」，不阻塞当前流程。

但这里有一个非常隐蔽、新手必踩的坑：

> `asyncio.create_task` 返回一个 `Task` 对象。如果你**没有用变量持有它的强引用**，Python 的垃圾回收器可能在任务还没跑完时就把它回收掉，导致**后台任务无声无息地消失**。

正确的做法是：用一个**模块级的 `set`** 持有所有后台任务的引用，并在任务完成时把它从 set 里移除（避免内存泄漏）：

```python
import asyncio

# 模块级集合：持有所有后台任务的强引用，防止被 GC 提前回收
_background_tasks: set[asyncio.Task] = set()

async def grade_exam(exam_id):
    print(f"开始批改试卷 {exam_id}……")
    await asyncio.sleep(2)               # 模拟耗时的批改过程
    print(f"试卷 {exam_id} 批改完成")

async def submit():
    task = asyncio.create_task(grade_exam("EX-001"))  # 丢到后台
    _background_tasks.add(task)                         # 关键①：强引用，防 GC
    task.add_done_callback(_background_tasks.discard)   # 关键②：跑完自动移除
    print("接口立即返回：已收到，正在后台批改")

async def main():
    await submit()
    await asyncio.sleep(3)    # 模拟服务持续运行，给后台任务跑完的时间
    print("当前后台任务数：", len(_background_tasks))

asyncio.run(main())
```

输出：
```
接口立即返回：已收到，正在后台批改
开始批改试卷 EX-001……
试卷 EX-001 批改完成
当前后台任务数：0
```

注意：`submit` 没有等批改完成就先打印了「接口立即返回」，批改是在后台进行的；任务跑完后通过回调从集合里自动移除，集合最终为空。

> **EduAgent 里的真实应用**：`api/v1/exam.py` 和 `api/v1/resume.py` 都在文件顶部定义了 `_background_tasks: set[asyncio.Task] = set()`，提交批改 / 简历审查时用的正是上面这个「create_task + add 进集合 + 完成时 discard」的标准模式。这是写异步后台任务时的**必备防御**。

### 2.1.6 异步上下文管理器：@asynccontextmanager

普通的 `with` 语句用来「进入时做点准备、退出时做点清理」（比如开文件、关文件）。异步世界里对应的是 `async with`，而创建它最方便的方式是 `@asynccontextmanager` 装饰器：

```python
import asyncio
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan():
    print("【启动】加载模型 / 建立数据库连接")
    yield                              # yield 之前 = 启动逻辑；之后 = 关闭逻辑
    print("【关闭】释放资源 / 清理缓存")

async def main():
    async with lifespan():
        print("应用运行中，处理请求……")

asyncio.run(main())
```

输出：
```
【启动】加载模型 / 建立数据库连接
应用运行中，处理请求……
【关闭】释放资源 / 清理缓存
```

理解的关键就一句话：**`yield` 上面的代码在「进入」时执行，下面的代码在「退出」时执行**。

> **EduAgent 里的真实应用**：`main.py` 用 `@asynccontextmanager` 写了一个 `lifespan` 函数，挂到 FastAPI 应用上。`yield` 之前负责「应用启动时」的工作——自动执行数据库迁移、并行预热三个本地模型；`yield` 之后负责「应用关闭时」的清理——清空大模型实例缓存。

### 2.1.7 三个常见坑（提前打预防针）

**坑一：忘记 `await`，拿到的是协程对象而不是结果。**

```python
async def get_value():
    return 42

# 错误：result 是一个 <coroutine object>，不是 42
result = get_value()
# 正确：必须 await
result = await get_value()      # 42
```

如果你发现某个变量打印出来是 `<coroutine object ...>`，十有八九是漏写了 `await`。

**坑二：在已经运行的事件循环里再调用 `asyncio.run`。**

`asyncio.run` 只能用在「最外层入口」。在一个已经由 FastAPI 启动了事件循环的接口函数里再调 `asyncio.run`，会直接报错。本项目的规约是：**需要在同步代码里兜底调用异步逻辑时，用 `asyncio.run(...)`；但不要用 `asyncio.new_event_loop()` 手动创建事件循环**（容易和框架已有的循环打架）。

**坑三：在协程里直接写阻塞调用。**

```python
async def bad():
    time.sleep(5)          # 错误！会卡死整个事件循环
    requests.get(url)      # 错误！同步网络库同样会阻塞

async def good():
    await asyncio.sleep(5)                          # 正确：异步等待
    await loop.run_in_executor(None, requests.get, url)  # 正确：丢线程池
```

凡是同步的、阻塞的调用，要么换成异步版本（`await asyncio.sleep`），要么用 `run_in_executor` 包起来。

### 2.1 面试题

#### 1. 同步编程和异步编程的核心区别是什么？为什么 EduAgent 这样的系统更需要异步？

**答案：**
同步编程中，任务按顺序执行，一个任务在等待 I/O 时（如等待网络响应、等待数据库查询结果），CPU 会闲置，让整个程序停下来等待。异步编程则允许在等待 I/O 的空档里去做别的事，让多个「等待」重叠起来。

EduAgent 后端主要是 I/O 密集型操作（调用大模型 API 需要几秒到十几秒、查询数据库、检索向量库），这些操作的特点是 CPU 几乎不干活，时间都花在「等」上面。如果使用同步编程，三个请求各等 2 秒，串行累加成 6 秒；而异步可以同时发起 3 个请求，总耗时约等于最慢的那个（2 秒），性能提升巨大。

#### 2. 协程、async/await 和 asyncio.run 的关系是什么？

**答案：**
- `async def` 定义协程函数，调用它不会立刻执行，而是返回一个协程对象（待办任务）
- `await` 用来等待一个协程跑完并拿到结果，只能写在 `async def` 内部
- `asyncio.run()` 是异步世界的总开关，负责启动事件循环并运行最外层的协程
- 整个程序通常只有一个 `asyncio.run` 作为入口

#### 3. asyncio.gather 的作用是什么？在 EduAgent 中有哪些应用场景？

**答案：**
`asyncio.gather` 能把多个协程同时启动、一起等待，按传入顺序收集返回值。总耗时约等于最慢的那个任务，而不是所有任务耗时的累加。

EduAgent 中的应用：
- 应用启动时，`main.py` 用 `asyncio.gather` 同时预热 BGE-Reranker、MiniLM、BGE-M3 三个本地模型
- 简历审查 Agent 对一份简历做六个维度的并行评分
- 试卷批改 Agent 把多道题并行批改

#### 4. 为什么在协程里不能直接调用同步阻塞函数？run_in_executor 是如何解决这个问题的？

**答案：**
在协程里直接调用同步阻塞函数（如 `time.sleep`、`requests.get`）会卡死整个事件循环，导致所有并发任务全部停摆。因为 Python 的事件循环是单线程的，同步阻塞函数会霸占线程，不让事件循环处理其他任务。

`run_in_executor` 的解决方案是：把这个同步函数丢进一个线程池里执行，主事件循环在它跑的时候继续处理别的任务，等它跑完再用 `await` 取回结果。标准写法是 `loop.run_in_executor(None, 同步函数, 参数)`。

#### 5. 后台任务被 GC 回收的问题是什么？如何正确防御？

**答案：**
`asyncio.create_task` 返回的 Task 对象如果没有被变量持有强引用，Python 的垃圾回收器可能在任务还没跑完时就把它回收掉，导致后台任务无声无息地消失。

正确的防御方法是标准三件套：
1. 定义模块级集合 `_background_tasks: set[asyncio.Task] = set()`
2. 创建任务后立即 `_background_tasks.add(task)` 持有强引用
3. 通过 `task.add_done_callback(_background_tasks.discard)` 在任务完成后自动移除

#### 6. @asynccontextmanager 的用法是什么？yield 前后的代码分别在什么时候执行？

**答案：**
`@asynccontextmanager` 用于创建异步上下文管理器，配合 `async with` 使用。yield 上面的代码在「进入」时执行（启动逻辑），yield 下面的代码在「退出」时执行（关闭逻辑）。

在 EduAgent 中，`main.py` 用 `@asynccontextmanager` 写了一个 `lifespan` 函数，yield 之前负责应用启动时的工作（自动执行数据库迁移、并行预热三个本地模型），yield 之后负责应用关闭时的清理（清空大模型实例缓存）。

### 2.2.1 Pydantic 是什么，解决什么问题

写程序时，我们经常要处理**来自外部、不可全信的数据**：用户提交的表单、数据库查询结果、第三方接口返回的 JSON……这些数据「该有哪些字段、字段是什么类型」，全靠我们自己一个个手动检查，又啰嗦又容易漏。

来感受一下「没有 Pydantic」时的痛苦——假设我们要确保一份学员数据合法：

```python
def check_student(data: dict):
    if "name" not in data or not isinstance(data["name"], str):
        raise ValueError("name 缺失或类型错误")
    if "age" not in data or not isinstance(data["age"], int):
        raise ValueError("age 缺失或类型错误")
    if data["age"] < 0:
        raise ValueError("age 不能为负")
    # ……字段一多，这样的检查会写到天荒地老
    return data
```

**Pydantic 把这一切自动化了**。你只需要用 Python 的「类型注解」声明「数据应该长什么样」，Pydantic 就会自动帮你校验、自动帮你做合理的类型转换、出错时给出清晰的报错。

在 EduAgent 里，Pydantic 有两个核心用途：

1. **让大模型输出结构化数据（最重要）**。比如让大模型从简历里抽取出「姓名、教育经历、项目经历」并以固定结构返回——靠的就是 Pydantic 模型。这是简历审查、试卷批改、问答等多个 Agent 的基础。
2. **读取配置与接口参数**。比如从 `.env` 文件读数据库密码（`BaseSettings`），以及定义 API 的请求/响应格式。

---

### 2.2.2 第一个模型：BaseModel 与自动校验

用 Pydantic，第一步是定义一个**继承自 `BaseModel` 的类**，用类型注解写明每个字段：

```python
from pydantic import BaseModel

class Student(BaseModel):
    name: str          # 字符串
    age: int           # 整数

# 用关键字参数创建实例
s = Student(name="小明", age=18)
print(s.name)          # 小明
print(s.age)           # 18
print(s)               # name='小明' age=18
```

Pydantic 会在创建实例时**自动校验类型**。它还会做**合理的自动转换**——比如你传了一个字符串 `"18"`，它会自动转成整数 `18`：

```python
s = Student(name="小红", age="18")   # age 传的是字符串
print(s.age, type(s.age))            # 18 <class 'int'>  -> 自动转成了 int
```

但如果数据**没法合理转换**，Pydantic 会立刻抛出 `ValidationError`，并告诉你错在哪：

```python
from pydantic import BaseModel, ValidationError

class Student(BaseModel):
    name: str
    age: int

try:
    Student(name="小刚", age="十八")   # "十八" 无法转成整数
except ValidationError as e:
    print(e)
```

输出（节选）：
```
1 validation error for Student
age
  Input should be a valid integer, unable to parse string as an integer ...
```

这就是 Pydantic 的核心价值：**你只管声明「数据该长什么样」，校验和报错它全包了。**

---

### 2.2.3 Field：给字段加「说明书」

光有类型还不够。很多时候我们想给字段补充更多信息：它是必填的还是可选的？默认值是什么？这个字段是什么含义？这些都通过 `Field` 来表达。

```python
from pydantic import BaseModel, Field

class UserProfile(BaseModel):
    name:  str = Field(description="用户姓名")            # 必填：没有默认值
    phone: str = Field(default="", description="手机号")  # 可选：有默认值 ""
    age:   int = Field(default=18, description="年龄")    # 可选：默认 18
```

几个要点：
- **必填 vs 可选**：`Field` 里**没写 `default` 的字段就是必填**（创建实例时必须提供，否则报错）；写了 `default` 的就是可选的。
- **`description`**：对字段含义的文字说明。**请记住这个参数——下一节你会看到它有多重要。**

#### 一个常见坑：列表 / 字典的默认值要用 default_factory

如果一个字段的默认值是「空列表」或「空字典」这类**可变对象**，**不要**写 `default=[]`，而要写 `default_factory=list`：

```python
from pydantic import BaseModel, Field

class Article(BaseModel):
    title: str  = Field(description="标题")
    tags:  list[str] = Field(default_factory=list, description="标签列表")  # 正确写法

a = Article(title="Python 入门")
print(a.tags)    # []  —— 默认是一个空列表
```

> **为什么不能用 `default=[]`？** 因为如果所有实例共享同一个列表默认值，往一个实例里加元素会「污染」到其他实例。`default_factory=list` 的意思是「每次创建实例时，都新建一个空列表」，从而避免这个隐患。**在 EduAgent 里，凡是列表字段一律用 `default_factory=list`**，你照做就对了。

---

### 2.2.4 重点：description 为什么是「大模型结构化输出」的关键

这是本节最该理解的一点，它直接关系到后面好几个 Agent 的实现原理。

我们后面会用到 LangChain 的一个能力：**让大模型不要返回一段自由文本，而是严格按照一个 Pydantic 模型的结构来填空**（对应代码 `llm.with_structured_output(你的模型)`，第 2.3 节会讲）。

那么大模型怎么知道每个字段该填什么？**答案就是：它会读取你这个 Pydantic 模型的「字段名 + 类型 + `description`」，把它们当成填空指令。** 换句话说：

> **你给字段写的 `description`，就是你对大模型下达的精确指令。** `description` 写得越清楚，大模型填得越准。

来看 EduAgent 简历审查里真实的一个模型（节选）：

```python
from pydantic import BaseModel, Field

class EducationItem(BaseModel):
    """单条教育经历"""
    school:   str = Field(description="学校名称")
    major:    str = Field(description="专业名称")
    degree:   str = Field(description="学历：本科/专科/硕士等")
    duration: str = Field(description="在校时间，如 2020.09 - 2024.06")
    gpa:      str = Field(default="", description="GPA 或成绩（可选）")
```

当我们把一份简历文本和这个模型一起交给大模型时，大模型读到：
- `school`（字符串，「学校名称」）-> 它就去简历里找学校名填进来
- `degree`（字符串，「学历：本科/专科/硕士等」）-> `description` 里给的例子帮它规范了输出格式
- `duration`（「在校时间，如 2020.09 - 2024.06」）-> 连日期格式都被这句话约束住了

所以**写 Pydantic 模型 = 设计大模型的输出格式 = 写提示词的一部分**。这就是为什么本项目里几乎每个字段都认真写了 `description`。

### 2.2.5 组合复杂结构：嵌套模型与列表

真实业务的数据往往是「模型套模型」。比如一份完整简历，里面有**多条**教育经历、**多条**项目经历。Pydantic 支持把一个模型作为另一个模型的字段类型，用 `list[子模型]` 表示「一个列表，里面每一项都是这种子模型」：

```python
from pydantic import BaseModel, Field

class EducationItem(BaseModel):
    school: str = Field(description="学校名称")
    major:  str = Field(description="专业名称")

class Resume(BaseModel):
    name:      str                = Field(description="姓名")
    education: list[EducationItem] = Field(default_factory=list)  # 教育经历列表

# 创建时，嵌套部分可以直接用字典，Pydantic 会自动转成对应的子模型
resume = Resume(
    name="小明",
    education=[
        {"school": "清华大学", "major": "计算机"},
        {"school": "北京大学", "major": "软件工程"},
    ],
)

print(resume.name)                    # 小明
print(resume.education[0].school)     # 清华大学  <- 注意：已经是 EducationItem 对象了
print(type(resume.education[0]))      # <class '__main__.EducationItem'>
```

注意最后一行：你传进去的是普通字典，但 Pydantic **自动把它转成了 `EducationItem` 对象**，所以你能用 `.school` 这样的点号访问。这就是 EduAgent 里 `ResumeStructured` 模型的结构——一个大模型里嵌着 `list[EducationItem]`、`list[ProjectItem]`、`list[WorkItem]`。

如果某个字段「可能有、也可能没有（可以是 None）」，用 `Optional`：

```python
from typing import Optional
from pydantic import BaseModel

class Profile(BaseModel):
    nickname: Optional[str] = None    # 可以是字符串，也可以是 None
```

### 2.2.6 model_dump()：在「模型」和「字典」之间转换

模型对象适合在代码里用（带类型、带校验、能点号访问），但当我们要**存进数据库、或作为 JSON 返回给前端**时，往往需要把它转成普通字典。用 `.model_dump()`：

```python
from pydantic import BaseModel, Field

class Student(BaseModel):
    name: str = Field(description="姓名")
    age:  int = Field(default=18, description="年龄")

s = Student(name="小明", age=20)

d = s.model_dump()       # 模型 -> 字典
print(d)                 # {'name': '小明', 'age': 20}
print(type(d))           # <class 'dict'>
```

反过来，如果你手上有一个字典，想把它变成模型对象，可以直接解包传入：

```python
data = {"name": "小红", "age": 22}
s2 = Student(**data)     # 字典 -> 模型
print(s2.name)           # 小红
```

> **EduAgent 里的真实应用**：简历 Agent、试卷批改 Agent 在拿到大模型返回的 Pydantic 结果后，几乎都会立刻调用 `.model_dump()` 转成字典，再存进 PostgreSQL 或放进 LangGraph 的 State 里。你会在代码里频繁看到 `result.model_dump()`。

### 2.2.7 配套：Enum 与 BaseSettings

#### Enum：把字段限定为「固定的几个取值」

有些字段的取值是固定的一小撮，比如模拟面试的「阶段」只能是「热身 / 技术基础 / 项目 / 收尾 / 结束」之一。这时用 `Enum`（枚举）来定义合法取值集合，既防止写错，又让代码更清晰：

```python
from enum import Enum

class InterviewStage(str, Enum):       # 继承 str，取值就是字符串
    WARMUP    = "warmup"
    TECH_BASE = "tech_base"
    PROJECT   = "project"
    CLOSING   = "closing"
    FINISHED  = "finished"

print(InterviewStage.WARMUP)           # InterviewStage.WARMUP
print(InterviewStage.WARMUP.value)     # warmup
```

> **EduAgent 里的真实应用**：模拟面试 Agent 用 `InterviewStage` 枚举表示对话进行到哪个阶段；Orchestrator 用枚举表示 Agent 类型（`qa` / `exam` / `resume` / `interview`）和执行模式。枚举也能直接作为 Pydantic 模型的字段类型。

#### BaseSettings：从环境变量 / .env 文件读配置

Pydantic 还有一个专门用来「读配置」的基类 `BaseSettings`（来自 `pydantic-settings` 包）。它能自动从**环境变量**或 **`.env` 文件**里把配置项读出来，并同样做类型校验。

```python
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    db_host: str = "localhost"
    db_port: int = 5433              # 会自动把环境变量里的字符串转成 int

settings = Settings()
print(settings.db_host, settings.db_port)
```

> **EduAgent 里的真实应用**：项目的 `config.py` 就是用 `BaseSettings` 定义的，所有数据库地址、API Key、端口等配置都从 `.env.local` 文件读取，绝不硬编码在代码里。

### 2.2 面试题

#### 7. Pydantic 解决的核心问题是什么？在 EduAgent 中有哪两大用途？

**答案：**
Pydantic 解决的核心问题是：用类型注解声明「数据该长什么样」，自动完成校验与合理的类型转换，出错时给出清晰的报错信息。开发者不需要手动写繁琐的 `isinstance` 检查。

在 EduAgent 中的两大用途：
1. **让大模型输出结构化数据（最重要）**：通过 `with_structured_output` 让大模型严格按照 Pydantic 模型的结构来填空，是简历审查、试卷批改、问答等多个 Agent 的基础。
2. **读取配置与接口参数**：用 `BaseSettings` 从 `.env` 文件读配置，用 Pydantic 模型定义 API 的请求/响应格式。

#### 8. Field 中 default 和 default_factory 的区别是什么？为什么列表字段要用 default_factory=list？

**答案：**
- `default` 用于不可变默认值（如字符串、数字），所有实例共享同一个值
- `default_factory` 用于可变默认值（如列表、字典），每次创建实例时都新建一个对象

不能使用 `default=[]` 的原因是：如果所有实例共享同一个列表默认值，往一个实例里添加元素会「污染」到其他实例。`default_factory=list` 确保每次创建实例时都新建一个空列表，避免这个隐患。

#### 9. 为什么说 Pydantic 模型的 description 字段是「让大模型输出结构化数据」的关键？

**答案：**
当使用 `with_structured_output` 让大模型按 Pydantic 模型填空时，大模型会读取模型的「字段名 + 类型 + description」作为填空指令。`description` 写得越清楚，大模型填得越准。因此，写 Pydantic 模型 = 设计大模型的输出格式 = 写提示词的一部分。这就是为什么本项目里几乎每个字段都认真写了 `description`。

#### 10. 嵌套模型是如何工作的？Pydantic 如何处理嵌套字典到子模型对象的转换？

**答案：**
Pydantic 支持把一个模型作为另一个模型的字段类型，用 `list[子模型]` 表示「一个列表，里面每一项都是这种子模型」。当创建外层模型时，嵌套部分可以直接用普通字典，Pydantic 会自动把字典转成对应的子模型对象，使开发者可以用点号（如 `.school`）访问嵌套字段。这种机制使得 EduAgent 可以构建像 `ResumeStructured` 这样包含 `list[EducationItem]`、`list[ProjectItem]` 等复杂结构的模型。

#### 11. model_dump() 的作用是什么？如何从字典创建模型实例？

**答案：**
`model_dump()` 将 Pydantic 模型对象转换为普通字典，适用于存数据库或返回 JSON。反过来，通过 `Model(**dict)` 可以将字典解包传入，创建模型实例并自动完成校验和类型转换。

#### 12. Enum 和 BaseSettings 在 EduAgent 中的典型应用场景是什么？

**答案：**
- **Enum**：用于将字段限定为固定取值，如模拟面试的阶段（`InterviewStage` 枚举）、Agent 类型（`qa` / `exam` / `resume` / `interview`）、执行模式等。枚举可以直接作为 Pydantic 模型的字段类型。
- **BaseSettings**：用于从环境变量或 `.env` 文件读取配置，如数据库地址、API Key、端口等。项目的 `config.py` 就是用 `BaseSettings` 定义的，确保配置不硬编码在代码里。

### 2.3.1 LangChain 是什么、在项目里干什么

市面上的大模型有很多（DeepSeek、通义千问、OpenAI……），每家的 SDK 调用方式都不一样。**LangChain 的核心价值，就是给各种大模型提供一套「统一接口」**：你用同一套代码就能调用不同的模型，将来换模型时业务代码几乎不用改。

在 EduAgent 里，LangChain 主要负责两件事：

1. **统一地调用 DeepSeek 大模型**——发消息、拿回答。
2. **把大模型的输出「约束」成结构化数据**——这是本节的重点，也是后面简历、批改、问答等 Agent 的实现基础。

> **版本提醒（务必注意）**：本项目锁定 **LangChain 1.x（1.2.10）**。网上大量旧教程用的是 0.x 的 API（如 `LLMChain`、`ChatOpenAI`、`initialize_agent`、`ConversationChain`），**那些写法在本项目里一律禁止使用**，照抄会报错或行为不一致。本节教的全部是 1.x 新写法。

---

### 2.3.2 用 init_chat_model 创建模型（1.x 新写法）

在 LangChain 1.x 里，创建一个大模型实例的标准方式是 **`init_chat_model`**（注意：**不是** 旧版的 `ChatOpenAI(...)`）。DeepSeek 提供的是「OpenAI 兼容接口」，所以我们通过指定 `model_provider="openai"` + DeepSeek 的 `base_url` 来接入它：

```python
from langchain.chat_models import init_chat_model

llm = init_chat_model(
    model="deepseek-chat",                       # 模型名称
    model_provider="openai",                     # 走 OpenAI 兼容协议（关键）
    api_key="sk-你的DeepSeekKey",                # DeepSeek 的 API Key
    base_url="https://api.deepseek.com/v1",      # DeepSeek 接口地址（关键）
    temperature=0,                               # 输出的随机性，0 = 最稳定
)
```

逐个理解关键参数：

- **`model_provider="openai"` + `base_url=...`**：这两个配合使用，意思是「用 OpenAI 的协议格式，但把请求发到 DeepSeek 的地址」。这里有个**必须避开的坑**：千万**不要**把模型名写成 `"deepseek/deepseek-chat"` 这种带前缀的形式，那会触发框架去找另一个专用的 `langchain-deepseek` 包，导致出错。正确做法就是上面这样：`model="deepseek-chat"` + `model_provider="openai"` + `base_url`。

- **`temperature`**：控制输出的随机性，范围 0~1（或更高）。`0` 表示「每次尽量给最确定、最稳定的答案」，适合评分、批改这种需要稳定的场景；对话场景可以调到 `0.3~0.7` 让回答更自然。

> **EduAgent 里的真实应用**：项目不会在业务代码里到处写 `init_chat_model`，而是把它统一封装进一个 **LLM Factory**（`core/llm_factory.py`），所有 Agent 都通过工厂获取模型。这样 Key、地址、超时、重试等配置只需在一处管理。

---

### 2.3.3 消息体系：System / Human / AI

和大模型对话时，每一句话都有一个「角色」。LangChain 用三种消息类来表示：

```python
from langchain_core.messages import SystemMessage, HumanMessage, AIMessage
```

- **`SystemMessage`（系统消息）**：给大模型设定身份和规则，比如「你是一位严谨的简历评审专家」。它影响大模型整体的行为风格。
- **`HumanMessage`（用户消息）**：用户实际说的话 / 提出的问题。
- **`AIMessage`（AI 消息）**：大模型的回复。我们调用模型后，拿到的就是一个 `AIMessage`；在多轮对话里，也用它来表示「AI 之前说过的话」。

调用模型时，我们传入一个**消息列表**，通常是「一条系统消息 + 一条用户消息」：

```python
messages = [
    SystemMessage(content="你是一位专业的 Python 讲师，用简洁的语言回答。"),
    HumanMessage(content="什么是装饰器？一句话解释。"),
]
```

> **关于提示词的写法**：LangChain 也提供了 `ChatPromptTemplate` 这类「提示词模板」工具，但 **EduAgent 选择更直白的方式**——直接用 Python 的 f-string 拼出提示词文本，放进 `HumanMessage(content=...)` 里。这样提示词一目了然、好调试。本课程沿用项目的这种写法，不引入额外的模板概念。

---

### 2.3.4 调用模型：ainvoke 与 .text

因为整个项目是异步的（回顾 2.1），我们用**异步方法 `ainvoke`** 来调用模型（`a` 代表 async）。它返回一个 `AIMessage`，我们用 **`.text` 属性**取出其中的文本：

```python
import asyncio
from langchain.chat_models import init_chat_model
from langchain_core.messages import SystemMessage, HumanMessage

llm = init_chat_model(
    model="deepseek-chat",
    model_provider="openai",
    api_key="sk-你的DeepSeekKey",
    base_url="https://api.deepseek.com/v1",
    temperature=0,
)

async def main():
    messages = [
        SystemMessage(content="你是一位专业的 Python 讲师，用一句话回答。"),
        HumanMessage(content="什么是装饰器？"),
    ]
    response = await llm.ainvoke(messages)    # 异步调用，返回一个 AIMessage
    print(response.text)                       # 用 .text 取出文本（属性，不加括号！）

asyncio.run(main())
```

这里有一个**本项目强制的细节**，请务必记住：

> 取文本用 **`response.text`（属性，不要加括号）**，**绝对不要写成 `response.text()`**。在 LangChain 1.x 里 `.text` 是属性而不是方法，写成 `.text()` 会出错。这是项目明确列入「禁用」的写法之一。

（补充：`AIMessage` 还有一个 `.content` 字段是更底层的原始内容，它有时是字符串、有时是结构化的内容块；日常取纯文本时，用 `.text` 最省心。）

---

### 2.3.5 重点：with_structured_output —— 让大模型按 Pydantic 填空

这是本节最重要的能力，它把 2.2 学的 Pydantic **真正用起来**。

普通调用拿回的是一段**自由文本**，但很多业务需要的是**结构化数据**：比如简历审查要拿到「姓名、教育经历、各维度分数」这种字段分明的结果。如果让大模型返回一段文本，我们还得自己费劲地解析——又容易出错。

LangChain 的 **`with_structured_output`** 解决了这个问题：你把一个 Pydantic 模型「绑定」到大模型上，大模型就会**严格按照这个模型的结构来填空**，并**直接返回一个 Pydantic 对象**（而不是文本，也不需要你手动解析 JSON）。

```python
import asyncio
from pydantic import BaseModel, Field
from langchain.chat_models import init_chat_model
from langchain_core.messages import SystemMessage, HumanMessage

llm = init_chat_model(
    model="deepseek-chat", model_provider="openai",
    api_key="sk-你的DeepSeekKey",
    base_url="https://api.deepseek.com/v1", temperature=0,
)

# ① 定义期望的输出结构
class PersonInfo(BaseModel):
    name: str = Field(description="姓名")
    age:  int = Field(description="年龄（整数）")
    city: str = Field(description="所在城市")

# ② 把模型绑定上去，得到一个「结构化输出版」的 llm
structured_llm = llm.with_structured_output(PersonInfo, method="function_calling")

async def main():
    messages = [
        SystemMessage(content="你负责从文本中抽取人物信息。"),
        HumanMessage(content="我叫小明，今年 25 岁，住在上海。"),
    ]
    # ③ 调用后直接返回 PersonInfo 对象，不是文本！
    result: PersonInfo = await structured_llm.ainvoke(messages)
    print(type(result))      # <class '__main__.PersonInfo'>
    print(result.name)       # 小明
    print(result.age)        # 25
    print(result.city)       # 上海

asyncio.run(main())
```

注意两个关键点：

1. **`method="function_calling"` 必须写**。这是本项目又一条强制规范——DeepSeek 不支持另一种 `json_schema` 模式，所以结构化输出必须指定 `method="function_calling"`，否则会报错。
2. **返回值直接就是 Pydantic 对象**。你能立刻用 `result.name`、`result.age` 点号访问，不需要自己解析任何 JSON 字符串。要存数据库时，再用 2.2 学的 `result.model_dump()` 转成字典即可。

> **EduAgent 里的真实应用**：这是项目的「核心招式」，反复出现——
> - 简历 Agent 用它把简历文本抽成 `ResumeStructured`，再做六个维度的结构化评分
> - 试卷批改 Agent 用它输出每道题的评分结果和薄弱点报告
> - 问答、面试 Agent 用它生成结构化的中间结果
> - 凡是「需要大模型给出格式固定的结果」，本项目一律用 `with_structured_output` + Pydantic，**绝不让大模型返回文本再手动解析**。

### 2.3.6 流式输出：astream（了解即可）

当用户问问题时，我们希望答案像打字机一样**一个字一个字地蹦出来**，而不是憋几秒后一次性弹出。这就是「流式输出」，用异步方法 `astream` 实现：

```python
async def main():
    messages = [HumanMessage(content="用三句话介绍一下 Python。")]
    async for chunk in llm.astream(messages):   # 逐块接收
        print(chunk.text, end="", flush=True)    # 拼接打印，形成打字机效果

asyncio.run(main())
```

`astream` 会不断「吐」出一小块一小块的内容（`chunk`），我们边收边显示，用户就能看到答案在实时生成。

> **EduAgent 里的真实应用**：智能问答和模拟面试都用流式输出。项目里在模型层用 `streaming=True` 打开流式能力，再在 API 层借助 LangGraph 的事件流，把生成的 token 通过 SSE 实时推给前端。

### 2.4.1 回顾心智模型，以及本节要造什么

回顾 1.2.4 讲过的心智模型：**一个 Agent 就是一张图**，由四要素构成——

- **State（状态）**：所有节点共享的一份数据
- **Node（节点）**：一个函数，读 State、做事、返回要更新的内容
- **Edge（边）**：决定一个节点之后去哪（固定边 / 条件边）
- **Checkpointer（检查点）**：把 State 存下来，实现记忆与恢复

本节我们就用这四要素，**从零搭一个「学习助手」Agent**：它接收一个问题，先判断问题类型（概念题 / 代码题 / 闲聊），再根据类型走不同分支给出回应，最后还能记住多轮对话。

---

### 2.4.2 第一步：定义 State

State 用一个 `TypedDict` 来定义——它就是规定「这张图里流动的数据有哪些字段」。我们的学习助手需要三个字段：

```python
from typing import TypedDict

class HelperState(TypedDict):
    question: str      # 用户的问题（输入）
    category: str      # 分类结果：concept / code / chat（中间结果）
    answer:   str      # 最终回应（输出）
```

你可以把 State 理解成一张**贯穿全程的「工单」**：问题进来时填上 `question`，经过分类节点填上 `category`，经过回应节点填上 `answer`。每个节点都在这张工单上读取已有信息、补充新信息。

---

### 2.4.3 第二步：写节点

节点就是普通的 Python 函数，遵循一个**固定约定**：

> **接收当前 State 作为参数，返回一个字典，字典里只包含「这个节点要更新的字段」**。

注意这个关键点：**节点不直接修改传进来的 State，而是返回一个「增量更新」**。LangGraph 会自动把你返回的字典合并进 State。没返回的字段保持原样。

```python
def classify_node(state: HelperState) -> dict:
    """分类节点：根据关键词判断问题类型"""
    q = state["question"]
    if "代码" in q or "报错" in q or "bug" in q:
        category = "code"
    elif "什么是" in q or "概念" in q or "原理" in q:
        category = "concept"
    else:
        category = "chat"
    return {"category": category}          # 只返回要更新的字段

def answer_concept_node(state: HelperState) -> dict:
    return {"answer": f"【概念解答】关于「{state['question']}」，它的核心思想是……"}

def answer_code_node(state: HelperState) -> dict:
    return {"answer": f"【代码助手】针对「{state['question']}」，我们一步步排查……"}

def answer_chat_node(state: HelperState) -> dict:
    return {"answer": "【闲聊】哈哈，没问题，我们继续聊～"}
```

---

### 2.4.4 第三步：搭图、编译、运行

现在把节点连成一张图。先搭一个最简单的**直线图**（分类 -> 概念解答 -> 结束），把机制跑通：

```python
from langgraph.graph import StateGraph, START, END

builder = StateGraph(HelperState)          # ① 用 State 类型创建图构建器

builder.add_node("classify", classify_node)         # ② 注册节点（名字, 函数）
builder.add_node("answer",   answer_concept_node)

builder.add_edge(START, "classify")        # ③ 连边：START 是入口
builder.add_edge("classify", "answer")     #    分类后去回应
builder.add_edge("answer", END)            #    回应后结束（END 是出口）

graph = builder.compile()                  # ④ 编译成可执行的图

# ⑤ 运行：传入初始 State，拿回最终 State
result = graph.invoke({"question": "什么是装饰器", "category": "", "answer": ""})
print(result)
```

输出：
```
{'question': '什么是装饰器', 'category': 'concept', 'answer': '【概念解答】关于「什么是装饰器」，它的核心思想是……'}
```

图的执行流向可以画成：
```
START --> classify --> answer --> END
```

逐步理解这五步：

1. **`StateGraph(HelperState)`**：创建一个「图构建器」，并告诉它图里流动的数据结构是 `HelperState`。
2. **`add_node("名字", 函数)`**：把一个函数注册成图上的节点，并给它起个名字（后面连边时用这个名字引用）。
3. **`add_edge(起点, 终点)`**：连一条固定的边。`START` 和 `END` 是 LangGraph 内置的特殊起点和终点——**入口必须从 `START` 连出，出口必须连到 `END`**。
4. **`compile()`**：把搭好的图编译成一个真正能执行的对象。
5. **`invoke(初始State)`**：从 `START` 开始执行，依次跑过各节点，每个节点的返回值被合并进 State，最后返回完整的最终 State。

> **规范提醒**：设置入口和出口，**统一用 `START` / `END` 连边**。旧教程里的 `builder.set_entry_point(...)` / `builder.set_finish_point(...)` 在本项目里**禁止使用**。

---

### 2.4.5 加分支：条件边

真实 Agent 需要**根据 State 的值动态选择走哪条路**，这就是**条件边**。

条件边需要两样东西：一个**路由函数**（读 State，返回一个字符串「路标」），和一张**路标 -> 目标节点**的映射表。

```python
from langgraph.graph import StateGraph, START, END

def route_by_category(state: HelperState) -> str:
    """路由函数：返回一个字符串路标，决定下一步去哪个节点"""
    return state["category"]      # 返回 "concept" / "code" / "chat"

builder = StateGraph(HelperState)

builder.add_node("classify", classify_node)
builder.add_node("concept",  answer_concept_node)
builder.add_node("code",     answer_code_node)
builder.add_node("chat",     answer_chat_node)

builder.add_edge(START, "classify")

# 条件边：分类后，根据 route_by_category 的返回值选择目标节点
builder.add_conditional_edges(
    "classify",                  # 从哪个节点出发
    route_by_category,           # 路由函数
    {                            # 路标 -> 目标节点 的映射
        "concept": "concept",
        "code":    "code",
        "chat":    "chat",
    },
)

builder.add_edge("concept", END)
builder.add_edge("code",    END)
builder.add_edge("chat",    END)

graph = builder.compile()

# 试三种不同的问题，观察走了不同分支
for q in ["什么是装饰器", "这段代码报错怎么办", "今天天气不错"]:
    result = graph.invoke({"question": q, "category": "", "answer": ""})
    print(f"问题：{q}\n  -> 分类：{result['category']}  回应：{result['answer']}\n")
```

输出：
```
问题：什么是装饰器
  -> 分类：concept  回应：【概念解答】关于「什么是装饰器」，它的核心思想是……

问题：这段代码报错怎么办
  -> 分类：code  回应：【代码助手】针对「这段代码报错怎么办」，我们一步步排查……

问题：今天天气不错
  -> 分类：chat  回应：【闲聊】哈哈，没问题，我们继续聊～
```

现在的图长这样：
```
                    +--> concept ---+
START --> classify --+--> code ------+--> END
                    +--> chat ------+
              （由 route_by_category 决定走哪条）
```

**这正是 EduAgent 智能问答 Agent 的核心结构**：先用一个分类节点判断问题类型，再用条件边把不同类型的问题分流到不同的处理路径。你现在已经掌握了它的骨架。

### 2.4.6 加记忆：MemorySaver 与 thread_id

到目前为止，每次 `invoke` 都是独立的，图记不住上一次聊了什么。要实现**多轮记忆**，需要两步：

1. 编译时绑定一个 **Checkpointer**（本地用 `MemorySaver`），它负责在每次执行后把 State 存下来
2. 调用时传入一个 **`thread_id`**，作为「这是哪一段对话」的标识。相同 `thread_id` 的多次调用，会接续同一份记忆

为了演示「累积记忆」，我们让消息字段使用一个特殊机制 **`add_messages`**——它能让每次新消息**追加**到历史里，而不是覆盖：

```python
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import MemorySaver
from langchain_core.messages import HumanMessage, AIMessage

class ChatState(TypedDict):
    # Annotated[..., add_messages]：告诉 LangGraph 这个列表字段「追加」而非「覆盖」
    messages: Annotated[list, add_messages]

def reply_node(state: ChatState) -> dict:
    last_user_msg = state["messages"][-1].content        # 取最后一条用户消息
    history_count = len(state["messages"])               # 看看记住了几条
    reply = f"我收到了「{last_user_msg}」（当前历史共 {history_count} 条消息）"
    return {"messages": [AIMessage(content=reply)]}      # 返回的新消息会被「追加」

builder = StateGraph(ChatState)
builder.add_node("reply", reply_node)
builder.add_edge(START, "reply")
builder.add_edge("reply", END)

graph = builder.compile(checkpointer=MemorySaver())      # 绑定记忆

config = {"configurable": {"thread_id": "user-1"}}        # 同一对话的标识

graph.invoke({"messages": [HumanMessage(content="你好")]}, config)
result = graph.invoke({"messages": [HumanMessage(content="还记得我刚说了啥吗")]}, config)

for m in result["messages"]:
    print(f"{type(m).__name__}: {m.content}")
```

输出：
```
HumanMessage: 你好
AIMessage: 我收到了「你好」（当前历史共 1 条消息）
HumanMessage: 还记得我刚说了啥吗
AIMessage: 我收到了「还记得我刚说了啥吗」（当前历史共 3 条消息）
```

看第二次调用：我们只传了一条新消息，但最终的 `messages` 里**累积了全部 4 条**（前两条来自第一轮）。这证明图确实**记住了上一轮对话**。关键就在两处：编译时的 `checkpointer=MemorySaver()`，和调用时相同的 `thread_id`。

> **`add_messages` 在做什么？** 它是一个「合并规则」：默认情况下，节点返回 `{"messages": [...]}` 会**覆盖**原列表；而加了 `Annotated[list, add_messages]` 后，新消息会**追加**到历史末尾。
>
> **EduAgent 里的真实应用**：四个 Agent 全部用 `add_messages` 管理对话消息；记忆通过 `MemorySaver` 实现，并按 Agent 类型隔离；`thread_id` 用 `student_{学员ID}_session_{会话ID}` 的格式拼成，确保每个学员的每段会话各记各的。

### 2.4.7 了解：interrupt 与 Command（人在环中）

LangGraph 还有一个强大能力：让图**在某个节点中途「暂停」，等外部（比如老师）做出决定后再继续**。这就是「人在环中（HitL）」，用 `interrupt()` 暂停、用 `Command(resume=...)` 恢复。

EduAgent 的试卷批改 Agent 正是用它实现「AI 批改完 -> 暂停 -> 等老师确认/修改 -> 继续发布」的流程。这是相对进阶的内容，我们放到**第六章**结合真实业务详细讲解。

### 2.4.8 LangGraph 规范小结

| 用途 | 禁用写法 | 必用写法 |
|------|---------|---------|
| 设置入口 / 出口 | `set_entry_point()` / `set_finish_point()` | `add_edge(START, ...)` / `add_edge(..., END)` |
| 快速创建 Agent | `create_react_agent`（作为主要方式） | 自己用 `StateGraph` 搭图 |
| 节点更新状态 | 直接修改传入的 state 对象 | 返回「要更新的字段」字典 |
| 多轮记忆 | `ConversationBufferMemory` | `compile(checkpointer=...)` + `thread_id` |

核心心法就一句：**自己用 `StateGraph` 显式地把节点和边画出来，让流程清晰可控**——这正是本项目选择 LangGraph 而非「一键式 Agent」的原因。

### 2.4 面试题

#### 18. LangGraph 的四要素是什么？分别如何理解？

**答案：**
1. **State（状态）**：所有节点共享的数据结构，定义为 TypedDict，包含所有需要共享的数据、控制信息和错误信息
2. **Node（节点）**：图中的处理单元，每个节点执行一个具体操作。是一个函数，接收 State 作为输入，返回要更新的字段字典
3. **Edge（边）**：连接节点，定义图的拓扑结构。固定边无条件从一个节点到另一个节点；条件边根据条件决定路由。条件边让图具备了分支和决策能力
4. **Checkpointer（检查点/持久化）**：将 State 持久化到存储中，实现中断恢复、状态持久化、调试回溯、并发隔离

#### 19. 用 LangGraph 实现一个 Agent 的五步套路是什么？

**答案：**
1. 定义 State：用 TypedDict 定义图里流动的数据结构
2. 写节点函数：接收 State 作为参数，返回「要更新的字段」字典，不直接修改 State
3. 连接边：用 `add_edge` 连固定边，用 `add_conditional_edges` 连条件边
4. 绑定 Checkpointer：用 `compile(checkpointer=...)` 绑定记忆
5. 编译运行：用 `invoke` 或 `ainvoke` 执行图

#### 20. 条件边是如何工作的？路由函数的作用是什么？

**答案：**
条件边需要两样东西：一个路由函数和一张路标到目标节点的映射表。路由函数读 State，返回一个字符串路标；映射表定义路标到目标节点的对应关系。`add_conditional_edges` 将路由函数和映射表绑定到源节点上，LangGraph 会在执行时自动调用路由函数，根据返回值选择目标节点。

#### 21. MemorySaver 和 thread_id 如何实现多轮记忆？add_messages 的作用是什么？

**答案：**
- 编译时绑定 `checkpointer=MemorySaver()`，LangGraph 在每次执行后自动保存 State
- 调用时传入相同 `thread_id` 的多次调用会接续同一份记忆
- `add_messages` 是一个合并规则，默认节点返回 `{"messages": [...]}` 会覆盖原列表；加了 `Annotated[list, add_messages]` 后，新消息会追加到历史末尾

#### 22. interrupt 和 Command 的作用是什么？在 EduAgent 的哪个场景中使用？

**答案：**
`interrupt` 让图在某个节点中途暂停，等待外部（如老师）做出决定后再继续。`Command(resume=...)` 用于恢复执行。这就是「人在环中（HitL）」机制。EduAgent 的试卷批改 Agent 正是用它实现「AI 批改完 -> 暂停 -> 等老师确认/修改 -> 继续发布」的流程，将在第六章详细讲解。

### 2.5.1 FastAPI 是什么、在项目里干什么

### 2.5.3 用 Pydantic 接收请求体

当前端要「提交数据」（比如登录时提交用户名密码），我们用一个 **Pydantic 模型作为接口函数的参数**。FastAPI 会自动把请求体里的 JSON 解析成这个模型，并完成校验：

```python
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()

# 请求体模型：前端要发来的数据长这样
class LoginRequest(BaseModel):
    username: str = Field(..., description="用户名或邮箱")
    password: str = Field(..., description="密码")

# 响应模型：我们会返回的数据长这样
class TokenResponse(BaseModel):
    access_token: str
    token_type:   str = "bearer"
    role:         str

@app.post("/login", response_model=TokenResponse)
async def login(req: LoginRequest):           # 参数类型是 Pydantic 模型
    # req 已经是解析并校验好的对象，直接用 req.username / req.password
    if req.username == "student01" and req.password == "Student@123456":
        return TokenResponse(access_token="fake-token-abc", role="student")
    return {"access_token": "", "token_type": "bearer", "role": "guest"}
```

要点：
- **`req: LoginRequest`**：把 Pydantic 模型写成参数类型，FastAPI 就知道「请求体应该是这个结构」，并自动解析 + 校验。如果前端少传了 `password`，FastAPI 会自动返回一个清晰的 422 错误，**你一行校验代码都不用写**
- **`response_model=TokenResponse`**：声明这个接口返回的数据结构。它会让自动文档更准确，也会过滤掉不该返回的多余字段
- `Field(..., description=...)` 里的 `...` 表示「必填」

### 2.5.4 路径参数与查询参数

**路径参数**——把参数嵌在 URL 路径里，用 `{}` 占位，函数里同名参数自动接收：

```python
@app.get("/reviews/{review_id}")

# 访问 GET /reviews/abc-123 -> review_id 自动等于 "abc-123"
```

**查询参数**——URL 问号后面的 `?key=value`，在函数里写成「带默认值的普通参数」：

```python
@app.get("/reviews")

    return {"page": page, "size": size}
# 访问 GET /reviews?page=2&size=20 -> page=2, size=20
# 不传则用默认值 page=1, size=10
```

### 2.5.5 依赖注入 Depends（核心）

很多接口都需要做一些**相同的前置工作**：拿一个数据库连接、校验用户有没有登录……如果在每个接口里都重复写这些，既啰嗦又难维护。FastAPI 用**依赖注入（`Depends`）**优雅地解决了这个问题：

> 把「通用的前置逻辑」写成一个函数（叫「依赖」），在接口参数里用 `Depends(依赖函数)` 声明一下，FastAPI 就会在执行接口前**自动先跑这个依赖、把结果喂给接口**。

本项目有两个最重要的依赖：

**依赖一：get_db —— 获取数据库会话（yield 型）**

```python
from typing import AsyncGenerator
from sqlalchemy.ext.asyncio import AsyncSession

async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as session:   # AsyncSessionLocal 见 2.7 / 第三章
        try:
            yield session            # yield 之前=准备连接；把 session 交给接口用
            await session.commit()   # 接口正常结束后：提交事务
        except Exception:
            await session.rollback() # 出错则回滚
            raise
```

注意它用了 `yield`（回顾 2.1.6 的「yield 上面是准备、下面是收尾」）：`yield` 把数据库会话交给接口使用，接口跑完后再自动提交或回滚、关闭连接。**接口完全不用操心连接的开关，拿来就用。**

**依赖二：get_current_user —— 校验登录（鉴权）**

```python
from fastapi import Depends, HTTPException, status
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials

bearer_scheme = HTTPBearer()

async def get_current_user(
    credentials: HTTPAuthorizationCredentials = Depends(bearer_scheme),
) -> dict:
    token = credentials.credentials
    user = verify_jwt(token)              # 解析并校验 JWT（伪代码，第三章实现）
    if not user:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="无效的认证凭证",
        )
    return {"user_id": user["id"], "role": user["role"]}
```

它负责从请求头里取出 JWT Token、校验合法性，合法就返回用户信息，不合法就抛出 `401` 错误。

**在接口里使用这两个依赖：**

```python
@app.get("/my-reviews")
async def my_reviews(
    db = Depends(get_db),                       # 自动注入数据库会话
    current_user: dict = Depends(get_current_user),  # 自动注入当前用户（顺便完成鉴权）
):
    # 走到这里，说明用户已登录，且 db 已就绪
    return {"user": current_user["user_id"], "data": "..."}
```

这个接口什么校验代码都没写，但因为声明了 `Depends(get_current_user)`，**未登录的请求会被自动挡在 401**；同时 `db` 也已经准备好。这就是依赖注入的威力：**通用逻辑写一次，处处复用。**

### 2.5.6 文件上传

简历审查、试卷批改都需要上传文件。FastAPI 用 `UploadFile` 接收上传的文件：

```python
from fastapi import FastAPI, File, UploadFile

app = FastAPI()

@app.post("/upload", status_code=202)
async def upload(file: UploadFile = File(...)):
    content = await file.read()                  # 异步读取文件内容（bytes）
    return {"filename": file.filename, "size": len(content)}
```

要点：
- **`file: UploadFile = File(...)`**：声明这是一个上传文件参数
- **`await file.read()`**：异步读出文件的二进制内容
- **`status_code=202`**：自定义返回的 HTTP 状态码。`202` 表示「已接受，正在后台处理」——很适合「先收下文件、后台慢慢批改」的场景

### 2.5.7 SSE 流式响应（重点）

普通接口是「算完一次性返回」。但智能问答、模拟面试希望答案**像打字机一样逐字蹦出来**，这就要用 **SSE（Server-Sent Events，服务器推送事件）**：服务器和浏览器保持连接，持续不断地往外推送一小段一小段内容。

本项目用 `sse-starlette` 库的 `EventSourceResponse` 实现。它接收一个**异步生成器**（回顾生成器：能不断 `yield` 产出值的函数），每 `yield` 一次就向前端推送一个事件：

```python
import asyncio
import json
from fastapi import FastAPI
from sse_starlette.sse import EventSourceResponse

app = FastAPI()

@app.post("/chat/stream")
async def chat_stream():
    async def event_generator():
        answer = "装饰器是一种包装函数的语法。"
        for char in answer:                       # 模拟逐字生成
            await asyncio.sleep(0.1)
            # 每个事件是一个字典，data 里放 JSON 字符串
            yield {"data": json.dumps({"type": "token", "content": char})}
        yield {"data": json.dumps({"type": "done"})}   # 结束标志

    return EventSourceResponse(event_generator())
```

要点：
- **`event_generator` 是一个异步生成器**：它用 `yield` 一次次产出事件，`EventSourceResponse` 负责把每个事件实时推给前端
- 每个事件是形如 `{"data": "..."}` 的字典，`data` 里通常放一段 JSON，前端解析后渲染
- 真实场景里，`for char in answer` 会换成「`async for chunk in llm.astream(...)`」——也就是 2.3 学的大模型流式输出，把模型吐出的每个 token 实时转发给前端

### 2.5 面试题

#### 23. FastAPI 相比 Flask 和 Django 有哪些优势？为什么 EduAgent 选择 FastAPI？

**答案：**
FastAPI 相比 Flask 的优势在于：原生异步支持、基于类型注解的自动请求校验、自动生成 `/docs` 交互式文档、更好的性能（基于 Starlette）。相比 Django 的优势在于：轻量灵活、没有 ORM 绑定、异步原生支持、更适合微服务架构。

EduAgent 选择 FastAPI 的原因是：项目需要全异步处理大模型调用（FastAPI 天然支持 `async def`），需要自动校验请求体（Pydantic 集成），需要 SSE 流式输出（问答/面试的打字机效果），需要自动文档方便调试。

#### 24. FastAPI 在 EduAgent 中扮演什么角色？两大招牌优势是什么？

**答案：**
FastAPI 是系统的 API 层，即系统对外的「大门」，负责接收并校验请求、调用业务逻辑、返回结果。两大招牌优势是：基于类型注解自动校验（用 Pydantic 写清楚请求格式，校验全自动）和全异步（天然支持 `async def` 接口，与异步编程和大模型调用无缝配合）。同时 FastAPI 自动生成 `/docs` 交互式文档页面。

#### 25. 如何用 Pydantic 模型接收请求体？response_model 的作用是什么？

**答案：**
将 Pydantic 模型作为接口函数的参数类型（如 `req: LoginRequest`），FastAPI 会自动解析请求体 JSON 并完成校验。如果前端传的数据不符合要求，FastAPI 自动返回 422 错误。`response_model` 用于声明接口返回的数据结构，让自动文档更准确，同时过滤掉不应返回的多余字段。

#### 26. 依赖注入 Depends 的作用是什么？本项目哪两个依赖最重要？它们分别解决了什么问题？

**答案：**
`Depends` 用于复用通用逻辑，把通用的前置逻辑（如获取数据库连接、校验登录）写成一个函数，在接口参数里声明 `Depends(依赖函数)`，FastAPI 在执行接口前自动先跑依赖、把结果喂给接口。

两个最重要的依赖：
1. **`get_db`**：获取数据库会话，用 yield 型依赖实现自动提交/回滚事务。接口完全不用操心连接的开关，拿来就用。
2. **`get_current_user`**：校验登录，从请求头取出 JWT Token 校验合法性，合法返回用户信息，不合法抛出 401 错误。

#### 27. SSE 流式响应是如何实现的？EventSourceResponse 接收什么类型的参数？

**答案：**
SSE 流式响应用 `sse-starlette` 库的 `EventSourceResponse` 实现。它接收一个异步生成器，生成器每 `yield` 一次就向前端推送一个事件。每个事件是形如 `{"data": "..."}` 的字典，data 里通常放一段 JSON 字符串。在真实场景中，生成器内部使用 `async for chunk in llm.astream(...)` 获取大模型输出的每个 token，实时转发给前端。

#### 28. 什么是 yield 型依赖？get_db 的 yield 前后代码分别在什么时候执行？

**答案：**
yield 型依赖使用 `yield` 关键字将资源（如数据库会话）交给接口使用。yield 之前是准备逻辑（建立连接），yield 之后是清理逻辑（提交/回滚事务、关闭连接）。在 `get_db` 中，yield 之前创建 `AsyncSession`，yield 把 session 交给接口，接口正常结束后执行 `await session.commit()` 提交事务，异常时执行 `await session.rollback()` 回滚后抛出异常。

#### 29. 路径参数和查询参数有什么区别？分别在什么场景下使用？

**答案：**
路径参数嵌在 URL 路径中（如 `/reviews/{review_id}`），用于标识唯一资源，如查询某条审查结果。查询参数在 URL 问号后面（如 `?page=2&size=20`），用于筛选、分页、排序等非唯一标识的场景，如分页列出所有审查结果。路径参数是必填的，查询参数可以有默认值，不传时使用默认值。

#### 30. 文件上传接口中 status_code=202 的含义是什么？和 200 有什么区别？

**答案：**
202 状态码表示「已接受，正在后台处理」，适合需要先收下文件、后台慢慢处理的场景，如简历审查、试卷批改。200 表示「请求已成功处理并返回了结果」，适合同步处理场景。接口返回 202 后，可以用后台任务（`create_task`）异步处理，用户无需在前端等待，体现了「异步处理」的设计模式。

#### 31. SSE 流式响应中的事件格式是什么？前端如何接收和解析？

**答案：**
SSE 流式响应中，每个事件是形如 `{"data": "..."}` 的字典，data 字段里通常放一段 JSON 字符串，如 `{"type": "token", "content": "某"}标识事件类型。前端通过 `EventSource` API 接收，解析 `data` 字段中的 JSON 字符串，逐块渲染到页面上，形成打字机效果。最后一个事件通常是 `{"type": "done"}` 表示流式输出结束。

### 2.6.1 PostgreSQL vs MySQL：差异全景

你已经会 MySQL 了，好消息是：**两者九成是相通的**——库、表、行、列的概念一样，`SELECT/INSERT/UPDATE/DELETE` 也几乎一样。你真正需要重新认识的，是下面这些差异（也正是本项目里会遇到的）：

| 方面 | MySQL 的做法 | PostgreSQL 的做法（本项目用） |
|------|-------------|---------------------------|
| 命令行工具 | `mysql -u root -p` | `psql -U 用户 -d 库` |
| 列出所有库 | `SHOW DATABASES;` | `\l` |
| 切换库 | `USE 库名;` | `\c 库名` |
| 列出所有表 | `SHOW TABLES;` | `\dt` |
| 查看表结构 | `DESC 表名;` | `\d 表名` |
| 主键自增 | `INT AUTO_INCREMENT` | `UUID DEFAULT uuid_generate_v4()`（本项目）或 `SERIAL` |
| 布尔类型 | `TINYINT(1)`（0/1） | `BOOLEAN`（`true`/`false`） |
| JSON 类型 | `JSON` | `JSONB`（二进制存储，更快、可建索引） |
| 自动更新时间 | `ON UPDATE CURRENT_TIMESTAMP` | `TIMESTAMPTZ` + **触发器** |
| 插入或更新（upsert） | `INSERT ... ON DUPLICATE KEY UPDATE` | `INSERT ... ON CONFLICT ... DO UPDATE` |
| 插入后拿回主键 | 另调 `LAST_INSERT_ID()` | 直接 `... RETURNING id` |
| CHECK 约束 | 8.0.16 之前被忽略 | **一直严格生效** |
| 执行 SQL 文件 | `source x.sql` | `\i x.sql`（psql 内）或 `psql -f x.sql` |

---

### 2.6.2 连接方式

**psql 命令行：**

```bash
psql -h localhost -p 5433 -U eduagent_user -d eduagent
```

连上后，使用反斜杠元命令：
- `\l`：列出所有数据库（= MySQL 的 `SHOW DATABASES;`）
- `\c eduagent`：切换到 eduagent 库（= `USE eduagent;`）
- `\dt`：列出当前库所有表（= `SHOW TABLES;`）
- `\d users`：查看 users 表结构（= `DESC users;`）
- `\q`：退出

**PyCharm 数据库工具：**
连上后，PyCharm 的 Query Console 只认标准 SQL，不认 psql 的反斜杠元命令。PostgreSQL 没有 MySQL 的 `USE 库名;` 这种切库语句，切换数据库要用控制台顶部的下拉选择器。

**两个关键区别：**
1. PyCharm 的 Query Console 不认 psql 的反斜杠元命令（`\l`、`\dt`、`\c` 用不了）
2. PostgreSQL 没有 `USE 库名;` 语句，`USE` 在 PG 里会直接报语法错误

### 2.6.3 基础 CRUD：和 MySQL 几乎一样

```sql
-- 查
SELECT id, username FROM users WHERE role = 'student' LIMIT 5;
-- 增
INSERT INTO users (tenant_id, username, email, password_hash, role)
VALUES ('tenant_default', 'demo01', 'demo01@x.com', 'hash...', 'student');
-- 改（务必带 WHERE）
UPDATE users SET is_active = false WHERE username = 'demo01';
-- 删（务必带 WHERE）
DELETE FROM users WHERE username = 'demo01';
```

只有两个小地方要留意：
- **字符串一律用单引号** `'student'`，不要用双引号（PG 里双引号是给「标识符/列名」用的，和 MySQL 不同）
- **布尔值直接写 `true` / `false`**，不是 `1` / `0`

---

### 2.6.4 PG 专属特性实操

#### ① UUID 主键 + uuid-ossp 扩展

本项目主键不用自增整数，而用 UUID。PG 生成 UUID 需要先启用扩展：

```sql
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";   -- 启用一次即可

-- 建表时主键默认用 uuid_generate_v4() 自动生成
id UUID PRIMARY KEY DEFAULT uuid_generate_v4()
```

#### ② RETURNING：插入后直接拿回生成的值

MySQL 插入后要另外查 `LAST_INSERT_ID()`，而 PG 用 `RETURNING` 一步到位：

```sql
INSERT INTO demo_members (username, role, profile)
VALUES ('alice', 'student', '{"city":"上海","tags":["java","spring"]}')
RETURNING id, username;
```

实际输出（`id` 是自动生成的 UUID）：
```
                  id                  | username
--------------------------------------+----------
 4b5da03a-b4f1-449d-9780-1eaeda825180 | alice
```

#### ③ JSONB：直接存查结构化数据

本项目大量用 `JSONB`（简历的评分、批改的薄弱点、面试报告都是）。查询时用 PG 的 JSON 操作符：
- `字段 ->> '键'`：取出该键的值（**文本**）
- `字段 -> '键'`：取出该键的值（**仍是 JSON**）

```sql
SELECT username,
       profile ->> 'city'  AS city,    -- 取文本
       profile -> 'tags'   AS tags     -- 取 JSON 数组
FROM demo_members
WHERE profile ->> 'city' = '上海';      -- 还能直接按 JSON 内部的值过滤
```

#### ④ ON CONFLICT DO UPDATE：upsert

本项目保存面试 / 问答会话时，用 `thread_id` 做「有则更新、无则插入」：

```sql
INSERT INTO demo_members (username, role)
VALUES ('alice', 'teacher')                       -- alice 已存在（username 唯一）
ON CONFLICT (username) DO UPDATE
    SET role = EXCLUDED.role                       -- EXCLUDED 代表「本次想插入的那行」
RETURNING username, role;
```

- `EXCLUDED` 指代你手头这箱新货物（而不是货架上的旧货），是固定写法

#### ⑤ CHECK 约束：数据库层面拦截非法值

**和 MySQL 不同，PG 的 CHECK 一直严格生效**——插入非法值会直接被拒：

```sql
-- role 只允许 student/teacher/admin，插入 'wizard' 会被拦
INSERT INTO demo_members (username, role) VALUES ('bob', 'wizard');
-- 报错：ERROR: new row for relation "demo_members" violates check constraint
```

#### ⑥ TIMESTAMPTZ + 触发器：自动维护 updated_at

MySQL 用 `ON UPDATE CURRENT_TIMESTAMP` 让时间字段自动刷新；PG 没有这个语法糖，而是用**触发器**实现。先写一个触发器函数，再把它挂到表上：

```sql
-- 触发器函数：每次更新行时，把 updated_at 设为当前时间
CREATE OR REPLACE FUNCTION demo_touch_updated_at()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- 把函数挂到表上：每行 UPDATE 之前自动执行
CREATE TRIGGER trg_demo_updated_at
BEFORE UPDATE ON demo_members
FOR EACH ROW EXECUTE FUNCTION demo_touch_updated_at();
```

大白话解释：
- `CREATE FUNCTION`：创建一个新技能（函数），起名叫 `demo_touch_updated_at`
- `RETURNS TRIGGER`：这个技能专为触发器准备
- `NEW.updated_at = NOW()`：把准备要修改的那一行数据里面的 updated_at 字段，改成现在的时刻
- `RETURN NEW`：把改过的草稿纸还给数据库
- `CREATE TRIGGER`：把函数挂到表上，以后只要有人改这行，出发前先帮我把 updated_at 填好

### 2.6.5 schema 与「清空重建」

PostgreSQL 有 `schema`（模式）的概念，用于在同一个数据库内做逻辑隔离。本项目使用默认的 `public` schema。清空重建时，可以直接 `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` 来快速重置整个数据库。

### 2.6 面试题

#### 32. PostgreSQL 和 MySQL 在命令行工具、主键自增、布尔类型、JSON 类型、自动更新时间、upsert 这六个方面各有什么差异？

**答案：**
- 命令行工具：MySQL 用 `mysql -u root -p`，PG 用 `psql -U 用户 -d 库`
- 主键自增：MySQL 用 `INT AUTO_INCREMENT`，PG 用 `UUID DEFAULT uuid_generate_v4()` 或 `SERIAL`
- 布尔类型：MySQL 用 `TINYINT(1)`（0/1），PG 用 `BOOLEAN`（`true`/`false`）
- JSON 类型：MySQL 用 `JSON`，PG 用 `JSONB`（二进制存储，更快、可建索引）
- 自动更新时间：MySQL 用 `ON UPDATE CURRENT_TIMESTAMP`，PG 用 `TIMESTAMPTZ` + 触发器
- upsert：MySQL 用 `INSERT ... ON DUPLICATE KEY UPDATE`，PG 用 `INSERT ... ON CONFLICT ... DO UPDATE`

#### 33. RETURNING 的作用是什么？相比 MySQL 的 LAST_INSERT_ID() 有什么优势？

**答案：**
`RETURNING` 可以在 INSERT、UPDATE、DELETE 操作后直接返回指定列的值，一步到位拿到生成的主键（UUID）或其他字段。相比 MySQL 的 `LAST_INSERT_ID()` 需要额外再查一次，`RETURNING` 更简洁高效，尤其适合「插入后立刻需要那条记录的 UUID」的场景。

#### 34. JSONB 的 -> 和 ->> 操作符有什么区别？如何按 JSON 内部字段过滤？

**答案：**
- `字段 ->> '键'`：取出该键的值（文本类型）
- `字段 -> '键'`：取出该键的值（仍为 JSON 类型）

可以通过 `WHERE profile ->> 'city' = '上海'` 直接在 SQL 里按 JSON 内部的字段查询，这是 JSONB 比 MySQL 的 JSON 更顺手的地方之一。

#### 35. 什么是 EXCLUDED 关键字？在 upsert 中起什么作用？

**答案：**
在 `ON CONFLICT ... DO UPDATE` 中，`EXCLUDED` 指代本次冲突时本来要插入的那行数据（即新货物），而不是货架上的旧货。`SET role = EXCLUDED.role` 的意思是用新数据替换旧数据。`EXCLUDED` 是固定写法。

#### 36. PostgreSQL 如何实现自动维护 updated_at 字段？触发器函数和触发器分别是什么？

**答案：**
PostgreSQL 通过触发器实现，分两步：
1. 创建触发器函数：定义一个函数，将 `NEW.updated_at` 设为 `NOW()`，`NEW` 代表准备要修改的那行数据
2. 创建触发器：将函数挂到表上，指定 `BEFORE UPDATE ... FOR EACH ROW`，以后每次更新行之前自动执行该函数

这样开发者不需要在每次 `UPDATE` 时手动设置 `updated_at`，数据库会自动完成。

## 2.7 用 SQLAlchemy 异步操作数据库

### 学习目标

- 掌握用 SQLAlchemy 异步连接 PostgreSQL 的三件套
- 掌握用 `text()` + 参数化查询执行原生 SQL
- 掌握完整的 CRUD 操作和事务管理
- 能把 FastAPI 依赖注入、参数化查询、`run_in_executor` 串起来写出完整接口

---

### 2.7.1 从手敲 SQL 到 Python 操作数据库

Python 操作 PostgreSQL 的「异步三件套」：

```python
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker, AsyncSession

DATABASE_URL = "postgresql+asyncpg://eduagent_user:密码@localhost:5433/eduagent"

engine = create_async_engine(DATABASE_URL)                    # ① 创建引擎
AsyncSessionLocal = async_sessionmaker(engine, expire_on_commit=False)  # ② 创建会话工厂
```

- **`create_async_engine`**：创建异步引擎，负责管理数据库连接池
- **`async_sessionmaker`**：创建异步会话工厂，每次调用返回一个 `AsyncSession` 实例
- **`AsyncSession`**：异步会话，用于执行 SQL 语句和管理事务

换数据库只需换连接地址。例如从 PostgreSQL 切换到 MySQL，只需将 `DATABASE_URL` 改为 `mysql+aiomysql://...` 即可。

---

### 2.7.2 text() + 参数化查询

SQLAlchemy 支持直接写原生 SQL，用 `text()` 包装，使用 `:名字` 占位符 + 字典传值实现参数化查询：

```python
from sqlalchemy import text

# SELECT
result = await db.execute(
    text("SELECT id, username FROM users WHERE role = :role LIMIT :limit"),
    {"role": "student", "limit": 5}
)
rows = result.fetchall()       # 返回所有行，每行是一个 Row 对象
# 或 rows = result.mappings().fetchall()  # 返回字典列表，每行是 {"id": ..., "username": ...}

# INSERT
await db.execute(
    text("INSERT INTO users (tenant_id, username, email, password_hash, role) VALUES (:tenant, :name, :email, :pwd, :role)"),
    {"tenant": "default", "name": "demo01", "email": "demo@x.com", "pwd": "hash...", "role": "student"}
)
await db.commit()  # INSERT/UPDATE/DELETE 需要提交事务

# UPDATE
await db.execute(
    text("UPDATE users SET is_active = :active WHERE username = :name"),
    {"active": False, "name": "demo01"}
)
await db.commit()

# DELETE
await db.execute(
    text("DELETE FROM users WHERE username = :name"),
    {"name": "demo01"}
)
await db.commit()
```

**为什么禁止 f-string 拼接 SQL？** 因为存在 SQL 注入风险。如果用户输入 `"'; DROP TABLE users; --"`，用 f-string 拼接可能导致灾难性后果。参数化查询用 `:名字` 占位符 + 字典传值，SQLAlchemy 会自动处理转义，彻底杜绝注入。

**读取结果的方法：**
- `fetchone()`：取一行，返回 Row 对象或 None
- `fetchall()`：取所有行，返回 Row 列表
- `mappings()`：将结果转换为字典形式，可通过列名访问（推荐）

---

### 2.7.3 完整 CRUD 示例

```python
import asyncio
from sqlalchemy import text
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker

DATABASE_URL = "postgresql+asyncpg://eduagent_user:密码@localhost:5433/eduagent"
engine = create_async_engine(DATABASE_URL)
AsyncSessionLocal = async_sessionmaker(engine, expire_on_commit=False)

async def main():
    async with AsyncSessionLocal() as db:
        # 建表
        await db.execute(text("""
            CREATE TABLE IF NOT EXISTS demo_users (
                id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
                username VARCHAR(50) UNIQUE NOT NULL,
                score INTEGER NOT NULL CHECK (score >= 0 AND score <= 100)
            )
        """))
        await db.commit()

        # 插入
        await db.execute(
            text("INSERT INTO demo_users (username, score) VALUES (:name, :score)"),
            {"name": "小明", "score": 85}
        )
        await db.commit()

        # 查询
        result = await db.execute(
            text("SELECT id, username, score FROM demo_users ORDER BY username")
        )
        for row in result.mappings():
            print(row["username"], row["score"])

asyncio.run(main())
```

**事务管理：** `async with AsyncSessionLocal() as db` 会自动管理事务。`await db.commit()` 提交事务；如果发生异常，`db.rollback()` 回滚事务。在项目中，这些事务逻辑由 `get_db` 依赖自动处理，接口里不需要手动 commit/rollback。

### 2.7.4 串起来：接口+数据库+依赖注入

```python
from fastapi import FastAPI, Depends, HTTPException
from sqlalchemy import text
from sqlalchemy.ext.asyncio import AsyncSession
from pydantic import BaseModel, Field

app = FastAPI()

class LoginRequest(BaseModel):
    username: str
    password: str

class TokenResponse(BaseModel):
    access_token: str
    role: str

@app.post("/login", response_model=TokenResponse)
async def login(req: LoginRequest, db: AsyncSession = Depends(get_db)):
    # 参数化查询
    result = await db.execute(
        text("SELECT id, password_hash, role FROM users WHERE username = :name"),
        {"name": req.username}
    )
    user = result.mappings().fetchone()
    if not user:
        raise HTTPException(status_code=401, detail="用户名或密码错误")

    # 密码校验使用 run_in_executor（bcrypt 是同步阻塞的）
    loop = asyncio.get_running_loop()
    is_valid = await loop.run_in_executor(None, verify_password, req.password, user["password_hash"])
    if not is_valid:
        raise HTTPException(status_code=401, detail="用户名或密码错误")

    return TokenResponse(access_token=create_jwt(user["id"], user["role"]), role=user["role"])
```

这个接口展示了如何把本章学到的各种技能融会贯通：
- FastAPI 依赖注入（`get_db` 自动提供数据库会话）
- Pydantic 模型（`LoginRequest` 接收请求，`TokenResponse` 约束响应）
- 参数化查询（`:name` 占位符防止 SQL 注入）
- `run_in_executor` 包装同步阻塞操作（`verify_password` 密码校验）
- 异步调用（`await db.execute`、`await loop.run_in_executor`）

## 2.8 状态合并与 Reducer（选读）

### 2.8.1 默认规则：覆盖式合并

LangGraph 的默认合并规则是**覆盖**：当节点返回一个字典时，LangGraph 会把返回的字段直接覆盖 State 中同名字段的值。

```python
def node_a(state):
    return {"name": "小明", "score": 85}

def node_b(state):
    return {"score": 90}  # 只覆盖 score，name 保持原样
```

---

### 2.8.2 列表字段的问题

当 State 中有列表字段时，覆盖式合并会导致问题——如果多个节点都向同一个列表添加内容，后面的节点会覆盖前面的节点添加的内容，导致数据丢失。

```python
class ChatState(TypedDict):
    messages: list  # 如果每个节点都返回 {"messages": [新消息]}，后一个会覆盖前一个
```

---

### 2.8.3 Reducer 解决方案

Reducer 是一个「合并函数」，它告诉 LangGraph 当节点返回某个字段时，如何将其与 State 中已有的值合并，而不是简单覆盖。使用 `Annotated` 类型注解来指定 Reducer：

```python
from typing import Annotated, TypedDict
from operator import add

class StateWithReducer(TypedDict):
    messages: Annotated[list, add]  # 使用 operator.add 实现列表拼接
```

`operator.add` 对于列表来说就是拼接——`[1, 2] + [3, 4] = [1, 2, 3, 4]`。这样多个节点向 `messages` 添加内容时，不会覆盖，而是追加。

---

### 2.8.4 add_messages

`add_messages` 是 LangGraph 为消息列表量身定制的 Reducer，比 `operator.add` 更智能：

- **追加**：新消息自动追加到历史末尾
- **自动包装**：如果传入的是字符串，它会自动包装成 `HumanMessage`
- **ID 去重**：如果消息有 `id` 字段，相同 `id` 的消息会替换而不是重复追加

```python
from langgraph.graph.message import add_messages
from typing import Annotated, TypedDict

class ChatState(TypedDict):
    messages: Annotated[list, add_messages]
```

---

### 2.8.5 自定义 Reducer 示例

除了内置的 `operator.add` 和 `add_messages`，你还可以自定义 Reducer 函数：

```python
from typing import Annotated, TypedDict

def accumulate_total(current_total: int, update: int) -> int:
    """累加器：每次更新时累加"""
    return current_total + update

class StatsState(TypedDict):
    total: Annotated[int, accumulate_total]
```

### 2.8 面试题

#### 40. LangGraph 默认的状态合并规则是什么？列表字段使用默认规则会有什么问题？

**答案：**
默认规则是覆盖式合并：节点返回的字典中的字段直接覆盖 State 中同名字段的值。列表字段使用默认规则会导致数据丢失——如果多个节点都向同一个列表添加内容，后一个节点会覆盖前一个节点添加的内容。

#### 41. Reducer 是什么？如何为字段指定 Reducer？

**答案：**
Reducer 是一个合并函数，告诉 LangGraph 当节点返回某个字段时，如何将其与 State 中已有的值合并，而不是简单覆盖。使用 `Annotated` 类型注解来指定 Reducer：`字段名: Annotated[类型, 合并函数]`。

#### 42. add_messages 相比 operator.add 有哪些额外功能？

**答案：**
`add_messages` 是 LangGraph 为消息列表量身定制的 Reducer，比 `operator.add` 更智能的三个功能：
1. **追加**：新消息自动追加到历史末尾
2. **自动包装**：如果传入的是字符串，自动包装成 `HumanMessage`
3. **ID 去重**：如果消息有 `id` 字段，相同 `id` 的消息会替换而不是重复追加

#### 43. 如何自定义 Reducer 函数？请给出一个累加器的例子。

**答案：**
自定义 Reducer 是一个普通的 Python 函数，接收两个参数（当前 State 中的值和节点返回的更新值），返回合并后的新值。使用 `Annotated[类型, 自定义函数]` 指定。

累加器示例：
```python
from typing import Annotated, TypedDict

def accumulate_total(current_total: int, update: int) -> int:
    return current_total + update

class StatsState(TypedDict):
    total: Annotated[int, accumulate_total]
```
这样每次节点返回 `{"total": 5}` 时，不会覆盖 `total`，而是累加。

#### 44. 在 LangGraph 中，什么情况下必须使用 Reducer？不使用会有什么后果？

**答案：**
当 State 中的字段需要被多个节点或同一次调用的多个步骤累积更新时，必须使用 Reducer。典型的场景是消息列表（`messages`），每轮对话都需要向列表追加新消息，而不是覆盖历史。

如果不使用 Reducer，后一个节点返回 `{"messages": [新消息]}` 会完全覆盖前一个节点添加的消息，导致对话历史丢失。Reducer 告诉 LangGraph 如何合并，而不是简单覆盖。
