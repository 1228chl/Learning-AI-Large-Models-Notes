### 3.1.1 基础设施总览

EduAgent 应用层真正连接的基础设施只有两个：

- **PostgreSQL**：关系型数据库，存用户、试卷、批改记录、会话等业务数据
- **Milvus**：向量数据库，存知识库文档的向量，支撑问答 Agent 的 RAG 检索

Milvus 运行时需要两个内部依赖——**etcd**（存元数据）和 **MinIO**（存向量文件）。这两个容器是给 Milvus 用的，应用代码完全不直接访问它们。

### 3.1.2 端口隔离设计

项目采用"端口隔离"策略，所有服务使用错开端口避免与本机已有服务冲突：

| 服务 | 容器内端口 | 对外端口 | 用途 | 应用是否直接连 |
|------|-----------|---------|------|---------------|
| PostgreSQL | 5432 | **5433** | 业务数据 | 是 |
| Milvus | 19530 | **19531** | 向量数据 | 是 |
| etcd | 2379 | 不对外 | Milvus 元数据 | 否（Milvus 内部用） |
| MinIO | 9000 | 不对外 | Milvus 向量文件存储 | 否（Milvus 内部用） |
| FastAPI 后端 | -- | **8000** | 主应用 | -- |

所有端口都从 `.env.local` 读取，代码里绝不写死。

## 3.2 数据库设计与建表

### 学习目标

- 理解三大贯穿性设计：UUID 主键、多租户 tenant_id、时间戳 + 自动更新触发器
- 掌握 11 张表的用途和关键字段
- 理解多租户设计：按 tenant_id 隔离数据
- 掌握数据库会话依赖 `get_db` 和自动迁移机制 `migrations.py`

### 3.2.1 三大贯穿性设计

**设计一：UUID 主键**

- 所有表的主键都用 `UUID DEFAULT gen_random_uuid()`，而不是自增整数
- 优点：全局唯一，不怕冲突，前端不必暴露自增 ID 猜数据量
- `gen_random_uuid()` 是 PostgreSQL 内置的 UUID 生成函数

**设计二：多租户 tenant_id**

- 几乎所有表都有 `tenant_id VARCHAR(64) NOT NULL` 字段
- 用于多校区数据隔离，不同租户的数据物理上在同一张表但逻辑隔离
- 默认值 `tenant_default`，单租户场景下也能跑

**设计三：时间戳 + 自动更新触发器**

- 每张表都有 `created_at` 和 `updated_at`（TIMESTAMPTZ 类型）
- 用 `update_updated_at_column()` 触发器函数自动维护 `updated_at`
- 业务代码无需手动维护修改时间

## 3.3 配置、日志与异常体系

### 学习目标

- 实现 `config.py`：用 Pydantic `BaseSettings` 读取 `.env.local`
- 实现 `logger.py`：结构化日志，支持 `logger.info("event", key=value)` 风格
- 实现 `exceptions.py`：EduAgent 统一异常类层次，为三层兜底打基础

### 3.3.1 config.py — 配置中心

**核心设计**：

- 继承 `BaseSettings`，自动从 `.env.local` 读取所有配置项
- 每个类属性对应 `.env.local` 里的一项（大小写不敏感）
- 无默认值的字段为必填项（如 `db_user`, `db_password`, `deepseek_api_key`, `jwt_secret_key`）
- `@property` 动态拼接 `database_url`，避免在 `.env.local` 存一长串
- `@lru_cache()` 保证全局单例——只创建一次 Settings、只读一次文件

**class Config 关键配置**：

- `env_file = ".env.local"`：指定读取文件
- `extra = "ignore"`：.env.local 里多出的字段自动忽略
- `case_sensitive = False`：大小写不敏感

**配置项分组**：数据库（PostgreSQL）、Milvus、大模型（DeepSeek）、本地模型路径、JWT 认证、MCP Server 地址、Web 搜索、应用基础配置

### 3.3.2 logger.py — 结构化日志

**核心设计**：

- `_Logger` 类：包装标准库 `logging`，支持 `logger.info("事件", key=value)` 写法
- `_fmt()` 方法：把事件名 + 关键字参数格式化为 `"事件 | key=value"` 字符串
- `configure_logging()`：全局只调一次，设置日志格式、级别，压制第三方库噪音
- `get_logger(name)` 工厂函数：每个模块用它拿 logger

**噪音压制**：将 sqlalchemy.engine、sqlalchemy.pool、httpx、httpcore 的日志级别提到 WARNING。

### 3.3.3 exceptions.py — 统一异常体系

**基类**：`EduAgentBaseError(Exception)`

- 比普通异常多带 `agent_type`（哪个 Agent 出错）和 `details`（任意细节字典）
- 所有自定义异常都继承自它

**7 个子类**：

| 异常类 | 说明 | 可重试 |
|--------|------|--------|
| LLMAPIError | 大模型 API 调用失败 | 是 |
| AgentExecutionError | Agent 业务逻辑执行失败 | 视情况 |
| PipelineError | 多 Agent 流水线编排失败 | 视情况 |
| IntentRouteError | 意图识别路由失败 | 视情况 |
| MilvusConnectionError | Milvus 连接失败 | 是 |
| FileParseError | 文件解析失败（Word/PDF） | 否 |
| InvalidInputError | 用户输入不合法 | 否 |
| AuthenticationError | 认证失败 | 否 |

## 3.4 LLM Factory：统一的大模型工厂

### 学习目标

- 理解为什么需要 LLM Factory 封装
- 实现 `LLMFactory`：按 Agent 类型路由模型、带缓存、统一配置
- 掌握 `get_llm` 和 `get_structured_llm` 两个核心入口
- 理解 `trust_env=False` 绕过系统代理的坑

### 3.4.1 为什么需要 LLM Factory

直接在各 Agent 里调用 `init_chat_model` 的问题：

1. **配置重复**：每处都要写 model_provider、base_url、api_key、temperature
2. **无法复用实例**：同样的模型被反复创建，浪费资源
3. **难以统一管控**：给所有模型加超时、关重试、绕代理，得改无数处

LLM Factory 把这些问题收口到一处，项目规定：**所有 Agent 必须通过工厂获取模型，禁止直接调用 `init_chat_model` **。

### 3.4.2 核心设计

**两个核心入口**：

- `get_llm(agent_type, temperature=0, streaming=False)`：拿普通模型
- `get_structured_llm(agent_type, output_schema)`：拿绑定 Pydantic 结构的模型

**关键设计点**：

1. **自定义 httpx 客户端**：`trust_env=False` 绕过系统代理（Windows 系统代理或 HTTPS_PROXY 环境变量会被 httpx 默认探测到，导致 DeepSeek 请求失败）
2. **Agent 类型→模型路由表**：用字典映射业务类型到具体模型，扩展性好
3. **按组合缓存实例**：缓存键 = `模型_温度_是否流式`，相同参数只创建一次
4. ** `max_retries=0` **：模型层不重试，重试统一由 retry.py 管理
5. ** `temperature=0` **：默认 0，评分/批改需要稳定输出

**Agent 类型路由表**（当前全部使用 deepseek-chat）：

- qa（智能问答）、exam_subjective（简答题批改）、exam_code（代码题批改）
- resume（简历审查）、interview（模拟面试）、intent（意图识别）、summarize（对话摘要）

## 3.5 三层兜底与重试机制

### 学习目标

- 理解三层兜底设计：自动重试 → Agent 级降级 → 系统级兜底
- 掌握用装饰器给任意异步函数加上自动重试与降级能力
- 理解可重试异常 vs 不可重试异常的区分

### 3.5.1 三层兜底总览

| 层级 | 触发条件 | 处理方式 |
|------|---------|---------|
| **第一层：自动重试** | 网络抖动/LLM 超时等短暂故障 | 自动重试最多 2 次（间隔 1s/3s），消化偶发故障 |
| **第二层：Agent 级降级** | 重试 2 次仍失败 | 退化为简单实现：问答→跳过检索直接答，批改→标记教师复核 |
| **第三层：系统级兜底** | 连降级都失败 | 返回友好提示，保证用户始终能收到响应 |

### 3.5.2 异常分类

```python
RETRYABLE_ERRORS = (LLMAPIError, MilvusConnectionError, TimeoutError, ConnectionError)
NON_RETRYABLE_ERRORS = (InvalidInputError, AuthenticationError)
```

### 3.5.3 装饰器工厂

`@with_retry(agent_type="qa")` 是一个装饰器工厂，三层嵌套函数：

- 最外层：接收参数（agent_type）
- 中间层：接收被装饰的函数
- 最内层：真正的执行逻辑（三层兜底都在这里）

**第一层**：for 循环最多跑 3 次，每次用 `asyncio.wait_for` 加 30 秒超时

- 成功 → 立即返回
- 不可重试异常 → 立即抛出
- 可重试异常 → 等待后重试，到上限后去降级

**第二层**：`AgentFallbackHandler` 按 agent_type 找降级策略

**第三层**：`_system_fallback_response` 返回友好提示

### 3.5.4 五个降级函数

| 降级函数 | 触发场景 | 返回内容 |
|---------|---------|---------|
| `_qa_fallback` | 知识库/模型不可用 | 静态提示语，标记 fallback_used |
| `_exam_code_fallback` | 代码评分超时/失败 | 标记 needs_teacher_review |
| `_exam_subjective_fallback` | 简答题 LLM 评分失败 | 标记 needs_teacher_review |
| `_resume_fallback` | 简历服务不可用 | 静态提示语 |
| `_interview_fallback` | 面试服务不可用 | 静态提示语 |

降级函数统一返回字典（对接 LangGraph 节点约定，接收完整 State，返回要更新的字段）。

## 3.6 认证与依赖注入

### 学习目标

- 理解 JWT 登录认证完整流程
- 实现密码的 bcrypt 哈希与校验
- 补全 `dependencies.py` 最终版（加上 `get_current_user`）
- 实现登录接口（`/login` 与 `/me`）

### 3.6.1 JWT 认证流程

```python
① 用户 POST /login（用户名+密码）
        │
        ▼
② 服务端查库、用 bcrypt 校验密码
        │  校验通过
        ▼
③ 签发 JWT Token（内含 user_id/role/tenant_id），返回给前端
        │
        ▼
④ 后续请求带上 Authorization: Bearer <token>
        │
        ▼
⑤ get_current_user 依赖解码 Token、验证有效性 → 拿到当前用户身份
```

### 3.6.2 bcrypt 密码安全

- 数据库里绝不存明文密码，存 `password_hash` 字段
- `passlib` 的 `CryptContext` 封装 bcrypt 算法
- `bcrypt` 特征：单向不可逆、自带盐值（同样密码每次哈希结果不同）
- 版本兼容坑：`bcrypt>=4.0` 删掉了 `__about__`，需手动注入一个假的 `__about__` 兜底
- 密码校验是 CPU 密集型操作（约 100ms），在异步接口里用 `run_in_executor` 丢到线程池

### 3.6.3 dependencies.py 最终版

提供两个 FastAPI 依赖：

1. `get_db`：异步数据库会话，自动提交/回滚/关闭
2. `get_current_user`：从请求头取 JWT、解码、验证，返回用户身份

`get_current_user` 使用 `HTTPBearer` 自动解析 `Authorization: Bearer <token>` 头，用 `python-jose` 的 `jwt.decode()` 解码验证。

### 3.6.4 接口实现

- `POST /login`：查用户（支持用户名或邮箱）→ 检查是否禁用 → 线程池校验密码 → 签发 Token
- `GET /me`：声明 `Depends(get_current_user)`，自动完成鉴权，返回用户身份

### 3.6.5 seed_data.py

灌入测试账号（如 admin/student/teacher 等角色），使用 bcrypt 哈希存储密码。

## 3.7 数据库表结构详解（扩展）

### 3.7.1 设计原则总结

- **UUID 主键**：所有表用 `UUID DEFAULT gen_random_uuid()`，全局唯一，不怕冲突
- **多租户**：`tenant_id` 字段贯穿所有业务表，按租户隔离数据
- **时间戳**：`created_at` + `updated_at` 配合触发器自动维护
- **JSONB 字段**：灵活存储结构化/半结构化数据（如 AI 评分结果、简历解析数据）
- **冗余设计**：`exam_reviews` 表冗余了 `question_type` 和 `knowledge_tag`，避免频繁 JOIN
- **级联删除**：外键关联使用 `ON DELETE CASCADE`，如试卷删除则题目级联删除

### 3.7.2 索引策略

- 租户查询索引：`idx_xxx_tenant_id`（几乎所有表）
- 业务查询索引：按 `exam_id`、`student_id`、`status` 等高频查询字段建立
- 筛选加速索引：`needs_review`、`is_active`、`difficulty` 等布尔/枚举字段
