## 10.1 全景回顾与系统总览

### 10.1.1 我们从零建成了什么

经过前面七章，你亲手写出了一个完整的后端系统——**EduAgent**：一个 IT 教培方向的 AI 原生多 Agent 教学辅助系统。技术栈是 LangChain 1.2.10 + LangGraph 1.0.9 + FastAPI + DeepSeek + Milvus + PostgreSQL。

它不是一个玩具 demo，而是具备：四个各司其职的专业 Agent、一套统一的对外入口、完整的异常/重试/降级体系、本地模型与 RAG 知识库、多轮对话记忆与持久化、以及把这一切装配起来的应用骨架。

**一句话概括整个系统：用户说一句话，系统自动听懂意图、路由到对的 Agent（或几个 Agent 串联）、执行并以流式返回结果，全程有记忆、能降级、可观测。**

### 10.1.2 三层架构总览

整个系统可以清晰地分成三层，自下而上：

```python
┌───────────────────────────────────────────────────────────────┐
│  集成层（第8章）                                                │
│    unified_chat.py  统一入口：前置拦截 + LLM 路由 + SSE 分发      │
│    orchestrator.py  编排器：单Agent直达 / 多Agent串联           │
│    main.py          应用装配：lifespan + 路由 + MCP + health     │
└───────────────────┬───────────────────────────────────────────┘
                    │ 调度
┌───────────────────▼───────────────────────────────────────────┐
│  Agent层（第4-7章）—— 四个Agent，四种LangGraph范式               │
│    简历审查（并行） QA（RAG） 试卷批改（HitL） 模拟面试（状态机+SSE）│
└───────────────────┬───────────────────────────────────────────┘
                    │ 复用
┌───────────────────▼───────────────────────────────────────────┐
│  地基层（第3章+第5章公共件）—— 所有Agent共用                      │
│    config / logger / exceptions / retry / llm_factory           │
│    memory（MemorySaver+摘要）/ 本地模型 / MCP / 认证              │
└───────────────────────────────────────────────────────────────┘
```

- **地基层**不感知任何 Agent 的业务逻辑，只提供底层能力（取模型、记忆、异常、重试、认证）。
- **Agent 层**每个 Agent 是一张独立的 LangGraph 图，复用地基层，互不依赖。
- **集成层**站在最上面，把四个 Agent 统一到一个入口背后，对用户屏蔽内部结构。

### 10.1.3 四个 Agent 与四种 LangGraph 范式

这是整门课的教学主线——**同一套 LangGraph 技术，用四种典型范式各演示一遍**。

| Agent | 章节 | LangGraph 范式 | 核心机制 | 解决的问题 |
|-------|------|--------------|---------|-----------|
| 简历审查 | 第 4 章 | **并行评审** | fan-out 多分支并行→fan-in 聚合 | 一份输入要从多个维度同时评估 |
| 智能问答 | 第 5 章 | **RAG** | 检索→精排→增强生成 | 让 LLM 基于私有知识库回答 |
| 试卷批改 | 第 6 章 | **Human-in-the-Loop** | interrupt 暂停→人工介入→resume 恢复 | 关键决策需要人来把关 |
| 模拟面试 | 第 7 章 | **状态机+SSE** | 阶段流转+多轮对话+流式输出 | 有明确阶段的长流程交互 |

这四种范式覆盖了现实里多 Agent 系统最常见的控制流，可以组合与变形迁移到大量其他场景。

### 10.1.4 公共地基：被所有 Agent 复用的零件

| 公共件 | 文件 | 章节 | 提供的能力 |
|-------|------|------|-----------|
| 配置中心 | config.py | 第 3 章 | 所有环境变量的唯一真相源（Settings） |
| 结构化日志 | core/logger.py | 3.3 | 统一日志格式，便于检索定位 |
| 异常体系 | core/exceptions.py | 3.3 | EduAgentBaseError + 子类，按类型决定降级 |
| 重试降级 | core/retry.py | 3.5 | with_retry 三层兜底（重试→Agent 降级→系统兜底） |
| LLM 工厂 | core/llm_factory.py | 3.4 | get_llm / get_structured_llm，统一取模型+缓存 |
| 认证 | dependencies.py | 3.6 | get_current_user，JWT 鉴权 |
| 记忆管理 | core/memory.py | 5.10 | MemorySaver 隔离、thread_id、滑动窗口、摘要压缩 |
| 本地模型 | reranker / classifier / embedder | 5.8/5.9/5.4 | 精排、意图分类、向量嵌入 |
| 知识库 | core/knowledge_base.py | 5.4/5.18 | 文档向量化入 Milvus+检索 |

**一个贯穿全课的设计原则**：调 LLM 一律走 `get_llm` / `get_structured_llm`，绝不在节点里手搓模型；存对话一律走 MemorySaver + `thread_id`；调用失败一律靠 `with_retry` 兜底。**统一入口收敛，是大型系统可维护的前提**。

### 10.1.5 集成层：从四个孤岛到一个系统

第 8 章把四个独立 Agent 拧成系统，靠两个核心角色：

- **接待员 unified_chat.py**：规则前置拦截处理社交/元场景（零 Token），LLM 路由判 6 类意图，按 label 分四支（qa 流式/引导跳转/pipeline 计划/澄清）。
- **调度台 orchestrator.py**：拿到明确的 agent_type 后直调对应图；或按预置 Pipeline 串联多个 Agent，把前序的结构化输出注入后序的上下文。
- **应用骨架 main.py**：lifespan 启动时跑迁移、并行预热三个本地模型、驱动 MCP；再挂路由、配 CORS、暴露/health。

### 10.1.6 一条请求的完整生命周期

用户说"什么是 RAG 的核心原理？"，请求穿过三层：

```python
[unified_chat] 前置拦截未命中→LLM路由判为qa→推routing_decision事件
[orchestrator] 单Agent直达→懒加载QA图→@with_retry包裹调用
[load_memory]  读MemorySaver历史（thread_id定位）+ 摘要
[classify]     意图分类器（MiniLM）判通用/专项
[retrieve]     BGE-M3嵌入→Milvus检索
[rerank]       BGE-Reranker精排
[generate]     get_llm("qa")增强生成→流式token
[unified_chat] 透传progress + token + meta事件→SSE流式返回
```

## 10.2 多 Agent 能力迁移场景

### 10.2.0 迁移方法论：四步拆解

拿到任何一个业务需求，按下面四步就能拆出一套多 Agent 架构：

**第一步：找"角色"**。问自己——如果这件事交给一个团队做，会有哪些不同专业的人？每个"专业角色"通常对应一个 Agent。

**第二步：给每个角色定范式**。看这个角色的工作性质，套 EduAgent 的四种范式：

| 工作性质 | 范式 | EduAgent 出处 |
|---------|------|-------------|
| 一个输入要从多个维度同时评估 | **并行评审** | 简历六维（第 4 章） |
| 需要基于私有知识/文档回答 | **RAG** | QA（第 5 章） |
| 关键决策必须人来把关 | **Human-in-the-Loop** | 试卷批改（第 6 章） |
| 有明确阶段的多轮交互 | **状态机+多轮** | 模拟面试（第 7 章） |

**第三步：定编排方式**。看角色之间是什么关系：互斥→路由分发；有先后依赖→串联 Pipeline；同时进行→并行 fan-out。

**第四步：补地基**。不管什么场景，都需要：取模型（get_llm）、记忆（MemorySaver+thread_id）、容错（with_retry 三层兜底）、统一入口（路由+SSE）。

> **一句话**：业务=一组角色，角色=一个 Agent+一种范式，系统=路由/串联/并行把角色编排起来，再架在通用地基上。

### 10.2.1 场景一：智能客服中台

**业务背景**：电商/SaaS 客服每天面对海量咨询：售前问产品、售后查订单、要退换货、闹投诉。这些诉求性质完全不同，用一个大 Prompt 硬接会四不像。

**Agent 拆解**：

- 意图路由 Agent（范式：LLM 路由+规则前置拦截，对应 8.4）
- FAQ 问答 Agent（范式：RAG，对应第 5 章）
- 订单状态 Agent（范式：多轮状态机，对应第 7 章）
- 退换货流程 Agent（范式：HitL，对应第 6 章）
- 投诉升级 Agent（范式：HitL 安全兜底）

**编排方式**：主体是路由分发；退换货场景里"先 RAG 确认政策、再发起退货流程"是一段串联 Pipeline。

**简历一句话**：基于 LangGraph+FastAPI 构建多 Agent 智能客服中台：规则前置拦截+LLM 意图路由分发至 FAQ-RAG/订单状态机/退换货 HitL 审批四类 Agent，SSE 流式响应，三层兜底保障高可用，客服人工介入率下降 X%。

### 10.2.2 场景二：合同/法律审查助手

**Agent 拆解**：

- 条款拆解 Agent（范式：结构化抽取，get_structured_llm）

### 10.2.3 场景三：研发协作与代码审查平台

**Agent 拆解**：

## 10.3 多 Agent 系统面试题集（20+题）

### 架构与编排

**Q1：多个 Agent 之间怎么协作？单 Agent 和多 Agent 串联怎么选？**

**答**：EduAgent 编排器 `core/orchestrator.py`（8.2/8.3）统一入口 `handle(request)`，按 `pipeline_mode` 分两条路——单 Agent 直达 `_run_single_agent`（最常见，直调对应图），多 Agent 串联 `_run_pipeline`（求职全链路：简历审查→模拟面试）。选择标准：诉求互斥用路由分发，有先后依赖用 Pipeline，同时进行用并行。生产里还可引入动态编排（由 LLM/规划器在运行时决定调用哪些 Agent，什么顺序）。

**Q2：Agent 之间怎么传递上下文？前一个的结果怎么给到后一个？**

**答**：Pipeline 里前序 Agent 的 `structured_output` 以 `{agent}_result` 为 key 注入 `current_context`，后序 Agent 通过 `**request.context` 平铺进自己的 State（`_run_pipeline`，8.3）。配合 MemorySaver+ `thread_id`（5.10）保证同一会话的历史可恢复。每步用独立 `session_id` 后缀防检查点串台。扩展可做跨 Agent 的共享语义记忆（把关键事实写入向量库/记忆层，任意 Agent 可检索），以及结构化的 blackboard黑板模式。

**Q3：为什么 Agent 图要懒加载？一次性全加载不行吗？**

**答**：`_get_agent_graph`（8.2）首次用到某 Agent 才 build 它的图并缓存，因为每个图有 Milvus 连接、本地模型等初始化开销，全量加载拖慢启动且浪费没用到的资源。配合 `get_orchestrator` 单例（8.3）让图缓存全程复用、只 build 一次。超大规模下可把 Agent 拆成独立微服务，编排器通过 RPC 调用，各 Agent 独立扩缩容。

### 意图识别与路由

**Q4：怎么判断用户请求该路由给哪个 Agent？用大模型还是分类模型？**

**答**：EduAgent 两层路由（`unified_chat.py`，8.4）——(1)规则前置拦截 `_pre_filter` 处理问候/感谢等社交场景（零 Token）；(2) `_llm_route` 用 DeepSeek 判 6 类意图。**跨 Agent 路由调用频率低、语义差异大，用 LLM 直接判更准且免维护模型**；而 QA 内部的"通用/专项"分类调用频率高，才用本地 MiniLM（5.9）。两个场景用不同方案，是关键取舍点。高并发下可加一层语义缓存（相同/相似 query 命中缓存的路由结果）。

**Q5：路由判错了怎么办？意图不明确怎么处理？**

**答**：`_llm_route` 异常或返回非法 label 时**降级回 qa**，不阻断 SSE 流（8.4）；意图不明返回 `clarify` 分支，推追问引导（8.5）。可扩展为带置信度的多轮澄清环（低置信度时反问确认），以及路由结果可纠错机制（用户点"不对，我要的是 X"后修正并记忆）。

### 可靠性与容错

**Q6：Agent 调用大模型失败（超时/限流/网络）怎么办？**

**答**：三层兜底 `core/retry.py` 的 `with_retry` 装饰器（3.5）——第一层自动重试（最多 3 次，固定退避 1s/3s，30s 超时保护，按异常类型区分可重试/不可重试）；第二层 Agent 级降级（`AgentFallbackHandler`，如 QA 跳过 RAG 直接 LLM 答+标注）；第三层系统级兜底（`_system_fallback_response` 返回友好提示，保证用户一定收到响应）。配合 `core/exceptions.py`（3.3）的语义化异常按类型决定策略。可加熔断器（连续失败后短路一段时间，避免雪崩）、死信队列、多模型 failover。

**Q7：怎么保证不管内部怎么崩，API 层总能拿到合法响应？**

**答**：编排器 `handle` 最外层包 `try/except`（8.2），即使 `with_retry` 三层全失败，也返回 `AgentResponse(success=False, content=友好文案)`，绝不把异常抛到 API 层。这是"最外层保险"，与 `with_retry` 的"执行内兜底"是两个层次。可补全局异常中间件（FastAPI 层统一兜底+错误码规范）、优雅降级开关（特性 flag 一键降级某Agent）。

### 记忆与上下文管理

**Q8：长对话怎么办？历史越来越长会撑爆上下文窗口？**

**答**：`core/memory.py`（5.10）双管齐下—— `trim_messages_to_window` 滑动窗口只裁"送给 LLM 看的内容"（State 里仍存完整历史）；`should_trigger_summary` + `compress_to_summary` 在超过阈值时**增量摘要压缩**（带上旧摘要一起压，不重复记录），摘要存 DB，下次 load 时注入 System Prompt。可做分层记忆（工作记忆/情景记忆/语义记忆分开存取）、重要性加权的记忆淘汰。

**Q9：多个 Agent 的对话记忆怎么隔离？会不会串台？**

**答**：每个 Agent 用独立的 MemorySaver 实例（`get_memory_saver("interview")`，5.10），因为不同 Agent 的 State schema 不同，共用会导致 msgpack 反序列化用错 schema。`thread_id` 用 `student_{id}_session_{id}` 格式（5.10）保证同一学员不同会话隔离；Pipeline 里每步再加 `_step{idx}` 后缀防串台（8.3）。多租户场景可在 thread_id 再加 `tenant_` 前缀做租户级隔离。

### 结构化输出与可控性

**Q10：让大模型返回 JSON，但它经常返回不稳定怎么办？**

**答**：统一走 `get_structured_llm`（`llm_factory`，3.4），内部 `with_structured_output(schema, method="function_calling")` 强制用 function calling 约束输出（DeepSeek 不支持 json_schema 模式）。面试报告生成（7.9）还做了兜底：复杂 schema 偶发返回 None 时，给一份保守的结构化默认值，不让流程崩。可加输出校验+自动修复重试（Pydantic 校验失败->把错误喂回 LLM 让它改）。

**Q11：怎么控制 Agent 不胡乱调用工具/不输出有害内容？**

**答**：EduAgent 用 MCP（5.11）规范了工具的暴露方式，但没有专门的输出审核层。扩展方向：加 guardrails 输出护栏（敏感词/越权/注入检测）、工具调用白名单+参数校验、提示注入防御（隔离用户输入与系统指令）。这是企业最关心的安全题，能讲出"输入隔离+输出审核+工具最小权限"三道防线就很加分。

### RAG 与知识增强

**Q12：RAG 检索不准/召回质量差怎么提升？**

**答**：QA Agent（第 5 章）做了**检索->精排**两段——BGE-M3 嵌入（5.4，dense+sparse 双向量）召回，BGE-Reranker（5.8）精排提升 top 结果相关性；意图分类器（5.9）先判是否需要走 RAG（通用问题直答，省检索）。可加 HyDE/多查询改写（用假设答案或多角度改写提升召回）、混合检索（向量+关键词 BM25）、父子分块/上下文窗口扩展。

**Q13：怎么防止 RAG 幻觉（检索不到却硬编）？怎么标引用来源？**

**答**：QA 生成节点把检索到的 sources 一并返回（`meta` 事件带 sources，8.5），答案可溯源；检索不可靠时降级策略（3.5）倾向"不硬答"。可加答案与来源的一致性校验（生成后回查每句是否有出处支撑）、置信度阈值拒答（低于阈值时明确说"知识库未覆盖"）。

### 成本与性能

**Q14：Agent 系统 Token 成本高，怎么省？**

**答**：(1)规则前置拦截（8.4）让社交/元话术零 Token 直接模板回复；(2)QA 内部用本地 MiniLM（5.9）判通用/专项，通用问题免检索免长 Prompt；(3)LLM 实例缓存（`llm_factory` 的 `cache_key`，3.4）复用连接。可加语义缓存、Prompt 压缩、小模型分流（简单任务走小模型、复杂走大模型）。

**Q15：怎么降低用户感知延迟？**

**答**：(1)全程 SSE 流式（`astream_events`），答案逐字浮现而非等全部生成；(2)本地模型启动时并行预热（`main.py` lifespan 用 `asyncio.gather + run_in_executor`，8.6），避免首个请求卡几秒；(3)图懒加载+单例复用（8.2/8.3）。可加并行调用无依赖的 Agent、预测式预取、流式+首 Token 优化。

### 人工介入与安全合规

**Q16：关键决策不能全交给 AI，怎么让人介入？**

**答**：试卷批改（第 6 章）用 LangGraph 的 `interrupt` 暂停图执行、等教师复核、再 `resume` 恢复——这就是 Human-in-the-Loop 范式。医疗/法律/投研场景可把它升级为"合规强制兜底"。生产里要补审批工作流（多级审批、超时升级）、审计日志（谁在什么时候改了什么）、HitL 的异步化（人工不在线时挂起任务而非阻塞）。

### 状态持久化与可观测性

**Q17：服务重启后对话状态丢了怎么办？怎么做持久化？**

**答**：EduAgent 本地用 LangGraph 的 MemorySaver（进程内），重启即丢——这在教学/本地够用。生产迁移的核心改动就是换成 `langgraph-checkpoint-postgres`（requirements 已预装备用），把检查点落到 Postgres，支持重启恢复和多实例共享。能讲清"MemorySaver vs PostgresSaver 的取舍、什么时候切"就是很好的落地意识。

**Q18：Agent 系统怎么做可观测性？出问题怎么定位？**

**答**：结构化日志（`structlog`，3.3）贯穿全链路，关键节点都有语义化日志键（如 `unified_chat.llm_route_result`、`orchestrator.pipeline_step_start`、`retry.system_fallback`，速查见 8.7）；`/health` 探活（8.6）。可接 LangSmith/Langfuse（trace 每次 LLM 调用、Token、延迟）、Agent 评估体系（用例集+自动评分回归）、指标监控（路由准确率、降级率、P99 延迟）。

**Q19：怎么评估一个 Agent 系统好不好？怎么防止改了 Prompt 就退化？**

**答**：建评测集（典型 query+期望行为）、离线回归（每次改动跑评测集对比指标）、在线 A/B（新旧 Prompt/模型分流对比）、LLM-as-judge（用强模型给输出打分）。能讲出"评测集+离线回归+在线 A/B"三段式，面试官会觉得你真做过迭代。

### 高频追问与诚实作答建议

**Q20："这套是你自己写的还是调框架？"**

**答**：讲清你手写了 LangGraph 图的节点/边/条件路由、状态机、并行 fan-out、HitL interrupt——能说到节点级就证明是真懂。

**Q21："遇到的最大难点是什么？"**

**答**：选一个真踩过的：如 DeepSeek 复杂 schema 偶发返回 None 的兜底（7.9）、LLM 路由 vs 本地分类的取舍（8.4）、长对话摘要压缩（5.10）、Pipeline 上下文传递与检查点隔离（8.3）。有取舍、有踩坑的回答最可信。

**Q22："如果让你重构会怎么改？"**

**答**：换 Postgres checkpointer 支持重启恢复、加熔断器防雪崩、加评估体系防退化、做动态编排而非预置 Pipeline。

## 扩展：Langfuse 监控与评估指南

### 一、为什么需要 Langfuse

上线 LLM 应用后最常遇到的三类困境：

| 困境 | Langfuse 能力 | 解决方式 |
|------|-------------|---------|
| 账单不透明 | Cost Tracking | 按模型/功能/用户分组统计 Token 和成本，实时可视化 |
| 问题难定位 | Trace | 每次请求的完整调用链（每步的输入/输出/耗时/Token） |
| 迭代无基准 | Dataset + Evaluation | 评测集批量运行+指标对比，Prompt 改动前后一目了然 |

### 二、部署与配置

**方案选择**：

- Langfuse Cloud（云端）：快速试用、小团队，免费额度够用
- 自托管（Docker Compose）：数据不出内网、生产环境，免费但需自己维护

**环境变量配置**：

```bash
# .env.local
LANGFUSE_SECRET_KEY=sk-lf-xxxxxxxxxxxxxxxx
LANGFUSE_PUBLIC_KEY=pk-lf-xxxxxxxxxxxxxxxx
LANGFUSE_HOST=https://cloud.langfuse.com  # 自托管改为http://localhost:3000
```

### 三、三种接入方式

**方式一：LangChain 回调（最快，改动最少）**

```python
from langfuse.callback import CallbackHandler

handler = CallbackHandler(
    session_id="session-abc123",
    user_id="user-liming",
    tags=["qa", "rag"],
)
# 在invoke时传入callbacks即可
response = await llm.ainvoke([HumanMessage(content="问题")], config={"callbacks": [handler]})
```

**方式二：手动 SDK（最灵活，精确控制）**

适合多步骤流程（检索->精排->生成），每步用 trace.span()记录。Langfuse 的 trace 结构为：Trace（一次完整请求）-> Span（一个处理步骤，可嵌套）-> Generation（一次 LLM 调用，Span 的特化）。

**方式三：LangGraph 集成（节点级可见）**

通过回调透传，让 Langfuse 自动捕获每个节点的执行情况。也可以手动创建 Trace，再通过 `trace.get_langchain_handler()` 将 handler 绑定到节点。

### 四、Token 成本监控

在 Langfuse 后台注册自定义模型价格（Settings->Models->Add Model），填写模型名称、Input/Output 价格。在 trace 里记录 usage 后，自动按价格表换算成本。后台可查看按模型/功能/用户分组的成本分析。

### 五、问题定位实战

**定位 RAG 答错根因**：搜索 trace->看 retrieval span 召回哪些文档->看 rerank span 排序是否正确->看 generation span 的 context 是否包含正确文档。

**定位路由失败**：过滤 tag=routing_decision 的 trace，看 LLM routing 的输入输出，判断 Prompt 对意图的描述是否覆盖了用户的实际表述。

**定位高延迟请求**：通过 API 按 latency 降序拉取慢 trace，逐个排查是哪个 Span 最慢。

### 六、Score 回写与离线评估

**用户反馈**：SSE 的 done 事件里带上 trace_id，前端用户点击/时把 trace_id 回传到后端，通过 `lf.score()`写入。

**LLM 评委打分**：自动评估后把分数写回对应 trace，归一化到 0-1。

**Dataset 与离线评估**：创建评测集（含 input 和 expected_output），批量运行系统，用不同 run_name 对比不同版本。在后台对比各版本的关键指标变化。

### 七、生产监控仪表板

建议监控的指标：每日调用次数（按 tag）、平均/P95 延迟、每日 Token 成本、用户满意度（score 均值）、错误率、降级率。配置告警规则：P95>5s 告警、日成本超预算告警、满意度低于 0.75 告警、错误率>5%告警、降级率>5%告警。

### 八、接入方式选择总结

| 目标 | 用 Langfuse 的哪个功能 |
|------|-------------------|
| Token 成本透明 | Cost Tracking（注册模型价格+usage 传入） |
| 问题根因定位 | Trace（多步 Span+LLM Generation） |
| 质量信号收集 | Score（用户反馈+LLM 评委） |
| 版本对比防退化 | Dataset + Runs 对比 |
| 生产持续监控 | Dashboard（延迟/成本/满意度/降级率） |
