# 第一章 项目简介 -- EduAgent 多Agent教学辅助系统

---

## 1.1 项目全景介绍

### 1.1.1 项目背景

#### IT教育培训机构的四大痛点

在传统的IT教育培训机构中，教学辅助工作长期依赖人力，随着学员规模的扩大，四大核心痛点日益突出：

**痛点一：学员答疑 -- 老师精力有限**

在IT培训场景中，学员每天都会产生大量技术问题。一个班级通常有30-50名学员，而授课老师往往只有1-2名。老师白天需要完成4-6小时的正课授课，课后还要准备次日课程内容，真正能用于答疑的时间极其有限。学员在晚自习或课后遇到问题时，往往需要排队等待老师解答，或者问题直接被搁置到第二天。

更关键的是，大量问题是重复性的。例如，在学习Spring Boot框架时，几乎每期学员都会问"为什么我的application.yml配置文件没有生效"、"@Autowired注入失败是什么原因"这类本质上相同的问题。老师不得不反复回答相似的内容，造成了严重的人力浪费。

此外，答疑场景存在明显的"时间错配"问题：学员最需要答疑的时间段是晚上19:00-22:00（晚自习时间），而这也是老师最疲劳、最需要休息的时间段。即使安排了助教，助教的经验水平往往不足以应对复杂的技术问题。

**痛点二：试卷批改 -- 工作量大、主观题评分不一致**

IT培训课程通常包含高频次的阶段性测试：每周小测、每模块结束后的模块测试、期中考试、期末考试，以及模拟面试中的技术问答评分。以一个中等规模的培训机构为例，一名老师同时负责3个班级，每个班级40人，一次考试仅批改编程题和简答题就需要花费8-12小时。

主观题（如SQL查询优化题、系统设计题、代码审查题）的评分一致性更是突出问题。同一份答卷，不同老师可能给出不同的分数；即便是同一位老师，在批改前几张试卷和最后几张试卷时，由于疲劳和心情变化，评分标准也会发生漂移。学员对评分公平性的质疑时有发生，给教学管理带来额外压力。

编程题的批改尤其复杂：老师不仅要看代码是否能正确运行，还要考察代码风格、异常处理、边界条件覆盖、算法复杂度等多个维度。人工批改很难做到每个维度都逐一核查，导致评分粒度不够精细。

**痛点三：简历审查 -- 没时间逐份精读**

在IT培训机构的就业服务环节，简历审查是至关重要的一步。一份合格的IT简历需要满足多个维度的要求：技术栈描述是否准确、项目经验是否突出个人贡献、格式排版是否专业、是否有明显的拼写或语法错误、是否针对目标岗位做了定制化调整等。

就业指导老师通常同时负责数百名学员的简历指导工作。在求职高峰期（如毕业季前后），老师每天需要处理数十份简历。逐份精读并给出结构化反馈几乎不可能完成，大多数情况下只能快速浏览，给出"整体还行""需要修改"这类模糊的反馈。

同时，简历审查是一个高度结构化的任务：它需要从简历中提取关键信息（如技术栈、项目经历、工作年限、教育背景），然后针对每个维度进行打分，最后汇总给出综合评估和改进建议。这种结构化任务恰恰是LLM（大语言模型）擅长的领域。

**痛点四：模拟面试 -- 缺少专业陪练**

模拟面试是IT培训学员求职准备中最关键但也最薄弱的环节。理想的模拟面试需要满足以下条件：
- 面试官具备真实的企业面试经验，了解不同公司的面试风格和考查重点
- 能够针对学员的目标岗位（Java后端、前端、大数据、测试等）进行专项训练
- 可以随时进行，高频次练习
- 面试后能给出详细的反馈报告，指出薄弱环节

现实中，培训机构很难同时满足这些条件。企业级的模拟面试需要大量有真实面试经验的专业人员，成本极高。大多数机构只能安排有限的几次模拟面试，远远达不到"以练代学"的效果。

更重要的是，传统模拟面试缺少"状态追踪"：面试官无法精确记录学员在每个问题上的回答质量，也无法在后续面试中针对性地强化薄弱环节。学员反复练习，却不知道自己的短板在哪里，进步缓慢。

#### 为什么通用大模型不够用

既然通用大模型（如ChatGPT、DeepSeek等）已经具备强大的对话能力，为什么不能直接使用它们来解决上述问题？原因有三：

**1. 缺少企业私有知识（幻觉问题）**

通用大模型的知识截止于其训练数据的时间点，并且不包含任何企业的私有数据。在IT培训机构场景中，这意味着：
- 模型不知道机构的课程大纲、教学进度和重点难点
- 模型不知道机构自研的教材和案例代码
- 模型不知道机构历届学员的常见错误和典型问题
- 模型不知道机构合作企业的招聘偏好和技术要求

当学员问"按照我们老师讲的步骤，为什么我的项目还是启动不了"时，通用大模型因为没有课程上下文，只能给出泛泛的通用答案，非常容易出现"幻觉" -- 即模型自信地给出了一个看似合理但实际错误或不适配的回答。

例如，如果机构使用的Spring Boot版本是2.3.x，而大模型基于其训练数据中的2.7.x版本给出配置建议，学员照着操作后可能完全无法运行。这种"幻觉"在教育场景中尤其危险，因为它会误导学员，浪费学员的调试时间，并降低学员对辅助工具的信任度。

**2. 缺少业务流程（多步骤有状态）**

教育教学场景中的很多任务不是"一问一答"就能完成的，而是需要多步骤、有状态的业务流程：
- 试卷批改需要：接收试卷 -> 拆解题目 -> 逐题批改 -> 汇总评分 -> 生成反馈报告。整个过程涉及多个步骤，中间状态需要保持。
- 模拟面试需要：自我介绍 -> 技术问答 -> 项目经验深挖 -> 算法题考核 -> 综合评估。面试官需要根据学员的回答动态调整后续问题，整个对话是一个有状态的状态机。
- 简历审查需要：解析简历 -> 结构化抽取 -> 多维度评分 -> 生成改进建议。每一步的输出是下一步的输入。

通用大模型的API调用是无状态的，每次调用都是独立的。虽然可以通过构建复杂的Prompt工程来模拟有状态对话，但这在工程上非常脆弱，难以维护。当业务逻辑发生变化时，需要重新设计整个Prompt，成本很高。

**3. 缺少工程化可靠性（重试降级）**

在真实的生产环境中，API调用可能因为网络波动、服务端过载、限流策略等原因而失败。通用大模型本身不提供任何工程化保障：
- 没有自动重试机制：一次调用失败，需要应用层自行处理重试逻辑
- 没有降级策略：当模型服务不可用时，没有备选方案
- 没有超时管理：长时间无响应时，无法自动中断并恢复
- 没有结果校验：模型返回的结果可能格式不正确或内容不符合预期，没有自动校验机制

在教育教学场景中，可靠性尤为重要：学员在晚自习时间使用答疑系统，如果系统频繁超时或返回错误，会严重影响学习体验；试卷批改如果因为某次API调用失败而导致整个批改流程中断，老师需要手动介入恢复，这违背了"自动化"的初衷。

#### EduAgent 的定位

EduAgent 是一个 **AI 原生教学辅助系统**，它通过多Agent架构，将大模型的能力与工程化可靠性相结合，专门解决IT教育培训机构的四大痛点。

**AI原生** 意味着系统从设计之初就以AI为核心，而不是在现有系统上"修补式"地接入AI能力。每一个Agent都针对特定的教学场景进行了深度优化，业务流程围绕AI的能力特点来设计，而不是强制AI去适配传统业务流程。

**多Agent架构** 是EduAgent的核心设计理念。不是用一个"超级大模型"解决所有问题，而是将不同的教学任务拆解给专门的Agent来处理。每个Agent专注于一个领域，拥有自己的知识库、提示词和业务流程。这种架构带来了以下优势：
- **职责清晰**：每个Agent只做一件事，复杂性可控
- **独立演进**：可以单独优化某个Agent而不影响其他Agent
- **容错隔离**：一个Agent的故障不会扩散到整个系统
- **灵活组合**：可以通过Orchestrator编排Agent，实现更复杂的业务流程

EduAgent 融合了三大核心能力：
1. **私有知识融合**：通过RAG（检索增强生成）技术，将机构的教学资料、课程大纲、案例代码等私有知识注入到问答流程中，从根本上解决幻觉问题
2. **内置业务流程**：使用LangGraph的图模型，将教学业务流程建模为状态图，每一步都有明确的输入输出和状态管理
3. **容错机制**：内置重试、降级、超时、熔断等工程化保障，确保系统在真实生产环境中稳定运行

#### 核心目标：掌握可迁移的方法论

EduAgent 项目的核心目标不仅仅是开发四个可用的Agent工具，更重要的是：
**掌握一套可迁移到任何企业业务场景的多Agent系统开发方法论。**

这意味着，当你完成EduAgent项目后，你将具备以下能力：
- 能够识别和分析任何业务场景，判断是否适合使用多Agent架构
- 能够将复杂业务拆解为多个Agent的协作流程
- 能够使用LangGraph等工具将业务流程建模为可执行的图
- 能够设计Agent之间的通信机制和数据流转
- 能够构建知识库管线，将私有知识注入Agent系统
- 能够设计容错降级机制，确保系统在生产环境中的可靠性

这套方法论可以应用于任何行业：金融风控、医疗辅助、客服系统、法律咨询、工业质检等。EduAgent只是一个载体，真正交付的是背后的方法论和工程实践。

### 1.1.2 四大核心 Agent

EduAgent 包含四个核心Agent，每个Agent对应一个教学痛点。下面从多个维度进行详细对比。

#### 对比总览

| 维度 | 智能问答 (QA) | 试卷批改 (Exam) | 简历审查 (Resume) | 模拟面试 (Interview) |
|------|---------------|-----------------|-------------------|---------------------|
| **对应痛点** | 学员答疑 | 试卷批改 | 简历审查 | 模拟面试 |
| **核心解决** | 老师精力有限，重复问题多 | 工作量大，主观题评分不一致 | 没时间逐份精读 | 缺少专业陪练 |
| **技术方案** | RAG检索增强生成 | 三轨并行批改 + HitL | 结构化抽取 + 多维并行评分 | 状态机多阶段对话 + 流式输出 |
| **输入** | 学员提问 | 试卷文本 + 参考答案 | 简历PDF/文本 | 学员信息 + 岗位要求 |
| **输出** | 精准解答 + 参考资料 | 逐题分数 + 总分 + 评语 | 各维度分数 + 综合建议 | 实时对话 + 面试报告 |
| **核心教你的技术** | RAG管线构建、向量检索、嵌入模型 | 并行任务编排、人工审核回路 | 结构化信息抽取、并行评分聚合 | 状态机设计、流式传输、对话管理 |
| **交互方式** | 问答 | 上传批改 | 上传评估 | 实时对话 |
| **状态管理** | 无状态 | 有状态（批改进度） | 有状态（评估进度） | 复杂状态机 |
| **复杂度** | 中等 | 高 | 中等 | 很高 |

#### 智能问答 Agent (QA)

**业务场景：** 学员在课后或自习时遇到技术问题，向QA Agent提问。Agent基于机构私有知识库给出精准回答，并附上参考资料来源。

**核心流程：**
1. 接收学员提问
2. 对问题进行意图识别和分类（判断是否属于课程相关技术问题）
3. 将问题向量化，从知识库中检索最相关的文档片段
4. 使用重排序模型（Reranker）对检索结果进行精细排序
5. 将问题+检索到的上下文+重排序结果送入大模型
6. 大模型生成基于上下文的精准回答
7. 返回回答，并附上参考文档的链接或来源

**关键技术点：**
- **嵌入模型**：使用BGE-M3模型将问题和文档片段转换为向量，支持Dense（稠密）和Sparse（稀疏）两种向量输出
- **向量检索**：使用Milvus向量数据库进行高效的近似最近邻搜索
- **重排序**：使用BGE-Reranker模型对初筛结果进行精细排序，提升检索质量
- **RAG管线**：完整的"检索 -> 重排序 -> 生成"管线

**教你什么：**
- 如何构建一个生产级的RAG系统
- 嵌入模型的选择和部署策略
- 向量数据库的Schema设计和索引优化
- 检索质量评估和优化方法
- 如何处理"检索不到"和"检索结果不相关"的边界情况

#### 试卷批改 Agent (Exam)

**业务场景：** 老师上传学员试卷和参考答案，Exam Agent自动批改试卷，支持客观题、编程题和主观题三种题型，批改完成后生成详细的评分报告。

**核心流程：**
1. 接收试卷和参考答案
2. 智能拆解试卷，识别不同题型（选择题、填空题、编程题、简答题等）
3. 三轨并行批改：
   - **客观题轨**：标准答案匹配，自动计分
   - **编程题轨**：代码审查，包括正确性、代码风格、异常处理、边界覆盖、算法复杂度等维度
   - **主观题轨**：语义相似度评估，考查学员对概念的理解深度
4. 汇总各题分数，计算总分
5. 生成评分报告，包含逐题得分、评语、改进建议
6. **HitL（Human-in-the-Loop）**：对于置信度低的批改结果，标记为"待人工审核"，老师可以介入修正

**关键技术点：**
- **三轨并行**：三种题型并行批改，互不干扰，提高效率
- **HitL**：人工审核回路，确保在自动化批改的同时保留人工裁决权
- **评分标准配置**：不同题型的评分权重和标准可配置

**教你什么：**
- 如何设计多轨并行任务架构
- 如何实现Human-in-the-Loop流程
- 如何对LLM的输出进行结构化解析和校验
- 如何处理批改结果中的不确定性（置信度评估）
- 并行任务的错误隔离和恢复

#### 简历审查 Agent (Resume)

**业务场景：** 学员上传简历，Resume Agent自动抽取结构化信息，从多个维度进行评分，生成综合评估报告和改进建议。

**核心流程：**
1. 接收简历文件（PDF或文本）
2. 简历内容解析，提取文本信息
3. 结构化信息抽取：技术栈、项目经历、工作年限、学历背景、证书资质等
4. 多维并行评分：
   - 技术栈匹配度
   - 项目经验深度
   - 简历格式规范性
   - 语言表达质量
   - 目标岗位匹配度
5. 综合评分和排序
6. 生成改进建议报告

**关键技术点：**
- **结构化抽取**：从非结构化的简历文本中提取结构化信息
- **多维评分**：多个评分维度并行评估，互不干扰
- **评分聚合**：将各维度评分加权汇总，生成综合评分
- **目标岗位适配**：根据目标岗位动态调整评分权重

**教你什么：**
- 如何对非结构化文本进行结构化信息抽取
- 如何设计多维评分体系和评分聚合策略
- 如何将评分结果以结构化的JSON格式输出
- 如何根据业务需求动态调整评分权重

#### 模拟面试 Agent (Interview)

**业务场景：** 学员与Interview Agent进行实时对话，Agent扮演面试官角色，根据学员的目标岗位和简历进行个性化面试，面试结束后生成详细的面试报告。

**核心流程：**
1. 接收学员信息和目标岗位
2. 初始化面试状态机，进入"自我介绍"阶段
3. 多阶段对话：
   - 阶段一：自我介绍评估
   - 阶段二：技术基础问答
   - 阶段三：项目经验深挖
   - 阶段四：算法/设计题考核
   - 阶段五：综合评估和反馈
4. 每个阶段根据学员的回答动态调整问题难度和方向
5. 面试结束后，生成面试报告，包含各阶段表现评分、薄弱环节分析和改进建议

**关键技术点：**
- **状态机**：面试流程被建模为状态机，每个阶段是一个状态，状态转换由学员的回答触发
- **流式输出**：面试官的问题以流式方式输出，模拟真实对话的节奏
- **动态难度调整**：根据学员在前期阶段的表现，自动调整后续问题的难度
- **对话历史管理**：维护完整的对话历史，确保面试的连贯性和一致性

**教你什么：**
- 如何使用状态机建模复杂的多阶段对话流程
- 如何实现流式输出（SSE）以提升用户体验
- 如何维护和管理长对话的上下文
- 如何根据用户输入动态调整对话策略
- 如何从对话记录中提取关键信息并生成结构化报告

#### 核心依赖详解

**Python 3.11 + 全异步**

项目选择Python 3.11作为开发语言，利用其强大的异步编程能力。在EduAgent中，多个Agent需要同时处理多个请求（如三轨并行批改），异步编程能够充分利用IO等待时间，提升系统吞吐量。

全异步意味着从Web框架（FastAPI）到数据库驱动（asyncpg for PostgreSQL）到HTTP客户端（httpx.AsyncClient for LLM API调用），整个调用链都是异步的。这避免了传统同步编程中线程阻塞导致的性能瓶颈。

```python
# 异步编程示例：并行调用多个评分维度
import asyncio

async def evaluate_resume(resume_text: str):
    """并行评估简历的多个维度"""
    tasks = [
        evaluate_tech_stack(resume_text),
        evaluate_project_experience(resume_text),
        evaluate_format(resume_text),
        evaluate_language_quality(resume_text),
    ]
    # 所有维度并行评估，等待所有结果
    results = await asyncio.gather(*tasks, return_exceptions=True)
    return aggregate_scores(results)
```

**FastAPI -- REST + SSE**

FastAPI是EduAgent的Web框架，提供两种核心接口：
- **REST API**：用于常规的请求-响应模式，如简历上传、试卷提交、评分结果查询等
- **SSE (Server-Sent Events)**：用于模拟面试的流式输出，面试官的问题以流式方式逐个token输出，给学员真实的对话体验

```python
# SSE流式输出示例
from fastapi import FastAPI
from sse_starlette.sse import EventSourceResponse

app = FastAPI()

@app.get("/interview/stream/{session_id}")
async def interview_stream(session_id: str):
    async def event_generator():
        interview_agent = get_interview_agent(session_id)
        async for token in interview_agent.respond():
            yield {
                "event": "token",
                "data": token
            }
    return EventSourceResponse(event_generator())
```

**LangChain 1.2.10 + LangGraph 1.0.9 -- 绝对核心**

LangChain和LangGraph是EduAgent的绝对核心依赖，版本被严格锁定。原因如下：

LangChain提供了与LLM交互的统一抽象层，包括：
- ChatModel：与各种LLM API交互的统一接口
- PromptTemplate：提示词模板化管理
- Document：文档对象的统一表示
- TextSplitter：文档切分工具
- Embeddings：嵌入模型的统一接口

LangGraph在LangChain的基础上，提供了图模型来编排Agent的工作流程：
- StateGraph：定义Agent的状态图
- State：节点之间共享的数据结构
- Node：图中的处理节点
- Edge：连接节点的边（固定边和条件边）
- Checkpointer：状态持久化

版本严格锁定是生产级项目的标准做法。LangChain和LangGraph的迭代速度非常快，不同版本之间的API可能有破坏性变更。锁定版本确保了项目的可复现性和稳定性。

```python
# LangGraph 图模型示例
from langgraph.graph import StateGraph, State
from typing import TypedDict, List

# 定义状态
class InterviewState(TypedDict):
    session_id: str
    current_stage: str
    dialogue_history: List[dict]
    evaluation: dict

# 创建图
graph = StateGraph(InterviewState)

# 添加节点
graph.add_node("greeting", greeting_node)
graph.add_node("technical_quiz", technical_quiz_node)
graph.add_node("project_deep_dive", project_deep_dive_node)
graph.add_node("evaluation", evaluation_node)

# 添加边
graph.add_conditional_edges(
    "technical_quiz",
    decide_next_stage,
    {
        "project_deep_dive": "project_deep_dive",
        "evaluation": "evaluation"
    }
)

# 编译
app = graph.compile()
```

**DeepSeek-V3 API**

项目使用DeepSeek-V3作为大语言模型，通过API调用。DeepSeek-V3在中文场景下表现出色，且性价比高。通过API调用意味着不需要在本地部署大模型，降低了硬件要求。

**Milvus -- 向量数据库**

Milvus是开源的向量数据库，专门用于存储和检索高维向量。在EduAgent中，Milvus存储了课程文档的向量表示，支持高效的近似最近邻搜索。当学员提问时，QA Agent将问题向量化后在Milvus中检索最相关的文档片段。

**PostgreSQL -- 关系数据库**

PostgreSQL用于存储业务数据，如学员信息、试卷记录、评分结果、面试记录等。它提供了强大的事务支持和复杂查询能力，与Milvus形成互补（关系型数据 + 向量数据）。

**BGE-M3 -- 进程内嵌入模型**

BGE-M3是一个多语言嵌入模型，支持Dense（稠密向量）和Sparse（稀疏向量）两种输出。这意味着一个模型可以同时提供两种检索方式，兼顾了稠密检索的语义理解能力和稀疏检索的关键词匹配能力。

**BGE-Reranker -- 进程内重排序模型**

BGE-Reranker是一个交叉编码器，用于对检索结果进行精细排序。与双编码器（如BGE-M3）不同，Reranker会将查询和文档拼接在一起作为输入，计算相关性分数，精度更高但速度较慢。因此，通常先用BGE-M3做初筛（召回Top-K），再用Reranker对Top-K结果精排。

**MiniLM -- 进程内意图分类模型**

MiniLM是一个轻量级的Transformer模型，用于对用户输入进行意图分类。在EduAgent中，MiniLM用于：
- 判断用户问题是否属于课程相关技术问题
- 识别用户意图（提问、投诉、闲聊等）
- 在Orchestrator层进行初步的意图路由

#### 什么是"进程内"以及工程简化价值

"进程内"（In-Process）指的是模型与主应用程序运行在同一个进程空间中，而不是作为一个独立的微服务或通过API调用。具体来说，在EduAgent中，BGE-M3、BGE-Reranker、MiniLM这三个模型都是直接加载到应用程序的内存中，通过函数调用来使用，而不是通过网络请求来调用。

**"进程内" vs "独立服务" 对比**

| 维度 | 进程内部署 | 独立服务部署 |
|------|-----------|-------------|
| 部署复杂度 | 低：一个进程搞定 | 高：需要额外部署模型服务 |
| 调用延迟 | 极低：函数调用，毫秒级 | 中等：网络传输，几毫秒到几十毫秒 |
| 资源隔离 | 共享主进程资源 | 独立资源，互不干扰 |
| 扩展性 | 随主进程水平扩展 | 可独立扩缩容 |
| 运维成本 | 低：一个进程的运维 | 高：多服务运维 |
| 适用场景 | 中小规模、开发阶段 | 大规模生产、需要独立扩缩容 |

**工程简化价值**

1. **部署简化**：整个项目只需要部署一个进程，不需要额外部署模型服务、配置网络、处理认证等。对于开发阶段和中小规模部署来说，这极大地降低了运维成本。

2. **延迟降低**：进程内调用是函数调用，没有网络开销。在RAG管线中，嵌入 -> 检索 -> 重排序 -> 生成，每一步都是进程内调用，端到端延迟显著降低。

3. **调试方便**：所有代码在同一个进程中，可以统一打日志、统一异常处理、统一配置管理。不需要跨服务追踪请求链路。

4. **资源利用率高**：模型加载后常驻内存，多个请求共享同一个模型实例，内存利用率高。GPU显存也只被一个进程占用，不存在多服务争抢显存的问题。

5. **开发效率高**：开发阶段不需要启动多个服务，不需要处理服务间通信，可以专注于业务逻辑的实现。

当然，进程内部署也有其局限性。当系统规模扩大到一定程度，需要独立扩缩容时，将模型拆分为独立服务是更好的选择。但这是"成长后的烦恼"，在项目初期，进程内部署是最务实的选择。

### 1.1.4 系统分层架构

EduAgent 采用六层分层架构，从上到下依次为：

```
┌─────────────────────────────────────────────┐
│           API 层（FastAPI）                   │
│   REST 接口 / SSE 流式接口 / WebSocket       │
├─────────────────────────────────────────────┤
│       编排层 Orchestrator                    │
│   意图识别 → Agent路由 / 多Agent串联         │
├─────────────────────────────────────────────┤
│              Agent 层                        │
│   QA Agent │ Exam Agent │ Resume Agent │ Interview Agent │
├─────────────────────────────────────────────┤
│              公共层 Common                   │
│   嵌入模型 │ 重排序模型 │ 意图分类 │ 工具函数 │
├─────────────────────────────────────────────┤
│               MCP 层                         │
│   模型调用协议 │ 统一LLM接口 │ 模型切换 │ 重试降级 │
├─────────────────────────────────────────────┤
│              数据层 Data                     │
│   Milvus │ PostgreSQL │ 文件存储 │ 缓存 │ 消息队列 │
└─────────────────────────────────────────────┘
```

#### 第一层：API 层

**职责：** 对外暴露的接口层，负责接收用户请求和返回响应。

**关键角色：**
- **REST 接口**：处理常规的请求-响应，如简历上传、试卷提交、评分查询等
- **SSE 流式接口**：处理模拟面试的流式输出，将Agent的响应以token流的方式推送给前端
- **WebSocket**：可选接口，用于需要双向实时通信的场景

**设计要点：**
- API层不做业务逻辑处理，只做参数校验、身份认证、请求转发
- 使用FastAPI的依赖注入系统管理数据库连接、模型实例等全局资源
- 统一的错误处理和响应格式

#### 第二层：编排层 Orchestrator

**职责：** 系统的"大脑"，负责理解用户意图并将请求路由到正确的Agent，或在复杂场景中串联多个Agent。

**关键角色：**
- **意图识别器**：使用MiniLM对用户输入进行意图分类，判断用户想要做什么
- **单Agent路由**：对于明确的请求（如"帮我批改试卷"），直接路由到对应的Agent
- **多Agent串联**：对于需要多个Agent协作的复杂场景（如"帮我面试并生成简历改进建议"），编排多个Agent的调用顺序

**设计要点：**
- Orchestrator本身不执行业务逻辑，只负责调度
- 意图识别结果附带置信度分数，低于阈值时请求用户确认
- 支持动态路由，可以根据业务需求添加新的Agent

#### 第三层：Agent 层

**职责：** 业务逻辑的执行层，每个Agent封装了完整的业务流程。

**关键角色：**
- **QA Agent**：RAG检索增强问答
- **Exam Agent**：三轨并行试卷批改
- **Resume Agent**：结构化简历评估
- **Interview Agent**：状态机模拟面试

**设计要点：**
- 每个Agent独立部署在自己的LangGraph图中
- Agent之间不直接通信，通过Orchestrator协调
- 每个Agent有自己的状态管理、错误处理和降级策略

#### 第四层：公共层 Common

**职责：** 提供所有Agent共享的基础能力。

**关键角色：**
- **嵌入模型服务**：封装BGE-M3的嵌入生成逻辑
- **重排序服务**：封装BGE-Reranker的精排逻辑
- **意图分类服务**：封装MiniLM的分类逻辑
- **工具函数**：文本切分、格式转换、时间处理等通用工具

**设计要点：**
- 公共层的组件是无状态的，可以被多个Agent共享
- 模型加载由公共层管理，避免每个Agent重复加载模型
- 公共层的接口设计为纯函数，便于测试和替换

#### 第五层：MCP 层（Model Communication Protocol）

**职责：** 统一的大模型调用接口，负责所有与LLM的通信。

**关键角色：**
- **统一LLM接口**：封装不同LLM提供商的API差异，提供统一的调用接口
- **模型切换**：支持在DeepSeek-V3、GPT-4等模型之间切换
- **重试降级**：调用失败时的自动重试、降级策略
- **流式处理**：将LLM的流式响应转换为统一的流式接口

**设计要点：**
- MCP层屏蔽了不同LLM的API差异，上层代码不需要关心使用的是哪个模型
- 重试策略采用指数退避算法，避免短时间内大量重试导致雪崩
- 降级策略包括：切换到备用模型、返回缓存结果、返回友好错误提示

```python
# MCP层统一接口示例
class LLMClient:
    """统一大模型调用客户端"""
    
    async def invoke(self, 
                     prompt: str,
                     model: str = "deepseek-v3",
                     stream: bool = False,
                     max_retries: int = 3) -> str:
        """调用大模型，包含重试和降级逻辑"""
        last_error = None
        
        for attempt in range(max_retries):
            try:
                return await self._do_invoke(prompt, model, stream)
            except TimeoutError:
                last_error = TimeoutError("模型响应超时")
                # 指数退避等待
                await asyncio.sleep(2 ** attempt * 0.5)
            except RateLimitError:
                last_error = RateLimitError("请求频率超限")
                # 限流时等待更长时间
                await asyncio.sleep(2 ** attempt * 2)
            except ServiceUnavailableError:
                last_error = ServiceUnavailableError("模型服务不可用")
                # 尝试切换到备用模型
                if attempt < max_retries - 1:
                    model = self._fallback_model(model)
        
        # 所有重试都失败，执行降级
        return await self._degrade(original_prompt=prompt, error=last_error)
    
    async def _do_invoke(self, prompt: str, model: str, stream: bool):
        """实际的模型调用"""
        ...
    
    def _fallback_model(self, model: str) -> str:
        """切换到备用模型"""
        fallback_map = {
            "deepseek-v3": "deepseek-v2",  # 版本降级
            "gpt-4": "gpt-3.5-turbo",     # 能力降级
        }
        return fallback_map.get(model, model)
    
    async def _degrade(self, original_prompt: str, error: Exception):
        """降级策略：返回缓存结果或友好提示"""
        # 尝试从缓存中查找相似问题
        cached = await self._search_cache(original_prompt)
        if cached:
            return cached
        
        # 返回友好错误提示
        return "抱歉，AI服务暂时不可用，请稍后再试。"
```

#### 第六层：数据层 Data

**职责：** 数据存储和管理的底层基础设施。

**关键角色：**
- **Milvus**：向量存储和检索，用于QA Agent的知识库检索
- **PostgreSQL**：关系数据存储，用于学员信息、试卷、评分、面试记录等
- **文件存储**：存储简历PDF、试卷图片等非结构化文件
- **缓存**：Redis或内存缓存，用于加速频繁查询的结果
- **消息队列**：可选，用于异步任务处理和削峰填谷

**设计要点：**
- 数据层通过Repository模式提供统一的访问接口，上层代码不直接操作数据库
- 向量数据库和关系数据库各司其职，不互相替代
- 数据访问层实现了连接池管理，避免频繁创建和销毁连接

### 1.1.5 最终交付物

EduAgent 项目的最终交付物包括以下三个部分：

#### 1. 四个端到端可用的 Agent

每个Agent都是一个完整的、可独立运行的业务系统：

- **QA Agent**：学员可以上传问题，系统基于私有知识库给出精准回答
- **Exam Agent**：老师可以上传试卷和参考答案，系统自动批改并生成评分报告
- **Resume Agent**：学员可以上传简历，系统从多维度评分并给出改进建议
- **Interview Agent**：学员可以与AI面试官进行实时对话，系统记录面试过程并生成评估报告

每个Agent都包含：
- 完整的业务流程实现
- 输入输出格式定义
- 错误处理和边界情况覆盖
- 日志和监控

#### 2. 知识库构建管线

知识库是QA Agent的核心组件。知识库构建管线包括：
- **文档解析**：将PDF、Word、Markdown等格式的文档解析为纯文本
- **文档切分**：将长文档切分为合适的片段，需要考虑段落边界、章节结构等
- **向量化**：使用BGE-M3将文档片段转换为向量
- **索引构建**：将向量存入Milvus，构建索引
- **质量评估**：对知识库的检索质量进行评估和优化

知识库构建管线是一个独立的工具，可以重复运行，用于更新和扩展知识库。

#### 3. 容错降级机制

系统级的容错降级机制确保在不同异常情况下系统仍能提供可用的服务：

- **重试机制**：API调用失败时自动重试，支持指数退避
- **降级策略**：模型服务不可用时切换到备用模型或返回缓存结果
- **超时控制**：所有外部调用都有超时限制，避免长时间阻塞
- **熔断机制**：当错误率超过阈值时，自动熔断，避免雪崩
- **优雅降级**：当某个Agent不可用时，系统给出明确的提示，而不是崩溃

## 1.2 多Agent系统核心概念

### 1.2.1 什么是 Agent

#### 一次大模型调用 vs Agent 的本质区别

很多人会把"调用大模型API"和"使用Agent"混为一谈，但实际上两者有本质的区别。

**一次大模型调用：**
```
用户输入 → 调用LLM API → 获取输出 → 结束
```

这是一个一次性的、无状态的交互。输入一个Prompt，得到一个Response。整个过程是"问-答"模式，模型没有记忆，不会主动采取行动，也不会使用工具。

```python
# 一次大模型调用
import openai

def ask_llm(question: str) -> str:
    response = openai.ChatCompletion.create(
        model="gpt-4",
        messages=[{"role": "user", "content": question}]
    )
    return response.choices[0].message.content
```

**Agent：**
```
用户输入 → Agent感知环境 → 结合记忆分析 → 决策 → 行动(调用工具/LLM/查询数据库等)
  → 观察结果 → 再次分析决策 → 再次行动 → ... → 达到目标或主动停止
```

Agent是一个**自主**的智能体，它能够：
1. 感知环境（感知用户输入和系统状态）
2. 结合记忆（记住之前的交互和知识）
3. 做出决策（决定下一步做什么）
4. 采取行动（调用工具、查询数据库、调用LLM等）
5. 循环执行（直到达到目标或主动停止）

```python
# Agent的简化实现
class SimpleAgent:
    def __init__(self):
        self.memory = []  # 内部记忆
        self.tools = {
            "search_knowledge_base": self.search_knowledge_base,
            "calculate": self.calculate,
        }
    
    async def run(self, user_input: str):
        self.memory.append({"role": "user", "content": user_input})
        
        while True:
            # 感知：分析当前状态
            state = self._analyze_state()
            
            # 决策：决定下一步行动
            action = await self._decide_next_action(state)
            
            if action["type"] == "respond":
                # 直接回答用户
                response = action["content"]
                self.memory.append({"role": "assistant", "content": response})
                return response
            elif action["type"] == "use_tool":
                # 调用工具
                tool_result = self.tools[action["tool_name"]](action["args"])
                self.memory.append({"role": "system", "content": f"工具调用结果: {tool_result}"})
                # 继续循环
```

#### Agent的五大能力

一个完整的Agent具备以下五大核心能力：

**1. 感知 (Perception)**

Agent能够感知外部环境的变化。在EduAgent中，感知包括：
- 接收用户的输入（问题、文件上传、对话消息）
- 读取系统状态（当前流程阶段、处理进度）
- 获取外部数据（数据库查询结果、API响应）

**2. 记忆 (Memory)**

Agent能够记住历史信息，包括：
- **短期记忆**：当前对话中的上下文，通常是对话历史
- **长期记忆**：跨会话的知识积累，如学员历史学习记录
- **工作记忆**：当前任务的处理状态和中间结果

在LangGraph中，记忆通过State和Checkpointer来实现。State是节点间共享的数据，Checkpointer负责将State持久化到存储中。

**3. 决策 (Decision)**

Agent能够根据当前状态做出决策，决定下一步的行动。决策方式包括：
- **LLM决策**：将决策问题交给大模型，通过Prompt让模型决定下一步
- **规则决策**：基于预定义的规则进行决策，如状态机转换
- **混合决策**：结合LLM和规则，在关键节点使用规则确保行为可控

**4. 行动 (Action)**

Agent能够执行具体的行动。行动类型包括：
- **调用LLM**：生成文本、回答问题、分析内容
- **调用工具**：搜索知识库、执行计算、查询数据库
- **调用其他Agent**：在复杂场景中，向其他Agent请求帮助
- **返回结果**：将结果返回给用户

**5. 可循环/可中断 (Loop/Interrupt)**

Agent不是一次性的，而是可以循环执行的：
- **循环**：Agent可以反复执行"感知-决策-行动"循环，直到任务完成
- **中断**：Agent可以在等待用户输入时主动中断，等待用户回复后再继续
- **恢复**：中断后可以从中断点恢复执行，而不是从头开始

#### 一句话概括

> **Agent = 大模型 + 记忆 + 工具 + 自主循环**

更完整地说：Agent是一个能够**自主感知环境、结合记忆做出决策、调用工具执行行动，并通过循环迭代直至完成任务**的智能体。它不仅仅是一个"更聪明的Prompt"，而是一个完整的、可自主运行的智能系统。

### 1.2.2 Agent的四种形态

根据复杂度和自主性，Agent系统可以分为四种形态：

#### 形态一：单次 LLM 调用

```
用户输入 → [LLM] → 模型输出
```

**说明：** 这是最简单的形式，一次Prompt调用，模型直接返回结果。没有状态管理，没有工具调用，没有循环。

**优点：** 实现简单，延迟低，成本低。

**缺点：** 功能有限，无法处理复杂任务，没有记忆和上下文。

**适用场景：** 简单的文本生成、翻译、摘要等。

**示例：** 直接调用DeepSeek-V3 API做简单的翻译。

#### 形态二：固定工作流 (Chain / Pipeline)

```
用户输入 → [检索] → [增强] → [生成] → 模型输出
```

**说明：** 将多个步骤串联成一个固定的工作流，每个步骤有明确的输入输出。步骤之间是确定的顺序执行，不存在分支和循环。LangChain的Chain就是这种形态的典型实现。

**优点：** 流程清晰，可控性强，易于调试和优化。

**缺点：** 灵活性差，无法处理动态变化的需求。

**适用场景：** 流程固定的任务，如RAG问答、数据处理管线。

**示例：** QA Agent的"检索 -> 重排序 -> 生成"流程就是一个固定工作流。

#### 形态三：单 Agent (自主循环)

```
用户输入 → [Agent] → 循环：感知-决策-行动 → 达到目标 → 输出
```

**说明：** 一个Agent自主运行，能够感知环境、做出决策、调用工具，并在循环中完成任务。Agent可以自主决定下一步做什么，而不是按照固定的流程执行。

**优点：** 灵活性高，能够处理复杂和不确定的任务。

**缺点：** 行为不可预测，调试困难，成本较高（可能多次调用LLM）。

**适用场景：** 需要自主探索和决策的任务，如代码生成、数据分析、网页浏览。

**示例：** 一个能够自主搜索网页、执行代码、分析结果的Research Agent。

#### 形态四：多 Agent 协作

```
                   ┌─── Agent 1 ───┐
用户输入 → [Orchestrator] ─── Agent 2 ─── 汇总输出
                   └─── Agent 3 ───┘
```

**说明：** 多个Agent协同工作，每个Agent负责一个子任务。Orchestrator负责协调和管理Agent之间的通信。Agent之间可以并行工作、串行依赖或混合编排。

**优点：** 职责清晰，可扩展性强，适合复杂业务场景。

**缺点：** 架构复杂，需要处理Agent间通信和状态同步，调试难度大。

**适用场景：** 复杂的企业级业务系统，需要多步骤、多角色协作的任务。

**示例：** EduAgent系统，四个Agent分别负责不同的教学辅助任务。

#### EduAgent 为什么选择形态二 + 形态四的组合

EduAgent 并没有选择单一的形态，而是采用了**形态二（固定工作流）和形态四（多Agent协作）的组合**：

**形态二（固定工作流）用于每个Agent内部：**

每个Agent内部的业务流程是固定的、可预测的。例如：
- QA Agent的流程是固定的：检索 -> 重排序 -> 生成。这个流程不需要Agent自主决策，每一步做什么都是确定的。
- Exam Agent的流程是固定的：拆解试卷 -> 三轨并行批改 -> 汇总评分。每个步骤的顺序和内容都是确定的。

使用固定工作流的好处是：
- 流程可控，结果可预测
- 易于调试和优化
- 每个步骤都可以单独测试
- 错误处理简单，可以在特定步骤设置重试和降级

**形态四（多Agent协作）用于系统整体架构：**

在系统层面，四个Agent是独立的，通过Orchestrator进行协作。Orchestrator负责：
- 接收用户请求，判断意图
- 将请求路由到正确的Agent
- 在需要时串联多个Agent

使用多Agent协作的好处是：
- 职责清晰，每个Agent只做一件事
- 独立演进，可以单独优化某个Agent
- 容错隔离，一个Agent的故障不会扩散到整个系统
- 灵活组合，可以编排多个Agent实现更复杂的业务流程

**总结：** 在EduAgent中，每个Agent内部采用固定工作流以确保流程的稳定性和可控性；系统层面采用多Agent协作架构以支持复杂业务场景的灵活编排。这种"组合拳"兼顾了稳定性、可控性和灵活性，是实际生产项目中最常用的架构模式。

### 1.2.3 为什么拆成四个Agent

#### 四类业务的流程形状根本不同

将四个业务拆分为四个独立Agent，根本原因在于它们的流程形状完全不同。如果用一个"万能Agent"来处理所有业务，会导致代码耦合严重，难以维护和演进。

**RAG流程（QA Agent）：**

```
用户提问 → [向量化] → [检索Milvus] → [重排序] → [LLM生成] → 回答
```

流程特征：**直线型**，数据流是单向的，没有分支和循环。输入是问题，输出是回答。整个过程是"检索->增强->生成"的流水线。

**HitL流程（Exam Agent）：**

```
试卷 → [拆解题目] → [三轨并行批改]
                     ├── 客观题轨 → 自动计分
                     ├── 编程题轨 → 代码审查 → [置信度低?] → [人工审核] → 修正
                     └── 主观题轨 → 语义评估 → [置信度低?] → [人工审核] → 修正
                     → [汇总评分] → 评分报告
```

流程特征：**扇入扇出型**，有并行分支（三轨并行），有判断节点（置信度检查），有回环（人工审核修正）。流程比RAG复杂得多，需要处理并行任务的协调和人工介入。

**扇出流程（Resume Agent）：**

```
简历 → [结构化抽取] → [多维并行评分]
                     ├── 技术栈评分
                     ├── 项目经验评分
                     ├── 格式评分
                     ├── 语言质量评分
                     └── 岗位匹配度评分
                     → [评分聚合] → 综合报告
```

流程特征：**扇出聚合型**，先抽取结构化信息，然后多个评分维度并行执行，最后聚合评分。每个评分维度是独立的，可以并行执行，但需要等待所有维度完成后再聚合。

**状态机流程（Interview Agent）：**

```
开始 → [自我介绍阶段] → [技术问答阶段] → [项目深挖阶段] → [算法考核阶段] → [综合评估]
         ↑                  ↑                  ↑                  ↑
         └── 动态调整 ──────┴── 动态调整 ──────┴── 动态调整 ──────┘
```

流程特征：**状态机型**，流程由状态和状态转换组成。每个状态是一个对话阶段，状态转换由学员的回答触发。Agent需要根据学员的表现动态调整后续流程。这是四种流程中最复杂的。

#### 高内聚低耦合的软件工程原则

将四个业务拆分为四个独立Agent，遵循了软件工程中"高内聚低耦合"的核心原则。

**高内聚：** 每个Agent内部的功能高度相关，专注于一个业务领域。
- QA Agent只做问答，不涉及批改和面试
- Exam Agent只做批改，不涉及问答和面试
- Resume Agent只做简历评估，不涉及其他
- Interview Agent只做模拟面试，不涉及其他

**低耦合：** Agent之间通过Orchestrator进行通信，不直接依赖。
- QA Agent不知道Exam Agent的存在
- Exam Agent不依赖Resume Agent的数据
- 每个Agent可以独立部署、独立测试、独立扩展

**不拆分的后果：**

如果用一个"万能Agent"来处理所有业务，代码会变成：

```python
class GodAgent:
    """一个包含了所有业务逻辑的'万能Agent'"""
    
    async def handle(self, request):
        intent = self.classify_intent(request)
        
        if intent == "qa":
            # QA相关逻辑
            ...
        elif intent == "exam":
            # Exam相关逻辑
            ...
            if need_human_review:
                # 人工审核逻辑
                ...
        elif intent == "resume":
            # Resume相关逻辑
            ...
        elif intent == "interview":
            # Interview相关逻辑
            ...
            if stage == "intro":
                # 自我介绍处理
                ...
            elif stage == "technical":
                # 技术问答处理
                ...
```

这种"上帝类"的坏处：
- 代码膨胀：一个类包含所有业务逻辑，代码量巨大
- 职责不清：不同业务逻辑混在一起，难以理解
- 修改困难：修改一个业务逻辑可能影响其他业务
- 测试困难：需要为所有业务逻辑编写测试用例，测试量巨大
- 团队协作困难：多人同时修改同一个文件，冲突频繁

**拆分的收益：**

- 每个Agent的代码量适中，容易理解和维护
- 修改一个Agent不影响其他Agent
- 每个Agent可以独立测试，测试用例更聚焦
- 团队成员可以并行开发不同的Agent
- 每个Agent可以独立部署和扩缩容

### 1.2.4 LangGraph 的图模型

#### 链(Chain)的局限性

在LangChain中，Chain是最核心的抽象。一个Chain代表一个固定的处理步骤序列，如：

```python
from langchain.chains import LLMChain
from langchain.prompts import PromptTemplate

# 定义一个Chain
chain = LLMChain(
    llm=llm,
    prompt=PromptTemplate.from_template("将以下内容翻译成英文: {text}")
)
result = chain.run(text="你好世界")
```

Chain的局限性在于：
1. **只能直线走**：Chain是线性的，步骤A -> 步骤B -> 步骤C，不能有分支和循环
2. **没有状态管理**：Chain之间不共享状态，数据需要通过输入输出显式传递
3. **没有分支逻辑**：不能根据中间结果决定下一步走哪条路
4. **没有循环逻辑**：不能重复执行某个步骤直到满足条件

对于复杂的业务场景（如HitL流程、状态机流程），Chain的线性模型显然不够用。这就是LangGraph引入图模型的原因。

#### 图的四要素

LangGraph将业务流程建模为**有向图**，核心包含四个要素：

##### 要素一：State（状态）

State是所有节点共享的数据结构。在LangGraph中，State被定义为一个`TypedDict`，包含了业务流程中所有需要共享的数据。

```python
from typing import TypedDict, List, Optional

class ExamState(TypedDict):
    """试卷批改的状态"""
    # 输入
    exam_paper: str                    # 试卷文本
    answer_key: str                    # 参考答案
    # 中间结果
    parsed_questions: List[dict]       # 拆解后的题目列表
    objective_results: Optional[dict]  # 客观题批改结果
    coding_results: Optional[dict]     # 编程题批改结果
    subjective_results: Optional[dict] # 主观题批改结果
    # 控制信息
    need_human_review: bool            # 是否需要人工审核
    review_items: List[dict]           # 待人工审核的项
    # 输出
    final_score: Optional[float]       # 最终分数
    report: Optional[str]              # 评分报告
    # 错误信息
    errors: List[str]                  # 处理过程中的错误
```

State的设计要点：
- 包含所有需要共享的数据，避免节点间通过输入输出传参
- 包含控制信息（如是否需要人工审核），用于条件边的判断
- 包含错误信息，用于异常处理和降级

##### 要素二：Node（节点）

Node是图中的处理单元，每个节点执行一个具体的操作。在LangGraph中，Node是一个函数，接收State作为输入，返回更新后的State。

```python
from langgraph.graph import StateGraph

# 定义节点函数
def parse_exam_paper(state: ExamState) -> dict:
    """拆解试卷，识别题目"""
    paper = state["exam_paper"]
    # 使用LLM拆解试卷
    questions = llm_parse_questions(paper)
    return {"parsed_questions": questions}

def grade_objective(state: ExamState) -> dict:
    """批改客观题"""
    questions = state["parsed_questions"]
    objective = [q for q in questions if q["type"] == "objective"]
    results = []
    for q in objective:
        score = 1.0 if q["answer"] == q["correct"] else 0.0
        results.append({"id": q["id"], "score": score})
    return {"objective_results": {"results": results, "status": "completed"}}

def grade_coding(state: ExamState) -> dict:
    """批改编程题"""
    questions = state["parsed_questions"]
    coding = [q for q in questions if q["type"] == "coding"]
    # 编程题使用LLM批改
    results = llm_grade_coding(coding)
    return {"coding_results": results}

def grade_subjective(state: ExamState) -> dict:
    """批改主观题"""
    questions = state["parsed_questions"]
    subjective = [q for q in questions if q["type"] == "subjective"]
    results = llm_grade_subjective(subjective)
    return {"subjective_results": results}
```

Node的设计要点：
- 每个节点只做一件事，保持单一职责
- 节点函数只返回需要更新的State字段，不需要返回整个State
- 节点函数应该是纯函数，不产生副作用（除了调用外部API）

##### 要素三：Edge（边）

Edge连接节点，定义了图的拓扑结构。LangGraph支持两种边：

**固定边（Fixed Edge）：** 无条件从一个节点到另一个节点。

```python
# 创建图
graph = StateGraph(ExamState)

# 添加节点
graph.add_node("parse", parse_exam_paper)
graph.add_node("objective", grade_objective)
graph.add_node("coding", grade_coding)
graph.add_node("subjective", grade_subjective)

# 添加固定边
graph.add_edge("parse", "objective")  # 拆解试卷后，开始批改客观题
graph.add_edge("parse", "coding")     # 拆解试卷后，开始批改编程题
graph.add_edge("parse", "subjective") # 拆解试卷后，开始批改主观题
```

**条件边（Conditional Edge）：** 根据条件决定从当前节点去哪个节点。

```python
def decide_after_scoring(state: ExamState) -> str:
    """根据批改结果决定下一步"""
    # 检查是否有需要人工审核的项目
    review_items = state.get("review_items", [])
    if review_items:
        return "human_review"    # 需要人工审核
    else:
        return "generate_report" # 直接生成报告

# 添加条件边
graph.add_conditional_edges(
    "aggregate",              # 源节点
    decide_after_scoring,     # 条件函数，返回目标节点名称
    {
        "human_review": "human_review",
        "generate_report": "generate_report"
    }
)
```

条件边是LangGraph最强大的能力之一，它让图具备了分支和决策能力。

##### 要素四：Checkpointer（检查点/持久化）

Checkpointer负责将State持久化到存储中，使得Agent可以在中断后恢复执行。

```python
from langgraph.checkpoint import MemorySaver

# 创建检查点（内存存储，进程重启后丢失）
checkpointer = MemorySaver()

# 或者使用SQLite持久化存储
# from langgraph.checkpoint import SqliteSaver
# checkpointer = SqliteSaver.from_conn_string("checkpoints.db")

# 编译图时绑定检查点
app = graph.compile(checkpointer=checkpointer)

# 执行图，指定线程ID（用于中断后恢复）
config = {"configurable": {"thread_id": "exam_session_001"}}
result = app.invoke(
    {
        "exam_paper": "试卷内容...",
        "answer_key": "参考答案..."
    },
    config=config
)

# 在另一个请求中，使用相同的线程ID恢复执行
# 从上次中断处继续
result = app.invoke(None, config=config)  # 传递None表示继续
```

Checkpointer的作用：
- **中断恢复**：Agent可以在等待用户输入时中断，用户输入后恢复执行
- **状态持久化**：State被持久化到存储中，进程重启后不会丢失
- **调试回溯**：可以查看Agent在每一步的状态，便于调试
- **并发隔离**：不同的线程ID对应不同的对话，互不干扰

#### 实现套路

用LangGraph实现一个Agent的套路是固定的，遵循以下五步：

```
Step 1: 定义 State
Step 2: 写节点函数
Step 3: 连接边
Step 4: 绑定 Checkpointer
Step 5: 编译并运行
```

```python
# 完整的LangGraph实现示例
from typing import TypedDict, List
from langgraph.graph import StateGraph, END

# Step 1: 定义State
class QAState(TypedDict):
    question: str
    retrieved_docs: List[str]
    reranked_docs: List[str]
    answer: str
    error: str

# Step 2: 写节点函数
def retrieve(state: QAState) -> dict:
    """检索相关文档"""
    docs = milvus_search(state["question"])
    return {"retrieved_docs": docs}

def rerank(state: QAState) -> dict:
    """重排序检索结果"""
    docs = reranker_rerank(state["question"], state["retrieved_docs"])
    return {"reranked_docs": docs}

def generate(state: QAState) -> dict:
    """生成回答"""
    answer = llm_generate(state["question"], state["reranked_docs"])
    return {"answer": answer}

# Step 3: 连接边
graph = StateGraph(QAState)
graph.add_node("retrieve", retrieve)
graph.add_node("rerank", rerank)
graph.add_node("generate", generate)
graph.add_edge("retrieve", "rerank")
graph.add_edge("rerank", "generate")
graph.add_edge("generate", END)

# Step 4: 绑定Checkpointer
graph = graph.compile(checkpointer=MemorySaver())

# Step 5: 编译运行
result = graph.invoke(
    {"question": "什么是依赖注入？"},
    config={"configurable": {"thread_id": "qa_001"}}
)
print(result["answer"])
```

这个五步套路是EduAgent中所有Agent的基础实现模式。

### 1.2.5 Orchestrator

Orchestrator是EduAgent系统的"大脑"，负责理解用户意图并将请求分发到正确的Agent。它包含两个职责层次：

#### 职责层次一：意图识别 + 单Agent路由

这是最基础的职责。当用户发送一个请求时，Orchestrator首先识别用户的意图，然后将请求路由到对应的Agent。

```python
class Orchestrator:
    """系统编排器"""
    
    def __init__(self):
        self.intent_classifier = MiniLMIntentClassifier()
        self.agents = {
            "qa": QAAgent(),
            "exam": ExamAgent(),
            "resume": ResumeAgent(),
            "interview": InterviewAgent(),
        }
    
    async def route(self, user_input: str, file: bytes = None) -> dict:
        """意图识别和路由"""
        # 1. 意图识别
        intent = self.intent_classifier.classify(user_input)
        
        # 如果意图置信度低，请求用户确认
        if intent.confidence < 0.7:
            return {
                "type": "clarification",
                "message": f"您是想问技术问题({intent.alternatives[0]})，还是想批改试卷({intent.alternatives[1]})？"
            }
        
        # 2. 根据意图路由到对应的Agent
        if intent.label == "qa":
            return await self.agents["qa"].handle(question=user_input)
        elif intent.label == "exam":
            return await self.agents["exam"].handle(paper=file)
        elif intent.label == "resume":
            return await self.agents["resume"].handle(resume=file)
        elif intent.label == "interview":
            return await self.agents["interview"].start(user_input=user_input)
        else:
            return {"error": "无法识别的请求类型"}
```

**意图识别的方式：**

在EduAgent中，意图识别使用MiniLM模型进行轻量级分类。MiniLM是一个经过蒸馏的小型Transformer模型，可以在CPU上快速运行，延迟通常在10毫秒以内。

意图分类的类别：
- `qa`：技术问题咨询
- `exam`：试卷批改
- `resume`：简历评估
- `interview`：模拟面试
- `unknown`：无法识别

**置信度阈值：**

分类结果附带置信度分数。当置信度低于阈值（通常为0.7）时，Orchestrator不直接路由，而是请求用户确认。这避免了误路由导致的错误响应。

#### 职责层次二：多Agent串联Pipeline

在某些复杂场景中，需要多个Agent协作完成一个任务。例如，当用户说"帮我面试Java后端岗位，然后根据面试表现评估我的简历"时，Orchestrator需要先启动Interview Agent进行面试，面试结束后将面试结果（包括暴露出的技术短板）传递给Resume Agent，让Resume Agent在评估简历时重点关注这些短板。

```python
class Orchestrator:
    
    async def execute_pipeline(self, user_input: str, file: bytes = None) -> dict:
        """执行多Agent串联pipeline"""
        # 1. 意图识别
        intent = self.intent_classifier.classify(user_input)
        
        # 2. 检查是否有预定义的pipeline
        pipeline = self._get_pipeline(intent)
        
        if pipeline:
            # 执行pipeline
            context = {}
            for step in pipeline:
                agent = self.agents[step["agent"]]
                step_input = self._prepare_input(step, context, user_input, file)
                step_output = await agent.handle(**step_input)
                context[step["name"]] = step_output
            return context
        else:
            # 单Agent路由
            return await self._single_route(intent, user_input, file)
    
    def _get_pipeline(self, intent) -> List[dict]:
        """获取预定义的pipeline"""
        pipelines = {
            "interview_and_review_resume": [
                {"agent": "interview", "name": "interview_result", "input": {"question": "{user_input}"}},
                {"agent": "resume", "name": "resume_review", "input": {"resume": "{file}", "interview_feedback": "{interview_result}"}},
            ]
        }
        return pipelines.get(intent.pipeline_id)
```

**Pipeline的设计要点：**

1. **步骤依赖**：后一步可以使用前一步的输出作为输入
2. **上下文传递**：通过`context`字典在步骤之间传递数据
3. **错误隔离**：某个步骤失败不会影响其他步骤的执行
4. **可配置性**：Pipeline的定义可以是配置化的，方便添加新的pipeline

**Orchestrator vs Agent 的职责边界：**

| 维度 | Orchestrator | Agent |
|------|-------------|-------|
| 职责 | 路由和编排 | 执行业务逻辑 |
| 状态 | 无状态或轻量状态 | 有状态（业务流程状态） |
| 复杂度 | 低（路由逻辑） | 高（业务逻辑） |
| 粒度 | 粗粒度（Agent级别） | 细粒度（节点级别） |
| 错误处理 | 路由错误、Agent不可用 | 业务错误、LLM调用失败 |

### 1.1 项目全景介绍 -- 面试题

#### 1. IT教育培训机构的四大痛点是什么？每个痛点的核心矛盾是什么？

**答案：**

四大痛点分别是：

1. **学员答疑** -- 核心矛盾：老师精力有限 vs 学员问题数量多且重复性高
   - 老师白天授课，课后备课，能用于答疑的时间极其有限
   - 大量问题是重复性的，老师不得不反复回答相似内容
   - 时间错配：学员最需要答疑的时间段（晚自习）正是老师最需要休息的时间

2. **试卷批改** -- 核心矛盾：批改工作量大 vs 评分一致性要求高
   - 一个老师同时负责多个班级，每次考试批改需8-12小时
   - 主观题评分一致性差，不同老师打分不同，同一老师在不同时间打分也不同
   - 编程题需要从代码风格、异常处理、边界条件等多个维度评估，人工难以做到逐一核查

3. **简历审查** -- 核心矛盾：简历数量多 vs 老师没时间逐份精读
   - 就业指导老师同时负责数百名学员的简历指导
   - 逐份精读并给出结构化反馈几乎不可能，只能给出模糊反馈
   - 简历审查是高度结构化的任务，恰恰适合LLM处理

4. **模拟面试** -- 核心矛盾：需要专业陪练 vs 缺少专业面试官资源
   - 理想模拟面试需要真实企业面试官，成本极高
   - 大多数机构只能安排有限的几次模拟面试，远远不够
   - 传统模拟面试缺少状态追踪，无法精确记录学员在每个问题上的表现

#### 2. 为什么通用大模型不能直接解决IT培训机构的痛点？请从三个角度说明。

**答案：**

通用大模型（如ChatGPT、DeepSeek等）不能直接使用，原因有三：

1. **缺少企业私有知识（幻觉问题）**
   - 通用大模型不知道机构的课程大纲、教学进度、教材案例等私有知识
   - 当学员问"按照我们老师讲的步骤为什么还是不行"时，模型没有课程上下文
   - 模型可能给出看似合理但实际不适用当前教学环境的回答，产生"幻觉"
   - 例如，机构使用Spring Boot 2.3.x，但模型基于2.7.x给出配置建议，学员照着操作后无法运行

2. **缺少业务流程（多步骤有状态）**
   - 教学场景中的很多任务不是简单的"一问一答"，而是多步骤业务流程
   - 试卷批改需要：接收试卷 -> 拆解题目 -> 逐题批改 -> 汇总评分 -> 生成报告
   - 模拟面试需要：自我介绍 -> 技术问答 -> 项目深挖 -> 综合评估
   - 通用大模型API是无状态的，每次调用独立，无法维护多步骤业务流程的状态
   - 虽然可以通过Prompt工程模拟，但非常脆弱，难以维护

3. **缺少工程化可靠性（重试降级）**
   - 通用大模型不提供自动重试、降级策略、超时管理等工程化保障
   - 真实生产环境中，API调用可能因网络波动、限流等原因失败
   - 没有自动重试机制，失败后需要应用层自行处理
   - 没有降级策略，模型服务不可用时没有备选方案
   - 没有结果校验，模型返回格式不正确或内容不符合预期时无法自动处理

#### 3. EduAgent 的定位是什么？它融合了哪三大核心能力？

**答案：**

EduAgent 是一个 **AI 原生教学辅助系统**，通过多Agent架构将大模型能力与工程化可靠性相结合，专门解决IT教育培训机构的四大痛点。

AI原生意味着系统从设计之初就以AI为核心，而不是在现有系统上"修补式"地接入AI。每个Agent针对特定教学场景深度优化，业务流程围绕AI能力特点设计。

三大核心能力：
1. **私有知识融合**：通过RAG技术将机构教学资料、课程大纲等私有知识注入问答流程，解决幻觉问题
2. **内置业务流程**：使用LangGraph的图模型，将教学业务流程建模为状态图，每一步都有明确的输入输出和状态管理
3. **容错机制**：内置重试、降级、超时、熔断等工程化保障，确保系统在生产环境中稳定运行

#### 5. 什么是"进程内"部署？它的工程简化价值是什么？

**答案：**

"进程内"（In-Process）部署指的是模型与主应用程序运行在同一个进程空间中，通过函数直接调用，而不是作为独立微服务通过API调用。

**工程简化价值：**
1. **部署简化**：整个项目只需要部署一个进程，不需要额外部署模型服务、配置网络、处理认证等
2. **延迟降低**：进程内调用是函数调用，没有网络开销，端到端延迟显著降低
3. **调试方便**：所有代码在同一个进程中，可以统一打日志、统一异常处理，不需要跨服务追踪请求链路
4. **资源利用率高**：模型加载后常驻内存，多个请求共享同一个模型实例，内存利用率高
5. **开发效率高**：开发阶段不需要启动多个服务，可以专注于业务逻辑实现

**局限性：** 当系统规模扩大到需要独立扩缩容时，将模型拆分为独立服务是更好的选择。但在项目初期，进程内部署是最务实的选择。

#### 6. EduAgent 的六层分层架构是哪六层？每层的职责是什么？

**答案：**

六层架构从上到下依次为：

1. **API层** -- 对外暴露的接口层，负责接收请求和返回响应。包含REST接口、SSE流式接口、WebSocket。不做业务逻辑，只做参数校验、身份认证、请求转发。

2. **编排层 Orchestrator** -- 系统的"大脑"，负责理解用户意图并将请求路由到正确的Agent，或在复杂场景中串联多个Agent。包含意图识别器、单Agent路由、多Agent串联Pipeline。

3. **Agent层** -- 业务逻辑的执行层，每个Agent封装了完整的业务流程。包含QA Agent、Exam Agent、Resume Agent、Interview Agent。

4. **公共层 Common** -- 提供所有Agent共享的基础能力。包含嵌入模型服务、重排序服务、意图分类服务、工具函数。

5. **MCP层** -- 统一的大模型调用接口，负责所有与LLM的通信。包含统一LLM接口、模型切换、重试降级、流式处理。

6. **数据层 Data** -- 数据存储和管理的底层基础设施。包含Milvus（向量数据库）、PostgreSQL（关系数据库）、文件存储、缓存、消息队列。

#### 7. EduAgent 的最终交付物包括哪些部分？

**答案：**

1. **四个端到端可用的Agent**：QA Agent（智能问答）、Exam Agent（试卷批改）、Resume Agent（简历审查）、Interview Agent（模拟面试）。每个Agent都包含完整的业务流程实现、输入输出格式定义、错误处理和边界情况覆盖、日志和监控。

2. **知识库构建管线**：包含文档解析（PDF/Word/Markdown）、文档切分（考虑段落边界和章节结构）、向量化（BGE-M3）、索引构建（Milvus）、质量评估。是可重复运行的独立工具。

3. **容错降级机制**：包含重试机制（指数退避）、降级策略（切换备用模型或返回缓存）、超时控制、熔断机制（错误率超阈值时自动熔断）、优雅降级（Agent不可用时给出明确提示而非崩溃）。

### 1.2 多Agent系统核心概念 -- 面试题

#### 8. 一次大模型调用和Agent的本质区别是什么？

**答案：**

**一次大模型调用：**
```
用户输入 → 调用LLM API → 获取输出 → 结束
```
- 一次性的、无状态的交互
- 输入一个Prompt，得到一个Response
- 模型没有记忆，不会主动采取行动，不会使用工具

**Agent：**
```
用户输入 → Agent感知环境 → 结合记忆分析 → 决策 → 行动(调用工具/LLM/查询数据库等)
  → 观察结果 → 再次分析决策 → 再次行动 → ... → 达到目标或主动停止
```
- 一个**自主**的智能体
- 能够感知环境、结合记忆、做出决策、采取行动
- 可以循环执行，直到任务完成或主动停止

**一句话总结：** 一次大模型调用是"问-答"，Agent是"感知-决策-行动"的自主循环。

#### 9. Agent的五大能力是什么？请详细说明。

**答案：**

1. **感知 (Perception)** -- 感知外部环境变化
   - 接收用户输入（问题、文件、对话消息）
   - 读取系统状态（当前流程阶段、处理进度）
   - 获取外部数据（数据库查询结果、API响应）

2. **记忆 (Memory)** -- 记住历史信息
   - 短期记忆：当前对话上下文
   - 长期记忆：跨会话知识积累
   - 工作记忆：当前任务处理状态和中间结果
   - 在LangGraph中通过State和Checkpointer实现

3. **决策 (Decision)** -- 根据当前状态决定下一步行动
   - LLM决策：将决策问题交给大模型
   - 规则决策：基于预定义规则
   - 混合决策：结合LLM和规则

4. **行动 (Action)** -- 执行具体行动
   - 调用LLM生成文本
   - 调用工具（搜索、计算、查询数据库）
   - 调用其他Agent
   - 返回结果给用户

5. **可循环/可中断 (Loop/Interrupt)** -- 反复执行直到任务完成
   - 循环：反复执行"感知-决策-行动"循环
   - 中断：在等待用户输入时主动中断
   - 恢复：中断后从中断点恢复执行

#### 10. Agent的四种形态是什么？EduAgent为什么选择形态二+形态四的组合？

**答案：**

四种形态：

1. **形态一：单次LLM调用** -- 最简单的形式，一次Prompt调用，直接返回结果。没有状态管理，没有工具调用，没有循环。
2. **形态二：固定工作流（Chain/Pipeline）** -- 多个步骤串联成固定工作流，步骤之间有明确的输入输出，顺序执行，不存在分支和循环。
3. **形态三：单Agent（自主循环）** -- 一个Agent自主运行，能够感知环境、做出决策、调用工具，在循环中完成任务。
4. **形态四：多Agent协作** -- 多个Agent协同工作，每个Agent负责一个子任务，Orchestrator负责协调和管理。

**EduAgent的选择原因：**

- **形态二（固定工作流）用于每个Agent内部**：每个Agent内部的业务流程是固定的、可预测的，如QA Agent的"检索->重排序->生成"流程。固定工作流确保流程可控、结果可预测、易于调试优化。

- **形态四（多Agent协作）用于系统整体架构**：四个Agent通过Orchestrator进行协作，职责清晰、独立演进、容错隔离、灵活组合。

这种组合兼顾了稳定性、可控性和灵活性，是实际生产项目中最常用的架构模式。

#### 11. 为什么要把四个业务拆成四个独立的Agent，而不是一个"万能Agent"？

**答案：**

拆分原因：

**1. 四类业务的流程形状根本不同：**
- RAG流程（QA Agent）：直线型，数据流单向，无分支循环
- HitL流程（Exam Agent）：扇入扇出型，有并行分支、判断节点、回环
- 扇出流程（Resume Agent）：扇出聚合型，先抽取再并行评分最后聚合
- 状态机流程（Interview Agent）：状态机型，状态转换由用户输入触发

**如果用一个"万能Agent"处理所有业务，会导致：**
- 代码膨胀：一个类包含所有业务逻辑，代码量巨大
- 职责不清：不同业务逻辑混在一起，难以理解
- 修改困难：修改一个业务逻辑可能影响其他业务
- 测试困难：需要为所有业务逻辑编写测试用例
- 团队协作困难：多人同时修改同一个文件，冲突频繁

**拆分收益：**
- 每个Agent代码量适中，容易理解和维护
- 修改一个Agent不影响其他Agent
- 每个Agent可以独立测试
- 团队成员可以并行开发不同的Agent
- 每个Agent可以独立部署和扩缩容

这遵循了软件工程"高内聚低耦合"的核心原则。

#### 12. LangGraph的图模型包含哪四个要素？请详细说明。

**答案：**

1. **State（状态）** -- 所有节点共享的数据结构，定义为TypedDict
   - 包含所有需要共享的数据
   - 包含控制信息（如是否需要人工审核）
   - 包含错误信息，用于异常处理

2. **Node（节点）** -- 图中的处理单元，每个节点执行一个具体操作
   - 是一个函数，接收State作为输入，返回更新后的State
   - 每个节点只做一件事，保持单一职责
   - 只返回需要更新的State字段

3. **Edge（边）** -- 连接节点，定义图的拓扑结构
   - 固定边：无条件从一个节点到另一个节点
   - 条件边：根据条件决定从当前节点去哪个节点
   - 条件边让图具备了分支和决策能力

4. **Checkpointer（检查点/持久化）** -- 将State持久化到存储中
   - 中断恢复：Agent可以在等待用户输入时中断，之后恢复执行
   - 状态持久化：进程重启后不会丢失
   - 调试回溯：可以查看Agent在每一步的状态
   - 并发隔离：不同的线程ID对应不同的对话，互不干扰

#### 13. 用LangGraph实现一个Agent的五步套路是什么？请写出代码骨架。

**答案：**

```
Step 1: 定义 State
Step 2: 写节点函数
Step 3: 连接边
Step 4: 绑定 Checkpointer
Step 5: 编译并运行
```

```python
from typing import TypedDict, List
from langgraph.graph import StateGraph, END
from langgraph.checkpoint import MemorySaver

# Step 1: 定义State
class QAState(TypedDict):
    question: str
    retrieved_docs: List[str]
    answer: str

# Step 2: 写节点函数
def retrieve(state: QAState) -> dict:
    docs = search(state["question"])
    return {"retrieved_docs": docs}

def generate(state: QAState) -> dict:
    answer = llm_generate(state["question"], state["retrieved_docs"])
    return {"answer": answer}

# Step 3: 连接边
graph = StateGraph(QAState)
graph.add_node("retrieve", retrieve)
graph.add_node("generate", generate)
graph.add_edge("retrieve", "generate")
graph.add_edge("generate", END)

# Step 4: 绑定Checkpointer
graph = graph.compile(checkpointer=MemorySaver())

# Step 5: 编译运行
result = graph.invoke(
    {"question": "什么是依赖注入？"},
    config={"configurable": {"thread_id": "qa_001"}}
)
```

#### 14. Orchestrator的两个职责层次是什么？请详细说明。

**答案：**

**层次一：意图识别 + 单Agent路由**
- 当用户发送请求时，Orchestrator首先识别用户意图（qa/exam/resume/interview）
- 使用MiniLM进行轻量级意图分类，延迟通常在10毫秒以内
- 分类结果附带置信度分数，低于阈值（如0.7）时请求用户确认，避免误路由
- 确认意图后，将请求路由到对应的Agent

**层次二：多Agent串联Pipeline**
- 在复杂场景中，需要多个Agent协作完成任务
- 例如：用户说"帮我面试，然后根据面试表现修改简历"，需要先启动Interview Agent，再将面试结果传递给Resume Agent
- Pipeline通过context字典在步骤之间传递数据
- 后一步可以使用前一步的输出作为输入
- 步骤之间错误隔离，某个步骤失败不会影响其他步骤

**Orchestrator vs Agent 的职责边界：**
Orchestrator负责路由和编排（轻量），Agent负责执行业务逻辑（重量）。Orchestrator无状态或轻量状态，Agent有状态（业务流程状态）。Orchestrator处理路由错误和Agent不可用，Agent处理业务错误和LLM调用失败。

#### 15. 在EduAgent中，意图识别是如何实现的？置信度阈值的作用是什么？

**答案：**

EduAgent的意图识别使用**MiniLM模型**进行轻量级分类。MiniLM是一个经过蒸馏的小型Transformer模型，可以在CPU上快速运行，延迟通常在10毫秒以内。

**分类类别：**
- `qa`：技术问题咨询
- `exam`：试卷批改
- `resume`：简历评估
- `interview`：模拟面试
- `unknown`：无法识别

**置信度阈值的作用：**
- 分类结果附带置信度分数（0-1.0）
- 当置信度低于阈值（通常为0.7）时，Orchestrator不直接路由
- 而是请求用户确认意图："您是想问技术问题，还是想批改试卷？"
- 这避免了误路由导致的错误响应
- 提升了系统的鲁棒性和用户体验
