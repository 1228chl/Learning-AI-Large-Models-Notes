## 8.1 系统集成全景

### 8.1.1 前四章造了什么，这一章做什么

到第7章为止，四个Agent各自从零实现，每个Agent演示一种LangGraph范式：

| Agent | 范式 | 章节 | 入口接口 |
|-------|------|------|----------|
| 简历审查 | 并行评审（六维度 fan-out/fan-in） | 第4章 | POST /resume/... |
| 智能问答 | RAG（检索增强 + 记忆） | 第5章 | POST /qa/... |
| 试卷批改 | Human-in-the-Loop（interrupt/resume） | 第6章 | POST /exam/... |
| 模拟面试 | 状态机 + SSE（多轮对话） | 第7章 | POST /interview/... |

但它们现在是四个互不相干的接口。学员要用，得自己知道"问技术问题去 /qa、批改去 /exam、面试去 /interview"——这把"判断该用哪个功能"的负担丢给了用户。

**第8章的核心任务**：在四个Agent前面架一个统一入口，用户只管说一句话，系统自动判断该路由到哪个Agent（或哪几个Agent串联），再把结果以统一格式返回。

> 关键认知：本章几乎不"造新轮子"。所有Agent图（build_*_graph）、异常体系、重试降级、LLM工厂、MCP工具、本地模型——全部在前面章节已经实现。本章的工作是**装配**：把这些零件接到一个统一入口和一个main.py上。

### 8.1.2 两个核心角色

| 文件 | 角色 | 一句话职责 |
|------|------|-----------|
| backend/api/v1/unified_chat.py | **统一入口** | 面向用户：收一句话 -> 判断意图 -> 用SSE流式返回（路由卡片/引导/答案） |
| backend/core/orchestrator.py | **编排器** | 面向Agent：拿到明确的agent_type -> 直调对应Agent图，或按序串联多个Agent |

简单说：**统一入口负责"听懂用户要什么"，编排器负责"把活派给对的Agent"**。前者是"接待员"，后者是"调度台"。

### 8.1.3 统一请求生命周期

用户在统一助手里发一句话，经历的全流程如下：

```
                   用户一句话
                        │
            ┌───────────▼────────────┐
            │ POST /api/v1/chat/stream │   unified_chat.py
            └───────────┬────────────┘
                        │
  ① 规则前置拦截 _pre_filter ── 命中五类社交/元场景 ──→ 零Token模板回复 → done
     （你好/谢谢/再见/你是谁/你能做什么）           （完全不调LLM）
                        │ 未命中
                        ▼
  ② LLM路由 _llm_route（DeepSeek判6类意图，无本地分类模型）
                        │
                        ▼
  ③ 推送 routing_decision 事件（前端显示"已路由到XXX"卡片）
                        │
      ┌──────────────┬──────┴───────────┬──────────────┐
      ▼              ▼                  ▼              ▼
     qa          exam/resume        multi_agent     clarify
  单Agent流式    /interview         求职全链路计划     意图不明
  执行QA图      引导跳转对应页面    （resume→interview） 追问澄清
      │              │                  │              │
      ▼              ▼                  ▼              ▼
  token流+meta   guidance 事件      pipeline_plan    guidance 事件
                        │
                        ▼
                    done 事件
```

**SSE事件类型表**：

| 事件类型 | 何时推送 | 前端表现 |
|----------|---------|----------|
| routing_decision | LLM路由判完 | 顶部"已为你转接到【智能问答】"卡片 |
| progress | QA各节点开始（检索/精排等） | "检索知识库中..."进度条 |
| token | QA生成时逐字 | 答案气泡逐字打出 |
| meta | QA答完 | 答案模式/引用来源 |
| guidance | exam/resume/interview/clarify | 引导卡片（含"前往XX"按钮） |
| pipeline_plan | multi_agent | 多步骤计划卡片（按序点击） |
| done | 流结束 | 结束信号 |
| error | 异常 | 错误提示 |

### 8.1.4 两种执行模式：单Agent vs 多Agent串联

编排器（Orchestrator）对外只有一个入口 handle(request)，内部分两种模式：

```
  Orchestrator.handle(AgentRequest)
              │
        pipeline_mode?
         ┌────┴─────┐
         否          是
         ▼           ▼
   _run_single     _run_pipeline
     _agent         按序跑多个Agent
         │          前序structured_output
         │          自动注入后序context
   @with_retry          │
   调对应Agent图        ▼
         │        _aggregate_pipeline
         ▼        聚合各步结果
              │
              ▼
       AgentResponse（统一出参）
```

**单Agent直达**：最常见。_run_single_agent 直接调目标Agent的LangGraph图，用@with_retry包一层自动重试降级（来自3.5），从最终State提取响应，封装成统一的AgentResponse。

**多Agent串联Pipeline**：把几个Agent按固定顺序跑，前一个的结构化输出喂给后一个。源码里预置了一条Pipeline：

| Pipeline key | 顺序 | 场景 |
|-------------|------|------|
| job_preparation | 简历审查 -> 模拟面试 | 求职全链路：先审简历，把简历结果作为面试背景 |

### 8.1.5 为什么意图路由用LLM而不是本地分类模型

判断"用户这句话该路由到哪个Agent"是一个文本分类问题。本项目直接用DeepSeek判断（get_llm("intent")，温度0，返回JSON标签），原因：

- **调用频率低**：只有统一入口这一个地方触发路由，一次LLM调用开销完全可接受
- **省一个本地模型**：不必额外加载、维护一个分类模型，部署更轻
- **更灵活**：要新增一类意图，改Prompt即可，不用重训模型

异常兜底：LLM路由失败（超时/JSON解析失败）就降级回qa，不阻断SSE流——大不了当成普通技术问答处理，用户体验不断线。

### 8.1.6 本章零件来源对照

| 零件 | 在哪一章造的 | 本章怎么用 |
|------|-------------|-----------|
| 四个Agent图 build_*_graph | 第4/5/6/7章 | Orchestrator懒加载后直调 |
| 异常体系 exceptions.py | 3.3 | Orchestrator捕获AgentExecutionError/PipelineError等 |
| 重试降级 retry.py (with_retry) | 3.5 | _run_single_agent 用 @with_retry 包裹 |
| LLM工厂 get_llm（含intent配置） | 3.4 | 路由判断、QA流式都靠它 |
| MCP工具（知识库/联网搜索Server） | 5.11 | main.py 把它们 mount 进 FastAPI |
| 本地模型（reranker/分类器/BGE-M3） | 5.8/5.9/5.4 | main.py 启动时并行预热 |
| DB迁移 run_migrations | 第3章（数据库） | main.py lifespan 启动时执行 |
| 认证/依赖注入 get_current_user | 3.6 | 统一入口、各端点鉴权 |

## 8.2 Orchestrator Schema 与单Agent直达

### 8.2.1 两个枚举

```python
class ExecutionMode(str, Enum):
    """执行模式：决定一个请求怎么跑。"""
    SINGLE   = "single"     # 单Agent直达（最常见）
    PIPELINE = "pipeline"   # 多Agent串联（如求职全链路）
    CLARIFY  = "clarify"    # 澄清对话（意图不明，需追问）

class AgentType(str, Enum):
    """四个Agent的类型标识（继承str，可直接当字符串用）。"""
    QA        = "qa"         # 智能问答（第5章）
    EXAM      = "exam"       # 试卷批改（第6章）
    RESUME    = "resume"     # 简历审查（第4章）
    INTERVIEW = "interview"  # 模拟面试（第7章）
```

### 8.2.2 三个统一Schema

**AgentRequest**：统一入参。包含student_id、tenant_id、session_id、agent_type、user_message、context（附加上下文，如文件路径/历史数据）、pipeline_mode（是否强制走串联Pipeline）。提供thread_id只读属性，由student_id + session_id拼出，格式必须和各Agent内部的build_thread_id完全一致，这样编排器调图时传的thread_id才能命中MemorySaver里同一个检查点。

**AgentResponse**：统一出参。包含success、agent_type、content（文本响应）、structured（结构化数据，如评分/报告）、fallback_used（是否触发降级处理）、error_msg、metadata。

**PipelineResult**：串联结果。包含steps（各步AgentResponse列表）、combined（聚合后的最终数据）。

### 8.2.3 Orchestrator初始化与图懒加载

Orchestrator类初始化时维护两个核心数据结构：
- _agent_graphs：Agent图注册表（懒加载，key=AgentType，value=编译后的LangGraph）
- _pipelines：串联Pipeline定义（key=字符串名称，value=AgentType顺序列表）

**懒加载**：四个Agent图各自有不小的初始化成本（QA图要连Milvus、装载reranker）。如果在__init__里一次性全build，会拖慢启动且没用到的Agent也白占资源。懒加载让每个图在"第一次真正被调用"时才构建，构建后缓存进self._agent_graphs复用。在_get_agent_graph内部import而不是文件顶部import，也是懒加载的一部分——把build_qa_graph等的import推迟到真正需要时。

### 8.2.4 handle：统一请求入口

handle是编排器对外的唯一入口，逻辑很薄：看pipeline_mode决定走单Agent还是Pipeline，最外层包一个try/except保证无论内部怎么炸，都返回一个合法的AgentResponse（success=False + 友好文案），绝不把异常抛到API层。

注意区分两层兜底：_run_single_agent内部用@with_retry（3.5的三层兜底）处理"Agent执行中"的失败；而handle这层的try/except是最外层的保险，连_run_pipeline选错key、Schema异常这类也兜住。

### 8.2.5 _run_single_agent：单Agent直达

单Agent直达就是把统一的AgentRequest翻译成具体Agent图能吃的initial_state，调图，再把图的最终State翻译回统一的AgentResponse。编排器在这里扮演"适配器"：上层只认AgentRequest/AgentResponse，下层各Agent各玩各的State。

**context扩展点**：**request.context这一行是关键扩展点——Pipeline里前序Agent的结果就是通过context平铺进后序Agent的State的。

## 8.3 多Agent串联Pipeline

### 8.3.1 为什么需要串联：求职全链路

有些需求一个Agent答不完。比如"帮我准备求职"，理想流程是：简历审查Agent（六维度评分+提取项目/技能）-> 模拟面试Agent（拿到简历项目背景，针对性深挖面试）。如果让用户先去/resume跑一遍、再手动把结果复制到/interview，体验很割裂。串联Pipeline把这件事自动化。

### 8.3.2 _run_pipeline 实现

_run_pipeline按序复用_run_single_agent跑每步。关键设计：

1. **独立session_id**：给每一步加_step{idx}后缀，让不同Agent的检查点（MemorySaver）互不干扰
2. **上下文传递**：前一步的structured_output以{agent}_result为key塞进current_context；下一步构造step_request时context=current_context，8.2的_run_single_agent里那行**request.context就会把它平铺进下一个Agent的initial_state
3. **失败保留**：某一步失败时break，保留已完成步骤的结果而不是整体回滚。如果"简历审查"成功了、"模拟面试"那步挂了，用户至少能拿到简历评分

### 8.3.3 上下文传递机制（Pipeline的灵魂）

以求职全链路为例，数据流动：

```
第1步：简历审查
  输入 context: {pipeline_key, ...}
  输出 structured: {review_id, weighted_score, projects, skills_list, ...}
        │
        ▼ 注入 current_context：
          "resume_result"    = {review_id, weighted_score, ...}  ← 完整审查结果
          "resume_review_id" = "uuid-xxx"                        ← Interview专用key
          （若weighted_score < 60 → break，不启动面试）
第2步：模拟面试
  输入 context: {pipeline_key, resume_result: {...}, resume_review_id: "uuid-xxx"}
  面试load_context_node用resume_review_id查DB，拿到简历项目和技能，针对性出题
```

### 8.3.4 _aggregate_pipeline 结果聚合

聚合策略：文本用---分隔线拼成一篇（前端可整体展示），结构化数据按step_1/step_2分层保留每步明细，成功标志取"任一步成功"（部分成功也算有价值），降级标志取"任一步降级"。

### 8.3.5 模块级单例

Orchestrator内部缓存了懒加载的Agent图。如果每个请求都new一个Orchestrator，懒加载的缓存就白费了——每次都得重新build图。用单例get_orchestrator()让整个应用共享同一个编排器，图只build一次，全程复用。

## 8.4 统一入口 前置拦截与LLM路由

### 8.4.1 文件组织

文件 backend/api/v1/unified_chat.py，包含：
- Agent中文名映射_AGENT_DISPLAY
- 非QA意图的引导消息_GUIDANCE（exam/resume/interview的引导文案和跳转路径）
- QA Agent节点进度提示_PROGRESS_LABELS

### 8.4.2 规则前置拦截：五类零Token回复

**设计目的**：如果用户发"你好"、"谢谢"这类社交/元场景消息，完全不调LLM，直接返回模板回复，省时省Token。

**五类场景**：
1. HELLO：你好、嗨、早上好等问候
2. THANKS：谢谢、感谢等致谢
3. GOODBYE：再见、拜拜等告别
4. WHO_ARE_YOU：你是谁、你叫什么等身份询问
5. CAPABILITIES：你能做什么、你有什么功能等能力询问

**匹配方式**：精确匹配（关键词集合，如hello_keywords = {"你好","嗨","hi","hello"...}）和正则匹配（如"你[是叫]谁|你的名字"）

**_pre_filter函数**：输入用户消息，遍历五类场景，若命中返回对应模板字符串，否则返回None。

### 8.4.3 LLM意图路由

**_llm_route函数**：使用DeepSeek（get_llm("intent")，温度0）判断用户意图，返回JSON格式的RouteResult，包含label、agent_type、execution_mode、confidence、reason。

**六类意图映射**：
| label | agent_type | execution_mode | 说明 |
|-------|-----------|---------------|------|
| qa | QA | single | 技术问答/知识查询 |
| exam | EXAM | single | 试卷批改需求 |
| resume | RESUME | single | 简历审查需求 |
| interview | INTERVIEW | single | 模拟面试需求 |
| multi_agent | RESUME | pipeline | 求职全链路（多步串联） |
| clarify | QA | clarify | 意图不明，澄清追问 |

**降级策略**：LLM路由失败（超时/JSON解析失败）就降级回qa，不阻断SSE流。

## 8.5 SSE分发

### 8.5.1 请求模型与SSE小工具

UnifiedChatRequest：包含session_id（会话ID）和message（用户输入，非空、限长2000字符）。

_sse小工具：把dict包成sse_starlette要的格式，统一负责"dict -> JSON字符串 -> sse格式"，避免每处手写json.dumps。

### 8.5.2 unified_chat_stream 主流程

```python
@router.post("/stream")
async def unified_chat_stream(req, current_user):
    async def event_generator():
        # Step 0：规则前置拦截（零Token，五类模板回复）
        pre_reply = _pre_filter(req.message)
        if pre_reply is not None:
            yield _sse({"type": "token", "content": pre_reply})
            yield _sse({"type": "done"})
            return

        # Step 1：LLM路由判断
        decision = await _llm_route(req.message)

        # Step 2：推送路由决策卡片
        yield _sse({"type": "routing_decision", ...})

        # Step 3：按路由结果分发
        label = decision.label
        if label == "qa":
            # 流式执行QA Agent
            ...
        elif label in ("exam", "resume", "interview"):
            # 推送guidance引导跳转
            ...
        elif label == "multi_agent":
            # 推送pipeline_plan求职全链路计划
            ...
        else:  # clarify
            # 推送追问提示
            ...

    return EventSourceResponse(event_generator())
```

### 8.5.3 四条分发分支

**qa分支**：流式执行QA Agent。通过astream_events逐token推送给前端，同时推送progress事件（各节点进度）和meta事件（答案模式/引用来源）。

**exam/resume/interview分支**：推送guidance事件，包含引导文案和跳转链接（action_url）。这些功能需要专门页面（上传文件/选岗位），统一入口不直接执行，而是让前端把用户导到对应功能页。

**multi_agent分支**：推送pipeline_plan事件，包含步骤数组（各步label、description、action_url）。注意：pipeline_plan不等于跑Pipeline——这里只推计划让前端逐步引导用户点击，而不是程序化跑完所有Agent。而编排器的_run_pipeline才是程序化一次跑完多个Agent（由强制Pipeline的请求触发）。两条路径并存，服务不同的交互需求。

**clarify分支**：推送guidance事件，提示用户补充信息（如"请说明您需要简历审查、试卷批改还是模拟面试？"），前端显示追问气泡。

### 8.5.4 _stream_qa_agent：流式跑QA

在统一入口里复用QA图的astream_events流式输出。通过监听不同的事件名（on_chat_model_stream对应token，on_chain_start对应progress节点进入），分别推送不同SSE事件类型给前端。

## 8.6 路由聚合与main集成

### 8.6.1 api/router.py：六个router聚合

每个功能模块（认证、问答、批改、简历、面试、统一入口）各自定义了一个APIRouter。router.py把它们带前缀聚合成一个总路由api_router：

```python
api_router = APIRouter()
api_router.include_router(auth.router, prefix="/auth", tags=["认证"])
api_router.include_router(unified_chat.router, prefix="/chat", tags=["AI助手"])
api_router.include_router(qa.router, prefix="/qa", tags=["智能问答"])
api_router.include_router(exam.router, prefix="/exam", tags=["试卷批改"])
api_router.include_router(resume.router, prefix="/resume", tags=["简历审查"])
api_router.include_router(interview.router, prefix="/interview", tags=["模拟面试"])
```

include_router三个要点：prefix（给该模块所有路由加统一前缀）、tags（给Swagger文档分组）、顺序（把unified_chat放在各Agent之前，语义上突出它是"主入口"）。

### 8.6.2 完整路由表

| 模块 | 前缀 | 代表性接口 |
|------|------|-----------|
| 认证 | /auth | POST /auth/login |
| AI助手 | /chat | POST /chat/stream（统一入口SSE） |
| 智能问答 | /qa | POST /qa/... |
| 试卷批改 | /exam | POST /exam/... |
| 简历审查 | /resume | POST /resume/... |
| 模拟面试 | /interview | POST /interview/... |

统一入口/chat/stream是"总机"——用户一句话进来，由它路由到后面五个模块。其余/qa /exam等是"分机"，前端的专门页面（上传简历、选岗位）直接调它们。两套接口并存：聊天框走总机，功能页走分机。

### 8.6.3 lifespan：启动与关闭钩子

**lifespan机制**是FastAPI的异步上下文管理器，在应用启动时执行初始化，关闭时执行清理。main.py的lifespan做三件事：

1. **DB迁移**：调用run_migrations()，确保所有表结构是最新版本
2. **本地模型预热**：并行（asyncio.gather）预热reranker、意图分类器、BGE-M3嵌入模型等本地模型，首次调用时不用等模型加载
3. **MCP子应用生命周期**：启动/关闭MCP Server（知识库检索Server和联网搜索Server）

**Windows conda兼容**：文件头有Windows conda专用的DLL搜索路径设置，把base环境的Library/bin加入DLL搜索路径，让_lzma.pyd能找到liblzma.dll。

### 8.6.4 应用创建与挂载


## 核心设计决策总结

### 1. Orchestrator设计模式
**决策**：创建独立的编排器类，统一管理Agent图的懒加载、单Agent直达和多Agent串联Pipeline。
**理由**：将调度逻辑从API层解耦，使API层只关注请求/响应格式，编排器关注执行逻辑。模块级单例确保图缓存只build一次。
**核心文件**：backend/core/orchestrator.py

### 2. LLM路由 vs 本地分类模型
**决策**：使用DeepSeek（get_llm("intent")，温度0）直接做意图分类，不部署本地分类模型。
**理由**：调用频率低（仅统一入口一处触发），省一个本地模型资源，改Prompt即可新增意图。失败时降级回qa。
**核心文件**：backend/api/v1/unified_chat.py _llm_route函数

### 3. SSE流式分发
**决策**：统一入口使用SSE（Server-Sent Events）流式返回，前端边收边渲染。
**理由**：SSE天然支持流式推送，适合AI生成场景。8种事件类型分别对应不同UI组件，前端按事件类型分别渲染。
**核心文件**：backend/api/v1/unified_chat.py unified_chat_stream函数

### 4. 前置拦截零Token回复
**决策**：在LLM路由之前做规则前置拦截，五类社交/元场景直接返回模板回复。
**理由**：完全不调LLM，省时省Token。对高频问候语/致谢场景响应极快，提升用户体验。
**核心文件**：backend/api/v1/unified_chat.py _pre_filter函数

### 5. 两种入口并存
**决策**：统一入口/chat/stream作为"总机"，各Agent的独立接口作为"分机"。
**理由**：用户可以从聊天框一句话触发路由，也可以从专门页面直接调用对应功能。两套接口并存，覆盖不同使用场景。
**核心文件**：backend/api/router.py

### 6. lifespan启动机制
**决策**：使用FastAPI的lifespan异步上下文管理器，在启动时执行DB迁移、本地模型预热、MCP子应用生命周期管理。
**理由**：确保应用启动时完成所有初始化工作，运行时不再有"首次调用慢"的问题。关闭时优雅清理MCP连接。
**核心文件**：backend/main.py lifespan函数

### 7. 图懒加载
**决策**：Orchestrator内部维护_agent_graphs缓存，首次访问某Agent时才build图并缓存。
**理由**：四个Agent图各有不小的初始化成本，一次性全build会拖慢启动且占用资源。懒加载用到才付代价。
**核心文件**：backend/core/orchestrator.py _get_agent_graph方法
