## 8.1 系统集成全景

### 8.1.1 前四章造了什么，这一章做什么

到第 7 章为止，四个 Agent 各自从零实现，每个 Agent 演示一种 LangGraph 范式：

| Agent | 范式 | 章节 | 入口接口 |
|-------|------|------|----------|
| 简历审查 | 并行评审（六维度 fan-out/fan-in） | 第 4 章 | POST /resume/... |
| 智能问答 | RAG（检索增强 + 记忆） | 第 5 章 | POST /qa/... |
| 试卷批改 | Human-in-the-Loop（interrupt/resume） | 第 6 章 | POST /exam/... |
| 模拟面试 | 状态机 + SSE（多轮对话） | 第 7 章 | POST /interview/... |

但它们现在是四个互不相干的接口。学员要用，得自己知道"问技术问题去 /qa、批改去 /exam、面试去 /interview"——这把"判断该用哪个功能"的负担丢给了用户。

**第 8 章的核心任务**：在四个 Agent 前面架一个统一入口，用户只管说一句话，系统自动判断该路由到哪个 Agent（或哪几个 Agent 串联），再把结果以统一格式返回。

> 关键认知：本章几乎不"造新轮子"。所有 Agent 图（build_*_graph）、异常体系、重试降级、LLM 工厂、MCP 工具、本地模型——全部在前面章节已经实现。本章的工作是**装配**：把这些零件接到一个统一入口和一个 main.py 上。

### 8.1.2 两个核心角色

| 文件 | 角色 | 一句话职责 |
|------|------|-----------|
| backend/api/v1/unified_chat.py | **统一入口** | 面向用户：收一句话 -> 判断意图 -> 用 SSE 流式返回（路由卡片/引导/答案） |
| backend/core/orchestrator.py | **编排器** | 面向 Agent：拿到明确的 agent_type -> 直调对应 Agent 图，或按序串联多个 Agent |

简单说：**统一入口负责"听懂用户要什么"，编排器负责"把活派给对的 Agent"**。前者是"接待员"，后者是"调度台"。

### 8.1.3 统一请求生命周期

用户在统一助手里发一句话，经历的全流程如下：

```python
                   用户一句话
                        │
            ┌───────────▼────────────┐
            │ POST /api/v1/chat/stream │   unified_chat.py
            └───────────┬────────────┘
                        │
  ① 规则前置拦截 _pre_filter ── 命中五类社交/元场景 ──→ 零Token模板回复 → done
     （你好/谢谢/再见/你是谁/你能做什么）           （完全不调LLM）
                        │ 未命中
                        ▼
  ② LLM路由 _llm_route（DeepSeek判6类意图，无本地分类模型）
                        │
                        ▼
  ③ 推送 routing_decision 事件（前端显示"已路由到XXX"卡片）
                        │
      ┌──────────────┬──────┴───────────┬──────────────┐
      ▼              ▼                  ▼              ▼
     qa          exam/resume        multi_agent     clarify
  单Agent流式    /interview         求职全链路计划     意图不明
  执行QA图      引导跳转对应页面    （resume→interview） 追问澄清
      │              │                  │              │
      ▼              ▼                  ▼              ▼
  token流+meta   guidance 事件      pipeline_plan    guidance 事件
                        │
                        ▼
                    done 事件
```

**SSE 事件类型表**：

| 事件类型 | 何时推送 | 前端表现 |
|----------|---------|----------|
| routing_decision | LLM 路由判完 | 顶部"已为你转接到【智能问答】"卡片 |
| progress | QA 各节点开始（检索/精排等） | "检索知识库中..."进度条 |
| token | QA 生成时逐字 | 答案气泡逐字打出 |
| meta | QA 答完 | 答案模式/引用来源 |
| guidance | exam/resume/interview/clarify | 引导卡片（含"前往 XX"按钮） |
| pipeline_plan | multi_agent | 多步骤计划卡片（按序点击） |
| done | 流结束 | 结束信号 |
| error | 异常 | 错误提示 |

### 8.1.4 两种执行模式：单 Agent vs 多 Agent 串联

编排器（Orchestrator）对外只有一个入口 handle(request)，内部分两种模式：

```python
  Orchestrator.handle(AgentRequest)
              │
        pipeline_mode?
         ┌────┴─────┐
         否          是
         ▼           ▼
   _run_single     _run_pipeline
     _agent         按序跑多个Agent
         │          前序structured_output
         │          自动注入后序context
   @with_retry          │
   调对应Agent图        ▼
         │        _aggregate_pipeline
         ▼        聚合各步结果
              │
              ▼
       AgentResponse（统一出参）
```

**单 Agent 直达**：最常见。_run_single_agent 直接调目标 Agent 的 LangGraph 图，用@with_retry 包一层自动重试降级（来自 3.5），从最终 State 提取响应，封装成统一的 AgentResponse。

**多 Agent 串联 Pipeline**：把几个 Agent 按固定顺序跑，前一个的结构化输出喂给后一个。源码里预置了一条 Pipeline：

| Pipeline key | 顺序 | 场景 |
|-------------|------|------|
| job_preparation | 简历审查 -> 模拟面试 | 求职全链路：先审简历，把简历结果作为面试背景 |

### 8.1.5 为什么意图路由用 LLM 而不是本地分类模型

判断"用户这句话该路由到哪个 Agent"是一个文本分类问题。本项目直接用 DeepSeek 判断（get_llm("intent")，温度 0，返回 JSON 标签），原因：

- **调用频率低**：只有统一入口这一个地方触发路由，一次 LLM 调用开销完全可接受
- **省一个本地模型**：不必额外加载、维护一个分类模型，部署更轻
- **更灵活**：要新增一类意图，改 Prompt 即可，不用重训模型

异常兜底：LLM 路由失败（超时/JSON 解析失败）就降级回 qa，不阻断 SSE 流——大不了当成普通技术问答处理，用户体验不断线。

### 8.1.6 本章零件来源对照

| 零件 | 在哪一章造的 | 本章怎么用 |
|------|-------------|-----------|
| 四个 Agent 图 build_*_graph | 第 4/5/6/7 章 | Orchestrator 懒加载后直调 |
| 异常体系 exceptions.py | 3.3 | Orchestrator 捕获 AgentExecutionError/PipelineError 等 |
| 重试降级 retry.py (with_retry) | 3.5 | _run_single_agent 用 @with_retry 包裹 |
| LLM 工厂 get_llm（含 intent 配置） | 3.4 | 路由判断、QA 流式都靠它 |
| MCP 工具（知识库/联网搜索 Server） | 5.11 | main.py 把它们 mount 进 FastAPI |
| 本地模型（reranker/分类器/BGE-M3） | 5.8/5.9/5.4 | main.py 启动时并行预热 |
| DB 迁移 run_migrations | 第 3 章（数据库） | main.py lifespan 启动时执行 |
| 认证/依赖注入 get_current_user | 3.6 | 统一入口、各端点鉴权 |

## 8.2 Orchestrator Schema 与单 Agent 直达

### 8.2.1 两个枚举

```python
class ExecutionMode(str, Enum):
    """执行模式：决定一个请求怎么跑。"""
    SINGLE   = "single"     # 单Agent直达（最常见）
    PIPELINE = "pipeline"   # 多Agent串联（如求职全链路）
    CLARIFY  = "clarify"    # 澄清对话（意图不明，需追问）

class AgentType(str, Enum):
    """四个Agent的类型标识（继承str，可直接当字符串用）。"""
    QA        = "qa"         # 智能问答（第5章）
    EXAM      = "exam"       # 试卷批改（第6章）
    RESUME    = "resume"     # 简历审查（第4章）
    INTERVIEW = "interview"  # 模拟面试（第7章）
```

### 8.2.2 三个统一 Schema

**AgentRequest**：统一入参。包含 student_id、tenant_id、session_id、agent_type、user_message、context（附加上下文，如文件路径/历史数据）、pipeline_mode（是否强制走串联 Pipeline）。提供 thread_id 只读属性，由 student_id + session_id 拼出，格式必须和各 Agent 内部的 build_thread_id 完全一致，这样编排器调图时传的 thread_id 才能命中 MemorySaver 里同一个检查点。

**AgentResponse**：统一出参。包含 success、agent_type、content（文本响应）、structured（结构化数据，如评分/报告）、fallback_used（是否触发降级处理）、error_msg、metadata。

**PipelineResult**：串联结果。包含 steps（各步 AgentResponse 列表）、combined（聚合后的最终数据）。

### 8.2.3 Orchestrator 初始化与图懒加载

Orchestrator 类初始化时维护两个核心数据结构：

- _agent_graphs：Agent 图注册表（懒加载，key=AgentType，value=编译后的 LangGraph）
- _pipelines：串联 Pipeline 定义（key=字符串名称，value=AgentType 顺序列表）

**懒加载**：四个 Agent 图各自有不小的初始化成本（QA 图要连 Milvus、装载 reranker）。如果在 __init__ 里一次性全 build，会拖慢启动且没用到的 Agent 也白占资源。懒加载让每个图在"第一次真正被调用"时才构建，构建后缓存进 self._agent_graphs 复用。在 _get_agent_graph 内部 import 而不是文件顶部 import，也是懒加载的一部分——把 build_qa_graph 等的 import 推迟到真正需要时。

### 8.2.4 handle：统一请求入口

handle 是编排器对外的唯一入口，逻辑很薄：看 pipeline_mode 决定走单 Agent 还是 Pipeline，最外层包一个 try/except 保证无论内部怎么炸，都返回一个合法的 AgentResponse（success=False + 友好文案），绝不把异常抛到 API 层。

注意区分两层兜底：_run_single_agent 内部用@with_retry（3.5 的三层兜底）处理"Agent 执行中"的失败；而 handle 这层的 try/except 是最外层的保险，连 _run_pipeline 选错 key、Schema 异常这类也兜住。

### 8.2.5 _run_single_agent：单 Agent 直达

单 Agent 直达就是把统一的 AgentRequest 翻译成具体 Agent 图能吃的 initial_state，调图，再把图的最终 State 翻译回统一的 AgentResponse。编排器在这里扮演"适配器"：上层只认 AgentRequest/AgentResponse，下层各 Agent 各玩各的 State。

**context 扩展点**：**request.context 这一行是关键扩展点——Pipeline 里前序 Agent 的结果就是通过 context 平铺进后序 Agent 的 State 的。

## 8.3 多 Agent 串联 Pipeline

### 8.3.1 为什么需要串联：求职全链路

有些需求一个 Agent 答不完。比如"帮我准备求职"，理想流程是：简历审查 Agent（六维度评分+提取项目/技能）-> 模拟面试 Agent（拿到简历项目背景，针对性深挖面试）。如果让用户先去/resume 跑一遍、再手动把结果复制到/interview，体验很割裂。串联 Pipeline 把这件事自动化。

### 8.3.2 _run_pipeline 实现

_run_pipeline 按序复用 _run_single_agent 跑每步。关键设计：

1. **独立 session_id**：给每一步加_ step{idx}后缀，让不同 Agent 的检查点（MemorySaver）互不干扰
2. **上下文传递**：前一步的 structured_output 以{agent}_result 为 key 塞进 current_context；下一步构造 step_request 时 context=current_context，8.2 的 _run_single_agent 里那行** request.context 就会把它平铺进下一个 Agent 的 initial_state
3. **失败保留**：某一步失败时 break，保留已完成步骤的结果而不是整体回滚。如果"简历审查"成功了、"模拟面试"那步挂了，用户至少能拿到简历评分

### 8.3.3 上下文传递机制（Pipeline 的灵魂）

以求职全链路为例，数据流动：

```python
第1步：简历审查
  输入 context: {pipeline_key, ...}
  输出 structured: {review_id, weighted_score, projects, skills_list, ...}
        │
        ▼ 注入 current_context：
          "resume_result"    = {review_id, weighted_score, ...}  ← 完整审查结果
          "resume_review_id" = "uuid-xxx"                        ← Interview专用key
          （若weighted_score < 60 → break，不启动面试）
第2步：模拟面试
  输入 context: {pipeline_key, resume_result: {...}, resume_review_id: "uuid-xxx"}
  面试load_context_node用resume_review_id查DB，拿到简历项目和技能，针对性出题
```

### 8.3.4 _aggregate_pipeline 结果聚合

聚合策略：文本用---分隔线拼成一篇（前端可整体展示），结构化数据按 step_1/step_2 分层保留每步明细，成功标志取"任一步成功"（部分成功也算有价值），降级标志取"任一步降级"。

### 8.3.5 模块级单例

Orchestrator 内部缓存了懒加载的 Agent 图。如果每个请求都 new 一个 Orchestrator，懒加载的缓存就白费了——每次都得重新 build 图。用单例 get_orchestrator()让整个应用共享同一个编排器，图只 build 一次，全程复用。

## 8.4 统一入口 前置拦截与 LLM 路由

### 8.4.1 文件组织

文件 backend/api/v1/unified_chat.py，包含：

- Agent 中文名映射 _AGENT_DISPLAY
- 非 QA 意图的引导消息 _GUIDANCE（exam/resume/interview 的引导文案和跳转路径）
- QA Agent 节点进度提示 _PROGRESS_LABELS

### 8.4.2 规则前置拦截：五类零 Token 回复

**设计目的**：如果用户发"你好"、"谢谢"这类社交/元场景消息，完全不调 LLM，直接返回模板回复，省时省 Token。

**五类场景**：

1. HELLO：你好、嗨、早上好等问候
2. THANKS：谢谢、感谢等致谢
3. GOODBYE：再见、拜拜等告别
4. WHO_ARE_YOU：你是谁、你叫什么等身份询问
5. CAPABILITIES：你能做什么、你有什么功能等能力询问

**匹配方式**：精确匹配（关键词集合，如 hello_keywords = {"你好","嗨","hi","hello"...}）和正则匹配（如"你[是叫]谁|你的名字"）

**_pre_filter 函数**：输入用户消息，遍历五类场景，若命中返回对应模板字符串，否则返回 None。

### 8.4.3 LLM 意图路由

**_llm_route 函数**：使用 DeepSeek（get_llm("intent")，温度 0）判断用户意图，返回 JSON 格式的 RouteResult，包含 label、agent_type、execution_mode、confidence、reason。

**六类意图映射**：

| label | agent_type | execution_mode | 说明 |
|-------|-----------|---------------|------|
| qa | QA | single | 技术问答/知识查询 |
| exam | EXAM | single | 试卷批改需求 |
| resume | RESUME | single | 简历审查需求 |
| interview | INTERVIEW | single | 模拟面试需求 |
| multi_agent | RESUME | pipeline | 求职全链路（多步串联） |
| clarify | QA | clarify | 意图不明，澄清追问 |

**降级策略**：LLM 路由失败（超时/JSON 解析失败）就降级回 qa，不阻断 SSE 流。

## 8.5 SSE 分发

### 8.5.1 请求模型与 SSE 小工具

UnifiedChatRequest：包含 session_id（会话 ID）和 message（用户输入，非空、限长 2000 字符）。

_sse 小工具：把 dict 包成 sse_starlette 要的格式，统一负责"dict -> JSON 字符串 -> sse 格式"，避免每处手写 json.dumps。

### 8.5.2 unified_chat_stream 主流程

```python
@router.post("/stream")
async def unified_chat_stream(req, current_user):
    async def event_generator():
        # Step 0：规则前置拦截（零Token，五类模板回复）
        pre_reply = _pre_filter(req.message)
        if pre_reply is not None:
            yield _sse({"type": "token", "content": pre_reply})
            yield _sse({"type": "done"})
            return

        # Step 1：LLM路由判断
        decision = await _llm_route(req.message)

        # Step 2：推送路由决策卡片
        yield _sse({"type": "routing_decision", ...})

        # Step 3：按路由结果分发
        label = decision.label
        if label == "qa":
            # 流式执行QA Agent
            ...
        elif label in ("exam", "resume", "interview"):
            # 推送guidance引导跳转
            ...
        elif label == "multi_agent":
            # 推送pipeline_plan求职全链路计划
            ...
        else:  # clarify
            # 推送追问提示
            ...

    return EventSourceResponse(event_generator())
```

### 8.5.3 四条分发分支

**qa 分支**：流式执行 QA Agent。通过 astream_events 逐 token 推送给前端，同时推送 progress 事件（各节点进度）和 meta 事件（答案模式/引用来源）。

**exam/resume/interview 分支**：推送 guidance 事件，包含引导文案和跳转链接（action_url）。这些功能需要专门页面（上传文件/选岗位），统一入口不直接执行，而是让前端把用户导到对应功能页。

**multi_agent 分支**：推送 pipeline_plan 事件，包含步骤数组（各步 label、description、action_url）。注意：pipeline_plan 不等于跑 Pipeline——这里只推计划让前端逐步引导用户点击，而不是程序化跑完所有 Agent。而编排器的 _run_pipeline 才是程序化一次跑完多个 Agent（由强制 Pipeline 的请求触发）。两条路径并存，服务不同的交互需求。

**clarify 分支**：推送 guidance 事件，提示用户补充信息（如"请说明您需要简历审查、试卷批改还是模拟面试？"），前端显示追问气泡。

### 8.5.4 _stream_qa_agent：流式跑 QA

在统一入口里复用 QA 图的 astream_events 流式输出。通过监听不同的事件名（on_chat_model_stream 对应 token，on_chain_start 对应 progress 节点进入），分别推送不同 SSE 事件类型给前端。

## 8.6 路由聚合与 main 集成

### 8.6.1 api/router.py：六个 router 聚合

每个功能模块（认证、问答、批改、简历、面试、统一入口）各自定义了一个 APIRouter。router.py 把它们带前缀聚合成一个总路由 api_router：

```python
api_router = APIRouter()
api_router.include_router(auth.router, prefix="/auth", tags=["认证"])
api_router.include_router(unified_chat.router, prefix="/chat", tags=["AI助手"])
api_router.include_router(qa.router, prefix="/qa", tags=["智能问答"])
api_router.include_router(exam.router, prefix="/exam", tags=["试卷批改"])
api_router.include_router(resume.router, prefix="/resume", tags=["简历审查"])
api_router.include_router(interview.router, prefix="/interview", tags=["模拟面试"])
```

include_router 三个要点：prefix（给该模块所有路由加统一前缀）、tags（给 Swagger 文档分组）、顺序（把 unified_chat 放在各 Agent 之前，语义上突出它是"主入口"）。

### 8.6.2 完整路由表

| 模块 | 前缀 | 代表性接口 |
|------|------|-----------|
| 认证 | /auth | POST /auth/login |
| AI 助手 | /chat | POST /chat/stream（统一入口 SSE） |
| 智能问答 | /qa | POST /qa/... |
| 试卷批改 | /exam | POST /exam/... |
| 简历审查 | /resume | POST /resume/... |
| 模拟面试 | /interview | POST /interview/... |

统一入口/chat/stream 是"总机"——用户一句话进来，由它路由到后面五个模块。其余/qa /exam 等是"分机"，前端的专门页面（上传简历、选岗位）直接调它们。两套接口并存：聊天框走总机，功能页走分机。

### 8.6.3 lifespan：启动与关闭钩子

**lifespan 机制**是 FastAPI 的异步上下文管理器，在应用启动时执行初始化，关闭时执行清理。main.py 的 lifespan 做三件事：

1. **DB 迁移**：调用 run_migrations()，确保所有表结构是最新版本
2. **本地模型预热**：并行（asyncio.gather）预热 reranker、意图分类器、BGE-M3 嵌入模型等本地模型，首次调用时不用等模型加载
3. **MCP 子应用生命周期**：启动/关闭 MCP Server（知识库检索 Server 和联网搜索 Server）

**Windows conda 兼容**：文件头有 Windows conda 专用的 DLL 搜索路径设置，把 base 环境的 Library/bin 加入 DLL 搜索路径，让 _lzma.pyd 能找到 liblzma.dll。

### 8.6.4 应用创建与挂载

```python
app = FastAPI(lifespan=lifespan, title="EduAgent API", version="7.7.0")
app.add_middleware(CORSMiddleware, ...)  # 配置CORS允许跨域

# MCP挂载：knowledge_search_server和web_search_server作为子应用mount到/mcp下
```

## 核心设计决策总结

### 1. Orchestrator 设计模式

**决策**：创建独立的编排器类，统一管理 Agent 图的懒加载、单 Agent 直达和多 Agent 串联 Pipeline。

**理由**：将调度逻辑从 API 层解耦，使 API 层只关注请求/响应格式，编排器关注执行逻辑。模块级单例确保图缓存只 build 一次。

**核心文件**：backend/core/orchestrator.py

### 2. LLM 路由 vs 本地分类模型

**决策**：使用 DeepSeek（get_llm("intent")，温度 0）直接做意图分类，不部署本地分类模型。

**理由**：调用频率低（仅统一入口一处触发），省一个本地模型资源，改 Prompt 即可新增意图。失败时降级回 qa。

**核心文件**：backend/api/v1/unified_chat.py _llm_route 函数

### 3. SSE 流式分发

**决策**：统一入口使用 SSE（Server-Sent Events）流式返回，前端边收边渲染。

**理由**：SSE 天然支持流式推送，适合 AI 生成场景。8 种事件类型分别对应不同 UI 组件，前端按事件类型分别渲染。

**核心文件**：backend/api/v1/unified_chat.py unified_chat_stream 函数

### 4. 前置拦截零 Token 回复

**决策**：在 LLM 路由之前做规则前置拦截，五类社交/元场景直接返回模板回复。

**理由**：完全不调 LLM，省时省 Token。对高频问候语/致谢场景响应极快，提升用户体验。

**核心文件**：backend/api/v1/unified_chat.py _pre_filter 函数

### 5. 两种入口并存

**决策**：统一入口/chat/stream 作为"总机"，各 Agent 的独立接口作为"分机"。

**理由**：用户可以从聊天框一句话触发路由，也可以从专门页面直接调用对应功能。两套接口并存，覆盖不同使用场景。

**核心文件**：backend/api/router.py

### 6. lifespan 启动机制

**决策**：使用 FastAPI 的 lifespan 异步上下文管理器，在启动时执行 DB 迁移、本地模型预热、MCP 子应用生命周期管理。

**理由**：确保应用启动时完成所有初始化工作，运行时不再有"首次调用慢"的问题。关闭时优雅清理 MCP 连接。

**核心文件**：backend/main.py lifespan 函数

### 7. 图懒加载

**决策**：Orchestrator 内部维护 _agent_graphs 缓存，首次访问某 Agent 时才 build 图并缓存。

**理由**：四个 Agent 图各有不小的初始化成本，一次性全 build 会拖慢启动且占用资源。懒加载用到才付代价。

**核心文件**：backend/core/orchestrator.py _get_agent_graph 方法
