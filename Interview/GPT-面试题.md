# 曹浩磊｜大模型应用开发工程师面试题及详细参考答案

> 适用岗位：2 年左右经验的大模型应用开发、Agent 开发、RAG 开发工程师  
> 使用说明：技术题给出相对确定的标准答案；项目题给出基于简历的高质量回答模板。项目中的样本规模、提升比例、线上指标和具体实现必须以候选人的真实经历为准，不应背诵或虚构。

## 一、技术能力面试题及答案

### 1. Agent 与 LangGraph

#### 1. LangGraph 中 `StateGraph`、节点、边和条件边分别解决什么问题？

**参考答案：**

- `StateGraph` 是以共享状态为中心的图执行模型。开发者先定义 State Schema，再注册节点和边，编译后得到可执行图。状态不是随意拼接的全局字典，而是各节点之间明确的数据契约；节点通常只返回部分状态更新，运行时依据字段对应的 reducer 合并更新。
- 节点（Node）负责“做什么”，本质上是普通函数或异步函数。节点可以调用 LLM、访问数据库、执行检索、调用工具，也可以只完成纯规则判断。
- 普通边（Edge）负责固定流转，例如“解析完成后一定进入检索”。
- 条件边（Conditional Edge）根据当前状态动态选择下一节点，例如模型判断为“需要工具”则进入工具节点，判断为“信息不足”则进入澄清节点，判断为“完成”则进入 `END`。
- `START` 和 `END` 是特殊节点，分别表示入口和终点。图在编译时会进行结构检查，并可注入 Checkpointer 等运行能力。

工程上应把稳定、可审计的业务步骤显式编排成图，把真正需要语义判断的部分交给模型。若所有步骤都交给模型自主决定，流程可控性、可观测性和错误定位都会下降。

#### 2. 你如何设计一个 Agent 的 State Schema？哪些状态需要持久化？

**参考答案：**

State 应围绕任务生命周期设计，至少可分为五类：

1. **身份与会话信息**：`user_id`、`session_id`、`thread_id`、租户、角色和权限。
2. **用户输入与对话信息**：原始问题、规范化问题、必要的历史摘要，而不是无限保存全部消息。
3. **任务规划信息**：意图、当前节点、计划、已完成步骤、待执行步骤、重试次数和终止原因。
4. **业务与工具信息**：订单号、商品 ID、工具调用参数、调用结果、错误码、幂等键和审批状态。
5. **检索与生成信息**：改写后的 Query、过滤条件、候选文档、引用来源、最终答案和置信度。

需要持久化的是恢复任务所需的最小充分状态，例如当前步骤、关键业务标识、审批状态、已成功的副作用操作、工具结果摘要和错误信息。大型原文、Embedding、完整日志不宜直接塞入 State，可保存对象存储地址或数据库主键。密码、令牌等秘密不应进入 State。

还要定义字段更新语义：单值字段通常覆盖，消息或审计事件可追加；并行节点可能写同一字段时必须设计 reducer，防止后写覆盖先写。生产环境还应为 Schema 加版本号，便于图升级后的状态迁移。

#### 3. Checkpointer 的作用是什么？如何实现任务暂停、恢复和断点续跑？

**参考答案：**

Checkpointer 按线程保存图状态快照，使系统能够支持多轮上下文、故障恢复、人工介入和历史状态检查。调用图时通过稳定的 `thread_id` 标识一次持续任务；每个执行阶段形成 checkpoint。进程重启后，只要使用持久化 Checkpointer 和相同 `thread_id`，仍能加载状态。

典型流程为：

1. 编译图时接入数据库型 Checkpointer，开发阶段可用内存实现，生产环境应使用 PostgreSQL 等持久化实现。
2. 请求进入时分配稳定的 `thread_id`。
3. 在退款等高风险节点调用 `interrupt()`，运行时保存状态并向外返回审批信息。
4. 人工审核后，用相同 `thread_id` 和 `Command(resume=审批结果)` 恢复。
5. 图根据审批结果继续、修改参数或终止。

一个重要细节是：中断恢复时，包含 `interrupt()` 的节点可能从头重新执行，因此中断之前的副作用必须幂等，或者把副作用放到审批之后的独立节点。Checkpointer 解决的是执行状态恢复，不等于业务数据库事务，也不能代替幂等控制。

#### 4. Agent 自主循环如何避免无限调用工具？

**参考答案：**

应采用多层限制，而不是只依赖 Prompt：

- 设置图递归上限、最大迭代数、最大工具调用数、总超时时间和 Token/费用预算。
- 在 State 中保存 `step_count`、同一工具及相同参数的调用指纹、最近错误和连续失败次数。
- 当同一工具以相同参数重复调用且状态没有新增信息时，判定为无进展循环。
- 工具结果要返回明确的结构化状态，如 `success`、`retryable`、`error_code`、`missing_fields`，不要只返回含糊自然语言。
- 将终止条件显式化：目标已完成、需要用户补充、必须人工接管、不可恢复错误或预算耗尽。
- 对可重试错误使用有限次数的指数退避；参数错误应重新规划或请求补充，不能机械重试。

最终兜底应生成可解释结果，例如“物流接口连续超时，已转人工处理”，而不是静默失败或继续循环。

#### 5. ReAct、Tool Calling 和普通 Prompt 调用有什么区别？

**参考答案：**

- 普通 Prompt 调用是输入消息、输出文本，适合摘要、改写、分类和无需外部实时数据的生成任务。
- Tool Calling 是模型输出符合工具 Schema 的调用意图与参数，由应用执行工具，再将结果返回给模型。它是一种结构化交互机制，不自动等同于完整 Agent。
- ReAct 是“推理与行动交替”的 Agent 范式：模型根据当前观察选择行动，得到工具结果后继续判断，直到完成任务。工程实现中通常不会向用户暴露模型内部思维，而是保存可审计的计划、工具调用和结果摘要。

三者可以组合：LangGraph 控制总体流程，节点内模型通过 Tool Calling 选择工具，整个循环体现 ReAct 风格。对于固定且高风险的流程，应优先显式图编排；对于开放探索任务，才给予更大自主循环空间。

#### 6. 如何判断用户应该被路由到商品审核 Agent、售后 Agent还是其他 Agent？

**参考答案：**

先定义清晰且互斥度尽可能高的意图体系，例如商品审核、订单查询、物流查询、退换售后、营销导购、闲聊、不支持和多意图。路由可以采用“规则 + 模型分类 + 置信度门槛”的组合：订单号、退款等强特征先用规则或实体识别辅助；其余使用带标签定义和 Few-shot 示例的分类模型，并通过结构化输出返回 `intent`、`confidence`、`entities`、`reason_code`。

若最高置信度不足、第一与第二分类差距过小或关键实体缺失，应进入澄清，而不是强行分派。多意图请求需要拆成子任务，并检查依赖关系。例如“查询物流，如果没发货就退款”必须先查状态，再根据结果决定是否进入售后。

评测时不能只看总体 Accuracy，还要看每类 Precision/Recall、混淆矩阵、拒识准确率和多意图任务成功率。线上还要记录人工改派率与下游 Agent 失败原因。

#### 7. 多 Agent 系统中，Orchestrator 与具体业务 Agent 如何划分职责？

**参考答案：**

Orchestrator 负责全局而轻量的职责：鉴权、意图识别、任务拆分、依赖排序、Agent 选择、全局预算、跨 Agent 状态汇总、异常兜底和最终响应聚合。领域 Agent 负责本领域知识、工具、业务规则和完成条件，例如售后 Agent 才理解退款条件、物流状态和审批策略。

边界原则是“领域逻辑归领域 Agent，全局协调归 Orchestrator”。Orchestrator 不应复制每个 Agent 的详细规则，否则会形成巨型 Prompt 和双重维护；领域 Agent 也不应擅自访问其他领域的高权限工具。各 Agent 之间通过版本化的输入输出 Schema 交互，而不是传递任意长对话文本。

#### 8. Agent 调用工具前后分别需要做哪些参数校验和结果校验？

**参考答案：**

调用前应完成：Schema 类型和必填项校验、格式和范围校验、业务前置条件校验、身份与资源权限校验、风险等级判断、幂等键生成、敏感操作审批、超时和重试策略配置。金额、地址、订单号等关键参数最好来自可信业务查询结果或人工确认，不应仅相信模型生成值。

调用后应区分：传输成功、接口业务成功和最终业务状态成功。需要校验 HTTP/协议状态、业务错误码、返回 Schema、关键字段、数据新鲜度，并通过查询接口确认最终状态。返回结果应标准化为 `status`、`data`、`error_code`、`retryable`、`trace_id`，再交给 Agent。

日志要脱敏，并记录工具名、参数摘要、耗时、重试、调用方、审批人、幂等键和结果状态，形成可审计链路。

#### 9. 如何设计 Agent 的重试、降级和兜底策略？

**参考答案：**

先进行错误分类：

- 网络超时、限流、临时 5xx 可有限重试，使用指数退避加随机抖动。
- 参数校验失败通常不应原样重试，而应修正参数、重新规划或询问用户。
- 鉴权失败、余额不足、业务规则禁止等确定性错误应立即终止或转人工。
- 非幂等写操作只有具备幂等键或可确认前次结果时才能重试。

降级可包括备用模型、减少检索规模、跳过非关键步骤、返回缓存结果、只读模式或人工工单。需要熔断器防止持续调用故障依赖，并用并发隔离避免一个工具拖垮全服务。兜底回复必须说明已完成和未完成的部分、失败原因、用户下一步以及追踪编号。

#### 10. Human-in-the-Loop 适合在哪些场景介入？如何防止重复执行已完成的操作？

**参考答案：**

适合人工介入的场景包括资金与订单变更、权限变更、法律或合规风险、模型置信度低、信息冲突、不可逆操作和超过阈值的异常处理。人工节点应展示操作对象、关键参数、依据、风险和即将发生的副作用，并允许批准、拒绝或修改。

防重复执行依赖：稳定的任务 ID 和幂等键、业务数据库唯一约束、状态机前置条件、执行记录表和操作后的状态核验。审批结果也应包含审批版本，防止用户修改参数后沿用旧批准。由于中断节点恢复时可能重跑中断前代码，副作用应放到审批后的独立节点，或确保前置代码完全幂等。

### 2. RAG 与智能检索

#### 11. 一个完整的 RAG 链路包含哪些环节？每个环节可能产生什么问题？

**参考答案：**

完整链路通常包括：数据接入、解析/OCR、清洗、结构识别、切分、元数据与权限标注、Embedding 与索引、Query 理解/改写、过滤、召回、融合、重排、上下文构建、答案生成、引用、评测与监控。

常见问题依次为：解析丢表格或标题；清洗误删关键信息；Chunk 太小造成语义断裂、太大造成噪声；元数据和权限缺失；Embedding 模型与语料不匹配；改写改变原意；过滤过严导致零召回；召回 Top-K 不足；不同检索分数直接相加失真；Reranker 截断长文本；上下文重复或冲突；模型未严格依据证据；引用无法对应原文；评测集覆盖不足。

排错要逐层进行：先判断答案依据是否存在于语料，再看是否被解析与切分、是否召回、是否排入最终上下文，最后看生成是否忠实。不能看到最终答案错就直接改 Prompt。

#### 12. 为什么要使用 BM25 与向量检索的混合召回？

**参考答案：**

BM25 擅长词面精确匹配，特别适合产品型号、错误码、专有名词、数字和缩写；向量检索擅长同义表达和语义相关，例如“货一直没到”可以匹配“物流延迟”。单独使用任何一路都会有盲区，因此并行召回后融合通常能提高稳健性。

两路分数一般不在同一尺度上，不宜直接相加。可使用 RRF 按排名融合，公式可写为：

`RRF(d) = Σ 1 / (k + rank_i(d))`

也可对分数归一化后加权，但权重必须在固定验证集上调优。融合后再对有限候选使用 Cross-Encoder Reranker 精排，形成“高召回、低成本粗排、较高成本精排”的两阶段结构。

#### 13. BM25 的核心思想是什么？它对专业术语检索有什么优势？

**参考答案：**

BM25 基于词频、逆文档频率和文档长度归一化计算相关性。简化公式为：

`score(D,Q) = Σ IDF(q) × [f(q,D)(k1+1)] / [f(q,D)+k1(1-b+b|D|/avgdl)]`

其中 `f(q,D)` 是词在文档中的频次，`IDF` 提高稀有词权重，`k1` 控制词频饱和，`b` 控制长度归一化。词出现十次不会简单获得十倍分数，长文档也不会因词多天然占优。

专业术语、SKU、版本号和错误码往往是低频且区分度高的 Token，BM25 能直接利用精确匹配；向量模型可能将相近型号映射得过近。中文场景效果还依赖分词器、同义词、大小写和字符规范化。

#### 14. BGE-M3 与 BGE-Reranker 分别承担什么职责？

**参考答案：**

BGE-M3 是检索表示模型。论文中的 M3 指多语言、多功能和多粒度，支持 Dense、Sparse 和 Multi-vector 等检索形式，并可处理较长输入。实践中常用它生成查询与文档向量，完成大规模候选召回。

BGE-Reranker 通常是 Cross-Encoder：把 Query 与候选文档成对输入模型，直接输出相关性分数。它能进行更细的词间交互，排序质量通常高于仅比较独立向量，但计算成本随候选数增长，因此适合对召回后的几十或几百个候选精排，不适合扫描全库。

#### 15. 为什么不能直接使用 Reranker 对整个知识库排序？

**参考答案：**

Cross-Encoder 需要对每个 Query-Document 对进行一次较重的模型推理。若有百万 Chunk，一次查询就需要百万次配对推理，延迟和成本不可接受，也难以利用向量索引的近似最近邻能力。因此先用 BM25/ANN 将候选缩小到几十或几百，再 Rerank。

需要权衡候选数：太少会发生“正确文档没进入精排”的召回上限问题，太多则提高延迟。应通过 Recall@candidate_k、精排后的 NDCG/MRR、P95 延迟共同选择候选规模。

#### 16. 父子块切分如何设计？父块和子块分别用于什么场景？

**参考答案：**

先按章节或语义边界构造父块，再将父块切成更小的子块。子块用于 Embedding 和召回，因为内容聚焦、匹配精确；命中子块后根据 `parent_id` 回取父块或命中点附近窗口，供 LLM 获取完整上下文。

父块不应无限大，可包含章节标题、前置定义和若干相邻段落。一个父块被多个子块命中时应去重，并控制父块总 Token。表格、代码和步骤列表要按结构整体保存，避免机械切断。评测需要比较固定长度切分、语义切分和父子块方案在召回、上下文精度、答案正确率与成本上的差异。

#### 17. 文档切分长度、重叠长度应该如何确定？

**参考答案：**

不存在通用最佳值。应根据文档结构、平均答案跨度、Embedding 模型输入限制、生成上下文预算和评测结果确定。操作手册适合按章节和步骤切，FAQ 可一问一答一个块，合同或制度应保留条款层级，代码需要函数或类级边界。

重叠用于缓解边界信息丢失，但过大将产生重复召回、索引膨胀和上下文浪费。可从小范围候选参数开始做消融实验，至少观察 Recall@K、Context Precision、答案正确率、索引规模和 P95。比固定字符数更稳妥的方式是“结构边界优先，Token 上限兜底”。

#### 18. Metadata Filter、Query Rewrite 和 Hybrid Retrieval 的执行顺序如何设计？

**参考答案：**

先解析原始 Query，抽取产品、版本、时间、部门和权限等结构化条件；再在不改变原意的前提下生成检索 Query；将可信过滤条件用于 BM25 和向量检索；两路并行召回后进行融合和 Rerank。

关键是区分硬过滤和软条件。租户、权限、明确版本应硬过滤；模型推断出的模糊产品名可作为软加权或扩大召回，避免错误 Rewrite 加错误 Filter 导致零召回。应保留原始 Query 与改写 Query，必要时并行检索两者。零结果时可逐步放宽非安全过滤条件，但绝不能放宽 ACL。

#### 19. 如果 Recall@K 很高，但最终问答效果不好，可能是什么原因？

**参考答案：**

Recall@K 只说明相关文档是否进入前 K，不表示排位足够靠前、上下文没有噪声或模型正确使用证据。可能原因包括：相关文档排在上下文末尾；Chunk 不完整；候选大量重复；存在版本冲突；Context Precision 低；上下文超过模型有效注意范围；Prompt 未要求基于证据；问题需要多跳推理；引用映射错误；生成模型能力不足。

应依次检查排序指标、最终进入 Prompt 的实际上下文、Context Precision/Recall、Faithfulness 和答案正确率。还要做 Oracle 实验：直接给模型标准证据，若仍答错则问题在生成；若答对则继续排查检索与上下文构建。

#### 20. 如何分析漏召回、排序错误、上下文冗余和答案幻觉？

**参考答案：**

建立失败样本标签体系和可重放链路：保存原 Query、改写结果、过滤条件、两路候选、融合分数、Rerank 分数、最终上下文、答案和引用。

- 漏召回：检查语料是否存在、解析是否完整、Chunk 是否可检索、实体是否规范化、过滤是否误杀、候选 K 是否过小。
- 排序错误：正确文档已召回但名次低，分析融合、Reranker、负样本和版本权重。
- 上下文冗余：按文档/父块去重，使用 MMR 或相邻块合并，并设置每来源配额。
- 幻觉：判断陈述是否被上下文支持；加强引用约束、证据不足时拒答、对关键事实做后验校验。

每次优化只改变一个主要变量，并在冻结测试集上做回归，避免凭个别案例调参。

#### 21. Milvus 和 Elasticsearch 在检索能力上有什么区别？

**参考答案：**

Milvus 以大规模向量存储和 ANN 检索为核心，支持多向量字段、标量过滤、稠密/稀疏向量和混合搜索，适合向量规模大、检索吞吐要求高的场景。Elasticsearch 以倒排索引和全文检索生态见长，BM25、分析器、复杂过滤、聚合、高亮和运维工具成熟，同时也支持 `dense_vector` 与 kNN、RRF 等混合检索。

选择取决于需求，而不是简单说谁更快：关键词与复杂结构化查询占主导时 Elasticsearch 更自然；向量规模和多向量检索占主导时 Milvus 更专注；也可两套系统并行，但要承担数据一致性和融合复杂度。新版本能力变化较快，应以实际版本压测为准。

#### 22. 如何处理 PDF、表格、图片、标题层级和跨页内容？

**参考答案：**

PDF 要先判断文本型还是扫描型；扫描页使用 OCR，并保存页码、坐标和 OCR 置信度。解析时去除重复页眉页脚、修复断行，同时保留段落和列表结构。标题层级要形成章节路径，如“产品 A > v3.2 > 安装 > 网络配置”。

表格应保存标题、表头和行列关系，可同时生成结构化 JSON/Markdown 与面向检索的自然语言描述；合并单元格需要展开语义。图片需要 OCR 或视觉模型生成描述，并与图题和所在章节关联。跨页段落不能按页机械切断，可根据句尾、排版框和标题判断是否合并。所有 Chunk 都要保留 `doc_id/page/bbox/section/version`，支持引用回显和问题追溯。

#### 23. 知识库文档更新后，如何实现增量入库和旧版本清理？

**参考答案：**

使用稳定 `doc_id` 加内容哈希识别新增、修改和未变化文档。解析后为每个 Chunk 生成稳定标识或哈希，仅重新向量化变化部分。新版本先写入临时版本并完成索引与抽样验证，再原子切换 `active_version`，避免用户看到半更新状态。

旧版本先软删除或标记失效，保留短期回滚窗口，再异步清理向量、倒排索引、对象存储和缓存。删除必须覆盖所有派生数据。缓存键应包含知识库版本，版本切换即可自然失效。还应保存文档血缘、处理器版本、Embedding 模型版本与失败重试记录。

#### 24. 如何防止 RAG 返回过期、权限不匹配或版本错误的文档？

**参考答案：**

入库时写入租户、ACL、有效期、文档状态、业务版本和生效时间；查询时将用户身份转换为服务端可信过滤条件，在召回阶段完成权限过滤。不能只在生成后过滤，也不能让模型决定 ACL。

版本冲突要有明确策略，例如优先当前生效版本，并在必要时提示历史版本。检索结果进入 Prompt 前再做一次防御性权限和有效期校验。缓存键包含租户、权限摘要和索引版本，权限变更时主动失效。引用返回 `doc_id/version/page`，便于审计。

### 3. 模型调用与评测

#### 25. 如何使用 Pydantic 或 JSON Schema 约束模型输出？

**参考答案：**

先定义业务对象而不是泛化字典，例如 `RouteResult(intent: Literal[...], confidence: float, entities: ..., need_clarification: bool)`，为字段设置枚举、范围、长度和必填约束。由 Pydantic 的 `model_json_schema()` 生成 JSON Schema，并在支持原生 Structured Output/Tool Calling 的模型接口中传入 Schema。

模型返回后仍必须用 `model_validate_json()` 或等价方法验证。Schema 约束只能保证形状和部分值域，不能保证事实正确，例如合法格式的订单号仍可能不存在，因此还需业务校验、数据库校验和权限检查。Schema 应有版本号并保持兼容，错误信息可以作为一次修复提示，但重试次数必须受控。

#### 26. 模型输出 JSON 格式错误时，你会如何处理？

**参考答案：**

优先使用模型原生结构化输出或工具调用，减少从自由文本中截取 JSON。若仍失败：先记录原始输出和验证错误；将精简后的错误、Schema 和原输出交给模型做一次或有限次数修复；仍失败则切换备用模型、使用确定性默认值或进入人工/兜底流程。

不要使用脆弱正则盲目修复，也不能为了通过校验而丢掉关键字段。应区分语法错误、类型错误、枚举越界和业务语义错误，并统计各类失败率。任何涉及资金或写操作的参数，校验失败时必须禁止执行。

#### 27. 如何设计模型调用的超时、重试、熔断和降级？

**参考答案：**

为连接、首 Token 和总响应分别设置超时；流式请求还要处理客户端取消。只对限流、暂时性网络错误和部分服务端错误重试，使用指数退避与抖动，并遵守服务端 `Retry-After`。每次调用使用请求 ID，避免上游重复记账或重复执行。

熔断器在连续失败或滑动窗口错误率超过阈值时停止请求，半开状态用少量流量探测恢复。降级顺序可为同能力备用区域、备用模型、降低上下文/关闭非核心步骤、缓存或规则答案、人工处理。监控应按模型、版本、场景统计成功率、TTFT、P95、Token 和成本。

#### 28. RAGAS 中 Faithfulness、Context Precision、Context Recall 分别衡量什么？

**参考答案：**

- `Faithfulness` 衡量回答中的事实性陈述是否能从给定上下文推出，关注“有没有脱离证据编造”。
- `Context Precision` 衡量检索上下文中真正相关内容的比例和排序质量，低值通常表示噪声多或相关文档排位不佳。
- `Context Recall` 衡量回答问题所需的参考事实有多少被检索上下文覆盖，低值通常表示漏召回。

这些指标不是绝对真值。LLM 型指标受评审模型、Prompt、语言和随机性影响，必须固定版本和参数，抽样人工复核，并同时保留可解释的传统检索指标和业务成功率。

#### 29. Recall@5 从 78% 提升到 91%，如何证明提升来自检索策略而不是测试集变化？

**参考答案：**

冻结同一份人工标注 Query 集、语料快照、相关性标签和评测脚本，只替换检索方案。至少比较纯向量、向量+BM25、向量+BM25+Reranker 三组消融实验；统一 Top-K、过滤条件和去重规则。报告样本数、各场景分层结果和置信区间，而不只报总体比例。

对同一 Query 的成败是配对数据，可用 bootstrap 置信区间或 McNemar 检验判断差异是否稳定。还要排查数据泄漏、重复 Query、标注质量和参数是否在测试集过拟合。最终同时报告 Recall@5、MRR/NDCG、P95 和成本，因为召回提升可能以延迟大幅上升为代价。

#### 30. LLM-as-Judge 有哪些偏差？如何提高评测可信度？

**参考答案：**

常见偏差包括位置偏差、偏爱更长或更流畅答案、自我偏好、对措辞敏感、领域知识不足、不同运行不稳定，以及被待评内容中的指令影响。若 Judge 看到不该看到的参考信息，还可能产生信息泄漏。

改进方法包括：使用明确 Rubric 和分项评分；随机交换 A/B 位置；必要时多 Judge 或多次投票；固定模型版本、温度和 Prompt；对边界样本人工复核；计算 Judge 与人工的一致性；保留理由但不要把理由当真值；把安全、格式、工具执行等可程序判断项交给确定性评测。评测数据本身也要防 Prompt Injection。

#### 31. TTFT 和端到端响应时间有什么区别？如何优化 TTFT？

**参考答案：**

TTFT 是从请求到达至客户端收到第一个 Token 的时间；端到端延迟是到完整响应或任务完成的时间。流式生成可明显改善 TTFT，但不一定减少总耗时。

TTFT 可分解为排队、鉴权、路由、检索、Prompt 构建、模型排队和 Prefill。优化包括连接复用、异步并行独立 I/O、缓存路由或检索结果、减少不必要的串行模型调用、控制 Prompt 长度、预热模型、合理批处理和就近部署。必须按 P50/P95/P99 观察，并保证优化前后模型、请求集、并发和缓存状态一致。

#### 32. 如何设计一套 Agent 路由准确率评测集？

**参考答案：**

先定义标签体系和标注指南，包括单意图、多意图、超范围、闲聊、信息不足和对抗输入。样本应来自脱敏真实流量，并补充边界对、同义表达、错别字、短 Query、长上下文和类别不平衡场景。至少双人标注，对分歧仲裁并记录一致率。

训练、验证、测试按用户或时间分割，避免近重复泄漏。指标包括总体 Accuracy、每类 Precision/Recall/F1、混淆矩阵、拒识能力、多意图拆分准确率、置信度校准和最终任务成功率。路由正确但下游失败与路由错误要分开归因。

#### 33. 多模型接入时，如何根据任务类型选择不同模型？

**参考答案：**

建立模型能力注册表，记录上下文长度、结构化输出、工具调用、语言、延迟、成本、可用性和安全等级。路由策略可将简单分类/改写交给小模型，把复杂规划、长上下文或高难度推理交给强模型；高风险操作即使模型强，也必须配合规则和审批。

先由规则和轻量分类判断任务，低置信度再升级模型。降级时要保证 Schema 兼容。选择依据来自固定评测集和线上 A/B，而不是主观印象，并同时优化质量、P95、成本与失败率。

#### 34. 如何处理模型幻觉、敏感内容和越权操作？

**参考答案：**

幻觉治理包括提供可追溯证据、证据不足拒答、引用校验、结构化输出、对关键事实二次验证和持续失败样本评测。敏感内容治理包括输入输出分类、个人信息脱敏、日志最小化、保留期限、模型供应商数据策略和合规审计。

越权治理必须由确定性系统实现：服务端身份认证、RBAC/ABAC、工具白名单、最小权限凭证、租户隔离、资源级鉴权、参数限制和高风险审批。模型只能“建议调用”，不能成为授权主体。工具返回的文本与检索文档都应视为不可信输入，防止间接 Prompt Injection。

### 4. Python、后端与数据库

#### 35. `asyncio` 的事件循环、协程和异步任务分别是什么？

**参考答案：**

协程是由 `async def` 定义的可暂停计算；调用它得到 coroutine object，并不会自动执行。事件循环负责调度就绪任务、监听 I/O 和计时器。`Task` 是把协程安排到事件循环执行的对象，可通过 `create_task` 创建，并可等待、取消和获取异常。

当协程执行到 `await` 且等待的是非阻塞 I/O 时，它让出控制权，事件循环运行其他任务。`asyncio` 主要提供并发，不自动提供 CPU 并行；CPU 密集工作会阻塞事件循环，应交给进程池、专用推理服务或其他执行器。生产代码还要处理超时、取消传播、Task 异常和资源关闭。

#### 36. 哪些操作适合异步并发？哪些操作不能简单改成异步？

**参考答案：**

适合异步的是等待时间占主导的 I/O：HTTP 模型调用、数据库异步驱动、Redis、向量库和文件网络读写。互不依赖的客户、订单、物流查询可用 TaskGroup/`gather` 并发，并用 Semaphore 控制并发。

CPU 密集的 PDF 解析、Embedding、本地模型推理、大型 Pandas 运算不能仅加 `async`；同步数据库/HTTP 客户端放在异步函数里仍会阻塞。并发也不适合有严格先后依赖或共享事务的步骤。应确保所用驱动真正异步，并设置超时、连接池、背压和取消处理。

#### 37. FastAPI 中如何实现请求参数校验、统一异常处理和接口鉴权？

**参考答案：**

使用 Pydantic 模型定义 Body、Query 和响应 Schema，设置字段类型、枚举、范围和自定义 Validator；FastAPI 会生成 JSON Schema/OpenAPI，并在输入不合法时返回验证错误。通过 `exception_handler` 将领域异常映射为稳定错误码，响应包含 `code/message/trace_id`，内部堆栈只进日志。

鉴权可用依赖注入解析 JWT/OAuth2 或内部服务凭证，再执行租户和资源级授权。认证只回答“你是谁”，授权回答“能否操作该资源”。还应加入限流、请求大小限制、CORS 策略、审计日志和敏感字段脱敏。同步阻塞操作不能直接放在异步路由里。

#### 38. Redis 在这些项目中分别承担了哪些职责？

**参考答案：**

可用于短期会话和任务中间状态、热点查询缓存、分布式限流、短期幂等记录、消息流或锁等。电商 Agent 可缓存用户/商品只读数据与路由结果；订单 Agent 可存会话上下文和短生命周期进度；知识平台可缓存规范化 Query 对应的检索结果。

但 Redis 不应作为唯一业务真相源。订单、审批和审计记录应进入 PostgreSQL 等持久数据库；Agent Checkpoint 若要求重启后恢复，也应使用持久实现。每类 Key 要定义命名、TTL、容量、失效策略和敏感数据规则。

#### 39. Redis 缓存如何设置过期时间？如何处理缓存穿透、击穿和雪崩？

**参考答案：**

TTL 根据数据可接受陈旧度与更新频率设置，并加入随机抖动避免集中失效。强一致数据可采用写数据库后删除缓存、版本化 Key 或事件驱动失效；不能只依赖长 TTL。

- 穿透：查询不存在数据反复打到数据库，可做输入校验、短 TTL 空值缓存、布隆过滤器和限流。
- 击穿：单个热点 Key 失效导致大量回源，可用互斥重建、singleflight、逻辑过期或提前刷新。
- 雪崩：大量 Key 同时失效或 Redis 故障，可随机 TTL、多级缓存、限流、熔断和容量冗余。

缓存回答还要把租户、权限与知识版本纳入 Key，避免数据泄漏。

#### 40. PostgreSQL 与 Redis 的数据边界如何划分？

**参考答案：**

PostgreSQL 保存需要事务、约束、关联查询、长期持久化和审计的数据，例如订单、客户、处理记录、审批记录和文档元数据。Redis 保存可丢失或可重建的短期、高频数据，例如缓存、会话摘要、限流计数和短期状态。

采用 cache-aside 时，数据库是真相源。写入流程要明确并发与失效策略；不能对 PostgreSQL 和 Redis 假设天然原子事务。必要时使用 Outbox/CDC 驱动缓存更新，并允许缓存短期不一致但不能影响资金类业务正确性。

#### 41. 如何保证 Agent 工具执行的幂等性？

**参考答案：**

为每个业务动作生成稳定幂等键，例如 `task_id + action_type + resource_id + normalized_params_hash`，由服务端持久记录；数据库为幂等键建立唯一约束。重复请求若前次成功则返回同一结果，处理中则返回处理中，失败是否可重试取决于错误类型。

同时使用业务状态机前置条件，例如只有 `PAID` 才能退款；写操作采用事务和乐观锁。调用超时后先查询业务状态，不能盲目再次提交。分布式锁只能减少并发，不替代数据库唯一约束和幂等记录。

#### 42. 多个工具同时更新订单时，如何保证数据一致性？

**参考答案：**

单库内使用事务、行锁或版本号乐观锁，并通过订单状态机限制合法迁移。跨服务场景使用 Saga/补偿事务、Outbox 和幂等消费者，接受最终一致性但明确每一步状态。若两个 Agent 操作同一订单，应按订单维度串行化关键命令或做冲突检测。

外部支付成功而本地记录失败时，不能简单回滚外部世界，需要对账和补偿任务。任何写操作都记录 command ID、旧状态、新状态、操作者和 trace ID，便于恢复与审计。

#### 43. Docker 部署 Agent 服务时，需要关注哪些问题？

**参考答案：**

使用精简固定版本基础镜像、多阶段构建、非 root 用户、只读文件系统和依赖锁定；密钥通过 Secret 注入，不写入镜像。服务应无状态化，把会话与 Checkpoint 放在外部存储。配置健康检查、优雅停机、资源限制、日志到标准输出和时区编码。

大模型/Reranker 本地部署还要考虑 GPU 驱动兼容、模型权重挂载、显存、批处理与启动预热。扩容时关注连接池总量、并发限制和下游配额，不能只增加容器而压垮数据库或模型服务。

#### 44. 如何监控 Agent 的调用链、Token 消耗、失败率和响应延迟？

**参考答案：**

为每个请求生成 trace ID，把 Orchestrator、每个节点、检索、模型和工具作为 Span，记录输入输出摘要而非未脱敏全文。指标包括请求量、成功率、路由混淆、工具错误码、循环次数、人工介入率、Token/成本、TTFT、总耗时及各阶段 P50/P95/P99。

日志、指标和 Trace 需要通过 `trace_id/task_id/thread_id` 关联。告警应基于 SLO 和错误预算，而不是单点平均值。还要建立质量监控：抽样评测 Faithfulness、任务成功率和安全违规，并监控模型/知识库版本变化后的回归。

### 5. NLP 与模型基础

#### 45. Transformer 的 Self-Attention 机制解决了什么问题？

**参考答案：**

Self-Attention 让序列中每个 Token 根据内容直接聚合其他 Token 信息。核心公式为：

`Attention(Q,K,V) = softmax(QK^T / √d_k)V`

缩放项防止维度大时点积过大导致 Softmax 饱和；Multi-Head Attention 在不同子空间学习不同关系。相较 RNN 的逐步递归，Transformer 训练时可并行处理序列，长距离依赖路径更短。代价是标准注意力的时间和显存复杂度随序列长度近似二次增长，并且模型需要位置编码表达顺序。

#### 46. BERT 和自回归大模型在训练目标和使用方式上有什么区别？

**参考答案：**

BERT 是双向 Encoder，经典预训练目标以 Masked Language Modeling 为主，Token 可以同时利用左右上下文，适合分类、NER、抽取和 Embedding 等理解任务。经典 GPT 类模型是使用因果掩码的 Decoder，通过预测下一个 Token 自回归生成，适合开放式生成和对话。

BERT 通常为下游任务加分类头并微调；生成模型通过 Prompt、指令微调和偏好对齐完成多任务。两者边界并非绝对，现代模型架构和训练目标有更多变体，但面试中应说清 Encoder 双向表示与 Decoder 因果生成的核心区别。

#### 47. LoRA 为什么能够降低微调成本？它修改了模型的哪些参数？

**参考答案：**

LoRA 冻结原始权重 `W`，不直接训练完整的 `ΔW`，而学习两个低秩矩阵，使 `ΔW = BA`，秩 `r` 远小于权重维度。前向时相当于 `Wx + scaling·BAx`。因此可训练参数、优化器状态和显存明显减少，基础模型还可共享多个任务 Adapter。

通常注入注意力投影矩阵，如 `q_proj`、`v_proj`，也可覆盖 `k/o` 或 MLP，具体位置、rank、alpha 和 dropout 要通过实验选择。QLoRA 进一步量化冻结的基础权重，但训练稳定性、目标模块和精度仍需评测。

#### 48. 量化、剪枝和知识蒸馏分别适用于什么场景？

**参考答案：**

量化降低权重/激活数值精度，如 FP16、INT8、INT4，以减少显存、存储和提高部分硬件吞吐；需关注异常值、校准和质量损失。剪枝移除不重要的权重、通道或结构，非结构化剪枝若硬件不支持稀疏加速，参数少不一定实际更快。知识蒸馏用教师模型的软输出或中间表示训练小模型，适合把大模型能力迁移到低延迟部署模型。

三者可组合，但必须在目标硬件上测真实吞吐、P95、内存和任务质量，不能只报模型文件大小。

#### 49. Accuracy、Precision、Recall 和 F1 如何选择？

**参考答案：**

`Precision = TP/(TP+FP)`，关心预测为正的样本有多少是真的；`Recall = TP/(TP+FN)`，关心真实正例被找回多少；`F1 = 2PR/(P+R)`，是 Precision 和 Recall 的调和平均；Accuracy 是全部预测正确比例。

选择依据是错误成本。违规商品审核若漏放代价高，优先 Recall；自动封禁若误伤代价高，优先 Precision；需要平衡时用 F1。类别极不平衡时 Accuracy 容易误导，应报告每类指标、Macro-F1、PR-AUC 和混淆矩阵，并根据业务成本选择阈值。

#### 50. 如果分类任务类别极不平衡，应该如何评估和优化？

**参考答案：**

评估时使用分层切分，报告每类 Precision/Recall、Macro-F1、PR-AUC、混淆矩阵和置信度校准，不只看 Accuracy 或 Micro-F1。测试集应保持真实分布，同时可建立边界挑战集。

优化手段包括收集困难少数类样本、类别权重、Focal Loss、合理过采样/欠采样、数据增强、Hard Negative Mining、阈值按业务成本调整，以及层级分类或拒识。过采样必须只在训练集进行，防止重复样本泄漏到验证集。

## 二、项目一：电商多智能体运营系统

> **面试使用提醒：**下面的回答是根据简历信息组织的“应答框架”，不是对候选人实际代码的证明。凡是涉及路由准确率、Recall@5、TTFT 和失败率的回答，都应继续追问数据集、基线、实验配置和线上统计口径。

### 项目架构与职责

#### 1. 请完整介绍该项目的系统架构和一次请求的执行流程。

**参考答案：**

系统可以分为接入层、Orchestrator、领域 Agent、知识检索层、业务工具层、状态持久化层和观测评测层。请求进入 FastAPI 后，先完成身份、租户和参数校验，再由 Orchestrator 做意图识别、实体抽取和任务拆分。根据路由结果进入商品审核 Agent、售后 Agent 或其他 Agent。

一次商品审核请求大致是：

1. 接收用户问题和商品信息，写入 `thread_id`、用户权限和原始输入。
2. 路由节点识别商品审核意图，抽取商品 ID、类目和审核条件。
3. 商品查询节点读取可信商品数据。
4. 检索节点执行 Query Rewrite、Metadata Filter、BM25/向量混合召回和 BGE-Reranker 精排。
5. 规则/审核节点根据商品事实和知识依据生成结构化审核意见。
6. 结果校验节点检查必填字段、证据引用和风险级别。
7. 对需要写入业务系统或高风险的操作进入人工确认，否则返回结论和引用。

售后请求类似，但会增加客户、订单、物流查询和工具执行。整个过程中由 State 传递任务状态，由 Checkpointer 保存断点，由 Redis 处理热点数据/短期状态，由 PostgreSQL 保存业务记录和审计记录。

#### 2. Orchestrator 如何识别用户意图并选择具体 Agent？

**参考答案：**

我会先设计意图标签和路由契约，例如 `product_audit`、`after_sales`、`order_query`、`marketing_guide`、`unsupported` 和 `multi_intent`。路由模型输入原始问题、有限的会话摘要和可用 Agent 描述，输出结构化的 `intent`、`confidence`、`entities`、`subtasks` 和 `clarification`。

路由前可使用规则提取强信号：退款、取消订单、订单号、商品审核词等；但规则只作为特征或高置信捷径，不能覆盖所有自然语言表达。置信度低、类别差距小或关键实体缺失时进入澄清，不直接调用业务工具。多意图请求先拆分子任务，再根据依赖图串行或并行执行。

评测要看总体准确率之外的每类召回、拒识、混淆矩阵、改派率和最终任务成功率。线上要记录“路由正确但 Agent 失败”和“路由本身错误”两类问题，否则无法知道该优化路由还是下游能力。

#### 3. 商品审核 Agent 和售后 Agent 的 State Schema 分别包含哪些字段？

**参考答案：**

两者共享基础字段，但领域字段应分开或通过版本化子结构管理。共享部分包括 `thread_id`、`user_id`、`tenant_id`、原始问题、会话摘要、意图、当前节点、任务状态、错误信息、重试次数、审批状态、trace ID 和最终响应。

商品审核部分可包括 `product_id`、商品事实、类目、审核规则类型、改写 Query、过滤条件、检索候选、证据引用、审核项结果、风险等级和审核结论。售后部分可包括 `customer_id`、`order_id`、订单状态、支付状态、物流状态、售后类型、工具调用记录、执行结果、幂等键、待审批动作和人工意见。

State 只保存恢复所需的结构化摘要和引用 ID，大型文档、图片、完整日志放在外部存储。字段需要明确 reducer；例如工具历史追加，当前节点覆盖，重试次数递增。Schema 变更时要做版本迁移，不能假设旧 checkpoint 一定符合新代码。

#### 4. 多个 Agent 之间如何共享用户信息、订单信息和工具调用结果？

**参考答案：**

短期任务内通过 Orchestrator 的共享 State 传递最小必要信息，例如用户 ID、订单 ID、已确认的业务事实和工具结果摘要。领域 Agent 输出必须经过 Schema 校验，不能把一段自然语言作为唯一契约。跨线程、跨任务或长期用户偏好放入 Store/数据库，而不是依赖某一次会话的消息历史。

敏感数据采用引用而不是原文，例如 State 只保存 `customer_id`，需要时由授权工具查询；不同 Agent 使用不同工具权限。工具结果要标注来源时间、错误码和可信状态，避免一个 Agent 把模型生成的猜测当成另一个 Agent 的事实。跨 Agent 写操作由统一命令服务执行，领域 Agent 不直接越权。

#### 5. 为什么采用 Multi-Agent，而不是一个统一的 Single-Agent？

**参考答案：**

选择 Multi-Agent 的合理依据是领域差异、工具权限差异、流程复杂度和团队维护边界。商品审核更偏知识检索和规则判断，售后更偏订单状态查询、外部工具和高风险执行，分开后 Prompt、工具集和测试集更聚焦，也更容易限制权限和定位错误。

但 Multi-Agent 不是天然更好，它会增加路由错误、状态同步、调用延迟、观测和调试成本。如果任务简单、领域高度重叠或调用量很低，Single-Agent 可能更合适。面试回答应说明选择依据和代价，并说明如何通过显式路由、共享 Schema、统一 Trace、最大步数和降级机制控制复杂度。

#### 6. Agent 路由准确率从 73% 提升到 90%+，具体做了哪些优化？

**参考答案：**

一个可信的回答应该按实验顺序说明，而不是只说“优化了 Prompt”。例如：先冻结 2,000 条标注样本，检查标签定义和类别分布；然后分析混淆矩阵，发现商品审核与售后、订单查询与物流查询等边界；接着补充边界样本和 Few-shot 示例，增加实体抽取和规则特征；使用结构化输出和置信度拒识；对多意图先拆分；最后通过阈值和澄清流程降低错误路由。

实验必须有版本化基线：同一模型、相同测试集、相同标签和推理参数，分阶段比较 Prompt、规则、分类模型或路由策略。应报告总体 Accuracy、各类 Precision/Recall/F1、拒识准确率和最终任务成功率。若只提供 90%+而无法说明样本如何标注、是否存在重复和是否在测试集调参，指标可信度不足。

#### 7. 路由错误主要集中在哪些意图？如何构造评测样本？

**参考答案：**

应从混淆矩阵和线上改派记录回答，而不是臆测。常见边界包括“商品规则咨询”和“商品审核执行”、“订单查询”和“售后处理”、“查询物流后要求退款”等复合请求。构造样本时要覆盖简短表达、同义词、口语、错别字、订单号/商品型号、历史上下文、多意图和超范围问题。

标注指南必须规定主意图、子任务、所需实体和是否允许直接执行。建议双人标注并仲裁，按用户或时间去重分割，防止同一模板泄漏到测试集。还要单独建立高风险集，例如“帮我直接退款”，观察系统是正确路由并触发审批，还是错误路由到普通查询。

#### 8. 当用户一个请求同时包含商品审核和售后问题时，系统如何处理？

**参考答案：**

先由路由节点识别多意图，并将请求拆成结构化子任务。若子任务独立，可并发查询；若存在依赖，例如“审核结果不通过就申请售后”，必须先完成商品审核，再根据结果决定售后分支。每个子任务要有自己的状态和结果，但共享同一个总任务 ID。

拆分时要保留原问题，防止改写丢失条件；合并时检查冲突、未完成项和证据来源。任一子任务涉及高风险写操作，都需要独立审批，不能因为另一个子任务已完成就自动执行。最终回复应分别说明两个子任务的状态，避免用一个模糊结论掩盖部分失败。

### 商品审核 Agent 与 RAG

#### 9. 商品审核流程具体包含哪些节点和条件分支？

**参考答案：**

可拆为输入校验、商品查询、审核类型识别、知识检索、规则匹配、风险判断、结果校验、人工审批和响应节点。输入缺少商品 ID 或关键字段时进入澄清；商品不存在或权限不足时终止；检索无证据时进入补充查询或人工；高风险结论或要修改商品状态时进入审批；普通只读审核可直接返回。

审核结果应是结构化的，例如每条规则包含 `rule_id`、结论、证据引用、命中事实、风险级别和建议动作。规则判断不能只依赖模型自由文本。流程还要设置最大检索/模型步数，工具异常进入有限重试或人工，而不是回到路由节点无限循环。

#### 10. 商品知识库中的文档如何解析、切分、入库和更新？

**参考答案：**

先按文档类型选择解析器，保留标题路径、版本、生效时间、类目、来源、页码和权限；清理页眉页脚、重复内容和编码问题，同时保留表格与规则条款结构。然后按章节和语义边界构造父块，再切分子块，给每个子块生成稳定 ID 和内容哈希。

Embedding 入 Milvus 或相关索引，关键词字段入 BM25 系统，元数据进入同一检索文档或 PostgreSQL。更新时按哈希做增量处理，先构建新版本索引，验证通过后切换生效版本，旧版本软删除并异步清理。每个审核结论必须能回到文档版本、章节和页码，防止引用过期规则。

#### 11. 商品审核为什么选择 BM25 + 向量检索 + Reranker？

**参考答案：**

审核问题通常同时包含自然语言描述和强精确字段，例如商品名称、规格、型号、法规条款号和错误码。BM25 适合精确词面，向量检索适合同义表达和语义召回，两者融合可覆盖更多表达；Reranker 再对有限候选做 Query-Document 交互排序，减少“召回到了但排位不对”。

不能把三者的分数直接随意相加。可先各取候选，使用 RRF 或经过验证的归一化加权融合，再用 BGE-Reranker 精排。最终要通过消融实验说明每一层贡献，并同时关注审核正确率、证据覆盖率、Recall@K 和延迟。

#### 12. 如果商品名称包含大量型号、编码和专业术语，如何保证召回效果？

**参考答案：**

对型号和编码做规范化处理，例如大小写、连字符、全半角、空格、中文数字和别名映射；保留原始值与规范值。检索 Query 中对实体单独抽取，并使用关键词字段精确匹配；向量召回用于补充描述语义。必要时按产品类目、版本和生效状态过滤。

召回后可对型号完全匹配、版本一致和规则条款号命中设置业务加权，但不能把模型相似度当作事实等价。测试集要专门包含近似型号、旧型号、错位数字和多个产品名，观察 Precision@K、Recall@K、版本错误率和人工复核率。

#### 13. Recall@5 从 78% 提升到 91%，具体实验对比如何设计？

**参考答案：**

先定义“相关”的标注标准：一个 Query 是否有一个或多个正确 Chunk，父子块命中如何计分，多个等价规则如何处理。冻结 2,000 条查询、知识库版本和标签，比较纯向量基线、向量+BM25、再加 Reranker 的三组或多组方案。

每组保持相同 Top-K 口径，并记录候选召回 K 与最终返回 K，不能把不同 K 的结果直接比较。按专业术语、自然语言、版本条件、长文档和多条件查询分层报告。最好给出逐样本配对提升、置信区间和失败案例。还要报告 Reranker 延迟、索引规模和上下文答案效果，避免只为 Recall 增大候选而牺牲生产体验。

#### 14. 审核结论如何引用知识依据？如何防止模型自行编造审核规则？

**参考答案：**

检索结果要携带 `doc_id`、标题、章节、版本、生效时间、页码/位置和片段内容。生成 Prompt 明确要求每个审核项绑定证据 ID，只能基于提供的证据和可信商品事实回答；证据不足时返回 `insufficient_evidence`，不得补写规则。

生成后进行引用完整性校验：引用 ID 必须存在，结论中的关键规则应能在证据中找到，版本必须是当前生效版本。高风险审核可由规则引擎或第二模型做一致性检查，最终结果保留原始证据和审计日志。禁止把知识库检索结果中的自然语言指令当成系统指令，防止 Prompt Injection。

### 售后 Agent 与业务工具

#### 15. 通过 MCP 封装了哪些售后工具？工具协议和参数如何定义？

**参考答案：**

根据简历，候选人应能说明客户查询、订单查询、物流查询、售后规则检索、退款申请、取消订单、地址修改和人工工单等工具。MCP 工具至少包含唯一名称、描述、JSON Schema 输入参数，可选输出 Schema、错误结果和能力声明。工具调用以 JSON-RPC 的 `tools/list` 发现工具，以 `tools/call` 执行。

工具 Schema 要写清字段类型、必填项、枚举、单位、金额精度和示例，输出应区分结构化数据、业务错误和协议错误。MCP 负责标准化连接，不替代业务鉴权、幂等、审批和权限控制。工具描述和返回文本都应视为不可信内容，服务端仍需做最终校验。

#### 16. 退款、取消订单等高风险操作如何实现人工确认？

**参考答案：**

Agent 先完成只读查询和方案生成，展示订单、金额、收货人脱敏信息、目标动作、适用规则、风险和预计副作用。系统在真正执行写操作前调用 `interrupt()` 保存状态，向审批系统返回审批单。人工可以批准、拒绝或修改允许修改的字段；修改后必须重新校验规则和权限。

恢复时使用原 `thread_id` 和审批结果，审批后的执行节点重新读取当前业务状态，检查订单仍满足前置条件，再以幂等键调用退款/取消工具。执行后查询最终状态并记录审批人、时间、参数版本、工具结果和 trace ID。超时未审批应过期，不能默认批准。

#### 17. 工具调用失败、超时、参数错误时，分别如何处理？

**参考答案：**

参数错误说明调用前或上游生成有问题，应返回字段级错误并尝试修正或请求用户补充，不应对同一错误机械重试。网络超时要先查询幂等键对应的执行状态，再决定是否重试；临时 5xx/限流可指数退避有限重试。业务拒绝、权限不足、订单状态不允许等确定性错误应直接反馈或转人工。

每次结果标准化为 `success/error_code/retryable/data/trace_id`，Agent 根据状态机选择下一步。对外回复不能只说“工具调用失败”，要说明已完成的查询、未完成的动作、原因和下一步。

#### 18. 如何防止 Agent 重复提交退款或重复修改订单？

**参考答案：**

业务服务生成稳定幂等键，并在数据库建立唯一约束；相同幂等键重复请求返回第一次结果。退款执行前检查订单状态、可退款金额和已有退款记录，执行后通过查询接口确认最终状态。订单修改采用版本号或条件更新，版本变化时返回冲突而不是覆盖。

Redis 锁可以减少短时间并发，但不能单独保证资金安全；真正的保证来自业务服务、数据库和支付系统的幂等协议。模型重试、网络超时、进程重启和人工重复点击都必须纳入测试。

#### 19. 工具返回结果不完整时，Agent 如何判断是否继续执行？

**参考答案：**

工具应定义输出 Schema 和完成判定字段，例如 `status`、`data_complete`、`next_action`、`error_code`。返回 HTTP 200 不代表业务成功，必须检查关键字段和业务状态。若只缺少展示性字段可继续；若缺少订单状态、金额、支付状态等决策字段，应重新查询或人工介入，不能猜测。

对存在最终一致性的系统，工具可返回 `pending`，Agent 进入轮询/异步回调状态，而不是立即重复提交。状态机要区分“未执行”“执行中”“成功”“失败”“未知”，未知状态优先查询和对账。

#### 20. Checkpointer 如何保存人工介入前后的任务状态？

**参考答案：**

中断前保存已确认的订单事实、待执行动作、标准化参数、幂等键、风险等级、审批单 ID、当前节点和前置查询结果。人工审批结果作为恢复输入，并记录审批人、时间、批准/拒绝、修改字段和审批版本。恢复后重新读取最新订单状态和权限，再执行写操作。

不能只保存“用户说同意了”这段文本。Checkpointer 保存的是图执行状态；PostgreSQL 审批表和业务操作表保存审计与事实；两者通过 `thread_id/task_id/approval_id` 关联。恢复操作还要处理重复恢复请求和审批过期。

### 稳定性与性能

#### 21. TTFT 降低约 30%的具体优化点是什么？

**参考答案：**

先把 TTFT 拆成 API 排队、路由、检索、工具查询、Prompt 组装、模型排队和首 Token 生成，使用 Trace 找最大项。可能的优化包括：连接池与 HTTP Keep-Alive、独立只读查询异步并发、缓存稳定路由/检索结果、减少串行 LLM 调用、缩短历史上下文、提前进行 Query 规范化、模型预热和流式返回。

指标必须在相同模型、并发、请求集、服务资源、缓存预热状态和统计窗口下对比，报告 P50/P95 而不只是平均值。若缓存命中率变化很大，应同时报告命中/未命中分组，否则 30%可能只是测试条件变化造成的。

#### 22. 请求失败率降低约 25%的统计口径是什么？

**参考答案：**

先定义分母：是全部 HTTP 请求、有效业务任务，还是模型调用；再定义失败：超时、5xx、Schema 失败、工具失败、任务未完成和人工转接是否计入。建议分别报告接口成功率、模型调用成功率、工具成功率和端到端任务成功率。

“相对降低 25%”与“降低 25 个百分点”不同。例如基线失败率 8%，相对降低 25%是 6%，不是 5%。应给出前后时间窗口、样本量、流量分布和置信区间，并排除流量结构或重试口径变化。理想情况下还按错误类型说明重试/降级分别减少了哪些失败。

#### 23. 缓存了哪些数据？缓存命中后如何保证数据不过期？

**参考答案：**

适合缓存的是短期、读多写少且可重建的数据，如商品基础信息、知识检索结果、路由结果和不敏感的物流查询。订单余额、可退款金额、支付状态和权限不应直接依赖长 TTL 缓存做最终决策。

缓存键包含租户、用户权限摘要、规范化 Query、过滤条件、索引/业务版本和模型版本；知识文档更新时按版本切换或主动删除；订单写操作后失效相关缓存。对关键写操作在执行前回源确认，防止缓存过期导致错误动作。缓存日志要统计命中率、陈旧命中和回源错误。

#### 24. 多 Agent 并发调用工具时，如何控制资源和请求数量？

**参考答案：**

使用全局和按工具的并发信号量、连接池上限、超时、速率限制和预算；根据依赖图只并发独立只读操作，对同一订单的写操作串行化。为每个任务设置最大工具调用数、Token 和总时限，并在 State 中记录当前并发/已调用工具。

高峰期采用队列、背压和优先级，避免无限创建 Task。外部 API 返回限流时遵守 Retry-After，不能让所有 Agent 同时重试。需要区分租户配额，避免一个大客户耗尽整个系统资源。

#### 25. 如果模型服务不可用，系统如何降级？

**参考答案：**

首先判断任务是否必须依赖生成：确定性订单查询、物流状态和已知规则可由规则/模板直接返回；高风险写操作在模型不可用时应暂停或转人工，不能为了可用性绕过审批。对于分类和改写可切备用模型或规则，RAG 可返回检索结果和人工入口，但不能冒充完整结论。

系统要使用熔断、备用模型、请求超时和任务状态持久化，避免服务恢复前堆积重试。对用户清楚说明当前已完成、未完成和追踪编号。恢复后可由人工或队列继续，但必须重新校验数据新鲜度和幂等状态。

#### 26. 项目上线后如何监控路由错误、检索失败和工具失败？

**参考答案：**

路由监控包括各类分布、置信度、拒识率、人工改派率、混淆样本和下游成功率；检索监控包括零召回率、Recall@K 离线趋势、过滤命中率、Reranker 分数、引用覆盖率、知识库版本和 P95；工具监控包括调用量、错误码、超时、重试、幂等冲突、业务成功率和人工接管率。

每条链路通过 `trace_id/task_id` 关联，保留脱敏输入、版本和结果摘要。定期抽样做 LLM-as-Judge 与人工复核，并针对模型、Prompt、Embedding、索引和工具版本做回归。告警不要只看平均值，应按租户、场景和高风险动作设置 SLO。

## 三、项目二：企业智能订单处理 Agent

### Agent 流程

#### 1. 请介绍订单处理 Agent 的完整节点流程。

**参考答案：**

可按“理解需求 → 补充信息 → 查询业务事实 → 检索政策 → 生成方案 → 风险判断 → 人工确认 → 工具执行 → 结果校验 → 回复/追踪”编排。开始时先识别订单号、客户、动作和目标；信息不足进入澄清，不直接调用写工具。

查询节点分别获取订单、支付、库存和物流的可信状态；知识节点检索售后政策和历史解决方案；决策节点输出结构化方案和证据；对退款、取消、地址变更暂停审批；执行节点带幂等键写入业务；校验节点再查询最终状态并记录处理轨迹。

每个节点都有明确成功、重试、澄清、人工和终止分支，不能只靠一条 Agent 链让模型自行决定流程。

#### 2. 需求理解、信息查询、知识检索和方案决策之间如何传递状态？

**参考答案：**

需求理解输出标准化任务对象：动作、订单号、客户 ID、约束、风险等级和缺失字段。信息查询节点将可信业务事实写入 State，并标记来源时间与查询状态。知识检索使用任务对象和业务事实生成 Query，返回政策片段、版本和引用。

方案决策只读取结构化任务、可信业务事实和检索证据，输出动作、参数、依据、前置条件和是否需要审批。这样可以避免决策节点重新从长对话猜订单状态。大型结果只保存引用和摘要，完整内容由数据库或工具按需获取。

#### 3. Agent 如何判断当前任务是否已经完成？

**参考答案：**

为每类任务定义完成条件。例如订单查询要求订单号已确认、状态字段齐全、回答已返回；退款要求审批通过、工具返回业务成功、退款记录存在且最终状态查询一致；地址修改要求新地址通过校验、执行成功并查询到新地址。

完成判断应由结构化校验器或状态机执行，不能只看模型说“完成”。如果工具返回 `accepted/pending`，任务状态应是执行中而不是成功；如果结果不确定，应进入查询、对账或人工。完成条件还要支持部分完成和失败原因。

#### 4. 哪些情况会触发重新规划、工具重试或人工接管？

**参考答案：**

参数缺失、订单匹配错误、业务状态与预期不符、检索到新规则、工具返回可恢复错误时重新规划；网络超时、临时 5xx 和限流且操作可确认幂等时有限重试；资金、取消、地址等高风险动作、权限冲突、连续失败、数据冲突和未知最终状态时人工接管。

决策依据应是错误分类和状态机，不是模型自由发挥。每次重规划记录原因、旧计划和新计划，设置最大次数。人工接管页面应提供足够上下文和操作依据，恢复后重新校验而不是盲目从原节点继续。

#### 5. 为什么订单处理适合使用 LangGraph 的显式流程编排？

**参考答案：**

订单流程有清晰节点、分支和副作用边界，且需要暂停审批、失败重试、断点恢复和审计。LangGraph 用 State 表示任务，用条件边表示订单状态分支，用 Checkpointer 保存线程状态，用 Interrupt 实现人工节点，能把这些要求显式表达出来。

相比完全自主 Agent，显式图更容易验证“未经审批不能退款”“工具失败不算完成”等不变量，也更利于监控和回放。模型仍可负责意图理解、方案生成和工具选择，但关键业务约束由代码和后端服务保证。

#### 6. 如果用户只提供了模糊的订单描述，系统如何补充订单信息？

**参考答案：**

先从当前输入和会话中提取订单号、手机号后四位、商品名、时间等实体，调用只读查询获得候选订单。若只有一个且符合用户权限，可展示脱敏摘要让用户确认；多个候选时列出最少必要信息要求选择；没有候选时询问缺失字段或转人工。

不能凭姓名或模糊商品名直接选订单，更不能在身份不确定时查询敏感信息。实体抽取结果要标记来源和置信度，写操作前必须再次确认资源和参数。

### 工具与业务执行

#### 7. 客户、订单、库存、支付和物流工具分别如何设计？

**参考答案：**

工具应小而单一、读写边界明确。客户工具查询客户身份和可见信息；订单工具查询订单详情和状态；库存工具查询可售/锁定库存；支付工具查询支付和退款状态；物流工具查询运单轨迹；订单更新工具执行受控变更。每个工具定义输入/输出 Schema、权限、超时、错误码、幂等要求和副作用等级。

只读工具可以并发，写工具必须带授权、前置状态和幂等键。不要提供一个“万能更新订单”工具给模型，而应按动作拆成取消、退款申请、地址变更等有限接口，减少越权面。

#### 8. 工具参数由模型生成时，如何避免订单号、金额等关键字段错误？

**参考答案：**

先用结构化输出限制字段格式，再由服务端做类型、长度、校验位、范围和业务存在性验证。订单号应来自用户确认或可信查询，不应由模型从自然语言猜测；金额从订单/支付服务读取，模型只能选择动作和原因，不能决定退款金额上限。

执行前展示关键参数并触发人工审批；执行服务再次做鉴权和前置状态校验。失败或不一致时停止并澄清。日志中保存参数哈希和脱敏值，便于审计但避免泄露支付数据。

#### 9. 退款和订单取消如何保证幂等性和数据一致性？

**参考答案：**

以订单、动作、参数版本和任务 ID 生成幂等键，业务服务建立唯一记录。执行前检查订单当前状态和已有退款；写入“处理中”后调用支付/订单服务；收到超时先用幂等键查询，不重复提交；最终通过查询或回调更新本地状态。

数据库内使用事务和状态机，跨支付系统使用 Outbox、回调、对账和补偿。退款金额应以支付系统和业务规则为准。Agent 只负责发起受控命令，不能直接操作数据库绕过领域服务。

#### 10. 订单状态与支付状态不一致时，Agent 应该如何决策？

**参考答案：**

不能直接猜测或执行高风险动作。先确认两套状态的时间戳、来源和是否最终一致，查询支付流水、订单事件或对账接口。如果是暂时同步延迟，进入等待/轮询；如果是业务冲突，转异常队列或人工；只有规则明确且状态一致时才能继续退款/取消。

回复中说明“订单状态”和“支付状态”分别是什么、数据时间和当前可执行动作。异常样本要进入监控和对账，不应被简单重试掩盖。

#### 11. 工具执行成功但结果没有及时返回，系统如何处理？

**参考答案：**

把这种情况标记为“未知/处理中”，不能当失败也不能立即重复执行。使用幂等键查询执行记录或状态接口；若业务支持回调，则等待事件并由幂等消费者更新状态；若只支持轮询，设置有限次数和总时长。超过阈值进入人工或异常队列。

用户看到的是“请求已受理，结果确认中”，而不是虚假的成功。恢复任务时重新验证订单和支付状态，不能依赖原始模型输出。所有状态迁移都记录来源和时间。

#### 12. 业务接口异常时，重试次数和重试间隔如何设置？

**参考答案：**

没有固定数字，应由错误类型、接口 SLA、操作幂等性和用户体验确定。对临时网络/限流可使用 2 到 3 次指数退避加抖动；读接口可以较积极重试，写接口必须先有幂等键并确认前次结果；参数、权限和状态错误不重试。

每次重试消耗任务预算，超过预算熔断或人工。使用服务端 Retry-After，设置总超时，避免多个层级同时重试造成放大。监控重试成功率和重试后延迟，若重试没有收益应调整策略。

#### 13. 为什么将 Redis 用于会话状态、PostgreSQL 用于业务记录？

**参考答案：**

会话上下文和任务中间状态读写频繁、生命周期短、结构灵活，Redis 适合低延迟访问；订单、客户、处理记录和审批记录需要事务、约束、关联查询、持久化和审计，PostgreSQL 更适合作为真相源。

如果任务必须跨进程重启恢复，不能使用只存内存的 Redis 配置或只把状态放在进程内；应配置持久化策略或使用数据库型 Checkpointer。Redis 丢失时，应能从 PostgreSQL/Checkpoint/业务状态恢复，而不是导致重复退款。

#### 14. 如何实现多轮订单跟进和历史处理过程追溯？

**参考答案：**

使用稳定 `thread_id` 关联会话，使用 `task_id` 表示一次订单任务，使用 `order_id` 关联业务对象。Redis 保存短期会话摘要和当前任务状态，PostgreSQL 保存不可变事件或处理记录：输入摘要、节点、工具、参数哈希、结果、审批和状态迁移。

每次新消息先加载当前任务和订单最新状态，再决定继续、创建子任务或关闭旧任务。历史消息要做权限和脱敏控制。追溯页面应能按时间线展示“谁在何时基于什么证据调用了什么工具，结果如何”，不能只保留最终答案。

### 项目成果核验

#### 15. 任务成功率提升 18%的基线和计算方式是什么？

**参考答案：**

需要先定义任务成功：例如目标订单正确、工具执行符合预期、最终状态校验通过、回答完整且无需重复人工处理。基线应是同一复杂订单测试集上的旧流程，比较时冻结模型、工具、数据和评测规则。

“提升 18%”必须澄清是绝对百分点还是相对提升。比如成功率从 60% 到 78% 是提升 18 个百分点，但相对提升是 30%；从 60% 到 70.8% 才是相对提升 18%。应报告样本数、置信区间、按任务类型分层结果和失败原因，不能只引用一个总数。

#### 16. 无效工具调用率如何定义和统计？

**参考答案：**

可定义为不必要、参数明显错误、权限不允许、重复且无状态变化、在已有结果后再次查询，或最终任务根本不需要的工具调用数除以总工具调用数。必须把“工具返回业务拒绝”与“Agent 不该调用工具”区分开，因为前者可能是正确发现业务条件。

评测需要记录每次工具调用的预期动作、参数正确性、前置条件、结果和是否促成状态推进，由人工标注或规则判定。优化后同时观察任务成功率、总调用数、成本和延迟，避免简单少调用导致任务失败。

#### 17. 自动处理率达到 70%+的适用范围是什么？

**参考答案：**

必须说明分母和场景范围。自动处理率通常是满足预先定义条件且无需人工完成的任务数除以进入统计范围的任务数；是全部订单，还是常规查询/异常处理子集，结论差异很大。还要说明高风险动作是否计入，以及人工转接后是否算失败。

可信的报告会按查询、物流、退款、取消、地址变更等类型分层，附带正确率、误自动化率、人工接管率和安全事件。降低人工率不能以漏掉异常为代价，必须设置人工抽检和高风险强制审批。

#### 18. 人工介入率降低 30%是否可能带来错误操作增加？

**参考答案：**

可能，因此不能把人工率单独当作正向指标。应同时监控自动任务成功率、错误退款率、客户投诉、撤销/补偿次数、异常漏检率、人工抽检不合格率和安全违规。对风险动作保持强制审批，只有低风险且证据充分的查询才可自动化。

还应采用分层自动化：低风险常规任务自动完成，中风险抽检或二次校验，高风险人工批准。上线初期做灰度和影子模式，让系统给建议但不执行，验证稳定后再扩大范围。

#### 19. 如何通过结果校验机制识别“工具成功但业务未完成”的情况？

**参考答案：**

工具成功只能说明请求被接口接受，不代表业务状态已达到目标。为每个动作定义目标状态和查询接口，例如退款目标是退款记录成功且订单可退款金额更新；地址修改目标是订单收货地址与新值一致。

执行后读取最终状态，与预期状态机比较；若为异步则等待事件或有限轮询。发现不一致时标记 `unknown`/`partial_failure`，进入重试、对账或人工，不向用户返回成功。校验结果、时间和数据来源写入审计记录。

#### 20. 如果让你继续优化，你会优先改进哪个环节？

**参考答案：**

应先用数据决定，而不是泛泛说“换更大模型”。如果主要失败来自订单识别，就优先做实体抽取和候选确认；如果来自知识依据，就优化检索和版本过滤；如果来自工具执行，就强化 Schema、幂等和结果校验；如果来自延迟，则分析 Trace 后优化并发和缓存。

一个可执行的回答应包含：失败样本占比、预期收益、实现成本、风险、灰度方案和验收指标。例如先针对退款/取消建立端到端状态机和幂等回归集，再通过离线回放、影子流量和小比例灰度验证。

## 四、项目三：企业智能知识平台

### 数据处理与入库

#### 1. 知识平台支持哪些文档类型？不同文档如何解析？

**参考答案：**

应按实际项目回答支持范围，例如 PDF、Word、Markdown、HTML、Excel 或扫描图片。文本型 PDF/Word 重点保留段落和标题；扫描件需要 OCR；Excel 要保留 Sheet、表头、行列关系；HTML 要去除导航和脚本但保留标题、列表和链接语义；Markdown 可直接利用标题层级。

所有解析器输出统一中间结构：文档 ID、页/Sheet、章节路径、文本、表格、图片、位置、版本、权限和解析器版本。这样下游切分和入库不依赖某个文件格式。解析失败、OCR 低置信度或表格结构异常应进入人工复核队列，而不是静默入库。

#### 2. 文档清洗主要处理哪些问题？

**参考答案：**

处理编码、重复页眉页脚、页码、断行、连字符、空白、重复段落、乱码、OCR 错字和无意义导航；同时不能误删否定词、数字、小数点、版本号、单位、代码、表头和条款编号。中文文档还要谨慎处理全半角、繁简体和标点规范化。

清洗要保留原文和清洗后文本，记录处理规则与版本，便于回溯。用哈希、标题和内容相似度识别重复，不能只用文件名。清洗后应抽样人工检查，并通过解析覆盖率、文本长度异常、表格字段完整率等质量指标阻止坏数据进入索引。

#### 3. 父子块切分的具体结构是什么？检索和生成阶段分别使用哪一级文本？

**参考答案：**

父块可以对应一节或一个语义完整的章节，子块是父块中更适合向量化的段落/条款。子块保存 `parent_id`、章节路径和位置，用于精确召回；命中后按父块或邻近子块扩展上下文，用于生成和引用。实际扩大多少要由上下文预算和冗余评测决定。

不能简单把整个长文档当父块，否则上下文噪声过大；也不能只把孤立子句给模型，否则容易缺少定义和限定条件。最终 Prompt 需要去重、保留标题和来源，并将引用映射到具体子块/页码。

#### 4. 如何保留文档标题、章节、页码和版本信息？

**参考答案：**

在解析中维护层级栈，给每个文本片段生成 `section_path`；分页解析时保留 `page_no`，表格和图片记录 Sheet/图号/坐标。元数据至少包括 `doc_id`、标题、来源、版本、生效时间、更新时间、租户、权限、解析器版本和 Embedding 模型版本。

这些字段同时进入向量/全文索引的 Metadata 和 PostgreSQL 元数据表。引用返回时从元数据表或可信索引回填标题、章节和页码。版本不能只写在展示字段中，必须参与过滤和缓存 Key，避免新旧规则混用。

#### 5. 文档重复、内容冲突和版本更新如何处理？

**参考答案：**

用文件哈希、清洗文本哈希和 Chunk 哈希识别完全重复及局部重复；重复文档保留来源关系但避免重复索引。冲突文档要根据生效时间、版本、业务优先级和审批状态选择有效版本，不能让模型自行投票决定制度条款。

更新采用新版本构建、校验、切换、旧版本软删除和异步清理。缓存与索引通过版本号失效，查询日志记录命中的版本。对冲突无法自动判定的内容，标记为人工审核，并允许回答“存在版本冲突，请确认当前制度”。

#### 6. 向量入库时如何设计文档 ID、Chunk ID 和元数据？

**参考答案：**

`doc_id` 应在文件重命名或重新上传后仍能稳定识别同一逻辑文档；`version_id` 区分内容版本；`chunk_id` 可由 `doc_id + version_id + chunk_index/content_hash` 生成；`parent_id` 关联父块。不要只使用数据库自增 ID，否则难以增量更新和跨系统对账。

Metadata 包括标题、章节、页码、语言、产品、版本、生效时间、权限、来源、内容哈希、解析器/Embedding 版本和状态。索引与 PostgreSQL 通过这些 ID 对账，支持重试、删除、回滚和引用。权限字段必须来自可信业务系统，不能由模型生成。

### 检索优化

#### 7. 向量召回和 BM25 召回结果如何合并？

**参考答案：**

两路独立召回并附带文档 ID、排名和分数，先按 Chunk/Parent 去重，再通过 RRF、加权归一化或业务规则融合，最后取候选交给 Reranker。RRF 的优势是不同检索器分数不需要同尺度校准；若用加权分数，需要在验证集确定权重并监控分布漂移。

融合前确保两路使用相同的权限、版本和租户过滤，否则可能把不该看的文档带入候选。候选数要让最终 Recall 足够，同时控制 Reranker 成本。评测时做单路、融合、融合+精排消融。

#### 8. 两路召回的分数不可比时，如何进行融合？

**参考答案：**

优先使用基于排名的 RRF：对每个结果列表按名次贡献 `1/(k+rank)`，同一文档出现在多路时分数累加。它对 BM25 和向量相似度尺度差异不敏感。也可以在固定数据上做 min-max、Z-score 或分位数归一化再加权，但线上分布变化会使阈值失效。

融合参数、每路候选窗口和最终 K 需要通过离线验证，并观察不同 Query 类别的效果。若精确型号类目需要更强调 BM25，可做基于 Query 类型的权重，但必须用测试集之外的验证集调参，并防止规则越来越复杂。

#### 9. BGE-Reranker 的输入和输出是什么？

**参考答案：**

输入通常是一对文本：用户 Query 和候选 Chunk/父块，模型通过 Cross-Encoder 交互编码后输出相关性分数或排序依据。与独立向量相比，它能捕获更细的词序、条件和局部匹配，适合对几十/几百候选进行精排。

输出分数通常只在本次候选列表中有相对意义，不应跨 Query 直接当作统一概率。要控制输入截断、候选数量、批处理和并发，并在生产上测模型加载、CPU/GPU、P95 和成本。精排后仍需去重、版本/权限复核和上下文构建。

#### 10. 带有产品、版本、章节条件的问题如何进行 Query Rewrite？

**参考答案：**

先用实体抽取识别产品、版本、章节和动作，再生成检索 Query，例如将“v3.2 的网络配置怎么改”拆成语义 Query 加 `product=v3.2`、`section=网络配置` 等结构化条件。改写必须保留原 Query，不能擅自补充事实；可以让模型输出 JSON，并对产品/版本从字典或元数据校验。

明确条件用于硬过滤，推断条件用于软召回或扩展检索。为了防止改写错误，可并行检索原 Query 和改写 Query，合并后再排序。改写质量要通过实体准确率、零召回率、Recall@K 和最终答案效果评估。

#### 11. Metadata Filter 设计不当可能造成什么问题？

**参考答案：**

过滤过严会把正确文档全部排除，造成假性零召回；过滤过松会返回其他租户、错误版本或无权限内容；类型和格式错误会使过滤失效或直接报错。模型生成的产品名、版本号若未经校验，也可能把自然语言误当成精确值。

解决方法是权限过滤必须由服务端强制，产品/版本字段来自可信枚举；对业务条件区分硬过滤与软条件；零结果时只放宽非安全条件并记录原因；对每次查询记录过滤前后候选数量和命中率。过滤条件要纳入离线测试和安全测试。

#### 12. 如果用户查询的是一个精确产品型号，为什么 BM25 可能优于纯向量检索？

**参考答案：**

型号是高信息量的精确 Token，例如带数字、字母和连字符。BM25 会因稀有词和精确词面匹配给对应文档高分；向量模型主要学习语义相似，可能把相邻型号或相似产品映射得很近，尤其在型号字符差异很小的情况下容易混淆。

因此应保留规范化型号字段、别名和字符级匹配，同时用向量检索补充用户描述。结果可按型号完全匹配、当前版本和权限做业务排序，但必须避免把“相似型号”当作“同一型号”。评测需包含近邻型号负样本。

#### 13. 如何处理跨多个 Chunk 才能完整回答的问题？

**参考答案：**

利用父子块和章节路径扩展上下文：命中一个子块后补充同父块的相邻块、定义块或步骤块；对多个候选按父文档聚合，避免只取同一段重复内容。复杂问题可先识别子问题，分别检索后合并证据。

上下文构建要设总 Token 预算、每文档配额和去重规则，优先选择能覆盖答案事实的块。若证据分散且排序不稳定，可进行二次检索或让模型输出证据覆盖清单。答案应为每个关键结论绑定引用，证据不足则明确缺失。

#### 14. 如何避免召回上下文过长、重复或互相矛盾？

**参考答案：**

先按内容哈希和父块去重，再合并相邻块；设置每个文档、章节和版本的数量上限；使用 Reranker、MMR 或多样性约束减少同义重复。根据问题类型优先当前生效版本和同一产品版本。

冲突内容不能让模型随意平均，应该依据生效时间、权威来源和版本规则选择，无法判断时并列展示冲突并转人工。上下文构建结果要记录版本、顺序和截断情况，便于复现。评测不只看召回，还看 Context Precision、答案正确率和 Token 成本。

### 评测与接口

#### 15. Recall@K、Context Precision、Context Recall 和 Faithfulness 如何配合分析？

**参考答案：**

Recall@K 主要看相关证据是否进入候选；Context Recall 看答案所需参考事实被上下文覆盖多少；Context Precision 看上下文中相关内容比例和排序质量；Faithfulness 看最终回答是否由上下文支持。可以按以下方式定位：

- Recall 低：先查文档、切分、Query、过滤和召回。
- Recall 高但 Context Precision 低：查融合、Reranker、去重和 K。
- 上下文指标好但 Faithfulness 低：查 Prompt、生成模型、引用约束和上下文冲突。
- Faithfulness 好但答案不全：查参考事实覆盖、问题拆分和生成长度。

还要结合人工答案正确率、引用准确率、零结果率、延迟和成本，不能把某一个 LLM 指标当作产品成功。

#### 16. 如何构造人工标注的查询集和标准答案？

**参考答案：**

样本来自脱敏真实问题、业务专家编写的边界问题和失败回流；覆盖产品/版本条件、精确型号、长文档、多跳、无答案、冲突版本、权限和错别字。每个 Query 需要标注相关文档/Chunk、必需事实、可接受答案、不可接受答案和引用位置。

标注指南要明确“一问多答案”“多个等价文档”和“答案不可判定”的处理。最好双人标注并仲裁，统计一致率。测试集按用户或文档时间分割，防止同一文档模板泄漏；文档更新后要重新确认标签有效期。保存知识库版本、标注版本和评测脚本版本。

#### 17. 如果 Recall@K 提升但 Faithfulness 下降，应该如何排查？

**参考答案：**

可能是新增召回带来更多噪声/冲突，Reranker 排序变差，上下文超长或 Prompt 没有处理证据冲突。先逐条比较改动前后的候选、最终上下文顺序和 Token 长度；检查答案引用是否来自新增噪声；再做“只给标准证据”的 Oracle 生成实验。

如果 Oracle 也下降，问题在生成 Prompt/模型或冲突证据；如果 Oracle 正常，问题在检索融合、去重和上下文构建。可降低最终 K、加强 Reranker、按版本过滤、增加证据一致性校验，并在固定测试集上回归，而不是简单回退 Recall 提升。

#### 18. Retrieval API 的请求参数和返回结果如何设计？

**参考答案：**

请求至少包含 Query、知识库/租户、过滤条件、Top-K、是否启用改写/混合检索/精排、请求 ID 和用户身份上下文。服务端要限制 Top-K、过滤字段和最大 Query 长度，不能把权限交给客户端自由传入。

返回包含文档 ID、Chunk/Parent ID、标题、章节、页码、版本、生效状态、相关性分数、检索来源（BM25/向量/融合）、片段和引用位置。还可返回耗时、索引版本和 trace ID。API 应有 Schema 版本、错误码、超时和分页/流式策略，避免返回大段无必要原文。

#### 19. 为什么需要返回标题、章节、页码等来源信息？

**参考答案：**

来源信息让答案可追溯、可核验和可审计，用户可以回到原文确认上下文，运营人员也能定位错误 Chunk。对企业制度来说，版本、生效时间和页码还影响答案是否有效。

引用对象应是稳定 ID 加展示信息，而不是模型自由生成的“第几页”。生成后校验引用 ID 存在且属于当前用户可见范围，避免伪造引用。来源信息也支持离线失败分析：知道错误来自哪份文档、哪一章节和哪个版本。

#### 20. Redis 缓存知识查询时，如何处理文档更新导致的缓存失效？

**参考答案：**

缓存 Key 应包含规范化 Query、过滤条件、租户/权限摘要、检索配置、Embedding/索引版本和知识库 active version。文档更新完成并切换版本后，新 Query 自然使用新 Key；旧 Key 可异步删除或设置短 TTL。

不能只按 Query 缓存，否则不同权限用户可能共享结果，旧版本也会继续返回。更新过程中使用新版本索引验证后原子切换，避免部分请求读到混合版本。缓存值应包含来源版本，读取时再做轻量有效性检查。

#### 21. 如何控制不同用户对不同知识库和文档的访问权限？

**参考答案：**

认证层识别用户、租户、角色和组织；授权服务根据资源级 ACL 生成服务端过滤表达式。权限过滤要在召回前执行，返回和缓存时再做防御性检查。模型不能决定“用户是否有权看这份文档”，也不能通过 Prompt 传递 ACL。

缓存 Key 包含权限上下文或按租户/用户隔离；权限变更主动失效相关缓存。日志中记录访问策略版本和被过滤数量，审计不保存不必要的敏感正文。应测试越权 Query、文档链接直接访问、缓存命中和多租户混合检索。

#### 22. 如果知识库没有相关答案，系统应如何返回？

**参考答案：**

先定义零召回和低置信度阈值，不能让模型用常识填空。回答可以说明“当前知识库没有找到足够依据”，返回已检索范围/版本、建议补充的信息、人工入口或创建知识需求；如果只找到部分证据，要明确哪些部分有依据、哪些部分无法确认。

对于高风险问题宁可拒答或转人工。系统记录 Query、过滤条件、零结果原因和用户反馈，用于补充文档、同义词、切分或路由。零答案率不能简单通过降低阈值来改善，否则会以幻觉增加为代价。

## 五、面试通用问题及参考回答

#### 1. 请做一个三分钟的自我介绍，重点介绍你最有代表性的项目。

**参考答案模板：**

“我叫曹浩磊，主要从事大模型应用和 Agent 开发，技术方向集中在 LangGraph/LangChain、多 Agent 编排、RAG、工具调用和 Python 后端。过去的项目主要有三个：电商多智能体运营系统、企业智能订单处理 Agent 和企业智能知识平台。我的工作不是只做 Prompt，而是参与了状态设计、检索链路、业务工具、人工确认、异常处理和效果评测。

我最有代表性的项目是电商多智能体系统。我负责商品审核和售后 Agent，并参与 Orchestrator 路由、State Schema、Checkpointer 和评测优化。回答项目指标时，我会重点说明数据集、基线、实验配置和线上统计口径，而不是只报提升结果。我的优势是能把模型能力和业务流程、权限、幂等、监控结合起来；后续希望继续深入 Agent 平台化和可靠性建设。”

回答时不要逐条复述简历，应突出职责、技术决策、结果和一个失败/改进案例。

#### 2. 你在三个项目中承担的职责有什么差异？

**参考答案：**

企业知识平台更偏 RAG 数据处理、混合检索、精排、评测和 Retrieval API；订单处理 Agent 更偏 LangGraph 流程、业务工具、状态管理、结果校验和人工审批；电商多智能体系统则在前两者基础上增加了 Orchestrator、多 Agent 路由、MCP 接入和跨领域协作。

可以进一步说明三个项目的共性能力：先把数据和状态结构化，再让模型做语义决策，最后由确定性规则、工具服务和审计保证业务安全。差异体现了从单一检索能力到单 Agent 执行，再到多 Agent 平台协调的经验积累。

#### 3. 哪个项目最能体现你的独立开发能力？为什么？

**参考答案模板：**

应选择自己真正负责范围最大的项目，并按“需求、方案、实现、验证、上线”回答。例如企业知识平台可以说明自己独立完成文档解析、父子切分、Embedding 入库、BM25/向量融合、Reranker、评测和 API；同时说明哪些基础设施由团队提供，哪些代码是自己完成的。

好的回答会给出一个具体难点和取舍，例如发现纯向量对型号匹配不稳定，于是引入 BM25 和元数据过滤，再通过固定评测集验证。不要把团队成果全部归到个人，也不要只说“我负责整个项目”而没有模块边界。

#### 4. 你遇到过最难定位的线上问题是什么？最后如何解决？

**参考答案模板：**

建议使用 STAR 结构。示例：“线上发现任务失败率升高，但模型和工具单项成功率都正常。我通过 trace 分阶段拆解，发现部分请求在缓存命中旧知识版本后生成了过期结论。后来把索引版本和权限摘要加入缓存 Key，并在文档切换时做失效，增加版本回归测试和告警。修复后看固定窗口的失败率、陈旧命中率和引用版本。”

候选人应讲清现象、定位证据、根因、修复、验证和后续预防。不要把“重启服务”当作解决方案，也不要暴露未脱敏的客户数据。

#### 5. 讲一个你主动发现并推动解决的问题。

**参考答案模板：**

可以讲“工具返回 HTTP 成功但业务状态未完成”的问题。主动发现后定义结果状态 Schema 和后验查询，将工具成功与任务完成分开；对超时使用幂等键查询，对未知状态进入人工/对账；补充失败样本和监控。这样体现你不仅关注模型输出，也关注业务闭环。

回答必须说明你做了什么、协调了哪些角色、结果如何量化，以及是否有文档、测试或监控沉淀。

#### 6. 你如何与产品、后端、算法或业务人员协作？

**参考答案：**

先共同定义业务目标和成功标准，再把需求拆成输入/输出 Schema、工具契约、状态机、权限边界和评测集。与产品确认异常和人工流程，与后端确认接口状态码、幂等和 SLA，与算法/模型人员确认模型能力与部署约束，与业务专家完成规则标注和样本仲裁。

开发中通过接口文档、样例请求、错误码、Trace 和固定回放集对齐；上线采用灰度和问题复盘。分歧时用数据、失败样本和风险成本沟通，而不是只争论模型大小或 Prompt 写法。

#### 7. 当项目时间紧但效果指标未达标时，你会如何处理？

**参考答案：**

先确认指标定义和是否是硬门槛，再分解到数据、检索、模型、工具和产品流程。优先修复高频且高风险的失败类型，建立最小可上线方案：低风险只读自动化，高风险保留人工；对质量不足的任务开启兜底，而不是强行扩大自动执行范围。

同时给出短期止血、中期优化和长期方案，明确负责人、截止时间和验收集。若指标改善来自缩小适用范围，要如实说明自动处理率变化，不能用指标口径掩盖能力退化。

#### 8. 如果模型效果和业务规则冲突，你会优先相信哪一方？为什么？

**参考答案：**

涉及权限、金额、订单状态、合规和安全时，优先相信可信业务系统和确定性规则，模型只能解释、规划或提出建议。若知识库和业务系统冲突，按照权威来源、版本和生效时间判断，无法判断就人工升级。

模型可以帮助发现规则缺口，但不能自行覆盖规则。系统应把冲突作为显式状态和监控事件记录下来，推动业务确认，而不是让 Prompt 里的“请相信模型”决定结果。

#### 9. 你如何判断一个 Agent 功能是否真正适合落地？

**参考答案：**

评估任务是否有清晰目标、可验证完成条件、稳定数据源、可控工具边界、可接受错误成本和人工兜底。开放式聊天不一定适合 Agent；如果业务结果无法验证、权限复杂且失败代价极高，应先做只读建议或人工辅助。

落地前建立离线评测集、影子模式和灰度方案，观察任务成功率、人工节省、延迟、成本、安全和投诉。只有质量和风险都达到门槛，才逐步扩大自动化范围。

#### 10. 你认为当前大模型应用开发中最容易被忽略的问题是什么？

**参考答案：**

最容易忽略的是业务闭环和可验证性：很多系统只看模型回答是否流畅，却没有考虑数据版本、权限、工具幂等、结果校验、审计、失败恢复和评测回归。RAG 也不能只看向量相似度，Agent 也不能只看 Tool Calling 是否成功。

我会把模型当作不完全可靠的决策组件，在外层用结构化状态、确定性规则、可信数据源、人工审批、监控和回放保证系统质量。

#### 11. 未来你希望继续深入 Agent、RAG、模型微调还是平台工程？为什么？

**参考答案模板：**

结合现有经历，可以回答希望深入 Agent 平台工程与 RAG 可靠性：前者关注状态、工具、权限、评测和可观测性，后者关注数据治理、检索效果和知识更新，两者直接决定大模型应用能否稳定落地。模型微调可以作为特定领域数据不足或格式/行为需要固化时的补充，而不是所有问题的第一选择。

回答应说明计划，例如学习服务编排、评测体系、推理优化和模型训练，而非只列技术名词。

#### 12. 为什么考虑离开上一家公司？

**参考答案模板：**

用事实和未来目标表达，不贬低原公司。例如：“过去的工作让我积累了 Agent、RAG 和业务系统落地经验，希望下一阶段接触更复杂的 Agent 平台、评测和生产化问题，承担更完整的模块责任。贵岗位与我的技术方向和项目经验匹配。”

避免抱怨同事、薪资作为唯一理由、透露前公司机密或声称已经掌握尚未实际使用的技术。

#### 13. 你期望的工作内容和团队环境是什么？

**参考答案：**

希望参与从需求、架构、实现、评测到上线的完整链路，尤其是 Agent 状态编排、RAG、工具接入、质量和稳定性建设。团队最好有明确的代码评审、数据和指标口径、线上复盘以及产品/业务协作机制。

同时应表现出对实际工程工作的接受度：接口联调、数据清洗、日志排查、测试和线上值班都是交付的一部分，而不是只希望做 Prompt。

#### 14. 你对加班、线上故障和紧急需求的看法是什么？

**参考答案：**

线上故障优先止损、隔离风险、恢复服务，再定位和复盘；涉及订单和资金时宁可转人工，也不能为追求可用性绕过安全控制。紧急需求可以配合，但要明确优先级、影响范围、回滚方案和后续补齐测试的时间。

长期不应依靠加班替代工程治理，应通过监控、自动化测试、灰度、Runbook 和复盘降低重复故障。

#### 15. 你认为自己目前最大的技术短板是什么？准备如何补足？

**参考答案模板：**

应选择真实、可改善且不直接否定岗位核心能力的短板。例如：“我在模型训练和底层推理优化方面参与深度还不如应用工程，过去主要做 BERT 微调了解和推理服务接入。计划通过复现 LoRA/量化实验、学习显存与吞吐分析，并在项目中承担一段模型评测或部署优化。”

好的回答有具体行动、时间安排和可验证产出；不要把“太追求完美”“没有短板”当作答案，也不要把安全、权限或数据意识说成不重要。

## 六、简历指标核验清单

面试官可以将以下问题作为二次追问：

1. 2,000 条路由样本如何标注？各意图数量和混淆矩阵是什么？
2. 路由准确率从 73% 到 90%+是绝对百分点还是相对提升？测试集是否冻结？
3. Recall@5 的“相关文档”由谁标注？父块命中是否算命中？
4. 78% 到 91% 的对比是否同时改变了 Top-K、切分、模型或知识库版本？
5. BGE-M3 是使用 Dense、Sparse 还是两者？BM25 是 Elasticsearch 还是 Milvus 内置能力？
6. BGE-Reranker 的候选数量、批大小、硬件和 P95 延迟是多少？
7. Checkpointer 使用什么实现？进程重启后是否真实恢复过任务？
8. `interrupt()` 恢复时节点是否会重跑？前置副作用如何保证幂等？
9. MCP 工具的 `inputSchema`、`outputSchema`、错误码和鉴权在哪里实现？
10. 退款或取消订单的幂等键是什么？超时后如何确认前次执行结果？
11. TTFT 30% 的分母、分位数、并发和缓存命中率是什么？
12. 失败率降低 25%是接口失败率、模型失败率、工具失败率还是端到端任务失败率？
13. RAGAS 使用的评审模型、Prompt、数据集版本和人工抽检一致率是多少？
14. PostgreSQL、Redis、Milvus/Elasticsearch 之间的数据真相源和一致性策略是什么？
15. 候选人能否画出一次请求的 State 变化、工具调用和异常分支？

若候选人只能解释概念，不能给出字段、错误码、状态迁移、数据样本、实验对照和线上排查路径，则更可能是“了解方案”而非“实际负责实现”。
