# 第一部分：RAG 高频面试题（答案已按简历填充）

## 一、项目主线

### 问题：介绍一下你的 RAG 项目流程。

**【简历事实版答案】**

我以**企业智能知识平台**为例（RAG 开发工程师）：项目目标是解决企业内部技术文档、产品资料、业务制度等多源知识**分散、结构复杂、关键词搜索匹配不准、问答缺少来源依据**的问题。

**离线侧**：将 PDF、Word、网页等文档按文件类型分管线解析 → 内容清洗（去页眉页脚/乱码/重复段落）→ 父子块切分（Child 约 256 token 用于精准检索，Parent 按章节保完整上下文）→ BGE-M3 生成向量 → 写入 Milvus（向量 + metadata[标题/章节/页码/版本] + 原文）。

**在线侧**：用户问题 → 先做 Query Rewrite 补全检索条件 + Metadata Filter 缩小范围 → BGE-M3 向量召回 + BM25 关键词召回 → 合并去重 → BGE-Reranker 精排 → 把带来源的上下文交给 LLM 生成 → 返回带引用的答案。同时用 Redis 缓存高频查询、PostgreSQL 管文档元数据。

**评测闭环**：基于人工标注查询集评估 **Recall@K、Context Precision**，对漏召回、排序不准确、上下文冗余等失败样本分类，定位切分、召回、精排环节的问题再迭代。

**我的职责**：独立完成数据入库、召回模块、复杂查询优化、离线评测和 Retrieval API 封装。遇到的主要问题是**多条件长文档查询（产品+版本+章节）召回率低**，通过 Query Rewrite + Metadata Filter + 混合检索 + 精排，把召回效果从纯向量基线的 78% 提升到 91%（Recall@5，2000 条查询集）。

### 问题：为什么不用普通搜索、FAQ 或微调？

**【简历事实版答案】**

- **FAQ**：适合问题和答案固定、数量有限的场景。企业内部高频固定问法（如"如何申请权限"）可用 FAQ 快速返回；
- **全文检索（关键词）**：适合精确编号、条款原文的匹配，但用户问法多样时命中率低；
- **RAG**：适合用户问法多样、知识需要频繁更新且需要引用依据的场景——企业知识恰恰如此：文档常更新、问法口语化、结果要可追溯；
- **微调**：解决的是模型行为或领域表达，不适合频繁注入事实知识：更新成本高、难以逐条溯源、无法给出来源。

**结论**：FAQ 处理高频固定问法，RAG 处理长尾知识问答，结构化实时数据另走数据库查询（如订单项目里订单/库存状态查业务库）。我的选择是三者分工，不是单一方案。

## 二、项目真实性与职责

### 问题：你具体负责什么？项目难点是什么？

**【简历事实版答案】**

按"输入—动作—结果"答：我负责**数据入库、检索召回、评测闭环和 Retrieval API** 四个模块，独立完成了**父块子切分 + 混合召回 + 精排**的检索链路，以及**基于人工标注查询集的离线评测**。

**最难的难点**：复杂多条件查询（如"B 产品 v1.0 第 3 章的保修条款"）召回率低——相关条款召不回来。我先通过失败样本分析定位是**检索条件丢失**（向量把版本号这种精确条件漂移了）而非模型问题，再引入 **Query Rewrite 抽取产品/版本/主题条件 + Metadata Filter 收窄检索空间 + 混合检索 + 精排**；结果是该子集召回显著提升、全量回归不降。

**注**：所有数字（78%→91%）都有 2000 条标注查询集支撑，不编造百分比。

## 三、软技能与交付

### 问题：客户觉得效果不好、工期又到了怎么办？

**【简历事实版答案】**

先把"效果不好"拆成可验证问题：**数据缺失、召回不准、答案表达、响应慢还是需求范围变化**，再用日志和失败样例复现。对已承诺范围交付可用的闭环；对高风险问题给明确限制、临时降级（如先只支持核心问答）和迭代计划，把验收样例、负责人和时间点写进记录。

不承诺"模型一定完全准确"，而是对齐可量化标准——**关键问题通过率、引用覆盖率、人工转接率、响应时间**（呼应简历：人工介入率 -30% 就是这种可量化指标）。

## 四、场景设计

### 问题：给你 PDF/Markdown，如何从零设计 RAG？

**【简历事实版答案】**

先问四个约束：**文档规模与更新频率、是否有图片表格、权限模型、准确率和时延目标**。随后按我知识平台的做法设计：

1. **解析与存储**：PDF/Word/HTML 分类型管线，扫描件 OCR，表格转结构文本；原文件放对象存储；
2. **结构化 chunk + metadata**：父子块切分，每块带 `doc_id、version、page、section_path、content_type、permission`；
3. **混合召回**：BGE-M3 向量 + BM25 关键词，合并去重；
4. **rerank**：BGE-Reranker 精排到 Top-K；
5. **引用式生成**：带来源注入，要求模型基于资料回答；
6. **离线评测 + 线上监控**：Recall@K/Context Precision + TTFT/P95/失败率。

MVP 先支持主格式和核心问答；生产版再补权限过滤、增量索引、失败回退、监控和灰度。若用户问"多个知识库"，用 metadata（kb_id）和权限过滤先缩小候选范围，再在目标库内检索——不依赖模型自由猜分类。

## 五、数据预处理与切块

### 问题：文档如何处理、PDF 如何切块？

**【简历事实版答案】**

**先区分文档类型**：原生文本 PDF、扫描件、图片、表格和结构化表。

- **原生文本**：按标题、段落、列表恢复结构（我知识平台里用 `PyMuPDF/pdfplumber` 抽文本与坐标，按章节锚定）；
- **扫描件**：走 OCR（PaddleOCR）并记录置信度，低置信内容隔离抽检；
- **表格**：保留表头、行列、单位和页码，转成 Markdown/键值对，防止语义崩坏；
- **图文混排**：按坐标重建阅读顺序。

**切块**：先按语义和结构边界（标题/章节）切，超长块再二次切分，overlap 只做边界兜底。我采用的是**父子块**：Child 约 256 token 用于向量检索（精准命中），Parent 按章节保完整上下文，命中 Child 回溯返回 Parent 给 LLM。每块保存 `doc_id、version、page、section_path、content_type、source_uri、permission`，支撑回溯、权限过滤和增量更新。

### 问题：表格、图片、跨页表怎么处理？

**【简历事实版答案】**

表格不能只抽文字。将表题、表头、行名、列名、单位和脚注转为 HTML/Markdown/JSON；大表按"表题+必要表头+行组"切，跨页先验证表头与 schema 一致再合并。图片绑定相邻标题与正文，保留页码与原图引用；扫描件低置信内容隔离抽检。

解析失败时记录文件、页码、解析器版本和错误类型，回退页级文本、OCR 或原图——**不把错误内容直接入向量库**（这是我在知识平台数据清洗里守住的红线）。

## 六、Embedding 与向量库

### 问题：为什么选这个 embedding 模型？能直接替换版本吗？

**【简历事实版答案】**

我选 **BGE-M3**，理由：① 多语言，企业文档中英混杂友好；② 一个模型同时产出 Dense/Sparse/多向量三种表示，混合检索省维护；③ 支持 8192 token 长文本，长条款可直接编码；④ 中文效果有保障、开源可控。

**版本升级的坑**：模型升级即使维度相同，也不应直接混用新旧向量——向量空间分布可能变化。正确方式是**离线重建索引、双索引灰度对比、验证召回后切流**。元数据除文本外保存来源、页码、知识库、版本、权限和时间，检索时**先 metadata filter 再做相似度召回**（呼应知识平台的版本隔离）。

### 问题：为什么用 Milvus/FAISS/ES/pgvector？

**【简历事实版答案】**

**按规模选型，不说"绝对最好"**：
- 数据量小、单机原型 → FAISS 或 pgvector；
- 需要文本检索和筛选 → ES（我订单项目里知识库以规则/政策文本为主，就用 ES 的 BM25 + 向量混合）；
- 大规模向量检索、要集群能力 → Milvus（我多智能体项目做大规模纯向量 + 混合检索，选 Milvus）。

选型必须结合项目规模和运维能力：知识平台用 Milvus 是因为要支撑混合召回 + 精排的完整检索链路和后续扩展。

## 七、数据库配合

### 问题：Redis、Milvus、MySQL 怎么分工？

**【简历事实版答案】**

以我的知识平台为例（Milvus + PostgreSQL + Redis 三者并用）：
- **Milvus**：存向量 + 检索用 metadata + chunk 原文；
- **PostgreSQL**：存文档元数据（标题/版本/状态/入库时间）、问答日志；
- **Redis**：存高频查询缓存（按 query+filters hash 做 key，TTL 300s）；
- **原文件**：放对象存储。

请求进入后先认证并确定知识库范围 → 读 Redis 缓存或检索 Milvus → 用 PG/对象存储回溯详情。若某项目只用了其中一部分，如实说明替代方案（如订单项目用 ES 而非 Milvus）。

## 八、检索、召回与混合检索

### 问题：语义、全文和混合检索分别何时用？

**【简历事实版答案】**

- **语义检索**：用户问法与文档表述不一致时（"怎么退换货"≈"退货政策"）；
- **全文/BM25**：产品名、编号、法规条款等精确词（"PO12345""B-100 型 v2.1"）；
- **混合检索**：同时要求语义理解和精确约束——这正是企业内部查询的常态，也是我知识平台的做法：**BGE-M3 向量召回 + BM25 关键词召回 → 合并去重 → BGE-Reranker 精排**。

融合前要做分数归一化或采用 rank fusion，不能直接比较不同检索器的原始分数。topK 通过离线评测选择：太小漏召回，太大增加 rerank 和上下文成本。

### 问题：检索不准如何定位？

**【简历事实版答案】**

按链路排查（我在知识平台评测里就是这么定位的）：正确文档是否入库 → chunk 是否完整 → query 是否表达真实意图 → 召回是否包含正确块 → rerank 是否把正确块压低 → prompt 是否使用了正确上下文 → 生成是否脱离资料。**每层保留 trace**，避免看到错答案就直接怪模型。我的失败样本分类法（漏召回/排序不准/上下文冗余）就是这套链路排查的产物。

## 九、Rerank

### 问题：为什么有向量召回还要 rerank？

**【简历事实版答案】**

embedding 是**双塔编码**，适合大规模快速粗召回，但 query 与 passage 交互有限；**reranker 联合看 query 和候选文本**，能看到词级细粒度交互，精度更高但成本更大。因此链路是：**召回 Top-100 → BGE-Reranker 精排 → 取 Top-K(3~5) 给 LLM**。

我的数据佐证：纯向量 Recall@5 78% → 混合检索 + BGE-Reranker 精排后 91%，提升核心就在"排序对了，前 5 条才命中"。若 rerank 慢：减少候选、批处理、缓存、量化，或按问题类型跳过——前提是用评测集证明对效果的影响。

## 十、意图与 FAQ/RAG 路由

### 问题：FAQ + RAG 怎么路由？分类错了怎么办？

**【简历事实版答案】**

先识别问题类型：固定高频问法、知识库问答、闲聊、越权或知识库外问题。FAQ 通过精确/高置信匹配快速返回；复杂或低置信问题走 RAG；知识库外应澄清、转人工或明确拒答。

分类模型可以是规则、embedding、轻量分类器或 LLM，但**必须设置置信度与兜底**。我在多智能体项目里用的是 **LLM 意图识别 + few-shot + 规则关键词兜底 + 低置信转通用 Agent/人工**；分类准确率用有标签测试集（2000 条）算 precision/recall/F1，重点看哪些类别容易互相混淆（售后 vs 售前）——这正是路由准确率从 73% 提到 90%+ 的抓手。

## 十一、多轮上下文与记忆

### 问题：上下文太长、用户换话题怎么办？

**【简历事实版答案】**

不把所有历史原样拼进 prompt。**保留最近关键轮次 + 结构化查询条件 + 任务摘要**；长历史做摘要或按需检索。用户明显换话题时**重置检索上下文**，只保留必要身份和权限信息。

我订单 Agent 的做法：把"订单号、用户诉求、当前状态"这些关键事实抽到 **State 结构化字段**（Pydantic），生成时不重放全部原文；会话上下文存 Redis（TTL 管理），支持多轮跟进。长期记忆只存对用户有价值且授权的信息，设过期与删除。

---

## 十二、MCP 与 Function Calling

### 问题：MCP 和 Function Calling 有什么区别？

**【简历事实版答案】**

- **Function Calling**：模型根据函数 schema 选择工具并生成参数的能力（"选哪个 + 填什么参数"）；
- **MCP**：把外部工具、资源和提示能力**标准化暴露**给客户端/模型的协议（"AI 世界的 USB-C"）。

两者可结合：**MCP Server 暴露业务工具**，应用层再以函数 schema 让模型调用。我在售后 Agent 里就是：订单/物流/客户工具封装成 MCP Server，Agent 通过 MCP 发现并调用，同时用 Function Calling 让 LLM 选工具。无论哪种方式，都要做**参数校验、权限控制、超时和审计**（Pydantic 校验 + 高风险人工确认 + 工具调用轨迹落库）。

---

## 十三、幻觉、安全与权限

### 问题：RAG 如何减少幻觉？

**【简历事实版答案】**

**先保证检索质量**（召回准，模型才有据可依）：混合检索 + 精排 + 父子块保证上下文完整（Recall@5 91%）。**再约束生成**：要求模型仅基于上下文回答并给出来源；无可靠依据时明确"不确定"或转人工。**最后校验**：引用匹配、答案与上下文一致性（Faithfulness 指标）、人工抽检定位问题。

**提示词注入**：输入识别、系统指令隔离（检索片段标"数据区"）、工具最小权限、敏感操作二次确认、输出过滤共同防护。**权限过滤在检索前/检索中完成**（metadata filter 带 tenant/permission），不能先召回越权文本再让模型"不要说"。

---

## 十四、性能与并发

### 问题：RAG 回答慢怎么优化？

**【简历事实版答案】**

先拆分耗时：鉴权、query 改写、召回、rerank、prompt 拼接、首 token、完整生成和网络。我的优化（知识平台 + 电商项目，TTFT -30%）：

1. **缓存**：热点 FAQ / 检索结果（Redis）命中免重算；
2. **并行独立召回**：向量召回与 BM25 并行、`asyncio.gather` 并发多工具；
3. **控制候选数与上下文长度**：精排阈值过滤，Top-K 不贪多；
4. **批处理/量化 rerank**；
5. **流式输出（SSE）**改善感知时延。

高并发还要配置连接池、队列、限流、超时、熔断和降级——不是只加线程。

---

## 十五、部署与接口

### 问题：FastAPI/Docker 上线后出问题怎么排查？

**【简历事实版答案】**

从请求 **trace_id** 开始，检查接口参数、应用日志、容器状态、环境变量、模型服务、数据库连接和网络。若本地正常线上异常，优先比较镜像版本、依赖、配置、挂载文件、权限和资源限制（`docker logs`、`docker inspect`、healthcheck）。接口区分同步问答、文件上传和流式响应；幂等请求、超时和重试策略要明确，敏感日志脱敏。

---

## 十六、评估指标

### 问题：RAG 准确率/召回率怎么评估？

**【简历事实版答案】**

**先构建评测集**：覆盖高频、长尾、表格、否定条件和知识库外问题，并标注相关文档（我知识平台用人工标注查询集）。

- **检索层**：Recall@K、MRR、nDCG 或人工命中率——我用 Recall@K（78%→91%）和 Context Precision；
- **生成层**：答案正确性、引用正确性、faithfulness、answer relevancy（RAGAS）；
- **系统层**：P50/P95、TTFT、失败率和用户反馈（电商项目 TTFT -30%、失败率 -25%）。

所有提升要说明 baseline、样本量、时间范围和评测方法，不能只报一个百分比。

---

## 十七、模型基础

### 问题：Transformer、自注意力、temperature/top_p/top_k 怎么回答？

**【简历事实版答案】**

Transformer 用自注意力建模 token 间关系，编码器更适合理解表征，解码器更适合自回归生成。注意力核心：**Q 和 K 算相关性 → softmax 得权重 → 对 V 加权汇聚**（缩放点积 `softmax(Q·K^T/√d)·V`，除 √d 防梯度饱和）。

**temperature** 控制采样随机性（低=稳定，适合路由/结构化输出，我工具参数调用用 0~0.1）；**top_k** 限制候选数量；**top_p** 从累计概率候选中采样。知识问答通常降低随机性，但**不能仅靠低温度解决幻觉**——还要靠检索质量和校验（呼应本项目幻觉治理）。

---

## 十八、复习顺序

先准备：项目流程（知识平台）、数据与切块（父子块）、检索与 rerank（混合检索 + 精排）、数据库分工（Milvus/PG/Redis）、幻觉治理、个人职责和一个真实难点（多条件查询召回低）。再准备：多轮上下文、权限、部署、评测和性能。进阶：索引参数（HNSW/IVF）、融合策略（RRF）、RAGAS、复杂表格/长文档和生产治理。

# RAG 逐题补全答案（技术题）

## 1. RAG 项目主线

### 问题：RAG 的目标是什么？怎么证明达到目标？

**【简历事实版答案】**

目标是让模型在**私有/频繁变化**的企业知识上回答**可追溯、可更新**的问题。证明拆三层：**检索层**看正确文档 Recall@K（我 78%→91%）；**答案层**看人工正确率/引用正确率（问答带标题/章节/页码来源）；**业务层**看人工咨询量、解决率或满意度（人工介入率 -30%）。比较对象、样本数（2000 条）、统计周期必须说清楚。

### 问题：数据来源、更新频率和脏数据怎么答？

**【简历事实版答案】**

数据来自企业内部多源（技术文档/产品资料/业务制度），说明授权范围、格式占比（PDF/Word/HTML）和更新方式。**增量更新**用文档 hash 或版本号判断：新增直接解析入库；变更先删除/失效旧 version 的 chunk 再写新版本；删除同步删索引和对象存储引用（我知识平台以 doc_id + version 管理）。脏数据（重复文档、乱码、空页、失效版本、错误 OCR）进入**隔离队列**而非直接入库。

---

## 2. 预处理与切块补充

### 问题：父子块、语义块、按标题块分别何时用？

**【简历事实版答案】**

- **按标题块**：制度、手册等层级清晰文档；
- **语义块**：无稳定标题的长文本，按段落/句子边界保持主题一致；
- **父子块**：既要精确召回又要补全上下文的场景——**子块检索、父块交给 LLM**，我知识平台采用这个（Child ~256 token 检索、Parent 按章节做上下文）。

三者不是互斥关系，可按文档类型组合（我的做法：先按标题结构定 Parent 边界，内部再切 Child）。

### 问题：切块大小、overlap 设多少？

**【简历事实版答案】**

以 **token** 而不是"汉字数"理解大小，根据文档类型、embedding 模型和上下文预算确定。我的保守配置：Child ~256 token、Parent 按章节（超长再按二级标题拆）、块间 overlap ~20 token 兜底。**不给固定万能数字**：在标注问答集上调 Recall@K、答案正确率、上下文 token 和延迟；发现条件句或列表被切断时优先调结构边界，最后才加 overlap。

### 问题：多模态文件如何保证图文顺序？

**【简历事实版答案】**

用页内坐标、栏位和 block 类型重建阅读顺序；图片绑定最近标题和说明文字，保留 page/bbox/image_id。多栏文档不能依赖 PDF 原始文本流（会串行错位）；抽样比对渲染页，检查标题、正文、图片和表格是否错位（知识平台数据清洗的质检环节）。

---

## 3. embedding 与索引补充

### 问题：向量索引 IVF_FLAT、HNSW、IVF_PQ、FLAT 怎么选？

**【简历事实版答案】**

- **FLAT**：精确但规模大时慢，适合小数据或做基准；
- **IVF**：先聚类再搜部分桶，靠 nprobe 平衡速度和召回；
- **HNSW**：图索引，召回高、查询快，但内存和构建成本更高（知识平台用 HNSW，参数 M/efSearch 调召回与速度）；
- **IVF_PQ**：压缩换内存和精度。

选择依据：数据量、内存、写入频率、目标 Recall 和 QPS。先用 FLAT/高精度配置建立 baseline，再压测调参。

### 问题：BERT 为什么不直接替代 BGE？

**【简历事实版答案】**

BERT 是通用语言表征模型，原始训练目标（MLM）不等于检索相似度；BGE 等 embedding 模型在 query-passage **对比学习**上优化，且对 query 指令、向量归一化有特定要求。不是 BERT 完全不能用，而是默认检索效果和工程约定通常不如专门检索模型——**必须以项目评测验证**。

---

## 4. 数据库与权限补充

### 问题：Milvus 只存向量吗，原文在哪里？

**【简历事实版答案】**

Milvus 可以存短文本和 metadata，但**原始文件、长正文、图片放对象存储或关系库**（我知识平台：PG 管文档元数据、对象存储管原文件）。Milvus 保留检索需要的向量、chunk 文本/摘要、doc_id、页码和权限字段。索引轻、原文可版本化，检索后再按 source_uri 回溯。

### 问题：多租户如何防止越权召回？

**【简历事实版答案】**

文档/chunk 写入时绑定 tenant_id、kb_id、role/ACL；请求先认证，再把可访问范围作为 **metadata filter 与向量检索同时执行**。**不能先全库召回再让 LLM 忽略越权结果**；日志中不记录明文敏感上下文（呼应知识平台权限设计原则）。

---

## 5. 检索与融合补充

### 问题：BM25 与 embedding 各自缺点是什么？

**【简历事实版答案】**

- **BM25**：依赖词项匹配，口语表达和同义改写时容易漏；
- **embedding**：擅长语义，但对编号、版本、专有缩写可能不够精确。

混合检索并行召回取长补短（我知识平台 BGE-M3 向量 + BM25），再用 RRF 或归一化加权融合；权重根据离线集调，不凭感觉固定。

### 问题：Query 改写怎么避免语义漂移？

**【简历事实版答案】**

只补全指代、规范化术语、拆分复合问题，**不改变用户约束**；改写 prompt 明确要求保留时间、数量、否定条件和实体。保留原 query 与改写 query 并行/回退检索，记录改写结果；低置信或高风险问题先澄清而不是擅自扩写（我知识平台：改写结果结构化 + 低置信只用高置信字段过滤）。

### 问题：topK、topN 怎么确定？

**【简历事实版答案】**

topK 是粗召回候选数，取决于索引召回质量和 rerank 成本（我取 50~100）；topN 是给 LLM 的上下文数，取决于上下文预算和信息密度（我取 3~5）。用 Recall@K 找到"正确文档开始饱和"的候选区间，再用答案质量和时延决定 topN；不同意图可用不同配置。

---

## 6. rerank 补充

### 问题：Cross-Encoder 为什么更准但更慢？

**【简历事实版答案】**

**双塔**分别编码 query 和 passage，可提前离线建库，查询时只算一次 query 向量；**Cross-Encoder** 把 query-passage 一起输入模型，能看到细粒度交互，因此相关性更准，但**每个候选都要跑一次模型**。它只用于小候选集的精排，不取代大规模向量召回（我链路：Top-100 粗召回 → BGE-Reranker 精排到 Top-5）。

### 问题：rerank 分数能直接当概率吗？

**【简历事实版答案】**

通常不能。不同模型的分数标度和温度不同，更多用于同一次候选集合内**排序**。若要跨模型/跨请求使用阈值，需要在验证集上校准；不能把某个分数天然解释成"80% 正确"（我精排只用于排序 + 低分过滤，不做绝对阈值）。

---

## 7. 路由、多轮与记忆补充

### 问题：短问题"查一下这个"怎么办？

**【简历事实版答案】**

先结合最近对话、当前知识库和已知对象补全；仍无法确定时提出最小澄清问题（"请问要查询哪份文档或哪个产品？"）。不能默认检索全库并生成看似合理的答案（呼应订单 Agent"缺信息先问清/查全，不硬来"）。

### 问题：历史信息冲突时以谁为准？

**【简历事实版答案】**

当前用户明确输入优先于历史摘要；业务数据库/权威文档优先于模型记忆；冲突若影响结论，展示来源差异或要求确认。上下文中标注时间和来源，避免旧版本规则覆盖新版本（知识平台 metadata 带版本号）。

---

## 8. 安全、性能、部署补充

### 问题：如何判断幻觉在召回还是生成？

**【简历事实版答案】**

先检查正确证据是否被召回；再检查是否被 rerank 和 context builder 丢弃；若证据已在 prompt 但答案仍违背，才是生成/提示约束问题。**每次请求保存 query、候选、最终 context、模型输出和引用**才能定位（我知识平台失败的样本分析就是这么做的）。

### 问题：提示词注入怎么防？

**【简历事实版答案】**

外部文档视为不可信数据而非系统指令；系统提示与检索内容分区；工具权限由服务端校验，不由模型文本决定；敏感操作二次确认；输入输出做安全检测和审计。仅靠"忽略注入"提示词不够（呼应售后 Agent 的高风险操作人工确认）。

### 问题：Docker 与线上排查顺序？

**【简历事实版答案】**

先用 trace_id 对齐请求、应用和依赖日志，再检查容器状态/资源、环境变量、镜像与依赖版本、挂载文件、网络/DNS、模型服务和数据库连接。把配置外置且版本化，避免本地环境变量掩盖线上差异。

# 第二部分：多 Agent 高频面试题（答案已按简历填充）

## 一、项目主线

### 问题：什么是 Multi-Agent？为什么不用单 Agent？

**【简历事实版答案】**

Multi-Agent 不是让多个模型自由聊天，而是把复杂任务拆成**职责明确、输入输出稳定**的协作单元。单 Agent 在工具多、权限不同、任务链长时容易 prompt 膨胀、工具选择不稳定、状态难排查。

我**电商多智能体运营系统**的拆分理由（对比订单单 Agent 项目）：
- **业务域天然隔离**：商品审核、售后、营销导购各自有独立知识库、工具、规则和流程，放一个 Agent 会让工具集互相干扰（工具太多 LLM 选错率上升）；
- **独立演进**：售后改工具不影响审核；各 Agent 可独立优化、评测、灰度；
- **可并行 + 可扩展**：新增业务域 = 新增一个 Agent 接入 Orchestrator。

拆分标准不是"模型越多越好"，而是**任务边界、权限边界、依赖关系和可观测性**。简单任务（订单处理）仍然用单 Agent 或固定 workflow（我订单项目就是单 Agent 节点编排）。

### 问题：Agent 和 Workflow 有什么区别？

**【简历事实版答案】**

Workflow 路径固定，输入满足条件就走预定义节点；Agent 有在受约束范围内规划、选工具或决定下一步的能力。

我两个项目正好是两者的结合：**确定性高的流程（校验、权限、审批、订单处理主链路）走 workflow/固定节点**；**需要在工具间选择的环节（售后该调哪个工具、审核该查哪条规则）才使用 Agent**。这样可控性、成本和可测试性更好——电商系统里 Orchestrator 是 workflow 式的调度骨架，各 Agent 内部是受约束的 Agent 决策。

---

## 二、场景设计

### 问题：面对抽象指令，Agent 如何执行？

**【简历事实版答案】**

先抽取**目标、对象、约束和风险等级**。信息不足时提出最少必要澄清问题；低风险任务可以根据明确假设执行并回显假设，高风险操作必须确认（呼应订单 Agent"缺订单号先追问/查最近订单，不硬来"）。之后生成受 schema 约束的计划，逐步调用白名单工具，记录每步结果；失败时只对可重试错误重试，其他返回可解释原因或转人工。

### 问题：设计售后 Agent 怎么做？

**【简历事实版答案】**

按我售后 Agent 的实际链路：**用户识别与鉴权 → 客户/订单/物流结构化查询 → FAQ/RAG 查询 → 规则判断是否可自动处理 → 执行或创建工单 → 返回带依据的结果**。订单退款、地址变更等有副作用操作**必须经过权限、参数校验和用户二次确认**；模型只负责理解和编排，真正执行由受控服务完成（MCP 工具 + Pydantic 校验 + 人工确认节点）。

### 问题：生产级多 Agent 系统需要补什么？

**【简历事实版答案】**

除功能外还需要：**统一身份与权限、任务与状态持久化（Checkpointer）、幂等、超时重试熔断、可观测 trace、评测与回归集、限流、灰度、审计和灾备**。上线前先压测工具依赖与模型服务，明确每类错误的降级路径（我电商项目：路由 2000 样本评测 + TTFT/失败率压测 + 兜底机制）。薪资不是分层标准，是否需要这些能力取决于岗位是否负责生产可靠性。

### 问题：几千个 API 怎么组织？

**【简历事实版答案】**

不能把几千个 API 全部直接暴露给模型。按业务域建立**工具目录和能力摘要**，由路由层先缩小候选域；每个域内再根据 schema、权限、风险和上下文选择工具。工具要有稳定名称、参数 schema、幂等性、权限和审计信息；新增 API 通过**注册、测试和评估**进入目录，而不是只改 prompt（我售后 Agent 通过 MCP 注册业务工具，动态发现、标准化接入）。

---

## 三、主 Agent：意图与路由

### 问题：主 Agent 做什么？如何路由？

**【简历事实版答案】**

主 Agent（Orchestrator）负责：**输入安全检查、意图识别、关键信息补全、任务计划、路由、结果聚合和异常处理**。我的实现：路由先用规则、权限和工具可用性过滤，再用 **LLM + few-shot** 在候选中选择意图（输出 intent + entities + confidence）；低置信度进入澄清或人工兜底。主 Agent **不应默认拥有所有业务工具**，尤其不直接绕过权限执行高风险操作（写操作归口领域 Agent + 人工确认）。

### 问题：意图识别错了怎么办？

**【简历事实版答案】**

识别结果带**置信度和候选意图**。执行前校验槽位与权限；执行后用工具返回和结果校验发现明显不一致时，允许**有限次数重新路由**（我：重路由计数上限，超限转人工）。记录错误样本更新规则或评测集——路由准确率 73%→90%+ 就是靠"错误样本回流 + 每轮 few-shot 迭代"（2000 条标注集）。

---

## 四、槽位识别

### 问题：槽位如何抽取，缺失怎么办？

**【简历事实版答案】**

按意图定义 schema，例如查询订单需要订单号、用户身份和时间范围。规则适合日期、编号等稳定格式；模型处理自然语言实体；**schema 校验必填、类型、枚举和范围**（Pydantic）。

缺少关键槽位时**澄清追问**，非关键槽位使用明确默认值并回显。历史槽位只能在**同一任务和未冲突时**复用（订单 Agent：缺订单号先查最近订单并确认，不直接执行）。

---

## 五、任务 schema 与路由

### 问题：任务分发数据怎么设计？

**【简历事实版答案】**

至少包括 `task_id、session_id、trace_id、user_id、intent、slots、target_agents、dependencies、execution_mode、timeout、retry_policy、fallback_policy`。所有 Agent 的输入、输出和错误都要 **schema 校验**（我电商项目用 Pydantic 定义 State Schema，统一字段规范）；模型生成 JSON 后使用解析器和业务校验，不合法就纠正或进入兜底，**不能直接执行**。

---

## 六、子 Agent 设计

### 问题：子 Agent 如何划分、如何通信？

**【简历事实版答案】**

按**稳定业务能力**拆分，不按模型名称拆分。我电商项目：商品审核 Agent 只负责"商品查询 + 审核规则检索 + 审核结论"；售后 Agent 只负责"客户/订单/物流查询 + 售后处置工具 + 人工确认"；营销导购 Agent 独立。每个 Agent 有明确 input/output、最小工具权限和结果命名空间（State 里 `collected` 子键隔离）。

通信采用**共享状态（State）**为主：Orchestrator 通过 State 字段分发与回收，消息带 task_id、source、target、trace_id、版本和错误语义。

---

## 七、串行、并行与异步

### 问题：什么时候串行、并行、异步？

**【简历事实版答案】**

**有数据依赖串行**：先鉴权/意图识别再路由、先查订单再判断售后；**互相独立并行**：售后同时查订单 + 物流 + 客户（`asyncio.gather`，TTFT -30% 的核心）；**耗时且不要求实时返回异步**：批量任务、离线报告。

并行结果要定义**聚合规则、超时和部分成功策略**（all-success / partial-success / fail-fast）；异步任务用 task_id 持久化状态，用户可轮询或订阅进度。

---

## 八、Plan-and-Execute

### 问题：计划由 LLM 生成可靠吗？

**【简历事实版答案】**

不完全可靠。计划必须限制在**白名单 Agent/工具和 schema 内**，校验依赖、权限、参数和预算。简单任务不必规划；复杂任务生成分步计划。执行中**只有在新工具结果改变前提时才允许 replan**，并限制最大步骤与总耗时（我订单 Agent：replan 计数上限，超限转人工），避免反复规划。

---

## 九、异常与兜底

### 问题：子 Agent 或工具失败怎么办？

**【简历事实版答案】**

先按错误类型分流：**参数/权限错误不重试**；网络超时可有限重试（退避）；依赖持续故障走备用工具或降级；高风险动作失败要停止并告知。错误结果**结构化返回**：错误码、可重试性、已完成步骤和建议。

**对有副作用动作用幂等键**，避免重试导致重复扣款、重复发消息或重复建工单（订单 Agent 写操作不盲目重试，先查状态再决定）。

---

## 十、超时、重试、熔断与死循环

### 问题：如何防止死循环？

**【简历事实版答案】**

限制**总步骤数、单 Agent 重试数和总时限**（State 里 step_count / retry_count）；记录 `visited_agents` 及**相同 action+input 的重复调用**（同工具同参数 hash 出现 ≥N 次即停，这是无效工具调用率 -25% 的手段之一）；工具连续失败时熔断；无有效进展时进入澄清、降级或人工节点。重试采用按错误类型的策略和指数退避，**不是对任何错误反复调用**。

---

## 十一、Checkpoint 与恢复

### 问题：Checkpoint 保存什么，怎么防止重复执行？

**【简历事实版答案】**

保存 task/session、**当前节点、已完成与待执行节点、结构化 state、中间结果、重试次数、错误和更新时间**。服务中断后从最近成功节点恢复（我电商项目：Pydantic State Schema + Checkpointer，State 序列化存 Redis，节点位置 + 快照）。

**防重复执行**：写数据库、通知、支付等副作用节点必须用**幂等键或事务外盒**，不能只依赖"节点已经执行过"的内存标记（订单 Agent 写操作带 request_id，重试时先查是否已生效）。

---

## 十二至十五、上下文与状态

### 问题：上下文如何管理、防止污染？

**【简历事实版答案】**

区分用户原始输入、近期对话摘要、任务 state、工具结果和外部知识。进入模型前**按当前任务和权限筛选**，不把全量日志或原始大文档塞给模型。

我电商项目的做法：
- 按 task_id 隔离状态，每个 Agent **只读必要字段、只写自己的 result namespace**（State 里 `collected` 子键隔离，防止售后污染审核）；
- 并行写入用 reducer/版本控制或明确合并规则（消息字段用 `add_messages` 追加，普通字段覆盖）；
- 长历史采用滑动窗口、摘要和按需检索，大文本只存引用（原文进 PG/对象存储）。

---

## 十六、协同与 A2A

### 问题：Agent 怎么知道何时调用另一个 Agent？A2A 如何做？

**【简历事实版答案】**

优先由**主 Agent（Orchestrator）根据路由或计划依赖统一调度**，不建议让子 Agent 无边界互调——我电商项目就是 Orchestrator 统一分发，子 Agent 不直接互调，避免权限、依赖和循环失控。

若用 A2A 或自定义协议，消息需要定义任务身份、目标能力、输入、上下文引用、权限、超时、trace 和回调/结果 schema；通信层还要鉴权、幂等、限流和审计。注意：**A2A 是协作通信方式，ReAct 是单 Agent 的推理—行动范式，二者不在同一层**。

---

## 十七、工具层

### 问题：LangChain、LangGraph、MCP、Function Calling、Skill 的区别？

**【简历事实版答案】**

- **LangChain**：模型、prompt、retriever、tool 等应用组件库；
- **LangGraph**：用状态图管理复杂分支、循环和 checkpoint（我两项目都用它做编排骨架）；
- **Function Calling**：模型按 schema 选择和填写函数参数（工具调用机制）；
- **MCP**：外部工具/资源的标准化接入协议（我售后 Agent 用它封装订单/物流/客户工具）；
- **Skill**：固定任务的能力与操作规范封装。

它们可以组合（MCP 工具可适配成 LangChain Tool 供 LangGraph 节点调用），但**不能把 MCP 说成插件、把 Skill 说成单纯提示词**。

---

## 十八、Agent + RAG

### 问题：RAG 在 Agent 中如何定位？

**【简历事实版答案】**

RAG 是一种**受控能力**：知识、制度、文档依据类问题调用 RAG；结构化实时数据调用 SQL/查询工具；有副作用操作调用 Tool Agent（我订单 Agent 就是：知识检索给决策依据，业务工具做执行，分层不混）。

RAG Agent（检索模块）应返回**召回片段、来源、置信度和摘要**，不直接把未经审查的大段文本当最终答案（我知识平台 Retrieval API 返回片段 + 标题/章节/页码来源）。召回为空时先改写/澄清或明确无依据，**不能让模型自由编造**。

---

## 十九、聚合与审查

### 问题：多个 Agent 结果冲突怎么办？

**【简历事实版答案】**

先按**数据源权威性、时效、权限和置信度**排序（业务库 > 知识库 > 模型记忆）；若关键事实冲突，展示差异、请求补充或转人工，而不是让 LLM 随机选一个。聚合后做 schema、事实引用、安全和格式校验。审查 Agent 也只是防线之一，**不能替代权限与业务规则**（高风险规则必须由确定性服务校验）。

---

## 二十、流式输出

### 问题：用户刷新后如何继续输出？

**【简历事实版答案】**

不要把任务生命周期绑定单个浏览器连接。服务端以 **task_id 保存执行状态和已生成内容**；前端重连时携带 task_id，从已确认位置续传或返回最终结果。

对内部多 Agent：**聚合到可解释的阶段再对外流式**，不把未经审查的内部推理直接暴露给用户（避免"模型审模型"的草稿泄漏）；已发送内容可追踪版本，必要时追加更正而不是静默覆盖。

---

## 二十一、评估

### 问题：如何评估 Agent 效果？

**【简历事实版答案】**

按层评估（我电商项目的分层评测方案）：

| 层 | 指标 | 简历数据 |
|---|---|---|
| 意图/路由 | 意图识别准确率、路由准确率 | 73%→90%+（2000 样本） |
| 槽位 | 槽位正确率 | 参数抽取校验 |
| 工具 | 工具调用成功率、无效调用率 | 无效调用 -25% |
| 检索 | Recall@K、Context Precision | 78%→91%（2000 查询集） |
| 生成 | RAGAS、LLM-as-Judge | 回答忠实/相关 |
| 端到端 | 任务完成率、人工介入率 | 成功率 +18%、介入率 -30% |
| 性能 | 平均/P95 时延、TTFT、超时率 | TTFT -30%、失败率 -25% |

评测集覆盖正常、模糊、越权、工具失败和多步骤任务；**每次改 prompt、工具或模型后做回归**（2000 条标注集 + 错误样本回流），而不是只看几个 demo。

## 二十二至二十五、连问与复习

一套项目回答顺序：**业务目标与为何多 Agent → Agent 边界和工具权限 → 主 Agent 路由与 state → 串并行/异步计划 → 异常、幂等、恢复与可观测 → 聚合与评估**。基础岗位先掌握这条主线、一个真实工具调用和一个真实失败案例；再深入 checkpoint、熔断、上下文压缩、A2A 与生产架构。**任何指标均说明统计口径、样本量（2000 条）和时间范围**。

# 多 Agent 逐题补全答案（技术题）

## 1. 选型与项目边界

### 问题：项目里有几个 Agent，如何分工？

**【简历事实版答案】**

以电商多智能体项目给出真实清单：
- **主 Agent（Orchestrator）**：只负责意图识别、路由、计划和聚合，默认没有业务工具；
- **商品审核 Agent**：商品信息查询（业务工具）+ 审核规则 RAG（BM25 混合检索 + 精排）+ 结构化审核结论（通过/驳回 + 理由 + 依据）；
- **售后 Agent**：客户/订单/物流查询 + 售后处置工具（MCP 封装）+ 高风险操作人工确认；
- **营销导购/客服 Agent**：商品推荐、常规咨询。

每个 Agent 说明输入、输出、工具权限和失败结果（审核失败 → 人工复核；售后失败 → 转人工坐席），不能说"一个负责检索、一个负责工具"这么含糊。

### 问题：Agent 和 Coze/Dify 有什么区别？

**【简历事实版答案】**

Coze/Dify 是应用搭建或工作流平台，能快速集成模型、知识库和工具；Agent 是任务理解、决策和工具调用的能力形态。面试重点不是贬低平台，而是说明我**在平台外做了什么**：工具 schema、路由规则（Orchestrator + 意图识别）、权限与状态管理（Pydantic State + Checkpointer）、评测闭环（路由/检索/生成分层指标）。若项目用低代码搭建，也要诚实说明其边界。

---

## 2. 路由与槽位补充

### 问题：规则路由和 LLM 路由冲突怎么办？

**【简历事实版答案】**

**安全、权限、精确业务规则优先级高于 LLM**：先用规则把不可执行和无权限候选排除，再让 LLM 在合法候选中分类（我：规则关键词兜底 + LLM few-shot 路由，规则优先）。冲突时记录两者结果和置信度，低置信进入澄清/人工；**不要让模型覆盖硬性风控规则**。

### 问题：target_agent 不存在、返回 JSON 不合法怎么办？

**【简历事实版答案】**

Agent 注册中心维护白名单与版本；分发前校验 target 是否存在、是否健康、调用方是否有权限。模型输出先经 **JSON parser、schema 和业务校验**（Pydantic）；失败可进行一次受约束修复或走固定 fallback（兜底通用 Agent），**不能把不合法 JSON 直接当指令执行**。

### 问题：槽位和意图谁先做？

**【简历事实版答案】**

通常**先粗识别意图**以确定所需 schema，再抽槽并校验；对多意图输入可联合抽取候选意图和槽位。关键不是固定顺序，而是**不同意图必须有各自的必填字段**，且缺失关键槽位时不能盲目执行（订单 Agent：缺订单号先追问/查最近订单确认）。

---

## 3. Agent 通信与状态补充

### 问题：全局 state 和局部 state 怎么划分？

**【简历事实版答案】**

**全局 state** 只放任务级信息：task_id、用户身份、权限、意图、计划、节点状态和结果引用；**局部 state** 放某 Agent 的候选、临时变量、工具原始返回（我：`collected` 子键按 Agent 隔离）。大文本、文件和完整日志放外部存储（PG/对象存储），state 只存 URI/摘要。并行 Agent 写不同 namespace，由 reducer 或聚合节点合并，避免覆盖（消息用 `add_messages` 追加）。

### 问题：子 Agent 是否允许再调用子 Agent？

**【简历事实版答案】**

默认不允许或严格白名单。自由互调会让权限、依赖和循环难以控制。我电商项目由 Orchestrator 统一调度，子 Agent 不互调。若确实需要（如审核 Agent 调用事实校验），应在**计划中显式定义调用边、最大深度、预算和回传 schema**，并由统一 trace 记录。

---

## 4. 执行模型补充

### 问题：并行结果如何合并？某个慢节点怎么办？

**【简历事实版答案】**

先定义 **all-success、partial-success、fail-fast** 三种策略。独立的非关键查询可设置 deadline，到期返回已完成结果并声明缺失（售后同时查订单/物流，先回已到的）；关键节点失败则停止下游或走备用路径。聚合时按来源、时间、置信度和 schema 合并，**而不是把多段自然语言直接拼接**（统一 JSON 结构）。

### 问题：异步任务怎么通知用户、刷新如何恢复？

**【简历事实版答案】**

创建任务后立即返回 task_id 和初始状态；状态与结果写入持久化存储（Redis 会话 + PG 处理记录），前端可轮询、SSE 或 WebSocket 订阅。用户刷新后用 task_id 重连并从已确认序号续传；任务完成后返回最终产物。设置过期、取消和权限校验，**防止他人凭 task_id 读取结果**。

---

## 5. 计划、失败与可靠性补充

### 问题：什么时候允许 replan？

**【简历事实版答案】**

只有**工具结果显示原计划前提不成立、候选资源不可用或用户补充关键约束**时才允许；replan 继承已完成步骤和预算，**不能重复执行有副作用动作**。限制最大重规划次数（我订单 Agent：replan 计数上限）；持续失败时转人工或返回部分结果。

### 问题：熔断、超时、重试怎么设置？

**【简历事实版答案】**

超时按**工具、Agent 和整任务分层设置**；网络抖动、限流等瞬时错误可指数退避重试，参数/权限/业务校验错误不重试；连续失败超过阈值熔断，半开状态探测恢复。熔断后主 Agent 走备用模型、降级 FAQ/规则或提示稍后重试。阈值由历史时延和错误率配置，**不是随意写死**（电商项目：TTFT -30%、失败率 -25% 靠这套分层策略）。

## 6. Checkpoint、上下文与污染补充

### 问题：Checkpoint 和日志区别是什么？

**【简历事实版答案】**

**Checkpoint** 是可恢复的结构化任务快照（当前节点、已完成步骤、中间结果引用、重试状态）；**日志**是用于诊断的执行记录。恢复依赖 checkpoint，排障依赖日志和 trace；二者都要有版本、保留周期和敏感信息脱敏（我电商项目：State 快照存 Redis 恢复用，工具调用轨迹 + 审批记录落库审计用）。

### 问题：如何防止上下文污染？

**【简历事实版答案】**

按 task_id/session 隔离；当前用户输入优先；工具结果通过 schema 和来源校验后才进入 prompt；**失败工具输出不作为事实**；切换话题时创建新任务状态；对检索文本施加权限和不可信内容标识。上下文摘要必须包含时间和来源，避免旧结论覆盖新事实（呼应知识平台版本号机制）。

## 7. 工具与 RAG 补充

### 问题：Function Calling 参数如何校验？

**【简历事实版答案】**

模型只产生候选参数，服务端通过 **JSON Schema、类型、枚举、长度、权限、业务规则和幂等键**校验（Pydantic）。查询类工具优先只读、参数化；写操作要展示动作摘要并让用户确认（售后 Agent 高风险操作人工确认）。工具返回统一包含成功状态、数据、引用、错误码和可重试性（我 `{status, data, message}` 标准结构）。

### 问题：RAG Agent 的输出为何不能只是答案？

**【简历事实版答案】**

它至少应返回**片段、来源、页码/文档、置信度和检索状态**，供主 Agent 判断是否足以回答和向用户展示引用（我知识平台 Retrieval API 就是这么设计的）。召回为空、低置信或来源互相冲突时，主 Agent 应澄清或拒答，**而不是把一个无依据的自然语言答案向后传递**（否则幻觉会扩散到整个 Agent 链路）。

## 8. 聚合、流式与评估补充

### 问题：审查 Agent 是否一定可靠？

**【简历事实版答案】**

不是。它只能增加一层模型/规则检查，**不能替代权限控制、参数校验和权威数据源**。高风险规则必须由确定性服务校验；审查结果也要带理由/来源并纳入评测，避免"模型审模型"的循环自信（审核 Agent 的结论仍要人工复核高风险样本）。

### 问题：多 Agent 流式输出如何避免半截错误？

**【简历事实版答案】**

内部节点先产生**结构化中间结果**，只有达到可展示阶段才向用户流式输出。若后续关键节点失败，明确标注已完成范围和失败原因，不把未经审查的草稿当最终结论。已发送内容可追踪版本，必要时追加更正而不是静默覆盖。

### 问题：Agent 指标如何算？

**【简历事实版答案】**

- **路由准确率**：以标注意图/目标 Agent 为真值（2000 条，73%→90%+）；
- **工具成功率**：区分调用成功、业务成功和用户成功；
- **端到端任务完成率**：定义完成条件（任务成功率 +18%）；
- **时延**：平均、P95、TTFT、超时率（TTFT -30%）；
- **高风险任务**：越权拦截率、错误执行率、人工介入率（介入率 -30%）。

每个指标明确样本范围和失败归因。

> 面试官常把两份题库交叉追问，以下是对接口径：

|---|---|
| RAG 检索质量怎么支撑 Agent 决策？ | 订单 Agent 的知识检索（BGE-M3+ES）给决策依据；审核 Agent 的规则 RAG（混合+精排）给审核依据——检索质量（Recall@5 91%）直接决定 Agent 回答是否可信 |
| Agent 里的检索失败/空召回怎么办？ | 先改写/澄清/降级，不能让模型自由编造（RAG Agent 返回置信度 + 检索状态，主 Agent 判断） |
