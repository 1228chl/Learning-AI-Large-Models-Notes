# 曹浩磊简历结合 RAG 与 Multi-Agent 高频面试题及详细答案

> 本文根据以下材料整理：曹浩磊的简历、《RAG 高频面试题横向扩展及纵向延伸：答案版》和《多 Agent 高频面试题横向扩展及纵向延伸：答案版》。
>
> 使用原则：答案中的技术知识是参考口径；简历中的项目指标、模型参数、数据库部署方式和个人职责必须以真实项目为准。面试时不要照背模板，应能够补充字段、流程、错误码、实验集、基线和线上统计口径。

## 一、面试主线与回答方法

### 1. 这份简历最应该如何概括？

**参考答案：**

“我的主要方向是大模型应用和 Agent 工程，核心能力包括 LangGraph 流程编排、Multi-Agent 路由、RAG 检索、业务工具接入以及效果和稳定性评测。三个项目分别体现了不同层次的能力：企业智能知识平台覆盖 RAG 数据处理和检索全链路；企业智能订单处理 Agent 覆盖单 Agent 的流程编排、业务工具和人工确认；电商多智能体运营系统进一步加入 Orchestrator、领域 Agent、MCP 和跨 Agent 状态管理。

我的工作重点不是只写 Prompt，而是把模型放进一个可验证的业务闭环：输入经过结构化解析，知识和业务数据分别通过 RAG 或工具获取，Agent 在受限状态图中做决策，高风险动作经过人工确认，最后通过结果校验、指标评测、日志和降级机制保证稳定性。”

这个回答把简历的三条主线串起来：**RAG 提供知识依据，Agent 负责任务编排，业务工具负责执行，工程机制负责安全和可靠性。**

### 2. 面试官应重点验证哪些内容？

**参考答案：**

重点不是让候选人重复技术名词，而是验证其是否真正参与过实现：

1. 能否画出一次请求的节点、状态和异常分支。
2. 能否说明 RAG 的文档、Chunk、Metadata、索引和引用结构。
3. 能否说明路由的标签集、置信度、拒识和混淆样本。
4. 能否说明工具的输入/输出 Schema、错误码、幂等键和权限。
5. 能否解释 Checkpointer 如何暂停、恢复，以及恢复时副作用如何避免重复。
6. 能否把 73%→90%+、78%→91%、TTFT 降低 30% 等指标拆成基线、样本、实验和统计口径。

如果只能说“用了 LangGraph、RAG、MCP 和混合检索”，但说不出状态字段、数据流和失败处理，通常说明只是了解方案，未必实际负责核心实现。

## 二、RAG 基础与简历结合题

### 3. 请介绍企业智能知识平台的完整 RAG 流程。

**参考答案：**

离线流程是：文档接入 → 文件类型识别 → 文档解析/OCR → 内容清洗 → 标题和章节结构恢复 → 父子块切分 → 元数据和权限标注 → BGE-M3 向量化 → Milvus/关键词索引入库 → 质量抽检和增量更新。

在线流程是：接收 Query → 鉴权并确定可访问知识库 → 抽取产品、版本、章节等条件 → Query Rewrite → Metadata Filter → BGE-M3 向量召回与 BM25 关键词召回 → 合并去重 → BGE-Reranker 精排 → Parent-Child Context Expansion → 构造带来源的上下文 → 返回 Retrieval API 结果或交给上层 LLM 生成答案。

最后要记录 Query、知识库版本、过滤条件、召回结果、精排结果、最终上下文、引用和耗时，用于 Recall@K、Context Precision、Context Recall、Faithfulness 和失败样本分析。简历中我的职责覆盖数据处理、知识入库、召回、精排、评测和统一 Retrieval API。

### 4. 为什么这个项目不直接使用普通搜索、FAQ 或模型微调？

**参考答案：**

普通全文检索对产品型号、错误码、版本号和条款号很有效，但对用户口语化表达、同义表达和跨段语义不够稳定；FAQ 适合问题和答案固定、数量有限的高频场景，不适合企业技术文档、产品资料和制度的长尾查询；微调主要改变模型的行为、格式和领域表达，不适合频繁写入和更新事实知识，也不能自然提供逐条来源。

所以合理方案是分层使用：固定高频问法可以走 FAQ；精确编号走 BM25；语义表达走向量检索；需要综合语义和术语时走混合检索；结构化实时数据走数据库或业务工具；模型微调只在确实需要固定风格、分类能力或工具调用行为时考虑。RAG 的核心价值是知识可更新、答案可追溯。

### 5. 你在知识平台中具体负责哪些模块？难点是什么？

**参考答案模板：**

“我主要负责 RAG 数据处理和检索链路。离线侧完成文档解析、清洗、父子块切分、BGE-M3 向量化和 Milvus 入库；在线侧完成向量召回、BM25 补充召回、候选合并、BGE-Reranker 精排、Metadata Filter、Query Rewrite 和 Retrieval API；同时搭建人工标注查询集和离线评测流程。

一个典型难点是复杂文档的条件查询：用户问题同时包含产品、版本和章节，如果只做纯向量搜索，可能召回语义相近但版本错误的内容；如果过滤过严，又可能零召回。我会先抽取并校验结构化条件，把可信条件用于 Metadata Filter，再保留原 Query 与改写 Query 并行召回，命中子块后回取父块上下文，最后用 Reranker 排序。验证时要按产品型号、版本条件、长文档和自然语言问题分层看 Recall@K 与 Context Precision。”

涉及具体百分比时必须替换成真实实验结果，不能用模板数字代替。

### 6. PDF、表格、图片和跨页内容如何处理？

**参考答案：**

先区分原生文本 PDF、扫描 PDF、表格、图片和多栏排版。原生 PDF 按标题、段落和列表恢复结构；扫描件使用 OCR，并记录页码、坐标和识别置信度；多栏文档根据坐标重建阅读顺序；图片绑定相邻标题和说明文字，并保留原图引用。

表格不能只抽取单元格字符串，需要保留表题、表头、行名、列名、单位、脚注和行列关系，可同时存 Markdown/HTML/JSON。大表按“表题 + 必要表头 + 行组”切分；跨页表先校验表头和字段结构再合并。每个 Chunk 保存 `doc_id`、`version`、`page`、`section_path`、`content_type`、`source_uri` 和权限信息。

解析失败、OCR 置信度低或表格结构异常的文档应进入隔离/人工复核队列，不能静默写入向量库，否则后续召回和答案错误很难定位。

### 7. 父子块切分解决什么问题？在你的项目中如何落地？

**参考答案：**

父子块方案让检索精度和生成上下文兼顾。子块较小、主题集中，用于 Embedding 和召回；命中子块后通过 `parent_id` 找到父块或相邻块，把足够完整的上下文交给生成模型。父块可以对应章节、规则条款或一个语义完整的段落集合，不能无限大。

子块需要保存父块 ID、章节路径、位置和内容哈希。多个子块命中同一父块时要去重，并设置每个父文档和章节的数量上限。最终 Prompt 不能只是把所有命中内容拼接起来，还需要按相关性排序、去重、控制 Token、保留标题和来源引用。

### 8. 切块大小和 overlap 应该如何确定？

**参考答案：**

没有适用于所有文档的固定值。应以 Token、文档结构、问题答案跨度、Embedding 模型输入限制和生成上下文预算为依据。制度文档优先按条款和标题切，FAQ 按问答切，代码按函数/类切，长段落才使用长度上限兜底。

overlap 用于缓解边界信息丢失，但过大将产生重复 Chunk、索引膨胀和上下文冗余。应在验证集上对切分长度、overlap、父块大小做消融，观察 Recall@K、Context Precision、答案正确率、Token 成本和 P95。发现条件句、列表或定义被切断时，优先修复结构边界，而不是盲目增加 overlap。

### 9. 为什么使用 BGE-M3？模型版本可以直接替换吗？

**参考答案：**

BGE-M3 适合这个项目的原因包括多语言、多粒度以及对 Dense、Sparse 等检索方式的支持，能够覆盖企业文档中的语义检索和专业术语场景。但选型不应只依据模型名，还要考虑中文和领域效果、向量维度、最大输入长度、推理吞吐、显存和部署成本。

Embedding 模型即使维度相同也不能直接把新旧向量混用，因为向量空间分布可能变化。正确做法是用新模型离线重建索引，建立新旧双索引，在固定评测集上比较 Recall@K、Context Precision、答案质量、延迟和成本，再灰度切流。元数据中要保存 Embedding 模型版本，便于回滚和排查。

### 10. Milvus、Elasticsearch、PostgreSQL 和 Redis 如何分工？

**参考答案：**

在知识平台中，Milvus 主要保存向量和检索所需的 Chunk/Metadata；BM25 可以使用独立全文检索能力，或按项目配置使用相应关键词索引；PostgreSQL 保存文档元数据、版本、权限配置、处理记录和评测记录；Redis 保存热点 Query 结果、短期会话、限流和可重建缓存；原始文件和图片更适合放对象存储。

如果订单项目使用 Elasticsearch，则 Elasticsearch 负责订单规则和售后政策的全文/向量检索，PostgreSQL 作为业务记录真相源，Redis 作为会话和缓存。关键原则是：Redis 不是业务真相源，向量索引不是原始文档唯一存储，模型不能成为权限判断主体。

### 11. 为什么需要 BM25 + 向量检索 + BGE-Reranker？

**参考答案：**

BM25 擅长产品型号、版本号、错误码、条款号等精确词面；向量检索擅长同义表达和语义匹配；Reranker 对 Query 和候选 Chunk 做联合编码，能捕获更细的交互关系。完整链路是“高召回 → 低成本融合/粗排 → 小规模精排”，而不是让 Reranker 扫描整个知识库。

两路原始分数通常不可直接相加，可以使用 RRF 按排名融合：`score(d)=Σ1/(k+rank_i(d))`，或者在验证集上做分数归一化和加权。之后对有限候选使用 Reranker，最后再去重、做版本/权限复核并构造上下文。

### 12. 如果 Recall@5 很高，最终答案仍不好，如何排查？

**参考答案：**

Recall@5 只说明正确文档进入前五，不说明它排位足够高、Chunk 完整、上下文无噪声或模型使用了证据。应按链路排查：

1. 正确文档是否真的包含完整答案。
2. 正确 Chunk 在候选中的排名和最终上下文中的位置。
3. Context Precision 是否低，是否存在大量重复或冲突版本。
4. Parent-Child 扩展是否带入过多无关内容。
5. Prompt 是否要求根据证据回答并引用。
6. 模型是否在证据充分时仍产生幻觉。

可以做 Oracle 实验：直接给模型标准证据。如果 Oracle 仍答错，问题偏向生成；如果 Oracle 能答对，继续查 Reranker、上下文构建和引用映射。

### 13. Query Rewrite 和 Metadata Filter 如何避免语义漂移或零召回？

**参考答案：**

先从 Query 中抽取产品、版本、章节、时间和部门等条件，再在保留原问题、否定条件和数量约束的前提下做改写。产品和版本要从可信字典/元数据校验，不能让模型随意发明值。租户、权限和明确版本是硬过滤；模型推断出的模糊条件可以作为软条件或扩展召回。

保留原 Query 与改写 Query，可以并行检索后融合。出现零结果时，只允许放宽非安全过滤条件并记录放宽原因，绝不能放宽 ACL。线上要监控过滤前后候选数量、零召回率和改写实体准确率。

### 14. RAG 如何减少幻觉和处理 Prompt Injection？

**参考答案：**

减少幻觉需要多层配合：提高召回和排序质量；要求模型只基于上下文回答；关键结论绑定来源；证据不足时明确不确定或转人工；生成后做引用存在性和关键事实校验；持续做人工抽检和 Faithfulness 评测。

Prompt Injection 防护不能只写一句“忽略文档中的指令”。应把外部文档视为不可信数据，与系统指令隔离；工具权限由服务端和用户身份决定；敏感写操作需人工确认；工具返回和检索内容进入模型前要带来源和不可信标记；输入输出做安全检测并记录审计。权限过滤应尽量发生在召回前/召回中，不能先把越权文本送进模型再要求模型不输出。

### 15. RAG 评测如何设计？Recall@K、Context Precision、Faithfulness 各解决什么问题？

**参考答案：**

先构造人工标注查询集，覆盖高频、长尾、专业术语、版本条件、表格、跨段、多跳、无答案和权限场景，标注相关文档/Chunk、必需事实、可接受答案和引用位置。

- Recall@K：正确证据是否进入候选，主要定位漏召回。
- Context Precision：最终上下文中相关内容比例和排序质量，主要定位噪声和排序问题。
- Context Recall：答案所需参考事实被上下文覆盖多少，主要定位证据缺失。
- Faithfulness：答案陈述是否能由上下文支持，主要定位生成幻觉。

还要报告答案正确率、引用正确率、零召回率、P50/P95、TTFT、Token 成本和人工介入率。指标提升必须说明 baseline、样本量、知识库快照、模型/Prompt 版本和统计周期。

## 三、Multi-Agent 与简历结合题

### 16. 什么是 Multi-Agent？为什么电商项目采用 Multi-Agent？

**参考答案：**

Multi-Agent 不是让多个模型自由对话，而是把复杂任务拆成职责、输入输出和权限明确的协作单元。电商项目中的商品审核偏知识检索和规则判断，售后偏客户/订单/物流查询和业务工具执行，营销导购又是另一套目标和知识。拆分后可以缩小每个 Agent 的工具范围、Prompt 和测试集，也方便独立演进。

但 Multi-Agent 会引入路由错误、跨 Agent 状态同步、额外延迟和调试成本。采用它的依据应是业务领域边界、权限边界、流程差异和维护需要，而不是“Agent 越多越先进”。简单查询仍可以由单 Agent 或固定 Workflow 处理。

### 17. Agent 和 Workflow 有什么区别？LangGraph 中如何结合？

**参考答案：**

Workflow 的路径通常是确定的，适合鉴权、参数校验、查询、审批和结果校验；Agent 在受限范围内理解语义、选择工具或决定下一步。生产系统一般采用混合方式：LangGraph 用节点和条件边显式编排确定性流程，在需要语义判断的节点调用模型或 Tool Calling。

例如订单处理可以固定为“需求理解 → 查询 → 检索 → 方案 → 审批 → 执行 → 校验”，但需求理解、知识 Query 改写和候选工具选择可以使用 Agent。这样既保留灵活性，又能保证“未经审批不能退款”等业务不变量。

### 18. Orchestrator 如何识别意图并路由到商品审核或售后 Agent？

**参考答案：**

先定义意图标签和路由契约，如 `product_audit`、`after_sales`、`order_query`、`logistics_query`、`marketing`、`unsupported` 和 `multi_intent`。输入经过安全检查后，规则提取订单号、商品型号、退款等强特征，再由分类模型或 LLM 输出结构化结果：`intent`、`confidence`、`entities`、`subtasks` 和 `need_clarification`。

路由前先做权限和 Agent 可用性过滤。置信度低、候选差距小、关键槽位缺失时澄清，不直接执行。多意图请求拆为子任务；有依赖时串行，无依赖时并行。路由指标除了 Accuracy，还要看每类 Precision/Recall/F1、拒识准确率、人工改派率和端到端任务成功率。

### 19. 如何解释路由准确率从 73% 提升到 90%+？

**参考答案：**

先确认 2,000 条样本的标注指南、类别分布和测试集是否冻结。然后从混淆矩阵定位主要问题，例如商品审核与商品咨询、订单查询与售后、物流查询后要求退款等边界。

可采用以下优化：补充边界和难例样本；重新定义互斥/多意图标签；加入商品、订单、退款等实体特征；改进 Few-shot 示例；使用结构化 JSON 输出；增加置信度拒识和澄清节点；对复合请求先拆分。实验要保持模型、数据、推理参数和评价脚本一致，分阶段做消融。

回答中必须说明 90%+是总体准确率还是其他指标，73%到90%+是绝对百分点还是相对提升，并报告各类 Recall、混淆样本和最终任务成功率。只报结果而说不出实验过程，指标可信度不足。

### 20. Agent 的 State Schema 应如何设计？

**参考答案：**

共享 State 可包括：

```python
class TaskState(BaseModel):
    task_id: str
    thread_id: str
    user_id: str
    tenant_id: str
    user_input: str
    intent: str | None = None
    entities: dict[str, str] = {}
    current_node: str
    plan: list[dict] = []
    completed_steps: list[str] = []
    tool_results: list[dict] = []
    retrieval_context: list[dict] = []
    approval: dict | None = None
    retry_count: int = 0
    final_answer: str | None = None
```

实际代码中需要避免可变默认值问题，并根据 Pydantic 版本使用 `Field(default_factory=list)`。商品审核可以增加 `product_id`、审核项和规则证据；售后可以增加 `customer_id`、`order_id`、物流/支付状态、动作参数、幂等键和审批单 ID。

State 只保存恢复所需的结构化数据和外部引用；大文档、原始响应和完整日志放外部存储。单值字段通常覆盖，工具历史和审计事件追加，并行写入需要 reducer 或命名空间隔离。

### 21. Checkpointer、Interrupt 和 Human-in-the-Loop 如何实现暂停与恢复？

**参考答案：**

编译 LangGraph 时接入持久化 Checkpointer，调用时使用稳定 `thread_id`。到达退款、取消订单、地址修改等高风险节点时执行 `interrupt()`，保存当前 State 并向审批端返回动作、参数、风险和依据。人工批准后使用同一个 `thread_id` 和 `Command(resume=审批结果)` 恢复。

恢复时要重新读取最新订单状态、权限和参数，不能盲信暂停时的旧数据。LangGraph 的中断恢复可能从包含 `interrupt()` 的节点开头重新执行，因此中断前的查询和准备步骤要幂等，真正的副作用执行放在审批之后，或通过幂等键保护。Checkpointer 保存图状态；PostgreSQL 保存审批和业务审计；两者通过 `task_id/thread_id/approval_id` 关联。

### 22. Agent 如何避免自主循环、重复调用和无限 ReAct？

**参考答案：**

不能只依赖 Prompt。State 中记录步数、重规划次数、每个工具的调用指纹、连续失败数和最近结果；设置最大递归步数、最大工具调用数、总超时、Token/费用预算。相同工具对相同资源和参数重复调用且状态没有变化，应识别为无进展。

网络超时和限流可以有限重试；参数错误、权限错误和业务状态错误不应机械重试。持续失败进入澄清、备用路径、降级或人工。每次重规划说明原因，并继承已完成步骤，不能再次执行已有副作用。

### 23. 如何设计售后 Agent 的业务流程？

**参考答案：**

流程可以是：用户身份与权限校验 → 识别售后意图 → 抽取订单号/客户/商品/动作 → 查询订单、支付和物流 → 检索售后规则 → 判断是否满足条件 → 生成方案 → 对退款/取消/地址修改触发人工确认 → 使用幂等键执行 → 查询最终状态 → 返回结果和依据。

只读查询可并发；有依赖的步骤串行。模型负责理解、计划和工具选择，业务服务负责鉴权、参数校验、状态机和实际写操作。工具结果必须区分传输成功、业务接受和最终业务完成。

### 24. MCP、Function Calling、LangChain、LangGraph 的区别是什么？

**参考答案：**

- LangChain：提供模型、Prompt、Retriever、Tool 等应用组件。
- LangGraph：用 StateGraph、节点、边、条件分支和 Checkpointer 编排复杂流程、循环和恢复。
- Function Calling：模型根据工具 Schema 选择函数并生成参数，是模型和应用之间的一种结构化调用能力。
- MCP：标准化外部工具、资源和提示能力的接入协议，包含工具发现和调用等机制。

在电商项目中，可以由 MCP Server 暴露客户、订单、物流和售后工具，应用层将工具 Schema 提供给 Agent，LangGraph 负责状态、审批和流程。MCP 不替代权限、幂等和业务校验；Function Calling 也不等于系统天然安全。

### 25. MCP 工具如何设计 Schema、参数校验和错误处理？

**参考答案：**

工具定义至少包含唯一名称、描述、输入 JSON Schema，可选输出 Schema 和副作用/风险信息。比如退款工具应明确 `order_id`、退款金额、原因、幂等键、单位和必填字段，输出包含 `status`、退款记录、业务错误码、是否可重试和 trace ID。

服务端必须再次完成类型、范围、资源存在性、权限、订单状态和幂等校验，不能只相信模型生成的参数。HTTP/协议成功不代表业务成功；工具结果要标准化为 `success/pending/failure/unknown`。参数错误通常修正或澄清，临时网络错误有限重试，权限/状态禁止立即终止或人工接管。

### 26. 如何保证退款、取消订单和地址修改不重复执行？

**参考答案：**

为每个写操作生成稳定幂等键，例如 `task_id + action_type + order_id + normalized_params_hash`，由业务服务持久记录并建立唯一约束。相同请求重复到达时返回第一次结果或当前处理中状态。执行前检查订单状态和已有操作记录；网络超时后先查询幂等键结果，再决定是否重试。

Redis 分布式锁只能减少并发，不能代替数据库唯一约束和支付/订单服务的幂等协议。地址修改还要使用版本号或条件更新，防止旧任务覆盖新地址。人工重复点击、模型重试、进程恢复和消息重复投递都要通过回归测试。

### 27. Multi-Agent 何时串行、并行或异步？

**参考答案：**

有数据依赖时串行，例如先鉴权和查询订单，再决定是否退款；互相独立的只读任务可并行，例如同时查询物流和检索售后政策；耗时长且不要求立即返回的批量审核可异步执行。

并行要设置每个 Agent 的 deadline、全局任务 deadline、并发信号量、部分成功策略和聚合规则。异步任务返回 `task_id`，状态和结果放持久化存储，前端通过轮询、SSE 或 WebSocket 获取进度；用户刷新后根据 task ID 恢复，不把任务绑定浏览器连接。

### 28. 多 Agent 结果冲突时如何处理？

**参考答案：**

先根据数据源权威性、时效、版本、权限和结果状态排序。订单状态、支付状态等关键事实以权威业务系统为准；知识库冲突按生效版本和制度优先级判断。如果两个可靠来源仍冲突，应保留差异、暂停高风险动作并转人工，不能让 LLM 随机选择。

聚合节点使用结构化 Schema 合并结果，校验必填字段、来源引用和安全条件。Review Agent 可以补充格式、事实和风险检查，但不能替代服务端权限和业务规则。

### 29. 子 Agent 是否允许继续调用其他子 Agent？

**参考答案：**

默认由 Orchestrator 统一调度，子 Agent 不允许无边界互调。自由互调会导致调用循环、权限扩散、预算失控和链路难排查。如果确实需要嵌套调用，应在白名单中声明能力、最大深度、超时、预算、输入输出 Schema 和 trace 传播。

例如商品审核 Agent 可以调用检索能力，但不应直接调用退款工具；售后 Agent 可以调用物流查询，但写操作仍必须经过审批和业务服务。能力按领域和最小权限划分，而不是给所有 Agent 全量工具。

### 30. 订单项目为什么使用显式 LangGraph Workflow，而不是完全自主 Agent？

**参考答案：**

订单处理有明确的节点、状态和副作用边界：需求理解、信息查询、知识检索、方案决策、工具执行和结果校验。退款、取消和地址变更还必须人工确认，因此显式图更容易表达“必须先查询”“未经审批不得写”“工具成功还要后验校验”等不变量。

模型仍可用于需求理解、Query 改写、方案生成和工具选择，但核心状态机、权限、幂等和完成条件由代码/业务服务控制。这样降低了 Prompt 膨胀和无限循环风险，也更容易做离线回放和线上审计。

### 31. 任务成功率提升约 18%，无效工具调用率降低约 25%，如何证明？

**参考答案：**

先定义成功：订单识别正确、必要信息完整、工具业务执行成功、最终状态校验通过且用户目标完成。基线应是同一人工标注复杂订单测试集上的旧流程，冻结模型、工具、数据、Prompt 和评价脚本。需要澄清“提升 18%”是相对提升还是百分点。

无效工具调用要有标注定义，例如参数错误、无权限、重复且无状态变化、明显不必要或最终未促进任务的调用。统计时区分“工具正确拒绝了业务请求”和“Agent 本不应调用”。报告样本数、按任务类型结果、失败原因、置信区间和总延迟，不能只报总数。

### 32. Agent 如何评估路由、工具和端到端效果？

**参考答案：**

按层评估：路由看 Accuracy、每类 Precision/Recall/F1、拒识、槽位正确率和人工改派；工具看 Schema 合法率、参数正确率、协议成功率、业务成功率、幂等冲突和重试后成功率；Agent 看子任务成功率、重规划率、循环率和人工接管率；端到端看任务完成率、错误执行率、P50/P95、TTFT、成本和投诉。

评测集必须覆盖正常、模糊、缺槽位、越权、工具超时、多意图、状态冲突和重复请求。修改 Prompt、模型、工具 Schema 或路由策略后，都要在冻结回归集上评测，并分层比较而非只看少数 Demo。

## 四、三个项目的纵向深挖题

### 33. 商品审核 Agent 的审核结论如何做到可追溯？

**参考答案：**

审核结果采用结构化格式，每条审核项包括规则 ID、结论、命中的商品事实、证据 Chunk ID、文档标题、章节、版本、页码和风险等级。RAG 返回的证据不只传一段文本，还要传稳定来源 ID。生成 Prompt 要求关键结论绑定证据，证据不足返回 `insufficient_evidence`。

生成后检查引用 ID 是否存在、是否属于当前用户可访问范围、版本是否当前生效、结论是否能被证据支持。高风险审核可通过规则引擎或人工复核。这样能够把“模型说不合规”追溯到具体规则和商品字段，而不是只有一句自然语言。

### 34. 商品型号含大量编码时，为什么要保留 BM25？

**参考答案：**

型号、SKU、规格和条款号通常是高信息量精确 Token。向量检索可能把近似型号当成相似语义，BM25 可以利用精确词面和稀有词 IDF。因此对型号做大小写、全半角、连字符和别名规范化，同时保留原始字段，以 BM25 精确匹配补充向量召回。

但 BM25 命中也不代表业务上是同一产品，还要结合类目、版本、权限和有效期过滤，必要时通过数据库查验产品 ID。评测中加入近似型号和旧版本负样本。

### 35. 订单状态与支付状态不一致时，Agent 怎么做？

**参考答案：**

不能直接根据一个状态决定退款或取消。先比较两个系统的来源、更新时间和最终一致性机制，查询支付流水、订单事件或对账接口。暂时同步延迟进入等待/轮询；确定性冲突进入异常队列或人工；只有状态和业务规则一致时才能执行高风险动作。

对用户明确说明订单状态、支付状态、数据时间和当前可执行动作。将冲突写入监控和对账系统，不能用无限重试掩盖系统一致性问题。

### 36. Redis、PostgreSQL 和 Checkpointer 如何协同？

**参考答案：**

Redis 适合短期会话摘要、任务中间状态和热点缓存；PostgreSQL 保存订单、客户、审批、处理记录和审计等长期事实；LangGraph Checkpointer 保存线程级图状态快照，用于暂停、恢复和故障恢复。三者通过 `task_id`、`thread_id` 和业务 ID 关联。

Redis 不应是唯一真相源；如果任务恢复依赖数据库，不能只使用进程内 MemorySaver。工具写操作的最终事实由业务数据库/服务确认，Checkpoint 只表示 Agent 走到哪一步，不代表外部副作用已经成功。

### 37. 如何实现知识库文档的增量更新和缓存失效？

**参考答案：**

使用稳定 `doc_id`、`version_id` 和内容哈希识别新增/修改/删除。新版本先完成解析、切分、向量化和索引，再抽样验证并原子切换 `active_version`；旧版本先软删除，保留回滚窗口后异步清理。

Redis 缓存 Key 需要包含规范化 Query、租户/权限摘要、过滤条件、检索配置和知识库版本。切换版本后新请求命中新 Key，旧缓存可异步删除。查询返回中记录索引版本，避免把缓存过期误当作当前知识。

### 38. TTFT 降低约 30%，如何拆解优化点？

**参考答案：**

先通过 Trace 分解排队、鉴权、路由、检索、工具查询、Prompt 构建、模型排队和首 Token 生成。针对电商系统可能的优化包括热点路由/检索缓存、独立只读工具异步并行、减少串行模型调用、缩短历史上下文、连接复用、模型预热和流式返回。

验证必须保持模型、并发、请求集、服务资源、超时、重试和缓存命中率一致，报告 P50/P95 TTFT 和命中/未命中分组。相对降低 30%与降低 30 个百分点不同；需要说明分母、时间窗口和样本量。

### 39. 订单自动处理率达到 70%+、人工介入率降低约 30%，如何防止以安全换效率？

**参考答案：**

先明确分母和范围：是常规查询与异常处理子集，还是全部订单；退款、取消、地址修改是否计入。按风险分层，低风险只读查询可自动化；中风险增加抽检或二次校验；资金和不可逆操作强制人工确认。

同时监控自动任务正确率、错误退款、投诉、异常漏检、人工抽检不合格率、人工转接和安全事件。早期可以影子模式只给建议不执行，再灰度放量。降低人工率不能单独作为成功指标。

## 五、横向扩展与纵向追问清单

### 40. 如果知识库规模扩大十倍，RAG 架构要改什么？

**参考答案：**

先做知识库、租户、产品和版本级路由，避免全库检索；按领域或租户分片，使用 Metadata Filter 和分层索引；召回候选与 Reranker 并发/批处理，控制候选和上下文预算。离线侧采用增量队列、幂等入库、索引构建和版本切换；在线侧增加缓存、限流、熔断、监控和容量压测。

不能只把向量库机器加大，还要检查 Embedding 生成吞吐、全文索引、对象存储、PostgreSQL 元数据查询和 Reranker GPU 是否成为瓶颈。

### 41. 如果 Agent 工具从几十个增加到几千个，如何组织？

**参考答案：**

不能把几千个工具全部暴露给模型。建立工具注册中心和业务域目录，记录名称、描述、Schema、版本、权限、风险、副作用、超时、幂等性和健康状态。先由路由层确定业务域和用户可用范围，再在域内选择少量候选。

工具接入要有契约测试、Schema 校验、灰度和回滚；高风险工具必须人工确认。模型看到的是能力摘要和有限工具，不是整个内部 API 清单。

### 42. Agent 与 RAG 如何协同？RAG Agent 为什么不能只返回答案？

**参考答案：**

RAG 是一种受控能力：文档、制度、产品规则问题调用 RAG；实时订单和库存调用业务工具；高风险执行调用受控写工具。RAG Agent 应返回片段、来源、版本、页码、相关性、检索状态和摘要，供 Orchestrator 判断证据是否足够并向用户展示引用。

召回为空、低置信或来源冲突时，应改写、澄清、拒答或人工，而不能把一个无来源答案传给主 Agent。主 Agent 也要把 RAG 证据和实时业务事实区分开，不能用旧文档覆盖当前订单状态。

### 43. 用户刷新页面后，如何继续一个正在执行的任务？

**参考答案：**

任务生命周期不能绑定浏览器连接。服务端创建稳定 `task_id`，将执行状态、Checkpoint、已生成阶段消息和最终结果写入持久化存储。前端刷新后用同一 task ID 重新鉴权，读取当前状态；若仍运行则轮询/SSE/WebSocket 订阅，若完成则直接返回结果。

对流式输出可保存递增 sequence 或事件 ID，重连时从最后确认位置续传；不能重复发送导致 UI 混乱。Task ID 仍需权限校验和过期机制，不能因为知道 ID 就读取他人订单结果。

### 44. 如果用户要求 Agent 直接执行高风险操作，系统怎么处理？

**参考答案：**

先确认用户身份、权限、目标资源和参数；查询当前状态与适用规则；展示动作摘要、金额/对象、依据和风险；在执行前暂停并进行人工或用户二次确认。恢复后重新读取最新状态，使用幂等键调用受控业务服务，执行后校验最终状态并记录审计。

“用户明确说了”不等于跳过权限和业务规则。模型只能建议或编排，不能成为最终授权主体。

## 六、通用面试问题及参考答案

### 46. 三个项目的职责有什么差异？

**参考答案：**

企业智能知识平台偏 RAG 全链路：数据解析、切分、Embedding、召回、精排、评测和 API；企业智能订单处理 Agent 偏单 Agent Workflow：节点流程、业务工具、状态、结果校验和人工确认；电商多智能体系统偏平台协作：Orchestrator、领域 Agent、MCP、路由、跨 Agent 状态和稳定性。

三者共通的方法是：把输入和输出结构化，把知识查询和实时业务查询分开，把副作用操作交给受控工具，把高风险动作放进审批节点，再用离线评测和线上 Trace 发现问题。

### 47. 讲一个最难定位的问题。

**参考答案模板：**

“我会选一个有完整证据链的问题。例如系统出现任务失败率升高，我先通过 trace_id 拆分路由、检索、模型、工具和数据库阶段，发现工具接口 HTTP 成功但业务状态没有真正完成，或者缓存命中了旧版本知识。之后把工具结果分成 success/pending/failure/unknown，增加最终状态查询和幂等键，或把知识库版本加入缓存 Key，并用回放集和线上指标验证。

这个回答需要补充真实项目中的现象、日志、根因、改动和前后指标，不能只说“重试解决了”。

### 48. 当效果不好但工期已到，如何处理？

**参考答案：**

先把“效果不好”拆成数据覆盖、召回、排序、生成、接口延迟还是需求变化。对已经承诺的低风险范围交付可用闭环，对高风险或证据不足的场景保留人工和明确拒答；用固定样例和量化指标对齐验收范围。

短期止血可以用 FAQ/规则、缓存、降级和人工工单；中期优化切分、混合召回、Reranker、Prompt 或工具校验；长期补充数据治理、评测集、监控和灰度。不能用放宽权限、减少校验或掩盖指标口径换取表面自动化率。

### 49. 你如何判断 Agent 功能是否适合落地？

**参考答案：**

看任务是否有明确目标和完成条件、数据源是否可信、工具边界是否可控、错误成本是否可接受、是否存在人工兜底、是否能做离线评测和线上观测。查询类和建议类通常比不可逆写操作适合先自动化。

上线前用回放集、影子模式和灰度验证质量、延迟、成本、安全和人工节省；高风险动作不因为模型准确率高就取消审批。

### 50. 你认为大模型应用最容易忽略什么？

**参考答案：**

最容易忽略的是业务闭环：很多系统只看答案是否流畅，却没有验证数据版本、权限、工具幂等、最终业务状态、失败恢复、引用、审计和回归评测。RAG 不能只看向量距离，Agent 不能只看 Tool Calling 成功。

我会把模型当作不完全可靠的决策组件，用可信业务数据、结构化 Schema、状态机、服务端权限、人工审批、结果校验、监控和降级机制把它约束在可验证范围内。

### 51. 你的技术短板是什么？

**参考答案模板：**

“我在模型训练底层和推理系统优化方面的深度还不如应用工程，过去更多负责 RAG、Agent、工具接入和 BERT 微调/模型调用。后续会通过复现 LoRA/量化实验、学习显存和吞吐分析、参与模型服务压测，把短板转化为可验证的项目产出。应用工程方面，我会继续加强评测、可观测性和生产治理。”

短板必须真实、可改善，并说明具体行动。不要回答“没有短板”，也不要把权限、安全和数据治理说成无关工作。

## 八、面试评分参考

### 1. 技术基础

- **较弱：** 能解释名词，但无法说明适用场景和边界。
- **合格：** 能解释 RAG、LangGraph、工具调用、状态和指标，并结合项目回答。
- **较强：** 能说明数据结构、错误分类、实验设计、性能瓶颈和安全边界。

### 2. 项目真实性

- **较弱：** 只复述技术栈和结果，无法说明个人代码和调试过程。
- **合格：** 能说明负责模块、流程、一个难点和验证方式。
- **较强：** 能画状态图，讲清 Schema、工具错误码、幂等、回滚、指标口径和线上排查。

### 3. 工程可靠性

- **较弱：** 认为模型输出正确或 HTTP 200 就代表任务成功。
- **合格：** 知道重试、降级、人工确认、缓存和日志。
- **较强：** 能区分协议成功/业务成功/用户成功，设计状态机、幂等、Checkpoint、权限和回放评测。
